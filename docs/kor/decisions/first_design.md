## 1. 프로젝트 개요

이 프로젝트는 사용자가 공유기 포트 포워딩을 직접 설정하지 않고도 멀티플레이 게임 서버에 접속할 수 있게 하는 **Windows 우선 P2P 가상 네트워킹 시스템**을 개발한다.

시스템은 참여 컴퓨터들 사이에 사설 가상 네트워크를 만든다. 각 클라이언트는 가상 IP 주소를 받고, 그 가상 주소로 보낸 게임 트래픽은 캡처되어 캡슐화된 뒤, 가능한 경우 직접 P2P 터널로 전송되어 원격 머신의 가상 네트워크 인터페이스에 주입된다.

실제 검증 대상은 **Minecraft Java Edition**이다. 프로젝트가 성공하면 플레이어는 수동 공유기 설정 없이 가상 IP 주소를 통해 다른 사용자의 컴퓨터에서 도는 Minecraft 서버에 접속할 수 있어야 한다.

프로젝트는 **직접 P2P 연결**을 최우선으로 한다. AWS는 게임 트래픽의 일반 경로가 아니라 피어 조율, 연결 메타데이터, 텔레메트리를 위한 **제어 평면**으로 주로 쓴다.

---

## 2. 문제 정의

가정용 네트워크에서 멀티플레이 게임을 호스팅하려면 보통 공유기 포트 포워딩 설정, 공인 IP와 사설 IP의 이해, 방화벽 규칙 수정, 또는 상용 가상 LAN 서비스 이용이 필요하다. 이런 요구사항은 일반 사용자에게 상당한 사용성 장벽이 된다.

이 프로젝트는 다음을 조합한 경량 사용자 공간 네트워킹 시스템이 플레이어 간 연결을 자동으로 수립할 수 있는지 조사한다.

- 가상 네트워크 인터페이스
- STUN 기반 공인 엔드포인트 발견
- NAT 통과
- UDP 홀펀칭
- P2P 터널링
- 클라우드 기반 피어 조율
- 네트워크 품질 측정과 진단

핵심 기술 과제는 실제 게임 트래픽을 가능한 한 직접 P2P 경로에 유지하면서 가상 LAN과 같은 경험을 제공하는 것이다.

---

## 3. 프로젝트 목표

### 주요 목표

1. **플레이 가능성**
   두 클라이언트가 패킷을 주고받을 수 있음을 증명하는 데 그치지 않고, 실제 멀티플레이 게임플레이를 지속적으로 지원해야 한다.

2. **직접 연결 우선**
   NAT 조건이 허용하는 한 게임 트래픽은 피어 간 직접 경로로 이동해야 한다.

3. **수동 포트 포워딩 불필요**
   일반 사용자가 지원 게임 세션을 호스팅하거나 참가할 때 공유기 포트 포워딩을 설정할 필요가 없어야 한다.

4. **가상 LAN 경험**
   사용자는 발견된 공인 엔드포인트를 직접 다루는 대신 가상 IP 주소로 통신해야 한다.

5. **관측 가능성**
   시스템은 연결 수립 결과와 관련 네트워크 성능 데이터를 기록해야 한다.

6. **진단 가능한 실패**
   실패한 연결은 STUN 실패, 후보 교환 실패, 홀펀칭 실패, 터널 실패처럼 단계별로 분류되어야 한다.

7. **게임 비종속 네트워킹 계층**
   Minecraft Java Edition을 첫 검증 대상으로 쓰지만, 터널 자체에는 Minecraft 전용 네트워킹 로직이 없어야 한다.

## 4. 초기 버전의 비목표

첫 버전은 한 학기 안에 달성 가능하도록 여러 기능을 의도적으로 제외한다.

- 상용 VPN 제품의 완전한 대체
- 대규모 공개 배포
- 자체 암호 알고리즘 개발
- 모바일 지원
- macOS 지원
- 고급 그래픽 사용자 인터페이스
- 1차 마일스톤에서의 완전한 ICE 구현
- 모든 NAT 구성에서의 연결 보장

직접 연결 작업이 충분히 일찍 끝나면 릴레이 폴백을 스트레치 목표로 추가할 수 있다.

## 5. 대상 플랫폼

프로젝트는 초기에 **Windows 환경**을 가정한다.

### 초기 목표

- Windows 10 / Windows 11
- x64
- C++20 클라이언트
- Windows 소켓 API
- Wintun을 통한 가상 네트워크 어댑터 (교수 승인 전제)

시간이 허락하면 나중에 Linux 지원을 추가할 수 있으나, Windows가 주 구현 및 시연 환경이다.

## 6. 제안 기술 스택

### 클라이언트 / 데이터 평면

**언어:** C++20

계획된 책임:

- UDP 소켓 관리
- STUN 클라이언트 구현
- 공인 엔드포인트 발견
- 피어 세션 관리
- NAT 홀펀칭
- 터널 패킷 프로토콜
- Keepalive와 연결 상태
- 가상 네트워크 어댑터 연동
- 가상 IP 라우팅
- 패킷 캡슐화 및 역캡슐화
- 텔레메트리 수집
- 진단

실용적인 범위에서 네트워킹 로직은 고수준 네트워킹 프레임워크 대신 네이티브 Windows API를 쓴다.

### Windows 네트워킹 API

사용 가능성이 있는 API:

- Winsock2
- `socket()`
- `bind()`
- `sendto()`
- `recvfrom()`
- `select()` 또는 `WSAPoll()`

### 가상 네트워크 어댑터

**계획된 의존성:** Wintun

Wintun은 Windows 가상 네트워크 인터페이스에 대한 접근만 제공한다. 프로젝트는 다음을 직접 구현한다.

- 피어 발견
- STUN 클라이언트 로직
- NAT 통과
- 홀펀칭
- 터널 프로토콜
- 라우팅 로직
- 세션 관리
- 모니터링
- 진단

CSP 400은 기본이 아닌 서드파티 라이브러리에 사전 승인을 요구하므로, Wintun은 프로젝트의 핵심 기술 기여가 아니라 교수 승인을 받은 인프라 의존성으로 취급한다.

### 제어 평면

**언어:** Python

초기 책임:

- 방 생성
- 방 참가
- 피어 등록
- 가상 IP 할당
- 엔드포인트/후보 교환
- 연결 메타데이터
- 텔레메트리 수집

첫 버전은 의도적으로 단순하게 유지한다.

가능한 초기 스택:

- Python 표준 라이브러리
- `socket`
- `asyncio`
- `json`
- `sqlite3`

고수준 웹 프레임워크는 필요성이 생기고 승인을 받은 뒤에 검토할 수 있다.

### 클라우드

**초기 배포 대상:** AWS EC2

첫 아키텍처는 다음을 쓸 가능성이 높다.

- EC2 인스턴스 1대
- Python 제어 서버
- SQLite 데이터베이스 또는 경량 영속 저장소

프로젝트의 핵심 기술 작업은 백엔드 웹 개발이 아니라 P2P 네트워킹이므로, 초기 클라우드 구성요소는 단순하게 유지한다.

```text
  -> 게임
```

## 8. STUN 범위

프로젝트는 초기에 완전한 STUN 서버가 아니라 **STUN 클라이언트**를 구현한다.

클라이언트는 다음을 수행한다.

1. STUN Binding Request를 구성한다.
2. 기존 STUN 서버로 UDP를 통해 요청을 보낸다.
3. Binding Response를 수신한다.
4. STUN 응답을 파싱한다.
5. `XOR-MAPPED-ADDRESS`를 디코드한다.
6. 클라이언트의 공인 IP 주소와 공인 UDP 포트를 알아낸다.

예시:

```text
로컬 엔드포인트:
192.168.1.10:50000

STUN으로 발견한 NAT 매핑:
73.12.34.56:42001
```

발견한 공인 엔드포인트는 AWS 제어 평면에 등록되어 다른 피어가 직접 연결을 시도할 수 있게 한다.

자체 STUN 서버 구현은 초기 범위가 아니지만, 유용한 실험 가치가 있다면 나중에 검토할 수 있다.

## 9. NAT 통과와 피어 연결

공인 엔드포인트 발견 후, 각 피어는 자신의 연결 정보를 AWS 제어 평면에 보낸다.

예시:

```text
Alice
가상 IP: 10.100.0.1
공인 엔드포인트: 73.x.x.x:42001

Bob
가상 IP: 10.100.0.2
공인 엔드포인트: 24.x.x.x:51032
```

제어 평면은 이 엔드포인트들을 피어 간에 교환한다.

이후 클라이언트들은 UDP 홀펀칭을 시도한다.

```text
Alice                              Bob
  |                                 |
  | ------ UDP packet ------------> |
  | <----- UDP packet ------------- |
  |                                 |
  +========= Direct P2P ============+
```

프로젝트는 완전한 ICE 명세를 즉시 구현하는 대신 최소한의 연결 수립 절차로 시작한다.

나중 버전에서는 호스트 후보, server-reflexive 후보, 연결성 검사, 릴레이 폴백 같은 ICE 개념과 자체 절차를 비교할 수 있다.

## 10. 가상 네트워크 설계

각 참가자는 프로젝트 네트워크 내의 가상 IP 주소를 받는다.

예시:

```text
호스트:     10.100.0.1
플레이어:   10.100.0.2
```

플레이어는 Minecraft에 다음을 입력해 원격 호스트에 접속할 수 있어야 한다.

```text
10.100.0.1:25565
```

가상 어댑터가 게임의 IP 패킷을 캡처한다. 클라이언트는 그 패킷을 프로젝트의 UDP 터널 프로토콜 안에 캡슐화한다.

개념적으로:

```text
Minecraft TCP 패킷
        |
        v
가상 네트워크 어댑터
        |
        v
원본 IP 패킷
        |
        v
프로젝트 터널 헤더 + IP 패킷
        |
        v
UDP
        |
        v
인터넷
```

원격 피어에서는 과정이 역순으로 진행되어 원본 IP 패킷이 가상 어댑터에 주입된다.

Minecraft Java Edition은 게임플레이에 TCP를 쓰지만, 원본 TCP 패킷이 터널 안에 실려 전달되므로 터널 자체는 UDP를 쓸 수 있다.

---

## 11. 터널 프로토콜

프로젝트 클라이언트 간 통신을 위해 작은 자체 패킷 헤더를 정의한다.

가능한 필드:

```cpp
struct TunnelHeader
{
    uint32_t magic;
    uint8_t  version;
    uint8_t  type;
    uint32_t peer_id;
    uint32_t sequence;
    uint16_t payload_length;
};
```

가능한 패킷 타입:

- `HELLO`
- `KEEPALIVE`
- `DATA`
- `PING`
- `PONG`

이 프로토콜은 터널링된 게임 패킷과 연결 품질 측정을 모두 지원할 수 있다.

---

## 12. 제어 평면 책임

제어 평면은 실제 게임 데이터 경로와 분리된다.

초기 연산에 포함될 수 있는 것:

```text
create_room
join_room
register_peer
register_candidate
get_peers
report_connection
report_telemetry
```

전형적인 연결 흐름:

```text
호스트가 클라이언트 실행
    -> AWS 접속
    -> 방 생성
    -> 가상 IP 수신
    -> STUN 실행
    -> 공인 엔드포인트 등록

플레이어가 클라이언트 실행
    -> AWS 접속
    -> 방 참가
    -> 가상 IP 수신
    -> STUN 실행
    -> 공인 엔드포인트 등록

AWS
    -> 피어 엔드포인트 교환

클라이언트
    -> UDP 홀펀칭 수행
    -> 직접 터널 수립
    -> 가상 네트워크 트래픽 시작
```

## 13. 텔레메트리와 분석

프로젝트는 연결 신뢰성과 네트워크 품질을 모두 평가할 수 있을 만큼의 데이터를 수집한다.

계획된 지표:

- 연결 수립 성공/실패
- 연결 수립 시간
- 왕복 시간 (RTT)
- 패킷 손실
- 지터
- Keepalive 실패
- 직접 연결 지속 시간
- 터널 처리량
- Minecraft 세션 안정성

가능한 테스트 환경:

- 동일 로컬 네트워크
- 가정망에서 다른 가정망
- 가정망에서 모바일 핫스팟
- 캠퍼스망에서 가정망
- 가용한 경우 서로 다른 NAT 거동

실패한 연결은 어느 단계에서 실패했는지도 기록해야 한다.

예시 분류:

```text
STUN_DISCOVERY_FAILED
CONTROL_PLANE_EXCHANGE_FAILED
HOLE_PUNCH_TIMEOUT
PEER_HANDSHAKE_FAILED
TUNNEL_DROPPED
```

## 14. 성공 기준

### 최소 성공 프로젝트

최소 허용 버전은 다음을 모두 보여야 한다.

1. Windows 머신 2대에서 프로젝트 클라이언트가 실행된다.
2. 두 머신 모두 자체 STUN 클라이언트로 사용 가능한 공인 엔드포인트를 발견한다.
3. 두 피어가 AWS 제어 평면을 통해 연결 정보를 교환한다.
4. 최소한 지원 NAT 환경에서 수동 포트 포워딩 없이 직접 UDP 연결을 수립한다.
5. 시스템이 직접 터널로 임의의 패킷 또는 애플리케이션 데이터를 전송한다.
6. 연결 상태와 기본 성능 데이터가 기록된다.

### 목표 성공 프로젝트

목표 버전은 추가로 다음을 보여야 한다.

1. Windows 머신 양쪽에 가상 어댑터가 올라간다.
2. 가상 IP가 할당된다.
3. IP 패킷이 P2P 터널로 라우팅된다.
4. 가상 네트워크 위에서 실제 Minecraft Java Edition 멀티플레이 세션이 성립한다.
5. 초기 연결 성공에 그치지 않고 지속적인 게임플레이가 유지된다.
6. 지연, 패킷 손실, 연결 시간, 세션 안정성이 측정된다.

### 스트레치 목표

- 직접 연결이 불가능한 피어를 위한 릴레이 폴백
- 암호화 및 인증된 피어 세션
- Windows 설치 프로그램
- 간단한 GUI
- 자동 재연결
- 한 가상 네트워크에 3자 이상
- UDP 기반 게임 검증
- Linux 상호 운용성

## 15. 개발 계획

개발 계획은 의도적으로 기술적 위험 순으로 정렬했다. 가장 이른 작업은 가상 어댑터나 사용자 인터페이스에 큰 시간을 들이기 전에 직접 P2P 연결이 가능함을 증명하는 데 집중한다.

### Phase 1: 핵심 UDP 네트워킹

**목표:** C++에서 기본 네트워킹 원시 기능을 갖춘다.

작업:

- CMake 기반 C++20 프로젝트 구조 생성
- Winsock 초기화 및 해제 구현
- UDP 소켓 래퍼 구축
- 엔드포인트 표현 구현
- 알려진 두 엔드포인트 간 UDP 패킷 송수신
- 기본 로깅 추가

산출물:

```text
Client A <------ UDP ------> Client B
```

---

### Phase 2: STUN 클라이언트

**목표:** NAT 뒤 클라이언트의 공인 UDP 엔드포인트를 발견한다.

작업:

- STUN 중 필요한 부분 학습
- Binding Request 패킷 구성
- 트랜잭션 ID 생성
- 공개 STUN 서버로 요청 송신
- Binding Response 파싱
- STUN 속성 파싱
- `XOR-MAPPED-ADDRESS` 디코드
- 발견된 공인 IP와 포트 출력
- 타임아웃 및 잘못된 응답 처리 추가

산출물:

```text
로컬 엔드포인트: 192.168.x.x:xxxxx
공인 엔드포인트: x.x.x.x:xxxxx
```

---

### Phase 3: AWS 조율 서버

**목표:** 피어들이 서로를 찾고 후보 정보를 교환하게 한다.

작업:

- 기본 Python 서버를 AWS EC2에 배포
- 방 생성 구현
- 방 참가 구현
- 피어 등록
- 가상 IP 등록
- 공인 엔드포인트 등록
- 피어 정보 교환
- 경량 방/피어 상태 저장

산출물:

서로 다른 네트워크의 두 클라이언트가 AWS 제어 평면을 통해 상대의 엔드포인트를 얻을 수 있다.

---

### Phase 4: UDP 홀펀칭

**목표:** 수동 포트 포워딩 없이 직접 P2P UDP 경로를 수립한다.

작업:

- 피어 핸드셰이크 설계
- 원격 엔드포인트로 연결 패킷 동시 송신
- 재시도 및 타임아웃 로직 추가
- 양방향 트래픽 확인
- Keepalive 패킷 추가
- `PING` / `PONG`으로 RTT 측정
- 성공 또는 실패 사유 기록

산출물:

```text
PC A <========== Direct UDP ==========> PC B
```

지원 환경에서 수동으로 설정한 공유기 포트 포워딩 없이 성립한다.

---

### Phase 5: 터널 프로토콜

**목표:** 프로젝트 패킷을 위한 안정적인 전송 계층을 만든다.

작업:

- 터널 패킷 헤더 정의
- 프로토콜 버전 추가
- 피어/세션 식별자 추가
- 패킷 타입 추가
- 시퀀스 번호 추가
- 직렬화/역직렬화 구현
- 손상 패킷 검증 추가
- `DATA`, `KEEPALIVE`, `PING`, `PONG` 구현

산출물:

두 피어 사이에 안정적인 애플리케이션 레벨 터널이 존재한다.

---

### Phase 6: Windows 가상 네트워크 어댑터

**목표:** 가상 인터페이스로 IP 패킷을 캡처하고 주입한다.

작업:

- Wintun 의존성 승인 획득

- 가상 IP 주소 할당
- 어댑터에서 패킷 읽기
- 어댑터로 패킷 주입
- 필요한 Windows 라우트 설정
- 게임 테스트 전에 간단한 IP 도구로 트래픽 검증

산출물:

```text

```

### Phase 7: 가상 어댑터와 P2P 터널 통합

작업:

- 원본 IP 패킷을 Wintun에 주입
- 패킷 크기 한계 처리
- 카운터와 진단 추가

산출물:

두 Windows 머신이 가상 IP 주소만으로 통신할 수 있다.

**목표:** 실제 멀티플레이 세션을 시연한다.

## 17. 위험 관리

### 위험 1: 모든 네트워크에서 NAT 홀펀칭이 동작하지는 않는다

완화:

- 상위 계층을 쌓기 전에 조기 테스트
- NAT 관련 실패를 숨기지 않고 기록
- 릴레이 폴백을 가능한 후속 해법으로 취급
- 지원/미지원 네트워크 조건을 명확히 정의

### 위험 2: Windows 가상 네트워킹이 예상보다 복잡하다

완화:

- 가상 어댑터 작업을 NAT 통과 작업과 분리
- 먼저 일반 애플리케이션 데이터로 직접 P2P 검증
- Wintun은 가상 인터페이스 접근에만 사용
- 라우팅 로직은 프로젝트가 통제

### 위험 3: 프로젝트 범위가 너무 커진다

완화:

우선순위 순서:

```text
P0: UDP + STUN + 엔드포인트 교환 + 홀펀칭
P1: 직접 피어 세션 + 터널 프로토콜
P2: Wintun + 가상 IP + Minecraft
P3: 텔레메트리 + 진단 + 분석
P4: 암호화 + 릴레이 + GUI + 추가 플랫폼 지원
```

핵심 P2P 네트워킹 목표를 훼손하기 전에 낮은 우선순위 기능부터 제거한다.

### 위험 4: 서드파티 라이브러리 제약

완화:

- Wintun이나 기타 비기본 의존성을 쓰기 전에 승인 요청
- 프로젝트의 핵심 네트워킹 알고리즘은 해당 의존성과 독립적으로 유지
- 승인된 각 라이브러리가 제공하는 바를 정확히 문서화

## 21. 한 문장 프로젝트 정의

## 22. 과목 연계

이 기획서는 컴퓨팅 솔루션의 구현, 비교와 분석, 기술 요구사항을 향한 반복, 측정 가능한 결과의 발표를 강조하는 CSP 400의 방향에 맞춰 의도적으로 구성했다. 개발 계획 또한 과목의 대략적인 5주, 10주, 15주차 마일스톤 구조를 따른다.

프로젝트는 소스 관리와 주간 개발 기록을 유지한다. 비기본 서드파티 라이브러리, 특히 Wintun의 사용은 통합 전에 교수 승인을 요청한다. AI 도구가 코드나 문서 작성을 도운 경우, 생성된 자료는 과목 정책에 따라 테스트, 이해, 검증, 출처 표기를 거친다.

## 23. 즉시 다음 단계

첫 구현 스프린트는 가장 위험도 높은 네트워킹 경로에만 집중해야 한다.

```text
C++ UDP 소켓
    -> STUN Binding Request
    -> 공인 엔드포인트 발견
    -> AWS 엔드포인트 교환
    -> UDP 홀펀칭
    -> 직접 양방향 피어 통신
```

이 경로가 안정적으로 동작한 뒤에야 Wintun과 Minecraft 트래픽 터널링으로 넘어가야 한다.

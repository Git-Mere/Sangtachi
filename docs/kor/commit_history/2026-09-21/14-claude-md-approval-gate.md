# 2026-09-21 CLAUDE.md 규칙 추가에 승인 절차를 둔다

`CLAUDE.md` 에 **새 규칙**을 넣을 때 저장소 소유자의 허락을 먼저 받도록 했다. 낡은 사실
수정과 현재 상태 갱신은 허락 대상이 아니다.

## 변경

`CLAUDE.md` 에 두 문단이다. 승인 절차 자체와, 그 절차를 처음 통과한 규칙 하나다.

**이 기록의 인용 블록은 전부 요약이다.** 전문은 `CLAUDE.md` 에 있고 여기에 옮겨 적지 않는다
(규칙 5).

**1. `규칙` 절.**

> 이 파일에 규칙을 새로 넣을 때는 저장소 소유자에게 먼저 허락을 받는다. 하위 에이전트의
> 동의나 크로스 모델 리뷰의 `LGTM` 은 허락이 아니다. 무엇을, 어느 절에, 무슨 근거로 넣을지
> 묶어서 제안하고 승인된 것만 적는다. 승인받지 못한 관찰은 `commit_history/` 에만 남긴다.
> 낡은 사실을 고치는 것과 현재 상태를 갱신하는 것은 허락 대상이 아니다.

**2. `코드 작업 시` 절.** 아래 "첫 적용" 에서 승인받은 규칙이다.

> 프로세스를 시작했다고 말하기 전에 핸들 상태를 확인한다. 그리고 한 셀에 편집, 상태 변경,
> 프로세스 시작을 같이 넣지 않는다. 앞줄에서 예외가 나면 뒷줄이 조용히 사라진다.

## 결정

**허락 범위를 그었다.** 긋지 않으면 "시험 수 105 -> 109" 같은 명백한 오류 수정까지 막힌다.
그러면 파일이 낡은 채로 고정되고, 정확하게 유지할 의무와 교착한다. 규칙을 **새로 만들거나
뜻을 바꾸는 것**만 승인을 받는다.

**승인자를 명시했다.** 처음에는 "허락을 받는다" 로만 적었다. 누구의 허락인지 없으면 하위
에이전트의 동의나 리뷰어의 `LGTM` 을 허락으로 읽을 수 있다. 크로스 모델 리뷰가 잡았다.

## 왜 필요한가

앞 커밋 `834bfab` 에서 세션 교훈을 규칙으로 적으면서 **두 번 어겼다.** 새 규칙 하나가
과장이었고("리뷰어는 diff 밖을 보지 않는다" — 거짓이다), 다른 하나는 기존 규칙의 중복이었다.
리뷰가 둘 다 잡았지만 소유자가 먼저 봤으면 더 빨랐다. 한 세션의 인상이 검토 없이 영구
규칙이 되면 다음 세션이 틀린 규칙을 그대로 따른다.

## 세션을 넘어서도 유지한다

`CLAUDE.md` 는 이 저장소에만 있다. 같은 동작이 다른 저장소에서도 필요하므로 에이전트의 전역
정책으로도 남겼다. 제안할 때 **무엇을 / 어느 절에 / 무슨 근거로** 셋을 함께 내고, 근거는 그
세션에서 실제로 밟은 사건이어야 한다. 일반론은 근거가 아니다.

## 작업 중 두 번 틀렸다

**1. 전역 항목이 저장 안 된 줄 알았다.** 조회가 빈 목록을 돌려줬기 때문이다. 실제로는 그
API 의 기본값이 로컬만 보는 것이었고 전역은 인자를 줘야 보인다. **조회 실패와 "없음" 을
구분한다** 는 `windows-prereq.md` 0장의 규칙이 여기서도 통했다.

**2. 시작하지 않은 리뷰를 시작했다고 보고했다.** 한 셀에 편집, 상태 변경, 프로세스 시작을
같이 넣었는데 두 번째 줄에서 예외가 났다. 뒤의 네 줄이 전부 실행되지 않았고 리뷰 핸들은
만들어진 적이 없다. 그런데 "2라운드 돌리고" 라고 적었다. **핸들 상태를 확인하지 않고 의도를
결과처럼 말했다.** 소유자가 "지금 돌리고 있는거야?" 라고 물어서 드러났다.

# Phase 4 4차 J2·J3: 로컬 후보 연결, 랑데부와 로비 통합

## 왜 했나

Phase 4 4차 J 의 나머지다. 1~3차가 세션, 수신 파이프라인, 라우팅 표, `ROSTER` 를 만들었지만 제품 경로에는 세션을 여는
자리가 없었다. 이 커밋이 제어 평면의 랑데부(`control_plane.md` 8.4 의 6~10번, `protocol.md` 10.2)를 세션에 잇고, 세션의
결과를 로비(`concurrency.md` 7장)와 J1 의 로컬 기록 파일(`architecture.md` 9장)에 잇는다. 이것으로 같은 기기의 두 프로세스가
방을 만들고 펀치해 `CONNECTED` 에 닿고, 기록 파일에 수립 줄과 종료 줄이 남는다.

J2(로컬 후보 수집 연결)와 J3(통합)는 처음에 따로 커밋하려 했다. 둘이 `Lobby` 와 `ControlRunner` 의 같은 자리를 고쳐 한
커밋으로 합쳤다.

## 중요한 결정

**착수 전에 저장소 소유자가 해석 넷을 승인했다.** 그중 둘은 문서에 자리가 없어 위 표대로 문서에 먼저 적었다.

1. 호스트 쌍의 시도는 준비 응답을 보고 세션을 연 때 생긴다. 펀치 지연 중에 끝나도 수립 줄이 하나 있다
2. 호스트는 방을 세우기 전(`register_candidate` 성공 전) 응답의 준비 쌍으로 세션을 열지 않는다
3. 로비로 가는 계기는 모두 방을 떠나는 것이다. 그때 남긴 종료 세션까지 지운다(`protocol.md` 5.6)
4. `Lobby` 는 순수 코드로 두고 세션 전이를 입력으로, 세션 열기·방 떠나기·명부·기록 줄을 행동으로 주고받는다

**세션 전이는 그 자리에서 처리하지 않는다.** 터널의 전이 콜백은 세션의 메서드 안에서 불린다. 거기서 `Lobby` 의 반응
(`LeaveRoom`)을 하면 지우는 중인 세션을 다시 만진다. 실행기가 값을 베껴 큐에 넣고, `[loop]` 이 터널을 부른 뒤마다
`flush` 한다. 실행기 자신이 행동하다 생긴 전이는 그 행동 목록 뒤에 처리한다.

**기록 줄은 세션이 있었는지로 나눠 쓴다.** 세션 없이 끝난 시도는 `Lobby` 가, 세션이 있는 쌍은 실행기가 그 세션의 전이로
쓴다. 결과 값은 `record_result` 의 표다(`architecture.md` 9장 결과 값).

**문서가 정하지 않은 작은 것은 코드가 정했다.** `lobby.hpp` 와 `runner.hpp` 의 표에 근거와 함께 있다. 펀치 지연이 0 이하면
타이머 없이 바로 펀치, 방을 세운 호스트의 모든 제어 평면 실패(요청 큐가 참, 응답 불일치 포함)는 방이 서버에서 끝난 것과
같이 다룬다, 쌍은 그 방에서 한 번만 연다, 종료 이벤트는 요청도 `LeaveRoom` 도 내지 않는다.

**문서와 어긋난 문장 하나를 고쳤다.** 코드의 `CONTROL_PLANE_EXCHANGE_FAILED` 문장이 `architecture.md` 8장 표의 마지막 문장
"방에 같은 이름이 있으면 다른 이름을 쓰세요." 를 빠뜨리고 있었다. 표가 출처라 코드를 표에 맞췄다.

| warn. 전이와 `flush` 가 같은 시각이라 `flush` 때 시계로 재는 구현이 통과한다 | 반영. 전이와 `flush` 사이에 시계를 민다 |

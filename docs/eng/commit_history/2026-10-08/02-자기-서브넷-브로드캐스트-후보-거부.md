# Reject Own-Subnet Broadcast in Received Candidates (ADR 0018)

## Why

Found during the ADR 0017 review. Received candidate hygiene judged broadcast as `255.255.255.255` only, so
if the peer or a malicious server put our LAN's directed broadcast in as a candidate, `HELLO` went to our
whole LAN during the punch. ADR 0017 created the own-subnet set, so the input to judge it exists. The
repository owner decided to put it in the rules now.

## Important decisions

- **The server does not apply this row.** The server has no set, and the 10.1 reason for not sending the
  prefix to the server still holds
- **Client code is not changed now.** The own-subnet set, the input to the decision, comes from Phase 4
  local candidate collection. Recorded under places to revisit during implementation in `plan.md`

## Verification

| What | Result |
|------|------|
| Case table | A script implementing the rule computed the 5 rows and matched the document |
| Mutants | No row, rejecting the whole subnet, taking the netmask too wide, rejecting last octet 255. All four were caught by at least one row |
| Scenario trace | A player registers from `192.168.0.10/24`, and the `get_peers` response carries a peer candidate `192.168.0.255:5000` and a reflexive candidate. Step 8 hygiene of 8.4 rejects the former and `HELLO` goes only to the reflexive candidate. The server stored that candidate |
| Document gate | `docgate.py` `VERDICT: pass` |

# Phase 9 첫 두 환경의 분석과 대시보드 대조

## 왜 했나

소유자가 CloudWatch 대시보드를 만들었고, AWS CloudShell 에서 `tools/tm-analysis` 를 돌려 결과를 넘겼다. 이 PC 와 인스턴스 역할은 텔레메트리 테이블을 읽지 못한다. `roadmap.md` Phase 9 검증의 "대시보드의 `SetupTime` 과 `Rtt` 백분위수를 분석 스크립트의 값과 한 번 대조" 를 했다.

## 무엇을 했나

| 무엇 | 결과 |
|------|------|
| 분석 도구 | 소유자가 CloudShell 에서 `--save` 로 돌렸다. 레코드 82개, 어느 묶음에도 들지 않은 시도 0. 이 PC 에서 `--load` 로 같은 레코드를 다시 돌려 출력이 바이트 단위로 같았다 |
| CloudWatch 값 | 인스턴스 역할의 `GetMetricStatistics` 로 21:55~22:55 UTC 의 지표 열 개를 1분 해상도로 받았다. 같은 역할로 환경마다 묶음 범위 전체를 한 기간으로 묶은 백분위수도 받았다 |
| 대시보드 정의 | git 이 무시하는 `tools/tm-analysis/local/dashboard.json`. 소유자가 콘솔에서 만들었다 |

## 분석 결과

| 환경 | 성공/시도 | 플레이어 수립 시간 중앙값 | RTT 중앙값 (사분위 범위) | 지터 중앙값 | 손실 |
|------|-----------|---------------------------|--------------------------|-------------|------|
| 동일 LAN | 10/10, Wilson 95% 72.2~100.0% | 10796.5ms | 12.4ms (9.6~17.1), n=119 | 2.1ms | 0/350 |
| 가정망 대 모바일 핫스팟 | 10/10, Wilson 95% 72.2~100.0% | 10250.5ms | 111.0ms (96.2~132.1), n=117 | 6.9ms | 8/359 (2.23%) |

- 두 환경 모두 플레이어와 같은 방 호스트의 `stun_same_endpoint` 가 `true` 다
- 통제된 실패 두 건은 따로 집계됐다. `HOLE_PUNCH_TIMEOUT` 1, `STUN_DISCOVERY_FAILED` 1. 가짜 호스트는 API 로만 만들어 호스트 레코드가 없으므로 짝지은 표에서 "짝 없음" 이다
- 호스트 수립 시간 중앙값은 두 환경 모두 약 6.2초다. 기점이 달라 플레이어 값과 비교하지 않는다(`architecture.md` 9장)

## 대조

| 환경 | 값 | CloudWatch | 분석 도구 |
|------|----|------------|-----------|
| 동일 LAN | `SetupTime` p50 | 10769.1ms | 10796.5ms |
| 동일 LAN | `Rtt` p50 | 12.3ms | 12.4ms |
| 가정망 대 핫스팟 | `SetupTime` p50 | 10158.6ms | 10250.5ms |
| 가정망 대 핫스팟 | `Rtt` p50 | 111.6ms | 111.0ms |

환경마다 두 쪽의 표본 수가 같다. `SetupTime` 은 둘 다 10, `Rtt` 는 동일 LAN 119, 핫스팟 117 이다. 차이는 1.1% 안이다(동일 LAN `Rtt` 가 가장 크다, 12.26ms 대 12.4ms). CloudWatch 의 백분위수는 근사이고 분석 도구는 정렬 후 선형 보간이라 같은 표본에서도 값이 조금 다르다. `roadmap.md` 대로 `experiments.md` 의 숫자는 분석 도구의 것을 쓴다.

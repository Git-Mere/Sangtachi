# 0005. The console client left a delay warning at logoff

- Status: Unresolved
- Found: 2026-10-31
- Related: [`../concurrency.md`](../concurrency.md) chapter 7 Shutdown,
  [`../commit_history/2026-10-31/01-phase-8-같은-기기-확인-결과.md`](../commit_history/2026-10-31/01-phase-8-같은-기기-확인-결과.md),
  [`../commit_history/2026-11-01/03-콘솔-로그오프-지연-경고-정리.md`](../commit_history/2026-11-01/03-콘솔-로그오프-지연-경고-정리.md)

## Symptom

In the Phase 8 same-machine check, the user logged off with a GUI host and a console player (Release, `--no-adapter`) running on one machine.

- System log `winsrvext` 100: `sangtachi_client.exe is delaying system shutdown after 5000 milliseconds`
- The player log has no `attempt.end reason=shutdown`. The session ended with the host's `CLOSE`

On 2026-10-01 a Debug console left the same event. So we suspected the console had not cleaned up as
[`concurrency.md`](../concurrency.md) chapter 7 Shutdown says.

## Investigation

| Suspected | Seen | Judgement |
|-----------|------|-----------|
| The console did not run `shutdown()` at logoff. There is no `attempt.end reason=shutdown` | The player received the host's `CLOSE` first, wrote `attempt.end reason=closed`, and went to the lobby. `Lobby::on_shutdown` does not write that line in the lobby. After it come 62 process counter lines with no `peer_id`, which is step 4 of `shutdown()`. The log of another `--no-adapter` player that ended normally ends the same way | No. `shutdown()` ran |
| End of standard input ended the process | `run_console_reader` only stops reading at the end of standard input; it does not start shutdown | No. The console control handler is taken to have signaled the shutdown event |
| Loading user32 or gdi32 kept the handler from being called. The `SetConsoleCtrlHandler` documentation says the handler is not called for the logoff and system shutdown signals in that case | The executable's static imports have no user32 or gdi32. user32 appears only as a delay import of ADVAPI32. The 24 modules of a Debug console started in the `--no-adapter` lobby have neither | Not supported by the inspected evidence. The modules the Release process actually loaded at that logoff were not checked |

The `HandlerRoutine` documentation says only services receive `CTRL_LOGOFF_EVENT` and interactive programs are terminated before it at logoff.
If so, the signal that started this shutdown may have been `CTRL_CLOSE_EVENT` from the console closing rather than `CTRL_LOGOFF_EVENT`. The handler
does not log which signal it received, so this cannot be told apart. The documentation sources are
[HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine) and
[SetConsoleCtrlHandler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler).

## Cause

**Confirmed.** At logoff the console player ran `shutdown()`. The process counter output in the log is the evidence.

**Unknown.** Whether the handler received `CTRL_LOGOFF_EVENT` or `CTRL_CLOSE_EVENT`, and why `winsrvext` 100 raised the delay warning after 5000 milliseconds. How long it actually delayed is also unknown. The log
lines carry no time, so this log cannot tell them apart.

## Handling

No further investigation. This is the repository owner's decision. Only the GUI ships, and the console's cleanup ran. No code or
specification changed.

The way to look again is to log which signal the handler received and log off with only the console running.

## Result

The console logoff investigation item was removed from `plan.md`. Host shutdown at logoff is measured through the GUI build's
`WM_ENDSESSION` path. That work belongs to `plan.md`.

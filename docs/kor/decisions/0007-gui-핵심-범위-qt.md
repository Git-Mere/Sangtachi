# 0007. 최소 GUI 를 핵심 범위로 올리고 Qt 를 쓴다

- 상태: 채택
- 날짜: 2026-09-28
- 관련: [`../spec.md`](../spec.md) 범위·FR-15·NFR-5·C-5, [`../roadmap.md`](../roadmap.md) Phase 8, [`../architecture.md`](../architecture.md) 3.1·11장·12장

## 맥락

지금까지 GUI 는 범위 밖이었다. `architecture.md` 12장이 "**GUI**: 콘솔 전용." 로 적었고,
`spec.md` 는 "고급 GUI" 를 제외에, "간단한 GUI" 를 스트레치 목표에 두었다. 우선순위 등급은
P4 였고, C-5 가 범위 초과 시 하위 등급부터 제거하라고 정했으므로 **가장 먼저 잘리는 자리**였다.

저장소 소유자가 최종 제품 형태에 GUI 를 포함한다고 정했다. 소유자가 말한 동작은 셋이다.
방 코드 입력으로 참가하고, 참가하면 가상 IP 가 부여되고, **어떤 사용자의 연결이 끊기면
다른 사용자 화면에서도 그 사용자가 나간 것으로 보인다.**

앞의 둘은 계약이 이미 있다. `control_plane.md` 4.2 `create_room` 과 4.3 `join_room`, 2.5
가상 IP 풀이 그것이다. **셋째를 만들 장치가 설계에 없다.** 피어 상태는 `joined` 와
`registered` 둘뿐이고 둘 다 연결 여부가 아니다(`control_plane.md` 5.3). 이 ADR 은 그 장치를
정하지 않는다. 범위와 등급과 툴킷만 정한다.

## 결정

**최소 GUI 를 핵심 범위로 올린다.** 여섯을 이 결정에 포함한다.

**1. "간단한 GUI" 를 스트레치 목표에서 뺀다.** `spec.md` 의 제외 목록에 있는 **"고급 GUI" 는
그대로 둔다.** 올리는 것은 최소 GUI 뿐이다.

**2. 최소 GUI 의 범위는 다섯 동작이다.** `spec.md` FR-15 가 그 목록을 갖는다. 방 만들기와
방 코드 표시, 방 코드 입력과 참가, 멤버 목록과 각 멤버의 연결 상태, 실패 시 단계별 코드 표시,
창 닫기로 종료다. 설정 화면, 로그 뷰어, 테마, 설치 마법사, 통계 화면은 범위 밖이다.

> **왜.** 범위를 적지 않으면 "핵심 범위" 에 경계가 없다. `spec.md` 는 판정 기준을 적는
> 문서이므로 무엇이 들어오고 무엇이 아닌지를 목록으로 둔다.

**3. 등급은 P2 다.** P2 가 "Wintun + 가상 IP + Minecraft + 최소 GUI" 가 되고 P4 는 "암호화 +
릴레이 + 추가 플랫폼" 이 된다. **대가를 같이 적는다.** P2 를 버릴 때 사라지는 것 목록에
FR-15 와 T-7 이 들어가므로, 범위를 넘으면 GUI 가 Minecraft 검증과 함께 통째로 잘린다.
중간 단계는 없다.

**4. 구현은 Phase 8 에 흡수한다.** 새 Phase 를 만들지 않는다. Phase 8 이 시연이고 시연을
GUI 로 하는 것이 자연스럽다. 새 Phase 를 넣으면 Phase 9 가 밀리고 문서 전체의 Phase 참조를
고쳐야 한다.

**5. 최소 성공 기준 M-1 ~ M-6 에 넣지 않는다.** 대신 목표 성공에 T-7 을 새로 둔다.

> **왜.** M 은 직접 연결이 성립한다는 증명이고 명령줄로 판정할 수 있다. M 에 GUI 를 넣으면
> 창이 뜨지 않는 것만으로 최소 성공이 실패가 된다.

**6. 툴킷은 Qt 다.** `spec.md` NFR-5 의 제품 의존성이고 **교수가 승인했다.** 그 전달은
저장소 소유자로부터 왔고 근거는 이 커밋의 기록이다. NFR-5 의 승인 목록이 셋에서 넷이 된다.

### 이 ADR 이 정하지 않는 것

- **GUI 가 어느 스레드에서 도는가.** Qt 는 자기 이벤트 루프를 갖고 `concurrency.md` 1장
  스레드는 `[loop]` 를 프로세스 주 스레드로 정했다. 둘 중 하나가 양보해야 한다. 정하는
  시점은 `roadmap.md` Phase 8 의 착수 전 항목이다
- **멤버의 연결 상태를 무엇이 나르는가.** 위 맥락에 적은 셋째 동작이다. `get_peers` 응답은
  연결 여부를 담지 않고([`../control_plane.md`](../control_plane.md) 4.5), 터널 메시지 타입은
  `0x01`~`0x07` 이다([`../protocol.md`](../protocol.md) 5장). [ADR 0006](0006-무중계-스타-토폴로지.md)의
  같은 미결 항목과 **하나의 질문**이다
- **GUI 가 쓰는 기동 입력 경로.** 지금 입력은 CLI 인자뿐이고 방 코드와 재참가 증명이 표준
  출력이다(`architecture.md` 3.5). 창에서 받는 값을 어디에 두는지는 Phase 8 에서 정한다
- **Qt 승인의 범위.** 어느 버전인지, 링크 방식과 라이선스 조건이 승인에 포함됐는지는
  전달받지 않았다

## 대안

**대안 1. Win32 API 직접.**
버렸다. 저장소 소유자의 결정이다. NFR-5 승인이 필요 없고 이미 Winsock2 와 Wintun 으로 Win32 를
쓰므로 빌드 구성이 바뀌지 않는다는 장점이 있었다. 버린 이유는 목록 컨트롤과 대화상자를 직접
다루는 분량이다.

**대안 2. 웹뷰 + HTML.**
버렸다. 화면을 만들기는 쉬우나 런타임 의존성과 설치 전제가 늘고, 그것 역시 NFR-5 승인
대상이다. 승인 비용이 Qt 와 같으면서 배포 전제가 하나 더 붙는다.

**대안 3. 스트레치로 둔다.**
버렸다. 저장소 소유자의 결정이다. 이 대안의 장점은 문서를 하나도 고치지 않는 것이었고,
대가는 C-5 에 따라 범위를 넘는 순간 GUI 가 사라지는 것이다.

## 결과

**얻는 것.**

- 사용자가 명령줄 인자 없이 방을 만들고 참가한다. T-7 이 그것을 판정한다
- 범위가 목록으로 고정된다. "GUI 를 더 좋게" 라는 요구가 들어올 자리가 FR-15 밖으로 밀린다
- 시연이 하나로 끝난다. Phase 8 이 Minecraft 세션과 GUI 를 같은 자리에서 보인다

**치르는 것.**

- **제품 의존성이 하나 는다.** 배포물에 Qt 런타임이 붙는다. `windows-prereq.md` 에 실행 전제가
  하나 늘어날 수 있다. 그 크기는 아래 "확인하지 못한 것" 이다
- **P2 의 부피가 는다.** 같은 등급 안에 Wintun, 가상 IP, Minecraft 검증, GUI 가 함께 있다.
  범위를 넘으면 넷이 같이 잘린다
- **스레드 모델이 미결로 남는다.** 그 결정 전에는 `concurrency.md` 가 GUI 를 다루지 않는다
- **멤버 연결 상태를 나르는 장치가 아직 없다.** FR-15 의 셋째 동작과 T-7 의 마지막 조건이
  그 장치에 달려 있다. ADR 0006 의 미결 항목과 같은 질문이고, **정하지 않으면 T-7 을 판정할
  수 없다**

**확인하지 못한 것.**

- Qt 승인의 범위. 위 "이 ADR 이 정하지 않는 것" 에 적었다
- Qt 런타임의 배포 크기와 절차. `windows-prereq.md` 에 무엇이 추가되는지는 Phase 8 에서 확인한다
- Qt 이벤트 루프와 `concurrency.md` 의 단일 소유 규칙이 부딪히는지. 실제로 써 보기 전에는
  확인할 수 없다

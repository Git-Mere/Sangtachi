## 3. Windows 사전조건 절

**문제.** 문서 어디에도 실행 전제가 없다. 시연 PC에서 처음 돌릴 때 막힌다.

| 다룰 것 | 근거 |
|---------|------|
| 관리자 권한. 어댑터 생성과 라우트 설정에 필요 | blocker 11 |
| 방화벽. 새 어댑터가 Public 프로필로 분류되어 ICMP와 TCP 25565 인바운드 차단. 클라이언트 UDP도 첫 실행 프롬프트에 의존 | blocker 12 |
| 비정상 종료 후 잔존 어댑터/주소/라우트 정리와 재실행 시 중복 생성 방지 | blocker 13 |
| Wintun DLL/드라이버 패키징, 아키텍처(x64), 서명 | blocker 14 |
| `server.properties`의 `server-ip`가 다른 인터페이스 주소면 `10.100.0.1:25565` 접속 거부. 비워 두거나 `10.100.0.1`로 명시 | blocker 15 |
| EC2 보안 그룹 인바운드, 바인드 주소(`127.0.0.1` 금지) | blocker 16 |
| `10.100.0.0/24`가 실제 LAN, Hyper-V, 다른 VPN과 충돌할 때의 탐지와 대체 대역 | blocker 17 |
| on-link `/24` 라우트가 이미 생성되어 중복 생성 오류 | warn |
| 주소가 tentative 상태일 때 시험을 시작하면 간헐 실패 | warn |
| EC2 재시작 시 공인 IP 변경. Elastic IP 또는 DNS | warn |
| Minecraft LAN 탐색은 멀티캐스트라 유니캐스트 터널로 안 된다. 직접 IP 입력으로 우회 | warn |
| Java 업데이트로 경로 기반 방화벽 예외 무효화 | warn |
| SmartScreen/Defender가 미서명 클라이언트를 격리 | warn |

**사용성 한계도 함께 다룬다.** `spec.md`의 주장은 "수동 포트 포워딩 없이"이고 그 주장은
유지된다. 다만 대신 관리자 권한, 드라이버 설치, 방화벽 규칙이 필요하다. 설정 부담이 사라진
것이 아니라 종류가 바뀌었고, 포트 포워딩보다 쉬운지는 별도 논증이 필요하다. 보고서에서
정직하게 서술한다.

**검증.** 지금 시점에 실제 PC로 끝까지 가볼 수는 없다. Phase 1은 CMake 구성만 되어 있고
Winsock2 래퍼부터가 미착수다. 그래서 검증은 문서 자체에 대해 한다.

- 위 13개 항목이 각각 하나의 절을 갖는다
- 각 절에 확인 명령과 **기대 출력**이 있다 (`ipconfig`, `route print`, `netsh advfirewall`,
  `Get-NetAdapter`, `Get-NetFirewallProfile`). 명령만 있고 무엇을 보면 통과인지 없으면 미완
- 자동 처리와 수동 처리를 구분해 표시한다. 클라이언트가 하는 것과 사람이 미리 해둬야 하는 것

초기화된 PC에서의 실제 종단 검증은 Phase 8 시연 시점 기준이며 이 항목의 완료 조건이 아니다.

## 4. spec 논리 오류 수정

| 다룰 것 | 근거 |
|---------|------|
| C-5 우선순위가 최소 산출물을 지키지 못한다. P1을 버리면 M-5가 사라지고 P3을 버리면 M-6과 과목 요구 분석이 함께 사라진다. Phase 1~9 안에서 실제로 버릴 수 있는 것은 P2(Wintun + 가상 IP + Minecraft, Phase 6~8)뿐이다. P4는 스트레치라 계산 밖 | blocker 18 |
| 추적표가 M-5를 Phase 4에 할당했으나 `DATA`는 Phase 5에나 생긴다 | blocker 19 |
| M1(Phase 1~4)과 M2(Phase 5~8)가 5주씩으로 불균형 | warn |
| Phase 4 keepalive 검증이 요구하는 외부 UDP 관측점이 설계에 없다 | warn |
| M-2 검증의 HTTPS IP 조회가 UDP 송신 경로와 다를 수 있다 | warn |

**검증.**

- C-5를 고친 뒤, **버려도 된다고 표시한 등급만** 제거했을 때 M-1~M-6이 전부 성립한다.
  현재 서술대로 P1이나 P3을 버리면 성립하지 않으며, 그것이 blocker 18의 내용이다.
  따라서 이 검증은 "모든 등급을 하나씩 빼봐도 성립"이 아니라 "droppable 표시가 사실과
  일치하는가"를 본다
- 추적표의 모든 M/T/A 항목이 해당 기능이 실제로 존재하는 Phase를 가리킨다. Phase별 산출물
  목록과 대조해 확인한다

## 5. 직접 연결 불가 대비책

**blocker 20. 가장 위험하다.** 가용한 두 가정망이 둘 다 목적지 의존 매핑이면 최소 성공이
불가능하다. 릴레이는 Phase 9 이후 스트레치라 구제가 안 된다. 프로젝트 전체가 통제 불가능한
외부 조건에 인질 잡혀 있다.

**먼저 할 것.** Phase 2 이전에라도 실측한다. 이 결정은 실측 없이 내릴 수 없다. 두 가지가
필요하고, **첫 번째만으로는 부족하다.**

1. **매핑 거동.** 두 개의 공개 STUN 서버에 Binding Request를 보내 관측 엔드포인트를 비교한다.
   **두 요청이 같은 bind된 UDP 소켓과 같은 로컬 엔드포인트를 써야 한다.** 소켓을 따로 열면
   출발지 포트가 달라 매핑도 달라져 목적지 의존성과 구분이 안 된다 (NFR-9와 같은 이유).
2. **실제 펀치 시험.** Binding 결과는 매핑 거동만 알려주고 **필터링 거동은 알려주지 않는다.**
   홀펀칭 성립 여부는 둘 다에 달려 있으므로, 두 망 사이에서 최소 펀치 스크립트로 실제 왕복을
   시도해 본다. 엔드포인트는 수동으로 주고받으면 되고 제어 평면은 필요 없다.

1번만 보고 결정하면 매핑은 괜찮은데 필터링 때문에 안 되는 경우를 놓친다.

**선택지.** 어느 것도 현재 M-1/M-4를 그대로 둔 채로는 성립하지 않는다는 점을 먼저 인정해야
한다. 현재 최소 성공은 "두 가정망 사이의 직접 UDP"로 정의되어 있는데, A는 그 토폴로지가
아니고 B는 직접이 아니며 C는 요구된 두 경로를 통과시키지 않는다. **따라서 어느 안을 고르든
성공 기준 자체를 함께 고쳐야 한다.**

| 안 | 내용 | 대가 |
|----|------|------|
| A | NAT 에뮬레이션 테스트베드. 원하는 매핑 거동을 만들어 검증 | 실제 환경 증거가 아니라 분석 설득력이 약해진다. M-4의 "지원 NAT 환경" 정의를 에뮬레이션 포함으로 넓혀야 한다 |
| B | 최소 릴레이를 P1로 승격. direct 실패 시 폴백 | direct-first 주장이 약해지고 Phase가 하나 늘어난다. 폴백 성공을 별도 등급으로 정의해야 한다 |
| C | 모바일 핫스팟 등 제3의 경로를 필수 시험 토폴로지에 추가 | CGNAT이면 더 나쁠 수 있다. 필수 토폴로지 계약을 고쳐야 한다 |

**검증.** 문서에 반영하는 것만으로는 완료가 아니다. 안 C를 골라놓고 그 경로도 실패하면
blocker 20은 그대로 남는다.

- 실측 결과(서버별 관측 엔드포인트, 목적지에 따른 매핑 변화 여부)를 수치로 기록한다
- M-1, M-4와 필수 시험 토폴로지 계약을 고른 안에 맞게 **명시적으로 개정**한다. 개정 없이
  안만 고르면 blocker 20은 그대로 남는다
- 고친 기준 아래에서 성공 경로를 재현한다. 재현 조건은 안마다 다르다

| 안 | 재현 조건 |
|----|-----------|
| A | 에뮬레이터 설정을 문서화하고 그 설정에서 3회 연속 성공. 설정이 곧 통제 조건이다 |
| B | direct 실패를 인위적으로 만든 뒤 폴백 경로로 3회 연속 성공 |
| C | 핫스팟은 통제 대상이 아니다. 통신사, 요금제, 시각, 신호 상태를 기록하고 **그 조건 아래에서** 3회 연속 성공. 조건이 바뀌면 결과가 달라질 수 있음을 함께 적는다 |
- 원래의 "두 가정망 직접 UDP"를 달성하지 못하는 경우, 그것을 실패가 아니라 별도 등급으로
  기록할지 미달로 기록할지 명시한다
- 그 경로가 실패했을 때 무엇이 남는지 적는다. 대비책의 대비책이 없다면 없다고 적는다
- 결정과 근거를 `decisions/`에 ADR로 남긴다

## 6. 과잉 검증 기준 되돌리기

네 항목이 같은 문제는 아니다. 하나는 정상 구현이 통과할 수 없는 기준이고(재발 방지 규칙 3번
위반), 둘은 측정 방법이 없어 판정 자체가 불가능하며, 하나는 증거로서 타당하지 않다.
구분해서 다룬다.

| 다룰 것 | 성격 | 근거 |
|---------|------|------|
| Phase 7 "송수신 바이트 카운터가 패킷 캡처와 정확히 일치, 오차 불허". 캡처 지점 위치, NIC 오프로드, 캡처 자체의 유실 때문에 정상 구현도 정확히 일치하지 않는다 | 통과 불가 | warn |
| Phase 8 게임 지연 ±30ms. 측정 방법과 계측 지점이 없어 판정 자체가 불가능하다 | 미정 | warn |
| A-2의 통제된 실패 시나리오(UDP 차단, 없는 엔드포인트)가 필수 사례로 고정. 인위적 실패가 실제 실패 분포의 증거가 되지 못한다 | 증거 타당성 | warn |
| Phase 9 통계 설계 미정. 시행 시간, 독립성, 불확실성 보고 | 미정 | warn |

**검증.** "정상 구현이 통과하는가"는 출발 질문이지 판정 기준이 아니다. 성격별로 완료 조건이
다르다.

**정량 기준**(Phase 7 카운터, Phase 8 지연, Phase 9 통계)은 아래 넷을 갖춰야 한다.

| 갖출 것 | 뜻 |
|---------|-----|
| 대상 문서와 절 | 어느 기준을 고쳤는지 |
| 측정 절차 | 무엇을 어떻게 재는지. 도구와 계측 지점 포함 |
| 허용 오차와 표본 조건 | 숫자. 표본 수와 통계량(중앙값 등)까지 |
| 기대 결과 | 어떤 값이 나오면 통과인지 |

**정성 기준**(A-2)은 숫자를 요구하지 않는다. 대신 그 시나리오가 무엇의 증거이고 무엇의
증거가 아닌지를 적는다. 인위적 실패는 실패 처리 경로가 동작한다는 증거이지, 실제 환경에서의
실패율에 대한 증거가 아니다. 이 구분을 쓰지 않으면 A-2는 다시 잘못된 기준이 된다.

기준을 낮출 때는 **무엇을 더 이상 보장하지 않는지** 같이 적는다. 느슨해진 만큼 진짜 결함도
같이 통과하게 되므로, 그 범위를 명시하지 않으면 기준을 없앤 것과 같다.

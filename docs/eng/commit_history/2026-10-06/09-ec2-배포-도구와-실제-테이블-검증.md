# EC2 deployment tools, real table verification, DynamoDB call settings

## Why

This is item 1 of "Next to do" in `plan.md`. The control server was put on EC2 and the "Deployment" group of
the `roadmap.md` Phase 3 verification was run. `control_plane.md` 7.6 decided "run the deployment procedure
for real once, then put it in a tool and have the document point to it", so the procedure was written as a
tool from the start, and that tool was run for real.

## What was done

| What | Content |
|------|---------|
| `tools/cp-deploy/deploy.py` | Uploads only committed code. System user, release folder, venv, config file, systemd unit. Confirms with `server.started` in this run's journal and one operation. On failure it rolls back to the previous state |
| `tools/cp-deploy/verify.py` | Runs the five operations against the deployed server. Concurrent joins, imitation of the 8.3 client retry, load for the capacity check |
| `__main__.py`, `constants.py` | The server's DynamoDB call settings. connect 1 second, read 1 second, no SDK retry |
| `control_plane.md` 2.6, 7.6, chapter 10 | Three constants, pointer to the deployment tools, the call settings and their rationale, measurement of transaction conflicts on the real table. Removed the one open line in chapter 10 |
| `roadmap.md` Phase 3 | The deployment work item points to the tools and 7.6 |

The deployed commit is `2cc0eef`. The call settings of this commit are not deployed yet. The next commit record
covers that redeployment.

## Deployment verification results

| Verification item | Result | How |
|-------------------|--------|-----|
| The five operations run on the real table | Passed | `verify.py`. The `join_room` and `host_report` confirm ran without permission errors. That means IAM has `ConditionCheckItem` |
| Transaction conflicts | They happen. They are absorbed as designed | Four concurrent joins run five times gave 7 `internal` out of 20. A transaction of the same shape was run on the instance, and the cancellation reason read as `TransactionConflict` (`ROOM` ConditionCheck). Imitating the 8.3 retry, ten runs joined all 40 |
| `elapsed_since_ready_ms` continues across a restart | Passed | The service was restarted after ready. The value went from 111ms to 3024ms, up by the time that passed in between. `elapsed_wall_fallback` at shutdown was 0 |
| The value does not jump when the wall clock is moved 1 minute | Passed | Stopped chrony and ran `date -s '+60 seconds'`. In that interval the value rose by 1620ms, and the real elapsed time was 1654ms. The clock was set back, chrony was started again, and sync was confirmed |
| CloudWatch capacity | Waiting | The server role has no CloudWatch read permission. It is not given, for least privilege. Load was applied with `verify.py --soak 180` at UTC 2026-10-07 02:45 ~ 02:49, and the repository owner checks it in the console |

The server-side time (`ms` of `http.request`) had per-operation medians of 8~118ms, and the longest was 331ms
(`host_report`). These values are the basis of the call settings.

## Tests broken by the call settings

After adding the settings, two server mutations survived. The shutdown test blocks dispatch with "a store
that does not answer" and sends the stop signal, but the 1-second read timeout released that block in 1
second, so the process ended even without `os._exit`. The premise of the test was broken. The store was
changed to trickle the response body one byte every 0.3 seconds, so the per-read timeout does not fire.
After that, 90/90. The mutation run caught this, and the review did not.

# Fixed the Platform Porting Seams (ADR 0010)

## What Was Done

The repository owner asked, "keep support for other operating systems a stretch goal, but lay
out the code so it can be moved later." Looking into it, **nothing was organized.** Four living
documents only said "we do not do this" (the exclusions and stretch goal of `spec.md`,
`architecture.md` chapter 12, `roadmap.md` P4), and none of the 9 ADRs covered porting. The
`architecture.md` 3.1 module table did not name the seams, and in one place the module name was
itself a vendor (`adapter/wintun_adapter`).

Four options were put up (do nothing / documents only / fix the seams / a full PAL) and the owner
chose **fixing the seams**. The scope is not widened. Only the places to be rewritten are named.

## Decision

[ADR 0010](../../decisions/0010-platform-porting-seams.md) owns it. There is one rule.

> Client sources that include OS headers live only under `client/src/platform/`.
> There is not one OS header under `client/include/`.

**Counting the seams turned four into five.** We were counting sockets, waiting and the
monotonic clock, the virtual adapter, and startup and privileges; reading the code added hashing.
`sha256_hex` calls `BCryptHash`. Moving it needs another implementation, and if that is
third-party it falls under the `spec.md` NFR-5 approval. Without counting it, that place would
have been missing from the porting estimate. The same survey also found Windows CNG missing from
the external dependency table of `architecture.md` chapter 11, and filled it in.

**The meaning of the headers was not made neutral.** `udp_socket.hpp` still hands out the integer
of `WSAGetLastError` and Win32 events. Renaming things to look neutral makes it look ported when
it is not. ADR decision 3 records that choice and its cost.

## Code

| What | Place |
|------|-------|
| Moved (contents unchanged) | `network/wsa.cpp`, `network/udp_socket.cpp`, `hash.cpp` -> `platform/win32/` |
| New | `client/include/sangtachi/platform/wait.hpp`, `client/src/platform/win32/wait.cpp` |
| Changed | `<windows.h>` removed from `loop.cpp` and `console.cpp`. The infinite timeout of `timer.hpp` became an alias |
| CMake | `FATAL_ERROR` off Windows. `ws2_32`/`bcrypt` moved under `if(WIN32)` |
| Tests | `tests/platform/wait_test.cpp`, 8 cases |

`wait_any` wraps `WaitForMultipleObjects`. Behaviour preservation was checked one item at a time:
the timeout computation and the `busy_` fast path, the order and length of the handle array,
`WAIT_FAILED` handling and the log tokens (including the `op` string), manual/auto reset, index
mapping, swallowed errors, and event ownership.

**The behaviour of one unreachable path did change.** The `WAIT_ABANDONED` range. The earlier
`loop.cpp` let it pass; now it becomes `Failed`, so it is recorded and goes to the cleanup path.
We decided not to read a return value whose meaning we do not know as normal. The reasoning is in
a comment in `wait.cpp`.

## Mutation Testing

6 of the 8 mutants on the `wait.cpp` side were caught. The two survivors are written down rather
than hidden.

- Deleting the **input validation guards** (empty array, over the cap) still passed, because the
  OS returns the same error. What the cases hold is the contract, not the guard. The guards stay,
  per rule 7
- **Deleting `busy_ ? 0 :` let all 91 tests pass.** This is not a defect this work created but
  **a gap that was already there**. A new case was written to catch it and that case passed the
  mutant too, because after stopping on budget `FD_READ` is signalled again and the next turn
  wakes regardless of `busy_`. It held nothing, so it was deleted (`loop_test.cpp` unchanged).
  **It needs the wait to be injectable.** Hung on `plan.md`

On the `platformgate` side 17 of 19 were caught. The two survivors cannot change the output, and
the reasoning is in a comment in the script.

## What This Round Confirmed

- **Splitting the lenses paid off.** The gate blocker sat where the first two lenses could not
  see. It points the same way as "cutting lenses cuts blockers, not tokens" in `CLAUDE.md`
- **Narrowing the review input costs one false blocker.** It was filtered out by checking HEAD.
  The choice to cut the scope stands
- **The record ran ahead of the code.** An edit adding one rule row to the ADR was put in the same
  cell as another edit, and a syntax error on the later line blocked the whole cell, so **the
  earlier edit did not land either.** That was not checked, it was reported as "accepted", and
  this record said so too. The confirmation round caught it. This is what "do not put an edit and
  a state change in one cell" in `CLAUDE.md` is meant to prevent, and the missing step was
  **reading the file again after editing it**
- **The judgement function was wrong twice.** Once in the subagent's first mutation run (line
  comments), once in the cross-model review (a comment inside the directive). Both were of the
  form that gives **a wrong answer**, not "unknown"

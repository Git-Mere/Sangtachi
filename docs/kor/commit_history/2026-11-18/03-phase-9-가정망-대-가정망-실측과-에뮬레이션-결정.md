# Phase 9 가정망 대 가정망과 에뮬레이션한 목적지 의존 매핑 실측

## 왜 했나

`roadmap.md` Phase 9 테스트 환경 표의 가정망 대 가정망이다. 상대는 소유자의 친구 집 가정망이다. 같은 날 소유자가 "가용한 다른 NAT 거동" 을 실제 망에서 구하기 어렵다고 해서, 목적지 의존 매핑을 에뮬레이션하는 결정([ADR 0040](../../decisions/0040-목적지-의존-매핑-에뮬레이션.md))을 하고 그 측정도 했다.

## 구성

시행 방법은 [2026-11-17 첫 실측](../2026-11-17/05-phase-9-상대-없는-검증과-첫-실측.md)과 같다. 다른 것만 적는다.

| 무엇 | 값 |
|------|-----|
| 역할 | 친구 PC 가 호스트, `mere-galaxy`(집 Wi-Fi, Comcast)가 플레이어 |
| 호스트 | 친구가 같은 실측 빌드(커밋 `5f9f710` 의 Windows Release 콘솔, `--no-adapter`)를 한 번 띄워 10회 내내 두었다. 플레이어만 시행마다 새로 띄웠다. 시행 사이 휴식은 60초로 같다 |
| 친구에게 준 것 | 실행 파일, 호스트를 띄우는 `host.cmd`, 안내문을 묶은 zip. 레포 밖이다 |
| 시행 스크립트 | git 이 무시하는 `.prime/p9-field/field_join.py`. 기존 방 코드로 플레이어만 띄운다 |
| `mere-galaxy` | 시작 전에 Wi-Fi 절전을 껐다(이슈 0001) |
| 기록 | git 이 무시하는 `field-test/2026-11-18/home-home/`. 묶음의 UTC 범위는 `tools/tm-analysis/local/batches.txt` 에 있다 |

**호스트를 계속 두면 수립 시간의 조건이 다르다.** 묶음 전에 `mere-galaxy` 를 호스트로 한 번 띄우고 이 PC 를 60초 간격으로 두 번 넣어 봤다. 둘 다 `CONNECTED` 였고, 시행 스크립트가 본 결과까지의 시간은 11.2초와 6.6초였다. 이 묶음의 수립 시간은 시행마다 호스트를 새로 띄운 다른 묶음과 비교하지 않는다. 성공 여부와 RTT 는 그대로 쓴다.

## 결과

아래 RTT 는 `mere-galaxy` 의 로그에서 본 예비 값이다. `experiments.md` 의 숫자는 분석 도구가 테이블에서 낸 값을 쓴다.

| 환경 | 결과 | 쓴 경로 | `mere-galaxy` 의 RTT 표본 |
|------|------|---------|---------------------------|
| 가정망(`mere-galaxy`, Comcast) 대 친구 집 가정망 | 10/10 `CONNECTED` | 10회 모두 공인 주소 | n=60, 중앙값 20.8ms, 사분위 범위 17.7~29.0ms |

- 업로드 실패는 두 기기 모두 0 이다. 친구의 표준 오류 로그, 로컬 기록 파일, `logs\` 사본을 받아 git 이 무시하는 `field-test/2026-11-18/home-home/friend/` 에 두었다. 친구 쪽 `telemetry_upload_failed` 와 `telemetry_queue_dropped` 는 0, `CONNECTED` 10, 종료 줄 10 이다
- 두 기기 모두 STUN 서버 둘에서 같은 공인 포트를 받았다. 친구 호스트는 STUN 을 한 번만 돌았다
- 친구 쪽 로컬 기록의 호스트 수립 시간은 n=10, 중앙값 6187.5ms(5953~6250)다. 시행마다 호스트를 새로 띄운 2026-11-17 두 묶음의 호스트 쪽 중앙값(약 6.2초)과 비슷하다. 호스트 쪽 기점은 플레이어가 `peers` 에 처음 보인 때라 호스트를 계속 둔 영향을 덜 받는 것으로 보이지만 확인하지 않았다

## 에뮬레이션 측정

ADR 0040 대로 `mere-galaxy` 에 네트워크 네임스페이스와 `MASQUERADE --random-fully` 를 걸었다. 네임스페이스 밖에서는 두 STUN 서버의 포트가 같았고, 안에서는 매번 달랐다. 이 PC(학교 유선 LAN)가 호스트, 네임스페이스 안 클라이언트가 플레이어다. 둘 다 시행마다 새로 띄웠다. 시행 스크립트는 git 이 무시하는 `.prime/p9-field/field_sym.py` 다. 기록은 `field-test/2026-11-18/emu-dep-map/` 이고, 묶음 종류는 `controlled` 다.

| 환경 | 결과 | 플레이어의 두 STUN 포트 |
|------|------|-------------------------|
| 에뮬레이션한 목적지 의존 매핑(`mere-galaxy`) 대 캠퍼스망(이 PC) | 10/10 `HOLE_PUNCH_TIMEOUT` | 10회 모두 달랐다 |

- 양쪽 다 `PUNCHING` 에서 `FAILED` 로 갔다. 10회 모두 두 쪽의 상대별 수신 카운터(`rx_bytes`, `rx_datagrams`)가 0 이다. 상대의 패킷이 어느 방향으로도 닿지 않았다. 프로세스 전체로는 두 쪽 다 3개(132바이트)를 받았고, 크기로 보아 STUN 응답이다. 플레이어 쪽 카운터는 `galaxy-rx-counters.txt` 로 받아 두었다
- 플레이어는 두 STUN 포트를 모두 후보로 등록했다. `--random-fully` 는 목적지마다 새 포트를 고르므로 펀치에 쓰인 매핑은 그 둘과 다른 포트였을 것이다. 그 포트를 직접 보지는 않았다
- 업로드 실패는 두 기기 모두 0 이다
- 이 결과는 ADR 0040 대로 실제 환경의 성공률에 넣지 않는다

본 측정 전에 같은 구성으로 두 시행을 돌리다 소유자의 결정으로 멈춘 적이 있다. 둘 다 `HOLE_PUNCH_TIMEOUT` 이었다. 묶음 파일에 적지 않아 분석 도구에서 어느 묶음에도 들지 않은 시도로 나온다. 기록은 `field-test/2026-11-18/emu-dep-map-aborted/` 다.

시험 뒤 네임스페이스와 규칙을 지웠고, 네임스페이스 밖의 STUN 포트가 다시 같은 것을 확인했다.

## What was newly seen while deciding

- A in the 6-1–6-4 run (with the 64 MiB transfer) was compared too. 49,786 received datagrams, 70,227,961 bytes, matched
  the capture. On the send side the counter was one 40-byte datagram higher. That run did not record dumpcap loss or
  `netstat`, so it is not used for the verdict
- The bytes where the console `send` stopped are about 64KB at both 576 bytes (110 × 596) and 1452 bytes (45 × 1472).
  This socket leaves the send buffer at its default (`udp_socket.hpp`)
- 40 bytes is the datagram size of `HELLO` and `HELLO_ACK` (header 20 + body 20). A in the second 6-5 run sent no
  20-byte `DATA`
- The 168 `drop_too_old` of A in the second 6-5 run are sequence numbers 11–178 of B's 1,000 20-byte datagrams, which
  already arrived up to 958 positions late in A's capture. They are outside the replay window (64), so they were dropped
  as specified. The receive counter counts at `recvfrom`, so the comparison is unaffected. Kept as an observation only

## Key decisions

- Instead of confirming why the send counter is higher, the network condition avoids it. The repository owner chose
  this. If the hotspot's phone network NAT is outside the supported conditions the connection may fail, so the procedure
  says to stop and decide again in that case
- The console `send` is not changed. The byte count check no longer depends on it

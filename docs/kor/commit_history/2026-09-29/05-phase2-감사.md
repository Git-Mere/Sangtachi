# Phase 2 전문 대상 감사

## 왜 했나

`CLAUDE.md` 재발 방지 규칙 2 다. **diff 리뷰는 국소 결함만 잡으므로 Phase 를 끝낼 때마다
전문 대상 감사를 따로 돌린다.** 범위는 그 Phase 가 건드린 문서와 코드다.

Phase 2 는 diff 리뷰를 5라운드 돌았고 blocker 1, warn 7 을 처리했다. 그 뒤에 이 감사에서
**blocker 14, warn 30** 이 더 나왔다. 렌즈 셋을 따로 돌렸다.

| 렌즈 | 무엇을 보았나 |
|------|---------------|
| 시나리오 추적 | 기동부터 끝까지 네 경로. 성공, 한 서버만 응답, 늦은 응답, 종료 중 STUN |
| 검증 기준 | `roadmap.md` Phase 2 검증 항목마다 "지금 무엇이 이것을 판정하는가" |
| 문서 전문 | 이번 Phase 에서 정의가 바뀐 넷에 기대던 문장을 전수로 |

**셋이 겹쳐 찾은 것이 셋 있다.** `timer.tick` 서술, 모듈 표의 빈자리, `plan.md` 의 틀린
인수인계다. 서로 다른 렌즈가 같은 자리를 가리키면 그것은 확실한 결함이다.

## 고친 것

### 문서가 코드와 어긋난 자리

| 무엇 | 어떻게 |
|------|--------|
| **`timer.tick` 은 시험 빌드에만 있다** | 틀렸다. Phase 2 가 STUN 타이머를 같은 집합에 걸어 제품 빌드에서도 나간다. 9장을 "만료하는 모든 타이머가 낸다. 시험 빌드가 `probe200` 을 하나 더 넣는다" 로 고쳤다 |
| 3.1 모듈 표와 10장 트리 | Phase 2 가 만든 다섯(`network/stun`, `network/stun_client`, `platform/random`, `platform/resolve`, 그리고 `win32` 트리)이 빠져 있었다 |
| **기본 목록은 "두 곳" 이 같아야 한다** | Phase 2 가 세 번째 자리를 만들었다. "셋" 으로 고쳤다 |
| 서버 교체 계기 | 3.5 는 마감만 적는데 코드는 성공·오류 응답에도 자리를 넘긴다. **계기 셋을 표로 만들었다** |

### 문서에 아예 없던 규칙

| 무엇 | 어디에 적었나 |
|------|---------------|
| 마감이 지난 자리의 응답은 쓰지 않는다 | `protocol.md` 11장. 유일한 출처가 코드 헤더였다 |
| `drop_stun_parse` 가 무엇을 세는가 | 같은 문서 13장. **케이스 표 셋**(대기 중 자리, 끝난 자리, 자리가 없음) |
| 재시도 세 값은 간격이지 마감이 아니다 | 11장. 절대 시각으로 읽으면 배증이 아니게 된다 |
| 단계 상한의 "목록 길이" 는 중복 제거 뒤의 길이 | 11장 |
| 숫자로만 된 이름은 해석하지 않는다 | `architecture.md` 3.5 |
| `rx.raw` 는 받은 데이터그램 전부에 나간다 | 같은 절 |

## 시험 하나를 고치면서 배운 것

`WAIT_FAILED` 를 재현하는 케이스가 **30초 만에 시간 초과로 실패했다.** 대기가 실패하지 않고
영원히 기다렸다.

원인은 핸들 값 재사용이다. 이벤트를 **먼저 닫고** 그 값을 루프에 넘겼더니, 루프 생성자가
만드는 종료 이벤트가 **방금 비워진 같은 값**을 받았다. 대기 집합에 같은 핸들이 두 번 들어가
유효한 대기가 되어 버렸다. 루프를 만든 뒤에 닫도록 순서를 바꿔 고쳤고 그 이유를 케이스
주석에 적었다.

## 남긴 것

시험이 지키지 못하는 자리를 `plan.md` 에 걸었다.

- 목록이 정확히 둘일 때의 성공 경로가 단위 시험에 없다. 지금 그 자리를 지키는 것은 e2e 하나다
- STUN 진단 로그 여섯 종을 아무 시험도 보지 않는다. `emit` 에 주입 지점이 없어 단위 시험이
  로그를 볼 수 없다
- `--stun` 호스트 문법의 통과 쪽 표에 라벨 안 숫자와 붙임표가 없다

**"STUN 소켓이 터널 소켓과 같다" 를 로그로 판정할 수단이 없다.** `roadmap.md` Phase 2 검증이
그것을 요구하는데 로그에 소켓 식별 필드가 없다. 그 항목이 스스로 "이것은 참고다. 와이어에서
보는 판정은 Phase 4 가 맡는다" 로 적어 두었으므로 이번에 바꾸지 않았다.

## 감사 자체에 대해

**diff 리뷰 5라운드가 blocker 1건을 찾았고, 전문 감사 셋이 14건을 찾았다.** 같은 코드다.
차이는 보는 방식이다. diff 리뷰는 바뀐 줄을 보고, 전문 감사는 바뀌지 않은 줄이 바뀐 줄과
맞는지 본다. **이번에 나온 blocker 대부분이 "우리가 이번에 만든 규칙이 우리 문서의 옛 문장을
낡게 만든 것"** 이었다.

# Build Path Resolution Moved Into One Place, and Lock Failures Measured Again

## Why

The default location for build output was `%LOCALAPPDATA%\Sangtachi\build`. The repository owner
decided to move that location to `C:\me\build`. Two things came with the move.

- The default was written the same way four times across four scripts (`build.ps1`, `test.ps1`,
  `cli-check.ps1`, `e2e-check.ps1`)
- An absolute path that differs per machine cannot be hardcoded into the repo

And the grounds for taking the output out of the repo in the first place (4/18 failures inside the
repo, 0/18 outside) were weak (`p = 0.052`, the locking process was never identified), so it was
measured again to see whether it still holds.

## What the Repository Owner Decided

**The build root on this machine is `C:\me\build`.** That is outside the sync folder
(`C:\me\sync`). It was first moved to the repo's parent folder (`CSP400\build`), but that place
turned out to be inside the sync folder too, so it went up one more level.

## What Changed

| Group | Content |
|-------|---------|
| New | `scripts/buildpath.ps1`. `Resolve-BuildDir` and `Get-BuildRootFromFile` decide the path |
| Priority | The value given with `-BuildDir` -> the first valid line of `scripts/build-root.local` + `\<Config>` -> `%LOCALAPPDATA%\Sangtachi\build\<Config>` |
| Root format | Only a path starting with a drive letter, or a UNC path, is accepted. Otherwise it stops right there |
| The four scripts | Each drops the default it wrote itself and dot-sources `buildpath.ps1` |
| Ignore | `scripts/build-root.local` in `.gitignore` |
| Documents | The build section and the run section of `README.md`. The header comment of `build.ps1` |

**An environment variable was not used.** The value differs per shell, so the same repo would build
in different places depending on the shell. A file gives the same value in a new terminal too.

**The default of the function that reads the root file is "no value when unknown".** If the file is
missing or has no valid line, it returns an empty string and falls back to `%LOCALAPPDATA%`.
Interpreting unreadable content as a path would build into the wrong directory, or make `-Fresh`
try to delete it.

## Measured Again

The same build was run in pairs at two locations, and the order was flipped for each pair. Always
running in the same order lets time-dependent effects such as cache warm-up imitate a location
effect.

| Location | Path |
|----------|------|
| Inside the repo | `Sangtachi\build\measure` |
| Outside the repo | `C:\me\build\measure\b` |

### The first run was invalid

The driver wrote the source path it meant to touch as `client/src/network/wsa.cpp`. The real
location is `client/src/platform/win32/wsa.cpp`. The mtime was never bumped, so ninja had nothing
to do, and all 36 runs **made nothing at all**. 2.8 seconds per run was the sign.

**That result was nearly reported as is.** "36 runs, 0 failures" measures nothing, because it never
linked once. Two checks were added to the driver to fix it.

- At startup it checks that the target file exists. If not, it stops right there
- For each run it checks the output for `Linking CXX executable`. If absent it is recorded as
  `relink=0` and excluded from the verdict

### The result of the two rounds

| Round | Condition | Inside the repo | Outside the repo | Mean |
|-------|-----------|:--:|:--:|:--:|
| 1 | Touch one source only, incremental link | 0 / 18 | 0 / 18 | 3.7 s |
| 2 | Touch all 51 sources, 34 objects regenerated | **1 / 18** | 0 / 18 | 7.7 s |

The failure in round 2 is this one.

```text
wsa.cpp : fatal error C1083: Cannot open compiler generated file:
  '...\build\measure\client\CMakeFiles\sangtachi_core.dir\src\platform\win32\wsa.cpp.obj':
  Permission denied
```

`hash.cpp.obj` hit the same error in the same run. **The compiler could not open the `.obj` it was
about to create.** It is the same family as the `LNK1168`, `LNK1201` and `C1041` of the original
record (access denied on a build output file), and only the stage differs: compile instead of link.

**The detection regex did not catch that error.** `C1083` was not in the list, so it was recorded
as `lock=0`, and the exit code check caught it and made it visible. Judging by the code list alone
would have missed it.

### What can be said

| Measurement | Inside the repo | Outside the repo |
|-------------|:--:|:--:|
| Earlier record (full build) | 4 / 18 | 0 / 18 |
| Round 1 this time | 0 / 18 | 0 / 18 |
| Round 2 this time | 1 / 18 | 0 / 18 |
| Total | 5 / 54 | 0 / 54 |

**Round 2 alone does not stand statistically.** One-sided Fisher exact gives `p = 0.5`. Combining
the three measurements gives `p = 0.028`, but **the three rounds used different methods, so that
combination is only a reference.**

Three things are confirmed.

- The failures happened only inside the repo
- All 5 share the same mechanism. A build output file cannot be accessed
- Outside the repo it is 0 out of 54 runs

**The locking process was not identified this time either.** All that is recorded is that
`GoogleDriveFS` and `MsMpEng` were running during the measurement. And **the round 2 failure was
the first run out of 36.** The effect of scanning a freshly created directory and the location
effect do not separate in this single case.

The measurement originals (the CSV, the failure logs, and the driver) are kept outside the repo.

## Cross-Model Review

Four rounds were run with Codex, split by lens. Of 7 findings, 3 were taken and 4 rejected.

| Lens | Scope | Result |
|------|-------|--------|
| PowerShell path resolution | `scripts/` | `LGTM` |
| Document accuracy + the duty of what was deleted | `docs/`, `README.md`, `CLAUDE.md`, `.gitignore` | 5 findings. 1 taken, 4 rejected |
| Confirmation | The whole diff | 1 finding. Taken |
| Confirmation (again, after the fix) | The whole diff | 1 finding. Taken |

### The 2 findings of the confirmation rounds were real

If a relative path is written in `build-root.local`, `Resolve-BuildDir` builds the path against the
current directory of the caller. Building there once creates `CMakeCache.txt`, so **it also passes
the deletion safeguard of `-Fresh`.** A single typo becomes a path that deletes the wrong
directory.

**But the fix the reviewer gave was insufficient too.** It said to use
`[System.IO.Path]::IsPathRooted`, and putting that in as given dropped one case.

```text
FAIL  drive-less root is rejected: expected 'THROW', got '\noroot\Debug'
```

Despite its name, `IsPathRooted` is true for `\noroot` as well. It is a drive-relative path that
attaches to the current drive. This is exactly where `CLAUDE.md` recurrence-prevention rule 7
applies. So it became an **allow list** instead of an exclusion list. Only a path starting with a
drive letter and a UNC path are accepted.

**There is one more reason for judging with a regex.** `IsPathFullyQualified` does not exist on
Windows PowerShell 5.1. The path `README.md` calls through `powershell` has to keep working too.

**Running the same lens again after the fix showed that allow list was still loose.** The UNC
judgement passed on `\\server` alone, so `Join-Path` makes `\\server\Debug`. That is a path with
the build configuration name in the share name slot. It was narrowed to require both a server and
a share. **A fix that narrows a judgement does not finish in one pass** is what these two rounds
teach.

### The 4 rejections

**Three of them were created by the review input scope.** `scripts/` was not given to the document
lens, and it came back with "`buildpath.ps1` is not in the diff", "it says four scripts were fixed
but they are not there", and "it points at code with no verification claim". **All three are in the
staging area.** This was confirmed with `git diff --cached --stat`. It falls under what `CLAUDE.md`
says: "a finding of the 'it is missing' kind is accepted or rejected only after checking HEAD
directly".

**The remaining one is where the judgment split.** On where `roadmap.md` Phase 2 verification says
to keep the observation record, the reviewer held that `roadmap.md` itself should be fixed. What
that document says is "the record is kept outside the repo. The repo records only how many
observations there were and whether the servers differed", and **it does not decide which file.** A
living document is not the place to hold an observation from a point in time, and
`commit_history/` does that job, so this record is that place. That judgment is written in the
Phase 2 section above.

**The 1 finding taken by the document lens came out of that rejection.** Without a sentence saying
this section is the required repo-side record, the next person makes the same finding again.

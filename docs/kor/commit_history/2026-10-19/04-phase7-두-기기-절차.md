# Phase 7 두 기기 실측 절차와 키트 `field-kit-p7`

## 왜 했나

Phase 7 의 남은 확인은 두 기기가 있어야 한다. 저장소 소유자가 절차가 `field-test` 에 있는지 물었고, 없었다. 남은 Phase 4~5 실측(시험 1, 5)과
같은 날 한 키트로 몰아서 하기로 소유자가 정했다. 이 커밋은 절차와 키트만 바꾼다. 실측은 소유자가 시점을 알려 준다.

## 무엇을 바꿨나

| 무엇 | 자리 |
|------|------|
| 키트를 `field-kit-p7` 로. 키트에 넣을 파일 표. 시험 1, 2, 5 에 `--no-adapter`. 시험 6 은 관리자 cmd, 끝나면 규칙을 지우는 명령, 서브넷 충돌이면 그 PC 로는 못 한다 | `field-test/README.md` 준비 |
| 시험 6. 다른 차단 규칙 확인, 기동과 캡처, 가상 IP `ping`, 파일 전송, 최대 크기 패킷과 MTU, 바이트 카운터와 캡처 대조, 모을 파일 | `field-test/README.md` |
| 키트 표, 다음에 할 것 4번, 결과를 받으면 할 일 4번 | `field-test/required-test.md` |
| 캡처 대조 표의 측정 경계(프로세스 수명, 상대가 먼저 끝난다)와 표본 조건 | `roadmap.md` Phase 7 |
| 남은 일을 두 기기 검증 하나로 | `plan.md` |

## 중요한 결정

- **측정 경계는 재는 쪽 클라이언트 프로세스의 수명 전체다.** `roadmap.md` 가 "대조 절차를 쓸 때 정한다" 고 비워 둔 칸이다. 로그 줄에 시각이
  없고 keepalive 와 `PING` 이 쉬지 않으므로 중간에서 자르면 카운터와 캡처의 경계를 맞출 수단이 없다. 카운터가 0 에서 시작하고 종료 때 전량이
  한 번 더 나오므로 수명 전체가 자를 필요 없는 구간이다. 저장소 소유자에게 안으로 보였고 소유자가 승인했다
- **상대가 먼저 끝난다.** 리뷰가 `blocker` 로 잡았다. 재는 쪽이 먼저 끝나면 상대의 keepalive 가 그 마지막 수신 뒤에 와서 캡처에만 남는다
- **시험 1, 2, 5 는 `--no-adapter` 다.** Phase 5 까지와 같은 경로라 그 시험의 판정(받은 쪽의 `drop_no_sink` 따위)이 그대로다. 관리자 권한이
  필요 없다
- **6-5 는 6-1~6-4 와 다른 프로세스로 한다.** 64 MiB 전송이 섞이면 캡처가 커지고 유실될 수 있다

## 검증

- `python tools/docgate/docgate.py` 통과
- 6-5 의 tshark 합산 명령을 2026-10-14 시험 1 의 A 캡처(`t1.pcapng`, 로컬 포트 53014)로 돌렸다. `capture tx=3847 rx=3244`, 보낸 데이터그램
  115 개가 나왔다. 그 빌드에는 바이트 카운터가 없어 대조는 하지 않았다
- 6-0 의 차단 규칙 조회를 이 기기에서 Windows PowerShell 과 pwsh 로 돌렸다. 둘 다 줄을 냈고, 나온 차단 규칙은 프로그램이 `Unity.exe` 라 통과 조건에 들지 않는다
- **돌려 보지 않은 것.** 시험 6 의 나머지. 두 기기가 있어야 한다

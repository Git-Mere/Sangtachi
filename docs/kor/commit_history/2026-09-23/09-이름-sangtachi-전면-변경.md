# 이름을 sangtachi 로 바꿨다

**대상 커밋:** 이 커밋
**Phase:** 없음. 동작을 바꾸지 않는다

옛 이름 `hamychi` 가 코드와 빌드 파일, 그리고 기록 문서에 남아 있었다. 살아 있는 문서는
이미 `Sangtachi` 를 쓰고 있었다. 저장소 소유자가 전면 변경을 지시했다.

## 무엇을 바꿨나

| 대상 | 전 | 후 |
|------|-----|-----|
| 헤더 디렉터리 | `client/include/hamychi/` | `client/include/sangtachi/` |
| CMake 모듈 | `cmake/HamychiWarnings.cmake` | `cmake/SangtachiWarnings.cmake` |
| CMake 프로젝트 | `project(Hamychi)` | `project(Sangtachi)` |
| CMake 대상 | `hamychi_core`, `hamychi_client`, `hamychi_tests`, `hamychi_warnings` | 같은 자리의 `sangtachi_*` |
| CMake 옵션 | `HAMYCHI_BUILD_TESTS`, `HAMYCHI_TEST_BUILD` | `SANGTACHI_BUILD_TESTS`, `SANGTACHI_TEST_BUILD` |
| 네임스페이스 | `hamychi`, `hamychi::network`, `hamychi::protocol` | `sangtachi`, `sangtachi::network`, `sangtachi::protocol` |
| include 경로 | `#include "hamychi/..."` | `#include "sangtachi/..."` |
| 기본 빌드 경로 | `%LOCALAPPDATA%\Hamychi\build` | `%LOCALAPPDATA%\Sangtachi\build` |
| 실행 파일 | `hamychi_client.exe` | `sangtachi_client.exe` |

디렉터리와 파일 이동을 Git 이 이름 변경으로 인식한다. `git status` 가 `R` 로 적는다.

**줄 끝은 바뀌지 않았다.** diff 에 파일 전체가 바뀐 곳이 없다. 이름이 든 줄만 바뀌었고 그
수는 아래 기록 표와 같다. 텍스트 모드로 읽고 쓰면 CRLF 가 LF 가 되어 diff 가 파일 전체로 번진다.

## 기록 폴더도 바꿨다

`CLAUDE.md` 는 `commit_history/` 와 `decisions/` 를 그 시점의 사실로 두고 고치지 말라고 한다.
이번 변경은 저장소 소유자가 정한 예외다.

| 파일 | 바꾼 곳 (줄) |
|------|:---:|
| `2026-09-23/04-phase1-endpoint-args.md` (kor, eng) | 각 1 (1줄) |
| `2026-09-23/07-phase1-event-loop.md` (kor, eng) | 각 1 (1줄) |
| `2026-09-23/03-phase1-빌드-뼈대.md` (kor, eng) | 각 6 (4줄) |
| `decisions/0005` (kor, eng) | 각 4 (3줄) |

> **왜.** 옛 이름으로 적힌 기록을 그대로 두면 다음 세션이 존재하지 않는 대상 이름을 읽는다.
> 바꾼 것은 식별자뿐이고 수치, 판정, 서술은 그대로다.

## 검증

동작을 바꾸지 않는 변경이므로 기존 검사가 그대로 통과하는지를 본다.

| 무엇 | 결과 |
|------|------|
| `scripts/build.ps1 -Fresh` | 성공. `/W4 /WX` 경고 0건 |
| Catch2 케이스 | 83 / 83 통과 |
| CLI 케이스 | 19 / 19 통과 |
| 끝단 검사 (`e2e-check.ps1`) | 실패 0건 |
| `docgate.py` | `VERDICT: pass`. pairs=57, links=525, findings=0 |
| 옛 이름 전수 검색 | `.git`, 빌드 산출물, 이 기록 두 파일을 뺀 전부에서 0건 |

**변이 시험은 돌리지 않았다.** 이 diff 는 식별자만 바꾸고 제어 흐름을 건드리지 않는다.
새로 생긴 판정 축이 없으므로 죽일 변이가 없다.

**전수 검색에 확장자를 제한하지 않았다.** 옛 이름은 `.hpp`, `.cpp`, `.txt`(CMake), `.ps1`,
`.md` 다섯 종류에 흩어져 있었다. `.md` 만 봤으면 빌드가 깨진 채로 남았다.

### 3라운드 — 기록 정확성과 미러 대칭

기록 파일 둘만 보냈다. 지적 2건(같은 것의 한국어와 영어)이 나왔고 반영했다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | `decisions/0005` 를 각 3곳 바꿨다고 적었는데 보낸 diff 에 그 변경이 없어 재현할 수 없다 | **반영.** 지적의 이유는 틀렸다. 그 변경은 스테이징에 있고 렌즈에 보낸 범위 밖이었다. **다만 수치가 틀렸다.** 위 표가 식별자 개수와 줄 수를 섞어 쓰고 있었다. 세 행이 개수(6, 1, 1)인데 `decisions/0005` 행만 줄 수(3)였다. 개수 4와 줄 수 3을 같이 적어 단위를 고정했다 |

**틀린 지적이 진짜 결함을 가리켰다.** 렌즈에 범위를 좁게 준 것이 지적의 원인이지만, 그
자리를 다시 세게 만들어 단위가 섞인 것을 찾았다.

### 4라운드 — 확정 (시나리오 렌즈 + 기록 렌즈)

전체 diff 에 렌즈 둘을 붙였다. 시나리오 렌즈는 지적이 없었고 기록 렌즈가 2건을 냈다.
둘 다 반영했다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | "옛 이름은 코드 쪽에만 있었다" 인데 같은 diff 가 기록 문서의 옛 이름도 바꾼다 | **반영.** 코드와 빌드 파일, 그리고 기록 문서에 남아 있었다고 고쳤다 |
| nit | "`git mv` 로 했다" 는 쓴 명령을 말하는 것이라 레포 내용으로 확인할 수 없다 | **반영.** 확인할 수 있는 것으로 바꿨다. Git 이 이름 변경으로 인식하고 `git status` 가 `R` 로 적는다 |

### 5라운드 — 수리 확인

고친 기록 파일만 보냈다. 지적 1건이 나왔고 반영했다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | 3라운드 서술이 한국어는 "넷이 6, 6, 1, 1", 영어는 "세 행이 6, 1, 1" 이라 미러가 같은 사실을 말하지 않는다 | **반영.** 표는 네 행이고 그중 개수를 쓴 것은 세 행이다. 한국어를 영어에 맞췄다 |

**앞 라운드에서 내가 새로 쓴 문장이 다음 라운드의 지적이 됐다.** `CLAUDE.md` 가 말하는
그 기전이다. 수리 라운드는 고친 자리만이 아니라 그 자리에 내가 새로 쓴 서술까지 본다.

### 6라운드 — 확인할 수 있는 주장으로

같은 범위를 다시 보냈다. 지적 2건(각각 한국어와 영어)이 나왔고 둘 다 반영했다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | "전수 검색 0건" 인데 이 기록 자체가 옛 이름을 여러 번 적는다 | **반영.** 이 기록 두 파일을 예외로 밝혔다. 전후 대조표는 옛 이름을 적어야 뜻이 선다 |
| warn | "파일을 바이트로 읽어" 는 쓴 방법이라 레포로 재현할 수 없다 | **반영.** 볼 수 있는 것으로 바꿨다. diff 에 파일 전체가 바뀐 곳이 없다 |

**두 번 같은 종류의 지적을 받았다.** 쓴 방법을 적으면 읽는 쪽이 확인할 수 없다. 기록에는
결과를 적고, 그 결과를 무엇으로 확인했는지를 같이 적는다.

### 7라운드 — 기각 1건

3라운드와 같은 지적이 다시 왔다. 기각한다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | `decisions/0005` 행을 보낸 diff 로 재현할 수 없다 | **기각.** 그 변경은 이 커밋에 있다. 리뷰 입력을 기록 문서로만 좁힌 것이 원인이고 기록이 틀린 것이 아니다. 다음 라운드는 `decisions/` 를 범위에 넣고 그 사실을 프롬프트에 적어서 돌렸다 |

**같은 지적이 두 번 온 이유는 범위였다.** 좁힌 범위가 지적을 만들면 범위를 넓히거나
기각 사유를 프롬프트에 적는다. 그러지 않으면 라운드마다 같은 자리가 다시 올라온다.

### 8라운드 — 마지막

`decisions/` 를 범위에 넣고 기각 사유를 프롬프트에 적어 돌렸다. 7라운드의 지적은 다시
오지 않았다. nit 1건이 나왔고 반영했다.

| 등급 | 지적 | 처리 |
|------|------|------|
| nit | 한국어가 "위 기록 표" 인데 그 표는 아래에 있고 영어는 "below" 다 | **반영.** "아래 기록 표" 로 고쳤다 |

**라운드 기록은 여기서 멈춘다.** 라운드를 적으면 그 문장이 다음 라운드의 입력이 되어
끝나지 않는다.

**마지막 확인 라운드의 결과.** blocker 0건, warn 1건이었다. 그 warn 은 바로 이 줄이 아직
없다는 것이었고, 이 줄을 적어 반영했다. 코드 diff 에 대한 지적은 4라운드 뒤로 없다. 더
돌리지 않고 커밋한다.

**`LGTM` 을 근거로 쓰지 않았다.** 없다는 주장은 기계로 따로 확인했다. 전수 검색 0건,
`docgate.py` 판정, 빌드와 시험 통과가 그것이다.

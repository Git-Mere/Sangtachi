# Tunnel Protocol v1

**프로젝트:** Direct-First P2P Virtual Network for Multiplayer Games
**상태:** 구현 전 확정본. 이 문서와 코드가 다르면 코드가 틀린 것이다.
**설계 배경:** [`architecture.md`](architecture.md) / **요구사항:** [`spec.md`](spec.md)

> English version: [`../eng/protocol.md`](../eng/protocol.md)

목적은 **구현자가 아무것도 발명하지 않아도 되게** 하는 것이다. 값이 정해지지 않은 곳이 있으면 그것은 이 문서의 결함이다.

---

## 1. 범위와 전제

| 항목 | v1 확정값 |
|------|-----------|
| 외부 전송 | IPv4 UDP만 |
| 내부 페이로드 | IPv4 패킷만. 내부 IPv6는 폐기하고 카운터 증가 |
| 바이트 오더 | 모든 다중 바이트 정수는 **빅엔디안** |
| 피어 수 | 한 방에 2 피어 |
| 암호화 | 없음 (2장) |

IPv6 지원은 v2 이후다. v1은 `AF_INET`으로만 소켓을 열고 STUN 서버도 IPv4로만 해석한다.

---

## 2. 보안 모델

**v1은 기밀성, 무결성, 피어 인증, 재전송 공격 방어를 제공하지 않는다.** 이것은 누락이 아니라 명시적 선택이다.

경로상 또는 경로 밖 공격자가 `peer_id`와 `session_epoch`를 알거나 추측하면 다음이 가능하다.

- 게임 트래픽 도청 및 변조
- 임의 패킷 주입
- 위조 `CLOSE`로 세션 강제 종료
- 위조 `HELLO`로 세션 재협상 유도
- 엔드포인트 로밍(10.5)을 악용한 트래픽 탈취

8.4의 내부 패킷 검증은 **공격 방어 수단이 아니다.** 오배달, 버그, 잘못된 라우팅으로 인한 우발적 주입을 막는 위생 장치다. 이전 판에서 이 검사를 "유일한 주입 방어선"이라고 쓴 것은 과장이었다.

이 선택의 근거는 `spec.md`의 비목표다. 자체 암호 알고리즘 개발과 인증된 피어 세션은 스트레치 목표이며 v1 범위 밖이다. 최종 보고서는 이 한계를 명시해야 한다.

다만 **타인에게 피해를 주는 경로는 v1에서도 막는다.** 후보 목록은 검증 없이 주어지므로, 이를 이용하면 클라이언트가 공격자가 지정한 제3자에게 200ms마다 패킷을 보내는 반사 도구가 된다. 10.1의 후보 위생 규칙은 선택이 아니라 필수다.

## 3. 상수

```cpp
constexpr uint32_t TUNNEL_MAGIC   = 0x53414E47;  // "SANG"
constexpr uint8_t  TUNNEL_VERSION = 0x01;
constexpr size_t   HEADER_SIZE    = 20;
constexpr size_t   MAX_INNER      = 1452;
constexpr size_t   MAX_DATAGRAM   = HEADER_SIZE + MAX_INNER;   // 1472
constexpr uint32_t STUN_COOKIE    = 0x2112A442;                // RFC 5389
constexpr size_t   MAX_CANDIDATES = 8;                         // 피어당 상한
constexpr size_t   REPLAY_WINDOW  = 64;
constexpr size_t   MAX_PENDING_PINGS = 16;
```

`TUNNEL_MAGIC`의 첫 바이트 `0x53`은 상위 2비트가 `01`이고, STUN 메시지는 상위 2비트가 반드시 `00`이다. 이 성질이 7장 분류의 근거이므로 magic 값을 바꿀 때 유지해야 한다.

## 4. 헤더

### 4.1 와이어 레이아웃

```text
 오프셋  크기  필드              타입        설명
   0      4   magic             uint32 BE   0x53414E47 고정
   4      1   version           uint8       0x01 고정
   5      1   type              uint8       PacketType (5장)
   6      2   payload_length    uint16 BE   헤더 뒤 바이트 수
   8      4   peer_id           uint32 BE   송신 피어 식별자
  12      4   session_epoch     uint32 BE   송신 피어의 이번 세션 시도 식별자
  16      4   sequence          uint32 BE   방향별 단조 증가 카운터
  = 20 바이트
```

4바이트 필드가 모두 4의 배수 오프셋에 오므로 MSVC 기본 정렬에서도 패딩이 없다. 그래도 구조체를 `memcpy` 하지 않는다. 바이트 오더 변환이 필요하고 정렬이 우연히 맞는 것에 의존하면 조용히 깨진다. **필드 단위로 직렬화**하고 길이는 `HEADER_SIZE` 상수를 쓴다.

### 4.2 peer_id

제어 평면이 방 참가 시 할당한다. **한 방 안에서 유일하다.** 두 피어의 `peer_id`가 같으면 송신자 판별과 자기/상대 구분이 불가능하므로, 제어 평면은 그런 할당을 하지 않고 클라이언트는 `get_peers` 응답에서 자신과 같은 값을 발견하면 `CONTROL_PLANE_EXCHANGE_FAILED`로 중단한다.

### 4.3 session_epoch

**세션 시도 단위**로 뽑는다. 프로세스 단위가 아니다. `IDLE`에서 새 시도를 시작할 때마다 새로 뽑으며 그 시도가 끝날 때까지 바뀌지 않는다. 0은 쓰지 않는다.

이 필드가 없으면 재시작이나 재시도 후 이전 시도의 지연 패킷이 새 세션에 수용된다. 수신 측은 첫 유효 패킷에서 상대 epoch를 고정(pin)하고, 이후 다른 epoch의 패킷은 9장 규칙에 따라 처리한다.

32비트 난수이므로 충돌 가능성이 있다. 이전 시도의 epoch를 최대 2분간 **폐기 목록**에 보관하고, 폐기 목록에 있는 epoch를 담은 패킷은 전부 버린다. 이것으로 같은 값이 다시 뽑히는 경우를 제외한 대부분의 지연 패킷을 막는다.

### 4.4 sequence

- **방향별, 세션 시도별로 하나의 카운터.** 타입을 구분하지 않는다.
- 송신 직전에 0부터 1씩 증가시켜 할당한다. 재전송에도 새 번호를 준다.
- 32비트에서 순환한다.

```cpp
// a 가 b 보다 엄격히 새로운가. a == b 는 거짓이다.
bool is_newer(uint32_t a, uint32_t b) {
    return a != b && (uint32_t)(a - b) < 0x80000000u;
}
```

`a == b`에서 참을 반환하면 중복이 새 패킷으로 분류되어 재생 방어가 무력화된다.

### 4.5 중복 억제와 손실 집계

수신 측은 상대 epoch별로 아래 상태를 유지한다.

```cpp
uint32_t highest;      // 지금까지 받은 최대 sequence (32비트 순환)
uint64_t position;     // highest 의 순환 없는 64비트 확장 위치
uint64_t seen_bits;    // back=1..64 에 해당하는 수신 비트맵. back=b 는 비트 (b-1)
bool     initialized;
```

수신 패킷 처리 순서는 다음과 같다. **이 판정은 어떤 부수 효과보다 먼저 온다.** 유휴 타이머 갱신, 상태 전이, Wintun 주입, `PONG` 매칭은 전부 이 단계를 통과한 뒤에만 일어난다.

```text
initialized 가 거짓이면:
    highest = seq; position = 0; seen_bits = 0; initialized = true
    -> 수용 (전진). 이 패킷의 pkt_pos = 0

seq == highest 이면:
    -> 폐기, drop_duplicate

is_newer(seq, highest) 이면:                       // 전진
    shift = (uint32_t)(seq - highest)              // 1 .. 2^31-1
    if      shift >  64:  seen_bits = 0
    else if shift == 64:  seen_bits = uint64_t{1} << 63
    else:                 seen_bits = (seen_bits << shift) | (uint64_t{1} << (shift-1))
    highest   = seq
    position += shift
    -> 수용 (전진). 이 패킷의 pkt_pos = position

그 외 (오래됨):
    back = (uint32_t)(highest - seq)               // 1 .. 2^31
    back > 64                            -> 폐기, drop_too_old
    seen_bits & (uint64_t{1}<<(back-1))  -> 폐기, drop_duplicate
    seen_bits |= uint64_t{1} << (back-1)
    -> 수용 (전진 없음). 이 패킷의 pkt_pos = position - back
```

경계 네 가지를 틀리기 쉽다.

- **`seq == highest`를 먼저 걸러야 한다.** `is_newer`는 `a == b`에서 거짓이므로 이 경우가 아래 분기로 내려가고, `back == 0`이 되어 `uint64_t{1} << (0-1)`이라는 미정의 동작이 된다. 명시적 중복 판정으로 먼저 처리한다.
- **세 분기는 상호 배타여야 한다.** `if / if / else`로 쓰면 `shift > 64`가 비트맵을 지운 뒤 `else`로도 들어가 64를 넘는 시프트를 수행한다. `if / else if / else`로 쓴다.
- **`shift == 64`에서 비트맵을 지우면 안 된다.** 지우면 직전 `highest`가 `back == 64` 위치에 미기록 상태로 남아 그 패킷이 중복인데도 다시 수용된다. `shift == 64`는 비트 63을 세우는 경우다. `seen_bits << 64`는 C++에서 미정의 동작이므로 별도 분기로 처리한다.
- **모든 비트 연산은 `uint64_t`로 한다.** `1 << 63`은 `int` 시프트라 미정의 동작이다.

**손실 집계는 `CONNECTED` 진입 시점에 초기화한다.** 펀치 구간에는 여러 후보로 보낸 `HELLO`가 각각 번호를 소모하지만 실제로 도달하는 경로는 하나뿐이므로, 그 구간의 간격을 손실로 세면 실측이 오염된다.

`CONNECTED`로 전이시킨 패킷을 처리한 **직후**에 기준선을 잡는다.

```text
baseline = position          // 전이 패킷 처리 후의 값
accepted = 0                 // baseline 보다 뒤에서 수용한 고유 패킷 수

이후 수용될 때마다: 그 패킷의 pkt_pos 가 baseline 보다 크면 accepted += 1

expected = position - baseline
손실     = expected - accepted
손실률   = expected > 0 이면 손실 / expected, 아니면 0
```

32비트 `sequence`가 아니라 순환 없는 64비트 `position`으로 계산하므로 시퀀스가 한 바퀴 돌아도 값이 무너지지 않는다.

`pkt_pos`는 전진 패킷이면 갱신된 `position`, 재정렬 패킷이면 `position - back`이다. 상태값 `position`을 그대로 쓰면 `baseline` 이전에 보내진 재정렬 패킷까지 `accepted`에 세어 `accepted > expected`가 되고 `손실`이 음수로 언더플로한다. `baseline` 이하의 재정렬 패킷을 정확히 배제해야 이 문제가 없다.

`drop_too_old`로 버린 패킷은 이미 손실로 확정된 것이므로 되돌리지 않는다. 손실률은 10초 주기로 스냅샷을 찍어 텔레메트리에 올린다.

## 5. 패킷 타입

| 값 | 이름 | 페이로드 길이 | 용도 |
|----|------|---------------|------|
| `0x01` | `HELLO` | 20 | 홀펀칭 및 핸드셰이크 개시 |
| `0x02` | `HELLO_ACK` | 20 | 상대 `HELLO`를 실제로 받았음을 증명 |
| `0x03` | `KEEPALIVE` | 0 | NAT 매핑 유지 |
| `0x04` | `DATA` | 20 ~ 1452 | 내부 IPv4 패킷 운반 |
| `0x05` | `PING` | 8 | RTT 측정 요청 |
| `0x06` | `PONG` | 8 | RTT 측정 응답 |
| `0x07` | `CLOSE` | 1 | 정상 종료 통지 |

목록에 없는 값은 폐기하고 `drop_unknown_type`을 올린다.

### 5.1 HELLO (20바이트)

```text
 오프셋  크기  필드         설명
   0     16   nonce        이번 시도의 128비트 난수
  16      4   virtual_ip   송신자에게 할당된 가상 IP (uint32 BE)
```

`nonce`는 **OS CSPRNG**에서 뽑는다(`BCryptGenRandom`). 세션 시도당 하나이며 재전송에서는 같은 값을 쓴다. 재전송마다 바꾸면 도착한 `HELLO_ACK`이 어느 nonce에 대한 응답인지 맞출 수 없다. 이전 시도의 nonce는 폐기 목록에 2분간 보관하고 재사용하지 않는다.

`virtual_ip`의 소비자: 수신 측은 제어 평면이 알려준 상대의 가상 IP와 비교한다. 다르면 폐기하고 `drop_vip_mismatch`를 올린다.

**probe nonce.** 10.4 (c)의 경로 검증용 `HELLO`는 시도 nonce가 아니라 별도의 **probe nonce**를 쓴다. 잠정 경로마다 하나씩 뽑아 5초간 별도 표에 보관한다. "시도당 하나"라는 위 규칙은 시도 nonce에만 적용된다. 두 종류를 같은 표에 섞으면 경로 검증 응답과 핸드셰이크 응답을 구분할 수 없다.

### 5.2 HELLO_ACK (20바이트)

```text
 오프셋  크기  필드         설명
   0     16   echo_nonce   응답 대상 HELLO 의 nonce 를 그대로 복사
  16      4   virtual_ip   송신자에게 할당된 가상 IP (uint32 BE)
```

`virtual_ip` 처리는 5.1과 같다.

### 5.3 KEEPALIVE (0바이트)

페이로드 없음.

### 5.4 DATA (20 ~ 1452바이트)

페이로드는 **완전한 내부 IPv4 패킷**이다. 이더넷 헤더도 추가 래핑도 없다.

### 5.5 PING / PONG (각 8바이트)

```text
 오프셋  크기  필드      설명
   0      8   ping_id   uint64 BE
```

`ping_id`는 세션 시도마다 0에서 시작해 1씩 증가한다. **타임스탬프를 와이어에 싣지 않는다.** 송신 시각은 로컬 표에만 둔다.

```cpp
uint64_t id = next_ping_id++;
pending_pings[id] = steady_clock::now();
```

- `pending_pings`는 최대 `MAX_PENDING_PINGS`(16)개다. 삽입 전에 5초가 지난 항목을 제거하고, 그래도 가득 차면 새 `PING`을 보내지 않는다.
- `PONG` 수신 시 `ping_id`로 조회한다. 없으면 폐기하고 `drop_unmatched_pong`을 올린다. 있으면 RTT를 계산하고 **항목을 제거한다.** 각 `ping_id`는 한 번만 유효하다.
- 5초를 넘긴 항목은 표본을 버리고 제거한다.

`PONG`은 받은 `ping_id`를 그대로 되돌려준다.

### 5.6 CLOSE (1바이트)

```text
 오프셋  크기  필드      설명
   0      1   reason    0x00 정상 종료, 0x01 사용자 취소, 0x02 설정 오류
```

`0x00`~`0x02` 외의 값은 폐기하고 `drop_bad_reason`을 올린다. 정상 종료 시 best-effort로 1회 보낸다. 재전송하지 않고 응답도 기다리지 않는다. 수신 측은 즉시 세션과 라우팅 항목을 제거한다.

`CLOSE`가 없으면 정상 종료와 크래시를 구분할 수 없어 상대가 50초 유휴 타임아웃까지 죽은 세션을 붙든다. 크래시 대비로 유휴 타임아웃은 유지한다.

## 6. 소켓 소유권

**하나의 로컬 UDP 소켓을 하나의 수신 루프가 배타적으로 소유한다.** 그 루프의 스레드 구성, 대기 방식, 상태 소유 범위는 [`architecture.md`](architecture.md) 3.2에 있다.

- STUN 클라이언트는 `recvfrom`을 직접 호출하지 않는다. 요청을 등록하고 응답을 수신 루프에서 전달받는다. 두 곳에서 읽으면 서로의 패킷을 소비한다.
- 소켓은 프로세스 시작 시 한 번 bind 하고 종료까지 유지한다. 재바인드하면 NAT 매핑이 바뀐다.
- `SO_REUSEADDR`를 쓰지 않는다. Windows에서 다른 소켓이 같은 엔드포인트를 bind 해 배달이 비결정적이 된다. `SO_EXCLUSIVEADDRUSE`를 쓴다.
- `connect()`를 호출하지 않는다. 연결된 UDP 소켓은 다른 출발지 데이터그램을 걸러내므로 STUN 서버와 여러 후보를 동시에 다룰 수 없다.
- **`SIO_UDP_CONNRESET`를 끈다.** 끄지 않으면 응답 없는 후보가 보낸 ICMP port unreachable이 `WSAECONNRESET`으로 올라와 수신 루프를 종료시킨다. 홀펀칭은 응답 없는 후보로 계속 쏘는 것이 정상이므로 이걸 빠뜨리면 Phase 4에서 반드시 터진다.

```cpp
BOOL off = FALSE;
DWORD bytes = 0;
WSAIoctl(sock, SIO_UDP_CONNRESET, &off, sizeof(off), nullptr, 0, &bytes, nullptr, nullptr);
```

## 7. 수신 분류

수신 루프는 데이터그램마다 **첫 바이트의 상위 2비트로만** 분류한다. magic과 version은 분류 기준이 아니라 검증 항목이다. 분류 단계에서 magic을 보면 magic이 틀린 패킷이 터널 파이프라인에 도달하지 못해 `drop_magic` 카운터가 영원히 0이 되고, 터널을 겨냥한 악성 트래픽이 `drop_unclassified`에 섞여 보이지 않게 된다.

```text
(buf[0] & 0xC0) == 0x00  이고  len >= 20  이고  buf[4..8) == STUN_COOKIE
      -> STUN 메시지. 트랜잭션 ID로 대기 중인 요청과 매칭 (13장)
(buf[0] & 0xC0) == 0x40
      -> 터널 후보. 8장 검증 파이프라인으로
그 외
      -> 폐기, drop_unclassified
```

`buf[a..b)`는 반열린 구간이다. `buf[4..8)`은 오프셋 4,5,6,7의 4바이트다.

## 8. 수신 검증 파이프라인

터널 후보는 아래 순서로 검사한다. 각 단계마다 전용 폐기 카운터를 둔다. 하나라도 실패하면 즉시 폐기한다.

### 8.1 공통 검사

| # | 검사 | 실패 카운터 |
|---|------|-------------|
| 1 | `len >= HEADER_SIZE` | `drop_short` |
| 2 | `magic == TUNNEL_MAGIC` | `drop_magic` |
| 3 | `version == TUNNEL_VERSION` | `drop_version` |
| 4 | `type`이 5장 목록에 있음 | `drop_unknown_type` |
| 5 | `payload_length == len - HEADER_SIZE` | `drop_length` |
| 6 | 타입별 길이 규정 충족: `HELLO`/`HELLO_ACK` 정확히 20, `KEEPALIVE` 0, `PING`/`PONG` 8, `CLOSE` 1, `DATA` 20~1452 | `drop_type_length` |
| 7 | `peer_id`가 이 방의 상대 피어 ID와 일치 | `drop_unknown_peer` |
| 8 | `session_epoch`가 폐기 목록에 없음 | `drop_retired_epoch` |

### 8.2 epoch 및 출발지 검사

`HELLO`와 `HELLO_ACK`은 **nonce로 스스로를 증명**하므로 epoch 고정 전에도 통과해야 한다. 나머지 타입은 epoch가 고정된 뒤에만 유효하다.

| 타입 | 규칙 |
|------|------|
| `HELLO` | epoch 고정 여부와 무관하게 수용. 출발지 제한 없음. 9.3의 epoch 규칙 적용 |
| `HELLO_ACK` (시도 nonce echo) | `echo_nonce`가 **우리가 이번 시도에서 보낸 nonce**와 일치. 핸드셰이크 증거로 쓰고(`got_ack`), epoch가 미고정이면 이 패킷으로 고정한다 |
| `HELLO_ACK` (probe nonce echo) | `echo_nonce`가 활성 probe nonce 중 하나와 일치하고 출발지가 그 probe를 보낸 주소와 같을 것. **해당 잠정 경로만 검증한다.** `got_ack`를 세우지 않고 epoch도 고정하지 않는다 |
| `HELLO_ACK` (그 외) | 폐기, `drop_bad_nonce` |
| 그 외 전부 | epoch 미고정이면 폐기, `drop_no_epoch`. 고정된 값과 다르면 폐기, `drop_stale_epoch` |

이 규칙이 없으면 "선행 `HELLO_ACK`은 정상"이라는 9.4의 서술과 epoch 검사가 서로 모순되어, 상대가 먼저 펀치를 시작한 정상 상황에서 양쪽이 타임아웃한다.

### 8.3 중복 억제

4.5의 판정을 적용한다. `drop_duplicate` 또는 `drop_too_old`로 버려진 패킷은 **유휴 타이머를 갱신하지 않고 어떤 상태도 바꾸지 않는다.**

### 8.4 DATA 내부 검증

`DATA`는 Wintun 주입 직전에 아래를 전부 통과해야 한다.

| # | 검사 | 실패 카운터 |
|---|------|-------------|
| 9 | 상태가 `CONNECTED` | `drop_data_early` |
| 10 | 내부 IP 버전 니블 == 4 | `drop_inner_not_ipv4` |
| 11 | 내부 IHL이 5~15이고 `IHL*4 <= payload_length` | `drop_inner_ihl` |
| 12 | 내부 IPv4 헤더 체크섬 유효 | `drop_inner_checksum` |
| 13 | 내부 `total_length == payload_length` | `drop_inner_length` |
| 14 | 내부 출발지 IP == 상대 피어의 가상 IP | `drop_inner_src` |
| 15 | 내부 목적지 IP == 자신의 가상 IP | `drop_inner_dst` |

14번과 15번은 오배달과 라우팅 버그로 인한 우발적 주입을 막는 위생 장치다. 2장에서 밝힌 대로 **공격 방어 수단이 아니다.**

### 8.5 송신 측 검증

Wintun에서 읽은 패킷은 아래를 통과해야 `DATA`로 캡슐화한다.

| 검사 | 실패 카운터 |
|------|-------------|
| 상태가 `CONNECTED` | `tx_drop_not_connected` |
| IP 버전 니블 == 4 | `tx_drop_not_ipv4` |
| 길이 <= `MAX_INNER` | `tx_drop_oversize` |
| 출발지 IP == 자신의 가상 IP | `tx_drop_bad_src` |
| 목적지 IP == 상대 피어의 가상 IP | `tx_drop_no_route` |

## 9. 세션

### 9.1 상태

| 상태 | 의미 |
|------|------|
| `IDLE` | 아직 상대 후보를 받지 못함 |
| `PUNCHING` | `HELLO` 재전송 중. 왕복 증거 없음 |
| `HANDSHAKING` | 한쪽 증거만 확보 |
| `CONNECTED` | 양쪽 증거 확보 |
| `FAILED` | 실패 코드와 함께 종료 |
| `CLOSED` | 정상 종료 |

### 9.2 CONNECTED 조건

```text
got_ack   = 우리 nonce 를 echo 한 HELLO_ACK 을 받았다      (우리 -> 상대 경로 확인)
sent_ack  = 상대의 유효한 HELLO 에 HELLO_ACK 을 보냈다      (상대 -> 우리 경로 확인)

CONNECTED  <=>  got_ack && sent_ack
```

`sent_ack`는 `sendto`가 성공을 반환한 뒤에만 세운다. 실패하면 `tx_err_ack`를 올리고 세우지 않는다.

둘 중 하나만 선 것이 `HANDSHAKING`이다. **어느 쪽이 먼저 서는지는 정해져 있지 않다.** 순서를 가정하면 한쪽만 뚫린 경로를 연결로 오판하거나 정상 순서에서 양쪽이 타임아웃한다.

`CONNECTED` 진입 시 손실 집계 상태를 초기화한다(4.5).

### 9.3 epoch 규칙

| 상황 | 동작 |
|------|------|
| epoch 미고정 상태에서 유효한 `HELLO` 또는 nonce 일치 `HELLO_ACK` 수신 | 그 패킷의 epoch를 고정 |
| 고정된 epoch와 같은 패킷 | 정상 처리 |
| 고정된 epoch와 다른 `HELLO` 수신 | **상대가 재시도했다.** 9.5의 재협상 절차 |
| 고정된 epoch와 다른 그 외 패킷 | 폐기, `drop_stale_epoch` |
| 폐기 목록에 있는 epoch | 폐기, `drop_retired_epoch` |

### 9.4 전이표

| 수신 \ 상태 | `PUNCHING` | `HANDSHAKING` | `CONNECTED` |
|---|---|---|---|
| `HELLO` (epoch 일치 또는 미고정) | `HELLO_ACK` 응답, `sent_ack=true`, 출발지 학습 | 같음 (중복이면 `HELLO_ACK`만 재응답) | **`HELLO_ACK`을 다시 보낸다.** 상대 ACK가 유실된 상황이므로 무시하면 상대가 타임아웃한다 |
| `HELLO` (다른 epoch) | 9.5 재협상 | 9.5 재협상 | 9.5 재협상 |
| `HELLO_ACK` (우리 nonce echo) | `got_ack=true`, 출발지 학습, epoch 미고정이면 고정 | 같음 | 중복. 무시, `dup_ack` |
| `HELLO_ACK` (모르는 nonce) | 폐기, `drop_bad_nonce` | 같음 | 같음 |
| `KEEPALIVE` | 유휴 타이머 갱신, 출발지 학습 | 같음 | 같음 |
| `PING` | `PONG` 응답 | 같음 | 같음 |
| `PONG` | 5.5 매칭 | 같음 | 같음 |
| `DATA` | 폐기, `drop_data_early` | 폐기, `drop_data_early` | 8.4 검증 후 주입 |
| `CLOSE` | `CLOSED` 전이 | `CLOSED` 전이 | `CLOSED` 전이 |

**`PUNCHING`에서 `HELLO_ACK`이 먼저 오는 것은 정상이다.** 상대가 먼저 펀치를 시작했고 우리 `HELLO`는 도착했지만 상대 `HELLO`가 아직 안 온 경우다.

**해당 타입에 적용되는 모든 검증을 통과한 패킷만** 유휴 타이머를 갱신한다. 모든 타입에 8.1~8.3이 적용되고, `DATA`는 8.4까지, `PONG`은 5.5의 `ping_id` 매칭까지, `CLOSE`는 reason 값 검증까지 포함한다. 11장의 표기도 같은 뜻이다.

### 9.5 재협상

고정된 epoch와 다른 `HELLO`를 받으면 상대가 새 시도를 시작한 것이다. 원자적으로 아래를 수행한다.

1. **상대의** 이전 epoch를 폐기 목록에 2분간 등록
2. `got_ack`, `sent_ack`를 거짓으로 초기화
3. 중복 억제 상태, `pending_pings`, 손실 집계를 초기화
4. 상대 epoch를 새 값으로 고정
5. **우리 쪽 `session_epoch`와 nonce는 그대로 유지한다**
6. 수신한 `HELLO`에 대한 `HELLO_ACK`을 **그 데이터그램의 출발지로 직접** 보낸다. `peer_endpoint`는 바꾸지 않는다
7. 상태를 `PUNCHING`으로 되돌리고, 펀치 마감을 **이 시점부터** 10초로 다시 잡는다
8. 제어 평면을 다시 거치지 않고 기존 후보 목록을 재사용한다

5번이 핵심이다. 상대의 재시도에 반응해 우리도 epoch를 바꾸면, 상대가 그것을 다시 재시도로 인식해 또 바꾸고, **두 피어가 epoch를 무한히 주고받으며 영원히 연결되지 않는다.** 로컬 epoch는 우리가 `IDLE`에서 새 시도를 시작할 때만 바뀐다.

2~3번 초기화를 빠뜨리면 이전 epoch에서 얻은 `got_ack`나 `sent_ack`가 남아 새 세션을 검증 없이 `CONNECTED`로 만든다.

6번에서 `peer_endpoint`를 바꾸지 않는 것이 중요하다. 재협상을 유발한 `HELLO`의 출발지가 후보 목록에 없을 수 있고, 거기서 바로 전환하면 위조된 재시도 `HELLO` 하나로 트래픽 전체를 임의의 주소로 돌릴 수 있다. 10.4의 경로 검증을 우회하는 셈이다.

**단건 응답과 대량 전환을 구분한다.** `HELLO_ACK`을 받은 데이터그램의 출발지로 되돌려 보내는 것은 안전하다. 위조된 주소로 가더라도 응답 1개이고 증폭이 없으며, 정상적인 NAT 리바인딩이라면 상대가 그 응답을 받는다. 반면 `peer_endpoint` 전환은 이후의 모든 `DATA`를 그쪽으로 보낸다는 뜻이므로 10.4 (c) 검증을 거쳐야 한다. 출발지가 후보 집합 안이면 10.4에 따라 전진 패킷에서 자동 전환되고, 밖이면 경로 검증 뒤에만 전환된다.

### 9.6 실패 전이

| 조건 | 기록 코드 |
|------|-----------|
| STUN 마감 초과 | `STUN_DISCOVERY_FAILED` |
| `get_peers` 폴링 마감 초과, 제어 평면 오류, 또는 `peer_id` 충돌 | `CONTROL_PLANE_EXCHANGE_FAILED` |
| 펀치 마감까지 `got_ack`, `sent_ack` 둘 다 미성립 | `HOLE_PUNCH_TIMEOUT` |
| 펀치 마감까지 하나만 성립 | `PEER_HANDSHAKE_FAILED` |
| `CONNECTED` 이후 유휴 타임아웃 | `TUNNEL_DROPPED` |

`FAILED`는 종료 상태다. 재시도는 `IDLE`부터 새 시도로 시작하며 새 epoch와 새 nonce를 뽑는다.

## 10. 후보와 엔드포인트

### 10.1 후보 수집과 위생

각 피어가 제어 평면에 등록하는 후보:

- **로컬 후보**: 활성 IPv4 인터페이스 주소. 루프백, APIPA(`169.254.0.0/16`), 자신의 Wintun 어댑터, 다른 터널/VPN 어댑터를 제외한다.
- **서버 반사 후보**: STUN으로 얻은 공인 엔드포인트. 질의한 STUN 서버별로 기록한다.

**수신한 후보 목록에 아래 위생 규칙을 적용한다. 선택이 아니다.**

| 규칙 | 근거 |
|------|------|
| 최대 `MAX_CANDIDATES`(8)개. 초과분은 버린다 | 무제한 목록은 무제한 송신을 뜻한다 |
| 브로드캐스트, 멀티캐스트(`224.0.0.0/4`), 미지정(`0.0.0.0`), 루프백(`127.0.0.0/8`) 주소 거부 | 반사 및 증폭 방지 |
| 포트 0 거부 | |
| 중복 제거 | |

2장에서 밝힌 대로, 이 규칙이 없으면 클라이언트가 공격자 지정 제3자에게 200ms마다 패킷을 보내는 반사 도구가 된다.

### 10.2 랑데부

펀치 시작이 어긋나면 한쪽 패킷이 상대 NAT에 전부 버려진다.

1. 두 피어가 각각 `register_candidate`를 완료한다.
2. `get_peers`는 양쪽 등록 전에는 `not_ready`를 반환한다.
3. **두 번째 등록이 완료되는 순간 서버가 `punch_delay_ms = 1000`을 방 단위로 한 번 확정해 저장한다.** 이후 모든 `get_peers` 응답은 저장된 값을 그대로 돌려준다. 응답마다 새로 계산하면 두 피어가 서로 다른 시각을 받는다.
4. 응답에는 `punch_delay_ms`와 함께 `elapsed_since_ready_ms`(서버가 준비 완료 이후 흐른 시간)를 담는다. **절대 시각을 쓰지 않는다.** 클라이언트 시계가 동기화되어 있다는 보장이 없다.
5. 클라이언트는 `get_peers`를 500ms 간격으로 폴링한다. 최대 60초.
6. 준비 완료 응답을 받으면 `max(0, punch_delay_ms - elapsed_since_ready_ms)` 밀리초 뒤에 펀치를 시작한다. 음수면 즉시 시작한다.

상대가 50초 늦게 클라이언트를 켜도 동작한다. 먼저 켠 쪽은 계속 폴링하고 있고, 준비가 되는 순간 양쪽이 같은 기준점에서 지연을 계산한다.

**남는 오차의 상한.** 두 피어의 실제 펀치 시작 시각 차이는 `폴링 간격(500ms) + 두 응답의 전송 지연 차이`로 제한된다. 서버가 준비 완료를 판정한 시점부터 각자가 응답을 받기까지 걸린 시간이 `elapsed_since_ready_ms`에 반영되지 않기 때문이다. 일반적인 조건에서 이 값은 1초 미만이고, 펀치 구간 10초와 200ms 재전송이 충분히 흡수한다. 이 상한을 넘는 환경(예: 응답 지연이 수 초)에서는 펀치 구간을 늘려야 하며, 그 경우 이 문서를 갱신한다.

### 10.3 펀치

- 펀치 시작부터 **상대의 모든 후보에** `HELLO`를 200ms 간격으로 보낸다.
- 펀치 마감은 **실제 로컬 시작 시각으로부터 10초**다. 예정 시각이 이미 지나서 즉시 시작한 경우에도 마감은 그 시점부터 10초다.
- 마감까지 `CONNECTED`에 도달하지 못하면 9.6에 따라 실패 기록.

### 10.4 엔드포인트 학습

v1은 고정 지명(nomination) 대신 **학습(learning)** 을 쓴다.

```text
peer_endpoint = 아래 조건을 모두 만족하는 가장 최근 패킷의 출발지 엔드포인트

  (a) 해당 타입의 모든 검증을 통과했다
      (8.1~8.3 공통 + DATA 는 8.4, PONG 은 5.5 매칭, CLOSE 는 reason 검증까지)
  (b) 4.5 에서 highest 를 **전진**시켰다 (재정렬 수용 패킷은 제외)
  (c) 출발지가 승인된 후보 집합에 있거나, 경로 검증(아래)을 통과했다
```

모든 송신은 `peer_endpoint`로 보낸다. 아직 학습 전이면(펀치 중) 모든 후보로 보낸다.

**(b)가 없으면** 재정렬 윈도우 안에서 수용된 오래된 패킷이 엔드포인트를 이전 경로로 되돌린다. 전진한 패킷만 학습에 쓰면 되돌림이 생기지 않는다.

**(c)의 경로 검증.** 후보 집합에 없는 주소에서 패킷이 오면 즉시 전환하지 않는다. NAT 리바인딩으로 포트가 바뀐 정상적인 경우와, 출발지를 위조한 공격의 구분이 불가능하기 때문이다.

```text
1. 새 주소를 잠정 경로로 기록한다. peer_endpoint 는 그대로 둔다.
2. 그 주소로 probe nonce 를 담은 HELLO 를 보낸다 (5.1).
3. 같은 주소에서 그 probe nonce 를 echo 한 HELLO_ACK 이 오면 그때 peer_endpoint 를 전환한다.
   이 ACK 은 핸드셰이크 상태(got_ack, epoch)를 바꾸지 않는다.
4. 5초 안에 오지 않으면 잠정 경로를 버리고 path_probe_failed 를 올린다.
```

**이 절차의 전제와 실측 한계.** 1번은 **후보 집합 밖 주소에서 패킷이 실제로 도착한다**는 것을 전제한다. 실측에서 그 전제가 성립하지 않는 경우를 확인했다. 측정한 망 3쌍(Windows↔Windows, Windows↔macOS, Windows↔Linux) 모두에서, **출발지 IP는 같고 출발지 포트만 다른** UDP가 양방향 전부 차단됐다(6건, 각 20발 중 0발 도착).

**가장 유력한 설명은 NAT의 포트 제한 필터링이다.** 호스트 방화벽 필터링이 없다고 보이는 macOS와 Linux에서도 같은 결과였기 때문이다. 다만 **단정하지는 않는다.** macOS 쪽은 기본값에 근거한 추론이고 직접 조회하지 않았으며, Linux 쪽은 `ufw` 가 꺼진 것만 확인했고 root 권한이 없어 `nft`/`iptables` 규칙 전체는 보지 못했다. 양쪽 패킷 캡처도 하지 않았다.

**따라서 v1은 (c)로 NAT 리바인딩을 복구한다고 보장하지 않는다.** 정확히는, **시험한 거동(출발지 포트만 바뀐 경우)과 일치하는 엔드포인트 변화에 대해 보장하지 않는다.** 실제 리바인딩을 인위적으로 일으켜 시험하지는 않았으므로 "모든 리바인딩에서 실패한다"고 주장하지 않는다. 보장되지 않는 경우에는 1번이 시작되지 않고, 같은 이유로 9.5 재협상도 계기를 얻지 못한다. 그때는 양쪽이 유휴 타임아웃(50s)에 도달해 `TUNNEL_DROPPED`로 세션이 끝난다. 9.6이 정한 대로 **재시도를 한다면** `IDLE`부터 새 epoch와 새 nonce로 시작하며 제어 평면을 다시 거친다. **재시도를 누가 언제 개시하는지는 이 문서가 정하지 않았다.** 자동 재시도 여부는 미정이다.

(c)를 없애지는 않는다. 두 가지 이유다. 첫째, **위조 출발지 방어**라는 보안 역할이 그대로 남는다. 후보 집합 밖 주소에서 패킷이 도착하기만 하면 그 검증이 필요하다. 둘째, **주소 제한(restricted cone) 필터링을 쓰는 NAT에서는 도착할 수 있다.** 이번 관측은 전부 포트 제한 NAT과 **일치할 뿐**이고, 그렇다고 확정된 것은 아니다. 근거와 버린 대안은 [`decisions/0002-리바인딩-복구-미보장.md`](decisions/0002-리바인딩-복구-미보장.md)에 있다.

출발지를 위조한 공격자는 2번의 `HELLO`를 받지 못하므로 3번을 통과할 수 없다. 이것이 2장에서 약속한 "제3자 피해 경로 차단"을 학습 방식에서도 유지하는 방법이다. 이 절차가 없으면 세션 식별자를 아는 쪽이 출발지를 위조해 게임 트래픽 전체를 임의의 피해자에게 돌릴 수 있다.

지명 방식을 쓰지 않는 이유는 세 가지다.

- **같은 NAT 뒤**: 두 피어가 LAN 경로와 헤어핀 공인 경로를 각각 지명하면 서로 다른 엔드포인트에 고정되어 상대 패킷이 전부 걸러지는 교착이 생긴다.
- **비대칭 지명**: 한쪽은 LAN 후보로 받고 다른 쪽은 공인 후보로 보내면 같은 교착이 생긴다.
- **NAT 리바인딩**: 매핑이 바뀌어도 epoch는 그대로이므로, 고정 방식에서는 재협상 계기가 없어 유휴 타임아웃까지 기다려야 한다. **이 이유는 실측으로 약해졌다.** 학습 방식도 **시험한 거동(출발지 포트만 바뀌고 관측된 필터링에 걸리는 경우)과 일치하는 리바인딩에 대해서는 복구를 보장하지 못한다**(위 (c)의 실측 한계 참조). 즉 **두 방식을 가르는 근거가 되지 못한다.** 리바인딩 자체를 일으켜 시험한 것이 아니므로 이 이유가 모든 리바인딩에서 무효라고 주장하지도 않는다. 나머지 두 이유는 유효하므로 학습 방식 자체는 유지한다.

학습 방식은 **가장 최근에 실제로 도착한 경로**를 쓰므로 앞의 두 경우(같은 NAT 뒤, 비대칭 지명)는 자동으로 수렴한다. **리바인딩은 다르다.** 후보 집합 밖 주소에서 패킷이 실제로 도착해야 10.4 (c)가 시작되고, 도착하지 않으면 수렴하지 않는다. 중복 억제(4.5)가 오래된 패킷을 먼저 걸러내므로 이전 경로의 지연 패킷이 엔드포인트를 되돌리지 못한다.

엔드포인트가 바뀌면 `endpoint_learned` 카운터를 올린다. 이 값이 계속 증가하면 경로가 진동하는 것이므로 진단에 쓴다.

### 10.5 보안 결과

10.4 (c)의 경로 검증 덕분에, 세션 식별자를 아는 공격자가 **출발지만 위조해서** 트래픽을 제3자에게 돌리는 것은 v1에서도 막힌다. 검증용 `HELLO`가 위조된 주소로 가므로 공격자가 응답할 수 없다.

막지 못하는 것은 여전히 남는다. 공격자가 실제로 패킷을 받을 수 있는 주소를 쓰면(자기 주소) 경로 검증을 통과해 트래픽을 자신에게 끌어올 수 있다. 내용을 읽고 변조하는 것도 막지 못한다. 2장의 전제상 v1은 이를 막지 않으며, 암호화와 피어 인증을 도입할 때 경로 검증에 MAC을 붙여야 한다.

| `pending_pings` 정리 | 삽입 전 매회 | - | - | - |

마감 비교는 **엄격 부등호**를 쓴다. 우선순위는 **큐에서 꺼낸 시각** 기준이다. 같은 바퀴에 꺼낸 수신 이벤트가 그 바퀴의 타이머 만료보다 먼저 처리된다.

도착 시각이 아니라 꺼낸 시각인 이유는 수신 루프가 한 바퀴에 처리하는 데이터그램 수에 상한을 두기 때문이다([`architecture.md`](architecture.md) 3.2.3). 상한 없이 비우면 타이머가 아예 돌지 않는다. 그 대신 마감 직전에 도착한 데이터그램이 다음 바퀴로 밀려 타이머에 질 수 있다. 루프가 부하를 따라가는 동안 이 지연은 1ms 미만이고, 가장 짧은 마감(200ms)보다 두 자릿수 작다. 루프가 지속적으로 못 따라가면 소켓 버퍼가 넘쳐 패킷이 버려진다. 그것은 타이머 순서 문제가 아니라 과부하다.

유휴 타임아웃이 45s가 아니라 **50s**인 이유: `CONNECTED` 진입 즉시 keepalive를 1회 보내므로 45s 안에 0s, 15s, 30s, 45s의 4회 송신 기회가 있다. 45s로 잡으면 마지막 송신과 타임아웃이 같은 시각에 경합한다. 50s는 3회 손실을 견디고 네 번째에 회복할 여유를 준다.

15s와 50s는 초기값이다. 매핑 수명 실측으로 조정하면 이 문서를 갱신한다.

## 12. 크기 제한과 조각화

```text
1500 (외부 경로 MTU 가정)
 - 20 (외부 IPv4 헤더)
 -  8 (외부 UDP 헤더)
 - 20 (터널 헤더)
= 1452 바이트 = MAX_INNER
```

가상 어댑터 MTU 기본값은 **1400**이다. `MAX_INNER`보다 52바이트 여유를 둬서 외부 경로 MTU가 1448까지 떨어져도 버틴다.

**외부 UDP 패킷에 DF 비트를 세우지 않는다.** Windows에서 `IP_DONTFRAGMENT`는 UDP 기본값이 off이므로 켜지 않으면 된다. DF를 세우면 경로 MTU가 작을 때 중간 라우터가 조용히 버려서 작은 패킷만 통과하고 큰 패킷이 사라진다. **내부 TCP가 재전송 블랙홀에 빠진다.** 로그인은 되는데 월드 로딩에서 멈추는 전형적 증상이 이것이다.

완전한 PMTU 탐색은 v1 범위 밖이다. 실측으로 기본값을 확정하고 한계를 [`experiments.md`](experiments.md)에 기록한다.

## 13. STUN 사용 범위

RFC 5389 중 아래만 구현한다.

- **메시지**: Binding Request(`0x0001`), Binding Success Response(`0x0101`), Binding Error Response(`0x0111`)
- **송신 속성**: 없음. Binding Request는 헤더만 보낸다
- **해석 속성**: `XOR-MAPPED-ADDRESS`(`0x0020`)만. 나머지 속성은 건너뛴다. `ERROR-CODE`는 값만 로그에 남긴다
- **트랜잭션 ID**: OS CSPRNG로 96비트
- **응답 검증**: magic cookie 일치, 트랜잭션 ID 일치, 메시지 길이가 헤더의 길이 필드와 일치, 속성 순회 중 경계 초과 시 중단
- **주소군**: `XOR-MAPPED-ADDRESS`의 family가 IPv4(`0x01`)가 아니면 폐기
- **재시도**: 11장 표

FINGERPRINT, MESSAGE-INTEGRITY, 인증, TURN, ICE 절차는 구현하지 않는다.

## 14. 제어 평면 스키마

`register_candidate`와 `get_peers`의 요청/응답 인코딩, 오류 스키마, 상태 전이는 이 문서 범위 밖이며 **별도 문서로 확정해야 한다.** 이 문서가 제어 평면에 요구하는 계약은 다음뿐이다.

1. `peer_id`는 방 안에서 유일하다 (4.2)
2. `get_peers`는 양쪽 등록 전에 `not_ready`를 반환한다 (10.2)
3. `punch_delay_ms`는 두 번째 등록 완료 시 방 단위로 한 번 확정되고 이후 변하지 않는다 (10.2)
4. `get_peers` 응답은 `elapsed_since_ready_ms`를 포함한다 (10.2)
5. 후보는 10.1의 위생 규칙을 통과한 것만 저장하고 전달한다
6. 각 피어의 가상 IP를 상대에게 알려준다 (5.1의 `virtual_ip` 검증에 필요)

이 6개 계약이 깨지면 터널 프로토콜이 성립하지 않는다.

## 순서 원칙

단계는 난이도가 아니라 **기술적 위험** 순으로 정렬한다. 가장 불확실한 가정(임의의 NAT 환경에서 UDP 홀펀칭이 실제로 되는가)을 가장 먼저 검증한다. 가상 어댑터와 게임 통합은 그 가정이 증명된 뒤에 착수한다.

범위 초과 시 제거 순서는 아래 우선순위의 역순이다.

```text
P0: UDP + STUN + 엔드포인트 교환 + 홀펀칭 + 터널 헤더 + DATA 최소 왕복 + 로컬 기록 (Phase 1-4)
P1: 프로토콜 견고성. 손실·재정렬 집계, 퍼즈 방어, 장시간 안정성                    (Phase 5)
P2: Wintun + 가상 IP + Minecraft                                                   (Phase 6-8)
P3: 텔레메트리 + 진단 + 분석                                                       (Phase 9)
P4: 암호화 + 릴레이 + GUI + 추가 플랫폼                                            (스트레치)
```

## Phase 1: 핵심 UDP 네트워킹

**목표:** C++ 네트워킹 기본기를 갖춘다.
**우선순위:** P0
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- 레포를 목표 구조로 재배치 (`src/` -> `client/src/`, `control-server/` 생성)
- CMake 기반 C++20 프로젝트 구성
- Winsock2 초기화 및 해제 (`WSAStartup` / `WSACleanup`) 래핑
- UDP 소켓 래퍼 구현 (`socket`, `bind`, `sendto`, `recvfrom`, `WSAEventSelect` 이벤트 핸들)
- 이벤트 루프 골격 구현. `WaitForMultipleObjects`, 타이머 마감 계산, drain 패턴 ([`architecture.md`](architecture.md) 3.2)
- 엔드포인트 표현 타입 구현 (파싱, 비교, 출력)
- 알려진 두 엔드포인트 간 UDP 패킷 송수신
- 기본 로깅 추가

### 산출물

```text
Client A <------ UDP ------> Client B
```

### 검증

- 같은 LAN의 두 머신(또는 한 머신의 두 프로세스)에서 양방향 메시지 송수신 성공
- 수신 내용이 송신 내용과 바이트 단위로 일치
- 소켓 오류 시 프로세스가 죽지 않고 오류 코드를 로그에 남김
- 콘솔 명령 큐 상한([`architecture.md`](architecture.md) 3.2.6). **소비자를 멈춘 상태에서 본다.** `[loop]`가 큐를 비우면 17줄을 넣어도 넘치지 않으므로, 소비를 막은 큐 단위 시험이거나 `[loop]`를 의도적으로 붙잡은 상태에서 17줄을 주입한다. 그 조건에서 앞의 16줄이 순서대로 남고 **17번째가 버려지며 `console_queue_dropped` 가 오른다.** 조건을 고정하지 않으면 정상 구현도 떨어진다. 가장 오래된 것을 밀어내는 구현은 여기서 걸린다
- bind 계약 확인 ([`protocol.md`](protocol.md) 6장). `INADDR_ANY`와 포트 0으로 bind 한 뒤 `getsockname`이 **0이 아닌 포트**를 돌려주고 그 값이 로그에 남는다. 같은 실행 파일을 한 기기에서 두 번 띄워도 둘 다 기동한다(포트를 고정했다면 두 번째가 실패한다)
- `SO_RCVBUF` 계약([`protocol.md`](protocol.md) 6장). 통과 조건은 셋이다. **요청값이 `262144` 이고**(로그의 `rcvbuf_requested`), 설정 호출이 실제로 있고, **적용값이 한 바퀴 예산 94208바이트 이상**이다(`rcvbuf_applied`). 적용값만 보면 128KB를 요청한 구현도 통과해 6장을 어긴 채 넘어간다. 두 값을 모두 로그에 남기는 것이 [`architecture.md`](architecture.md) 9장의 `socket.bind` 계약이다
- 한 번의 신호로 도착한 데이터그램 여러 개가 같은 바퀴에 처리됨 (drain 패턴 동작)
- 과대 데이터그램이 배칭을 끊지 않음. **두 경로를 따로 돌린다.** (a) 정확히 **1473바이트**는 길이 비교(`n > MAX_DATAGRAM`)로 걸리고, (b) **1474바이트 이상**은 `WSAEMSGSIZE`로 걸린다 ([`architecture.md`](architecture.md) 3.2.3). 각각을 정상 데이터그램 여러 개 **사이에** 끼워 보내 과대분이 `drop_oversize_datagram`으로 오르고 **같은 바퀴에서 뒤따르는 정상 데이터그램이 계속 처리되는지** 본다. (a)만 시험하면 `WSAEMSGSIZE`에서 바퀴를 끝내는 구현이 통과한다
- 수신이 끊이지 않고 들어오는 동안에도 주기 타이머가 계속 만료됨 (drain 예산 동작). **"계속" 을 값으로 못박는다.** 예산을 넘는 수신 부하를 **10초간** 끊기지 않게 준 상태에서, 시험용 **200ms 주기 타이머의 연속 만료 간격이 400ms를 넘지 않는다.** 허용 지연이 값으로 없으면 부하에 우연히 생긴 틈에서 타이머가 돌아도 통과하므로 예산 없는 구현이 걸러지지 않는다. **drain 예산 코드를 제거한 변이가 이 기준에서 `FAIL` 하는지 확인한다.** 변이가 통과하면 이 케이스는 아직 아무것도 지키지 않는 것이다
- `cmake --build` 가 **MSVC `/W4` 수준에서 경고 0건**으로 성공. 경고 수준을 CMake 구성에 고정한다. 수준을 적지 않으면 기본 경고 수준에서도 같은 문장이 통과해 "경고 없이" 가 컴파일러 설정마다 다른 뜻이 된다

## Phase 2: STUN 클라이언트

**목표:** NAT 뒤 클라이언트의 공인 UDP 엔드포인트를 알아낸다.
**우선순위:** P0
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- RFC 5389 중 Binding Request/Response 부분 학습
- Binding Request 패킷 구성 (헤더, magic cookie)
- 트랜잭션 ID 생성 및 응답 매칭
- 공개 STUN 서버로 요청 송신
- Binding Response 파싱
- STUN 속성(TLV) 순회
- `XOR-MAPPED-ADDRESS` 디코드
- 발견된 공인 IP와 포트 출력
- 타임아웃 및 잘못된 응답 처리

### 산출물

```text
Local endpoint:  192.168.x.x:xxxxx
Public endpoint: x.x.x.x:xxxxx
```

### 검증

- 이 Phase 의 판정은 **두 STUN 서버 응답의 파싱 성공**이다. 각 응답에서 `XOR-MAPPED-ADDRESS` 를 디코드해 공인 엔드포인트를 얻으면 통과다. **외부 IP 확인 서비스와의 일치 여부는 참고로만 기록한다.** 그 서비스는 TCP 경로라 UDP 송신 경로와 다를 수 있다 ([`spec.md`](spec.md) M-2가 같은 이유로 그 관측을 참고로 낮췄다). 질의 대상과 관측값 기록은 아래 항목이 정한다
- 트랜잭션 ID가 다른 응답은 무시됨
- 응답하지 않는 주소를 지정하면 타임아웃 후 `STUN_DISCOVERY_FAILED`가 [`architecture.md`](architecture.md) 9장의 **로그**에 남고 무한 대기가 없다. M-6의 로컬 기록 파일은 Phase 4 산출물이라 이 Phase에는 없다
- 잘린 응답이나 잘못된 magic cookie를 넣으면 크래시 없이 거부
- 최소 두 곳 이상의 공개 STUN 서버에 질의해 각각의 server-reflexive 주소를 기록. **동일 결과를 요구하지 않는다.** 서버마다 다르면 목적지 의존 매핑으로 관측값을 남긴다
- STUN에 사용한 소켓이 이후 홀펀칭과 터널이 쓸 소켓과 동일함을 로그로 확인. **이것은 참고다.** 자기 보고이므로 소켓을 새로 연 구현도 같은 줄을 남길 수 있다. 와이어에서 보는 판정은 캡처가 가능한 Phase 4 검증이 맡는다

## Phase 3: AWS 조율 서버

**목표:** 피어들이 서로를 찾고 후보 정보를 교환한다.
**우선순위:** P0
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- Python 제어 서버를 AWS EC2에 배포
- 방 생성 구현
- 방 참가 구현
- 피어 등록
- 가상 IP 할당 (`10.100.0.0/24` 풀 관리)
- 후보 엔드포인트 등록 (로컬, 공인). 로컬 후보는 두 피어가 같은 LAN일 때 쓰인다
- 피어 정보 교환 (`get_peers`)
- SQLite에 방/피어 상태 저장
- C++ 측 제어 평면 클라이언트 구현

### 산출물

서로 다른 네트워크의 두 클라이언트가 AWS를 통해 상대의 엔드포인트를 얻는다.

### 검증

- 방 생성자가 `10.100.0.1`, 참가자가 `10.100.0.2`를 받음
- 같은 방에 두 번 참가해도 가상 IP가 중복 할당되지 않음
- `get_peers` 응답에 상대의 가상 IP와 공인 엔드포인트가 포함됨
- 서버 재시작 후에도 SQLite에서 방 상태가 복원됨
- 존재하지 않는 방에 참가 시도 시 명확한 오류 응답

## Phase 4: UDP 홀펀칭

**목표:** 수동 포트 포워딩 없이 직접 P2P UDP 경로를 만든다. **프로젝트에서 가장 위험한 단계다.**
**우선순위:** P0
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **착수 전 keepalive 매핑 수명 측정 절차 재설계.** 지금 적혀 있던 절차는 실행할 수 없어 뺐다. EC2가 클라이언트의 공인 엔드포인트로 UDP probe를 보내는 형태였는데, 클라이언트는 EC2에 UDP를 보낸 적이 없으므로(제어 평면은 TCP다) 그 probe는 **요청하지 않은 인바운드**다. [`protocol.md`](protocol.md) 10.4의 실측(출발지 포트만 달라도 3쌍 전부 차단)과 [`windows-prereq.md`](windows-prereq.md) 2절의 실측(요청하지 않은 인바운드 6건 전부 차단)이 도착 0을 예고하고, 그러면 "매핑이 만료됐다"와 "필터가 애초에 닫혀 있다"를 구분할 수 없어 매핑 수명을 0으로 오판한다. 유휴 구간을 만드는 부분(그 소켓의 **모든** UDP 송신을 멈춘다. `PING`과 `DATA`를 포함한다. keepalive만 끄는 시험은 게임/`PING` 트래픽이 매핑을 갱신하므로 무효다)은 그대로 쓴다. 다시 정할 것은 셋이다. 유휴 직전에 경로를 여는 송신, probe 형식과 EC2 쪽 송신 도구, 클라이언트의 도착 시각 기록 방법. **측정 대상이 "매핑 수명"이 아니라 "그 경로의 필터+매핑 수명"임을 함께 적는다.** 제어 평면 스키마와 같이 정한다. 11장의 15초와 50초는 그때까지 초기값이다

- **착수 전 `tools/nat-probe` 재측정.** 직접 연결이 성립한다는 판정이 아직 유효한지 확인한다. 여기서 조건이 바뀐 것을 발견하면 설계를 되돌릴 시간이 있다 ([ADR 0001](decisions/0001-직접-연결-대비책-미도입.md))
- **착수 전 로컬 기록 파일의 경로와 줄 형식 확정.** [`architecture.md`](architecture.md) 9장에 계약 4개만 있고 형식이 없다. **정하기 전에는 M-6을 판정할 수 없다.** 코드에서 임의로 정하지 않고 그 문서를 먼저 고친다

[`protocol.md`](protocol.md) 15장 구현 체크리스트를 그대로 따른다. 이 Phase는 설계가 아니라 구현이다.

- 헤더 직렬화/역직렬화 (필드 단위, 네트워크 바이트 오더)
- 단일 수신 루프의 배타적 소켓 소유, STUN/터널 역다중화 (`protocol.md` 6~7장)
- 필수 소켓 옵션: `SO_EXCLUSIVEADDRUSE`, `SIO_UDP_CONNRESET` off, `connect()` 미호출
- 수신 검증 파이프라인과 전용 폐기 카운터. 7장 출발지 위생(분류 전), 8.1 공통 검사 1~8번, 8.4 내부 검증 9~15번, 8.5 송신 측 검사 1~6번이 모두 이 Phase다 (`protocol.md` 7~8장). **8.5의 입력은 이 Phase에서는 합성 내부 패킷이다.** Wintun 읽기가 입력이 되는 것은 Phase 6부터이고 검사 자체는 같다
- `session_epoch` 생성과 고정
- 후보 수집(로컬/서버 반사)과 제어 평면 랑데부 폴링 (`protocol.md` 10.1, 10.2)
- 상대의 **모든** 후보로 `HELLO` 200ms 재전송, 펀치 마감 10초
- 검증을 통과하고 `sequence`를 전진시킨 패킷의 출발지로 `peer_endpoint`를 갱신하는 엔드포인트 학습과 새 주소에 대한 probe nonce 경로 검증 (`protocol.md` 10.4)
- 이중 플래그 `CONNECTED` 조건, 9.4 전이표 전체, 9.4.1 종료 상태 폐기
- 3장의 상한 넷과 9.5 재협상 상한 둘 (`protocol.md` 3, 4.3, 9.5, 10.4)
- `KEEPALIVE` 15초(`CONNECTED` 진입 즉시 1회), 유휴 타임아웃 50초 기반 단절 판정
- `PING`/`PONG` `ping_id` 방식 RTT 측정
- `CLOSE` 송수신
- `DATA` 타입 최소 구현과 왕복. 페이로드는 [`protocol.md`](protocol.md) 5.4가 정의한 **완전한 내부 IPv4 패킷**이다. Wintun이 없으므로 **합성 IPv4 패킷**을 만들어 넣는다. 가상 IP는 Phase 3에서 제어 평면이 배분한 값을 쓴다
- `DATA` 송신 측 검증 (`protocol.md` 8.5)
- 연결 결과(성공 또는 FR-13 실패 코드)와 RTT를 **로컬 기록 파일**에 남긴다. 제어 평면에 올리지 않는다 (M-6)

> **프로토콜은 이미 확정되어 있다**
> 와이어 프로토콜이 확정되지 않으면 구현할 수 없다. 그래서 [`protocol.md`](protocol.md)를 구현 착수 전에 확정본으로 작성했다.
> Phase 4에서 프로토콜을 **설계하지 않는다.** `protocol.md`를 구현할 뿐이다. 구현 중 문서에 빠진 값이 발견되면 코드에서 임의로 정하지 말고 `protocol.md`를 먼저 고친다.
> Phase 5로 남기는 것은 손실·재정렬 집계, 퍼즈 방어, 장시간 안정성이다.

### 산출물

```text
PC A <========== Direct UDP ==========> PC B
```

지원 환경에서 공유기 포트 포워딩 설정 없이 성립한다. 주고받는 패킷은 정식 터널 헤더를 쓰며, Phase 5에서 교체되지 않는다.

### 검증

- 포트 포워딩 규칙이 없는 상태에서 서로 다른 가정망의 두 PC가 양방향 통신 성공
- 패킷 캡처로 트래픽이 AWS를 경유하지 않음을 확인
- 펀치 직전에 **같은 소켓으로** 서로 다른 두 STUN 서버에 질의해 **같은 공인 IP:Port 가 관측됨** ([`spec.md`](spec.md) M-2와 "지원 네트워크 조건"의 판정이다). Phase 2는 동일 결과를 요구하지 않으므로 이 판정은 여기가 처음이다. 관측이 갈리면 목적지 의존 매핑이고 미지원 조건이므로, 실패로 적지 않고 관측값과 함께 미지원으로 기록한다
- 같은 캡처에서 **STUN 질의의 출발지 포트와 터널 송신의 출발지 포트가 같음**을 대조 (NFR-9). Phase 2는 로그로만 확인했고, 로그는 자기 보고라 실제로 소켓을 새로 연 구현도 통과한다
- 헤더 직렬화 후 역직렬화 결과가 원본과 동일 (라운드트립 테스트)
- 캡처한 패킷의 바이트 배열이 `protocol.md` 4.1의 오프셋과 바이트 오더에 정확히 일치. 첫 4바이트가 `53 41 4E 47`
- `PUNCHING` 상태에서 `HELLO_ACK`이 먼저 도착해도 정상 수용됨 (`protocol.md` 9.4)
- `CONNECTED` 상태에서 상대가 `HELLO`를 재전송하면 `HELLO_ACK`을 다시 보냄
- 재협상 뒤 지연 패킷 처리. **NAT 를 건너는 재시작 시험으로 돌리지 않는다.** 재시작한 상대의 새 `HELLO` 는 [`protocol.md`](protocol.md) 10.4 의 실측대로 차단될 수 있고 v1 은 그 복구를 보장하지 않으므로, 와이어로 돌리면 재협상이 아예 일어나지 않아 **정상 구현이 떨어진다.** 새 `HELLO` 도착이 보장되는 자리에서 돌린다. 같은 기기의 두 프로세스이거나 수신 경로 직접 주입이다. 그렇게 해서 새 `HELLO` 가 9.5 재협상을 일으킨 **뒤**에 도착한 이전 epoch 의 지연 패킷이 `drop_retired_epoch` 로 폐기됨. 재협상 1단계가 이전 epoch 를 폐기 목록에 넣고, 8.1 공통 검사 8번(폐기 목록)이 8.2/9.3 의 epoch 비교보다 **먼저** 돌기 때문이다. **재협상 전에 도착한 지연 패킷은 고정된 epoch 와 일치하므로 수용되는 것이 규정이다.** 그 구간까지 폐기를 기대하면 규정대로 만든 구현이 떨어진다
- 응답 없는 후보로 계속 송신해도 `WSAECONNRESET`로 수신 루프가 죽지 않음
- 출발지 위생([`protocol.md`](protocol.md) 7장)을 두 층에서 본다. (a) **판정 함수**에 그 절의 케이스 표를 그대로 돌린다. 멀티캐스트·제한 브로드캐스트·자기 서브넷의 directed broadcast·미지정·포트 0은 거부하고 **루프백과 일반 유니캐스트는 통과**한다. (b) **수신 파이프라인**에 거부 대상 출발지를 넣으면 STUN 분류와 터널 분류 **어느 쪽에도 도달하지 않고** `drop_bad_source`에서 끝나며 응답이 한 개도 나가지 않는다. (a)만 시험하면 함수는 맞게 만들고 분류 뒤에서 부르는 구현이 통과한다. 보통의 Windows UDP 소켓으로는 출발지를 위조한 데이터그램을 만들 수 없으므로, (b)는 와이어로 보내는 대신 수신 경로에 데이터그램을 직접 주입해 돌린다. **그러려면 수신 경로에 시험용 진입점이 있어야 한다.** `(버퍼, 길이, 출발지 엔드포인트)`를 받아 분류부터 태우는 함수 하나를 시험 빌드에 노출한다. 그 함수가 `recvfrom` 뒤의 경로와 **같은 코드**를 타야 한다. 시험 전용으로 따로 짜면 그 시험은 실제 경로를 검증하지 않는다 **규칙 한 줄을 지운 변이와 루프백을 거부하도록 바꾼 변이가 각각 `FAIL` 하는지 확인한다**
- 종료 상태 수신(9.4.1). `CLOSE`를 주고받아 `CLOSED`에 도달한 뒤 같은 상대가 보낸 `KEEPALIVE`가 `drop_terminal_state`로만 오르고 어떤 응답도 나가지 않는다. 캡처로 무응답을 확인한다
- 폐기 목록 상한(4.3). epoch를 17개 등록시키면 목록이 16개를 넘지 않고 **가장 오래된 것이 밀려난다.** 밀려난 epoch를 단 비-`HELLO` 패킷은 그 뒤 epoch 고정 비교에서 `drop_stale_epoch`로 걸린다(두 번째 방어선). 상한 없이 자라는 구현과 새 항목을 거부하는 구현이 각각 걸린다
- `session_epoch` 난수원(4.3). 난수원을 주입할 수 있게 만들고, (a) 0이 나오면 다시 뽑는지, (b) 뽑는 경로가 OS CSPRNG인지를 본다. 값 분포로는 `rand()` 구현을 가릴 수 없으므로 **호출 경로를 코드에서 확인하는 것을 판정에 포함한다**
- 재협상 상한(9.5). 같은 기기의 주입기로 서로 다른 epoch의 `HELLO`를 1초 안에 연달아 보내면 첫 건만 재협상되고 나머지는 `drop_reneg_rate`로 오른다. 간격을 1초 넘겨 `MAX_RENEGOTIATIONS`회를 넘기면 그 뒤는 `drop_reneg_limit`으로 오른다. **정상 경로가 여기 걸리지 않는 것도 같이 본다.** 재협상 한 번 뒤의 `HELLO` 재전송은 같은 epoch이므로 일반 `HELLO`로 처리되어야 한다
- 잠정 경로 상한(10.4). 후보 집합 밖의 서로 다른 출발지 포트 다섯 곳에서 검증을 통과하고 `sequence`를 전진시킨 패킷을 보내면, 앞의 넷만 잠정 경로가 되고 다섯째는 `drop_probe_full`로 오른다. **다섯째 패킷 자체는 정상 처리된다.** 유휴 타이머가 갱신되고, `DATA`였다면 주입된다. 그 패킷을 버리는 구현은 이 항목에서 걸린다. 검증 `HELLO`는 경로마다 **1회만** 나간다(캡처로 확인). 가장 오래된 경로가 밀려나지 않는다
- 무검증 목적지 공통 예산([`protocol.md`](protocol.md) 9.4). 네 가지를 본다. (a) 후보 집합 밖 출발지에서 `HELLO`를 초당 20회로 10초간 보내면 나가는 송신 수가 **초기 10개 + 초당 5개 보충**을 넘지 않고 초과분이 `drop_unverified_tx`로 오른다. (b) 같은 시험을 후보 집합 안 출발지로 돌리면 제한이 없어 전부 응답한다. (c) **정상 재전송이 막히지 않는다.** 후보 밖 출발지에서 200ms 간격으로 30초간 보내면 응답이 하나도 누락되지 않는다. (d) **예산이 하나임을 본다.** 후보 밖 출발지에서 `HELLO`와 `PING`을 섞어 보내면 `HELLO_ACK`, `PONG`, 검증 `HELLO`가 **합쳐서** 위 한도 안에 들어온다. 경로마다 따로 세는 구현은 여기서 걸린다. 연속 10발 뒤 11발째가 막히고 200ms 뒤 한 발이 통과하는 것도 확인한다. 고정 창 구현은 (c)에서 걸린다
- `CLOSE` 송신 조건(5.6). `peer_endpoint`를 학습한 세션에서 종료하면 `CLOSE`가 그 주소로 1회 나가고, 학습 전에 종료하면 **한 개도 나가지 않는다**(캡처로 확인). 후보 전체로 뿌리는 구현은 이 항목에서 걸린다
- 한쪽만 `HELLO`를 받은 상태에서는 `CONNECTED`로 전이하지 않음 (한 방향만 뚫린 경우를 성공으로 오판하지 않는다)
- keepalive 주기: 캡처에서 `CONNECTED` 진입 즉시 1회, 그 뒤 15초 간격으로 `KEEPALIVE`가 나간다. **여기서 재는 것은 우리 송신 주기이고 NAT 매핑 수명이 아니다.** 매핑 수명 측정은 아래 작업 절의 착수 전 항목이다
- **검증 절차가 쓰는 콘솔 명령을 못박는다.** Phase 1~5 의 `[console]` 스캐폴딩([`architecture.md`](architecture.md) 3.2)이 받는 최소 어휘는 셋이다. `quit` 는 세션을 닫고 프로세스를 정상 종료한다. `counters` 는 카운터 전량을 즉시 로그로 낸다([`architecture.md`](architecture.md) 9장). 카운터를 보는 검증 항목이 이 명령으로 시점을 잡는다. `send <n>` 은 합성 내부 IPv4 패킷을 `DATA` 로 `n` 개 보낸다. **`n` 은 1 이상 1000 이하의 정수다.** 범위 밖이거나 정수가 아니면 아무것도 보내지 않고 `WARN` 한 줄을 남긴다. 세션이 `CONNECTED` 가 아니면 보내지 않고 `WARN` 한 줄을 남긴다(8.5 검사 1번이 어차피 막는다. 명령 단계에서 걸러 시험이 무엇을 보는지 흐리지 않는다). 송신은 한 바퀴에 몰아넣지 않고 `MAX_DRAIN` 예산과 같은 방식으로 나눠 보낸다. 중간에 `sendto` 가 실패하면 거기서 멈추고 보낸 개수를 남긴다. **바이트를 못박는다.** 값이 정해져 있어야 아래 M-5의 byte-for-byte 비교와 RTT 기준선의 에코가 같은 입력을 쓴다

내부 패킷 100바이트의 **절대 오프셋**이다. 반열린 구간으로 적는다

| 오프셋 | 크기 | 값 |
|--------|:----:|-----|
| `0` | 1 | `0x45` (version 4, IHL 5) |
| `1` | 1 | `0x00` (DSCP/ECN) |
| `2..4` | 2 | `total_length` = 100 (BE) |
| `4..6` | 2 | id = 0 |
| `6..8` | 2 | flags + fragment offset = 0 |
| `8` | 1 | TTL = 64 |
| `9` | 1 | protocol = 17 (UDP) |
| `10..12` | 2 | IPv4 헤더 체크섬. 계산해 채운다. [`protocol.md`](protocol.md) 8.4 검사 12번이 본다 |
| `12..16` | 4 | 출발지 = 자신의 가상 IP |
| `16..20` | 4 | 목적지 = 상대의 가상 IP |
| `20..22` | 2 | UDP 출발지 포트 = 25565 |
| `22..24` | 2 | UDP 목적지 포트 = 25565 |
| `24..26` | 2 | UDP `length` = 80 (헤더 8 + 페이로드 72) |
| `26..28` | 2 | UDP 체크섬 = 0 (IPv4에서 허용된다. 8.4가 보지 않는다) |
| `28..32` | 4 | 0부터 세는 패킷 번호 (BE) |
| `32..40` | 8 | 송신 시각. 단조 시계 밀리초 (BE). RTT 기준선이 쓴다 |
| `40` | 1 | **방향 표시.** `0xA5` 는 요청, `0x5A` 는 에코 응답 |
| `41..100` | 59 | `0xA5` 반복 |

체크섬과 송신 시각 외에 파생되는 값이 없어야 한다. **그래서 한 번의 송신에 대해 송신 측 바이트와 수신 측 바이트가 정확히 같다.** 아래 M-5 비교가 그것이다. **다른 실행끼리 비교하지 않는다.** 송신 시각 8바이트와 그에 딸린 체크섬은 실행마다 다르므로, 재실행 간 바이트 비교를 통과 조건으로 삼으면 올바른 구현도 떨어진다. 아래 왕복 시험과 실패 코드 시험은 이 두 명령으로 개시하고 끝낸다. 어휘가 없으면 누가 왕복을 개시하는지가 시험마다 달라진다
- 합성한 내부 IPv4 패킷을 `DATA`로 양방향 왕복시켜 바이트가 일치 (M-5). **비교 지점을 못박는다.** 송신 측이 캡슐화 직전에 가진 페이로드 바이트열과, 수신 측이 8.4 검증을 통과한 뒤 꺼낸 페이로드 바이트열을 **길이를 포함해 byte-for-byte** 비교한다. 로그 문자열이나 재구성한 헤더를 비교하지 않는다. 그렇게 하면 헤더를 다시 쓰거나 패딩이 붙어도 통과한다
- 내부 출발지/목적지 가상 IP가 틀린 `DATA`가 `drop_inner_src` / `drop_inner_dst`로 폐기됨
- 로컬 기록 파일의 줄 수가 도달 여부와 맞는다 (M-6, [`architecture.md`](architecture.md) 9장). **수립에 실패한 시도는 수립 줄 한 줄, `CONNECTED`에 도달한 시도는 수립 줄과 종료 줄 두 줄이다.** 실패 시 FR-13 코드가 적힌다. **RTT 는 표본이 없으면 비어 있는 것이 정상이다.** 수립 줄은 `PING` 이 아직 돌기 전이라 대개 비어 있고, 종료 줄에 마지막 표본이 들어간다. 빈 값을 실패로 판정하지 않는다
- 홀펀칭 실패 시 `HOLE_PUNCH_TIMEOUT`이 기록되고 프로세스는 정상 종료
- RTT 기준선 비교는 ICMP가 아니라 **같은 소켓, 같은 엔드포인트 쌍에서의 왕복**으로 한다. NAT 뒤 피어를 향한 ICMP는 차단되거나 피어의 공유기가 응답하는 경우가 많아 같은 경로를 재지 못한다. **기준선을 위해 새 와이어 타입을 만들지 않는다.** 위 M-5 항목이 쓰는 합성 내부 IPv4/UDP 패킷에 송신 시각을 넣어 `DATA` 로 나르고, **에코 응답기**가 내부 출발지와 목적지를 뒤집고, **오프셋 40 의 방향 표시를 `0x5A` 로 바꾸고**, **IPv4 헤더 체크섬을 다시 계산해** 되돌린다. **`0x5A` 인 패킷에는 응답하지 않는다.** 이 규칙이 없으면 양쪽이 옵션을 켰을 때 응답이 다시 에코되어 두 피어 사이에 패킷이 영원히 오간다. 체크섬을 그대로 두면 되돌아온 패킷이 [`protocol.md`](protocol.md) 8.4 검사 12번에서 `drop_inner_checksum` 으로 걸려 이 시험이 성립하지 않는다. **에코 응답기는 시험 빌드에만 넣는다.** 제품 빌드에 포함하지 않는다. 받은 `DATA` 를 되돌려 보내는 기능은 그 자체로 반사 경로이므로 시연 빌드에 남으면 안 된다. CMake 옵션으로 가르고, 켜진 빌드는 기동 시 `WARN` 한 줄을 남겨 로그만 봐도 구분되게 한다. [`protocol.md`](protocol.md) 5장에 에코 타입이 없고 7장 분류가 프로토콜 밖 데이터그램을 폐기하므로, 별도 에코 패킷을 전제하면 규정대로 만든 구현이 이 시험을 돌릴 수 없다. `PING`/`PONG` 20회 표본의 중앙값이 `DATA` 에코 20회 중앙값 대비 절대차 10ms 이내 또는 상대차 30% 이내 (사용자 공간 처리 오버헤드 감안). ICMP 비교는 참고 정보로만 기록할 수 있다
- 실패 코드 강제 발생 시험: 제어 평면을 내린 상태 -> `CONTROL_PLANE_EXCHANGE_FAILED`, 응답 없는 엔드포인트 주입 -> `HOLE_PUNCH_TIMEOUT`, `HELLO_ACK` 응답을 차단 -> `PEER_HANDSHAKE_FAILED`. 각각 정확한 코드와 상태 전이가 기록됨

### 위험

이 단계가 실패하는 NAT 환경이 존재한다. 실패를 숨기지 않고 NAT 환경 정보와 함께 기록한다. 지원/미지원 네트워크 조건을 명시적으로 정의한다. 릴레이 폴백은 이 시점에서 구현하지 않고 스트레치로 남긴다.

## Phase 5: 터널 프로토콜 완성

**목표:** Phase 4에서 왕복까지 확인한 터널에 견고성을 더한다. 손실·재정렬 집계, 손상 패킷과 퍼즈 방어, 장시간 안정성이다.
**우선순위:** P1
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다
**선행:** [`protocol.md`](protocol.md) 15장 체크리스트가 Phase 4에서 전부 완료되어 있다.

### 작업

- `sequence` 기반 손실 및 재정렬 **집계**. [`protocol.md`](protocol.md) 4.5 의 `position` / `baseline` / `accepted` 계산을 구현해 손실과 손실률을 낸다. **수용 창 자체는 Phase 4 의 몫이다.** 4.5 의 창은 시간 기반 만료가 없는 **64칸 위치 기반 비트맵**이라 "윈도우 만료" 라는 계기가 없다. 손실은 만료로 확정되는 것이 아니라 `expected - accepted` 로 나오고, `drop_too_old` 로 버린 패킷은 이미 손실로 확정된 것이므로 되돌리지 않는다
- 퍼즈 방어. 손상되고 절단된 입력에도 크래시하지 않는다
- 장시간 연결 안정성 확보
- **자동 재시도 여부 확정.** `TUNNEL_DROPPED` 뒤에 누가 언제 재시도를 개시하는지 [`protocol.md`](protocol.md) 9.6이 정하지 않았다. 정한 뒤 그 문서를 고친다

**Phase 4 가 이미 구현한 것은 여기서 다시 만들지 않는다.** 아래 셋은 **시험**이 이 Phase의 몫이고 구현은 Phase 4에 있다. 어디에 무엇이 있는지 헷갈리면 검증 기준이 두 Phase에 갈라진다.

| 항목 | 구현 | 이 Phase에서 하는 것 |
|------|------|----------------------|
| 8.1 공통 검사 1~8번과 폐기 사유별 카운터 | Phase 4 | 잘못된 magic, 미지원 version, 길이 불일치, 절단 패킷을 주입해 카운터가 맞는 사유로 오르는지 본다 |
| 8.4 / 8.5 크기 한계와 `payload_length` 검증 | Phase 4 | 20바이트와 `MAX_INNER` 경계, 그리고 경계 바로 밖을 시험한다 |
| 9.4 세션 상태 머신 전체 | Phase 4 | 장시간 구간과 실패 전이에서 상태가 규정대로 머무는지 본다 |

### 산출물

두 피어 사이에서 내부 IPv4 패킷을 손실, 재정렬, 손상 조건에서도 안정적으로 나르는 애플리케이션 레벨 터널이 존재한다. Phase 7에서 이 `DATA` 페이로드 자리에 Wintun이 실제로 캡처한 IP 패킷이 들어간다.

### 검증

- 경계 크기 케이스 표를 전부 돌린다. **범위를 말로 적지 않고 값으로 적는다.** 값이 없으면 경계 바로 밖이 시험되지 않는다

| 페이로드 크기 | 기대 |
|--------------:|------|
| 19 | 수신 시 `drop_type_length`. `DATA` 최소는 20이다 |
| 20 | 왕복 성공. 옵션 없는 IPv4 헤더만 있는 최소 패킷이다 |
| 576 | 왕복 성공. 중간값 |
| 1452 | 왕복 성공. `MAX_INNER` 경계 |
| 1453 | 송신 시 `tx_drop_oversize`. **수신 쪽은 이 표로 시험하지 않는다.** 데이터그램이 `MAX_DATAGRAM`(1472)을 넘어 `recvfrom` 이 `WSAEMSGSIZE` 로 실패하므로 검증 파이프라인에 닿지 않는다 |

  왕복 성공 케이스의 일치 판정은 Phase 4와 같은 비교 지점을 쓴다
- 잘못된 magic, 미지원 version, `payload_length` 불일치 패킷이 모두 폐기되고 해당 사유 카운터 증가
- 퍼즈 시험: 고정 seed로 생성한 1~2000바이트 무작위 패킷 100,000개를 소켓에 주입해도 크래시와 메모리 오류 없음. seed, 개수, 길이 범위를 로그에 남겨 재현 가능하게 한다
- 제어 평면 중단 시험: `CONNECTED` 도달 후 제어 서버를 내려도 10분간 `DATA` 전송과 세션 상태가 유지됨 (NFR-3)
- 의도적으로 패킷을 누락시켰을 때 `sequence` 간격으로 손실률이 계산됨
- 패킷 순서를 뒤바꿔 주입해도 손실로 집계되지 않음 ([`protocol.md`](protocol.md) 4.5 의 64칸 수용 창이 재정렬 패킷을 수용하고, 그 패킷이 `accepted` 에 세어진다)
- `sequence`가 32비트 경계를 넘어가도 손실률이 튀지 않음
- 유휴 타임아웃 시험: 상대 송신을 완전히 끊으면 `TUNNEL_DROPPED`가 정확한 상태 전이와 함께 기록됨 (FR-13 실패 코드 집합 완성)
- 장시간(1시간 이상) 연결 유지 중 세션 상태가 `CONNECTED`로 유지됨

## Phase 6: Windows 가상 네트워크 어댑터

**목표:** 가상 인터페이스로 IP 패킷을 캡처하고 주입한다.
**우선순위:** P2
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **착수 전 Wintun 배포물의 기대 발행자 문자열과 공개 해시를 적어 둘 위치 확정.** [`windows-prereq.md`](windows-prereq.md) 4절은 배포물의 `Subject` 와 해시를 **기대값과 비교**하라고 하는데, 그 기대값을 어디에 적어 두는지가 없다. 둘 곳이 없으면 그 절의 판정 2번과 3번을 돌릴 수 없고 `Status` 만 보는 검사로 무너진다. 위치를 정한 뒤 그 문서를 고친다
- **착수 전 Wintun 주입 실패의 표현 확인.** 쓰는 헤더와 그 문서에서 실패가 어느 호출에서 어떤 형태로 나오는지 확인하고, "링이 찬 것"을 별도 카운터로 나눌지를 [`architecture.md`](architecture.md) 3.2.3에 적는다. 동작 계약(폐기, `drop_inject_error`, 재시도 금지, 루프 비차단)은 이미 정해져 있으므로 이 항목이 막는 것은 카운터 세분뿐이다
- Wintun 의존성 **승인됨**. 제공 범위 문서화는 그대로 유지한다
- 가상 어댑터 생성 및 개방
- 가상 IP 주소 할당
- 어댑터에서 패킷 읽기
- 어댑터로 패킷 주입
- 필요한 Windows 라우트 설정 및 종료 시 정리
- 게임 없이 기본 IP 도구로 트래픽 검증

### 산출물

```text
Windows IP 스택
      |  10.100.0.0/24 로 향하는 패킷
      v
Wintun Adapter  --- read ---> 클라이언트 (카운터 증가)
Wintun Adapter  <-- inject -- 클라이언트 (직접 만든 응답)
```

단일 호스트에서 가상 어댑터로부터 패킷을 읽고 다시 주입할 수 있다. 두 가상 IP 간 통신은 터널 통합이 필요하므로 Phase 7의 산출물이다.

### 검증

- `ipconfig`에 가상 어댑터와 할당된 가상 IP가 표시됨
- `route print`에 `10.100.0.0/24` 경로가 어댑터로 향함
- 같은 머신에서 **미할당** 가상 IP(예: `10.100.0.9`)로 `ping`을 보내면 어댑터 read 카운터가 증가. 이 패킷에 대한 ICMP 응답을 직접 만들어 inject 하면 `ping`이 응답을 받는다 (read/inject 양방향 경로 검증)
- 자기 가상 IP `ping`은 Windows 로컬 스택에서 단락 처리되어 어댑터를 거치지 않으므로 검증에 쓰지 않는다
- 두 피어 간 실제 가상 IP 왕복은 터널 통합 이후이므로 Phase 7에서 검증한다
- 클라이언트 종료 후 어댑터와 라우트가 남지 않음
- 비정상 종료 후 재실행 시 어댑터가 정상 재생성됨

### 위험

Windows 가상 네트워킹은 예상보다 복잡할 수 있다. 이 작업은 Phase 4의 NAT 통과 작업과 분리해 진행한다. Wintun은 가상 인터페이스 접근에만 쓰고 라우팅 결정 로직은 프로젝트가 직접 소유한다.

## Phase 7: 가상 어댑터와 P2P 터널 통합

**목표:** 가상 네트워크 IP 패킷을 피어 간에 전달한다.
**우선순위:** P2
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- Wintun에서 송신 IP 패킷 읽기
- 목적지 가상 IP로 대상 피어 결정
- `DATA` 패킷으로 캡슐화
- 직접 UDP 연결로 전송
- 수신 패킷 역캡슐화
- 원본 IP 패킷을 Wintun에 주입
- 패킷 크기 한계 처리 및 MTU 확정
- 카운터와 진단 추가

### 산출물

두 Windows 머신이 가상 IP만으로 통신한다.

### 검증

- 상대 가상 IP로 `ping` 왕복 성공
- 가상 IP 간 파일 전송(SMB 또는 임시 TCP 서버) 성공, 내용 일치. **이 항목이 NFR-2 의 판정이다.** Minecraft 가 아닌 트래픽이 터널을 그대로 지나가는 것을 보인다. 통과 조건에 하나를 더 붙인다. 이 시험과 Phase 8 의 Minecraft 시험을 **같은 터널 빌드**로 돌린다. 애플리케이션을 바꾸느라 터널 코드를 고쳐야 했다면 NFR-2 가 성립하지 않는다
- 최대 크기 패킷 전송 시 조각화 없이 전달 (실측으로 MTU 값 확정)
- 라우팅 대상이 없는 가상 IP로 보낸 패킷은 폐기되고 카운터 증가
- 주입 실패 처리([`architecture.md`](architecture.md) 3.2.3). 송신 링을 채운 상태를 만들면 그 패킷이 `drop_inject_error`로 폐기되고 **루프가 그 자리에서 기다리지 않는다.** 판정은 카운터만 보지 않는다. 주입이 실패하는 구간에도 keepalive 송신 간격이 유지되는지 같이 본다. 자리가 날 때까지 재시도하는 구현은 그 간격이 무너져 걸린다
- 송수신 바이트 카운터를 패킷 캡처와 대조한다. **"정확히 일치, 오차 불허" 는 정상 구현도 통과할 수 없어 아래로 바꿨다.**

| 항목 | 정의 |
|------|------|
| 계수 기준 | **터널 헤더를 포함한 UDP 페이로드 바이트.** 이더넷·IP·UDP 헤더는 세지 않는다 |
| 계측 지점 | 클라이언트는 `sendto`/`recvfrom` 이 성공 반환한 바이트를 센다. 캡처는 같은 기기에서 그 소켓의 5-튜플만 거른다 |
| 표본 조건 | 게임 트래픽이 아니라 **생성한 트래픽**으로 한다. 유휴에서 시작해 정해진 개수를 보내고 멈춘 구간만 본다. 크기는 Phase 5 경계 표의 20 / 576 / 1452바이트를 쓴다 |
| 개수 | **여기서 정하지 않는다.** 1,000 / 5,000 / 10,000 / 50,000 을 순서대로 시도해 **캡처 유실이 0으로 보고된 가장 큰 값**을 고르고 그 값을 이 표에 적는다. 이 사다리는 탐색 격자일 뿐이고 판정에 쓰는 것은 고른 값이다. 기기와 캡처 설정에 달려 미리 지어낼 수 없다 |
| 유효 구간 | 캡처 도구가 보고하는 유실 수가 **0인 구간에서만 판정한다.** 0이 아니면 실패가 아니라 **버리고 다시 잰다** |
| 통과 조건 | 유효 구간에서 바이트 합이 일치한다. 캡처 합이 카운터 합보다 **크면 실패**다. 세지 않은 바이트를 보낸 것이므로 계수 버그다 |
| 패킷 수 | **참고로만 기록한다.** UDP 분할 오프로드가 켜져 있으면 캡처가 보는 데이터그램 수가 달라진다. 바이트 합은 그래도 같다 |

  **더 이상 보장하지 않는 것.** 캡처가 유실을 겪는 구간의 정확성은 판정하지 않는다. 부하가 높을 때의 계수 정확성은 이 시험이 말해 주지 않는다

## Phase 8: Minecraft 검증

**목표:** 실제 멀티플레이 세션을 시연한다.
**우선순위:** P2
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **Phase 8 착수 시 `tools/nat-probe` 재측정.** 시연 환경을 꾸리기 전에 직접 연결 판정이 아직 유효한지 확인한다 ([ADR 0001](decisions/0001-직접-연결-대비책-미도입.md))
- **시연 직전 한 번 더 재측정.** 당일 확인이다. 직접 연결 판정은 특정 시점의 관측이고 공유기 교체나 ISP 구성 변경으로 무효가 될 수 있다
- 호스트에서 Minecraft Java 서버 실행
- 플레이어가 호스트 가상 IP로 접속
- 로그인 및 월드 진입 확인
- 장시간 플레이
- 지연과 연결 끊김 거동 측정
- 패킷 및 연결 지표 기록

### 산출물

```text
Minecraft Client -> 10.100.0.1:25565 -> Project Virtual Network -> Minecraft Server
```

### 검증

- 플레이어가 `10.100.0.1:25565` 입력만으로 접속, 공인 IP/포트 입력 없음
- 호스트 공유기에 포트 포워딩 규칙이 없는 상태에서 성공
- 30분 이상 연속 플레이 중 강제 종료 없음
- 게임 표시 지연과 터널 RTT 를 같은 구간에서 기록하고 **둘의 차이를 보고한다.** **"±30ms 이내" 는 측정 방법과 계측 지점이 없어 판정할 수 없었다.** 아래로 바꿨다

| 항목 | 정의 |
|------|------|
| 재는 것 | 게임 표시 지연은 Minecraft 클라이언트가 보여 주는 값이고, 터널 RTT 는 `PING`/`PONG` 측정치다. **둘은 같은 것을 재지 않는다.** 게임 값은 응용 계층 왕복이고 터널 위에 있다 |
| 계측 지점 | 게임 값은 화면에서 읽고, 터널 값은 클라이언트 로그에서 읽는다 |
| 표본 조건 | 같은 구간에서 각각 20회 이상. 구간의 시작과 끝을 로그에 남긴다. **이것은 통계적 충분성 주장이 아니라 기록의 최소 조건이다.** 게임 표시 지연이 초 단위로 갱신되므로 20회를 모으려면 대략 1분이 든다 |
| 통계 | 중앙값과 사분위 범위. 평균과 표준편차를 쓰지 않는다 |
| 무엇을 판정하는가 | **계측 일관성이다. 품질이 아니다.** 게임 지연이 아무리 커도 이 기준만으로는 실패하지 않는다. 체감 품질 판정은 아래 반영 시험이 맡는다 |
| 통과 조건 | 게임 표시 지연의 중앙값이 터널 RTT 중앙값 **이상**이다. 작더라도 그 차이가 **허용 폭 안이면 통과로 본다.** 허용 폭은 **터널 RTT의 사분위 범위와 게임 표시값의 표시 해상도 1단위 중 큰 쪽**이다. 조용한 LAN에서는 사분위 범위가 0에 가까워지는데, 그때 화면 반올림만으로 뒤집히면 정상 구현이 떨어진다. 허용 폭을 넘게 작으면 실패이고, 둘 중 하나를 잘못 재고 있다는 뜻이다. **허용 폭을 밀리초로 지어내지 않는다. 같은 측정에서 나온 흩어짐과 도구의 표시 해상도만 쓴다** |
| 보고 | 차이의 중앙값과 사분위 범위를 [`experiments.md`](experiments.md)에 싣는다 |

  **더 이상 보장하지 않는 것.** 절대 지연 상한을 보장하지 않는다. 체감 품질은 아래 반영 시험으로만 본다
- 블록 배치 20회와 채팅 20회를 시도해 전부 2초 이내에 상대 클라이언트에 반영

## Phase 9: 모니터링과 실험적 평가

**목표:** 동작하는 데모를 넘어 측정 가능한 CSP 분석 결과를 만든다.
**우선순위:** P3
**관련 요구사항:** 이 문서 앞머리의 "요구사항 추적" 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- 연결 수립 시간 기록
- RTT 기록
- 패킷 손실 기록
- 지터 추정
- 터널 전송량 기록
- 세션 지속 시간 기록
- 텔레메트리 업로드를 전용 스레드와 유실 허용 큐로 분리 ([`architecture.md`](architecture.md) 3.2.6)
- 복수 네트워크 환경 테스트
- 성공한 NAT 통과 사례와 실패 사례 비교 (NAT 유형이 아니라 관측된 매핑 거동 기준)
- 실험 결과 시각화
- 한계 문서화
- [`experiments.md`](experiments.md) 작성

### 테스트 환경

| 환경 | 목적 |
|------|------|
| 동일 LAN | 기준선 측정 |
| 가정망 대 가정망 | 주 사용 시나리오 |
| 가정망 대 모바일 핫스팟 | CGNAT 등 어려운 NAT 조건 |
| 캠퍼스망 대 가정망 | 기관 방화벽 조건 |
| 가용한 다른 NAT 거동 | 매핑 거동별 비교 |

### 통계 설계

**무엇을 한 번의 시행으로 세는지, 시행들이 독립인지, 불확실성을 어떻게 적는지를 먼저 정한다.**
정하지 않으면 나중에 나온 숫자가 무엇을 뜻하는지 아무도 말할 수 없다.

| 항목 | 정의 |
|------|------|
| 한 시행 | 클라이언트 시작부터 `CONNECTED` 도달 또는 실패 코드 기록까지. 세션 지속과 품질 측정은 `CONNECTED` 이후의 별도 구간이다 |
| 시행 사이 | 클라이언트를 내리고 새 `session_epoch` 로 다시 시작한다. 유휴 타임아웃(50s)보다 길게 쉬어 이전 NAT 매핑이 살아 있지 않게 한다 |
| 독립성 | **같은 날 같은 망에서 이어 돌린 10회를 독립 시행으로 부르지 않는다.** 공유기 상태와 ISP 경로가 공유되기 때문이다. **반복 측정**으로 적고, 환경이 바뀐 것만 별개 조건으로 센다 |
| 대표값 | 중앙값과 사분위 범위. **평균과 표준편차를 쓰지 않는다.** RTT 와 수립 시간은 한쪽으로 치우쳐서 평균이 대표하지 못한다 |
| 성공률 | 비율과 함께 **분모 n 을 반드시 적는다.** 구간을 붙일 때는 Wilson 점수 구간을 쓴다. 정규 근사는 n 이 작고 비율이 1에 가까울 때 틀린 구간을 낸다 |
| 표본 수 | 환경마다 10회 이상. **통계적 충분성 주장이 아니다.** 한 학기에 접근할 수 있는 망에서 실행 가능한 최소치로 잡은 값이다. 그 한계를 [`experiments.md`](experiments.md)에 적고 숫자에 과한 의미를 붙이지 않는다 |

**더 이상 보장하지 않는 것.** 이 설계는 모집단 추정이 아니다. 우리가 접근할 수 있었던 소수의
망에서 관측한 것을 적을 뿐이고, 다른 NAT 환경으로 일반화하지 않는다.

### 산출물

최종 보고서와 발표에 쓸 반복 가능한 실험 세트와 데이터.

### 검증

- 제어 평면 중단 시험 재실행: 텔레메트리가 켜진 상태에서 제어 서버를 내려도 10분간 터널이 유지됨 (NFR-3). Phase 5 시험을 텔레메트리 포함 구성으로 다시 돌린다
- 큐가 가득 찬 상태에서 `[loop]`의 지표 기록이 블록되지 않고 `telemetry_queue_dropped` 가 증가함. **크기와 버리는 방향도 같이 본다.** 링 크기는 [`architecture.md`](architecture.md) 3.2.6이 소유하며(이 시점의 값은 256항목) 가득 차면 **새 레코드**를 버린다. 가장 오래된 것을 버리는 구현은 지표가 더 좋아 보이지만 생산자가 소비자의 tail을 움직이는 것이므로 여기서 걸러야 한다
- 각 환경별로 최소 10회 반복 측정 데이터 확보. 위 통계 설계의 시행 정의와 간격을 지킨다
- 실패 건 전부에 단계별 코드와 NAT 환경 정보가 기록됨. 통제된 실패와 실제 환경의 실패를 **따로 집계한다** (A-2)
- 성공률이 관측된 매핑 거동별로 집계됨. RFC 5389 Binding 결과만으로 NAT 유형을 단정한 서술이 없음
- 재현 시행 1회 통과. 통과 조건은 [`spec.md`](spec.md) A-4 가 정한다
- 그래프와 한계 서술이 [`experiments.md`](experiments.md)에 포함됨

## 위험 관리

| 위험 | 대응 |
|------|------|
| 모든 네트워크에서 홀펀칭이 되지 않음 | 상위 계층을 쌓기 전에 Phase 4에서 조기 검증. NAT 관련 실패를 숨기지 않고 기록. 릴레이 폴백을 후속 해법으로 유보. 지원/미지원 조건을 명시 |
| Windows 가상 네트워킹이 예상보다 복잡함 | 가상 어댑터 작업을 NAT 통과 작업과 분리. 일반 애플리케이션 데이터로 직접 P2P를 먼저 검증. Wintun은 인터페이스 접근에만 사용. 라우팅 로직은 프로젝트가 소유 |
| 범위 과대 | P0-P4 우선순위 고정. 하위 우선순위부터 제거하며 핵심 P2P 목표는 마지막까지 유지 |
| 서드파티 라이브러리 제약 | Wintun 등 비기본 의존성은 사용 전 승인 요청. 핵심 알고리즘은 해당 의존성과 독립적으로 구현. 각 라이브러리가 제공하는 범위를 정확히 문서화 |

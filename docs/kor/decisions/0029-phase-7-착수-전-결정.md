# 0029. Phase 7 착수 전 결정

- 상태: 채택
- 날짜: 2026-10-19
- 관련: [`../roadmap.md`](../roadmap.md) Phase 6·7, [`../windows-prereq.md`](../windows-prereq.md) 2절·14절, [`../protocol.md`](../protocol.md) 8.5·12장, [`../concurrency.md`](../concurrency.md) 3장, [`../architecture.md`](../architecture.md) 7장, [ADR 0027](0027-phase-6-구현-결정.md)

## 맥락

Phase 7 을 시작하려고 문서와 코드를 대조했더니 정하지 않은 자리와 지금 코드와 부딪치는 자리가 있었다. 저장소 소유자가 자리마다
선택지 가운데 하나를 골랐다.

- `windows-prereq.md` 2절은 어댑터로 좁힌 인바운드 허용 규칙의 모양만 정했다. 누가 만들고 언제 지우는지, 이미 있는 규칙을 어떻게
  믿는지가 없다
- 같은 절의 규칙은 TCP 25565 와 ICMP 에코 요청만 연다. `roadmap.md` Phase 7 검증의 파일 전송(SMB 또는 임시 TCP 서버)이 어느 포트를
  쓰는지가 없다
- Phase 6 시험 빌드의 ICMP 응답기는 어댑터에서 읽은 에코 요청에 목적지를 보지 않고 응답한다. 읽기 경로를 라우팅에 이으면 시험
  빌드에서 상대의 가상 IP 로 보낸 `ping` 에 자기가 답한다
- `roadmap.md` Phase 7 검증은 송수신 바이트 카운터를 캡처와 대조하라고 하는데 바이트를 세는 카운터가 없다
- 어댑터가 서자마자 운영체제가 스스로 보내는 패킷이 있다(Phase 6 에서 `adapter_rx` 가 `ping` 전에 0 이 아니었다). 읽기 경로를
  라우팅에 이으면 그중 멀티캐스트와 브로드캐스트가 `tx_drop_no_route` 를 올려, 경로 없는 유니캐스트를 보는 검증과 진단을 흐린다
- 주입 실패 검증은 실제 Wintun 송신 링을 채운 상태를 요구하는데, 그 상태를 결정적으로 만들 수단이 없다

**규칙이 어댑터 재생성 뒤에도 걸리는지를 관리자 셸에서 쟀다.** 어댑터를 띄운 채 `New-NetFirewallRule -InterfaceAlias Sangtachi` 로
규칙 둘을 만들고, 클라이언트를 끝내 어댑터를 없앤 뒤 다시 띄웠다.

- 방화벽은 규칙의 인터페이스를 이름이 아니라 GUID 로 저장한다. 레지스트리의 규칙 원문이 `IF={E2085BB3-83CE-4597-8DD3-68795CCFD00A}` 였다
- 어댑터가 없는 동안 그 규칙의 `InterfaceAlias` 는 GUID 문자열로 보였고, 같은 GUID 의 어댑터가 다시 서자 `Sangtachi` 로 돌아왔다
- 규칙은 사라지지도 꺼지지도 않았다

절차는 [`tools/winprereq/Probe-FirewallRuleBinding.ps1`](../../../tools/winprereq/Probe-FirewallRuleBinding.ps1) 이고, 기기와 출력은
[이 결정의 변경 기록](../commit_history/2026-10-19/02-phase7-착수-전-결정.md)에 있다.

우리 어댑터의 GUID 는 코드 상수다(ADR 0027). 그래서 한 번 만든 규칙이 다음 실행의 어댑터에도 묶인다. 묶인 규칙이 실제로 트래픽을
통과시키는지는 상대 기기가 있어야 보므로 Phase 7 두 기기 검증이 본다.

## 결정

| 자리 | 고른 것 |
|------|---------|
| 방화벽 규칙의 수명 | 클라이언트가 어댑터를 만든 직후 규칙이 없으면 만든다. 지우지 않는다. 지우는 명령은 `windows-prereq.md` 2절에 둔다 |
| 이미 있는 규칙 | 쓰기 전에 검증한다. 새로 만든 직후에도 같은 검증을 한 번 돈다. 검사 항목은 `windows-prereq.md` 2절이 갖는다 |
| 검증에 실패한 규칙 | 기동 실패다. 클라이언트가 고치거나 지우지 않는다. `ERROR` 줄에 어긋난 검사와 지우는 명령을 싣는다 |
| 규칙 만들기 실패 | 기동 실패다 |
| 범위 밖 검사 | 방화벽이 `BlockInboundAlways` 인지는 본다. 같은 포트를 막는 다른 차단 규칙은 보지 않는다 |
| 구현 방식 | 실행 파일 옆의 PowerShell 스크립트를 `System32` 의 Windows PowerShell 로 부르고 종료 코드로 판정한다. 서브넷 충돌 검사와 같은 방식이다 |
| 여는 범위 | TCP 25565 와 ICMPv4 에코 요청(type 8). 호스트와 플레이어가 같은 규칙을 쓴다 |
| 파일 전송 검증 | 25565 의 임시 TCP 서버와 클라이언트로 보내고 양쪽의 SHA-256 을 비교한다 |
| 시험 빌드 ICMP 응답기 | 목적지가 `10.100.0.0/24` 안이고 마지막 옥텟이 `MAX_PEERS` 보다 크고 255 보다 작은 에코 요청에만 답한다. 그 밖은 라우팅으로 간다. 두 기기 검증은 제품 빌드로 돈다 |
| 바이트 카운터 | 프로세스 표에 `tx_bytes`, `rx_bytes`, `tx_datagrams`, `rx_datagrams`. `sendto`, `recvfrom` 이 성공해 돌려준 값을 센다. 캡처는 그 소켓의 로컬 포트로 거른다 |
| 멀티캐스트와 브로드캐스트 목적지 | 송신 측 검증에서 경로 조회 전에 따로 걸러 `tx_drop_not_unicast` 를 올린다 |
| 어댑터 MTU | `protocol.md` 12장의 1400 을 그대로 쓰고 두 기기 실측 뒤 확정한다 |
| 주입 실패 검증 | 가짜 어댑터 단위 시험(`tests/adapter_loop_test.cpp`)이 판정한다 |

## 대안

**방화벽 규칙의 수명.** 실행마다 만들고 종료할 때 지우는 안을 버렸다. 사용자에게 남는 것이 없지만 실행마다 정책을 고친다. 위
실측으로 규칙이 어댑터 재생성을 견딘다는 것을 봤으므로 한 번 만든 규칙을 쓸 수 있다. 사람이 설정 스크립트를 한 번 돌리게 하는 안도
버렸다. 클라이언트가 보안 정책을 바꾸지 않지만 사람의 일이 양쪽 기기에 하나씩 는다.

**검증에 실패한 규칙.** 우리 이름의 규칙을 지우고 다시 만드는 안을 버렸다. 사람 손이 들지 않지만 이름 하나를 근거로 남의 정책을
지운다.

**범위 밖 검사.** 같은 포트를 막는 차단 규칙까지 보는 안을 버렸다. 차단은 허용보다 앞서므로 실제로 막히는 원인이지만, 판정이
규칙 전체의 범위 계산이 되고 `windows-prereq.md` 12절이 Java 쪽 규칙을 사람의 일로 두었다. 두 기기 검증 절차에서 본다.

**구현 방식.** C++ 에서 방화벽 COM API 를 부르는 안을 버렸다. PowerShell 을 한 번 덜 띄우지만 인터페이스 범위의 표현을 따로
확인해야 하고, 규칙을 읽고 판정하는 코드가 `tools/winprereq/Test-FirewallPolicy.ps1` 과 다른 언어로 한 벌 더 생긴다.

**여는 범위.** 포트를 기동 인자로 받는 안을 버렸다. 서버 포트를 바꾼 사용자를 받지만 인자와 시험이 는다. v1 의 한계로 적는다.
우리 어댑터로 들어오는 것을 전부 여는 안도 버렸다. 노출은 방 멤버로 한정되지만 `windows-prereq.md` 2절과 판정 스크립트의 결정을
뒤집는다.

**파일 전송 검증.** SMB 를 버렸다. 445 와 파일 공유를 따로 열어야 한다.

**시험 빌드 ICMP 응답기.** 지우는 안을 버렸다. 관리자 셸 한 기기로 읽기와 주입을 함께 보는 `scripts/adapter-check.ps1` 이
사라진다. 방에 속하지 않았을 때만 답하는 안도 버렸다. 같은 `ping` 이 상태에 따라 다르게 끝난다.

**바이트 카운터.** 세션 표에 두는 안을 버렸다. 상대별로 볼 수 있지만, 수신은 `recvfrom` 시점에 세션을 모른다. 검증 앞 단계에서
버려진 데이터그램이 빠져 캡처와 어긋난다.

**멀티캐스트와 브로드캐스트 목적지.** 그대로 `tx_drop_no_route` 로 세는 안을 버렸다. 운영체제의 잡음이 같은 카운터를 올려 그
카운터의 증가로 판정하는 실기 검증이 고장 난 구현도 통과시킨다. 운영체제 쪽에서 잡음을 줄이는 안도 버렸다. 시스템 설정을 하나 더
바꾼다.

**어댑터 MTU.** 1452 를 버렸다. PPPoE(1492) 경로에서 바깥 UDP 가 조각난다. 1280 도 버렸다. 터널 안의 터널까지 덮지만 효율이
떨어지고, 실측 근거 없이 줄일 이유가 없다.

**주입 실패 검증.** 실제 송신 링을 채우는 안을 버렸다. 운영체제가 링을 비우는 속도에 달려 결과가 정해지지 않는다.

## 결과

**얻는 것.**

- 사람이 방화벽 규칙을 만들지 않는다. 양쪽 기기의 할 일이 그만큼 준다
- 이미 있는 규칙이 우리가 만든 모양과 다르면 기동 시점에 드러난다
- 시험 빌드에서도 상대 가상 IP 로 보낸 `ping` 은 터널을 지난다
- 바이트 카운터를 캡처와 같은 지점에서 잰다
- `tx_drop_no_route` 가 오르면 경로 없는 유니캐스트다

**치르는 것.**

- 클라이언트가 지우지 않으므로 규칙이 시스템에 남는다. 지우는 것은 사람이다
- 기동이 PowerShell 한 번만큼 더 느려진다
- 서버 포트를 25565 가 아닌 값으로 바꾸면 규칙이 그 포트를 덮지 않는다
- 같은 포트를 막는 다른 차단 규칙은 기동 검증이 잡지 않는다
- 바이트 카운터는 상대별로 나뉘지 않는다

## 0. 이 문서의 위치

**제어 평면의 단일 출처다.** 여기서 정하는 것은 다음이다.

- 연산, 요청과 응답 인코딩, 오류
- 식별자, 방과 피어의 상태 전이
- DynamoDB 테이블 설계, 서버 구현 구조
- 클라이언트 쪽 호출 계약

[`architecture.md`](architecture.md) 3.3 제어 평면과 6장 제어 평면 인터페이스는 이 문서를

제어 평면에 요구하는 것**을 적은 목록이다. 요구는 그 문서가, 충족 방법은 이 문서가 갖는다.

| 충돌하는 것 | 우선 |

| 터널 와이어 포맷, 세션 상태, 프로토콜 타이머(`get_peers` 폴링 간격과 마감 포함) | `protocol.md` |

구현 중 이 문서에 없는 값을 만나면 코드에서 정하지 않고 이 문서를 먼저 고친다.

## 1. 범위와 신뢰 가정

### 1.1 하는 것과 하지 않는 것

| 하는 것 | 하지 않는 것 |
|---------|--------------|
| 방 생성과 참가 | 게임 트래픽 중계. 데이터 경로에 있지 않다 (NFR-1) |
| 가상 IP 배정 | 지표 수집. 텔레메트리 서비스가 맡는다 ([`architecture.md`](architecture.md) 3.4, [ADR 0003](decisions/0003-텔레메트리-서비스-분리.md)) |
| 후보 엔드포인트 저장과 전달 | **UDP 소켓을 열지 않는다.** NAT 매핑 수명 측정에 쓰는 EC2 쪽 UDP probe 송신기는 제어 서버의 기능이 아니라 별개 도구다. 그 도구의 소속과 절차는 [`roadmap.md`](roadmap.md) Phase 4 착수 전 항목이 갖는다 |
| 랑데부 기준점(`punch_delay_ms`, `elapsed_since_ready_ms`) 제공 | NAT 유형 판정, 홀펀칭 결과 판정. 클라이언트가 한다 |
| 호스트의 통지로 자리 회수, 후보 없이 떠난 참가자의 서버 회수 (4.6 `host_report`) | 세션 재시도 개시. 누가 언제 재시도하는지는 미정이고 [`protocol.md`](protocol.md) 10.4 엔드포인트 학습이 그렇게 적었다 |
| 호스트의 신호로 방 임대 갱신 (4.6, 5.1) | **터널 생존 판정.** 임대가 끊겨도 이미 수립된 터널은 그대로 간다 ([`spec.md`](spec.md) NFR-3) |
| 쌍의 준비 완료 기록 (4.6, 5.2) | **떠난 피어의 식별자 복구.** 재참가가 없다(4.3). 다시 들어오는 것은 새 참가다 |

### 1.2 신뢰 가정

**v1 의 제어 평면 경로는 평문이고 호출자 인증이 없다.** [`protocol.md`](protocol.md) 2장이 터널 경로에 대해 한 것과 같은 종류의 명시적 선택이다. 최종 보고서는 이 한계를 터널 쪽 한계와 나란히 적어야 한다.

| 가정 | 내용 | 결과 |
|------|------|------|
| 서버를 신뢰한다 | 클라이언트는 서버가 돌려준 상대 후보와 가상 IP 를 검증 없이 쓴다. 후보 위생(`protocol.md` 10.1 후보 수집과 위생)은 클라이언트가 따로 적용하지만 그것은 형식 검사이고 진위 검사가 아니다 | 악의적 서버는 임의의 후보를 넣어 클라이언트를 제3자에게 200ms 마다 패킷을 보내는 **반사 도구**로 쓸 수 있다. 그 반사의 상한은 `protocol.md` 2장 보안 모델이 적는다. 아래 "반사 후보를 넣는 것" 을 같이 본다 |
| `room_id` 가 유일한 비밀이다 | 방에 참가하는 데 필요한 것은 `room_id` 하나다. 호스트가 그것을 참가자에게 다른 채널로 전달한다 | `room_id` 를 아는 임의의 호출자가 두 번째 피어로 참가해 후보를 받고 게임 상대가 된다. **방 탈취**다. 그러면 진짜 참가자는 `room_full` 을 받는다 |
| 경로상 관측자가 있다 | TCP 평문이라 경로상 관측자가 `room_id`, `peer_token`, 양쪽의 로컬·공인 엔드포인트를 읽는다 | 위와 같은 방 탈취, 그리고 **내부망 주소 노출.** 로컬 후보는 사설 IP 와 포트다 |
| `peer_token` 은 참가 안에서만 쓰는 인증 비밀이다 | 참가 시 발급하고 그 참가가 끝나면 버린다. 프로세스 밖으로 내보내지 않는다 ([`architecture.md`](architecture.md) 3.5 기동 입력) | 평문 경로에서 새는 것은 `room_id` 와 같다. **경로상 관측자에 대한 방어가 아니다.** 막는 것은 `room_id` 만 아는 제3자가 이미 참가한 피어를 사칭해 그 피어의 후보를 바꾸거나(4.4), 호스트를 사칭해 남의 자리를 지우는 것이다(4.6) |
| 호출자 IP 를 그 TCP 연결에서 응답할 수 있는 주소로 본다 | 핸드셰이크를 마친 연결의 출발지다. 그 뒤에 NAT 나 프록시가 있어 여러 사용자가 한 주소로 보일 수 있고, 반대로 한 호출자가 여러 주소를 쓸 수 있다 | 6.4 속도 제한의 출발지별 예산이 이 가정 위에 선다. 주소가 많은 호출자에게는 효과가 그만큼 줄고, 주소를 공유하는 정상 사용자는 남의 예산 소진에 걸린다(6.4 속도 제한의 케이스 표 `row-12`) |
| `client_nonce` 도 비밀이다 | 멱등성 키(2.4)이지만, 그 값을 아는 누구든 같은 요청을 다시 보내 **같은 응답**을 받는다. 응답에는 `peer_token` 이 들어 있다(4.2, 4.3) | 경로상 관측자는 토큰을 이미 읽으므로 새 능력은 아니다. 다만 클라이언트가 nonce 를 로그나 화면에 남기면 토큰을 남긴 것과 같다. **`room_id` 와 같은 등급으로 다룬다** |

**반사 후보를 넣는 것은 서버만 할 수 있는 일이 아니다.** 방에 참가한 상대 피어가
`register_candidate` 로 같은 주소를 등록하면 결과가 같다. 서버는 형식만 보고 전달한다.
`protocol.md` 10.1 후보 수집과 위생이 막는 것은 브로드캐스트·멀티캐스트 같은 증폭 경로다.

**v1 이 수용하는 한계다.** 인증과 TLS 는 [`spec.md`](spec.md) 스트레치 목표다. 도입할 때 위 표의 "결과" 열이 무엇을 잃는지가 판정 기준이 된다. `room_id` 의 크기가 작은 것(2.1)도 같은 표의 연장이다.

**가용성 쪽 한계도 여기에 적는다.** 위 표가 기밀성과 사칭을 다뤘다면 아래 둘은 **무인증
호출자가 서비스를 느리게 만드는** 경로다. v1 은 둘 다 수용한다.

| 경로 | 무엇이 일어나는가 | 왜 수용하는가 |
|------|-------------------|---------------|
| 동시 연결 자리 고갈 | 헤더를 보내지 않는 연결 32개(`MAX_INFLIGHT`)를 5초마다 다시 여는 호출자가 그 구간의 정상 요청을 `unavailable` 로 만든다 (3.4, 7.2) | 출발지별 동시 연결 상한이 필요한데 그 판정이 위 표의 "호출자 IP" 가정 위에 서므로 같은 한계를 물려받는다 |
| `create_room` 남용 | `create_room` 은 입력이 `client_nonce` 하나이고 성공 응답이라 6.4 속도 제한이 세지 않는다. nonce 를 바꿔 반복하면 호출마다 항목 4개짜리 트랜잭션 쓰기가 생기고 만료 뒤 하루까지 남는다(6.5). provisioned 쓰기 용량을 소진하면 정상 요청이 스로틀에 걸려 `internal` 이 된다 | 성공을 세면 정상 폴링이 걸린다는 6.4 속도 제한의 이유는 `get_peers` 에 대한 것이고 `create_room` 에는 폴링이 없다. 출발지별 방 생성 상한은 넣을 수 있으나 v1 은 넣지 않는다. **관측은 한다.** `room.created` 로그(7.5)의 출발지별 빈도가 그 근거다 |

**이 둘은 방을 탈취하거나 값을 바꾸지 못한다.** 느리게 하거나 멈출 뿐이다. 그래서 위 신뢰
가정 표와 나누어 적는다.

## 2. 식별자와 상수

### 2.1 room_id

**6글자, 32자 알파벳, CSPRNG.** 알파벳은 다음이다.

```text
ABCDEFGHJKLMNPQRSTUVWXYZ23456789      (32자. I, O, 0, 1 을 뺐다)
```

- 엔트로피는 32^6 = 2^30 이다. **약 10억 가지이고 온라인 추측이 가능한 크기다**
  - 사람이 콘솔에 치는 값이라 길이를 6 으로 정했고, 그 대가로 6.4 속도 제한을 둔다
  - 속도 제한이 없으면 열린 방을 찾아내는 데 드는 요청 수를 제한하는 것이 서버 처리량뿐이다
  - 제한을 두어도 막는 것이 아니라 느리게 하는 것이다. 1.2 신뢰 가정의 한계 표에 속한다
- `I`, `O`, `0`, `1` 을 뺀 이유는 사람이 읽고 옮겨 적을 때 헷갈리기 때문이다. 알파벳에 없는 글자를 받으면 오류다. **닮은 글자로 바꿔 해석하지 않는다.** `0` 을 `O` 로 고쳐 주면 두 입력이 같은 방을 가리켜 알파벳을 줄인 의미가 없어진다
- 입력은 **대소문자를 무시한다.** 서버는 받은 값이 ASCII 인지 먼저 보고, 대문자로 바꾼 뒤 알파벳 검사를 한다. 소문자 `a` 는 `A` 다. 이것은 닮은 글자 치환이 아니라 같은 글자의 표기 차이다
  - ASCII 검사가 대문자 변환보다 먼저다. 순서가 반대면 `ſ`(U+017F) 처럼 대문자로 바꾸면 ASCII 가 되는 글자가 통과한다
- 서버는 생성 시 `ROOM` 항목의 조건부 쓰기(6.3)로 충돌을 잡고, 충돌하면 다시 뽑는다. 시도 상한은 `MAX_ROOM_ID_ATTEMPTS`(4)다. 넘기면 `internal` 오류다. 열린 방이 수십 개인 규모에서 30비트 공간의 충돌은 사실상 없고, 상한은 저장소 오류가 무한 재시도로 번지는 것을 막기 위한 것이다

**케이스 표.** 정규화와 검사가 통과해야 하는 표는
[`test_room_id.py`](../../control-server/tests/test_room_id.py) 의 `ROOM_ID_CASES` 다. 표 밖 규칙을 지키는
행은 같은 파일의 `ROOM_ID_EXTRA_CASES` 에 있다. 앞뒤 공백을 지워 주지 않고, 문자열이 아니거나 필드가
없으면 `bad_request` 다.

### 2.2 peer_id

**CSPRNG 32비트, 0 제외, 방 안 유일.** 와이어 헤더가 `peer_id` 를 4바이트로
정했고([`protocol.md`](protocol.md) 4.2 `peer_id`) 서버가 이 값을 발급한다.

- `secrets.randbits(32)` 로 뽑고 0 이면 다시 뽑는다
- 방 안 유일성은 `PEER#<peer_id>` 항목의 조건부 쓰기(6.3)가 보장한다
- 충돌하면 다시 뽑고 시도 상한은 `MAX_PEER_ID_ATTEMPTS`(4)다. 상한은 요청 하나에 하나다. `join_room`
  이 풀의 다음 주소로 넘어가도 새로 주지 않는다

순차 할당을 쓰지 않는다. 근거는 아래 "왜 이렇게 정했나" 에 있다.

### 2.3 peer_token

**128비트 CSPRNG, 소문자 16진수 32자.** `secrets.token_hex(16)`. 참가(또는 방 생성)
응답에 실리고, 그 뒤 그 피어의 모든 요청에 들어간다. **서버는 원문을 저장한다**(6.3).
요청에 실린 값이 이 형식이 아니면(대문자가 섞이거나 길이가 다르면) 토큰을 비교하지 않고
`bad_request` 다(7.3 연산 처리 순서의 1번).

- 해시만 저장하면 응답을 잃은 클라이언트가 같은 `client_nonce` 로 다시 왔을 때(2.4, 4.2,
  4.3) 같은 토큰을 돌려줄 수 없다
- 저장소가 읽히면 토큰이 새는 대가가 있다. 경로가 평문이고 `room_id` 가 유일한 비밀인 v1
  에서 그 대가는 이미 치르고 있는 것과 같은 종류다(1.2). 인증을 도입할 때 이 줄을 다시 본다

토큰이 필요한 이유는 아래 "왜 이렇게 정했나" 에 있다.

### 2.4 client_nonce

**클라이언트가 만드는 128비트 CSPRNG, 소문자 16진수 32자.** `create_room` 과
`join_room` 요청에 실린다. 멱등성 키다. 응답을 받지 못하고 재시도한 요청이 두 번째 피어
자리를 다시 차지하는 것을 막는다(4.2, 4.3). 서버는 이 형식만 받는다. 대문자가 섞이거나 길이가
다르면 `bad_request` 다.

클라이언트는 **한 참가에서 한 값**을 쓰고 그 참가의 재시도마다 바꾸지 않는다. 방을 나가
다음 방에 참가할 때는 새 값을 뽑는다.

> **왜.** 멱등이어야 하는 작업의 단위가 참가 1회다. 한 기동에 한 값으로 고정하면 로비에서
> 다시 참가할 때 6.3 취소 사유 1번이 그 요청을 "이미 성립한 요청" 으로 보고 옛 방의 응답을
> 돌려준다. 참가 안에서 값을 바꾸면 반대로 멱등성이 사라진다.

### 2.5 가상 IP 풀

| 항목 | 값 |
|------|-----|
| 대역 | `10.100.0.0/24` ([`spec.md`](spec.md) FR-4) |
| 호스트(방 생성자) | `10.100.0.1`. 방 생성 시 확정 |
| 참가자 풀 | `10.100.0.2` 부터 `10.100.0.(MAX_PEERS)` 까지. `MAX_PEERS` 가 5 이므로 풀은 `10.100.0.2` 부터 `10.100.0.5` 까지 넷이다 |
| 배정 순서 | 풀을 낮은 주소부터 순회하며 `VIP#<ip>` 항목을 조건부 쓰기로 선점한다(6.3). 실패하면 다음 주소. 풀이 끝나면 `room_full` |
| 시도 상한 | 풀 크기. 풀을 한 바퀴 돌면 끝난다. 무한히 돌지 않는다 |
| 회수 | 둘이다. 호스트가 4.6 `host_report` 로 그 피어의 이탈을 알리면 `PEER#` 와 `VIP#` 를 함께 지운다. 후보를 한 번도 등록하지 않은 채 `JOIN_REGISTER_GRACE_S` 가 지난 참가자는 서버가 같은 요청을 처리하면서 지운다(4.6). 방이 만료되면 남은 항목이 TTL 로 삭제된다(6.5) |

**회수한 주소는 다음 `join_room` 새 참가가 바로 쓴다.** 되돌아올 자리를 비워 두지 않는다.
재참가가 없으므로(4.3) 그 주소를 원래 쓰던 피어가 다시 요구하는 경로 자체가 없다.

**회수의 선행조건은 그 피어의 터널 세션이 종료 상태인 것이다.** 호스트는 세션이 끝난 뒤에만
알린다(4.6). 서버 회수는 이 조건을 따로 보지 않는다. 후보가 없는 피어는 호스트가 확인할 수
없어(4.6 처리 순서의 3번) 터널 세션이 생긴 적이 없다. 아직 살아 있는 세션의 주소를 회수하면 클라이언트의 라우팅 표 한 칸을 두 세션이
요구하게 된다([`protocol.md`](protocol.md) 8.5 송신 측 검증).

`MAX_PEERS` 를 올리면 풀이 그만큼 늘고 다른 것은 바뀌지 않는다. 6인 이상은 `spec.md`
스트레치 목표다.

### 왜 이렇게 정했나

- **2.2 `peer_id` 에 순차 할당을 쓰지 않는다.** [`protocol.md`](protocol.md) 2장 보안
  모델의 위협 전제가 "`peer_id` 를 알거나 추측하면" 이기 때문이다. 순차 할당이면 추측이
  자명해져 그 문서의 위조 `HELLO` 공격이 경로 밖에서 성립한다. 32비트 난수는 그 추측을
  어렵게 하는 보조 수단이다. 위조 `HELLO` 는 UDP 로 클라이언트에 직접 오므로 서버의 속도
  제한(6.4)이 그 추측을 늦추지 못하고, 추측 비용의 상한을 이 문서가 계산하지는 않는다.
  **경로상 관측자에게는 아무것도 숨기지 못한다.** 평문이다
- **2.3 `peer_token` 이 필요한 이유는 둘이다.** (1) `register_candidate` 가 `room_id` 와
  `peer_id` 만으로 되면 `room_id` 를 아는 제3자가 상대 피어의 후보를 덮어써 그 피어의
  `HELLO` 를 임의의 주소로 보내게 할 수 있다. (2) 4.6 `host_report` 는 남의 항목을 지우므로
  호출자가 호스트 본인임을 판정할 근거가 필요하다

## 3. 전송과 인코딩

### 3.1 왜 HTTP 부분집합인가

전송은 **TCP 위의 HTTP/1.1 부분집합**이고 본문은 JSON 이다. 세 가지를 저울질했다.

| 안 | 장점 | 단점 |
|----|------|------|
| **HTTP/1.1 부분집합 (채택)** | `curl` 로 시험할 수 있다. 서버 쪽 `ss`, 보안 그룹, `Test-NetConnection` 같은 기존 절차([`windows-prereq.md`](windows-prereq.md) 6절)가 그대로 맞는다 | 양쪽을 손으로 짜야 한다. 부분집합을 좁게 못박아 그 비용을 줄인다 |
| 줄 단위 JSON over TCP | 구현이 가장 단순하다 | 표준 도구로 시험할 수 없다. 시험 도구를 하나 더 만들게 된다 |
| 웹 프레임워크 | 파싱을 안 짠다 | [`spec.md`](spec.md) NFR-5 승인이 필요하고, 클라이언트 쪽 비용은 그대로다 |

부분집합은 아래 3.3 HTTP 부분집합이 전부다. **거기 없는 HTTP 기능은 지원하지 않는다.** 받았을 때
거부하는지 표 밖 헤더로 무시하는지는 3.3 의 규칙 표가 정한다.

> **왜.** 지원하는 척하다 조용히 틀리는 것보다 낫다.

### 3.2 주소

| 항목 | 값 |
|------|-----|
| 프로토콜 | TCP, IPv4 |
| 서버 bind | `0.0.0.0:8000`. 판정 방법은 [`windows-prereq.md`](windows-prereq.md) 6절 |
| 클라이언트가 받는 주소 | **DNS 이름 또는 IPv4 리터럴.** 기동 입력([`architecture.md`](architecture.md) 3.5 기동 입력)으로 받는다. DNS 이름은 Elastic IP 를 가리키는 A 레코드다. Elastic IP 가 필요한 이유는 `windows-prereq.md` 10절 |
| 경로 접두사 | `/v1/`. 인코딩이 호환되지 않게 바뀌면 `/v2/` 를 연다. 같은 서버가 두 접두사를 동시에 낼 수 있다 |

DNS 해석은 클라이언트의 `[control]` 스레드가 한다([`concurrency.md`](concurrency.md) 8장 `[control]`
스레드). 해석 결과가 여럿이면 첫 IPv4 주소를 쓰고 나머지는 쓰지 않는다. `AAAA` 는 쓰지
않는다. 터널이 IPv4 전용인 것([`protocol.md`](protocol.md) 1장 범위와 전제)과 같은 범위다.

### 3.3 HTTP 부분집합

**요청.**

```text
POST /v1/<op> HTTP/1.1\r\n
Host: <서버 주소>\r\n
Content-Type: application/json\r\n
Content-Length: <본문 바이트 수>\r\n
Connection: close\r\n
\r\n
<JSON 본문>
```

**응답.**

```text
HTTP/1.1 <status> <reason>\r\n
Content-Type: application/json\r\n
Content-Length: <본문 바이트 수>\r\n
Connection: close\r\n
\r\n
<JSON 본문>
```

| 항목 | 규칙 |
|------|------|
| 메서드 | `POST` 만. 조회(`get_peers`)도 `POST` 다. 인증 정보(`peer_token`)가 URL 이나 로그에 남지 않게 본문에 싣기 때문이다 |
| 경로 | `/v1/` + 4장의 연산 이름. 쿼리 문자열 없음 |
| 본문 길이 | `Content-Length` 필수. `Transfer-Encoding` 이 있으면 값이 무엇이든 거부 |
| 연결 | 요청 하나에 연결 하나. 응답 뒤 서버가 닫는다. keep-alive 와 파이프라이닝 없음 |
| 헤더 | 이름은 대소문자 무시. 위 형식의 넷(`Host`, `Content-Type`, `Content-Length`, `Connection`)과 `Transfer-Encoding` 을 표의 헤더로 본다. 그 밖의 헤더는 무시한다(두 번 와도 무시한다). **표의 헤더가 두 번 오면 거부한다.** `Content-Length` 의 중복은 아래를 본다 |
| 헤더 줄 문법 | `이름:값` 이다. 콜론이 없는 줄과, 이름과 콜론 사이에 공백이나 탭이 있는 줄은 거부한다(RFC 9112 5.1). 콜론 바로 뒤의 공백 하나는 구분자로 떼고, 그 밖의 공백은 값의 일부다 |
| 본문 | UTF-8 JSON **객체** 하나. 배열이나 스칼라는 거부. 알 수 없는 키는 무시한다(전방 호환). 한 객체 안의 중복 키는 중첩 객체까지 거부한다. `NaN`, `Infinity` 는 JSON 이 아니므로 거부한다 |
| 크기 | 요청 줄과 헤더 합계 `MAX_HEADER_BYTES`(2048), 본문 `MAX_BODY_BYTES`(4096). 앞쪽은 요청 줄 첫 바이트부터 헤더 끝 빈 줄의 CRLF 까지 센다 |
| 인코딩 | 문자열은 UTF-8. 정수는 JSON number 이고 소수점 없음. `uint32` 필드는 0 이상 4294967295 이하 |
| 압축, 청크, 100-continue, 업그레이드, 인증 헤더 | 지원하지 않는다. `Transfer-Encoding` 은 거부하고, `Content-Encoding`, `Expect`, `Upgrade`, `Authorization` 은 표 밖 헤더라 무시한다 |
| 바이트 정확 일치 | 요청 줄은 `POST <경로> HTTP/1.1` 이고 구분자는 공백 하나다. 공백 둘, 탭, 절대 형식(`POST http://host/v1/op`), 끝에 붙은 `/`, 퍼센트 인코딩(`%5F`)은 전부 거부한다. 경로는 대소문자를 구분한다. 문법은 표 아래 |
| `Content-Length` 값 | `^[0-9]+$` 만 받는다. `+17`, `1_7`, 앞뒤 공백, 전각 숫자는 거부한다. 언어의 정수 변환 함수에 맡기지 않는다. Python `int()` 는 앞의 셋을 받는다 |
| 헤더 접기 (obs-fold) | 헤더 줄이 공백이나 탭으로 시작하면 거부한다. 이어 붙이지 않는다 |
| `Host`, `Content-Type` | **검사하지 않는다.** 클라이언트는 항상 보내지만(위 형식) 서버는 값을 보지 않는다. 가상 호스트도 콘텐츠 협상도 없다 |
| `Content-Length` 보다 긴 본문 | 앞의 `Content-Length` 바이트만 읽고 응답한 뒤 연결을 닫는다. 남은 바이트는 읽지 않는다. 연결 하나에 요청 하나이므로 그 바이트는 두 번째 요청이 될 수 없다 |

**요청 줄 문법.** 첫 CRLF 앞의 바이트가 `([!-~]+) ([!-~]+) HTTP/1\.1` 에 전체 일치해야 한다.
둘째 묶음(대상)은 `/` 로 시작하고, `/` 로 끝나지 않고, `%` 를 담지 않는다. 어긋나면 `400` 이다.
그다음 메서드가 정확히 `POST` 가 아니면 `405`, 대상이 정확히 `/v1/<op>` 가 아니면 `404` 다.
`<op>` 는 4장의 다섯 연산이고 대소문자를 구분한다.

**`Content-Length` 가 두 번 오는 것을 특히 거부한다.** 값이 다른 `Content-Length` 가
여럿인 메시지를 거부하라는 것은 RFC 9112 의 6.3 절 규정이고, 앞뒤 중계자가 다른 값을 고르는
것이 요청 밀반입의 한 형태다. 값이 같아도 거부한다. 구분할 이유가 없다.

**서버 파싱 케이스 표.** [`test_http.py`](../../control-server/tests/test_http.py) 의 `CASES` 다. 판정
함수는 이 표를 통과해야 한다. 위 규칙 가운데 그 표의 행이 다루지 않는 것은 같은 파일의
`RULE_CASES`, 파싱 실패 응답이 요청 내용을 되돌려 보내지 않는지는 `ECHO_CASES`, 여러 번에 나눠
도착하는 요청과 3.4 서버 쪽 시간 제한은 `STREAM_CASES` 가 본다.

`Content-Length` 가 `MAX_BODY_BYTES` 를 넘으면 본문을 읽지 않고 `413` 을 보낸 뒤 닫는다.

**검사 순서.** 복합 결함의 응답을 정하려면 순서가 필요하다. 위에서부터 본다.

1. 요청 줄의 바이트 형식과 `HTTP/1.1` -> `400`
2. 메서드 -> `405`
3. 경로 (`/v1/` 접두사와 연산 이름, 쿼리 문자열 없음) -> `404`
4. 헤더 전체 크기 -> `431`. 요청 줄이 상한 안에서 끝나지 않으면 1~3 을 판정할 수 없으므로 바로 `431` 이다
5. 헤더 문법 (접기, 표에 있는 헤더의 중복) -> `400`
6. `Transfer-Encoding` 존재 -> `400`
7. `Content-Length` 존재 -> `411`, 값 형식 -> `400`, 상한 초과 -> `413`
8. 본문 읽기와 시간 제한 (3.4) -> 응답 없이 닫음. 다 받기 전에 상대가 닫아도 응답 없이 닫는다. 그때는 카운터를 올리지 않는다
9. 본문이 UTF-8 JSON 객체인가 -> `400`

`400` 대 오류에도 본문은 4.1 공통 봉투의 오류 봉투다. **파싱 실패 응답은 요청 내용을
되돌려 보내지 않는다.**

> **왜.** 그러면 서버가 임의 바이트를 반사하는 자리가 된다.

### 3.4 서버 쪽 시간 제한

연결 수락부터 요청 한 건을 다 읽기까지 `SERVER_READ_TIMEOUT_S`(5초)다. 넘기면 응답 없이 닫고 `http_read_timeout` 을 올린다. 응답 송신에도 같은 5초를 건다. 송신이 그 안에 끝나지 않으면 남은 바이트를 버리고 연결을 끊는다(abort). 카운터는 없다.

**요청을 다 읽지 않은 채 답하는 경로는 바로 닫지 않는다.** `503`, `413`, `431` 과 그 밖의 파싱 실패가 그렇다. 응답을 보낸 뒤 쓰기 쪽을 먼저 닫고, 남은 입력을 `LINGER_S`(1초) 또는 `LINGER_MAX_BYTES`(8192) 까지 읽어 버린 다음 닫는다.

> **왜.** 읽지 않은 바이트가 수신 버퍼에 남은 채 닫으면 OS 가 RST 를 보내고, 클라이언트는 이미 도착한 응답을 읽기 전에 연결 재설정 오류를 받을 수 있다. RFC 9112 의 9.6 절이 같은 문제를 다룬다. 개발 기기(Windows)에서 쟀다. 이 처리 없이 닫으면 `503` 과 `413` 을 20번씩 보내 20번 모두 응답 대신 연결 재설정을 받고, 이 처리가 있으면 20번 모두 응답을 받는다.

- 파싱 실패 뒤의 이 대기는 처리 중 요청 수(7.2 의 `MAX_INFLIGHT`)에 들어 그 자리를 최대 `LINGER_S` 더 차지한다. `503` 뒤의 대기는 자리를 차지하지 않는다. 그 연결은 처음부터 자리를 받지 못했다
- 정상 응답과 송신 시간 초과로 끊은 연결에는 이 대기가 없다

**막는 것과 막지 못하는 것을 구분해 적는다.** 이 값이 막는 것은 한 연결의 점유 시간이다.

**동시 연결 자리의 고갈은 막지 못한다.** `MAX_INFLIGHT`(32)는 수락 직후, 파싱 전에
오르므로(7.2) 헤더를 보내지 않는 연결 32개를 5초마다 다시 여는 호출자는 그 구간의 정상
요청을 전부 `unavailable` 로 만든다.

- 그 호출자는 6.4 속도 제한의 예산도 쓰지 않는다. `http_read_timeout` 은 그 절이 세는 셋에
  없기 때문이다
- 정상 클라이언트는 8.3 오류 분류와 재시도의 규칙대로 재시도한 뒤
  `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다
- 막으려면 출발지별 동시 연결 상한이 필요하고, 그것은 6.4 속도 제한의 출발지 가정(1.2)을 그대로
  물려받는다

**v1 이 수용하는 한계다.** 1.2 신뢰 가정의 한계 표에 속한다.

### 3.5 클라이언트가 하는 검사

클라이언트는 응답에서 다음만 본다. 그 외는 무시한다.

1. 상태 줄이 `HTTP/1.1 <3자리 숫자>` 로 시작하는가. 아니면 `CONTROL_PLANE_EXCHANGE_FAILED` 로 이어지는 전송 오류다(8.3)
2. `Content-Length` 헤더 하나. 없거나 `MAX_BODY_BYTES` 를 넘으면 전송 오류
3. 본문을 그 길이만큼 읽고 JSON 객체로 해석한다. 실패하면 전송 오류
4. `ok` 필드(4.1)로 성공과 오류를 가른다. **HTTP 상태 코드로 가르지 않는다**
   - 상태 코드는 `curl` 을 든 사람을 위한 것이고 프로그램이 보는 것은 본문이다
   - 둘이 어긋나는 구현은 시험에서 걸러야 한다. 다만 클라이언트가 둘 다 보면 어긋났을 때
     어느 쪽을 믿을지가 구현마다 달라진다

## 4. 연산

연산은 다섯이다. `create_room`, `join_room`, `register_candidate`, `get_peers`,
`host_report`.

**앞의 넷은 누구나 부르고 `host_report` 는 호스트만 부른다.** 그 판정은 4.6 이 정한다.

**`register_peer` 는 없다.** 참가는 `create_room` 과 `join_room` 둘로 끝나므로 별도 연산이
할 일이 없다. 클라이언트가 "언제 `join_room` 이고 언제 `register_peer` 인가" 를 판단하지
않는다.

**`leave_room` 도 없다.** 나가는 본인이 부르는 연산을 두지 않는다. 자리를 회수해도 되는지를
아는 것은 그 터널 세션의 한쪽 끝인 호스트이고(2.5 회수), 본인이 부르면 호스트가 아직 세션을
닫기 전에 자리가 비는 상태가 생긴다. 후보 없이 떠난 참가자는 세션이 생긴 적이 없으므로 서버가
회수한다(4.6 서버 회수).

### 4.1 공통 봉투

**성공.**

```json
{"ok": true, ...연산별 필드}
```

**오류.**

```json
{"ok": false, "error": "<오류 코드>", "message": "<사람용 한 줄>"}
```

`error` 는 아래 표의 문자열 중 하나이고 프로그램이 본다. `message` 는 사람이 읽는 것이고 내용을 못박지 않는다. **`message` 에 요청 본문이나 토큰을 넣지 않는다.**

| 오류 코드 | HTTP | 뜻 | 클라이언트 동작 |
|-----------|------|-----|-----------------|
| `bad_request` | 400 | 필수 필드 누락, 형식 위반, 2.1 알파벳 위반 | 재시도하지 않는다. `CONTROL_PLANE_EXCHANGE_FAILED` |
| `method_not_allowed` | 405 | `POST` 아님 | 같음 |
| `unknown_op` | 404 | 경로가 4장의 연산이 아님 | 같음 |
| `length_required` | 411 | `Content-Length` 없음 | 같음 |
| `too_large` | 413 / 431 | 본문 또는 헤더 상한 초과 | 같음 |
| `room_not_found` | 404 | 그 `room_id` 의 방이 없다 | 같음. **만료된 방도 이 코드가 아니다.** 아래 `room_expired` |
| `room_expired` | 410 | 방이 있으나 만료 시각이 지났다(5.1) | 같음 |
| `room_full` | 409 | 참가자 풀의 주소가 전부 선점됐다(2.5) | 같음 |
| `unauthorized` | 403 | `peer_token` 이 그 `peer_id` 의 것이 아니다 | 같음 |
| `rate_limited` | 429 | 6.4 속도 제한의 출발지별 예산 소진 | 같음. 클라이언트가 스스로 기다렸다 다시 하지 않는다. 사람이 다시 시작한다. `host_report` 만 예외다(4.6) |
| `internal` | 500 | 저장소 오류, 재추첨 상한 도달 | **일시 오류다.** 8.3 오류 분류와 재시도의 규칙을 따른다 |
| `unavailable` | 503 | `MAX_INFLIGHT` 초과(7.2) | 같음. 일시 오류 |

**`bad_request`, `rate_limited`, `internal`, `unavailable` 은 모든 연산에서 나올 수 있다.**
파싱과 속도 제한과 저장소 오류는 연산 앞뒤의 공통 단계(7.2, 7.3)에서 나기 때문이다. 아래
연산별 "오류" 줄은 그 연산에서만 나는 것을 적고 이 넷을 다시 적지 않는다.

`room_not_found` 와 `room_expired` 를 나눈 근거는 아래 "왜 이렇게 정했나" 에 있다.

### 4.2 create_room

호스트가 부른다. 방을 만들고 호스트를 첫 피어로 등록하고 `10.100.0.1` 을 준다.

**요청.**

| 필드 | 형 | 필수 | 뜻 |
|------|-----|:---:|-----|
| `client_nonce` | 16진수 32자 문자열 | 예 | 멱등성 키(2.4) |

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `room_id` | 문자열 6자 | 2.1 |
| `peer_id` | uint32 | 2.2 |
| `peer_token` | 16진수 32자 | 2.3 |
| `virtual_ip` | 점 십진 문자열 | `10.100.0.1` |
| `expires_in_s` | 정수 | 응답 시점부터 만료까지 남은 초. 절대 시각을 주지 않는다. 클라이언트 시계를 믿지 않는다 |

**멱등성.** 같은 `client_nonce` 로 다시 오면 **이미 만든 방의 같은 응답**을 돌려준다. `expires_in_s` 만 줄어든다. 그 방이 만료됐으면 `room_expired` 다. 새 방을 만들지 않는다. 판정 근거는 `NONCE#` 항목(6.3)이다.

**오류.** 연산 고유의 것은 없다. 공통 넷(4.1)만 난다.

### 4.3 join_room

**참가자가 부른다.** 풀에서 가상 IP 를 선점하고 새 `peer_id` 와 `peer_token` 을 발급한다.
형식은 하나다.

**재참가는 없다.** 프로세스가 죽으면 그 피어의 자리는 호스트의 통지로 회수되고(2.5), 다시
들어오는 것은 새 참가다. 새 `peer_id` 를 받고 가상 IP 는 2.5 배정 순서대로 다시 배정한다.
옛 주소가 그때 비어 있으면 같은 값이 나올 수 있다.

> **왜.** 되돌아올 자리를 비워 두려면 방이 살아 있는 동안 그 주소를 회수할 수 없다. 늦게 온
> 참가자가 그 자리를 쓰는 것과 떠난 피어가 그 자리를 되받는 것은 같이 성립하지 않는다.

**요청.**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예. 2.1 정규화를 거친다 |
| `client_nonce` | 16진수 32자 | 예 |

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `room_id` | 문자열 6자 | 정규화된 값. 클라이언트는 이후 이 값을 쓴다 |
| `peer_id` | uint32 | |
| `peer_token` | 16진수 32자 | 이 참가 동안의 인증 비밀(2.3) |
| `virtual_ip` | 점 십진 문자열 | |
| `expires_in_s` | 정수 | 남은 임대(5.1). 표시에만 쓴다 |

**멱등성.** 같은 `room_id` 와 `client_nonce` 로 다시 오면 처음 발급한 것을 그대로 준다.
`NONCE#` 항목이 근거다. 다른 `client_nonce` 로 오면 새 참가이고, 풀의 주소가 전부
선점됐으면 `room_full` 이다.

- `NONCE#` 가 가리키는 `PEER#` 가 없으면 처음 발급한 것을 줄 수 없다. 판정 불가이고 `internal`
  이다. 회수는 `PEER#` 와 `NONCE#` 를 함께 지우므로(4.6) 정상 경로에서는 생기지 않는다
- `NONCE#` 는 있는데 방이 TTL 로 먼저 지워졌으면 5.1 방의 (없음) 이므로 `room_not_found` 다
- `NONCE#` 는 연산을 가리지 않는다. `create_room` 의 nonce 를 같은 방의 `join_room` 에 주면 저장된
  기록(그 피어의 것)을 돌려준다. 반대도 같다. 다른 방이면 `bad_request` 다(6.3 취소 사유 1번)

> **왜.** 응답을 잃은 클라이언트가 nonce 를 바꿔 재시도하면 자기 자신이 방을 채운다. 그래서
> 2.4 `client_nonce` 가 한 참가에 한 값이라고 정했다.

**`room_full` 의 판정은 풀 순회 결과뿐이다.** 풀을 한 바퀴 돌아 빈 주소가 하나도 없을 때만
이 오류다. 방이 `ready` 인지는 보지 않는다(5.1).

> **왜.** 준비 완료가 쌍 단위이므로 이미 붙은 쌍이 있는 방에도 빈 자리가 있을 수 있다.
> 자리의 진실은 `VIP#` 선점이고 피어 수는 그 파생이다. 두 곳에서 판정하면 회수 직후에
> 어긋난다.

**오류.** `room_not_found`, `room_expired`, `room_full`. 공통 넷(4.1)은 따로 적지 않는다.

### 4.4 register_candidate

피어가 STUN 을 마친 뒤 부른다. 후보 목록을 **통째로 교체**한다. 추가가 아니다. 두 번
부르면 두 번째 목록이 남는다.

> **왜.** 교체 의미를 택한 이유는 멱등하기 때문이다. 응답을 잃고 다시 보내도 결과가 같다.

**요청.**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예 |
| `peer_id` | uint32 | 예 |
| `peer_token` | 16진수 32자 | 예 |
| `candidates` | 배열 | 예. 길이 1 이상 `MAX_CANDIDATES`(8) 이하 |

후보 원소:

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `ip` | 점 십진 IPv4 문자열 | |
| `port` | 정수 1~65535 | |
| `kind` | `"local"` 또는 `"reflexive"` | [`protocol.md`](protocol.md) 10.1 후보 수집과 위생의 두 종류. 서버는 저장하고 전달만 한다. 판정에 쓰지 않는다 |

**위생.** `protocol.md` 10.1 후보 수집과 위생의 규칙을 서버가 적용한다(14장 계약 5). 클라이언트도 받은
목록에 같은 규칙을 다시 적용한다. 서버를 신뢰하는 것과 무관하게 형식 검사는 양쪽이 한다.
규칙 자체는 그 절이 소유한다. 그 규칙을 **서버 입력에 대해** 펼친 케이스 표는
[`test_candidates.py`](../../control-server/tests/test_candidates.py) 의 `CANDIDATE_CASES` 다. 아래 거부
정책의 두 결과는 같은 파일의 `POLICY_CASES` 가 본다. 아래 처리 순서와 대역 문단은 `ORDER_CASES` 와
`BAND_CASES`, 그 밖의 표 밖 규칙은 `CANDIDATE_EXTRA_CASES` 가 본다.

케이스 표의 결과 가운데 규칙으로 읽어야 하는 것은 셋이다.

- 후보 목록은 루프백을 거부한다. 수신 출발지 위생(`protocol.md` 7장)과 다르다
- 9개는 요청 전체 `bad_request` 다. 10.1 의 "초과분은 버린다" 는 **수신한** 목록에 대한
  클라이언트 규칙이고, 서버는 보내는 쪽에 상한을 강제한다
- 중복은 위생 거부가 아니므로 `rejected` 에 세지 않는다. 그래서 `accepted + rejected` 가 보낸
  개수보다 작을 수 있다

**`inet_aton` 류의 관대한 파서를 쓰지 않는다.** 이 레포의 Windows Python 3.11 버전에서
`socket.inet_aton` 은 `10.0.5` 를 `10.0.0.5` 로, `010.0.0.5` 를 `8.0.0.5`(8진수) 로 받았다.

**거부 정책. 결과는 둘뿐이고 케이스 표 `CANDIDATE_CASES` 의 `result` 필드가 행마다 어느 쪽인지 적는다.**

| 무엇 | 결과 |
|------|------|
| **위생 거부** — 주소나 포트 값이 10.1 후보 수집과 위생의 규칙에 걸린다(브로드캐스트, 멀티캐스트, 미지정, 루프백, 포트 0) | 그 후보만 버리고 나머지를 저장한다. `rejected` 를 올리고 응답은 `ok` 다 |
| **형 위반** — `ip`·`port`·`kind` 가 형이나 범위를 벗어나거나 없다, 목록이 9개거나 비었다 | **요청 전체가 `bad_request`** 다. 개별 후보 문제가 아니라 요청 문제다 |

**가르는 기준은 "값이 규칙에 걸리는가" 와 "형이 아닌가" 다.** `10.0.0.5:0` 은 형으로는 정수
`0` 이고 규칙이 그 값을 거부하는 것이라 위생 거부다. `10.0.0.5:65536` 은 범위 밖이라 형
위반이다. 이 구분이 없으면 같은 입력에 `{"ok": true, "rejected": 1}` 과 `400 bad_request`
둘 다 규정에 맞게 읽혀 시험을 쓸 수 없다.

**전부 위생 거부되어 저장할 후보가 0개면 `bad_request`** 다. 0개를 저장해 놓고 `ok` 를 주면
상대가 준비 완료 뒤 빈 목록을 받아 `HOLE_PUNCH_TIMEOUT` 으로 끝나고, 그 실패가 NAT 실패로
위장한다.

**처리 순서는 셋이다.** 형 검사로 요청 전체를 먼저 판정하고, 위생 거부를 한 뒤, 남은 것에서
중복을 지운다. `protocol.md` 10.1 후보 수집과 위생의 규칙 표와 같은 순서다.

- 같은 위생 거부 후보가 두 번 오면 `rejected` 가 2 다. 거부가 중복 제거보다 먼저이기 때문이다
- 중복이면 먼저 온 원소를 남긴다. `kind` 도 그 원소의 것이다
- 후보 원소 안의 모르는 키는 무시한다. 저장하는 것은 `ip`, `port`, `kind` 셋이다

**서버가 판정하는 대역은 10.1 의 목록 그대로다.** 브로드캐스트는 `255.255.255.255` 하나이고,
미지정은 `0.0.0.0` 하나다. 루프백은 `127.0.0.0/8` 전체다.

- 서버는 피어의 prefix 길이를 받지 않으므로(10.1) 서브넷의 directed broadcast 를 판정할 수
  없다. `10.0.0.255` 는 저장한다
- `0.0.0.0/8` 의 나머지와 `240.0.0.0/4` 는 10.1 목록에 없어 저장한다

**클라이언트 쪽 결과가 다르다.** 위생 거부는 `rejected` 가 0 이 아니므로 `WARN` 한 줄을
남기고 진행하고, `bad_request` 는 확정 오류라 재시도 없이 `CONTROL_PLANE_EXCHANGE_FAILED`
다(8.3).

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `accepted` | 정수 | 저장한 후보 수 |
| `rejected` | 정수 | 위생에서 버린 후보 수. 클라이언트는 0 이 아니면 `WARN` 한 줄을 남긴다 |

**이 연산은 준비 완료를 기록하지 않는다.** 후보를 저장하고 끝난다. 쌍의 준비 완료는 호스트가
4.6 `host_report` 로 그 쌍을 확인할 때 기록된다(5.2).

> **왜.** 쌍의 한쪽 끝은 항상 호스트이고, 호스트가 그 쌍의 존재를 모르는 채로 상대가 펀치를
> 시작하면 호스트 쪽에서 나가는 패킷이 없어 구멍이 열리지 않는다
> ([`protocol.md`](protocol.md) 10.3 펀치). 기준 시각을 호스트가 아는 시점으로 두면 두 피어가
> 같은 값을 받는다.

**클라이언트는 이 연산의 성공 응답을 폴링 시작점으로 쓴다**(`protocol.md` 11장 타이머).
등록 직후에는 아직 준비 완료가 아니므로 `get_peers` 가 `ready: false` 를 주는 것이 정상이다.

**오류.** `room_not_found`, `room_expired`, `unauthorized`. 공통 넷(4.1)은 따로 적지 않는다.

### 4.5 get_peers

**플레이어가 부른다.** 호스트는 부르지 않는다. 호스트가 같은 정보를 4.6 `host_report` 의
응답으로 받기 때문이다. 호스트가 불러도 오류가 아니다. 4.6 `host_report` 응답의 `peers` 처럼 자신을
뺀 피어 전부를 준다.

- `peers` 원소의 순서는 정하지 않는다. 클라이언트는 순서에 기대지 않는다
- 플레이어가 불렀는데 방에 호스트의 `PEER#` 가 없으면 판정 불가이고 `internal` 이다

클라이언트가 [`protocol.md`](protocol.md) 11장 타이머의 간격(500ms)과 마감(60s)으로
폴링한다. **간격과 마감은 그 문서가 소유한다.** 여기에 숫자를 다시 적지 않는다.

**요청.**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예 |
| `peer_id` | uint32 | 예 |
| `peer_token` | 16진수 32자 | 예 |

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `ready` | 불 | `peers` 에 준비 완료인 원소가 하나라도 있으면 참 |
| `peers` | 배열 | **자신을 제외한** 피어. 플레이어가 부르면 길이 1 이다. 원소는 호스트뿐이다 |

`peers` 원소:

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `peer_id` | uint32 | |
| `virtual_ip` | 점 십진 문자열 | `protocol.md` 5.1 `HELLO` 의 `virtual_ip` 검증에 쓴다 (14장 계약 6) |
| `ready` | 불 | 이 쌍의 `PAIR#` 항목이 있으면 참 |
| `punch_delay_ms` | 정수 | 그 쌍에 기록된 값. `ready` 가 참일 때만 있다 |
| `elapsed_since_ready_ms` | 정수 0 이상 | 그 쌍의 준비 완료 기록 시점부터 이 응답을 만드는 시점까지. `ready` 가 참일 때만 있다. 계산 방법은 7.4 |
| `candidates` | 배열 | 4.4 `register_candidate` 와 같은 원소 형. 저장된 순서대로. `ready` 가 참일 때만 있다 |

**원소의 필드 집합은 `ready` 가 가른다.** `PAIR#` 가 없으면 `peer_id`, `virtual_ip`,
`ready: false` 셋이다. 있으면 거기에 `punch_delay_ms`, `elapsed_since_ready_ms`, `candidates` 가
더해진다. 케이스 표는 [`test_get_peers.py`](../../control-server/tests/test_get_peers.py) 의
`FIELD_SETS` 다.

> **왜.** 준비 전에 후보를 주면 클라이언트가 호스트의 확인 없이 펀치를 시작할 수 있다. 펀치
> 시각을 맞추는 것이 4.6 의 확인이므로(5.2) 그 전에는 쏠 주소를 주지 않는다.

**쌍의 준비 완료는 그 `PAIR#` 항목의 존재다.** 피어 수나 후보 수를 응답 시점에 다시 세지
않는다.

> **왜.** 다시 세면 한 피어가 후보를 다시 등록하는 순간 준비 완료가 거짓으로 돌아가 상대가
> 이미 시작한 펀치와 어긋난다.

**준비 완료인데 상대 후보가 0개인 응답은 없다.** `PAIR#` 를 쓰는 것은 호스트이고, 호스트는
양쪽 후보를 확인한 뒤에만 쓴다(4.6). 클라이언트는 그래도 빈 목록을 받으면 준비 완료로
취급하지 않고 폴링을 계속한다. 마감에 닿으면 `protocol.md` 9.6 실패 전이의 폴링 마감
초과로 `CONTROL_PLANE_EXCHANGE_FAILED` 다.

> **왜 그래도 검사하나.** 빈 목록으로 펀치에 들어가면 보낼 곳이 없는 채 10초를 기다려
> `HOLE_PUNCH_TIMEOUT` 이 되고, 그것은 NAT 실패로 위장한 제어 평면 실패다.
> [`architecture.md`](architecture.md) 8장 실패 진단이 "상대 후보 없음" 을
> `CONTROL_PLANE_EXCHANGE_FAILED` 로 분류한 것과 같은 판단이다.

**자신을 제외하는 판정은 `peer_id` 다.** 같은 `peer_id` 가 둘일 수 없으므로(2.2) 응답에
자신과 같은 `peer_id` 가 있으면 서버 결함이다. 클라이언트는 그 경우
`CONTROL_PLANE_EXCHANGE_FAILED` 로 끝낸다(`protocol.md` 4.2 `peer_id`).

**오류.** `room_not_found`, `room_expired`, `unauthorized`. 공통 넷(4.1)은 따로 적지 않는다.

**`not_ready` 는 오류가 아니다.** `ok: true` 에 `ready: false` 다.

> **왜.** 폴링이 정상 진행 중인 것이라 오류 봉투에 넣으면 클라이언트가 "오류지만 계속"
> 이라는 예외 경로를 갖게 된다.

### 4.6 host_report

**호스트만 부른다.** 하나의 요청이 셋을 한다. 방의 임대를 갱신하고, 끝난 세션의 자리를
회수하고, 아직 확인하지 않은 쌍을 준비 완료로 기록한다. 응답은 호스트가 알아야 할 방의
현재 상태다.

> **왜 하나로 묶나.** 셋 다 호스트가 주기적으로 제어 평면에 말하는 것이다. 나누면 같은 인증과
> 같은 속도 제한 예산을 세 벌 두고, 세 요청의 순서가 어긋나는 경우를 따로 다뤄야 한다.

**간격.** 빈 자리가 있으면 `HOST_REPORT_OPEN_S`(5초), 정원이 찼으면 `HOST_REPORT_FULL_S`(30초)
마다 부른다. 판정은 직전 응답의 `peers` 길이로 한다.

**세션이 끝나면 다음 주기를 기다리지 않고 바로 한 번 부른다.** 그 호출의 `departed` 에 끝난
피어를 담는다. 미결 요청이 있으면 그 응답을 받은 직후에 부른다. 한 번에 하나라는 규칙
([`concurrency.md`](concurrency.md) 8장 `[control]` 스레드)은 그대로다. 주기 타이머는 이
호출에서 다시 센다.

**호스트는 아직 보고하지 못한 `departed` 를 모아 둔다.** 세션이 끝난 피어를 그 집합에 넣고, 모든
`host_report` 에 집합 전체를 담는다. 성공 응답을 받으면 그 요청에 담았던 것을 집합에서 뺀다.
`released` 에 없어도 뺀다. 이미 없던 피어라는 뜻이기 때문이다. 실패하면 그대로 두고 다음
호출에 다시 담는다.

- 집합은 `MAX_PEERS - 1` 을 넘지 않는다. 보고되지 않은 피어는 서버에서 아직 자리를 차지하므로
  그 수가 풀 크기를 넘을 수 없다
- 회수는 멱등이므로 같은 피어를 두 번 담아도 안전하다

> **왜.** 정원이 찬 방에서 한 명이 나가면, 호스트가 알린 뒤에야 그 자리가 빈다. 주기만 따르면
> 그 공백이 최대 30초이고 그동안 온 참가는 `room_full` 이다. 바로 부르면 공백이 요청 한 건으로
> 준다. 플레이어 프로세스가 죽은 경우는 호스트도 유휴 타임아웃([`protocol.md`](protocol.md) 11장)이 지나야
> 알므로 이 규칙이 줄이지 못한다.

**두 간격은 `ROOM_LEASE_S` 보다 작아야 한다.** 그래야 정상 호스트의 방이 임대 만료로 죽지
않는다. 지금 값은 5·30 대 120 이고 **연속 실패를 네 번까지 견딘다.** 값을 바꿀 때 이 여유를
같이 본다.

**요청.**

| 필드 | 형 | 필수 | 뜻 |
|------|-----|:---:|-----|
| `room_id` | 문자열 | 예 | |
| `peer_id` | uint32 | 예 | 호출자. 호스트의 `peer_id` 여야 한다 |
| `peer_token` | 16진수 32자 | 예 | |
| `departed` | 배열 | 아니오 | 세션이 끝난 피어의 `peer_id`. 없으면 빈 배열이거나 생략. 길이 `MAX_PEERS - 1` 이하 |
| `confirm` | 배열 | 아니오 | 준비 완료로 기록할 상대의 `peer_id`. 같은 제약 |

**호출자 판정.** `peer_id` 가 `ROOM.host_peer_id` 와 같고 `peer_token` 이 그 피어의 것일
때만 처리한다. 둘 중 하나라도 어긋나면 `unauthorized` 다.

> **왜 호스트만인가.** 자리를 회수해도 되는지는 그 터널 세션이 끝났는지로 정해지고(2.5),
> 그것을 아는 것은 세션의 한쪽 끝인 호스트다. 나가는 본인이 부르면 호스트가 아직 세션을 닫기
> 전에 자리가 비는 상태가 생긴다.

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `expires_in_s` | 정수 | 갱신 뒤 남은 임대. 정상이면 `ROOM_LEASE_S` 다 |
| `released` | 배열 | 실제로 지운 `peer_id`. 이미 없던 것은 담지 않는다 |
| `confirmed` | 배열 | 이번 호출로 `PAIR#` 를 새로 쓴 상대의 `peer_id` |
| `peers` | 배열 | 4.5 `get_peers` 와 같은 원소 형. 자신을 제외한 현재 피어 전부 |

**처리 순서를 못박는다.** 한 요청 안에서 아래 순서로 돈다.

1. 호출자 판정. 어긋나면 `unauthorized` 로 끝난다
2. `departed` 의 각 `peer_id` 에 대해 `PEER#` 와 그 피어의 `VIP#`, 그 피어가 낀 `PAIR#`, 그
   피어의 `NONCE#` 를 지운다(6.3). 이어서 서버 회수 대상도 `PEER#` 와 `VIP#` 를 지운다. 대상은 아래
   "서버 회수" 가 정한다. `departed` 에 든 피어는 서버 회수가 다시 판정하지 않는다. 그 피어의
   회수는 호스트의 것이고 로그의 `by` 가 `host` 다
3. `confirm` 의 각 `peer_id` 에 대해, 그 피어와 호출자가 **둘 다 후보를 1개 이상** 갖고 있고
   그 쌍의 `PAIR#` 가 없으면 조건부 쓰기로 만든다. 항목에 `ready_at_*` 과
   `punch_delay_ms = PUNCH_DELAY_MS` 를 넣는다(6.3)
4. `ROOM.expires_at_ms` 를 `now + ROOM_LEASE_S * 1000` 으로 갱신한다
5. `Query(pk, ConsistentRead=true)` 로 읽어 응답을 만든다

**서버 회수.** 1번에서 읽은 방의 피어 가운데 아래를 모두 만족하는 것이 대상이다.
지울 때 그 피어의 `NONCE#` 도 같이 지운다. 키는 `PEER#` 의 `client_nonce` 로 안다. 2번에서
지운 피어는 `released` 에 담는다.

- 호스트가 아니다
- 후보가 비어 있다. 5.3 피어의 `joined` 다
- `joined_at_ms + JOIN_REGISTER_GRACE_S * 1000 <= now` 다

**판정할 수 없는 피어는 지우지 않고 건너뛴다.** 피어마다 아래 순서로 보고, 앞에서 결론이 나면
뒤를 보지 않는다. 건너뛸 때 7.5 의 `peer.reclaim_skipped` 로그 줄을 남긴다.

| 순서 | 보는 것 | 결과 |
|:--:|---------|------|
| 1 | `peer_id` 가 정수인가 | 아니면 건너뛴다. `reason=peer_id_unreadable` |
| 2 | 호스트인가 | 호스트면 남는다 |
| 3 | `candidates` | 속성이 없으면 빈 것이다(6.3 의 조건과 같다). 리스트가 아니면 건너뛴다. `reason=candidates_unreadable`. 비어 있지 않으면 남는다 |
| 4 | `joined_at_ms` 가 정수인가 | 아니면 건너뛴다. `reason=joined_at_unreadable` |
| 5 | 유예가 지났는가 | 위 셋째 조건. 지나지 않았으면 남는다 |
| 6 | 지울 키를 만들 수 있는가 | `virtual_ip` 와 `client_nonce` 가 문자열이 아니면 건너뛴다. `reason=keys_unreadable`. 문자열이면 지운다 |

> **왜 건너뛰나.** 판정 불가를 회수로 바꾸면 손상된 항목 하나가 살아 있는 피어를 지운다. 요청
> 전체를 `internal` 로 끝내면 그 방의 임대 갱신까지 막힌다.

**경합은 저장소 조건으로 막는다.** 읽은 뒤 지우기 전에 그 피어가 후보를 등록할 수 있다. 그래서
삭제 조건에 "후보가 아직 비어 있다" 를 넣는다(6.3). 조건이 실패하면 그 피어는 지우지 않는다.
지워진 피어의 다음 `register_candidate` 는 7.3 연산 처리 순서의 토큰 검사에서 `unauthorized`
로 끝난다. 토큰 검사를 통과한 뒤 쓰기 전에 회수되면 6.3 의 조건부 update 가 실패하고, 그것도
`unauthorized` 다. 어느 쪽이든 클라이언트는 8.3 오류 분류와 재시도대로 `CONTROL_PLANE_EXCHANGE_FAILED` 다.

> **왜 서버가 지우나.** 후보 없이 떠난 참가자는 호스트와 세션이 생긴 적이 없어 호스트가 알릴
> 계기가 없다. 로비에서 같은 방에 다시 참가할 때마다 그 자리가 쌓여 풀이 찬다. 후보가 비어
> 있는지는 서버가 저장소에서 직접 아는 사실이고, 터널이 살아 있는지와 달리 호스트에게 물을
> 필요가 없다. 근거는 [ADR 0012](decisions/0012-후보-없는-참가자는-서버가-회수한다.md) 다.

> **왜 90초인가.** 기준점 `joined_at_ms` 는 서버가 `PEER#` 를 쓴 시각이다. 거기서 플레이어의
> `register_candidate` 가 성공하기까지의 상한은 셋의 합이다.
>
> - `join_room` 의 응답을 잃고 같은 nonce 로 다시 받기까지. 첫 시도를 포함해 3회, 회당 최대 9초에
>   간격 1초 둘이라 29초다(8.2, 8.3)
> - STUN 단계. 기본 목록이면 10초다(`protocol.md` 11장 타이머)
> - `register_candidate` 재시도. 위와 같이 29초다
>
> 합 68초에 여유를 둔다. 이 합은 문서의 상한에서 계산한 것이고 재지 않았다. 넘는 경우가
> 둘 있다. `--stun` 으로 목록을 길게 주면 STUN 상한이 는다. 그리고 회당 9초는 8.2 의 요청 한 건
> 상한인데, 그 표가 적은 대로 송수신 제한이 연산별이라 실제로는 더 길 수 있다. 어느 쪽이든 위
> `unauthorized` 경로로 끝난다.

**호출자 자신의 `peer_id` 가 `departed` 나 `confirm` 에 있으면 그 원소를 건너뛴다.** 지우지도
쓰지도 않고 `released` 와 `confirmed` 에 담지 않는다. 그대로 처리하면 호스트가 자기 자리를 지우고,
확인은 같은 항목에 ConditionCheck 둘을 넣어 DynamoDB 가 요청 전체를 거부한다.

**5번의 다시 읽기에서 읽을 수 없는 `PEER#` 가 나오면 `internal` 이다.** 6.3 항목의 형 규칙이다.
4번 갱신은 이미 끝났으므로 임대는 산다. 그 항목이 남아 있는 동안 호스트는 매 주기 `internal` 을
받는다. `departed` 나 `confirm` 의 대상이 읽을 수 없는 `PEER#` 일 때와 호출자의 `PEER#` 를 읽을 수
없을 때도 `internal` 이다. 예외는 `departed` 대상의 `client_nonce` 하나다. 그것만 읽을 수 없으면
6.3 항목의 회수 행대로 `NONCE#` 만 빼고 지운다.

**2번이 3번보다 먼저다.** 같은 요청에 `departed` 와 `confirm` 이 같은 `peer_id` 를 담으면
회수가 이긴다. 끝난 세션을 준비 완료로 기록하면 그 자리가 다시 찬다.

**4번이 5번보다 먼저다.** 응답의 `expires_in_s` 가 갱신 뒤의 값이어야 호스트가 자기 임대를
바로 읽는다.

**5번이 마지막인 것이 이 절의 변이 시험이다.** 1~4번의 쓰기 전에 읽은 결과로 응답을 만드는
구현은 방금 회수한 피어를 `peers` 에 담는다.

**확인 경합 케이스 표.** [`test_host_report.py`](../../control-server/tests/test_host_report.py) 의
`CONFIRM_RACE` 다. `H` 는 호스트의 `host_report`, `P` 는 플레이어의 `register_candidate` 다. 전 행이
저장소가 있어야 돈다. 3번을 조건 없이 쓰는 구현이 마지막 행(`unconditional-write-impl`)에서
걸린다. 3번의 사전 조건 자체는 같은 파일의 `CONFIRM_CORE` 가 저장소 없이 본다.

**서버 회수 케이스 표.** [`test_host_report.py`](../../control-server/tests/test_host_report.py) 의
`RECLAIM_CASES` 다. 위 판정 순서 표의 판독 행은 같은 파일의 `RECLAIM_READ` 가 본다. 저장소가 있어야
도는 행은 `needs="store"` 로 표시되어 있다.

**회수된 피어가 같은 nonce 로 `join_room` 을 다시 보내면 새 참가다.** `NONCE#` 가 함께 지워졌으므로
4.3 `join_room` 의 멱등 응답이 아니다. 위 "왜 90초인가" 의 첫 항 때문에 정상 클라이언트의
재시도는 회수보다 먼저 끝난다.

**멱등성.** `client_nonce` 를 쓰지 않는다. 같은 요청을 두 번 보내면 두 번째의 `released` 와
`confirmed` 가 비고 저장소 상태가 같다. 갱신은 그때의 `now` 를 쓰므로 임대만 더 밀린다. 서버
회수도 그때의 `now` 로 판정하므로, 두 요청 사이에 유예가 지난 피어가 있으면 두 번째가 그것을
지운다. 멱등성이 보장하는 것은 같은 `departed` 와 `confirm` 이 두 번 적용되지 않는 것이다.

**오류.** `room_not_found`, `room_expired`, `unauthorized`. 공통 넷(4.1)은 따로 적지 않는다.

**만료된 방은 되살리지 못한다.** `expires_at_ms` 가 이미 지났으면 `room_expired` 이고 갱신도
하지 않는다. 임대가 끊긴 방은 끝난 방이다.

**호스트가 오류를 받으면 셋으로 나눠 다룬다.** 8.3 오류 분류와 재시도의 일반 규칙과 다르다.
`host_report` 의 실패는 시도의 실패가 아니라 이미 터널이 있는 방의 일이기 때문이다.

| 받은 것 | 뜻 | 호스트가 하는 것 |
|---------|-----|------------------|
| `room_expired`, `room_not_found`, `unauthorized`, `bad_request` | 방이 서버에서 끝났다. 같은 요청을 다시 보내도 같은 답이다 | `FAIL CONTROL_PLANE_EXCHANGE_FAILED` 줄을 한 번 내고 `host_report` 를 멈춘다. 세션이 끝나도 위 즉시 호출을 하지 않는다. 이미 있는 세션은 그대로 둔다. 남은 세션이 모두 끝나면 로비로 간다. 세션이 없으면 바로 간다 |
| `rate_limited` | 방은 살아 있을 수 있다. 같은 공인 IP 의 다른 출발지가 예산을 태웠을 수 있다(6.4) | `FAIL` 을 내지 않고 다음 주기에 다시 부른다 |
| `internal`, `unavailable`, 전송 오류 | 일시 오류다 | 다음 주기에 다시 부른다 |

- 방이 끝난 뒤에도 남은 세션의 터널은 간다([`spec.md`](spec.md) NFR-3). 잃는 것은 새 참가뿐이다
- `rate_limited` 가 이어지는 동안 임대가 만료될 수 있다. 예산 검사가 저장소보다 앞이라(6.4) 그
  사이의 응답은 계속 `rate_limited` 다. 예산이 차서 처리되는 첫 요청이 `room_expired` 나, TTL 이
  이미 지웠으면 `room_not_found` 를 받고 첫 행으로 간다
- 로비로 가는 계기의 목록은 `concurrency.md` 7장 로비가 갖는다

> **왜 첫 행에서 멈추나.** 만료된 방은 되살릴 수 없고, 그 행의 앞 세 오류는 출발지의 속도 제한
> 예산을 깎는다(6.4). 계속 부르면 얻는 것 없이 같은 공인 IP 의 다른 사용자를 막는다.

> **왜 `rate_limited` 는 다시 부르나.** 남의 추측이 태운 예산 때문에 멈추면 살아 있는 방이 임대
> 만료로 죽는다. 예산은 6초마다 하나씩 찬다.

### 왜 이렇게 정했나

- **4.1 두 코드를 나눈다.** 사람이 방 코드를 잘못 친 것과, 맞게 쳤는데 호스트가 신호를 멈춘
  방인 것은 다른 조치가 필요하다. 합치면 어느 쪽인지 알 수 없다. 대신 **존재하지 않는
  방을 추측하는 호출자에게 만료된 방의 존재를 알려 준다.** 만료된 방은 참가할 수 없으므로
  알려 줘도 잃는 것이 없다
- **4.6 없는 `peer_id` 로 부르면 `unauthorized` 다.** 방은 있다. 없는 것은 그 피어다.
  존재하지 않는 `peer_id` 와 토큰이 틀린 `peer_id` 를 같은 코드로 답해야 `room_id` 만 아는
  호출자가 방 안의 `peer_id` 를 열거하지 못한다. 32비트 공간이라 열거는 어차피
  비현실적이지만, 응답으로 구분해 줄 이유가 없다
- **4.6 확인을 쓰기 뒤에 읽는다.** 회수와 확인과 갱신을 마친 뒤 다시 읽어 응답을 만들지
  않으면, 방금 지운 피어가 `peers` 에 남고 방금 확인한 쌍이 `ready: false` 로 나간다.
  호스트는 그 응답을 보고 같은 상대를 다음 주기에 또 `confirm` 하고, 그 호출은 조건부 쓰기가
  실패해 아무 일도 하지 않는다. 겉으로는 정상이라 결함이 드러나지 않는다
- **4.6 확인의 조건이 양쪽 후보다.** 호스트가 후보 없는 상대를 `confirm` 해도 쓰지 않는다.
  쓰면 4.5 `get_peers` 가 빈 후보 목록과 함께 준비 완료를 주고, 상대는 보낼 곳이 없는 채
  펀치 마감을 기다려 `HOLE_PUNCH_TIMEOUT` 으로 끝난다. **NAT 실패로 위장한 제어 평면
  실패다**

## 5. 상태 전이

### 5.1 방

방의 상태는 **저장된 필드에서 파생**한다. 상태 필드를 따로 두지 않는다.

> **왜.** 상태 필드를 두면 필드와 상태가 어긋나는 경우가 생긴다.

| 상태 | 정의 |
|------|------|
| `open` | `ROOM` 항목이 있고 `now < expires_at` |
| `expired` | `ROOM` 항목이 있고 `now >= expires_at`. TTL 삭제 전까지 이 상태로 보인다 |
| (없음) | `ROOM` 항목이 없다. 처음부터 없었거나 TTL 이 지웠다 |

```text
(없음) --create_room--> open --임대 만료--> expired --TTL 삭제--> (없음)
                          ^                   |
                          +-- host_report ----+   (갱신은 만료 전에만 된다)
```

**준비 완료는 방의 상태가 아니다.** 쌍마다 따로 판정하므로(5.2) 같은 방에 준비된 쌍과 그렇지
않은 쌍이 같이 있다.

**방은 호스트의 임대로 산다.** `host_report` 한 번이 만료 시각을 `now + ROOM_LEASE_S` 로
민다(4.6). 절대 상한은 없다. 호스트가 신호하는 동안 방 코드는 유효하고, 몇 시간 뒤에 온
참가자도 그 코드로 들어온다.

> **왜 연장을 허용하나.** "방이 언제 사라지는가" 에 답할 수 있기 때문이다. 답은 **호스트가
> 신호를 멈춘 뒤 `ROOM_LEASE_S` 안**이다. 고정 수명은 그 답이 더 단순한 대신, 호스트가 죽은
> 방이 남은 시간만큼 살아 있고 살아 있는 방이 시간이 됐다고 죽는다. 근거는
> [ADR 0009](decisions/0009-방-호스트-임대.md) 다.

**임대는 터널의 생존 조건이 아니다.** 제어 평면이 죽어 호스트가 갱신에 실패해도 이미 수립된
터널은 그대로 간다([`spec.md`](spec.md) NFR-3). 임대가 끊긴 방이 잃는 것은 **새 참가와 제어
평면 연산**이다.

**임대가 덮는 것과 덮지 않는 것을 나눠 적는다.**

- 플레이어가 호스트의 확인을 받기까지의 여유는 이 값이 아니라 [`protocol.md`](protocol.md)
  11장 타이머의 `get_peers` 마감이다. 플레이어는 자기 `register_candidate` 성공 시점부터 그
  마감 안에 호스트의 확인을 봐야 하고, 넘기면 방이 아직 살아 있어도
  `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다(9.6)
- 호스트에게는 이 마감이 없다. `get_peers` 를 부르지 않고(8.4), 방을 세운 뒤에는 플레이어가
  없어도 방에 남는다([`concurrency.md`](concurrency.md) 7장 로비)
- 프로세스가 죽은 피어는 그 자리를 잃는다. 다시 들어오는 것은 새 참가이고 가상 IP 는 그때
  새로 배정한다(4.3). 방은 살아 있으므로 같은 방 코드를 다시 쓴다
- 호스트가 죽으면 방은 `ROOM_LEASE_S` 안에 만료된다. 그 사이에 들어온 참가자는 쌍을 확인해
  줄 호스트가 없어 준비 완료에 닿지 못하고 폴링 마감으로 끝난다

**두 값의 역할이 다르다는 것을 시연 대본에 반영한다.** 호스트의 확인을 받지 못한 플레이어가 1분 안에 실패하는 것은
제어 평면 장애가 아니다.

**연산별 허용 상태.**

| 연산 | `open` | `expired` | (없음) |
|------|--------|-----------|--------|
| `create_room` | 같은 nonce 면 기존 방(4.2) | 같은 nonce 면 `room_expired`(4.2) | 생성 |
| `join_room` | 선점 시도. 빈 주소가 없으면 `room_full` | `room_expired` | `room_not_found` |
| `register_candidate` | 저장 | `room_expired` | `room_not_found` |
| `get_peers` | 쌍별 준비 여부를 담아 응답 | `room_expired` | `room_not_found` |
| `host_report` | 회수·확인·갱신 | `room_expired`. 갱신하지 않는다 | `room_not_found` |

**만료 판정.** `now` 는 서버 벽시계 밀리초, `expires_at_ms` 는 저장값이다. 경계
`now == expires_at_ms` 는 만료 쪽이다. `expires_in_s` 가 0 인 방은 참가할 수 없다.
`expires_at_ms` 가 없거나 정수가 아니면 **`internal`** 이다. 판정 불가를 통과로 바꾸지 않는다.
생성 경로가 항상 넣는 필드이므로 없으면 저장소가 손상된 것이다.

케이스 표는 [`test_room_state.py`](../../control-server/tests/test_room_state.py) 의 `EXPIRY` 이고, 정수가
아닌 값은 `EXPIRY_UNREADABLE` 이 본다.
위 상태 표를 지키는 행은 같은 파일의 `STATES`, 아래 `expires_in_s` 의 값은 `EXPIRES_IN` 이 본다.

`expires_in_s` 는 `max(0, ceil((expires_at_ms - now) / 1000))` 이다. 클라이언트는 이 값을
표시에만 쓰고 판정에 쓰지 않는다.

- **살아 있는 방에서는 1 이상이다.** 1ms 라도 남았으면 올림이 1 을 만든다
- 0 은 만료를 뜻한다. 위 만료 판정의 경계와 같은 말이다

### 5.2 준비 완료

**준비 완료의 단위는 쌍이다.** 호스트와 한 플레이어가 한 쌍이고, 그 쌍의 `PAIR#` 항목이
있으면 준비 완료다(6.3).

**쓰는 것은 호스트뿐이다.** 호스트가 `host_report` 의 `confirm` 으로 그 쌍을 지목하고,
서버가 양쪽 후보를 확인한 뒤 조건부 쓰기로 만든다(4.6).

> **왜 호스트가 쓰나.** 쌍의 한쪽 끝은 항상 호스트다(ADR 0006). 호스트가 모르는 채로 상대가
> 펀치를 시작하면 호스트 쪽에서 나가는 패킷이 없어 구멍이 열리지 않는다. 기준 시각을 호스트가
> 아는 시점으로 두면 두 피어가 같은 값을 받는다.

`PAIR#` 의 `ready_at_wall_ms` 는 **한 번 기록되면 그 쌍이 사라질 때까지 바뀌지 않는다.**
어느 피어가 후보를 다시 등록해도 그대로다. 근거는 4.5 `get_peers` 와 4.6 `host_report` 에
있다.

**쌍이 사라지는 것은 그 피어가 회수될 때뿐이다**(2.5, 4.6). 그때 `PEER#`, `VIP#`, `PAIR#`
가 같이 지워진다.

### 5.3 피어

| 상태 | 정의 |
|------|------|
| `joined` | `PEER#` 항목이 있고 `candidates` 가 비어 있다 |
| `registered` | `candidates` 가 1개 이상 |

```text
(없음) --create_room / join_room--> joined --register_candidate--> registered
   ^  ^                               |                                |
   |  +-- 서버 회수 (유예 경과) -------+                                |
   +------------------ host_report 의 departed (자리 회수) -------------+
```

**피어를 지우는 것은 둘이다.** 호스트의 통지와, 후보 없이 `JOIN_REGISTER_GRACE_S` 가 지난
참가자의 서버 회수(4.6)다. 그 밖에는 방과 함께 사라진다.

> **왜.** `leave_room` 을 두지 않는 이유는 4장 머리에 있다. 나가는 본인은 자기 세션이 호스트
> 쪽에서도 닫혔는지를 모른다.

## 6. 저장

### 6.1 저장 계약

상태는 Amazon DynamoDB 에 둔다. **왜 DynamoDB 이고 무엇을 버렸는지는** [ADR 0004](decisions/0004-상태-저장소-dynamodb.md)가 갖는다. 계약은 다섯이다.

| 계약 | 내용 |
|------|------|
| 저장 1 | 읽은 값으로 판정하는 읽기는 **테이블에 `ConsistentRead=true`** 를 건다. 저장 5 때문에 연산이 방·피어 항목을 읽는 모든 자리가 여기에 해당하고 `get_peers` 만이 아니다. 기본 읽기는 최종 일관성이라(ADR 0004 결정 1 의 AWS 문서 인용) 방금 등록된 후보가 빠질 수 있고, 그러면 펀칭이 `HOLE_PUNCH_TIMEOUT` 으로 끝나 NAT 실패로 위장한다 |
| 저장 2 | 강한 일관성 읽기는 테이블과 LSI 에서만 된다. **GSI 를 만들지 않는다.** 이 설계에는 GSI 가 필요한 조회가 없다 |
| 저장 3 | 가상 IP 배정은 아이템 하나를 키로 두고 **조건부 쓰기(`attribute_not_exists`)로 선점**한다. 원자적 카운터를 쓰지 않는다. 그것은 멱등하지 않아 재시도가 주소를 건너뛴다. 선점에 실패하면 다음 후보 주소로 넘어가고, 풀을 한 바퀴 돌면 `room_full` 로 끝낸다(2.5). 무한히 돌지 않는다 |
| 저장 4 | 방 만료 **판정은 애플리케이션이 한다**(5.1). TTL 은 저장 공간 회수 수단이며, 만료 시각이 지난 항목도 삭제 전까지 조회에 보인다 |
| 저장 5 | 제어 서버는 방·피어 상태를 **메모리에 들고 있지 않는다.** 요청마다 DynamoDB 에서 읽는다 |

**저장 5 때문에 "재시작 복원" 절차가 없다.** 기동 시 방 목록을 읽어 들이는 단계가 없고,
재시작 직후의 첫 요청이 평소와 똑같이 읽는다.

- [`spec.md`](spec.md) NFR-3 이 요구하는 재시작 후 방 상태 유지는 복원 절차가 아니라 이
  계약으로 성립한다
- 캐시를 두면 그 캐시가 최종 일관성 읽기와 같은 문제를 다시 만든다. 캐시가 필요해지면 저장
  1 과 함께 다시 정한다

**저장 5 의 예외는 속도 제한 표(6.4)와 처리 중 요청 수(7.2)다.** 둘은 방·피어 상태가
아니라 서버 프로세스의 자기 보호 상태다. 재시작하면 사라지고, 사라져도 잃는 것은 재시작
직후 잠깐의 보호뿐이다. 이 둘 외에 메모리에 두는 상태를 만들지 않는다.

### 6.2 테이블

**테이블 하나다.** 이름은 배포 설정(7.6)이 정하고 코드에 박지 않는다.

| 항목 | 값 |
|------|-----|
| 파티션 키 | `pk` (문자열). 값은 `room_id` |
| 정렬 키 | `sk` (문자열). 항목 종류와 식별자 |
| TTL 속성 | `ttl` (숫자, epoch 초). 6.5 |
| 용량 모드 | [ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 4. provisioned. 값은 배포 설정 |
| 인덱스 | 없음 (저장 2) |

방에 속한 항목(`ROOM`, `PEER#`, `VIP#`, `PAIR#`)은 같은 파티션 키를 가지므로 방 하나의
전체 상태를 `Query(pk = room_id, ConsistentRead=true)` 하나로 읽는다. 항목 수는
`1 + MAX_PEERS × 2 + (MAX_PEERS - 1)` 이하다(`ROOM` 하나, 피어마다 `PEER#` 와 `VIP#`,
호스트와 각 플레이어의 쌍마다 `PAIR#` 하나). v1 에서 최대 15개다.

**`NONCE#` 항목은 파티션 키가 다르다.**

> **왜.** `create_room` 의 멱등성 조회는 `room_id` 를 아직 모르는 시점에 nonce 만으로 찾아야
> 하기 때문이다.

### 6.3 항목

| `sk` | 속성 | 뜻 |
|------|------|-----|
| `ROOM` | `created_at_ms`, `expires_at_ms`, `host_peer_id`, `ttl` | 방. 처음 `expires_at_ms` 는 `create_room` 의 `now + ROOM_LEASE_S * 1000` 이고 `host_report` 가 민다(4.6) |
| `PAIR#<lo>-<hi>` | `ready_at_wall_ms`, `ready_at_mono_ns`, `ready_boot_id`, `punch_delay_ms`, `ttl` | 쌍의 준비 완료. `lo` 와 `hi` 는 두 `peer_id` 를 수의 오름차순으로 놓고 10진수로 적는다. `9` 가 `10` 보다 앞이다. 7.4 시계가 세 값을 쓴다 |
| `PEER#<peer_id>` | `peer_id`, `peer_token`, `virtual_ip`, `candidates`(리스트), `client_nonce`, `joined_at_ms`, `ttl` | 피어. `peer_id` 는 `sk` 에서 10진수로 적는다. `peer_token` 은 원문이다(2.3). `candidates` 는 첫 `register_candidate` 전에는 쓰지 않는다 |
| `VIP#<virtual_ip>` | `peer_id`, `ttl` | 가상 IP 선점 표식. `<virtual_ip>` 는 점 십진 |
| (pk = `NONCE#<client_nonce>`, sk = `NONCE`) | `room_id`, `peer_id`, `ttl` | 멱등성 키 → 방과 피어 대응. **pk 가 방이 아니라 nonce 다** |

토큰 비교는 상수 시간 비교(`hmac.compare_digest`)로 한다. 조건식에 넣는 비교(`peer_token
= :t`)는 DynamoDB 가 하므로 상수 시간을 주장하지 않는다. 그래서 토큰이 필요한 연산은 순서가
둘이다.

- **먼저 `PEER#` 를 읽어 애플리케이션에서 상수 시간 비교를 한다**
- 조건식의 `peer_token = :t` 는 읽기와 쓰기 사이에 값이 바뀌지 않았음을 확인하는 용도다

**쓰기는 전부 조건부이고, 여러 항목을 함께 쓰는 자리는 `TransactWriteItems` 다.** 하나라도 조건이 실패하면 전부 취소된다. 예외는 `host_report` 갱신 하나다(아래 표).

| 연산 | 쓰기 | 조건 |
|------|------|------|
| `create_room` | 트랜잭션: `ROOM` put, `PEER#host` put, `VIP#10.100.0.1` put, `NONCE#` put | **네 put 전부 `attribute_not_exists(pk)`** 다. `ROOM` 실패는 `room_id` 충돌 → 재추첨(2.1). `NONCE#` 실패는 동시에 같은 nonce 가 들어온 것이므로 다시 읽어 그 결과를 돌려준다. `PEER#`·`VIP#` 는 `ROOM` 이 없으면 있을 수 없으므로 실패가 나면 저장소가 앞선 방의 항목을 일부만 지운 상태다. 그때는 `internal` 이고 재추첨하지 않는다 |
| `join_room` 새 참가 | 풀의 주소마다 트랜잭션: `ROOM` **ConditionCheck**, `VIP#<ip>` put, `PEER#<peer_id>` put, `NONCE#` put | `ROOM` 에 `attribute_exists(pk) AND expires_at_ms > :now`. 사전 읽기와 쓰기 사이에 방이 만료되거나 삭제되는 경합을 막는다. `VIP#` 와 `PEER#` 와 `NONCE#` 각각 `attribute_not_exists(pk)`. 실패 처리는 아래 취소 사유 표 |
| `register_candidate` | `PEER#` update: `candidates = :list` | `attribute_exists(pk) AND peer_token = :t`. 실패는 `unauthorized` 다. 토큰 검사 뒤 그 피어가 회수된 경우다(4.6 서버 회수) |
| `host_report` 회수 | 대상마다 트랜잭션: `PEER#<target>` delete, `VIP#<그 피어의 virtual_ip>` delete, 그 피어가 낀 `PAIR#` delete, `NONCE#<그 피어의 client_nonce>` delete | **`PEER#` 에만 `attribute_exists(pk)` 를 건다.** 그 조건이 실패하면 이미 없던 대상이고 `released` 에 담지 않는다(4.6). 나머지는 조건 없는 delete 다. 확인 전에 나간 피어는 `PAIR#` 가 아예 없고, 조건을 걸면 그 회수가 통째로 취소된다. `client_nonce` 를 읽을 수 없으면 `NONCE#` 만 빼고 지운다 |
| `host_report` 서버 회수 | 대상마다 트랜잭션: `PEER#<target>` delete, `VIP#<그 피어의 virtual_ip>` delete, `NONCE#<그 피어의 client_nonce>` delete | `PEER#` 에 `attribute_exists(pk) AND (attribute_not_exists(candidates) OR size(candidates) = :zero) AND joined_at_ms <= :cutoff`. `:cutoff` 는 `now - JOIN_REGISTER_GRACE_S * 1000` 이다. 조건이 실패하면 그 사이 등록했거나 이미 없는 것이므로 `released` 에 담지 않는다. 후보가 없던 피어는 `PAIR#` 가 있을 수 없으므로 지우지 않는다 |
| `host_report` 확인 | 쌍마다 트랜잭션: `PEER#<호스트>` **ConditionCheck**, `PEER#<상대>` **ConditionCheck**, `PAIR#<lo>-<hi>` put | 두 ConditionCheck 는 각각 `attribute_exists(pk) AND size(candidates) > :zero` 다. put 은 `attribute_not_exists(pk)`. **양쪽 후보 조건을 저장소 조건으로 건다.** 읽고 나서 쓰기 전에 상대가 회수되거나 후보가 비워지는 경합이 있다. put 조건만 실패하면 이미 확인된 쌍이므로 오류가 아니다(4.6) |
| `host_report` 갱신 | `ROOM` update(`expires_at_ms = :new`, `ttl = :new_ttl`) 하나를 먼저 쓴다. 그것이 성공하면 그 방의 나머지 항목마다 `ttl = :new_ttl` update 를 따로 쓴다. 트랜잭션으로 묶지 않는다 | `ROOM` 에 `attribute_exists(pk) AND expires_at_ms > :now`. 실패는 `room_expired` 이고 나머지를 쓰지 않는다. **나머지 항목은 각각 `attribute_exists(pk)`** 다. 조건이 실패하면 그 사이 지워진 항목이므로 무시한다. 항목 목록은 이 요청의 첫 `Query` 결과에서 2번이 지운 항목을 뺀 것이다 |

**트랜잭션이 취소되면 취소 사유를 항목별로 읽고 아래 우선순위로 판정한다.**
`TransactionCanceledException` 의 `CancellationReasons` 는 트랜잭션에 넣은 항목과 **같은
위치**에 하나씩 나온다. 그래서 위치로 항목을 식별하고, 판정 순서는 위치가 아니라 아래 표다.

> **왜.** 여러 항목이 동시에 실패할 수 있으므로 어느 것을 먼저 보는지가 응답을 정한다.

| 순서 | 실패한 조건 | 동작 |
|:----:|-------------|------|
| 1 | `NONCE#` | **다른 사유가 무엇이든** 같은 nonce 의 요청이 먼저 성립한 것이다. `NONCE#` 를 다시 읽어 그 `room_id`·`peer_id` 로 방을 `Query` 하고 같은 응답을 돌려준다. 그 방이 만료됐으면 `room_expired` 다(4.2). `room_full` 이나 재추첨으로 가지 않는다. **다시 읽은 `room_id` 가 요청의 방과 다르면 `bad_request`** 다. nonce 를 다른 방에 재사용한 것이고, 사전 읽기 경로가 같은 입력에 내는 답과 같아야 한다 |
| 2 | `ROOM` ConditionCheck (`join_room`) | 방을 다시 읽는다. 없으면 `room_not_found`, 있으면 `room_expired`. 다음 주소로 넘어가지 않는다 |
| 3 | `VIP#` | 다음 주소. 풀이 끝나면 `room_full` |
| 4 | `PEER#` | `peer_id` 재추첨. 상한은 `MAX_PEER_ID_ATTEMPTS` |
| 5 | `ROOM` put (`create_room`) | `room_id` 재추첨. 상한은 `MAX_ROOM_ID_ATTEMPTS` |
| - | 조건 실패가 아닌 사유 (`TransactionConflict`, 스로틀) | `internal`. 클라이언트가 8.3 오류 분류와 재시도의 규칙대로 재시도한다 |

`NONCE#` 를 1번에 둔 근거는 아래 "왜 이렇게 정했나" 에 있다.

- **`create_room` 은 1번 다음에 5번을 본다.** `room_id` 가 살아 있는 방과 부딪히면 `ROOM` put 과
  함께 `VIP#10.100.0.1` 과 `PEER#` 도 실패하는데, `create_room` 에는 다음 주소가 없다. `ROOM` put 이
  성공했는데 `PEER#` 나 `VIP#` 만 실패하면 위 쓰기 표대로 `internal` 이다
- 조건 실패와 조건 실패가 아닌 사유가 섞이면, `NONCE#` 조건 실패가 있을 때만 1번이다. 그 밖에는
  조건 실패가 아닌 사유나 모르는 사유가 하나라도 있으면 `internal` 이다

**단일 항목 update(`register_candidate`, `host_report` 의 확인)는 방 생존을 조건에 넣지
않는다.** `host_report` 의 갱신은 예외다. 그 쓰기의 목적이 방의 만료 시각이므로 조건에
방 생존이 들어간다(위 표). 7.3 연산 처리 순서대로 만료를 먼저 판정한 뒤 쓰므로, 걸리는 것은 읽기와 쓰기 사이
수십 ms 안에 방이 만료되는 경합뿐이다. 그 경합은 허용하고 그 결과를 정확히 적는다.

- 현재 요청은 `ok` 를 받을 수 있다. `register_candidate` 라면 `accepted` 까지 정상 값으로
  돌아온다
- 갱신된 항목은 만료된 방 안에 있고, 그 방을 읽는 **이후의** 모든 연산이 7.3 연산 처리 순서의 6번 만료 검사에서
  `room_expired` 로 끝난다. 그래서 갱신된 값이 실리는 응답은 그 요청 하나뿐이다
- 클라이언트는 다음 요청(대개 `get_peers` 폴링)에서 `room_expired` 를 받고
  `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다
- 응답 직전에 만료를 다시 검사하지 않는다. 검사해도 그 검사와 응답 사이에 같은 경합이 있다

> **왜.** 새 참가만 조건에 넣는 이유는 그 경합이 `VIP#`·`NONCE#` 항목을 만료된 방에 새로
> 만들고 그 항목의 `ttl` 을 방 값에서 파생시켜야 하는데 방이 이미 없을 수 있기 때문이다.

**조건이 실패해도 쓰기 용량을 쓴다** (ADR 0004 결정 2). 그래서 새 참가는 풀을 돌기 **전에**
방을 읽어 만료와 존재를 먼저 확인하고, 풀 크기가 곧 시도 상한이다.

**읽기.**

| 연산 | 읽기 |
|------|------|
| `create_room` | `NONCE#` GetItem (멱등성). 있으면 그 `room_id` 로 `Query` 해 같은 응답을 조립 |
| `join_room` 새 참가 | `NONCE#` GetItem → 있으면 저장된 `room_id` 가 요청과 같아야 한다(다르면 `bad_request`. nonce 를 다른 방에 재사용한 것이다) → 없으면 `ROOM` GetItem (만료·존재) → 트랜잭션 |
| `register_candidate` | `Query(pk)` 로 `ROOM` 과 `PEER#` 전부 (만료·토큰 검사) → `PEER#` update |
| `get_peers` | `Query(pk)` 한 번. `ROOM` 과 `PEER#` 와 `PAIR#` 전부가 나온다. 토큰 검사도 그 결과로 한다 |
| `host_report` | `Query(pk)` 로 만료·호출자 판정 → 회수·확인·갱신 쓰기 → **`Query(pk)` 를 다시 읽어** 응답을 조립 (4.6). 읽기가 두 번인 이유는 그 절에 있다 |

**저장소가 돌려준 값의 형은 `store.py` 가 맞춰 넘긴다.** `boto3` 는 숫자를 `Decimal` 로
돌려주므로 정수 속성은 `int` 로 바꾼다. 위 항목 표의 속성이 없거나 형이 다르면 판정 불가이고
`internal` 이다. 예외는 둘이다.

- `PEER#` 의 `candidates` 는 없으면 빈 목록이다. 아직 후보를 등록하지 않은 피어(5.3 피어의
  `joined`)다. 4.6 서버 회수의 삭제 조건이 `attribute_not_exists(candidates)` 를 빈 것으로 보는
  것과 같다
- 4.6 서버 회수의 판정은 요청을 끝내지 않고 그 피어만 건너뛴다
- 4.6 `host_report` 의 `departed` 회수에서 대상의 `client_nonce` 만 읽을 수 없으면 `NONCE#` 만 빼고
  지운다

방 파티션에서 위 항목 표에 없는 `sk` 가 나오면 판정 불가이고 `internal` 이다.

전부 `ConsistentRead=true` 다(저장 1). **토큰만으로 피어를 찾는 형식을 두지 않는다.** 모든
인증 연산이 `peer_id` 를 함께 받으므로 그 키로 바로 읽는다. 토큰으로 찾으려면 피어 전부를
읽어 대조해야 한다.

### 6.4 속도 제한

**출발지 IP 별로 실패 응답에 예산을 둔다.** 세는 것은 `room_not_found`, `room_expired`,
`unauthorized` 셋이다. 성공과 `bad_request` 는 세지 않는다.

> **왜.** `bad_request` 는 추측과 무관한 형식 오류이고, 성공을 세면 정상 폴링이 걸린다.

| 항목 | 값 |
|------|-----|
| 예산 | 출발지 IP 당 토큰 `RATE_LIMIT_BUCKET`(10). 위 세 오류가 한 번 나갈 때마다 하나 쓴다 |
| 보충 | 분당 `RATE_LIMIT_REFILL_PER_MIN`(10). **연속형이다.** 마지막 보충 시각으로부터 6초가 지날 때마다 1개씩 차고 상한은 `RATE_LIMIT_BUCKET`(10)이다. 기준 시각 규칙은 아래를 본다 |
| 소진 시 | **요청을 처리하지 않고** `rate_limited`. 저장소를 읽지 않는다. 그래야 제한이 저장소 비용도 막는다 |
| 표 | 메모리. 출발지 IP → (토큰, 마지막 보충 시각). 상한 `MAX_RATE_ENTRIES`(4096) |
| 항목 생성 | **토큰을 쓸 때만 만든다.** 조회만 하고 만들지 않는다. 항목이 없는 출발지는 토큰이 가득한 것과 같다 |
| 항목 제거 | **보충으로 토큰이 상한에 닿으면 지운다.** 가득 찬 항목은 없는 것과 판정이 같으므로 들고 있을 이유가 없다. 보충은 그 출발지가 다시 올 때 계산하므로, 다시 오지 않는 출발지의 항목은 표가 찼을 때 지운다. 새 출발지가 토큰을 쓰려는데 표가 차 있으면 표 전체를 한 번 훑어 상한에 닿은 항목을 지운다 |
| 표가 찼을 때 | **새 출발지를 제한하지 않고 통과시킨다.** 그리고 `rate_table_full` 카운터를 올린다. 가장 오래된 항목을 밀어내면 많은 IP 를 가진 공격자가 표를 채워 진짜 추측자의 항목을 밀어낸다. 통과시키면 공격자는 표를 채우는 것으로 얻는 것이 없다. 대가는 표가 찬 동안 새 출발지에 제한이 없는 것이고, 이 값이 오르면 상한을 다시 본다 |
| 예산 검사 시점 | 요청을 파싱한 **뒤**, 저장소를 읽기 전 |

**보충 시각의 기준은 보충이 일어난 시각이다.** 토큰 소모도, `rate_limited` 응답도 그 시각을
바꾸지 않는다.

- 소모가 기준을 미루면 계속 쓰는 출발지의 보충이 영원히 늦어진다
- `rate_limited` 가 미루면 공격자가 계속 두드리는 것만으로 쿨다운을 영구히 연장해 같은
  출발지의 정상 사용자를 영원히 막을 수 있다. [`protocol.md`](protocol.md) 9.5 재협상이
  재협상 쿨다운에 같은 규칙을 둔 이유와 같다
- 기준 시각은 6초씩 나아간다. 기준에서 11초 뒤에 보면 1개가 차고 기준은 6초 뒤로 간다. 남은
  5초는 다음 보충에 이어진다

**토큰은 0 아래로 내려가지 않는다.** 처리 중인 두 요청이 같은 마지막 토큰으로 예산 검사를
통과하고 둘 다 세는 오류로 끝나면, 두 번째 소모는 0 에서 멈춘다.

**60초에 10개를 한꺼번에 채우지 않는다.** 일괄 보충은 예산이 빈 구간을 최대 1분으로 늘려
정상 클라이언트의 한 번뿐인 실패 응답이 오래 막힌다.

**막는 것이 아니라 느리게 하는 것이다. 얼마나 느려지는지를 적는다.**

| 무엇 | 값 |
|------|-----|
| 한 IP 로 30비트 공간(2^30) 전체 | 분당 10회면 약 **204년**. `2^30 / 10 / 60 / 24 / 365` |
| 살아 있는 방 하나를 맞히기까지 | 그 시점에 열린 방이 `N` 개면 기대 시도 수가 `2^30 / N` 이다. 2.1 `room_id` 가 상정한 "열린 방 수십 개" 규모(`N` = 50)면 한 IP 로 약 **4년** |
| IP 가 여럿이면 | 그만큼 나뉜다. IP 100 개면 위 값의 1/100 이다 |

만료된 방도 `room_expired` 로 존재를 알려 주므로(4.1) 표적은 살아 있는 방만이 아니다.
**이 수치는 보호의 크기가 아니라 한계의 크기다.** 1.2 신뢰 가정의 마지막 줄이 그 한계다.

**케이스 표.** [`test_rate_limit.py`](../../control-server/tests/test_rate_limit.py) 의 `CASES` 다. 행
`order` 가 순서 번호이고 같은 출발지에서 차례로 돈다. 위 규칙 가운데 그 표의 행이 다루지 않는
것은 같은 파일의 `RULE_CASES` 가 본다.

표의 12번 행(`row-12`)은 예산을 다 쓴 출발지의 정상 `get_peers` 도 `rate_limited` 로 막힌다는
것이다. 예산이 출발지 단위이기 때문이다. 그것이 뜻하는 것을 적는다. **같은 NAT 뒤의 두 사용자가 공인 IP 를 공유하면 한 사람의
추측이 다른 사람의 정상 요청을 막는다.** 캠퍼스망이 그렇다.

- 정상 클라이언트는 한 기동에 실패 응답을 한두 번 받고 끝나므로 예산 10 은 그 경우를
  덮는다. 다만 옆 사람이 예산을 태우면 막힌다. v1 이 수용하는 한계다
- 대안(토큰 있는 요청은 세지 않기)은 `unauthorized` 추측을 열어 두므로 쓰지 않는다

### 6.5 TTL

| 항목 | `ttl` 값 |
|------|----------|
| 방의 모든 항목 (`ROOM`, `PEER#`, `VIP#`, `PAIR#`, `NONCE#`) | `floor(expires_at_ms / 1000) + STORAGE_GRACE_S`. `expires_at_ms` 는 그 항목을 쓰는 시점의 값이다 |

갱신이 끝난 뒤 방 파티션의 항목은 같은 `ttl` 을 갖는다. 방이 만료된 뒤 하루가 지나면 DynamoDB 가
지운다.

**임대를 갱신하면 방 파티션의 모든 항목(`ROOM`, `PEER#`, `VIP#`, `PAIR#`)의 `ttl` 을 같이 민다.**
`NONCE#` 는 밀지 않는다. 파티션이 달라 갱신의 `Query` 에 나오지 않고, 그 일은 응답을 잃은 요청의
재시도가 끝나면 끝난다. 그래서 오래 산 방의 `NONCE#` 는 그 피어가 들어온 때로부터 하루 남짓 뒤에
먼저 지워진다. 그 뒤 같은 nonce 로 온 요청은 새 참가다. `ROOM` 만 밀면 오래 산 방의
`PEER#`·`VIP#`·`PAIR#` 가 먼저 지워지고, 방은 살아 있는데 피어가 사라진다. 쓰기는 4.6
`host_report` 의 갱신 쓰기가 한다(6.3).

- **갱신 사이에 새로 생긴 항목은 그 시점의 `expires_at_ms` 로 `ttl` 을 갖는다.** 다음 갱신에서
  함께 밀린다. 신호 간격이 최대 30초이고 `STORAGE_GRACE_S` 가 하루라 그 사이에 지워지지 않는다

- **하루의 여유를 두는 이유는 만료 판정이 저장 4 대로 애플리케이션 몫이기 때문이다.** 만료
  직후 항목이 지워지면 `room_expired` 와 `room_not_found` 의 구분(4.1)이 삭제 시점에 따라
  흔들린다. 하루 뒤에는 어느 쪽으로 답하든 상관없는 시점이다
- AWS 문서가 삭제 지연을 "within a few days" 로만 적고 상한을 정하지 않는다는 것은
  [ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 3 과 "확인하지 못한 것" 1번에 있다

### 왜 이렇게 정했나

- **6.3 `host_report` 갱신을 트랜잭션으로 묶지 않는다.** 조건 없는 update 는 없는 항목을
  만들므로, 같은 요청의 회수나 겹친 다른 요청이 지운 `PEER#`·`VIP#` 를 `ttl` 만 가진 항목으로
  되살린다. 되살아난 `VIP#` 는 그 주소를 방이 끝날 때까지 막는다. 조건을 걸고 트랜잭션에 넣으면
  다른 요청이 지운 항목 하나 때문에 임대 갱신 전체가 취소된다. 따로 쓰면 일부 항목의 `ttl` 이
  한 번 덜 밀릴 수 있지만 다음 주기가 다시 밀고, `STORAGE_GRACE_S` 가 하루라 그 사이 지워지지
  않는다
- **6.3 `NONCE#` 를 취소 사유 1번에 둔다.** 재시도 시나리오 때문이다. 응답을 잃은 참가자가
  같은 nonce 로 다시 왔을 때 첫 요청이 이미 `VIP#` 를 선점했으면 `VIP#` 와 `NONCE#` 가 같은
  트랜잭션에서 함께 실패한다. `VIP#` 를 먼저 보면 다음 주소로 넘어가 `room_full` 을
  돌려주고, 그 클라이언트는 자기가 이미 들어간 방에 못 들어갔다고 믿는다

### 7.1 모듈

모듈은 `control-server/controlplane/` 패키지 아래에 있다.

| `log.py` | 7.5 로그 줄. 이벤트와 필드를 허용 목록으로 받는다 | 없음 |

**`ipaddress` 모듈로 후보를 판정하지 않는다.**

- 이 레포의 Python 3.11 버전에서 확인한 값으로 `ip_address('127.0.0.1').is_private` 와
  `ip_address('192.0.2.1').is_private` 가 참이고 `ip_address('224.0.0.1').is_global` 도
  참이다. 버전에 따라 다를 수 있으므로 어느 버전에서도 그 술어에 판정을 맡기지 않는다
- 4.4 위생의 판정은 옥텟 4개를 직접 파싱해 앞 옥텟과 범위로 가른다. 파싱은
  `[0-9]{1,3}(\.[0-9]{1,3}){3}` 의 전체 일치에 각 옥텟 0~255, **선행 0 거부**다
- 숫자 범위를 `\d` 로 쓰지 않는다. Python 의 `\d` 는 ASCII 밖의 숫자도 받는다. `$` 로 끝을 잡지
  않는다. `$` 는 끝의 줄바꿈 앞에서도 맞는다
- `ipaddress.IPv4Address` 를 형식 파싱에만 쓰는 것은 된다. 판정에 그 술어를 쓰지 않는다는
  뜻이다

`asyncio` 와 `json` 은 표준 라이브러리다. `boto3` 는 [`spec.md`](spec.md) NFR-5 승인을 받았다. 웹 프레임워크는 쓰지 않는다(3.1).

### 7.2 요청 처리 한 바퀴

```text
on_connection(reader, writer):
    src = peer IP
    if inflight >= MAX_INFLIGHT:
        counters.unavailable += 1
        respond(503, unavailable); close; return          # 저장소를 건드리지 않는다
    inflight += 1
    try:
        try:
            req = await wait_for(read_request(reader), SERVER_READ_TIMEOUT_S)
        except OpError as e:                              # 3.3 HTTP 부분집합의 4xx
            respond(e.status, e.envelope()); return
        except TimeoutError:
            counters.http_read_timeout += 1; return       # 응답 없음 (3.4)
        except EOF:
            return                                        # 다 받기 전에 닫혔다. 응답 없음, 카운터 없음
        if rate.exhausted(src):                           # 6.4. 파싱 뒤, 저장소 전
            counters.rate_limited += 1
            respond(429, rate_limited); return
        try:
            fields = await to_thread(ops.dispatch, req)   # boto3 는 블로킹이다. 기본 실행기로 건 전용 풀이다
        except OpError as e:
            if e.code in {room_not_found, room_expired, unauthorized}:
                rate.spend(src)                           # 6.4 속도 제한이 세는 셋
            respond(e.status, e.envelope()); return
        respond(200, {ok: true, **fields})
    except Exception:
        counters.internal_error += 1
        respond(500, internal)                            # 예외 내용을 본문에 싣지 않는다
    finally:
        inflight -= 1; close
```

**시간 초과는 요청 읽기에만 건다.** 연산 안에서 나는 `TimeoutError` 는 읽기 시간 초과가
아니다. Python 의 `socket.timeout` 도 `TimeoutError` 이므로, 블록 전체에 걸면 저장소 쪽 시간
초과를 응답 없는 닫기로 잘못 처리한다. 그 경우는 포괄 처리가 `internal` 로 답한다.

**`ops.dispatch` 의 계약.** 성공이면 연산별 필드의 dict 를 돌려주고 서버가 `ok: true` 를 붙인다.
오류이면 4.1 공통 봉투의 오류 코드를 담은 예외를 던진다. 성공의 HTTP 상태는 200 이다.

**저장소 오류는 두 길로 `internal` 이 된다.** 트랜잭션 취소는 `store.py` 가 6.3 취소 사유 표대로
판정해 오류 코드로 바꾼다. 그 밖의 `boto3` 오류(스로틀, 연결 실패, 시간 초과)는 예외로 올라와 포괄
처리가 답하고 `internal_error` 를 올린다. 응답은 같고 카운터만 다르다.

**`boto3` 호출은 블로킹으로 취급한다.** `MAX_INFLIGHT` 개짜리 전용 스레드 풀로 보낸다. 서버가 그
풀을 만들어 이벤트 루프의 기본 실행기로 건다. 종료 때 처리 중인 호출을 기다리지 않으려면(7.6
종료) 그 풀을 프로세스가 직접 쥐고 있어야 한다. 종료는 카운터를 내고 출력을 비운 뒤 풀을 기다리지
않고 프로세스를 끝낸다.

- 이벤트 루프 스레드에서 직접 부르면 DynamoDB 응답 지연 동안 다른 연결의 수락과 파싱이
  멈춘다
- 동시 처리 상한 `MAX_INFLIGHT`(32)는 그 스레드 풀이 무한히 자라는 것과, 저장소가 느려질 때
  대기 요청이 쌓여 메모리를 먹는 것을 막는다. 넘치면 `unavailable` 이고 클라이언트는 8.3
  오류 분류와 재시도의 규칙대로 재시도한다

**거절하는 연결도 상한이 있다.** 자리가 없어 `503` 으로 거절하는 연결은 처리 중 요청 수에
들지 않지만, 응답을 보내고 3.4 서버 쪽 시간 제한의 대기를 마칠 때까지 남는다. 그런 연결이 `MAX_REJECTING`(64)
개면 새 연결은 응답 없이 바로 끊고 `unavailable` 을 올린다.

**한 프로세스, 이벤트 루프 하나, 스레드 풀 하나다.** 멀티프로세스를 두지 않는다.

> **왜.** 멀티프로세스를 두면 속도 제한 표(6.4)가 프로세스마다 따로 생겨 예산이 프로세스
> 수만큼 늘어난다.

### 7.3 연산 처리 순서

`ops.dispatch` 안의 공통 순서다. 연산마다 이 순서를 지킨다. 순서를 바꾸면 케이스 표의 응답이 달라진다.

```text
1. 필드 존재와 형 검사 (4장 표)             -> 실패: bad_request
2. room_id 정규화 (2.1)                     -> 실패: bad_request
3. 연산별 필드 조합 검사 (4장 연산별 표)     -> 실패: bad_request
4. 저장소 읽기 (6.3 읽기 표, ConsistentRead)
5. 방 존재                                  -> 없음: room_not_found
6. 방 만료 (5.1 방의 만료 판정)            -> 만료: room_expired
7. 토큰 검사 (필요한 연산만)                 -> 실패: unauthorized
   host_report 는 호출자가 호스트인지도 본다 (4.6)
8. 연산 본체 (조건부 쓰기)
9. 응답 조립
```

**시각은 요청을 시작할 때 한 번 읽는다.** 만료, 회수, 갱신의 판정이 모두 같은 `now` 를 쓴다.
예외는 `PAIR#` 의 `ready_at_*` 세 값과 응답의 `elapsed_since_ready_ms` 다. 단조 시계와 벽시계가 같은
순간을 가리켜야 하므로 쓰거나 계산하는 그 시점에 읽는다(7.4).

**형식 검사가 저장소 읽기보다 먼저다.** 그래야 `bad_request` 가 저장소 비용을 쓰지 않고,
속도 제한(6.4)이 형식 오류를 세지 않아도 추측 공격이 저장소에 닿지 않는다.

**만료가 토큰보다 먼저다.** 만료된 방에 토큰이 틀린 요청은 `room_expired` 다.

> **왜.** 만료된 방은 어차피 쓸 수 없으므로 토큰 유무를 알려 줘도 잃는 것이 없고, 순서를
> 못박아야 케이스 표가 결정적이다.

### 7.4 시계

`elapsed_since_ready_ms` 는 **단조 시계로 계산한다** ([`protocol.md`](protocol.md) 14장
계약 4). 그래서 세 값을 함께 저장한다.

- 벽시계로 계산하면 NTP 가 시각을 건너뛰는 순간 두 피어가 받는 값이 어긋나 `protocol.md`
  10.2 랑데부의 오차 상한이 깨진다
- 저장 5 때문에 서버는 메모리에 준비 완료 시각을 들고 있지 않고, 단조 시계 값은 부팅마다
  기준이 다르다

| 저장값 | 출처 | 용도 |
|--------|------|------|
| `ready_at_mono_ns` | `time.monotonic_ns()`. **전제는 배포 환경(Linux)에서 이것이 시스템 전체 시계(`CLOCK_MONOTONIC`)여서 프로세스 재시작에 기준이 바뀌지 않는다는 것이다.** 아래 참조 | 같은 부팅 안의 경과 계산 |
| `ready_boot_id` | `/proc/sys/kernel/random/boot_id` 내용. **전제는 이 값이 부팅마다 바뀐다는 것이다** | 위 값이 같은 기준인지 판정 |
| `ready_at_wall_ms` | `time.time()` 밀리초 | 부팅이 바뀌었을 때의 대체, 그리고 5.1 방의 준비 완료 존재 판정 |

```text
elapsed_since_ready_ms(room):
    if room.ready_boot_id == current_boot_id:
        d = (monotonic_ns() - room.ready_at_mono_ns) // 1_000_000
        source = "mono"
    else:
        d = wall_ms() - room.ready_at_wall_ms                # 인스턴스가 재부팅됐다
        source = "wall"
        counters.elapsed_wall_fallback += 1
    return max(0, d)
```

**계산 경로.** 케이스 표는 [`test_clock.py`](../../control-server/tests/test_clock.py) 의 `CLOCK_CASES`,
표 밖 규칙은 `CLOCK_EXTRA_CASES` 다.

- 같은 부팅이면 단조로 계산한다. 프로세스를 재시작해도 그렇다. `CLOCK_MONOTONIC` 은 프로세스와
  무관하다
- 인스턴스가 재부팅됐으면 벽시계로 대체하고 `elapsed_wall_fallback` 을 올린다. NTP 스텝만큼 틀릴
  수 있다. **이 경우 `protocol.md` 10.2 랑데부의 오차 상한은 보장되지 않는다.** 14장 계약 4 가 그
  예외를 이 문서에 위임한다. 준비 완료와 폴링 응답 사이 몇 초 안에 재부팅과 시각 조정이 겹쳐야
  하므로 드물다. 카운터로 관측한다
- 벽시계 대체에서 음수가 나오면 0 이다. 클라이언트는 `punch_delay_ms` 를 다 기다린다
- `boot_id` 파일이 없거나, 읽을 수 없거나, 비었으면 프로세스 시작 시 뽑은 난수를 `boot_id` 로
  쓴다. 그러면 프로세스 재시작마다 벽시계 대체로 떨어진다. Linux 가 아닌 로컬 시험이 그렇다.
  배포 대상은 Linux 다

`CLOCK_CASES` 의 `deploy_only` 행은 순수 함수가 같은 부팅인지의 판정까지만 본다. 단조 시계가
재시작에 이어지는지는 [`roadmap.md`](roadmap.md) Phase 3 검증의 "시계와 로그" 묶음이 배포
인스턴스에서 본다.

**두 전제는 배포 인스턴스에서 확인했다.** 7.6 의 배포 환경에서 두 가지를 봤다.

- `time.get_clock_info('monotonic')` 의 구현이 `clock_gettime(CLOCK_MONOTONIC)` 이고
  `adjustable=False` 다
- `boot_id` 를 재부팅 전후에 읽었고 두 값이 달랐다

개발 기기는 Windows 라 같은 호출이 `GetTickCount64()` 를 돌려준다. 로컬 시험은 위 계산 경로의
마지막 항목이다. 배포 이미지를 바꾸면 같은 두 확인을 다시 한다. 어긋나면 벽시계 대체로 떨어지므로
틀린 값이 아니라 정확도를 잃는다.

### 7.5 로그와 카운터

표준 오류에 한 줄 한 이벤트. 클라이언트 로그 계약([`architecture.md`](architecture.md) 9장
텔레메트리와 기록)과 같은 모양 `<수준> <이벤트키> <이름>=<값> ...` 을 쓴다. Phase 3 검증이 찾는 키는 다음이다.

| 이벤트키 | 필수 필드 | 어느 검증이 쓰는가 |
|----------|-----------|--------------------|
| `http.request` | `op`, `status`, `error`(성공이면 `-`), `src`, `ms` | 모든 연산 검증. **`peer_token`, 본문, `room_id` 를 싣지 않는다.** 방 코드가 로그에 남으면 로그 열람이 곧 방 탈취다 |
| `room.created` | `peer_id`, `virtual_ip` | 가상 IP 배정 검증. `room_id` 는 싣지 않는다 |
| `pair.ready` | `host_peer_id`, `peer_id` (쌍의 상대), `punch_delay_ms` | 준비 완료 1회 기록 검증. 쌍마다 **정확히 한 번** 나와야 한다. 방이 둘 이상인 로그에서 줄을 가르려면 두 `peer_id` 가 있어야 한다 |
| `peer.released` | `peer_id`, `virtual_ip`, `by`(`host` 또는 `server`) | 자리 회수 검증 (4.6). 회수된 주소가 다시 `vip.claimed` 에 나오는 것으로 재배정을 본다. `by` 가 호스트 통지와 서버 회수를 가른다 |
| `peer.reclaim_skipped` | `peer_id`, `reason` | 서버 회수가 판정할 수 없어 건너뛴 피어. `reason` 의 값은 4.6 서버 회수의 판정 순서 표가 정한다. `peer_id` 를 읽을 수 없으면 `-` 다. 수준은 `WARN` 이다 |
| `room.renewed` | `host_peer_id`, `expires_in_s` | 임대 갱신 검증 (5.1). 호스트가 신호를 멈춘 뒤 이 줄이 끊기는 것을 본다 |
| `vip.claimed` | `virtual_ip`, `peer_id` | 동시 참가 중복 배정 검증. `join_room` 의 선점에만 낸다. 호스트의 `10.100.0.1` 은 `room.created` 가 싣는다 |
| `server.started` | `bind`, `port` | 기동 확인. 리슨이 성공한 뒤 한 번 낸다. [`windows-prereq.md`](windows-prereq.md) 6절 제어 평면 EC2 의 bind 확인과 같은 값이다 |
| `counter` | `name`, `value` | 아래 카운터 |

카운터는 `http_read_timeout`, `internal_error`, `rate_limited`, `rate_table_full`, `elapsed_wall_fallback`, `unavailable` 이다. 종료 시와 60초마다 전량을 낸다. 값이 0 인 것도 낸다.

- 수준은 `peer.reclaim_skipped` 만 `WARN` 이고 나머지는 `INFO` 다
- `http.request` 는 답한 요청마다 한 줄이다. `ms` 는 수락부터 송신이 끝날 때까지를 밀리초로 내림한
  값이다. `op` 는 요청을 끝까지 읽어 다섯 연산 가운데 하나로 판정한 경우에만 싣고, 그 밖에는 `-` 다
- 이벤트와 필드는 `log.py` 가 이 표를 허용 목록으로 갖는다. 표에 없는 이름은 줄을 만들지 않고
  오류다

**`room_id` 를 로그에 싣지 않는 것을 다시 적는다.** `http.request` 의 `op` 와 `status` 만으로 Phase 3 검증은 충분하다. 어느 방인지가 필요한 진단은 `peer_id` 로 한다. `peer_id` 는 방 안에서만 뜻이 있어 그것만으로는 참가할 수 없다.

### 7.6 설정과 배포

설정은 환경 변수다. 파일을 두지 않는다. 값이 넷뿐이다.

| 변수 | 뜻 | 기본값 |
|------|-----|--------|
| `SANGTACHI_CP_PORT` | bind 포트. `[1-9][0-9]{0,4}` 전체 일치이고 65535 이하. 빈 값은 오류다 | `8000` |
| `SANGTACHI_CP_TABLE` | DynamoDB 테이블 이름 | 없음. **필수** |
| `AWS_REGION` | 리전 | 없음. 필수. `boto3` 표준 변수 |
| `SANGTACHI_CP_ENDPOINT` | DynamoDB 엔드포인트 URL 덮어쓰기. 로컬 시험용 | 없음. 없으면 리전 기본 |

**서버가 자격 증명을 받는 변수는 없다.** EC2 에서는 IAM
역할이다([ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 5).

로컬 시험은 다르다. DynamoDB local 은 자격 증명을 검사하지 않지만 `boto3` 는 자격 증명을 찾지
못하면 요청을 보내지 않는다(`NoCredentialsError`). 그래서 시험 하네스가 `boto3` 표준 변수에 실제
키가 아닌 값을 넣는다. 이 값이 실제 AWS 로 가지 않도록 하네스는 엔드포인트가 루프백일 때만
저장소 시험을 돈다. 사용자의 AWS 프로파일과 설정 파일도 읽지 않게 막는다.

> **왜.** 액세스 키를 받는 변수를 두면 누군가 그것을 쓴다.

배포는 **systemd 서비스 하나**다. `Restart=always`. 재시작 복원 절차가 없으므로(6.1)
재시작이 싸다. 필수 변수가 없거나 형식이 틀리면 종료 코드 2 로 바로 끝난다. 리슨이나 신호 처리
설정처럼 설정 검사 뒤의 기동이 실패하면 종료 코드 1 이다. 어느 쪽이든 고정 문구 한 줄만 내고
변수 값과 예외 추적은 내지 않는다. 기동 실패의 문구에는 이름 하나만 붙인다. OS 오류면 그 오류
이름(예: `EADDRINUSE`, 모르는 번호면 `OSError`)이고, 그 밖의 예외면 예외 클래스 이름이다. 이 규칙은
리슨에 성공하기 전까지의 실패에 적용한다. 리슨 뒤의 예외는 그대로 올라간다.

**종료.** `SIGINT` 나 `SIGTERM` 을 받으면 리슨을 닫고 카운터를 낸 뒤 끝난다. 처리 중인 요청은
기다리지 않는다. 그 요청의 결과는 종료 때의 카운터에서 빠질 수 있고, 클라이언트는 전송 오류를
받아 8.3 오류 분류와 재시도대로 다시 보낸다. 보안 그룹은 인바운드 TCP 8000 을 연다. 텔레메트리 서비스의 포트는 이 문서
범위 밖이고 [`roadmap.md`](roadmap.md) Phase 9 착수 전 항목이다.

**배포 환경.** 아래는 실제 인스턴스와 테이블에서 확인한 값이다. 리전, 테이블 이름, 공인 주소,
계정 정보 같은 실제 값은 공개 레포에 두지 않는다. 레포 안의 `deploy/aws.local.md` 에 두고
`.gitignore` 가 막는다.

| 항목 | 값 | 어떻게 확인했나 |
|------|-----|----------------|
| OS | Ubuntu 26.04 LTS, x86_64 | 인스턴스에서 `/etc/os-release`, `uname -m` |
| 인스턴스 유형 | t3.micro | 콘솔 |
| Python | 3.14 (시스템). 서버는 venv 에 `boto3` 를 넣어 돈다 | `python3 --version` |
| systemd | 있음 | `systemctl --version` |
| 자격 증명 | IAM 역할. 인스턴스에 자격 증명 파일이 없다 | `aws sts get-caller-identity` 가 `assumed-role`, `~/.aws/credentials` 없음 |
| 보안 그룹 인바운드 | TCP 8000 전체 허용 | 콘솔 |
| 공인 주소 | Elastic IP. 클라이언트에는 IPv4 리터럴을 준다. DNS 이름은 쓰지 않는다 | 콘솔. [`windows-prereq.md`](windows-prereq.md) 10절 |
| 테이블 | 6.2 의 키 둘(`pk`, `sk`), TTL 속성 `ttl`, 인덱스 없음 | 콘솔 |
| 용량 | provisioned, RCU 25, WCU 25 | 콘솔. 아래 "용량" |

**IAM 역할에 필요한 동작은 여섯이다.** 리소스는 그 테이블 하나로 좁힌다.

| 동작 | 쓰는 자리 |
|------|-----------|
| `dynamodb:GetItem` | `NONCE#`, `ROOM` 사전 읽기 (6.3 읽기) |
| `dynamodb:Query` | 방 전체 읽기 (6.3 읽기) |
| `dynamodb:PutItem`, `dynamodb:UpdateItem`, `dynamodb:DeleteItem` | 단일 쓰기와 트랜잭션 안의 같은 동작 |
| `dynamodb:ConditionCheckItem` | 트랜잭션 안의 ConditionCheck (6.3 의 `join_room`, `host_report` 확인) |

> **왜 `ConditionCheckItem` 을 따로 적나.** 트랜잭션 안의 Put, Update, Delete 는 같은 이름의
> 단일 동작 권한으로 허용되지만 ConditionCheck 는 이 권한이 따로 필요하다(AWS DynamoDB 개발자
> 가이드의 트랜잭션 IAM 절). 빠지면 참가와 쌍 확인이 권한 오류로 끝난다.

**용량.** RCU 25, WCU 25 는 DynamoDB 의 Always Free 한도다. 이 한도는 리전과 결제 계정 단위이고
테이블 클래스가 Standard 일 때 적용된다. 계정의 Free Tier 화면에서 "Always Free monthly
allowance" 로 표시되는 것을 확인했다.

부하는 항목 하나가 1KB 이하라는 가정의 최악값이다. 쓰기는 항목마다 1 WCU 이고, 강한 일관성
`Query` 는 읽은 바이트 합을 4KB 단위로 올림한 만큼 RCU 를 쓴다(AWS DynamoDB 개발자 가이드의
읽기·쓰기 단위 절). 방 하나의 항목은 6.2 대로 최대 15개다.

| 부하 | 최악값 |
|------|--------|
| 정원 미만 방의 `host_report` 갱신 쓰기 | 플레이어 셋이면 항목 12개를 5초마다. 2.4 WCU/s |
| 정원이 찬 방의 갱신 쓰기 | 항목 15개를 30초마다. 0.5 WCU/s |
| `host_report` 의 읽기 | 호출마다 `Query` 둘(4.6). 방이 막 정원이 찼으면 15KB 라 회당 4 RCU, 호출당 8 RCU 다. 간격은 직전 응답으로 정하므로 그 호출이 5초 뒤일 수 있어 주기 호출만으로 최악 1.6 RCU/s 다. 세션이 끝날 때의 즉시 호출이 호출당 8 RCU 씩 더해진다 |
| `get_peers` 로 폴링하는 플레이어 한 명 | 0.5초마다 `Query` 한 번. 항목 15개면 15KB 라 4 RCU, 8 RCU/s. 준비 완료까지만 돈다 |

방 하나는 쓰기가 25 안에 든다. 읽기는 플레이어 넷이 동시에 폴링하는 몇 초 동안 폴링만으로 최악
32 RCU/s 이고, 거기에 `host_report` 의 읽기가 더해져 25 를 넘는다. 넘는 부분은 DynamoDB 가 쓰지
않은 용량을 최대 300초어치 모아 두는 burst capacity 가 받을 수 있다. 다만 보장되지 않는다. 같은
가이드가 그 여유를 예고 없이 백그라운드 작업에 쓸 수 있다고 적었으므로 스로틀이 날 수 있다.
그때 클라이언트는 `internal` 을 받고(6.3 취소 사유 표) 8.3 대로 재시도하거나 다음 폴링을
기다린다. 실제 항목은 1KB 보다 훨씬 작아 방 전체가 4KB 안에 들 것으로 보지만 재지 않았다. 여러 방이 같은 순간에 참가 중이면 넘을 수 있다. 실제 소비 용량을 확인하는
시점은 `roadmap.md` 가 갖는다.

**배포 절차는 [`tools/cp-deploy/`](../../tools/cp-deploy/README.md) 가 갖는다.** 유닛 파일과 배포
명령을 여기 옮겨 적지 않는다. 그 도구가 커밋된 코드만 올리고, 시스템 사용자와 systemd 유닛을 쓰고,
`server.started` 줄과 연산 하나의 응답으로 기동을 확인한다.

**DynamoDB 호출의 시간 제한과 재시도.** 서버가 `boto3` 에 주는 값이다.

| 항목 | 값 |
|------|-----|
| connect 시간 제한 | `DDB_CONNECT_TIMEOUT_S`(1초) |
| read 시간 제한 | `DDB_READ_TIMEOUT_S`(1초) |
| SDK 가 보내는 횟수 | `DDB_MAX_ATTEMPTS`(1). SDK 는 다시 보내지 않는다 |

> **왜.** 재시도는 클라이언트의 몫이다(8.3 오류 분류와 재시도). 8.2 시간 제한의 클라이언트는 소켓
> 수신 한 번에 3초를 건다. 서버가 응답을 보내기 시작하기 전에 그 3초가 지나면 클라이언트는
> 포기하고, 포기한 요청은 서버 자리(`MAX_INFLIGHT`)만 차지한다. SDK 가 다시 보내면 호출 하나의
> 시간이 몇 배로 늘어 그 3초를 넘기 쉽다. 1초는 배포한
> 테이블에서 잰 값에 여유를 둔 것이다. 연산 하나 전체의 서버 쪽 시간이 `http.request` 의 `ms` 로
> 중앙값 8~118ms, 가장 긴 것이 331ms(`host_report`) 였다.

**이 값들은 연산 하나 전체의 상한이 아니다.** 연산 하나가 저장소를 여러 번 부르므로, 호출마다
1초가 걸리면 전체는 그 배수가 된다. 연산 전체에 거는 상한은 없다.

**로컬 시험의 한계.** DynamoDB local 은 읽기가 대개 최신 값처럼 보여 `ConsistentRead`
누락이 드러나지 않고, `TransactionConflictException` 도 나지 않는다.

- 둘 다 ADR 0004 "치르는 것" 절이 AWS 문서를 인용해 적었다
- 저장 1 은 코드를 읽어 판정하고, 트랜잭션 충돌 경로는 실제 테이블에서 확인한다

**실제 테이블에서 트랜잭션 충돌이 난다.** 한 방에 플레이어 넷이 동시에 `join_room` 을 보내면
일부가 `internal` 을 받는다. 다섯 번 돌려 20건 가운데 7건이었다. 모든 새 참가 트랜잭션이 같은
`ROOM` 항목을 ConditionCheck 하므로 겹치는 트랜잭션이 `TransactionConflict` 로 취소된다. 취소 사유를
직접 읽어 확인했다. 6.3 항목의 취소 사유 표대로 `internal` 이고, 8.3 오류 분류와 재시도의 클라이언트 재시도(같은 nonce, 1초
간격, 3회)를 흉내 내면 열 번 돌려 40건이 모두 참가했다. 시험 도구는 `tools/cp-deploy/verify.py` 다.

## 8. 클라이언트 쪽 계약

### 8.1 소유 스레드

제어 평면 TCP 호출과 DNS 해석은 **`[control]` 스레드**가 한다. 스레드 구성, `[loop]` 와의
큐, 종료 순서는 [`concurrency.md`](concurrency.md) 8장 `[control]` 스레드가 소유한다.
여기서는 그 스레드가 이 문서의 어느 규칙을 지키는지만 적는다.

> **왜.** `[loop]` 에 넣지 않는 이유는 한 줄이다. 제어 서버가 응답하지 않으면 연결 시간
> 제한을 걸지 않은 TCP `connect` 가 OS 기본 재시도 동안 길게 블록되고, 그동안 `HELLO`
> 재전송과 keepalive 가 멈춘다. 그것은 [`spec.md`](spec.md) NFR-3 위반이다.

### 8.2 시간 제한

| 단계 | 값 | 넘기면 |
|------|-----|--------|
| DNS 해석 (`getaddrinfo`) | OS 기본. **별도 제한을 걸지 않는다.** 동기 호출에 시간 제한을 거는 수단을 이 설계는 쓰지 않는다 | `[control]` 이 그만큼 블록된다. `[loop]` 는 영향 없다 |
| `connect` | `CLIENT_CONNECT_TIMEOUT_S`(3). 논블로킹 `connect` + `select` | 전송 오류 |
| 송신, 수신 각각 | `CLIENT_IO_TIMEOUT_S`(3). `SO_SNDTIMEO` / `SO_RCVTIMEO`. [`concurrency.md`](concurrency.md) 7장 종료의 텔레메트리 소켓과 같은 옵션이고 같은 한계(연산별이라 합이 더 길 수 있다)가 있다 | 전송 오류 |
| 요청 한 건 상한 | 위 셋의 합. **DNS 를 빼고 최대 9초** | - |

**DNS 해석은 기동 시 한 번만 한다.** 결과 IPv4 주소를 `[control]` 이 들고 그 뒤의 모든 요청에 쓴다. 폴링마다 해석하면 DNS 장애가 폴링을 멈춘다. 주소가 기동 중에 바뀌지 않는다는 전제는 Elastic IP 에서 오고, 그 근거와 대가는 [`windows-prereq.md`](windows-prereq.md) 10절이 갖는다.

**해석에 실패하면 기동 실패다. 재시도하지 않는다.** 이것은 [`spec.md`](spec.md) FR-13 의
실패 코드가 아니다. 연결 시도를 시작하지도 못한 것이라 `ERROR` 한 줄과 0 이 아닌 종료
코드로 끝나고, 세션이 없으므로 로컬 기록 파일에도 줄이 생기지 않는다
(`architecture.md` 9장 텔레메트리와 기록). **이름이 풀린 뒤 서버가 응답하지 않는 것은
다르다.** 그것은 요청 실패이고 8.3 오류 분류와 재시도의 규칙대로
`CONTROL_PLANE_EXCHANGE_FAILED` 다. 경계는 "요청을 보낼 주소를 얻었는가" 다.

**연결은 요청마다 새로 연다** (3.3). 재사용하지 않는다.

### 8.3 오류 분류와 재시도

`[control]` 이 `[loop]` 에 돌려주는 결과는 셋 중 하나다.

| 결과 | 무엇 | 예 |
|------|------|-----|
| 성공 | `ok: true` 응답 | 연산 결과 |
| 확정 오류 | `ok: false` 이고 `error` 가 일시 오류가 아님 | `room_not_found`, `room_full`, `unauthorized`, `bad_request`, `rate_limited` |
| 일시 오류 | 전송 오류(3.5), `internal`, `unavailable` | connect 타임아웃, 500, 503 |

**재시도를 판단하는 것은 `[loop]` 다.** `[control]` 은 한 번의 요청을 보내고 결과를 응답 큐에
넣을 뿐이다([`concurrency.md`](concurrency.md) 8장 `[control]` 스레드). 재시도 횟수와 1초 간격 타이머는
`[loop]` 가 세션 상태 옆에 들고, 재시도할 때 요청 큐에 같은 요청을 다시 넣는다. 그래야
`[control]` 이 "유일한 상태는 해석된 서버 주소" 라는 그 절의 규칙을 지킨다.

**재시도는 일시 오류에만, 그리고 연산마다 규칙이 다르다.**

| 연산 | 일시 오류 시 |
|------|--------------|
| `create_room`, `join_room` 새 참가 | **같은 `client_nonce` 로** 1초 간격, **첫 시도를 포함해 총 3회**. 넘기면 `CONTROL_PLANE_EXCHANGE_FAILED` |
| `register_candidate` | 1초 간격, 첫 시도를 포함해 총 3회. 교체 의미(4.4)라 재시도가 안전하다 |
| `get_peers` | **재시도 규칙이 따로 없다.** 다음 폴링이 곧 재시도다. 폴링 간격과 마감은 [`protocol.md`](protocol.md) 11장 타이머 |
| `host_report` | **재시도 규칙이 따로 없다.** 다음 주기가 곧 재시도다. 멱등하므로(4.6) 보고하지 못한 `departed` 를 다시 담아 보낸다(4.6). 일시 오류가 이어져 임대가 끊겨도 터널은 유지한다(5.1). 확정 오류도 아래 일반 규칙이 아니라 4.6 의 오류 표를 따른다 |

확정 오류는 재시도하지 않고 즉시 `CONTROL_PLANE_EXCHANGE_FAILED` 다. **`rate_limited` 도
확정 오류다.** 사람이 다시 시작한다. `host_report` 만 예외이고 4.6 의 오류 표를 따른다.

> **왜.** 클라이언트가 스스로 기다렸다 다시 하면, 같은 NAT 뒤의 정상 클라이언트 여럿이
> 동시에 물러나고 동시에 몰려와 다시 걸린다.

`CONTROL_PLANE_EXCHANGE_FAILED` 로 끝나는 조건의 목록은 `protocol.md` 9.6 실패 전이가
소유한다. 이 절은 그 조건 중 "제어 평면 오류" 가 무엇인지를 펼친 것이다.

### 8.4 기동부터 펀치까지

클라이언트가 이 문서의 연산을 부르는 순서다. 타이머 값은 전부
[`protocol.md`](protocol.md) 11장 타이머의 것이고 여기서는 순서만 정한다.

```text
1. 방을 만들지 참가할지를 받는다. CLI 역할이나 로비 명령이다 (architecture.md 3.5).
   호스트면 create_room, 플레이어면 join_room
2. [control] 이 DNS 를 한 번 해석한다. 실패면 기동 실패
3. UDP 소켓 bind, getsockname (protocol.md 6장)
4. create_room 또는 join_room. 응답의 room_id 를 콘솔에 낸다 (host 는 이것을 상대에게 전한다)
5. STUN (protocol.md 13장). 두 서버에 질의한다
6. register_candidate. 로컬 후보 + 반사 후보. 8개를 넘으면 클라이언트가 먼저 자른다
7. 플레이어: get_peers 폴링. 그 쌍의 ready: true 이고 상대 후보가 1개 이상일 때까지 (4.5).
   **폴링 간격과 마감은 6번의 성공 응답을 받은 시점부터 센다** (protocol.md 11장)
   호스트: host_report 주기 호출. 응답의 peers 에서 후보를 가진 새 상대를 보면
   다음 호출의 confirm 에 그 peer_id 를 넣는다 (4.6). get_peers 를 부르지 않는다
8. 받은 후보에 10.1 위생을 다시 적용한다. 자신의 peer_id 가 보이면 CONTROL_PLANE_EXCHANGE_FAILED
9. max(0, punch_delay_ms - elapsed_since_ready_ms) 뒤 펀치 (protocol.md 10.2)
10. 세션이 끝나면 호스트가 host_report 를 바로 한 번 보내 departed 에 그 peer_id 를 넣는다 (4.6)
```

**2번과 3번은 프로세스에 한 번이다.** 역할 인자가 없어도 기동 시 한다. 로비에서 새 시도를
시작하면 1번의 명령을 받은 뒤 4번부터 다시 간다. 5번 STUN 도 다시 돈다. 건너뛸지는
[`concurrency.md`](concurrency.md) 7장 로비가 미결로 둔다.

**4번이 5번보다 앞이다.** 순서를 바꿔도 프로토콜은 성립하지만 사람이 더 기다린다.

> **왜.** STUN 은 5초 마감이 있고 방 코드는 사람이 전달해야 한다. 방을 먼저 만들어 코드를
> 내주고 그 사이에 STUN 을 돌리면 사람이 기다리는 시간이 겹친다.

**7번이 역할로 갈리는 유일한 자리다.** 호스트와 플레이어가 같은 정보를 다른 연산으로 받는다.
데이터 평면은 갈리지 않는다([ADR 0006](decisions/0006-무중계-스타-토폴로지.md) 결정 6).

**호스트는 4번 직후부터 `host_report` 를 시작한다.** 임대를 갱신해야 방이 살아 있기
때문이다(5.1). 확인할 쌍이 없어도 주기는 돈다.

## 9. 검증

Phase 3 의 검증 항목은 [`roadmap.md`](roadmap.md) 가 갖는다. 그 항목이 돌리는 **케이스 표는
`control-server/tests/` 에 있다.** 이 문서는 규칙을 갖고, 각 절이 자기 표의 파일을 가리킨다. 문서에
표 한 벌, 시험에 한 벌을 두지 않는다.

- 케이스 표가 있는 자리는 2.1 `room_id`, 3.3 HTTP 부분집합, 4.4 `register_candidate`(후보
  위생), 4.5 `get_peers`(원소의 필드 집합), 4.6 `host_report`(회수·확인 경합), 5.1 방,
  6.4 속도 제한, 7.4 시계다
- 저장소가 있어야 도는 행은 `needs="store"` 로 표시되어 있고 그때까지 건너뛴다
- 시험을 돌리는 법은 [`control-server/README.md`](../../control-server/README.md) 에 있다

**케이스 표마다 변이 시험을 붙인다.** 규칙 한 줄을 지운 구현이 그 표의 어느 행에서 `FAIL` 하는지 확인한다. 한 행도 떨어뜨리지 못하는 변이가 있으면 그 규칙은 아직 아무것도 지키지 않는다. 변이 목록은 `control-server/tests/mutants/` 에 표마다 한 파일이고, 실행기 `tests/mutate.py` 가 판정한다.

**코드를 읽어서만 판정할 수 있는 것.**

| 무엇 | 왜 동작 시험으로 안 되는가 |
|------|----------------------------|
| 저장 1 `ConsistentRead=true` | 최종 일관성 읽기도 대개 최신 값을 준다. 로컬은 더 그렇다 |
| 토큰 비교가 상수 시간이고 애플리케이션에서 먼저 한다 (6.3) | 시간 차이는 시험으로 재현하기 어렵다 |
| 판정에 `ipaddress` 술어를 쓰지 않음 (7.1) | 케이스 표 행이 우연히 통과할 수 있다 |
| `room_id` 와 `peer_token` 이 로그에 없음 (7.5) | 로그를 전부 훑어도 "어느 경로에서도 안 나온다" 는 증명이 아니다 |
| `host_report` 의 응답이 쓰기 **뒤에** 읽은 것인가 (4.6) | 두 요청의 읽기·쓰기 순서를 밖에서 강제할 수 없다. 그냥 동시에 보내면 대개 순차로 끝나 결함이 드러나지 않는다. 4.6 확인 경합 케이스 표를 돌리려면 store 계층에 **쓰기 직후 지연을 넣는 주입점**이 있어야 하고, 그 주입점이 있는지도 코드로 본다 |

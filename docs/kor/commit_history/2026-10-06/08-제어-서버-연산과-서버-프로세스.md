# 제어 서버의 연산과 서버 프로세스

## 왜 했나

`plan.md` 다음에 할 일 1번의 둘째 단계다. 저장소 계층(`a0ad5ca`) 위에 연산 다섯(`ops.Service`)과
서버 프로세스(수락 루프, 로그, 카운터, 진입점)를 올렸다. 이것으로 제어 서버가 DynamoDB local 위에서
끝에서 끝까지 돈다.

## 어떻게 나눠 했나

디렉터가 공용 로그 모듈 `log.py` 를 먼저 쓰고 두 작업자에게 계약을 정해 주었다.

| 작업자 | 맡은 것 |
|--------|---------|
| worker-ops2 | `ops.Service.dispatch` 와 연산 다섯, 7.3 처리 순서, 주소 순회와 재추첨, `test_host_report.py` 의 건너뛴 8행 |
| worker-server | 수락 루프, `MAX_INFLIGHT`, 송신 시간 제한, 링거, `http.request` 와 카운터, `__main__.py` |

계약은 둘이다. `Service(store).dispatch(req) -> dict` 이고 오류는 `OpError` 다. 로그는 `log.py` 의
허용 목록으로만 낸다.

## 문서에 정한 것

작업자와 리뷰가 낸 빈자리를 코드보다 먼저 문서에 적었다.

| 절 | 정한 것 |
|----|---------|
| 2.2 | `peer_id` 재추첨 상한은 요청 하나에 하나다 |
| 2.6 | `LINGER_S`, `LINGER_MAX_BYTES`, `MAX_REJECTING` |
| 3.4 | 송신 시간 초과는 끊고 카운터가 없다. 요청을 다 읽지 않은 채 답하면 쓰기 쪽을 먼저 닫고 남은 입력을 버리며 기다린다(링거) |
| 4.3 | 회수된 피어의 `NONCE#`, TTL 로 먼저 지워진 방, 연산을 넘는 nonce 재사용 |
| 4.5 | 호스트가 `get_peers` 를 부르면 자신을 뺀 전부. 원소 순서는 정하지 않는다 |
| 4.6 | 호출자 자신의 `peer_id` 는 건너뛴다. 다시 읽기의 판독 실패는 `internal`. `departed` 회수가 `NONCE#` 도 지우고, `departed` 에 든 피어는 서버 회수가 다시 판정하지 않는다 |
| 6.3 | 회수 행에 `NONCE#` delete |
| 7.2 | 전용 스레드 풀을 기본 실행기로 건다. 거절하는 연결의 상한 |
| 7.3 | 시각은 요청 시작에 한 번 읽는다. 준비 완료 시각만 쓰는 시점 |
| 7.5 | `server.started`, 수준, `http.request` 의 `ms` 와 `op`, 허용 목록 |
| 7.6 | 포트 형식, 종료 코드 2 와 1, 기동 실패 문구, 종료 절차 |

**코드를 바꾼 결정은 하나다.** 호스트가 `departed` 로 회수할 때 `NONCE#` 를 지우지 않아, 회수된
피어가 같은 nonce 로 다시 오면 `internal` 이 반복됐다. 서버 회수처럼 지우게 해 새 참가가 되게 했다.

## Windows 에서 재현한 RST

worker-server 가 찾았다. 서버가 요청을 다 읽지 않고 `503` 이나 `413` 을 보낸 뒤 바로 닫으면, 늦게
도착한 바이트 때문에 OS 가 RST 를 보내 클라이언트가 응답을 읽기 전에 `WinError 10053` 을 받는다.
링거 없이 20번씩 보내 20번 모두 응답이 사라졌고, 링거를 넣은 뒤 20번 모두 받았다.

## 끝에서 끝까지

DynamoDB local 위에 `python -m controlplane` 을 띄우고 `curl` 로 연산 다섯을 차례로 불렀다.

- 방 생성 `10.100.0.1`, 소문자 방 코드로 참가 `10.100.0.2`, 같은 nonce 재시도는 같은 응답
- 루프백 후보는 위생 거부. 확인 전 `get_peers` 는 `ready: false`, 확인 뒤 `pair.ready` 한 줄과 후보
- 틀린 토큰 `403`, 없는 방 `404`, `departed` 회수 뒤 옛 nonce 는 새 참가
- 서버 로그를 방 코드, 두 토큰, 두 nonce 로 훑어 0 건

이 확인 중 디렉터의 테이블 생성 스크립트가 `endpoint_url` 을 빠뜨려 가짜 자격 증명의 요청이 실제
AWS 로 갈 뻔했다. 리전을 못 찾아 요청 전에 멈췄다. README 에 경고를 적었다.

테이블에서 본다(`control_plane.md` 7.6).

## 변이 실행기의 원본 시험 시간 상한

마지막 전체 실행이 "원본이 시험을 통과하지 못한다" 로 멈췄다. 시험은 떨어지지 않았다. 변이를 넣기 전에
kills 의 파일 전체를 원본으로 한 번 돌리는데, `--store` 로 약 140초가 걸려 변이 한 번의 상한
120초에 걸렸다. 원본 시험에 따로 900초를 주고, 시간 초과면 그렇다고 말하게 했다. 시험 한 건을 더했다.

## 순서 원칙

단계는 난이도가 아니라 **기술적 위험** 순으로 정렬한다. 가장 불확실한 가정(임의의 NAT 환경에서 UDP 홀펀칭이 실제로 되는가)을 가장 먼저 검증한다. 가상 어댑터와 게임 통합은 그 가정이 증명된 뒤에 착수한다.

범위 초과 시 제거 순서는 아래 우선순위의 역순이다.

```text
P0: UDP + STUN + 엔드포인트 교환 + 홀펀칭 + 터널 헤더 + DATA 최소 왕복 + 로컬 기록 (Phase 1-4)
P1: 프로토콜 견고성. 손실·재정렬 집계, 퍼즈 방어, 장시간 안정성                    (Phase 5)
P2: Wintun + 가상 IP + Minecraft + 최소 GUI                                        (Phase 6-8)
P3: 텔레메트리 + 진단 + 분석                                                       (Phase 9)
P4: 암호화 + 릴레이 + 추가 플랫폼                                                  (스트레치)
```

## Phase 1: 핵심 UDP 네트워킹

- **목표:** C++ 네트워킹 기본기를 갖춘다.
- **우선순위:** P0
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- 레포를 목표 구조로 재배치 (`src/` -> `client/src/`, `control-server/` 생성)
- CMake 기반 C++20 프로젝트 구성. 경고 수준과 시험 실행 파일을 여기서 고정한다
- 시험 실행 파일과 CTest 등록 ([ADR 0005](decisions/0005-시험-프레임워크-catch2.md))
- Winsock2 초기화 및 해제 (`WSAStartup` / `WSACleanup`) 래핑
- UDP 소켓 래퍼 구현 (`socket`, `bind`, `sendto`, `recvfrom`, `WSAEventSelect` 이벤트 핸들)
- 이벤트 루프 골격 구현. `WaitForMultipleObjects`, 타이머 마감 계산, drain 패턴 ([`concurrency.md`](concurrency.md))
- 엔드포인트 표현 타입 구현 (파싱, 비교, 출력)
- 알려진 두 엔드포인트 간 UDP 패킷 송수신
- 기본 로깅 추가

### 산출물

```text
Client A <------ UDP ------> Client B
```

### 검증

- 같은 LAN의 두 머신(또는 한 머신의 두 프로세스)에서 양방향 메시지 송수신 성공
  - 입력과 판정 수단은 [`architecture.md`](architecture.md) 3.5 기동 입력의 `--peer` 인자와
    `raw <바이트 수>` 콘솔 명령이다
  - 두 머신으로 돌리면 양쪽이 **먼저 한 번씩** 보낸다

  > **왜.** 한쪽만 보내면 그 첫 데이터그램이 상대에게 요청하지 않은 인바운드라
  > [`windows-prereq.md`](windows-prereq.md) 2절의 실측대로 막힌다.
- 수신 내용이 송신 내용과 바이트 단위로 일치
  - **판정은 `rx.raw` 로그 두 줄의 `len` 과 `sha256` 대조다** (`architecture.md` 9장)
  - 눈으로 바이트를 비교하지 않는다
- 소켓 오류 시 프로세스가 죽지 않고 오류 코드를 로그에 남김
- 콘솔 명령 큐 상한([`concurrency.md`](concurrency.md) 6장 텔레메트리 격리). **소비자를 멈춘
  상태에서 본다**
  - `[loop]`가 큐를 비우면 17줄을 넣어도 넘치지 않는다. 소비를 막은 큐 단위 시험이거나
    `[loop]`를 의도적으로 붙잡은 상태에서 17줄을 주입한다
  - 그 조건에서 앞의 16줄이 순서대로 남고 17번째가 버려지며 `console_queue_dropped` 가 오른다
  - 가장 오래된 것을 밀어내는 구현은 여기서 걸린다

  > **왜.** 조건을 고정하지 않으면 정상 구현도 떨어진다.
- bind 계약 확인 ([`protocol.md`](protocol.md) 6장). `INADDR_ANY`와 포트 0으로 bind 한 뒤 `getsockname`이 **0이 아닌 포트**를 돌려주고 그 값이 로그에 남는다. 같은 실행 파일을 한 기기에서 두 번 띄워도 둘 다 기동한다(포트를 고정했다면 두 번째가 실패한다)
- `SO_RCVBUF` 계약(`protocol.md` 6장). 통과 조건은 셋이다
  - 요청값이 `262144` 다. 로그의 `rcvbuf_requested` 로 본다
  - 설정 호출이 실제로 있다
  - 적용값이 한 바퀴 예산 94208바이트 이상이다. 로그의 `rcvbuf_applied` 로 본다
  - 두 값을 모두 로그에 남기는 것이 `architecture.md` 9장의 `socket.bind` 계약이다

  > **왜.** 적용값만 보면 128KB를 요청한 구현도 통과해 6장을 어긴 채 넘어간다.
- 한 번의 신호로 도착한 데이터그램 여러 개가 같은 바퀴에 처리됨 (drain 패턴 동작)
- 과대 데이터그램이 배칭을 끊지 않음. **두 경로를 따로 돌린다** (`concurrency.md` 3장 루프 한 바퀴)
  - (a) 정확히 1473바이트는 길이 비교(`n > MAX_DATAGRAM`)로 걸린다
  - (b) 1474바이트 이상은 `WSAEMSGSIZE`로 걸린다
  - 각각을 정상 데이터그램 여러 개 사이에 끼워 보낸다. 과대분이 `drop_oversize_datagram`으로
    오르고, 같은 바퀴에서 뒤따르는 정상 데이터그램이 계속 처리되는지 본다

  > **왜.** (a)만 시험하면 `WSAEMSGSIZE`에서 바퀴를 끝내는 구현이 통과한다.
- 수신이 끊이지 않고 들어오는 동안에도 주기 타이머가 계속 만료됨 (drain 예산 동작).
  **"계속" 을 값으로 못박는다**
  - 기준. 예산을 넘는 수신 부하를 10초간 끊기지 않게 준 상태에서, 시험 빌드의 200ms 주기
    타이머(`timer.tick name=probe200`)의 `elapsed_ms` 가 400 을 넘지 않는다
    (`architecture.md` 9장)
  - 간격을 로그 줄의 시각이 아니라 그 필드로 읽는다. 로그 형식에 시각이 없기 때문이다
  - 부하가 실제로 예산을 넘게 만든다. 시험 빌드에서 `classify` 에 데이터그램당 지연을 넣어
    예산 초과를 결정적으로 만들고, 그 지연 값을 기록한다
  - drain 예산 코드를 제거한 변이가 이 기준에서 `FAIL` 하는지 확인한다

  > **왜.** 허용 지연이 값으로 없으면 부하에 우연히 생긴 틈에서 타이머가 돌아도 통과하므로
  > 예산 없는 구현이 걸러지지 않는다. 루프백 생성기가 처리 속도를 못 넘으면 큐가 매 바퀴 비어
  > 예산 없는 구현도 통과한다. 변이가 통과하면 이 케이스는 아직 아무것도 지키지 않는 것이다.
- `cmake --build` 가 **MSVC `/W4` 수준에서 경고 0건**으로 성공. 수준을 적지 않으면 기본 경고 수준에서도 같은 문장이 통과해 "경고 없이" 가 컴파일러 설정마다 다른 뜻이 된다
  - 수준과 `/WX`(경고를 오류로)를 CMake 구성에 고정한다. 그래야 이 항목을 사람이 눈으로 세지 않는다
  - 이 레포의 대상에만 건다. 외부 라이브러리에 걸면 빌드가 그 라이브러리 버전에 묶인다

## Phase 2: STUN 클라이언트

- **목표:** NAT 뒤 클라이언트의 공인 UDP 엔드포인트를 알아낸다.
- **우선순위:** P0
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- RFC 5389 중 Binding Request/Response 부분 학습
- Binding Request 패킷 구성 (헤더, magic cookie)
- 트랜잭션 ID 생성 및 응답 매칭
- 공개 STUN 서버로 요청 송신. **어느 서버인지, 두 서버를 어떻게 고르고 실패 시 어떻게 바꾸는지는
  [`architecture.md`](architecture.md) 3.5 기동 입력이 정한다.** 코드에 서버 주소를 박지 않는다
- 기동 입력 처리. 인자 목록과 형식은 `architecture.md` 3.5. 이 Phase 에 필요한 것은 `--stun` 이고
  `--server` 와 `--room` 은 받아서 보관만 한다
- Binding Response 파싱
- STUN 속성(TLV) 순회
- `XOR-MAPPED-ADDRESS` 디코드
- 발견된 공인 IP와 포트 출력
- 타임아웃 및 잘못된 응답 처리

### 산출물

```text
INFO socket.bind local=0.0.0.0:51000 rcvbuf_requested=262144 rcvbuf_applied=262144
WARN stun.duplicate server=stun1.l.google.com:19302 same_as=stun.l.google.com:19302
INFO stun.result server=stun.l.google.com:19302 mapped=x.x.x.x:51000
INFO stun.result server=stun.cloudflare.com:3478 mapped=x.x.x.x:51000
```

**둘째 줄이 목록의 두 번째 항목이 아닌 이유.** 기본 목록의 앞 두 이름이 같은 주소로 풀리면
뒤엣것이 빠지고 그 자리를 다음 항목이 받는다([`architecture.md`](architecture.md) 3.5 기동
입력). 어느 이름이 겹치는지는 그때의 DNS 응답이 정하므로 위 줄은 한 가지 예다.

bind 한 엔드포인트는 `0.0.0.0:<포트>` 다([`protocol.md`](protocol.md) 6장). 인터페이스
주소(`192.168.x.x`)는 10.1 후보 수집과 위생의 **로컬 후보**이고 그 수집은 Phase 4 다.

### 검증

- 이 Phase 의 판정은 **두 STUN 서버 응답의 파싱 성공**이다. 각 응답에서
  `XOR-MAPPED-ADDRESS` 를 디코드해 공인 엔드포인트를 얻으면 통과다
  - 외부 IP 확인 서비스와의 일치 여부는 참고로만 기록한다. 그 서비스는 TCP 경로라 UDP 송신
    경로와 다를 수 있다. [`spec.md`](spec.md) M-2 도 같은 이유로 그 관측을 참고로 둔다
  - 질의 대상과 관측값 기록은 아래 항목이 정한다
- 트랜잭션 ID가 다른 응답은 무시됨
- 응답하지 않는 주소를 지정하면 타임아웃 후 `STUN_DISCOVERY_FAILED`가 [`architecture.md`](architecture.md) 9장의 **로그**에 남고 무한 대기가 없다. M-6의 로컬 기록 파일은 Phase 4 산출물이라 이 Phase에는 없다
- 잘린 응답이나 잘못된 magic cookie를 넣으면 크래시 없이 거부
- 최소 두 곳 이상의 공개 STUN 서버에 질의해 각각의 server-reflexive 주소를 기록. **동일 결과를 요구하지 않는다.** 서버마다 다르면 목적지 의존 매핑으로 관측값을 남긴다
  - **기록은 레포 밖에 둔다.** 관측값에 공인 IP 가 들어가고, `tools/nat-probe/` 의 실측 원본을
    `.gitignore` 로 로컬 보관하는 것과 같은 이유다. 레포에는 관측이 몇 건이고 서버별로 갈렸는지
    아닌지만 적는다
  - 이 항목은 `scripts/e2e-check.ps1` 이 판정하지 않는다. 그 스크립트는 망이 없어도 돌아야 해서
    공개 서버를 부르지 않는다
- NFR-4 판정. STUN 메시지 구성·파싱과 재시도가 우리 코드인지 **코드를 읽어 확인한다.** 외부 STUN 라이브러리를 부르는 구현은 여기서 걸린다. 동작 시험으로는 구분되지 않는다
- STUN에 사용한 소켓이 이후 홀펀칭과 터널이 쓸 소켓과 동일함을 로그로 확인. **이것은 참고다.** 자기 보고이므로 소켓을 새로 연 구현도 같은 줄을 남길 수 있다. 와이어에서 보는 판정은 캡처가 가능한 Phase 4 검증이 맡는다

## Phase 3: AWS 조율 서버

- **목표:** 피어들이 서로를 찾고 후보 정보를 교환한다.
- **우선순위:** P0
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **제어 평면 스키마는 [`control_plane.md`](control_plane.md) 가 확정했다.** 연산, 인코딩, 오류,
  식별자, 상태 전이, DynamoDB 테이블 설계(파티션 키, 정렬 키, 항목, 조건부 쓰기, TTL)가 거기 있다
  - 이 Phase 는 그 문서를 구현한다. 설계하지 않는다
  - 문서에 빠진 값을 만나면 코드에서 정하지 않고 그 문서를 먼저 고친다
  - 저장소를 SQLite에서 바꾼 결정과 그 대가는
    [ADR 0004](decisions/0004-상태-저장소-dynamodb.md)에 있다
- 로컬 시험은 DynamoDB local 로 돌린다. Docker 컨테이너로 띄운다 ([ADR 0014](decisions/0014-제어-서버-시험-pytest와-docker.md)). **다만 일관성 경로는 여기서 판정하지 않는다.** 로컬은 읽기가 대개 최신 값처럼 보여서 `ConsistentRead` 누락이 드러나지 않는다 (ADR 0004)
- **`control_plane.md` 의 케이스 표(2.1, 3.3, 4.4, 4.5, 4.6, 5.1, 6.4, 7.4)는
  `control-server/tests/` 에 두고 문서는 그 파일을 가리킨다.** 표 한 벌이 두 곳에 있으면 한쪽만
  고쳐져 어긋난다. 표마다 변이 시험을 붙인다(`control-server/tests/mutants/`)
  - 저장소가 있어야 도는 행(`needs="store"`)은 store 계층을 만들 때 풀고, 그때 store 쪽 변이를
    붙인다
- Python 제어 서버를 AWS EC2에 배포. systemd 서비스, 보안 그룹 TCP 8000. **배포 절차를 실제로
  한 번 돌린 뒤 도구로 넣고 문서는 가리킨다** (`control_plane.md` 7.6). 배포 환경과 계정 쪽
  확인 결과도 그 절에 있다
  - 배포 도구는 `tools/cp-deploy/` 다. 서버가 DynamoDB 를 부를 때의 시간 제한과 재시도 횟수는
    `control_plane.md` 7.6 설정과 배포가 갖는다
- 방 생성 구현 (`create_room`, 멱등성 nonce)
- 방 참가 구현 (`join_room`. 형식은 하나다. 재참가는 없다)
- 가상 IP 할당 (`VIP#` 조건부 쓰기 선점)
- 후보 엔드포인트 등록 (`register_candidate`, 서버 쪽 위생). 로컬 후보는 두 피어가 같은 LAN일 때 쓰인다
- 호스트 주기 보고 구현 (`host_report`. 임대 갱신, 자리 회수, 쌍 확인 1회 기록)
- 피어 정보 교환 (`get_peers`, 단조 시계 `elapsed_since_ready_ms`)
- 출발지별 속도 제한과 `MAX_INFLIGHT`
- DynamoDB에 방/피어 상태 저장
- C++ 측 제어 평면 클라이언트 구현. `[control]` 스레드와 두 큐
  ([`concurrency.md`](concurrency.md) 8장 `[control]` 스레드), 최소 HTTP/1.1 클라이언트,
  오류 분류와 재시도 (`control_plane.md` 8장)
- 기동 입력 처리 완성. `--server` 와 `--room` 이 실제로 쓰인다 ([`architecture.md`](architecture.md) 3.5)
  - 역할 없이 준 `--room` 을 기동 실패로 바꾼다. 지금은 Phase 1~2 경로라 통과한다
- 로비 명령 `host`, `join`, `leave` 와 `FAIL` 줄 (`architecture.md` 3.5 기동 입력, `concurrency.md`
  7장 로비)
  - 시도가 실패하면 `FAIL` 줄을 낸다. 지금은 `session.failed` 로그만 낸다. 그 뒤 로비로 가는지는
    `concurrency.md` 7장 로비의 계기를 따른다
  - `leave` 가 중단한 시도의 늦은 응답을 버린다 (`concurrency.md` 8장 `[control]` 스레드)
- **이 Phase 의 클라이언트는 `control_plane.md` 8.4 기동부터 펀치까지의 8번에서 멈춘다.** 9번과
  10번(펀치와 세션)은 Phase 4 다
  - 플레이어는 7번의 조건이 8번을 거친 뒤에도 성립한 첫 응답에서 `control.peers` 한 줄을 내고
    `get_peers` 폴링을 멈춘다. 그 뒤 `leave` 나 `quit` 까지 방에 남는다
  - 호스트는 상대마다, 그 쌍이 `ready: true` 이고 8번을 거친 상대 후보가 있는 첫 응답에서 그 상대의
    `control.peers` 한 줄을 낸다. `host_report` 주기는 그대로 돈다
  - 6번의 후보는 반사 후보뿐이다. 로컬 후보 수집은 Phase 4 다
  - `control.peers` 의 필드는 `architecture.md` 9장 텔레메트리와 기록이 갖는다. 후보는 8번의 위생을
    거친 뒤의 목록이다

### 산출물

서로 다른 네트워크의 두 클라이언트가 AWS를 통해 상대의 엔드포인트를 얻는다.

### 검증

**기본 동작.**

- 방 생성자가 `10.100.0.1`, 참가자가 `10.100.0.2`를 받음
- 같은 방에 두 번 참가해도 가상 IP가 중복 할당되지 않음
- `get_peers` 응답에 상대의 가상 IP와 공인 엔드포인트가 포함됨
- 서버 재시작 후에도 방 상태가 유지됨. **복원 절차를 거치지 않고** 재시작 직후 첫 요청이
  DynamoDB 에서 바로 읽는다 ([`control_plane.md`](control_plane.md) 6.1 저장 계약, 저장 5)
- 존재하지 않는 방에 참가 시도 시 명확한 오류 응답
- **제어 서버에 지표 수집 엔드포인트가 없음.** 텔레메트리는 별개 서비스이고 Phase 9다
  ([`architecture.md`](architecture.md) 3.4 텔레메트리 서비스)

**저장 계약과 동시성.**

- **방·피어 항목을 읽는 모든 자리가 `ConsistentRead=true`** (`control_plane.md` 6.1 저장 1).
  `get_peers` 만이 아니다. 코드를 직접 본다. 동작 시험으로는 판정할 수 없다

  > **왜.** 최종 일관성 읽기도 대개 최신 값을 돌려주므로 빠뜨려도 시험이 통과한다.
- 두 피어가 **동시에** 참가해도 가상 IP 가 겹치지 않음. 순차 참가만 보는 위 항목과 다른 시험이다 (저장 3)
- 만료 시각이 지난 방에 참가 시도 시 `room_expired`. 존재하지 않는 방은 `room_not_found`.
  **둘이 다른 코드다.** TTL 삭제를 기다리지 않는다 (저장 4, `control_plane.md` 4.1 공통 봉투).
  `now == expires_at_ms` 경계가 만료 쪽인 것도 본다
- 자리 회수 (`control_plane.md` 4.6 host_report). 호스트가 `departed` 로 알린 피어의 `PEER#`
  와 `VIP#` 가 사라지고, 그 가상 IP 를 다음 참가자가 받는다
  - 호스트가 아닌 피어가 부르면 `unauthorized`
  - 토큰이 틀리면 `unauthorized`
  - 이미 없는 `peer_id` 를 알리면 `released` 가 빈 배열이고 오류가 아니다
- 서버 회수 (`control_plane.md` 4.6 host_report 의 서버 회수). 서버 회수 케이스 표를 전 행 돌린다
  - 시각은 서버 시계를 주입해 만든다. 유예를 실제로 기다리지 않는다
  - `join_room` 만 하고 후보를 등록하지 않은 플레이어 넷으로 풀을 채운다. 유예가 지난 뒤의
    `host_report` 가 넷을 `released` 에 담고, 그 뒤의 `join_room` 이 `room_full` 이 아니다
  - 로그의 `peer.released` 가 `by=server` 다
  - 읽은 뒤 지우기 전에 등록하는 행은 store 계층의 지연 주입점으로 만든다
  - 반대 순서도 돌린다. `register_candidate` 가 토큰 검사를 통과한 뒤 쓰기 전에 회수가 먼저
    커밋되면 `unauthorized` 이고, 지워진 `PEER#` 가 되살아나지 않는다
- 임대 갱신 (`control_plane.md` 5.1 방). `host_report` 를 멈추면 `ROOM_LEASE_S` 안에 방이
  만료되고 그 뒤의 `join_room` 이 `room_expired` 다
  - **이미 수립된 터널은 그대로다** (`spec.md` NFR-3). 임대 만료가 세션을 끊지 않는다
  - 만료된 방에 `host_report` 를 보내면 `room_expired` 이고 되살아나지 않는다
- 멱등성 (`control_plane.md` 4.2 create_room, 4.3)
  - 같은 `client_nonce` 로 `join_room` 을 두 번 부르면 두 번째가 첫 번째와 같은 응답을
    돌려주고 **`VIP#` 항목이 하나만 생긴다**
  - 다른 `client_nonce` 로 부르면 새 참가다. 새 `peer_id` 와 다른 가상 IP 를 받는다. 첫 참가가
    자리를 그대로 차지하고 있기 때문이다
  - 풀의 주소가 전부 선점된 뒤의 참가만 `room_full` 이다 (`control_plane.md` 4.3 join_room)
  - `create_room` 도 같은 nonce 면 같은 방이다
- 준비 완료가 **쌍마다 정확히 한 번** 기록된다 (`control_plane.md` 4.6 host_report,
  5.2 준비 완료)
  - 호스트가 같은 상대를 두 번 `confirm` 해도 서버 로그의 `pair.ready` 가 한 줄이다
  - 그 뒤 어느 피어가 후보를 다시 등록해도 `punch_delay_ms` 와 `elapsed_since_ready_ms` 의
    기준점이 바뀌지 않는다
  - 경합 케이스 표(4.6)를 전 행 돌린다. 순서를 밖에서 강제할 수 없으므로 store 계층의 쓰기
    직후 지연 주입점으로 각 순서를 만든다
  - **후보가 없는 상대를 `confirm` 했을 때 0 줄인 것**을 특히 본다. 조건 없이 쓰는 구현이 그
    행에서 걸리고, 그것이 표의 마지막 행이다
  - 다섯이 동시에 참가하는 경우도 돌린다. 그 표는 2자 기준이라 쌍이 넷인 방의 경합 거동을
    말해 주지 않는다 ([ADR 0008](decisions/0008-스타-토폴로지-후속-결정.md))
- 호스트가 확인하기 전에는 `get_peers` 가 그 쌍을 `ready: false` 로 주고 상대 후보를 싣지
  않는다. 양쪽 등록만으로 준비 완료를 주는 구현은 여기서 걸린다 (`control_plane.md` 4.5 get_peers)
- 늦은 참가. 이미 한 쌍이 `CONNECTED` 인 방에 새 플레이어가 들어와도 기존 쌍의
  `punch_delay_ms` 기준점이 바뀌지 않고, 새 쌍만 따로 준비 완료가 된다

**케이스 표 전 행 통과.** 아래가 가리키는 `control_plane.md` 의 절은 그 표의 **규칙**을 갖는다.
표 자체는 그 절이 가리키는 `control-server/tests/` 의 파일에 있다.

- HTTP 파싱 케이스 표(`control_plane.md` 3.3 HTTP 부분집합) 전 행 통과. 특히 `Content-Length` 두 번, `Transfer-Encoding`, 본문 4097 바이트, `HTTP/1.0` 이 거부된다. 행마다 규칙을 지운 변이가 그 행에서 `FAIL` 한다
- `room_id` 정규화 케이스 표(`control_plane.md` 2.1 room_id) 전 행 통과. `0` 을 `O` 로 고쳐 받는 구현이 걸린다
- 후보 위생 케이스 표(`control_plane.md` 4.4) 전 행 통과. 전부 거부되면 `bad_request` 이고 `ok` 가 아니다. `ipaddress` 술어로 판정하지 않는 것은 코드를 읽어 본다
- 속도 제한 케이스 표(`control_plane.md` 6.4 속도 제한) 전 행 통과. 11번째 실패 요청이 `rate_limited` 이고 **저장소 호출이 없다**(store 계층 호출 수를 센다). 성공과 `bad_request` 는 세지 않는다
- 서버 로그에 `room_id` 와 `peer_token` 이 없다 (`control_plane.md` 7.5 로그와 카운터)
  - 정상 경로와 모든 오류 경로를 한 번씩 밟은 뒤 로그 전체를 두 값으로 `grep` 한다.
    **0 건이어야 한다**
  - 이것은 필요 조건이고 충분 조건이 아니다. 어느 경로에서도 나오지 않는다는 것은 코드를
    읽어 본다

**배포.**

- 배포한 서버가 실제 테이블에서 연산 다섯을 다 돈다. 특히 `join_room` 과 `host_report` 확인이
  권한 오류(`AccessDeniedException`)로 `internal` 이 되지 않는다. IAM 동작 목록
  (`control_plane.md` 7.6 설정과 배포)에서 `ConditionCheckItem` 이 빠지면 여기서 걸린다
- 방 하나를 만들고 플레이어를 넷까지 넣었다 빼는 동안 CloudWatch 의 테이블 지표를 1분 단위로
  본다. `ConsumedReadCapacityUnits` 와 `ConsumedWriteCapacityUnits` 는 1분 `Sum` 을 60 으로 나눈
  값이 25 이하이고, 같은 기간 `ThrottledRequests` 의 `Sum` 이 0 이다. 7.6 의 용량 계산이 재지
  않은 최악값이기 때문이다
  - 지표의 원시 값은 기간 합이라 초당 용량 25 와 바로 비교하지 않는다

**시계와 로그.**

- `elapsed_since_ready_ms` 가 단조 시계에서 나온다. **배포 대상과 같은 Linux 에서 돌린다**
  (`control_plane.md` 7.4 시계)
  - 준비 완료 뒤 서버 프로세스를 재시작하고 `get_peers` 를 부르면 값이 이어지고
    `elapsed_wall_fallback` 카운터가 0 이다
  - 서버 벽시계를 1분 앞으로 돌려도 값이 1분 뛰지 않는다
  - Windows 로컬에서는 이 항목을 돌리지 않는다. 돌리면 정상 구현도 떨어진다

  > **왜.** `boot_id` 가 없어 프로세스 재시작마다 벽시계 대체로 내려가는 것이 `control_plane.md`
  > 7.4 시계의 계산 경로가 정한 동작이고, 그때 카운터가 1 인 것이 규정이다.

**로비.** 판정은 표준 출력의 `FAIL` 줄과 요청 로그로 한다. 종료 코드로 하지 않는다
(`architecture.md` 3.5 기동 입력).

- 역할 없이 기동하면 제어 요청이 하나도 나가지 않고 로비에서 기다린다. `--room` 만 주면
  종료 코드 2 로 기동 실패다
- 없는 방 코드로 `join` 하면 `FAIL CONTROL_PLANE_EXCHANGE_FAILED` 로 시작하는 줄이 표준 출력에
  한 줄 나오고 프로세스가 남는다. 이어서 맞는 방 코드로 `join` 하면 참가된다
- 참가한 방을 `leave` 한 뒤 같은 방에 다시 `join` 하면 새 `peer_id` 를 받는다
  - `client_nonce` 를 참가마다 새로 뽑는지를 보는 항목이다 (`control_plane.md` 2.4
    client_nonce)
  - 값을 다시 쓰는 구현은 옛 참가의 응답을 그대로 돌려받으므로 여기서 걸린다
  - 다시 참가할 때 STUN 요청이 새로 나간다 (`control_plane.md` 8.4). 앞 시도의 결과를 다시 쓰는
    구현이 여기서 걸린다
- 방에 있는 동안 친 `host` 와 `join` 은 `WARN` 한 줄이고 요청이 나가지 않는다. 로비에서 친
  `leave` 도 `WARN` 한 줄이다
- 응답이 미결인 동안의 `leave` ([`concurrency.md`](concurrency.md) 8장 `[control]` 스레드)
  - 제어 서버의 응답을 늦추는 주입점으로 `host` 를 미결로 둔 채 `leave` 한다
  - 응답이 와도 `ROOM` 줄이 나오지 않고, 그 뒤에 STUN 요청도 `register_candidate` 도 나가지
    않는다. 출력만 숨기고 응답을 반영하는 구현이 여기서 걸린다
  - 응답이 오기 전에 친 `host` 는 `WARN` 이고, 온 뒤에 친 `host` 는 받는다
- 호스트가 받은 `host_report` 오류 (`control_plane.md` 4.6 host_report 의 오류 표)
  - 첫 행의 네 응답(`room_expired`, `room_not_found`, `unauthorized`, `bad_request`)을 각각
    돌린다. `room_expired` 는 서버 시계를 주입해 만들고, 나머지 셋은 서버의 응답 주입점으로 만든다
  - 넷 다 호스트가 `FAIL CONTROL_PLANE_EXCHANGE_FAILED` 로 시작하는 줄을 한 번 내고, 그 뒤
    `host_report` 가 더 나가지 않으며, 세션이 없으므로 로비로 간다
  - `rate_limited` 는 서버의 속도 제한 보충 시계를 멈춘 채 같은 출발지에서 없는 방 `join_room`
    을 10번 보내 만든다. 보충이 멈춰 있으므로 다음 `host_report` 가 반드시 `rate_limited` 다
  - 그때 `FAIL` 줄이 나오지 않고 다음 주기의 호출이 나간다. 보충 시계를 풀어 예산이 찬 뒤의
    호출은 성공한다
  - `rate_limited` 에 멈추는 구현과 첫 행 응답에도 계속 부르는 구현이 각각 여기서 걸린다

**클라이언트 쪽 계약.**

- 제어 서버가 죽어 있을 때 클라이언트의 `[loop]` 가 멈추지 않는다
  - 연결 거부 또는 무응답 주소를 `--server` 로 주고, 시험 빌드의 `timer.tick name=probe200`
    이 계속 나오는지 본다 (`architecture.md` 9장)
  - **판정은 Phase 1 과 같은 값이다.** 제어 요청이 미결인 구간에서도 `elapsed_ms` 가 400 을
    넘지 않는다
  - 콘솔 명령 응답도 함께 보되 그것만으로 판정하지 않는다. 사람이 치는 속도로는 수십 초 멈춘
    것도 "응답했다" 로 보인다
  - `connect` 가 `[loop]` 에 있는 구현은 여기서 걸린다 (`concurrency.md` 8장)
- 클라이언트의 제어 평면 재시도 (`control_plane.md` 8.3 오류 분류와 재시도)
  - `rate_limited`, `room_full`, `unauthorized` 를 받으면 재시도 없이 즉시
    `CONTROL_PLANE_EXCHANGE_FAILED` 다. `host_report` 는 예외이고 위 "로비" 의 호스트 항목이 본다
  - `internal`, `unavailable`, 전송 오류는 **같은 `client_nonce` 로 첫 시도를 포함해
    총 3회**를 시도한다
  - 전송 오류는 루프백에서 둘로 만든다. 연결을 받고 답하지 않는 서버(수신 시간 제한)와 닫힌
    포트(연결 거부)다. Windows 루프백에서는 connect 타임아웃을 만들 수 없다. 연결 대기열이 차도 거부로
    끝난다. connect 타임아웃 자체는 경로가 없는 주소가 있어야 하므로 이 묶음에서
    돌리지 않는다
  - 연산마다 판정 축이 다르다. `create_room` 은 방이 하나만 생기는 것으로 본다
    (`ROOM` 항목 수 1)
  - `join_room` 은 두 번째 응답이 첫 번째와 같은 `peer_id` 와 가상 IP 인 것으로 본다.
    **`VIP#` 항목 수 1 도 같이 본다.** 풀이 넷이므로(`control_plane.md` 2.5) nonce 를 무시하는
    구현은 두 번째 주소를 선점해 항목이 둘이 된다
  - 위의 연결 거부와 무응답, 그리고 `unavailable` 은 저장소에 닿기 전이라 nonce 동일성이 저장소에
    남지 않는다. 그래서
    `internal` 재시도로 본다. 첫 시도는 store 계층에 커밋 뒤 응답 직전에 실패를 내는 주입점으로
    만든다. 같은 nonce 의 두 번째 시도는 저장된 응답을 다시 돌려줄 뿐 쓰기가 없어 그 주입점에
    걸리지 않는다. 두 번째 실패는 연산을 처리한 뒤 응답 직전에 오류를 내는 주입점으로 만든다

  > **왜 두 축을 같이 보나.** 항목 수만 보면 정원이 찬 방에서 변이가 `room_full` 로 끝나 항목이
  > 그대로인 경우를 통과시킨다. `peer_id` 동일성이 그 경우를 잡는다.

## Phase 4: UDP 홀펀칭

- **목표:** 수동 포트 포워딩 없이 직접 P2P UDP 경로를 만든다. **프로젝트에서 가장 위험한 단계다.**
- **우선순위:** P0
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

**착수 전에 정할 것.** 둘이다. 이것들이 정해지기 전에는 그 자리의 구현을 시작하지 않는다

- **착수 전 keepalive 매핑 수명 측정**

  - [`tools/nat-lifetime`](../../tools/nat-lifetime/README.md) 로 잰다. 절차, 와이어 형식, 판정 표는 그
    README 가 갖고, 이 방식을 고른 이유는 [ADR 0019](decisions/0019-매핑-수명은-별도-도구로-잰다.md) 가
    갖는다
  - 측정 대상은 "매핑 수명" 이 아니라 "그 경로의 필터+매핑 수명" 이다
  - 응답기는 제어 서버의 기능이 아니다. 제어 평면도 텔레메트리 서비스도 UDP 를 열지 않으므로
    ([`control_plane.md`](control_plane.md) 1.1 하는 것과 하지 않는 것) 측정할 때만 EC2 에서 띄운다
  - 결과를 값에 옮기는 규칙은 [`protocol.md`](protocol.md) 11장 타이머가 갖는다. 시연에 쓸 두 가정의 망을
    모두 잰다. 규칙을 깨는 망이 나오면 그 장을 고친다

  > **왜.** EC2 가 클라이언트에 먼저 보내는 probe 는 요청하지 않은 인바운드라
  > [`windows-prereq.md`](windows-prereq.md) 2절의 실측대로 막히고, "매핑이 만료됐다" 와 "필터가 애초에
  > 닫혀 있다" 를 구분할 수 없어 수명을 0으로 오판한다.

- **착수 전 `tools/nat-probe` 재측정.** 직접 연결이 성립한다는 판정이 아직 유효한지 확인한다. 여기서 조건이 바뀐 것을 발견하면 설계를 되돌릴 시간이 있다 ([ADR 0001](decisions/0001-직접-연결-대비책-미도입.md))
  - **한 호스트가 동시에 네 쌍과 펀치할 때의 거동을 같이 잰다.** 지금 실측 22건은 2자
    기준이라 스타 토폴로지의 호스트 쪽을 말해 주지 않는다
    ([ADR 0006](decisions/0006-무중계-스타-토폴로지.md))
    - 도구는 `tools/nat-probe` 의 `host` 와 `players` 다. 절차와 흉내의 한계는 그 README 가 갖는다
    - 통과는 호스트 쪽 네 쌍이 모두 `success` 인 회차가 3회 연속인 것이다. 펀치 직전 확인을 통과한
      회차만 센다
  - 호스트 NAT 의 위험을 방 생성 전에 판정해 사람에게 경고할지를 이 측정 결과로 정한다
    (ADR 0006). 넣기로 하면 그 판정이 무엇을 입력으로 보는지부터 정한다

**구현.** `protocol.md` 15장 구현 체크리스트를 그대로 따른다. 이 Phase는 설계가 아니라 구현이다.

- 헤더 직렬화/역직렬화 (필드 단위, 네트워크 바이트 오더)
- 단일 수신 루프의 배타적 소켓 소유, STUN/터널 역다중화 (`protocol.md` 6~7장)
- 필수 소켓 옵션: `SO_EXCLUSIVEADDRUSE`, `SIO_UDP_CONNRESET` off, `connect()` 미호출
- 수신 검증 파이프라인과 전용 폐기 카운터 (`protocol.md` 7~8장)
  - 7장 출발지 위생(분류 전), 8.1 공통 검사 1~8번, 8.4 내부 검증 9~15번, 8.5 송신 측 검사
    1~6번이 모두 이 Phase다
  - **8.5 송신 측 검증의 입력은 이 Phase에서는 합성 내부 패킷이다.** Wintun 읽기가 입력이 되는
    것은 Phase 6부터이고 검사 자체는 같다
- `session_epoch` 생성과 고정
- **7장 출발지 위생의 자기 서브넷 브로드캐스트 판정을 여기서 넣는다.** Phase 2 의 분류는 그
  행만 비워 두었다. 인터페이스 주소와 넷마스크가 있어야 계산할 수 있고 그것을 읽는 자리가
  바로 아래의 로컬 후보 수집이다
  - **그때까지는 자기 서브넷 브로드캐스트를 출발지로 하는 데이터그램이 분류 단계를 통과한다.**
    회신이 증폭될 수 있는 경로이고, 회신을 내는 코드(`HELLO_ACK`, `PONG`)가 Phase 4 에서
    생기므로 그 코드와 같은 Phase 에 막는다
  - 원격 서브넷의 브로드캐스트는 넷마스크를 모르므로 막지 못한다. 그것은 7장이 남는 위험으로
    적은 자리이고 이 항목이 바꾸지 않는다
- 후보 수집(로컬/서버 반사)과 제어 평면 랑데부 폴링 (`protocol.md` 10.1, 10.2). **Phase 3 이 만든 제어 평면 클라이언트를 세션 상태 머신에 연결하는 일이다.** 연산 호출 자체는 Phase 3 산출물이고, 여기서는 그 결과로 후보 집합과 펀치 시각을 만든다
- 상대의 **모든** 후보로 `HELLO` 200ms 재전송, 펀치 마감 10초
- 검증을 통과하고 `sequence`를 전진시킨 패킷의 출발지로 `peer_endpoint`를 갱신하는 엔드포인트 학습과 새 주소에 대한 probe nonce 경로 검증 (`protocol.md` 10.4)
- 이중 플래그 `CONNECTED` 조건, 9.4 전이표 전체, 9.4.1 종료 상태 폐기
- 3장의 상한 넷과 9.5 재협상 상한 둘 (`protocol.md` 3, 4.3, 9.5, 10.4)
- `KEEPALIVE` 15초(`CONNECTED` 진입 즉시 1회), 유휴 타임아웃 50초 기반 단절 판정
- `PING`/`PONG` `ping_id` 방식 RTT 측정
- `CLOSE` 송수신
- `DATA` 타입 최소 구현과 왕복. 페이로드는 `protocol.md` 5.4 `DATA` 가 정의한 **완전한 내부
  IPv4 패킷**이다. Wintun이 없으므로 합성 IPv4 패킷을 만들어 넣는다. 가상 IP는 Phase 3에서
  제어 평면이 배분한 값을 쓴다
- `DATA` 송신 측 검증 (`protocol.md` 8.5)
- 라우팅 표의 고정 배열과 두 단계 조회. 그 절의 케이스 표를 전 행 돌린다 (`protocol.md` 8.5 송신 측 검증)
- `ROSTER` 송수신과 전용 폐기 카운터. 방향, 구조, `generation`, 예약 비트, 이름을 본다
  (`protocol.md` 5.7 ROSTER)
- `ROSTER` 송신 시점 셋 (`protocol.md` 5.7)
- **표시 이름** ([`spec.md`](spec.md) FR-16). Phase 3 이 만든 제어 서버와 클라이언트를 고친다
  - 제어 서버. `create_room` 과 `join_room` 의 `name` 검사와 `NAME#` 선점, `name_taken`, 두 회수
    경로의 `NAME#` 삭제, `peers` 원소의 `name` 이다 ([`control_plane.md`](control_plane.md) 2.7,
    4장 연산, 6.3 항목)
  - `control_plane.md` 2.7 의 케이스 표를 `control-server/tests/` 에 먼저 쓴다. 그 뒤 2.7 과 9장
    검증이 그 파일을 가리키게 고친다
  - 클라이언트. `--name` 인자, 로비 명령 `name`, 응답의 `name` 형식 검사, `FAIL` 줄의 `<상대>`
    칸이다 ([`architecture.md`](architecture.md) 3.5 기동 입력, `control_plane.md` 3.5)
  - `ROSTER` 멤버의 이름은 위 `ROSTER` 송수신 항목과 같이 넣는다
  - 고친 제어 서버를 배포한다. 배포 전에 만든 방의 `PEER#` 에는 `name` 이 없어 그 방의 요청이
    `internal` 이 된다(`control_plane.md` 6.3 의 형 규칙). 배포는 그 전의 방을 모두 끝내는 것으로
    본다. 시연이나 측정 중에는 올리지 않는다
- 연결 결과(성공 또는 FR-13 실패 코드)와 RTT를 **로컬 기록 파일**에 남긴다. 제어 평면에 올리지 않는다 (M-6). 경로, 줄 형식, 시도의 정의는 [`architecture.md`](architecture.md) 9장 로컬 기록 파일이다

> **프로토콜은 이미 확정되어 있다.** 와이어 프로토콜이 확정되지 않으면 구현할 수 없다.
> 그래서 `protocol.md` 를 구현 착수 전에 확정본으로 작성했다. Phase 4에서 프로토콜을
> 설계하지 않는다. `protocol.md`를 구현할 뿐이다. 구현 중 문서에 빠진 값이 발견되면 코드에서
> 임의로 정하지 말고 `protocol.md`를 먼저 고친다.
> Phase 5로 남기는 것은 손실·재정렬 집계, 퍼즈 방어, 장시간 안정성이다.

### 산출물

```text
PC A <========== Direct UDP ==========> PC B
```

지원 환경에서 공유기 포트 포워딩 설정 없이 성립한다. 주고받는 패킷은 정식 터널 헤더를 쓰며, Phase 5에서 교체되지 않는다.

### 시험 장치

검증 절차가 쓰는 도구의 계약이다. 검증 기준이 아니라 준비물이다.

- **검증 절차가 쓰는 콘솔 명령을 못박는다.** `[console]`([`concurrency.md`](concurrency.md))이
  받는 명령 가운데 아래 다섯을 검증 절차가 쓴다. 방을 만들고 참가하는 `host` 와 `join` 은
  로비 명령이고 계약은 `architecture.md` 3.5 기동 입력에 있다
  - `quit` 는 종료 이벤트를 신호해 정상 종료 절차를 시작한다 (`concurrency.md` 3장 루프 한
    바퀴). **로비에 있든 세션이 있든 프로세스를 끝낸다**
  - `leave` 는 방을 떠나 로비로 간다. 프로세스는 남는다 (`concurrency.md` 7장 로비)
  - `counters` 는 카운터 전량을 즉시 로그로 낸다 (`architecture.md` 9장). 카운터를 보는 검증
    항목이 이 명령으로 시점을 잡는다
  - `raw <바이트 수>` 는 Phase 1~2 의 원시 송신이고 그 계약은 `architecture.md` 3.5 기동
    입력에 있다
  - `send <n> [size]` 은 합성 내부 IPv4 패킷을 `DATA` 로 `n` 개 보낸다

  `send <n> [size]` 의 계약이다.

  - `n` 은 1 이상 1000 이하의 정수다
  - `size` 는 생략하면 아래 100바이트이고, 주면 20 이상 `MAX_INNER`(1452) 이하의 정수로 그
    크기의 패킷을 만든다 (Phase 5 경계 표가 쓴다)
  - 범위 밖이거나 정수가 아니면 아무것도 보내지 않고 `WARN` 한 줄을 남긴다
  - 고른 세션이 `CONNECTED` 가 아니면 보내지 않고 `WARN` 한 줄을 남긴다. 8.5 의
    `tx_drop_not_connected` 검사가 어차피 막지만, 명령 단계에서 걸러 시험이 무엇을 보는지
    흐리지 않는다
  - **목적지를 무엇으로 고르는지는 라우팅 표를 구현할 때 같이 정한다.** 세션이 여럿이면
    목적지 없이는 어느 세션으로 보내는지가 정해지지 않는다 (`protocol.md` 8.5 송신 측 검증)
  - 송신은 한 바퀴에 몰아넣지 않고 `MAX_DRAIN` 예산과 같은 방식으로 나눠 보낸다
  - 중간에 `sendto` 가 실패하면 거기서 멈추고 보낸 개수를 남긴다
  - **보내는 바이트를 못박는다.** 아래 표가 그 레이아웃이다

내부 패킷 100바이트의 **절대 오프셋**이다. 반열린 구간으로 적는다

| 오프셋 | 크기 | 값 |
|--------|:----:|-----|
| `0` | 1 | `0x45` (version 4, IHL 5) |
| `1` | 1 | `0x00` (DSCP/ECN) |
| `2..4` | 2 | `total_length` = 100 (BE) |
| `4..6` | 2 | id = 0 |
| `6..8` | 2 | flags + fragment offset = 0 |
| `8` | 1 | TTL = 64 |
| `9` | 1 | protocol = 17 (UDP) |
| `10..12` | 2 | IPv4 헤더 체크섬. 계산해 채운다. `protocol.md` 8.4 검사 12번이 본다 |
| `12..16` | 4 | 출발지 = 자신의 가상 IP |
| `16..20` | 4 | 목적지 = 상대의 가상 IP |
| `20..22` | 2 | UDP 출발지 포트 = 25565 |
| `22..24` | 2 | UDP 목적지 포트 = 25565 |
| `24..26` | 2 | UDP `length` = 80 (헤더 8 + 페이로드 72) |
| `26..28` | 2 | UDP 체크섬 = 0 (IPv4에서 허용된다. 8.4 내부 검증이 보지 않는다) |
| `28..32` | 4 | 0부터 세는 패킷 번호 (BE) |
| `32..40` | 8 | 송신 시각. 단조 시계 밀리초 (BE). RTT 기준선이 쓴다 |
| `40` | 1 | **방향 표시.** `0xA5` 는 요청, `0x5A` 는 에코 응답 |
| `41..100` | 59 | `0xA5` 반복 |

> **왜.** 바이트 값이 정해져 있어야 아래 M-5 의 byte-for-byte 비교와 RTT 기준선의 에코가
> 같은 입력을 쓴다.

체크섬과 송신 시각 외에 파생되는 값이 없어야 한다. **그래서 한 번의 송신에 대해 송신 측
바이트와 수신 측 바이트가 정확히 같다.** 아래 M-5 비교가 그것이다.

다른 실행끼리 비교하지 않는다. 송신 시각 8바이트와 그에 딸린 체크섬은 실행마다 다르므로,
재실행 간 바이트 비교를 통과 조건으로 삼으면 올바른 구현도 떨어진다.

아래 왕복 시험과 실패 코드 시험은 이 두 명령으로 개시하고 끝낸다.

> **왜.** 어휘가 없으면 누가 왕복을 개시하는지가 시험마다 달라진다.

### 검증

**직접 경로 수립.**

- 포트 포워딩 규칙이 없는 상태에서 서로 다른 가정망의 두 PC가 양방향 통신 성공
- **같은 LAN 의 두 PC 에서도 `CONNECTED` 에 도달한다.** [`spec.md`](spec.md) 의 "지원 네트워크
  조건" 이 필수 토폴로지 둘을 정했고 이것이 그중 하나다
  - 학습된 `peer_endpoint` 가 상대의 로컬 후보인 것을 로그로 확인한다
    ([`protocol.md`](protocol.md) 10.1 후보 수집과 위생, 10.4 엔드포인트 학습)
  - 같은 NAT 뒤에서 공인 후보로 수렴하면 헤어핀에 기대는 것이므로 그 경우도 관측값으로 적는다

  > **왜.** Phase 1 의 같은 LAN 시험은 터널 이전의 원시 송수신이라 이 항목을 대신하지 못하고,
  > Phase 9 의 "동일 LAN 기준선" 은 P3 이라 최소 성공 판정을 그쪽에 둘 수 없다.
- 패킷 캡처로 트래픽이 AWS를 경유하지 않음을 확인
- 기동 절차 5번([`control_plane.md`](control_plane.md) 8.4 기동부터 펀치까지)에서 **같은
  소켓으로** 서로 다른 두 STUN 서버에 질의해 같은 공인 IP:Port 가 관측됨
  - `spec.md` M-2와 "지원 네트워크 조건"의 판정이다. Phase 2는 동일 결과를 요구하지 않으므로
    이 판정은 여기가 처음이다
  - 관측이 갈리면 목적지 의존 매핑이고 미지원 조건이므로, 실패로 적지 않고 관측값과 함께
    미지원으로 기록한다
- 같은 캡처에서 **STUN 질의의 출발지 포트와 터널 송신의 출발지 포트가 같음**을 대조 (NFR-9). Phase 2는 로그로만 확인했고, 로그는 자기 보고라 실제로 소켓을 새로 연 구현도 통과한다

**와이어 포맷.**

- 헤더 직렬화 후 역직렬화 결과가 원본과 동일 (라운드트립 테스트)
- 캡처한 패킷의 바이트 배열이 `protocol.md` 4.1(와이어 레이아웃)의 오프셋과 바이트 오더에
  정확히 일치. 첫 4바이트가 `53 41 4E 47`

**상태 머신.**

- `PUNCHING` 상태에서 `HELLO_ACK`이 먼저 도착해도 정상 수용됨 (`protocol.md` 9.4)
- `CONNECTED` 상태에서 상대가 `HELLO`를 재전송하면 `HELLO_ACK`을 다시 보냄
- 재협상 뒤 지연 패킷 처리. **NAT 를 건너는 재시작 시험으로 돌리지 않는다**
  - 새 `HELLO` 도착이 보장되는 자리에서 돌린다. 같은 기기의 두 프로세스이거나 수신 경로 직접
    주입이다
  - 그렇게 해서 새 `HELLO` 가 `protocol.md` 9.5 재협상을 일으킨 뒤에 도착한 이전 epoch 의
    지연 패킷이 `drop_retired_epoch` 로 폐기됨
  - 재협상 전에 도착한 지연 패킷은 고정된 epoch 와 일치하므로 수용되는 것이 규정이다. 그
    구간까지 폐기를 기대하면 규정대로 만든 구현이 떨어진다

  > **왜.** 재시작한 상대의 새 `HELLO` 는 `protocol.md` 10.4 엔드포인트 학습의 실측대로 차단될
  > 수 있고 v1 은 그 복구를 보장하지 않으므로, 와이어로 돌리면 재협상이 아예 일어나지 않아
  > 정상 구현이 떨어진다. 폐기되는 이유는 재협상 1단계가 이전 epoch 를 폐기 목록에 넣고,
  > 8.1 공통 검사 8번(폐기 목록)이 8.2 epoch 및 출발지 검사와 9.3 epoch 규칙의 epoch 비교보다
  > 먼저 돌기 때문이다.

**수신 위생과 상한.**

- 응답 없는 후보로 계속 송신해도 `WSAECONNRESET`로 수신 루프가 죽지 않음
- 로컬 후보 판정, 등록 목록, 수신 후보 위생의 자기 서브넷 행 (`protocol.md` 10.1 후보 수집과
  위생). 그 절의 케이스 표 셋을 전 행 돌린다
  - 판정 함수가 인터페이스 열거와 경로 조회를 OS 대신 주입받을 수 있어야 한다. 두 조회의 실패도
    주입한다
  - 변이 다섯이 각각 `FAIL` 한다. `IfType` 53 을 제외 목록에서 지운 것, 활성 판정을 `OperStatus`
    만으로 줄인 것, 자기 Wintun 식별자 규칙을 지운 것, 상한 자르기를 정렬 앞으로 옮긴 것, 수신 후보
    위생의 자기 서브넷 행을 지운 것이다
  - 그 절의 자기 서브넷 집합이 아래 출발지 위생 (a)의 directed broadcast 행과 수신 후보 위생의 자기
    서브넷 행의 입력이다. 두 판정은 이 집합을 주입해 돌린다
- 출발지 위생(`protocol.md` 7장)을 두 층에서 본다
  - (a) **판정 함수**에 그 절의 케이스 표를 그대로 돌린다. 멀티캐스트·제한 브로드캐스트·자기
    서브넷의 directed broadcast·미지정·포트 0은 거부하고 루프백과 일반 유니캐스트는 통과한다
  - (b) **수신 파이프라인**에 거부 대상 출발지를 넣으면 STUN 분류와 터널 분류 어느 쪽에도
    도달하지 않고 `drop_bad_source`에서 끝나며 응답이 한 개도 나가지 않는다
  - (b)는 와이어로 보내는 대신 수신 경로에 데이터그램을 직접 주입해 돌린다. 보통의 Windows
    UDP 소켓으로는 출발지를 위조한 데이터그램을 만들 수 없다
  - **그러려면 수신 경로에 시험용 진입점이 있어야 한다.** `(버퍼, 길이, 출발지 엔드포인트)`를
    받아 분류부터 태우는 함수 하나를 시험 빌드에 노출한다. 그 함수가 `recvfrom` 뒤의 경로와
    같은 코드를 타야 한다
  - 규칙 한 줄을 지운 변이와 루프백을 거부하도록 바꾼 변이가 각각 `FAIL` 하는지 확인한다

  > **왜.** (a)만 시험하면 함수는 맞게 만들고 분류 뒤에서 부르는 구현이 통과한다. 진입점을 시험
  > 전용으로 따로 짜면 그 시험은 실제 경로를 검증하지 않는다.
- 종료 상태 수신(9.4.1). `CLOSE`를 주고받아 `CLOSED`에 도달한 뒤 같은 상대가 보낸 `KEEPALIVE`가 `drop_terminal_state`로만 오르고 어떤 응답도 나가지 않는다. 캡처로 무응답을 확인한다
- 폐기 목록 상한(`protocol.md` 4.3 `session_epoch`). **단위로 시험한다**
  - 폐기 목록 자료구조에 직접 17개를 등록해 목록이 16개를 넘지 않고 가장 오래된 것이
    밀려나는지 본다
  - 파이프라인 확인은 따로 한다. 상대 epoch 가 고정된 세션에서 밀려난 epoch를 단 비-`HELLO`
    패킷을 주입하면 `drop_stale_epoch`로 걸린다(두 번째 방어선)
  - epoch 미고정 상태에서 넣으면 `drop_no_epoch` 라 다른 것을 본 것이 된다
  - 상한 없이 자라는 구현과 새 항목을 거부하는 구현이 각각 걸린다

  > **왜.** 정의된 인터페이스로는 17개를 만들 수 없다. 재협상은 시도당 8회가 상한이고(9.5)
  > 우리 쪽 재시도는 Phase 4 에 개시 수단이 없다.
- `session_epoch` 난수원(4.3). 난수원을 주입할 수 있게 만들고, (a) 0이 나오면 다시 뽑는지, (b) 뽑는 경로가 OS CSPRNG인지를 본다. 값 분포로는 `rand()` 구현을 가릴 수 없으므로 **호출 경로를 코드에서 확인하는 것을 판정에 포함한다**
- 재협상 뒤 타이머(`protocol.md` 9.5 재협상 10번). `CONNECTED` 세션에 다른 epoch 의 `HELLO` 를
  주입해 재협상을 일으킨 뒤 셋을 본다
  - `HELLO` 재전송이 200ms 간격으로 다시 나간다 (캡처)
  - `KEEPALIVE` 와 `PING` 이 그 구간에 나가지 않는다
  - **유휴 타임아웃이 멈춰 있다.** 유휴 타임아웃이 얼마 남지 않은 시점에 재협상을 일으켜 본다.
    재협상 직전에 상대 송신을 끊어 유휴를 45초까지 올린 뒤 주입하면, 타이머를 멈추지 않는
    구현은 펀치 마감(10초) 전에 `TUNNEL_DROPPED` 로 끝나 걸린다. 정상 구현은 그 구간에 단절
    판정을 하지 않는다
- 재협상 상한(`protocol.md` 9.5)
  - 같은 기기의 주입기로 서로 다른 epoch의 `HELLO`를 1초 안에 연달아 보내면 첫 건만 재협상되고
    나머지는 `drop_reneg_rate`로 오른다
  - 간격을 1초 넘겨 `MAX_RENEGOTIATIONS`회를 넘기면 그 뒤는 `drop_reneg_limit`으로 오른다
  - **정상 경로가 여기 걸리지 않는 것도 같이 본다.** 재협상 한 번 뒤의 `HELLO` 재전송은 같은
    epoch이므로 일반 `HELLO`로 처리되어야 한다
- 잠정 경로 상한(`protocol.md` 10.4)
  - 후보 집합 밖의 서로 다른 출발지 포트 다섯 곳에서 검증을 통과하고 `sequence`를 전진시킨
    패킷을 보내면, 앞의 넷만 잠정 경로가 되고 다섯째는 `drop_probe_full`로 오른다
  - **다섯째 패킷 자체는 정상 처리된다.** 유휴 타이머가 갱신되고, `DATA`였다면 주입된다. 그
    패킷을 버리는 구현은 이 항목에서 걸린다
  - 검증 `HELLO`는 경로마다 1회만 나간다(캡처로 확인). 가장 오래된 경로가 밀려나지 않는다
- 무검증 목적지 공통 예산(`protocol.md` 9.4 전이표). **먼저 토큰 셈을 맞춘다**
  - 후보 집합 밖의 새 출발지에서 온 `HELLO` 한 발은 토큰을 둘 쓴다. `HELLO_ACK` 하나와
    10.4 (c)가 그 출발지를 잠정 경로로 올리며 보내는 검증 `HELLO` 하나다
  - 같은 출발지의 두 번째 발부터는 잠정 경로가 이미 있어 토큰 하나만 쓴다. 그 자리는 결과와
    무관하게 5초를 채운다

  다섯 가지를 본다.

  - (a) 후보 집합 밖 출발지에서 `HELLO`를 초당 20회로 10초간 보내면 나가는 송신 수가 초기
    10개 + 초당 5개 보충을 넘지 않고 초과분이 `drop_unverified_tx`로 오른다
  - (b) 같은 시험을 후보 집합 안 출발지로 돌리면 제한이 없어 전부 응답한다
  - (c) **정상 재전송이 막히지 않는다.** 후보 밖 출발지에서 200ms 간격으로 30초간 보내면
    응답이 하나도 누락되지 않는다. 주입기는 검증 `HELLO`에 `HELLO_ACK`으로 답한다
  - (d) **예산이 하나임을 본다.** 후보 밖 출발지에서 `HELLO`와 `PING`을 섞어 보내면
    `HELLO_ACK`, `PONG`, 검증 `HELLO`가 합쳐서 위 한도 안에 들어온다. 경로마다 따로 세는
    구현은 여기서 걸린다
  - (e) **경계를 센다.** 잠정 경로가 이미 있는(5초 안에 등록된) 출발지에서 연속으로 보내면
    10발째까지 나가고 11발째가 막힌다. 새 출발지에서 곧바로 시작하면 첫 발이 둘을 쓰므로
    9발째까지 나가고 10발째가 막힌다. 둘 중 어느 조건으로 돌리는지 적고 그에 맞는 수를
    기대한다. 200ms 뒤 한 발이 통과하는 것도 확인한다. 고정 창 구현은 (c)에서 걸린다

  > **왜.** 토큰 셈을 빼고 세면 규정대로 만든 구현이 (e)에서 떨어진다. (c)의 주입기가 답하지
  > 않으면 잠정 경로가 5초마다 만료되고 다시 등록되어 토큰이 5초에 하나씩 더 나가므로, 시험을
  > 길게 잡을수록 정상 구현도 언젠가 예산에 걸린다. 답하면 그 경로가 검증되어 그 뒤로는 무검증
  > 목적지가 아니다.

**종료와 타이머.**

- `CLOSE` 송신 조건(`protocol.md` 5.6 `CLOSE`, 9.6 실패 전이)
  - `peer_endpoint`를 학습한 세션에서 종료하면 `CLOSE`가 그 주소로 1회 나가고, 학습 전에
    종료하면 **한 개도 나가지 않는다**(캡처로 확인). 후보 전체로 뿌리는 구현은 이 항목에서
    걸린다
  - reason 값도 캡처에서 본다. `CONNECTED` 세션을 `quit` 으로 닫으면 `0x00`, 수립 중에 `quit`
    하면 `0x01`, 펀치 마감으로 실패하면 `0x03` 이다. 셋을 한 값으로 보내는 구현은 여기서
    걸린다
- 한쪽만 `HELLO`를 받은 상태에서는 `CONNECTED`로 전이하지 않음 (한 방향만 뚫린 경우를 성공으로 오판하지 않는다)
- 호스트는 마지막 플레이어의 세션이 끝나도 방에 남는다 ([`concurrency.md`](concurrency.md) 7장 로비)
  - 플레이어가 `leave` 한 뒤에도 호스트의 `host_report` 가 계속 나간다
  - 그 플레이어가 같은 방 코드로 다시 `join` 하면 연결된다
  - 세션 목록이 비었다고 로비로 가는 구현은 여기서 걸린다
- 방이 서버에서 끝나도 연결된 세션은 유지된다 (`control_plane.md` 4.6 host_report 의 오류 표)
  - 플레이어 둘이 `CONNECTED` 인 방에서 서버 시계를 주입해 임대를 만료시킨다. 호스트는 `FAIL`
    줄을 한 번 내지만 두 세션의 `KEEPALIVE` 와 `DATA` 왕복이 계속된다
  - 한 플레이어가 `leave` 하면 그 세션만 끝나고 `host_report` 는 나가지 않는다. 즉시 보고 규칙이
    살아 있는 구현이 여기서 걸린다. 호스트는 아직 방에 남는다
  - 그동안 새 플레이어의 `join` 은 `room_expired` 로 `FAIL` 이다
  - 나머지 플레이어도 `leave` 하면 호스트가 로비로 간다
  - 따로 한 번 더, 두 세션이 남은 상태에서 호스트가 `leave` 하면 세션을 닫고 바로 로비로 간다
- 세션이 끝나면 호스트의 `host_report` 가 다음 주기를 기다리지 않고 나간다 (`control_plane.md`
  4.6 host_report)
  - 정원이 찬 방에서 한 플레이어가 `leave` 하고 그 `host_report` 응답이 온 뒤 새 플레이어가
    `join` 하면 `room_full` 이 아니다
  - 판정은 호스트 로그의 그 세션 `session.state to=CLOSED` 와 서버 로그
    `peer.released by=host` 의 시각 차가 20초 이내인 것이다. 상한은 미결 요청 하나의 응답을
    기다린 뒤 새 요청 하나를 보내는 시간이다(요청 한 건 9초)
  - 이 상한은 요청이 `control_plane.md` 8.2 시간 제한의 표대로 끝난다는 전제의 값이다. 그 표가
    적은 대로 송수신 제한이 연산별이라 더 길어질 수 있으므로, 이 항목은 제어 서버를 느리게
    하는 주입 없이 돌린다
  - `leave` 시각에서 재지 않는다. `CLOSE` 는 한 번만 보내므로(`protocol.md` 5.6) 유실되면 호스트가
    유휴 타임아웃까지 모르고, 그것은 이 규칙이 줄이는 공백이 아니다
  - `leave` 는 주기 호출의 응답을 받은 직후에 친다. 그러면 다음 주기가 30초 뒤라 주기를 기다리는
    구현이 우연히 통과하지 않는다
- 호스트가 보고하지 못한 `departed` 는 다음 호출에 다시 담긴다
  - 응답을 잃게 하는 주입점으로 `host_report` 를 한 번 실패시키고, 그동안 다른 세션이 끝나게
    한다. 다음 성공 호출의 `departed` 에 두 피어가 다 있다
- keepalive 주기: 캡처에서 `CONNECTED` 진입 즉시 1회, 그 뒤 15초 간격으로 `KEEPALIVE`가 나간다. **여기서 재는 것은 우리 송신 주기이고 NAT 매핑 수명이 아니다.** 매핑 수명 측정은 아래 작업 절의 착수 전 항목이다

**`DATA` 왕복.**

- 합성한 내부 IPv4 패킷을 `DATA`로 양방향 왕복시켜 바이트가 일치 (M-5). **비교 지점을
  못박는다**
  - 송신 측이 캡슐화 직전에 가진 페이로드 바이트열과, 수신 측이 8.4 검증을 통과한 뒤 페이로드
    훅이 받은 바이트열을 길이를 포함해 byte-for-byte 비교한다
  - 그 훅이 어댑터 없는 빌드에서 8.4 통과 `DATA` 가 가는 자리이고 계약은
    `concurrency.md` 3장 루프 한 바퀴에 있다. 에코 응답기도 같은 자리에
    붙는다
  - 로그 문자열이나 재구성한 헤더를 비교하지 않는다
  - 제품 빌드에서는 그 `DATA` 가 `drop_no_sink` 로 버려지는 것도 함께 확인한다. 훅이 제품
    빌드에 남아 있으면 안 된다

  > **왜.** 로그 문자열이나 재구성한 헤더를 비교하면 헤더를 다시 쓰거나 패딩이 붙어도 통과한다.
- 내부 출발지/목적지 가상 IP가 틀린 `DATA`가 `drop_inner_src` / `drop_inner_dst`로 폐기됨

**표시 이름.**

- 이름 형식 검사 ([`control_plane.md`](control_plane.md) 2.7 name). 케이스 표에 아래가 다 있다
  - 통과: 1자, 16자, 숫자만, 밑줄만, 대소문자가 섞인 것
  - 거부: 빈 문자열, 17자, 가운데 공백, 앞이나 뒤의 공백, 하이픈, 한글, 전각 숫자, 끝 줄바꿈,
    제어 문자, 문자열이 아닌 값
  - 문자 집합 검사를 지운 변이와 `str.isalnum()` 이나 정규식 `\w` 로 바꾼 변이가 각각 `FAIL` 한다
- 방 안 유일성 (`control_plane.md` 4.3, 6.3)
  - `Alice` 가 있는 방에 `alice` 로 참가하면 `name_taken` 이다. 다른 방에서는 성공한다
  - 같은 이름의 두 참가를 동시에 보내면 하나만 성공한다. 저장소가 있어야 돈다
  - `name_taken` 은 풀의 다음 주소로 넘어가지 않는다. 그 요청의 트랜잭션 시도가 한 번이다.
    `VIP#` 를 먼저 보는 구현은 시도 수에서 걸린다
- 이름은 자리와 함께 풀린다 (`control_plane.md` 4.6)
  - 호스트가 `departed` 로 알린 피어의 이름으로 새 참가가 성공한다
  - 서버 회수된 피어의 이름도 같다
  - 회수 전에는 같은 이름이 `name_taken` 이다
- `peers` 원소에 `name` 이 있고 필드 집합이 `control_plane.md` 4.5 get_peers 와 맞는다
- `FAIL` 줄의 `<상대>` 칸 ([`architecture.md`](architecture.md) 3.5 기동 입력)
  - 호스트에 플레이어 둘을 붙이고 한 쌍만 실패시킨다. 호스트의 `FAIL` 줄 `<상대>` 가 그
    플레이어의 이름이고, 다른 쌍은 그대로 `CONNECTED` 다. 한 쌍만 실패시키는 방법은 아래 실패
    코드 강제 발생 시험의 주입을 쓴다
  - 플레이어의 쌍 실패는 `<상대>` 가 호스트의 이름이다
  - `STUN_DISCOVERY_FAILED` 와 `CONTROL_PLANE_EXCHANGE_FAILED` 는 `<상대>` 가 `-` 다
- `ROSTER` 의 이름 ([`protocol.md`](protocol.md) 5.7 ROSTER). 수신 경로 주입으로 돌린다
  - 이름 길이 0 과 17, 마지막 멤버가 페이로드 끝을 넘는 것, `count` 개를 읽고 바이트가 남는 것은
    `drop_type_length` 다
  - 길이 1 과 16 은 받아들인다
  - 이름에 공백이나 제어 바이트가 든 것은 `drop_roster_name` 이다
- 로비 명령 `name` 으로 이름을 바꾸면 다음 `join` 요청이 새 이름을 싣는다. 형식이 틀린 `name` 은
  `WARN` 한 줄을 남기고 이름을 바꾸지 않는다

**기록과 실패 코드.**

- 로컬 기록 파일의 줄 수가 도달 여부와 맞는다 (M-6, `architecture.md` 9장 로컬 기록 파일. 아래 "그 절" 은 이 절이다)
  - **`CONNECTED` 에 도달하지 못한 시도는 수립 줄 한 줄, `CONNECTED`에 도달한 시도는 수립 줄과 종료 줄 두
    줄이다.** 실패 시 FR-13 코드가 적힌다
  - RTT 는 표본이 없으면 비어 있는 것이 정상이다. 수립 줄은 `PING` 이 아직 돌기 전이라 대개
    비어 있고, 종료 줄에 마지막 표본이 들어간다. 빈 값을 실패로 판정하지 않는다
  - 줄 수는 그 절의 "무엇이 시도 하나인가" 표의 행마다 따로 센다. 호스트에 플레이어 둘을 붙여
    두 쌍이 모두 펀치를 시작하게 하고, 하나만 연결시킨 뒤 모두 끝내면 호스트 파일의 시도는 둘이고
    줄은 셋이다. 한 플레이어가 준비 전에 떠나면 그 쌍은 호스트 쪽 시도가 아니다. 방을 만들고 아무도 오지 않은 호스트는 줄이 없다
  - 수립 중에 `leave` 하면 수립 줄 하나가 `result=ABORTED` 다. 줄을 쓰지 않는 구현과 실패 코드로
    적는 구현이 여기서 걸린다
  - 수립 중에 상대의 `CLOSE` 를 수신 경로로 주입한다. `reason` 이 `0x01` 이면 `ABORTED`, `0x03` 이면
    `PEER_FAILED` 다. 둘을 같은 값으로 적는 구현이 여기서 걸린다
  - 모든 줄의 필드가 그 절의 표 순서대로 아홉이고 빈 값은 `-` 다
  - 단위는 줄을 만드는 함수에 값을 주입해 본다. RTT 23410 마이크로초는 `rtt_us=23410`, 수립 시간
    2410 밀리초는 `setup_ms=2410` 이다. 밀리초를 마이크로초 자리에 적는 구현이 여기서 걸린다
  - 판정은 그 절의 "판정할 수 있는 실행" 에 드는 실행으로만 한다
  - 같은 기기의 두 프로세스가 서로 다른 파일을 만든다. 파일 이름의 PID 가 각 프로세스의 것이다
  - `records` 폴더가 없는 새 실행 파일 폴더를 만들고 그 폴더에 하위 폴더와 파일을 만들 수 없게 한
    뒤 기동하면 기동 실패다
  - 쓰기 실패를 주입하면 `record_write_failed` 가 오르고, 그 뒤 시도의 줄이 파일에 생기지 않고, 터널은
    이어진다
- 홀펀칭 실패 시 `HOLE_PUNCH_TIMEOUT`이 기록되고 `FAIL` 줄이 나온다. **프로세스는 끝나지
  않는다.** 플레이어는 로비로 가고 호스트는 방에 남는다 (`concurrency.md` 7장 로비)
  - 그 전이에서 `HELLO` 재전송이 멈추는 것도 캡처로 함께 본다. 멈추지 않는 구현은 끝난 세션이
    후보 전체로 계속 쏜다 (`protocol.md` 9.6)
- RTT 기준선 비교는 ICMP가 아니라 **같은 소켓, 같은 엔드포인트 쌍에서의 왕복**으로 한다
  - 기준선을 위해 새 와이어 타입을 만들지 않는다. 위 M-5 항목이 쓰는 합성 내부 IPv4/UDP
    패킷에 송신 시각을 넣어 `DATA` 로 나른다
  - 에코 응답기가 내부 출발지와 목적지를 뒤집고, 오프셋 40 의 방향 표시를 `0x5A` 로 바꾸고,
    IPv4 헤더 체크섬을 다시 계산해 되돌린다
  - `0x5A` 인 패킷에는 응답하지 않는다
  - 에코 응답기는 시험 빌드에만 넣는다. 제품 빌드에 포함하지 않는다. CMake 옵션으로 가르고,
    켜진 빌드는 기동 시 `WARN` 한 줄을 남겨 로그만 봐도 구분되게 한다
  - 통과 조건. `PING`/`PONG` 20회 표본의 중앙값이 `DATA` 에코 20회 중앙값 대비 절대차 10ms
    이내 또는 상대차 30% 이내다 (사용자 공간 처리 오버헤드 감안)
  - ICMP 비교는 참고 정보로만 기록할 수 있다

  > **왜.** NAT 뒤 피어를 향한 ICMP는 차단되거나 피어의 공유기가 응답하는 경우가 많아 같은
  > 경로를 재지 못한다. `0x5A` 규칙이 없으면 양쪽이 옵션을 켰을 때 응답이 다시 에코되어 두 피어
  > 사이에 패킷이 영원히 오간다. 체크섬을 그대로 두면 되돌아온 패킷이 `protocol.md` 8.4 검사
  > 12번에서 `drop_inner_checksum` 으로 걸려 이 시험이 성립하지 않는다. 받은 `DATA` 를 되돌려
  > 보내는 기능은 그 자체로 반사 경로이므로 시연 빌드에 남으면 안 된다. `protocol.md` 5장에
  > 에코 타입이 없고 7장 분류가 프로토콜 밖 데이터그램을 폐기하므로, 별도 에코 패킷을 전제하면
  > 규정대로 만든 구현이 이 시험을 돌릴 수 없다.
- 실패 코드 강제 발생 시험: 제어 평면을 내린 상태 -> `CONTROL_PLANE_EXCHANGE_FAILED`, 응답 없는 엔드포인트 주입 -> `HOLE_PUNCH_TIMEOUT`, `HELLO_ACK` 응답을 차단 -> `PEER_HANDSHAKE_FAILED`. 각각 정확한 코드와 상태 전이가 기록됨

### 위험

이 단계가 실패하는 NAT 환경이 존재한다. 실패를 숨기지 않고 NAT 환경 정보와 함께 기록한다. 지원/미지원 네트워크 조건을 명시적으로 정의한다. 릴레이 폴백은 이 시점에서 구현하지 않고 스트레치로 남긴다.

## Phase 5: 터널 프로토콜 완성

- **목표:** Phase 4에서 왕복까지 확인한 터널에 견고성을 더한다. 손실·재정렬 집계, 손상 패킷과 퍼즈 방어, 장시간 안정성이다.
- **우선순위:** P1
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다
- **선행:** [`protocol.md`](protocol.md) 15장 체크리스트가 Phase 4에서 전부 완료되어 있다.

### 작업

- `sequence` 기반 손실 및 재정렬 **집계**. [`protocol.md`](protocol.md) 4.5 중복 억제와 손실
  집계의 `position` / `baseline` / `accepted` 계산을 구현해 손실과 손실률을 낸다
  - 수용 창 자체는 Phase 4 의 몫이다
  - 그 창은 시간 기반 만료가 없는 64칸 위치 기반 비트맵이라 "윈도우 만료" 라는 계기가 없다
  - 손실은 만료로 확정되는 것이 아니라 `expected - accepted` 로 나온다. `drop_too_old` 로
    버린 패킷은 이미 손실로 확정된 것이므로 되돌리지 않는다
- 퍼즈 방어. 손상되고 절단된 입력에도 크래시하지 않는다
- 장시간 연결 안정성 확보
- **자동 재시도 여부 확정.** `TUNNEL_DROPPED` 뒤에 누가 언제 재시도를 개시하는지
  `protocol.md` 9.6 실패 전이가 정하지 않았다. 정한 뒤 그 문서를 고친다

**Phase 4 가 이미 구현한 것은 여기서 다시 만들지 않는다.** 아래 셋은 **시험**이 이 Phase의 몫이고 구현은 Phase 4에 있다. 어디에 무엇이 있는지 헷갈리면 검증 기준이 두 Phase에 갈라진다.

| 항목 | 구현 | 이 Phase에서 하는 것 |
|------|------|----------------------|
| 8.1 공통 검사 1~8번과 폐기 사유별 카운터 | Phase 4 | 잘못된 magic, 미지원 version, 길이 불일치, 절단 패킷을 주입해 카운터가 맞는 사유로 오르는지 본다 |
| 8.4 / 8.5 크기 한계와 `payload_length` 검증 | Phase 4 | 20바이트와 `MAX_INNER` 경계, 그리고 경계 바로 밖을 시험한다 |
| 9.4 세션 상태 머신 전체 | Phase 4 | 장시간 구간과 실패 전이에서 상태가 규정대로 머무는지 본다 |

### 산출물

두 피어 사이에서 내부 IPv4 패킷을 손실, 재정렬, 손상 조건에서도 안정적으로 나르는 애플리케이션 레벨 터널이 존재한다. Phase 7에서 이 `DATA` 페이로드 자리에 Wintun이 실제로 캡처한 IP 패킷이 들어간다.

| 576 | 왕복 성공. 중간값 |
| 1452 | 왕복 성공. `MAX_INNER` 경계 |
| 1453 | 송신 시 `tx_drop_oversize`. **수신 쪽은 이 표로 시험하지 않는다.** 데이터그램이 20+1453 = 1473바이트라 `n > MAX_DATAGRAM` 길이 비교에서 `drop_oversize_datagram` 으로 버려져 검증 파이프라인에 닿지 않는다 ([`concurrency.md`](concurrency.md) 3장. `WSAEMSGSIZE` 경로는 1474바이트부터다) |

  왕복 성공 케이스의 일치 판정은 Phase 4와 같은 비교 지점(페이로드 훅)을 쓴다.

  **크기를 주는 수단과 20바이트 단서.** Phase 4 의 콘솔 명령을 `send <n> [size]` 로 쓴다.
  `size` 를 생략하면 Phase 4 가 못박은 100바이트 레이아웃이고, 주면 그 크기의 내부 IPv4/UDP
  패킷을 만든다.

  - 20바이트는 IPv4 헤더뿐이라 UDP 헤더도 방향 표시(오프셋 40)도 들어가지 않는다. 에코
    응답기는 방향 표시를 읽을 수 없으므로 되돌리지 않는 것이 규정이고, 그래서 이 크기는
    편도로 보내 수신 측 훅에서 바이트를 비교한다
  - 576과 1452는 100바이트 레이아웃을 그대로 쓰고 오프셋 41 이후의 채움 바이트만 늘린다
  - `total_length` 와 UDP `length` 와 IPv4 체크섬은 크기에 맞춰 다시 계산한다
- 잘못된 magic, 미지원 version, `payload_length` 불일치 패킷이 모두 폐기되고 해당 사유 카운터 증가
- 퍼즈 시험. **두 단계로 나눈다**
  - **1단계 (분류와 8.1).** 고정 seed로 생성한 1~2000바이트 무작위 패킷 100,000개를 소켓에 주입해도 크래시와 메모리 오류 없음
  - **2단계 (8.2 epoch 및 출발지 검사 이후).** magic·version·상대 `peer_id`·고정된 epoch 까지
    유효한 헤더를 붙이고 그 뒤를 무작위로 채운 패킷 100,000개를 Phase 4 의 수신 주입 진입점으로
    넣는다. `type` 과 `payload_length` 도 변이 대상에 넣어 길이 불일치와 경계를 밟게 한다
    - 도달했는지는 카운터로 본다. `drop_magic` 만 오르고 그 뒤의 카운터가 하나도 오르지
      않으면 그 시험은 파이프라인을 밟지 않은 것이다
  - 두 단계 모두 seed, 개수, 길이 범위를 로그에 남겨 재현 가능하게 한다

  > **왜.** 1단계만 돌리면 검증 파이프라인이 거의 실행되지 않는다. 무작위 첫 바이트의 3/4 은
  > [`protocol.md`](protocol.md) 7장 분류에서 끝나고, 남은 것도 4바이트 magic 에서 사실상 전부
  > 걸려 8.2 epoch 및 출발지 검사 이후(nonce 표, 중복 억제 비트맵, 8.4 내부 검증, `CLOSE`
  > reason, 재협상)에 도달하는
  > 입력이 없다.
- 제어 평면 중단 시험: `CONNECTED` 도달 후 제어 서버를 내려도 10분간 `DATA` 전송과 세션 상태가 유지됨 (NFR-3)
- 의도적으로 패킷을 누락시켰을 때 `sequence` 간격으로 손실률이 계산됨
- 패킷 순서를 뒤바꿔 주입해도 손실로 집계되지 않음 (`protocol.md` 4.5 중복 억제와 손실
  집계의 64칸 수용 창이
  재정렬 패킷을 수용하고, 그 패킷이 `accepted` 에 세어진다)
- `sequence`가 32비트 경계를 넘어가도 손실률이 튀지 않음. **수신 주입 진입점으로 돌린다**
  - `sequence = 0xFFFFFFF0` 부터 시작하는 패킷열을 주입해 `position` 이 순환 없이 이어지는지
    본다 (`protocol.md` 4.5)

  > **왜.** 규정대로 0부터 세면 경계까지 2^32 개를 보내야 하므로 와이어로는 돌릴 수 없다.
- 유휴 타임아웃 시험: 상대 송신을 완전히 끊으면 `TUNNEL_DROPPED`가 정확한 상태 전이와 함께 기록됨 (FR-13 실패 코드 집합 완성)
- 장시간(1시간 이상) 연결 유지 중 세션 상태가 `CONNECTED`로 유지됨

## Phase 6: Windows 가상 네트워크 어댑터

- **목표:** 가상 인터페이스로 IP 패킷을 캡처하고 주입한다.
- **우선순위:** P2
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **착수 전 Wintun 배포물의 기대 발행자 문자열과 공개 해시를 적어 둘 위치 확정.**
  [`windows-prereq.md`](windows-prereq.md) 4절은 배포물의 `Subject` 와 해시를 기대값과
  비교하라고 하는데, 그 기대값을 어디에 적어 두는지가 없다. 위치를 정한 뒤 그 문서를 고친다

  > **왜.** 둘 곳이 없으면 그 절의 판정 2번과 3번을 돌릴 수 없고 `Status` 만 보는 검사로
  > 무너진다.
- **착수 전 대체 대역을 넣을지 정한다.** `windows-prereq.md` 7절은 지금 차단 조건에서 중단만
  한다
  - 대역을 바꾸려면 양쪽이 같은 값을 써야 하고, 그러려면 제어 평면이 그 값을 알려 줘야 하는데
    [`control_plane.md`](control_plane.md) 4장의 연산에 그 필드가 없고 2.5 가상 IP 풀이 대역을
    상수로 고정한다
  - 넣기로 하면 두 문서를 같이 고친다
  - 넣지 않기로 하면 중단이 v1 의 최종 동작이고 그 한계를 7절에 그대로 둔다
- **착수 전 Wintun 주입 실패의 표현 확인.** 쓰는 헤더와 그 문서에서 실패가 어느 호출에서 어떤
  형태로 나오는지 확인하고, "링이 찬 것"을 별도 카운터로 나눌지를
  [`concurrency.md`](concurrency.md) 3장 루프 한 바퀴에 적는다
  - 동작 계약(폐기, `drop_inject_error`, 재시도 금지, 루프 비차단)은 이미 정해져 있으므로 이
    항목이 막는 것은 카운터 세분뿐이다
- Wintun 의존성 **승인됨**. 제공 범위 문서화는 그대로 유지한다
- Wintun 과 IP Helper 를 부르는 원본은 `client/src/platform/win32/` 에 둔다
  ([ADR 0010](decisions/0010-플랫폼-이식-이음새.md) 이음새 3). `tools/platformgate/` 가 판정한다
  - **쓰기 시작하는 OS 헤더를 그 도구의 `OS_HEADERS` 목록에 먼저 넣는다.** 목록에 없는 헤더는
    판정하지 않고 통과한다. `.h` 나 `.c` 로 된 원본을 들이면 `SOURCE_SUFFIXES` 도 같이
    고친다. 두 목록의 현재 내용은 [`../../tools/platformgate/README.md`](../../tools/platformgate/README.md)가 갖는다
  - 어댑터 원본이 생기면 [`architecture.md`](architecture.md) 10장 목표 구조를 같이 고친다.
    현재 배치의 출처는 그 문서다
- 가상 어댑터 생성 및 개방
- 가상 IP 주소 할당
- 어댑터에서 패킷 읽기
- 어댑터로 패킷 주입
- 필요한 Windows 라우트 설정 및 종료 시 정리
- 게임 없이 기본 IP 도구로 트래픽 검증

### 산출물

```text
Windows IP 스택
      |  10.100.0.0/24 로 향하는 패킷
      v
Wintun Adapter  --- read ---> 클라이언트 (카운터 증가)
Wintun Adapter  <-- inject -- 클라이언트 (직접 만든 응답)
```

단일 호스트에서 가상 어댑터로부터 패킷을 읽고 다시 주입할 수 있다. 두 가상 IP 간 통신은 터널 통합이 필요하므로 Phase 7의 산출물이다.

### 검증

- `ipconfig`에 가상 어댑터와 할당된 가상 IP가 표시됨
- `route print`에 `10.100.0.0/24` 경로가 어댑터로 향함
- 같은 머신에서 **미할당** 가상 IP(예: `10.100.0.9`)로 `ping`을 보내면 어댑터 read 카운터
  `adapter_rx` 가 증가. 이 패킷에 대한 ICMP 응답을 직접 만들어 inject 하면 `ping`이 응답을
  받는다 (read/inject 양방향 경로 검증)
  - ICMP 응답 생성기는 시험 빌드에만 넣는다. 받은 것을 되돌리는 기능이라 Phase 4 의 에코
    응답기와 같은 성격이고 같은 CMake 옵션 아래 둔다
- 자기 가상 IP `ping`은 Windows 로컬 스택에서 단락 처리되어 어댑터를 거치지 않으므로 검증에 쓰지 않는다
- 두 피어 간 실제 가상 IP 왕복은 터널 통합 이후이므로 Phase 7에서 검증한다
- 클라이언트 종료 후 어댑터와 라우트가 남지 않음
- 비정상 종료 후 재실행 시 어댑터가 정상 재생성됨

### 위험

Windows 가상 네트워킹은 예상보다 복잡할 수 있다. 이 작업은 Phase 4의 NAT 통과 작업과 분리해 진행한다. Wintun은 가상 인터페이스 접근에만 쓰고 라우팅 결정 로직은 프로젝트가 직접 소유한다.

## Phase 7: 가상 어댑터와 P2P 터널 통합

- **목표:** 가상 네트워크 IP 패킷을 피어 간에 전달한다.
- **우선순위:** P2
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- Wintun에서 송신 IP 패킷 읽기
- 목적지 가상 IP로 대상 피어 결정
- `DATA` 패킷으로 캡슐화
- 직접 UDP 연결로 전송
- 수신 패킷 역캡슐화
- 원본 IP 패킷을 Wintun에 주입
- 패킷 크기 한계 처리 및 MTU 확정
- 카운터와 진단 추가

### 산출물

두 Windows 머신이 가상 IP만으로 통신한다.

### 검증

- 상대 가상 IP로 `ping` 왕복 성공
- 가상 IP 간 파일 전송(SMB 또는 임시 TCP 서버) 성공, 내용 일치. **이 항목이 NFR-2 의 판정이다**
  - Minecraft 가 아닌 트래픽이 터널을 그대로 지나가는 것을 보인다
  - 통과 조건에 하나를 더 붙인다. 이 시험과 Phase 8 의 Minecraft 시험을 같은 터널 빌드로
    돌린다. 애플리케이션을 바꾸느라 터널 코드를 고쳐야 했다면 NFR-2 가 성립하지 않는다
- 최대 크기 패킷 전송 시 조각화 없이 전달 (실측으로 MTU 값 확정)
- 라우팅 대상이 없는 가상 IP로 보낸 패킷은 폐기되고 카운터 증가
- 주입 실패 처리([`concurrency.md`](concurrency.md) 3장 루프 한 바퀴). 송신 링을 채운
  상태를 만들면 그 패킷이 `drop_inject_error`로 폐기되고 **루프가 그 자리에서 기다리지 않는다**
  - 판정은 카운터만 보지 않는다. 주입이 실패하는 구간에도 keepalive 송신 간격이 유지되는지
    같이 본다
  - 자리가 날 때까지 재시도하는 구현은 그 간격이 무너져 걸린다
- 송수신 바이트 카운터를 패킷 캡처와 대조한다. **판정 기준은 아래 표가 갖는다.**

| 항목 | 정의 |
|------|------|
| 계수 기준 | **터널 헤더를 포함한 UDP 페이로드 바이트.** 이더넷·IP·UDP 헤더는 세지 않는다 |
| 계측 지점 | 클라이언트는 `sendto`/`recvfrom` 이 성공 반환한 바이트를 센다. 캡처는 같은 기기에서 그 소켓의 5-튜플만 거른다 |
| 표본 조건 | 게임 트래픽이 아니라 **생성한 트래픽**으로 한다. 유휴에서 시작해 정해진 개수를 보내고 멈춘 구간만 본다. 크기는 Phase 5 경계 표의 20 / 576 / 1452바이트를 쓴다 |
| 개수 | **아직 비어 있다. 시험 때 정해 이 칸에 적는다.** 1,000 / 5,000 / 10,000 / 50,000 을 순서대로 시도해 캡처 유실이 0으로 보고된 가장 큰 값을 고른다. 이 사다리는 탐색 격자일 뿐이고 판정에 쓰는 것은 고른 값이다. 기기와 캡처 설정에 달려 미리 지어낼 수 없다 |
| 유효 구간 | 캡처 도구가 보고하는 유실 수가 **0인 구간에서만 판정한다.** 0이 아니면 실패가 아니라 버리고 다시 잰다 |
| 통과 조건 | 유효 구간에서 바이트 합이 일치한다. 캡처 합이 카운터 합보다 **크면 실패**다. 세지 않은 바이트를 보낸 것이므로 계수 버그다 |
| 패킷 수 | **참고로만 기록한다.** UDP 분할 오프로드가 켜져 있으면 캡처가 보는 데이터그램 수가 달라진다. 바이트 합은 그래도 같다 |

  **이 시험이 보장하지 않는 것.** 캡처가 유실을 겪는 구간의 정확성은 판정하지 않는다. 부하가
  높을 때의 계수 정확성은 이 시험이 말해 주지 않는다

  아래의 FR-15 주석이 정한다. 명부의 송수신과 검증은 Phase 4 산출물이고 여기서는 표시만 한다
- **GUI 스레드 모델을 먼저 정한다.** Qt 이벤트 루프와 [`concurrency.md`](concurrency.md) 1장
  스레드의 `[loop]` 주 스레드 규칙 중 어느 쪽이 주 스레드인지를 이 Phase 착수 전에 정하고
  `concurrency.md` 에 적는다. [ADR 0007](decisions/0007-gui-핵심-범위-qt.md)이 미결로 두었다
- **GUI 가 쓰는 기동 입력 경로를 정한다.** 지금 입력은 CLI 인자뿐이고
  ([`architecture.md`](architecture.md) 3.5 기동 입력) 방 코드와 실패 줄이 표준 출력이다
- **착수 전 GUI 조작과 제어 평면 속도 제한의 관계를 정한다.** 사람이 버튼을 빠르게 누르면
  같은 출발지에서 호출이 몰린다. 지금 한도는 [`control_plane.md`](control_plane.md) 6.4
  속도 제한이 갖고 그 문서는 GUI 를 다루지 않는다. 창 쪽에서 막을지 받은 오류를 보여 줄지를
  정하고 그 자리에 적는다
- **착수 전 GUI 에서의 권한 승격과 잔존물 정리 시점을 정한다.** [`windows-prereq.md`](windows-prereq.md)
  14절 자동과 수동은 관리자 권한을 사람이 실행할 때마다, 잔존물 정리를 클라이언트가 시작할 때로
  적는다. 창이 뜨기 전인지 뒤인지와 승격을 거부했을 때 창이 무엇을 보이는지가 없다
- **착수 전 Qt 런타임의 배포 형태 확인.** 배포물에 무엇이 붙고 실행 전제가 얼마나 느는지
  확인한 뒤 [`windows-prereq.md`](windows-prereq.md) 4절 배포물 패키징을 고친다 (ADR 0007)
- **호스트 종료가 OS 유예 안에 드는지 잰다.** 세션마다 보내는 `CLOSE` 최대 네 개와 어댑터
  정리가 `CTRL_CLOSE_EVENT` 의 유예 3초 안에 끝나는지를 측정한다. 정하는 것이 아니라 재는
  것이다 (`concurrency.md` 7장 종료)

### 산출물

```text
Minecraft Client -> 10.100.0.1:25565 -> Project Virtual Network -> Minecraft Server
```

### 검증

- **FR-15 의 다섯 동작을 GUI 만으로 끝에서 끝까지 수행한다** (`spec.md` T-7). 명령줄 인자를 쓰지 않는다
- **플레이어 하나를 끊었을 때 다른 플레이어의 멤버 목록에서 그 멤버가 끊긴 것으로 바뀐다**
  (T-7 의 마지막 조건). 판정 시한은 호스트가 단절을 아는 시점에 명부 주기 한 번을 더한 값이다
  (`protocol.md` 5.7 ROSTER)
  - 정상 종료로 끊으면 호스트가 `CLOSE` 를 받은 시점이다 (`protocol.md` 5.6 CLOSE)
  - 프로세스를 강제 종료해 끊으면 유휴 타임아웃 시점이다 (`protocol.md` 11장 타이머)
  - 둘을 각각 한 번씩 돌린다. 한쪽만 돌리면 단절 판정 경로 하나가 시험되지 않는다
  - **끊는 대상이 호스트면 명부를 보낼 쪽이 없다.** 그때 플레이어가 보는 것은 멤버 목록의
    변화가 아니라 방에서 나가 로비로 돌아가는 것이고, 그 규칙은
    [`concurrency.md`](concurrency.md) 7장의 로비 절이 갖는다. 그 경우도 한 번 돌린다
- 플레이어가 `10.100.0.1:25565` 입력만으로 접속, 공인 IP/포트 입력 없음
- 호스트 공유기에 포트 포워딩 규칙이 없는 상태에서 성공
- 30분 이상 연속 플레이 중 강제 종료 없음
- 게임 표시 지연과 터널 RTT 를 같은 구간에서 기록하고 **둘의 차이를 보고한다.** 판정 기준은
  아래 표가 갖는다

| 항목 | 정의 |
|------|------|
| 재는 것 | 게임 표시 지연은 Minecraft 클라이언트가 보여 주는 값이고, 터널 RTT 는 `PING`/`PONG` 측정치다. **둘은 같은 것을 재지 않는다.** 게임 값은 응용 계층 왕복이고 터널 위에 있다 |
| 계측 지점 | 게임 값은 화면에서 읽고, 터널 값은 클라이언트 로그에서 읽는다 |
| 표본 조건 | 같은 구간에서 각각 20회 이상. 구간의 시작과 끝을 로그에 남긴다. **이것은 통계적 충분성 주장이 아니라 기록의 최소 조건이다.** 게임 표시 지연이 초 단위로 갱신되므로 20회를 모으려면 대략 1분이 든다 |
| 통계 | 중앙값과 사분위 범위. 평균과 표준편차를 쓰지 않는다 |
| 무엇을 판정하는가 | **계측 일관성이다. 품질이 아니다.** 게임 지연이 아무리 커도 이 기준만으로는 실패하지 않는다. 체감 품질 판정은 아래 반영 시험이 맡는다 |
| 통과 조건 | 게임 표시 지연의 중앙값이 터널 RTT 중앙값 **이상**이다. 작더라도 그 차이가 허용 폭 안이면 통과로 본다. 허용 폭은 터널 RTT의 사분위 범위와 게임 표시값의 표시 해상도 1단위 중 큰 쪽이다. 조용한 LAN에서는 사분위 범위가 0에 가까워지는데, 그때 화면 반올림만으로 뒤집히면 정상 구현이 떨어진다. 허용 폭을 넘게 작으면 실패이고, 둘 중 하나를 잘못 재고 있다는 뜻이다. 허용 폭을 밀리초로 지어내지 않는다. 같은 측정에서 나온 흩어짐과 도구의 표시 해상도만 쓴다 |
| 보고 | 차이의 중앙값과 사분위 범위를 [`experiments.md`](experiments.md)에 싣는다 |

  **이 기준이 보장하지 않는 것.** 절대 지연 상한을 보장하지 않는다. 체감 품질은 아래 반영
  시험으로만 본다
- 블록 배치 20회와 채팅 20회를 시도해 전부 2초 이내에 상대 클라이언트에 반영

## Phase 9: 모니터링과 실험적 평가

- **목표:** 동작하는 데모를 넘어 측정 가능한 CSP 분석 결과를 만든다.
- **우선순위:** P3
- **관련 요구사항:** [요구사항 추적](#요구사항-추적) 표가 출처다. 여기에 다시 나열하지 않는다

### 작업

- **착수 전 텔레메트리 서비스의 스펙 확정.** 수집 스키마, 인증 여부, 업로드 주기, 보존 기간, DynamoDB 테이블 설계를 정한다. **정하기 전에는 구현하지 않는다.** 분리 계약 자체는 [`architecture.md`](architecture.md) 3.4 텔레메트리 서비스가 이미 갖는다
- **착수 전 한 인스턴스 안의 자원 격리 방법 확정.** 두 서비스는 같은 EC2 인스턴스에 뜨므로 텔레메트리가 디스크나 CPU를 고갈시키면 제어 평면도 함께 멈춘다. 설계상 의존이 없다는 것과 자원이 격리됐다는 것은 다르다 (`architecture.md` 3.4 텔레메트리 서비스)
- 텔레메트리 서비스 구현과 배포 (제어 서버와 별개 프로세스, 별개 포트)
- 연결 수립 시간 기록
- RTT 기록
- 패킷 손실 기록
- 지터 추정
- 터널 전송량 기록
- 세션 지속 시간 기록
- 텔레메트리 업로드를 전용 스레드와 유실 허용 큐로 분리 ([`concurrency.md`](concurrency.md) 6장
  텔레메트리 격리)
- 복수 네트워크 환경 테스트
- 성공한 NAT 통과 사례와 실패 사례 비교 (NAT 유형이 아니라 관측된 매핑 거동 기준)
- 실험 결과 시각화
- 한계 문서화
- [`experiments.md`](experiments.md) 작성

|------|------|

### 통계 설계

**아래 표가 Phase 9 의 통계 설계다.** 무엇을 한 번의 시행으로 세는지, 시행들이 독립인지,
불확실성을 어떻게 적는지를 측정 전에 고정한 것이다.

> **왜.** 정하지 않으면 나중에 나온 숫자가 무엇을 뜻하는지 아무도 말할 수 없다.

| 항목 | 정의 |
|------|------|
| 한 시행 | 클라이언트 시작부터 `CONNECTED` 도달 또는 실패 코드 기록까지. 세션 지속과 품질 측정은 `CONNECTED` 이후의 별도 구간이다 |
| 시행 사이 | 클라이언트를 내리고 새 `session_epoch` 로 다시 시작한다. 유휴 타임아웃(50s)보다 길게 쉬어 이전 NAT 매핑이 살아 있지 않게 한다 |
| 독립성 | **같은 날 같은 망에서 이어 돌린 10회를 독립 시행으로 부르지 않는다.** 공유기 상태와 ISP 경로가 공유되기 때문이다. 반복 측정으로 적고, 환경이 바뀐 것만 별개 조건으로 센다 |
| 대표값 | 중앙값과 사분위 범위. **평균과 표준편차를 쓰지 않는다.** RTT 와 수립 시간은 한쪽으로 치우쳐서 평균이 대표하지 못한다 |
| 성공률 | 비율과 함께 **분모 n 을 반드시 적는다.** 구간을 붙일 때는 Wilson 점수 구간을 쓴다. 정규 근사는 n 이 작고 비율이 1에 가까울 때 틀린 구간을 낸다 |
| 표본 수 | 환경마다 10회 이상. **통계적 충분성 주장이 아니다.** 한 학기에 접근할 수 있는 망에서 실행 가능한 최소치로 잡은 값이다. 그 한계를 [`experiments.md`](experiments.md)에 적고 숫자에 과한 의미를 붙이지 않는다 |

**이 설계가 보장하지 않는 것.** 이 설계는 모집단 추정이 아니다. 우리가 접근할 수 있었던
소수의 망에서 관측한 것을 적을 뿐이고, 다른 NAT 환경으로 일반화하지 않는다.

### 산출물

최종 보고서와 발표에 쓸 반복 가능한 실험 세트와 데이터.

### 검증

- 제어 평면 중단 시험 재실행: 텔레메트리가 켜진 상태에서 **제어 서버와 텔레메트리 서비스를 함께** 내려도 10분간 터널이 유지됨 (NFR-3). Phase 5 시험을 텔레메트리 포함 구성으로 다시 돌린다.

  > **왜.** 둘을 함께 내리는 것은 어느 쪽 장애든 터널을 끊지 않아야 하기 때문이다. 한쪽만 내리면 다른 쪽이 살아 있어 무엇이 터널을 지탱했는지 구분되지 않는다
- **텔레메트리 서비스 프로세스만** 중지한 상태에서 방 생성, 방 참가, `get_peers` 가 정상 응답함 (NFR-10). 분리 4의 판정이다 ([`architecture.md`](architecture.md) 3.4). 인스턴스를 내리는 시험이 아니다. 둘이 같은 EC2에 있으므로 인스턴스를 내리면 양쪽이 같이 죽어 아무것도 판정하지 못한다
- **제어 서버 프로세스만** 중지한 상태에서 지표 업로드가 정상 수신됨 (NFR-10). 분리 2의 판정이다. 텔레메트리가 식별자 유효성을 제어 평면에 묻는 구현이면 여기서 실패한다
- 큐가 가득 찬 상태에서 `[loop]`의 지표 기록이 블록되지 않고 `telemetry_queue_dropped` 가
  증가함. **크기와 버리는 방향도 같이 본다**
  - 링 크기는 [`concurrency.md`](concurrency.md) 6장 텔레메트리 격리가 소유한다. 이 시점의 값은
    256항목이다
  - 가득 차면 새 레코드를 버린다. 가장 오래된 것을 버리는 구현은 여기서 걸러야 한다

  > **왜.** 가장 오래된 것을 버리면 지표는 더 좋아 보이지만, 생산자가 소비자의 tail 을
  > 움직이는 것이다.
- 각 환경별로 최소 10회 반복 측정 데이터 확보. 위 통계 설계의 시행 정의와 간격을 지킨다
- 실패 건 전부에 단계별 코드와 NAT 환경 정보가 기록됨. 통제된 실패와 실제 환경의 실패를 **따로 집계한다** (A-2)
- **통제된 실패 두 시나리오를 실제로 돌린다** ([`spec.md`](spec.md) A-2)
  - (1) 호스트 방화벽에서 아웃바운드 UDP 를 막고 클라이언트를 띄우면 `STUN_DISCOVERY_FAILED`
    가 기록된다. 규칙은 시험 뒤 되돌린다
  - (2) 응답 없는 엔드포인트를 주입하면 `HOLE_PUNCH_TIMEOUT` 이 기록된다. Phase 4 의 같은
    시험을 이 구성에서 한 번 더 돌린다
  - 두 건은 실패 처리 경로의 증거이고 실패율의 증거가 아니다. 집계에 그렇게 적는다

  > **왜 (1) 이 Phase 2 와 다른 경로인가.** Phase 2 의 "응답하지 않는 주소" 시험은 주소가
  > 틀린 것이고 이쪽은 우리 송신이 막히는 것이다. 막힌 경로에서도 마감과 기록이 도는지는
  > 여기서만 본다.
- 성공률이 관측된 매핑 거동별로 집계됨. RFC 5389 Binding 결과만으로 NAT 유형을 단정한 서술이 없음
- 재현 시행 1회 통과. 통과 조건은 `spec.md` A-4 가 정한다
- 그래프와 한계 서술이 [`experiments.md`](experiments.md)에 포함됨

# 0001. 직접 연결 불가 대비책을 도입하지 않는다

- 상태: 채택
- 날짜: 2026-09-20
- 관련: [`../audit-history/design-audit.md`](../audit-history/design-audit.md) blocker 20, [`../plan.md`](../plan.md) 5장

## 맥락

설계 전면 점검에서 blocker 20이 가장 위험한 항목으로 꼽혔다.

> 가용한 두 가정망이 대칭형 거동이면 최소 성공이 불가능하고 대안이 없다. 릴레이는 Phase 9
> 이후 스트레치라 구제가 안 된다.

이것은 우리가 고칠 수 있는 결함이 아니다. ISP와 공유기가 정하는 조건이고, 학기 중반에
드러나면 되돌릴 시간이 없다. `plan.md` 5장은 실측 없이는 이 결정을 내릴 수 없다고 못박았고,
매핑 거동과 필터링 거동을 **둘 다** 재야 한다고 요구했다.

진단 도구([`../../../tools/nat-probe/`](../../../tools/nat-probe/))를 만들어 2026-09-17부터
2026-09-20까지 측정했다.

| 항목 | 값 |
|------|-----|
| 측정 건수 | 22 |
| 서로 다른 망 | 7곳 (T-Mobile 3, Comcast 3, KT 1) |
| 매핑 판정 | **22건 전부 `endpoint-independent`** |
| 펀치 결과 | **22건 전부 `success`** |
| 대칭형(목적지 의존) NAT | **0건** |
| 시도한 망 조합 | 6쌍. 실패 0쌍 |

필수 시험 토폴로지 (2) "서로 다른 가정망 2곳"은 2026-09-18에 **3회 연속** 성공했다.
회차 사이에 조건을 바꾸지 않았고, 종료 시각이 매 회차 1초 이내로 일치했다.

## 결정

**대비책을 도입하지 않는다. `spec.md`의 M-1과 M-4를 현재 문구 그대로 유지한다.**

- 릴레이는 Phase 9 이후 스트레치 목표로 둔다. P1으로 올리지 않는다
- 필수 시험 토폴로지 계약을 바꾸지 않는다
- direct-first 주장을 유지한다

**개정 불필요도 결정이다.** 기준을 고치면 실제로 달성한 것보다 약한 주장을 하게 된다.

**대신 재측정 게이트를 세 지점에 둔다.** Phase 4 착수, Phase 8 준비, 시연 직전이다.
시연 직전 한 번만으로는 늦다 — 그때 발견해도 대응할 시간이 없다. 자세한 근거는
"결과" 절에 있다. 이 결정의 근거는 특정 시점의 관측이고,
공유기 교체나 ISP 구성 변경으로 무효가 될 수 있다.

## 대안

| 안 | 내용 | 기각 사유 |
|----|------|-----------|
| A | NAT 에뮬레이션 테스트베드를 만들어 원하는 매핑 거동을 재현 | 실제 환경 증거가 확보됐으므로 불필요하다. 에뮬레이션은 분석 설득력이 더 낮고, M-4의 "지원 NAT 환경" 정의를 에뮬레이션 포함으로 넓혀야 한다 |
| B | 최소 릴레이를 P1으로 승격해 direct 실패 시 폴백 | direct가 6쌍 전부에서 성립했다. 폴백을 필수로 만들면 direct-first 주장이 약해지고 Phase가 하나 늘어난다. 구현 비용을 쓰는데 그것을 정당화할 실패 관측이 없다 |
| C | 모바일 핫스팟 등 제3의 경로를 필수 시험 토폴로지에 추가 | 필수 토폴로지 (2)가 이미 3회 연속으로 통과했다. 통제 불가능한 조건(통신사, 시각, 신호)을 필수 계약에 넣을 이유가 없다. 핫스팟은 best-effort로 남긴다 |

세 안 모두 **성공 기준을 함께 개정해야 한다**는 대가가 있었다. 실측이 기준을 만족시켰으므로
그 대가를 치를 이유가 사라졌다.

## 결과

**얻는 것.**

- Phase 1~9 구조가 그대로 유지된다. 새 Phase가 없다
- `spec.md`의 성공 기준과 `roadmap.md`의 Phase 구조를 고치지 않는다. `roadmap.md` Phase 8에
  재측정 작업 세 줄(Phase 4 착수, Phase 8 준비, 시연 직전)만 추가한다
- 릴레이 구현 비용을 쓰지 않는다

**받아들이는 위험.**

- **증거가 쪼개져 있다.** "NAT↔NAT + 다른 ISP + Windows↔Windows" 세 조건을 **한 측정 안에서**
  동시에 만족한 적이 없다. 조합으로는 전부 덮였고 시도한 6쌍이 모두 성공했지만, 단일 측정으로
  증명한 것은 아니다
- **다른 ISP 조합이 가정망 2곳이 아니다.** T-Mobile ↔ Comcast 조합은 한쪽이 모바일
  핫스팟이고, 이는 `spec.md` 123행 기준 best-effort 토폴로지다
- **표본이 미국 서부·중서부와 한국 1곳에 치우쳐 있다.** Comcast 3곳이 전체의 절반에 가깝다.
  다른 ISP에서 대칭형 NAT을 만날 가능성을 배제하지 못한다
- **대비책의 대비책이 없다.** 시연 당일 조건이 바뀌어 direct가 실패하면 남는 것이 없다.
  이것을 알고 받아들인다

**따라야 할 조치.**

1. **재측정 게이트를 세 지점에 둔다.** 시연 직전 한 번만으로는 늦다. 그때 조건이 바뀐 것을
   발견해도 대응할 시간이 없다.

   | 시점 | 이유 |
   |------|------|
   | Phase 4 착수 시 | 홀펀칭 구현을 시작하기 전. 여기서 조건이 바뀌었으면 설계를 되돌릴 시간이 있다 |
   | Phase 8 준비 시 | 시연 환경을 꾸리는 시점 |
   | 시연 직전 | 당일 확인 |
2. 실측 원본과 기록은 `.gitignore` 로 로컬 보관한다. 공인 IP가 들어 있고 레포가 public이다.
   **보고서에 첨부할 때도 그대로 내지 않는다.** 제출 시스템과 공유 링크에도 같은 노출이
   생긴다. **공인 주소는 되돌릴 수 없는 가명(`망 A`, `망 B`)으로 바꾸고 시각은 날짜
   단위까지만 남긴다.** IPv4 마지막 옥텟만 가리는 방식은 부족하고 IPv6에 적용되지도 않는다.
   그렇게 하지 않으려면 당사자 동의를 명시적으로 받는다. 어느 쪽을 택했는지 보고서에 적는다
3. 보고서에는 위 "받아들이는 위험" 네 항목을 그대로 싣는다. 증거의 한계를 감추지 않는다

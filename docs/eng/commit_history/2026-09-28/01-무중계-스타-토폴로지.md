# Chose a No-Relay Star Topology and 5 People per Room

## Changes

- `docs/{kor,eng}/decisions/0006-*.md` **new.** A maximum head count of 5 per room, a no-relay
  star, role generalization. 6 decisions and 3 dropped alternatives
- Put the two sections "no-relay star follow-up" and "waiting on the GUI scope decision" into
  `docs/kor/plan.md`, and changed the axes of the remaining work from two to three

**The living documents have not been fixed yet.** This commit leaves only the decision. The order
and the count of what has to be reflected are owned by `plan.md`.

## Decisions

**The topology was decided before the head count.** Raising the head count from 2 to 5 was not one
constant. The blast radius was investigated first, and of 135 findings 44 needed a design decision
again. How many sessions come into being decides the direction of those 44.

**The basis for choosing no relay is the structure of the target application.** Minecraft Java
multiplayer is client-server, and `spec.md` FR-12 writes that as a requirement. There is no game
traffic between players to begin with. A relaying star pays the price of making the host a router
and gains a feature that will not be used.

**We decided not to split the data plane by role.** Splitting it would make two code paths and
double the tests. Generalizing to the session list writes the shutdown rule, the transmit check
order, the counter unit, and the record unit once. A player becomes the case where the list has
1 entry.

## Investigation

It was run in three parts and the artifacts are kept outside the repository. Only the numbers are
written here.

| Investigation | Result |
|------|------|
| 2 -> 5 blast radius | 135 findings. 5 constants, 86 descriptions, 44 design |
| GUI blast radius | 70 findings. 16 descriptions, 34 design, 20 conflicts |
| Re-grading after the star was fixed | Of 78 design findings, 2 resolved, 32 narrowed, 44 left. 8 new questions |
| The price of role generalization | 9 in code, 4 in tests (of 83), 51 in documents |

**Fixing the star actually finished only 2 design questions.** The mechanism behind the 32 narrowed
ones is one. The player-side path has 1 session, so the current 2-peer descriptions still hold and
only the host side has to be decided again.

**The price is not code but documents.** Of the 12 client modules `architecture.md` 3.1 lists, 2
are in the repository, and of the 6 that carry session state, 0 are. The session state machine,
`session_epoch`, the replay-prevention bitmap and the routing table are not one line in
`client/src/`. So on the code side it is not the cost of fixing but the cost of writing it
differently from the start.

## What the Generalization Exposed

`protocol.md` 4.5 writes that the duplicate-suppression state is kept "per remote epoch". With one
session that is correct. With several sessions the state mixes when two peers draw the same random
epoch. The key has to be `(peer_id, epoch)`. This place is in the follow-up list of `plan.md`.

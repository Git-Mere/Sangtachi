# Store layer and store test harness of the control server

## Why

This is the first step of item 1 of "Next to do" in `plan.md` (implement the control server with DynamoDB
local). Following the order agreed with the repository owner, the store layer was made first. `ops.dispatch`
and the accept loop are the next step and rely on this interface.

## What was done

| What | Content |
|------|---------|
| `controlplane/store.py` | The `boto3` calls and all the 6.3 condition expressions. Each call is tried only once. Walking the addresses and redrawing are the job of `ops`. The injection point `on_write(phase, label, sk)` before and after writes |
| Store test harness | `pytest --store`. The endpoint is only from a loopback allowlist (`127.0.0.1`, `localhost`, `::1`). A new table per test. An isolation fixture applied to every test removes AWS variables, uses an empty config file, fake keys, IMDS off, removes proxies, and clears `boto3.DEFAULT_SESSION` |
| `tests/mutate.py` | `--store`, `-j N`. For each mutation, only the `kills` rows are run once on the original and once on the mutation. If the original does not pass those rows on their own, it is `ERROR` |
| `ops.reclaim_verdict` | Step 6 `keys_unreadable` of the 4.6 judgement order |

The work was done by one worker (`worker-store`), and the director edited the documents.

## What was not added as mutations because it cannot be observed

The worker ran eight of them separately and confirmed all were `SURVIVED`. The director checked the reasons.

- Five places of `attribute_exists(pk)` in the condition expressions. Another clause of the same condition
  is already false on a missing item. The document wrote that clause, so it was not removed from the code
- The line that skips `ROOM` in renewal. It only writes the same value once more
- Paging of the `Query`. One room is 15 items and does not exceed 1MB, so it cannot be produced locally

The three mutations that remove `ConsistentRead` are caught by a device that records the request
arguments. DynamoDB local did not reveal a consistency difference. The code-reading judgement of chapter 9
stays as it is.

## What was newly learned about DynamoDB local

- It accepts only letters and digits in the access key ID. Any other character gives
  `UnrecognizedClientException`
- It actually runs TTL deletion. If a test's time is set in the past, the item disappears. Test times are
  kept near the real wall clock
- When table creation bursts at the same time, it gives `InternalFailure` (500). Reproduced by running one
  test file eight times at once. Only the admin client was wrapped in standard retry (5 times). After that
  the same eight all passed

## Made the mutation runner parallel

A store mutation takes about 35 seconds each, so the whole run took over an hour. The repository owner
asked about parallelising it.

- For each mutation, only the `kills` rows are run. The verdict looks only at those rows, so the verdict is
  the same
- Running rows on their own makes a row that passes only when the whole file runs give a false `KILLED`.
  So for each mutation, the same rows are also run on their own on the original
- All 323 took about three and a half minutes with `--store -j 8`

The first parallel run gave 11 `ERROR`s, caused by the `InternalFailure` above. One `PARTIAL`
(`create-lease-seconds`) was a wrong `kills` in the mutation. The `PAIR#` of that test gets its `ttl` from a
room put in beforehand, so it has nothing to do with the `create_room` mutation. That row was taken out of
`kills`.

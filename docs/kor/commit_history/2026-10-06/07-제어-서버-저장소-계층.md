# 제어 서버의 저장소 계층과 저장소 시험 하네스

## 왜 했나

`plan.md` 다음에 할 일 1번(제어 서버를 DynamoDB local 로 구현)의 첫 단계다. 저장소 소유자와 정한
순서대로 저장소 계층을 먼저 만들었다. `ops.dispatch` 와 수락 루프는 다음 단계이고 이 인터페이스에
기댄다.

## 무엇을 했나

| 무엇 | 내용 |
|------|------|
| `controlplane/store.py` | `boto3` 호출과 6.3 조건식 전부. 한 호출에 한 번만 시도한다. 주소 순회와 재추첨은 `ops` 몫이다. 쓰기 앞뒤의 주입점 `on_write(phase, label, sk)` |
| 저장소 시험 하네스 | `pytest --store`. 엔드포인트는 루프백 허용 목록(`127.0.0.1`, `localhost`, `::1`)만. 시험마다 새 테이블. 모든 시험에 걸리는 격리 픽스처가 AWS 변수 제거, 빈 설정 파일, 가짜 키, IMDS 끔, 프록시 제거, `boto3.DEFAULT_SESSION` 비우기를 한다 |
| `tests/mutate.py` | `--store`, `-j N`. 변이마다 `kills` 행만 원본과 변이로 한 번씩 돌린다. 원본이 그 행을 단독으로 통과하지 못하면 `ERROR` |
| `ops.reclaim_verdict` | 4.6 판정 순서 6번 `keys_unreadable` |

작업은 작업자 하나(`worker-store`)가 했고 문서는 디렉터가 고쳤다.

## 작업자가 찾은 문서 빈자리

아홉 건을 문서에 먼저 정했다.

| 절 | 정한 것 |
|----|---------|
| 6.3 취소 사유 | `create_room` 은 1번 다음 5번. `PEER#`·`VIP#` 만 실패하면 `internal`. 조건 실패와 다른 사유가 섞이면 `NONCE#` 만 이기고 나머지는 `internal` |
| 6.3 `ROOM` | 첫 `expires_at_ms` 는 `now + ROOM_LEASE_S * 1000` |
| 6.3 `PEER#` | `candidates` 는 첫 등록 전에는 쓰지 않는다 |
| 6.3 | 방 파티션의 모르는 `sk` 는 `internal` |
| 6.5 | 임대 갱신이 `NONCE#` 의 `ttl` 은 밀지 않는다. 파티션이 달라 `Query` 에 나오지 않는다 |
| 4.6 판정 순서 | 6번. 지울 키(`virtual_ip`, `client_nonce`)가 문자열이 아니면 `keys_unreadable` |
| 7.2 | 트랜잭션 밖의 저장소 오류는 포괄 처리가 받고 `internal_error` 를 올린다 |
| 7.6 | 하네스가 사용자의 AWS 프로파일과 설정 파일을 읽지 않게 막는다 |
| 10장 | 서버의 DynamoDB 호출 시간 제한과 재시도 횟수는 배포한 테이블의 지연을 잰 뒤 정한다. `roadmap.md` Phase 3 배포 작업에 걸었다 |

## 관측할 수 없어 변이로 넣지 않은 것

작업자가 여덟 개를 따로 돌려 전부 `SURVIVED` 를 확인했다. 디렉터가 이유를 확인했다.

- 조건식의 `attribute_exists(pk)` 다섯 자리. 같은 조건의 다른 절이 없는 항목에서 이미 거짓이다.
  문서가 그 절을 적었으므로 코드에서는 지우지 않았다
- 갱신에서 `ROOM` 을 건너뛰는 줄. 같은 값을 한 번 더 쓸 뿐이다
- `Query` 의 페이지 넘김. 방 하나가 15항목이라 1MB 를 넘지 않아 로컬에서 만들 수 없다

`ConsistentRead` 를 지운 변이 셋은 요청 인자를 기록하는 장치가 잡는다. DynamoDB local 이 일관성
차이를 드러낸 것이 아니다. 9장의 코드 읽기 판정은 그대로 남는다.

## DynamoDB local 에서 새로 안 것

- 액세스 키 ID 에 영문자와 숫자만 받는다. 다른 문자가 있으면 `UnrecognizedClientException`
- TTL 삭제를 실제로 돌린다. 시험 시각을 과거로 두면 항목이 사라진다. 시험의 시각은 실제 벽시계
  근처로 둔다
- 테이블 생성이 동시에 몰리면 `InternalFailure`(500)를 낸다. 시험 파일 하나를 여덟 개 동시에
  돌려 재현했다. 관리용 클라이언트만 표준 재시도(5회)로 감쌌다. 그 뒤 같은 여덟 개가 전부
  통과했다

## 변이 실행기를 병렬로 바꿨다

저장소 변이가 하나에 약 35초라 전체가 한 시간을 넘었다. 저장소 소유자가 병렬화를 물었다.

- 변이마다 `kills` 행만 돌린다. 판정이 그 행만 보므로 판정은 같다
- 행을 따로 돌리면 파일째 돌 때만 통과하는 행이 거짓 `KILLED` 를 낸다. 그래서 변이마다 같은 행을
  원본으로도 단독으로 돌린다
- 전체 323건이 `--store -j 8` 로 약 3분 반 걸렸다

첫 병렬 실행에서 `ERROR` 11건이 나왔고 원인은 위 `InternalFailure` 였다. `PARTIAL` 1건
(`create-lease-seconds`)은 변이의 `kills` 가 틀렸다. 그 시험의 `PAIR#` 는 미리 넣은 방에서 `ttl`
을 얻으므로 `create_room` 의 변이와 무관하다. 그 행을 `kills` 에서 뺐다.

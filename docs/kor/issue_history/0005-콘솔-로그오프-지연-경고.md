# 0005. 로그오프 때 콘솔 클라이언트가 지연 경고를 남겼다

- 상태: 미해결
- 발견: 2026-10-31
- 관련: [`../concurrency.md`](../concurrency.md) 7장 종료,
  [`../commit_history/2026-10-31/01-phase-8-같은-기기-확인-결과.md`](../commit_history/2026-10-31/01-phase-8-같은-기기-확인-결과.md),
  [`../commit_history/2026-11-01/03-콘솔-로그오프-지연-경고-정리.md`](../commit_history/2026-11-01/03-콘솔-로그오프-지연-경고-정리.md)

## 증상

Phase 8 같은 기기 확인에서 GUI 호스트와 콘솔 플레이어(Release, `--no-adapter`)를 한 기기에 띄운 채 로그오프했다.

- System 로그 `winsrvext` 100: `sangtachi_client.exe is delaying system shutdown after 5000 milliseconds`
- 플레이어 로그에 `attempt.end reason=shutdown` 이 없다. 세션은 호스트의 `CLOSE` 로 끝났다

2026-10-01 에도 Debug 빌드 콘솔이 같은 이벤트를 남겼다. 그래서 콘솔이 [`concurrency.md`](../concurrency.md) 7장 종료대로
정리했는지 의심했다.

## 조사

| 의심한 것 | 본 것 | 판단 |
|-----------|-------|------|
| 콘솔이 로그오프 때 `shutdown()` 을 돌지 않았다. `attempt.end reason=shutdown` 이 없다 | 플레이어는 호스트의 `CLOSE` 를 먼저 받아 `attempt.end reason=closed` 를 내고 로비로 갔다. `Lobby::on_shutdown` 은 로비에서 그 줄을 내지 않는다. 그 뒤에 `peer_id` 없는 프로세스 카운터 62줄이 있다. `shutdown()` 의 4번 단계다. 정상으로 끝난 다른 `--no-adapter` 플레이어 로그도 같은 모양으로 끝난다 | 아니다. `shutdown()` 은 돌았다 |
| 표준 입력이 끝나서 종료했다 | `run_console_reader` 는 표준 입력이 끝나면 읽기를 멈출 뿐 종료를 걸지 않는다 | 아니다. 종료 이벤트를 신호한 것은 콘솔 제어 핸들러로 본다 |
| user32 나 gdi32 를 불러와 핸들러가 불리지 않았다. `SetConsoleCtrlHandler` 문서가 이 경우 로그오프와 시스템 종료 신호에 핸들러가 불리지 않는다고 적는다 | 실행 파일의 정적 가져오기에 user32, gdi32 가 없다. ADVAPI32 의 지연 가져오기에 user32 가 있을 뿐이다. Debug 콘솔을 `--no-adapter` 로비로 띄운 프로세스의 모듈 24개에도 없다 | 본 증거로는 뒷받침되지 않는다. 그 로그오프 때 Release 프로세스가 실제로 불러온 모듈은 보지 않았다 |

`HandlerRoutine` 문서는 `CTRL_LOGOFF_EVENT` 를 서비스만 받고 대화형 프로그램은 로그오프 때 그 전에 종료된다고 적는다.
그렇다면 이번 종료를 건 신호는 `CTRL_LOGOFF_EVENT` 가 아니라 콘솔이 닫히며 온 `CTRL_CLOSE_EVENT` 일 수 있다. 핸들러가 받은 신호
종류를 로그에 남기지 않아 가를 수 없다. 문서 원본은 [HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine) 과
[SetConsoleCtrlHandler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler) 다.

## 원인

**확인한 것.** 로그오프 때 콘솔 플레이어는 `shutdown()` 을 돌았다. 로그의 프로세스 카운터 출력이 근거다.

**모르는 것.** 핸들러가 받은 신호가 `CTRL_LOGOFF_EVENT` 인지 `CTRL_CLOSE_EVENT` 인지, `winsrvext` 100 이 왜 5000ms 뒤의 지연 경고를 냈는지다. 실제로 얼마나 늦췄는지도 모른다.
로그 줄에 시각이 없어 이 로그로는 가를 수 없다.

## 처리

더 조사하지 않는다. 저장소 소유자 결정이다. 배포물은 GUI 뿐이고 콘솔의 정리는 돌았다. 코드와 사양은 바꾸지 않았다.

다시 볼 때 쓸 길은 핸들러가 받은 신호 종류를 로그에 남기고 콘솔만 띄운 채 로그오프하는 것이다.

## 결과

`plan.md` 가 갖는다.

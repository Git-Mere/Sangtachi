# 0002. 엔드포인트 학습으로 NAT 리바인딩을 복구하지 않는다

- 상태: 채택
- 날짜: 2026-09-20
- 관련: [`../protocol.md`](../protocol.md) 10.4, 9.5, [`../design-audit.md`](../design-audit.md) blocker 12

## 맥락

`protocol.md` 10.4는 고정 지명 대신 **학습**을 쓰기로 했고, 그 이유 셋 중 하나가 이것이었다.

> **NAT 리바인딩**: 매핑이 바뀌어도 epoch는 그대로이므로, 고정 방식에서는 재협상 계기가 없어
> 유휴 타임아웃까지 기다려야 한다.

10.4 (c)는 후보 집합 밖 주소에서 온 패킷을 경로 검증 뒤에 수용하도록 정했다. 그 절차는
**"후보 집합에 없는 주소에서 패킷이 오면"** 으로 시작한다.

2026-09-20 측정에서 그 전제를 직접 시험했다. 펀치 성립 후 **새 소켓(새 출발지 포트)** 에서
상대에게 쏘고, 상대가 받는지 봤다.

| 측정 | 호스트 OS | 호스트 방화벽 | 결과 |
|------|-----------|---------------|------|
| WA ↔ WA | Windows 11 양쪽 | 인바운드 기본 `Block`, `python.exe` 규칙 없음 | `blocked` 양방향 |
| WA ↔ MI | Windows 11 / **macOS** | macOS는 Application Firewall이 기본 꺼짐 | `blocked` 양방향 |
| 핫스팟 ↔ WA | **Linux** / Windows 11 | Linux는 `/etc/ufw/ufw.conf` 가 `ENABLED=no` (직접 확인) | `blocked` 양방향 |

**6건 전부 `blocked`다.** 매 측정에서 동기화가 성립했고(`sync.peer_ready: true`), 상대가
실제로 20발을 쐈으며(`peer_sent_reported: 20`), 도착은 0발이었다.

**호스트 방화벽 필터링이 없다고 보이는 기기에서도 막혔다.** 그러면 원인은 호스트가 아니라 그 앞, 즉 **NAT의
포트 제한 필터링**일 가능성이 가장 높다. 우리가 보낸 적 없는 출발지 포트에서 오는 패킷을
NAT이 버린다는 설명이 관측 전부와 일치한다.

**단정하지는 않는다.** macOS 쪽은 기본값에 근거한 추론이고 직접 조회하지 않았다. Linux 쪽은
`ufw` 가 꺼진 것만 확인했고 root 권한이 없어 `nft`/`iptables` 규칙 전체는 보지 못했다.
양쪽 패킷 캡처도 하지 않았다. 관측은 포트 제한 NAT과 **일치할 뿐**이다.

**원인이 무엇이냐에 따라 할 수 있는 일이 다르다.** 상대 NAT이나 상대 호스트의 필터링이
원인이면 우리 쪽에서 할 수 있는 것이 없다. 반면 **우리 Windows 방화벽이 원인이면 우리
클라이언트가 규칙을 등록해 자기 쪽 수신을 고칠 수 있다.** 그래서 이 결정은 잠정이고,
아래에 뒤집는 조건을 적었다.

따라서 10.4 (c)의 전제가 실제 환경에서 성립하지 않는다. 절차의 1번(새 주소를 잠정 경로로
기록)이 시작되지 않으므로 2번 이후가 돌지 않는다.

9.5 재협상도 같은 이유로 막힌다. 재협상은 다른 epoch의 `HELLO` 수신이 계기인데, 리바인딩한
상대의 `HELLO`도 새 출발지 포트에서 오기 때문이다.

## 결정

**v1은 엔드포인트 학습으로 NAT 리바인딩을 복구한다고 보장하지 않는다. 그 사실을
`protocol.md`에 명시한다.** 정확히는 **시험한 거동(출발지 포트만 바뀌고 관측된 필터링에
걸리는 경우)과 일치하는 리바인딩**에 대해 보장하지 않는다. 실제 리바인딩을 일으켜 시험하지
않았으므로 "모든 리바인딩에서 실패한다"고 주장하지 않는다.

- 10.4 (c) 경로 검증은 **삭제하지 않는다.** 두 가지 이유다. **위조 출발지 방어**라는 보안
  역할이 남고(후보 집합 밖 주소에서 패킷이 도착하기만 하면 그 검증이 필요하다), **주소
  제한(restricted cone) 필터링을 쓰는 NAT에서는 그 패킷이 도착할 수 있다**
- 다만 **리바인딩 복구를 보장하지 않는다**고 적는다. 10.4가 지명 대신 학습을 고른 세 이유 중
  이 하나는 실측으로 무효가 됐다. 나머지 둘(같은 NAT 뒤 교착, 비대칭 지명)은 유효하므로
  학습 방식 자체는 유지한다
- 리바인딩이 일어나면 양쪽이 유휴 타임아웃(50s)에 도달해 `TUNNEL_DROPPED`로 세션이 끝난다.
  `protocol.md` 9.6에 따라 **재시도를 한다면** `IDLE`부터 새 시도로 시작하며 제어 평면을 다시
  거친다. **다만 자동 재시도 여부는 문서에 정해져 있지 않다.** 지금 확인할 수 있는 것은
  "세션이 끝난다" 까지이고, 그 뒤가 자동인지 사람이 다시 실행해야 하는지는 미정이다

**클라이언트가 방화벽 규칙을 등록하지 않는다.** 원인이 NAT일 가능성이 높아 효과가 없다.
**잠정 결정이다.** 아래 재검토 조건을 본다.

**이 결정을 뒤집는 조건.** 옵션 a를 기각이 아니라 **보류**로 둔 이유다.

방향별로 보면 원인이 다르게 좁혀진다.

| 방향 | 막을 수 있는 것 | 좁혀진 정도 |
|------|-----------------|-------------|
| Windows -> macOS / Linux | 상대 NAT, 상대 호스트 방화벽 | 상대 방화벽이 꺼져 있을 가능성이 높아 **NAT 쪽으로 기운다.** macOS는 기본값 추론이고 Linux는 `ufw` 만 확인했으므로 호스트 필터링이 배제된 것은 아니다 |
| macOS / Linux -> Windows | 우리 NAT, 우리 Windows 방화벽 | **둘 다 남는다. 좁혀지지 않았다** |

즉 "우리 Windows가 받는 방향"에서는 방화벽이 원인일 가능성이 살아 있다. 그쪽이 원인이라면
클라이언트가 인바운드 규칙을 등록해 **자기 쪽 수신은** 고칠 수 있다. 상대 NAT이 여전히 막으면
전체로는 해결되지 않지만, 최소한 우리 쪽 요인은 제거된다.

**결정적 시험.** 방화벽을 끄지 않는다. **범위를 좁힌 임시 인바운드 규칙 하나를 넣었다 빼는
쪽이 안전하고 더 정확하다.** 프로필을 끄면 어느 프로필이 활성인지에 따라 엉뚱한 것을 끄게 되고,
되돌릴 때 원래 값을 덮어쓸 수 있다.

관리자 PowerShell에서 아래를 한다. 포트를 고정해야 규칙을 걸 수 있다.

```powershell
# 관리자 PowerShell.
$group = "natprobe-unsolicited-test"     # 이 시험 전용 식별자

# 0. 이전 실행이 남긴 규칙을 먼저 치운다. 중단·재부팅이 finally 를 건너뛸 수 있다.
#    이름 와일드카드가 아니라 전용 Group 으로 찾는다.
#    이 기기에서 같은 시험이 동시에 돌고 있지 않을 때만 실행한다.
Get-NetFirewallRule -Group $group -ErrorAction SilentlyContinue | Remove-NetFirewallRule

# 1. 주소를 입력받는다. 명령줄에 적지 않는다 — PowerShell 기록에 영구히 남는다.
#    Read-Host 는 "Any" 나 CIDR 도 그대로 받으므로 공인 유니캐스트 IPv4 인지 검사한다.
$raw  = Read-Host "상대 공인 IP"
$peer = [System.Net.IPAddress]::Parse($raw)      # 형식이 아니면 여기서 예외
if ($peer.AddressFamily -ne 'InterNetwork') { throw "IPv4 주소여야 한다: $raw" }
$b = $peer.GetAddressBytes()
$notPublic =
  ($b[0] -eq 0) -or ($b[0] -eq 10) -or ($b[0] -eq 127) -or ($b[0] -ge 224) -or
  ($b[0] -eq 169 -and $b[1] -eq 254) -or
  ($b[0] -eq 172 -and $b[1] -ge 16  -and $b[1] -le 31)  -or
  ($b[0] -eq 192 -and $b[1] -eq 168) -or
  ($b[0] -eq 100 -and $b[1] -ge 64  -and $b[1] -le 127) -or
  ($b[0] -eq 192 -and $b[1] -eq 0   -and ($b[2] -eq 0 -or $b[2] -eq 2)) -or
  ($b[0] -eq 198 -and ($b[1] -eq 18 -or $b[1] -eq 19)) -or
  ($b[0] -eq 198 -and $b[1] -eq 51  -and $b[2] -eq 100) -or
  ($b[0] -eq 203 -and $b[1] -eq 0   -and $b[2] -eq 113)
if ($notPublic) { throw "공인 유니캐스트 IPv4 가 아니다: $raw" }

$rule = $null
try {
    $rule = New-NetFirewallRule -DisplayName "natprobe-temp-$((New-Guid).Guid)" `
      -Group $group -Direction Inbound -Protocol UDP -LocalPort 47000 `
      -RemoteAddress $peer.IPAddressToString -Action Allow -Profile Any
    # 레포 루트에서 실행한다고 가정한다. 경로를 명시해 작업 디렉터리에 의존하지 않는다.
    py .\tools\nat-probe\natprobe.py punch --label us-home --port 47000 --unsolicited
}
finally {
    # 이름이나 Group 이 아니라 **그 객체**를 지운다. 동시 실행이 있어도 안전하다.
    if ($rule) { Remove-NetFirewallRule -InputObject $rule }
}

# 2. 확인. 아무것도 출력되지 않아야 한다.
Get-NetFirewallRule -Group $group -ErrorAction SilentlyContinue
```

**규칙은 영구 규칙이다.** `New-NetFirewallRule` 은 기본으로 디스크에 남는 규칙을 만든다.
측정 중 프로세스가 죽거나 창을 닫거나 재부팅하면 `finally` 가 돌지 않아 규칙이 남는다.
그래서 0번을 매번 먼저 돌리고 2번으로 확인한다. **2번에서 출력이 있으면 지우고 다시 확인한다.**

주소 검사는 `natprobe.py` 의 `classify_nat` 이 쓰는 것과 같은 규칙이다. 사설, 루프백,
링크 로컬, CGNAT, 문서용, 벤치마킹, 멀티캐스트를 전부 거부한다. 오타 하나로 넓은 규칙이
만들어지는 것을 막는다.

`Read-Host` 를 쓰는 이유는 상대 공인 IP를 명령 기록에 남기지 않기 위해서다. 이 레포의
실측 원본을 커밋하지 않기로 한 것과 같은 이유다([ADR 0001](0001-직접-연결-대비책-미도입.md)).

**이 시험 자체가 관리자 권한을 요구한다는 점도 관측값이다.** 옵션 a를 채택하면 클라이언트가
같은 일을 해야 하고, 그 비용이 여기서 그대로 드러난다.

| 결과 | 해석 | 조치 |
|------|------|------|
| 규칙을 넣어도 `blocked` | **기본 인바운드 정책은 원인이 아니다.** 방화벽 전체를 배제하지는 못한다 — 명시적 차단 규칙이 허용 규칙보다 우선하고, 제3자 보안 제품의 필터링도 남는다. NAT 쪽으로 더 기울지만 확정은 아니다. 확정하려면 유효 WFP 규칙 확인이나 양쪽 패킷 캡처가 필요하다 | 이 ADR 유지. 추가 확인은 선택 |
| 규칙을 넣으니 `allowed` | **Windows 방화벽이 원인이었다.** 이 ADR을 개정한다 | 옵션 a를 다시 검토하고, 관리자 권한 요구를 `spec.md`와 후속 3번에 반영한다 |

이 시험을 하기 전까지 **"클라이언트가 방화벽 규칙을 등록하지 않는다"는 잠정 결정이다.**

## 대안

| 안 | 내용 | 기각 사유 |
|----|------|-----------|
| a | 클라이언트가 인바운드 허용 방화벽 규칙을 등록 | **보류.** 기각이 아니다. 방화벽 필터링이 없다고 보이는 호스트(macOS, Linux)에서도 막혔으므로 원인은 NAT일 가능성이 높고, 그렇다면 규칙 등록은 효과가 없다. 관리자 권한이 필요해져 blocker 11의 부담이 커지고 `spec.md`의 "수동 포트 포워딩 없이" 주장에 단서가 붙는 비용도 있다. **다만 Windows 수신 방향에서는 방화벽이 원인일 가능성이 배제되지 않았다.** 아래 재검토 조건 참조 |
| b | 상대 포트 범위를 예측해 여러 포트로 동시 송신 | 목적지 의존 매핑의 포트는 예측 신뢰도가 낮다. 트래픽이 늘고, 10.1의 후보 위생 규칙(무제한 후보로 제3자에게 쏘지 않는다)과 충돌할 소지가 있다 |
| c | 제어 평면에 리바인딩 재협상 트리거를 추가 | Phase 3 범위가 커진다. 리바인딩 자체가 30분 시연에서 드물고, 15s keepalive가 매핑을 유지한다. v1 범위 밖으로 둔다 |
| d | 10.4 (c)를 통째로 삭제 | 경로 검증은 위조 출발지로 트래픽을 제3자에게 돌리는 공격을 막는 장치다(10.4의 보안 논증). 삭제하면 그 방어가 사라진다 |

## 결과

**얻는 것.**

- 관리자 권한 요구사항이 생기지 않는다. `spec.md`의 "수동 포트 포워딩 없이" 주장이 유지된다
- 후속 3번(Windows 사전조건 절)에 방화벽 규칙 등록 항목이 추가되지 않는다
- 문서와 실제 거동이 일치하게 된다

**받아들이는 위험.**

- **리바인딩이 일어나면 최대 50초 뒤 세션이 끊어진다.** 50초는 **실패를 감지하는 데** 걸리는
  상한이지 복구까지의 시간이 아니다. 자동 재시도가 정의되지 않았으므로(위 결정 3번)
  **복구 시간에는 상한이 없다.** 30분 시연 중 리바인딩 발생 확률은 낮지만 0이 아니다
- **관측이 전부 포트 제한 필터링과 일치했다.** 확정된 것은 아니다. 주소 제한(restricted cone) NAT을 쓰는 환경에서는
  10.4 (c)가 정상 동작할 수 있다. 이 결정은 "보장하지 않는다"이지 "불가능하다"가 아니다
- **친구 기기의 macOS 방화벽 상태를 직접 확인하지 않았다.** Linux 쪽은 확인했고 macOS는 기본값에
  근거한 추론이다. 확인하면 근거가 하나 더 붙는다
- **Linux 쪽도 root 권한이 없어 `nft`/`iptables` 규칙 전체는 보지 못했다.** `ufw` 가 꺼져 있다는
  것만 확인했다

**따라야 할 조치.**

1. `protocol.md` 10.4에 전제와 한계를 적는다. 리바인딩 복구를 보장하지 않는다고 명시한다
2. Phase 4 keepalive 실측에서 매핑 수명을 재고, 15s 간격이 리바인딩을 실제로 막는지 확인한다
3. **`TUNNEL_DROPPED` 뒤 자동 재시도 여부를 정한다.** 이 ADR을 쓰면서 드러난 공백이다.
   `protocol.md` 9.6은 "재시도는 `IDLE`부터 시작한다"만 정하고 누가 언제 개시하는지는
   정하지 않았다. 리바인딩 복구를 전체 재시도에 맡기기로 한 이상 이 공백을 메워야 한다
4. 보고서에 이 관측을 싣는다. "학습 방식을 골랐지만 그 이유 중 하나는 실측으로 무효가 됐다"는
   설계 과정의 정직한 기록이다

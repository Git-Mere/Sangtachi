# Mapping Lifetime Measurement at a Friend's Home

## Why

The `KEEPALIVE` rule in `protocol.md` chapter 11 Timers (`interval × 3 < smallest measured lifetime`) uses the
smallest value across measured networks. The first measurement was only this machine's home Wi-Fi (`[58, 60)`
seconds). The same tool was run at the repository owner's friend's home.

## Measurement

Conditions. The friend's machine, the friend's home Wi-Fi. Its public IP differs from this machine's (the security
group rule was opened to that `/32`). Router model, firewall prompt answer, and VPN were not reported. The responder
was `natlife.py` from commit `d122719`, uploaded again to EC2. The repository owner put the result JSON in
`tools/nat-lifetime/results/` (ignored).

| Run | Delays (s) | Arrived | Verdict |
|------|------|------|------|
| check | 2 | All | Check passed |
| friend-r1, r2, r3 | 5, 20, 30, 40, 45, 50, 55, 60, 70, 80, 90, 100, 110, 120, 135, 150, 165, 180, 210, 240, 270, 300 | All | `300` or more all three times |

- Every trial of the three measurement runs got 6/6 warm-up ACKs, and the check trial got 2/2. Every final ACK was
  "scheduled". Zero refusals and zero arrivals outside the window
- The responder log shows both `scheduled` and `late_sent` at 67 (1 check + 66)
- **The friend's home path is 300 seconds or more.** The upper bound was not observed. The list was shorter than the
  responder cap (600 seconds)

## Verdict

The smallest measured value stays at this machine's home, 58 seconds. 15 seconds gives 45 seconds and keeps the rule.
The 15 and 50 seconds in `protocol.md` chapter 11 stay. The two homes differ a lot, so if the demo peer is on another
network, that network is measured too.

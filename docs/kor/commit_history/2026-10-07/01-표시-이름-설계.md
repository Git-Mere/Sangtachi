# 표시 이름 설계 (FR-16, ADR 0015)

## 왜 했나

`plan.md` 다음에 할 일의 첫째인 Phase 4 착수 전 결정 가운데 하나다. 호스트 쪽 쌍 실패의 `FAIL` 줄이
어느 플레이어의 것인지 담는지를 정해야 했다(`concurrency.md` 7장 로비가 미결로 두었다).

후보는 `peer_id` 와 `virtual_ip` 였다. 저장소 소유자가 둘 다 사람이 알아보기 어렵다고 보고, 방에
들어갈 때 이름을 정해 그 이름을 보이자고 했다. 같이 정한 것은 넷이다.

| 질문 | 결정 |
|------|------|
| 문자와 길이 | ASCII 영문자, 숫자, 밑줄. 1~16자 |
| 겹치는 이름 | 서버가 `name_taken` 으로 거부한다. 대소문자는 무시하고 비교한다 |
| 필수인가 | 필수. 기본값을 두지 않는다 |
| 호스트도 이름을 갖는가 | 갖는다 |

설계를 문서로만 정했다. 코드는 `roadmap.md` Phase 4 의 표시 이름 작업이다.

## 중요한 결정

- **이름은 표시 전용이다.** 수신 검증, 라우팅, 기록 짝짓기는 `peer_id` 를 쓴다. v1 의 `ROSTER` 는
  인증하지 않으므로 화면의 이름은 위조될 수 있다
- **`FAIL` 줄의 상대 칸은 늘 있다.** 세션 코드 셋이면 상대 이름이고 나머지는 `-` 다. `-` 는 이름 문자
  집합에 없다
- **유일성은 `NAME#` 항목의 조건부 쓰기다.** 취소 사유 순서에서 `VIP#` 보다 먼저다. 그래서 이름이 겹친
  참가가 풀을 돌지 않는다
- **회수는 `NAME#` 를 `peer_id` 로 찾는다.** `PEER#` 의 `name` 으로 키를 만들면 그 값을 읽을 수 없을
  때 `NAME#` 가 남아 방이 끝날 때까지 이름을 막는다. 리뷰가 찾았다
- **이름은 자리와 함께 풀린다.** 프로세스가 죽은 플레이어는 호스트의 유휴 타임아웃 뒤에야 같은 이름으로
  다시 들어온다. 그동안은 다른 이름을 쓴다
- **방 하나의 항목 상한이 15에서 20으로 늘었다.** 7.6 의 최악값을 다시 계산했다. 잰 값은 그 전의
  것이라고 적었다
- **`--name` 은 Phase 4 이후 필수다.** "Phase 3 이후" 로 적으면 끝난 Phase 3 바이너리가 거꾸로
  기동 입력 계약을 어기게 된다

## 검증

| 무엇 | 결과 |
|------|------|
| 한국어 쪽만 고친 뒤 `python tools/docgate/docgate.py` | 미러와 parity 만 실패. 끊긴 링크 없음 |
| 시나리오 추적 1 | 이름이 겹친 참가. `join_room` → 7.3 1번 형식 통과 → 트랜잭션의 `NAME#` 실패 → 취소 사유 3번 `name_taken` → 클라이언트 3.5 8번, 8.3 확정 오류 → `FAIL CONTROL_PLANE_EXCHANGE_FAILED - ...` → 로비 → `name` 으로 바꾸고 다시 `join` |
| 시나리오 추적 2 | 호스트의 한 쌍 펀치 실패. 상대 이름은 `host_report` 응답의 `peers` 에서 받았다 → `FAIL HOLE_PUNCH_TIMEOUT <이름> ...` → 방에 남음 → `departed` → 회수가 `peer_id` 로 `NAME#` 를 지움 |

# Captures C6-C9: harness scene modes and the run

## Why

The `roadmap.md` Phase 5 task "a way to run Phase 4 captures C6-C9". What the four sections look at on the wire was in roadmap Phase 4,
but there was no way to create those situations on one machine, so they were deferred.

## What changed

| What | Where |
|------|------|
| Four fake-peer scene modes. Each first brings the peer to `CONNECTED`, then opens the scene 2 seconds later. `close_then_keepalive` (C6), `renegotiate` (C7), `probe5` (C8), `flood` (C9) | `control-server/tests/harness/cp_harness.py` |
| A fake peer can use sources outside its candidate. Each item to send carries a source number, and the endpoint opens the socket for that number on first use. The sockets are waited on with `select`. Whatever arrives on an outside socket only gets a `fake.rx` line | Same file |
| 13 scene-mode tests (setup and the moment the scene opens per mode, an echo of another nonce, the sends of each mode, a separate socket per source) | `control-server/tests/test_harness.py` |
| The deferred section became sections C6-C9. Run R5, a filter and pass conditions per section, rows of the record form. "Deferred" removed from the table of covered roadmap items | `tools/phase4-capture/README.md` |
| Removed this item from the next work | `plan.md` |

## Important decisions

- The C9 capture looks only at roadmap (a). (b)-(e) are cases of the logic and the unit test already covers them. What the wire has to
  show is that the cap really applies to what is sent
- The scene opens 2 seconds after the peer enters `CONNECTED`, so the peer's entry sends (`KEEPALIVE`, `ROSTER`) finish before the scene
- After the scene opens, the fake does not answer the peer. That is why in C7 retransmission continues for 10 seconds after renegotiation
  and ends in `PEER_HANDSHAKE_FAILED`. The C9 source not answering matches the injector of roadmap (a)
- The run chains four scenes in one R5. A is the host, so it stays in the room when a pair ends (C6 requires that)

| C7 | 10011 ms from the new-epoch `HELLO` to A's `CLOSE` (0x03). In that window 48 `HELLO`s `P_A` → `F`, gaps 202-218 ms, 0 ms from the start to the first `HELLO`, 177 ms from the last `HELLO` to the `CLOSE`. `KEEPALIVE` 0, `PING` 0. A printed `FAIL PEER_HANDSHAKE_FAILED Fseven` | Pass |

| C9 | 200 `HELLO`s from `X` (10 seconds). 59 packets `P_A` → `X` (`HELLO_ACK` 58, validation `HELLO` 1). Smallest margin between the running count and `11 + 5t` per packet: 1.004. 40 packets in the 8 seconds from `t0 + 2 s`. `drop_unverified_tx` 242 | Pass |

After the review, a second round was added to `probe5`, the C7 and C9 conditions were narrowed, and R5 was run again. The table above is
that run. The first run also passed all four under the conditions of the time.

The fake peers also behaved as the README expects. All four had `to=CONNECTED` in A's log, followed by `fake.scene` in the harness log.

do the pass conditions catch the named defects, and do the tests pin the behavior.

| Finding | Handling |

| warn. The per-second cap of C9 lets a bucket that never refills pass and misses short bursts | Accepted.

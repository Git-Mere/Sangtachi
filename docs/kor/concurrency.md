## 0. 이 문서의 위치

**클라이언트의 스레드와 루프 구조의 단일 출처다.** 여기서 정하는 것은 다음이다.

- 스레드 구성과 각 스레드의 책임
- 대기 집합, 루프 한 바퀴의 순서, 타이머

`architecture.md` 3.2 동시성 모델은 이 문서를 가리키는 요약이다.

| 충돌하는 것 | 우선 |

| 터널 와이어 포맷, 세션 상태, 프로토콜 타이머 값 | `protocol.md` |

구현 중 이 문서에 없는 값을 만나면 코드에서 정하지 않고 이 문서를 먼저 고친다.

## 1. 스레드

**터널 상태를 건드리는 모든 코드는 한 스레드에서만 돈다.** 잠금을 걸어 공유하는 대신
공유하지 않는다.

`[main]` / `[net_rx]` / `[tun_rx]` / `[timer]` 4스레드로 나누지 않는다. 이유는 둘이다.

- 네 스레드가 세션 상태와 송신 `sequence`를 동기화 없이 변경한다
- 텔레메트리 업로드가 타이머 스레드를 공유해 **업로드 대상 장애가** keepalive를 멈춘다.
  이쪽은 NFR-3을 설계 단계에서 위반한다

| 스레드 | 책임 | 공유 상태 |
|--------|------|-----------|
| `[loop]` | UDP 수신, Wintun 수신, 콘솔 명령, 타이머, 세션 상태, 라우팅, 모든 송신 | **터널 상태 없음.** 큐 네 개(텔레메트리, 콘솔, 제어 요청, 제어 응답)의 한쪽 끝과 종료/정리 이벤트만 공유한다 |
| `[telemetry]` | 지표 큐 소비, 텔레메트리 서비스 업로드. Phase 9 이후 | 큐 하나 |
| `[console]` | 표준 입력 읽기. Phase 1~5 스캐폴딩 | 명령 큐 하나 |
| `[control]` | 제어 평면 TCP 호출, DNS 해석. Phase 3 이후 | 요청 큐와 응답 큐 하나씩 (8장 `[control]` 스레드) |

**`[loop]`가 프로세스 주 스레드다.** 나머지는 그 구간에 그 일이 있을 때만 있다.

| 구간 | 스레드 |
|------|--------|
| Phase 1~2 | `[loop]`, `[console]` |
| Phase 3~5 | `[loop]`, `[console]`, `[control]` |
| Phase 6~8 | `[loop]`, `[control]` |
| Phase 9 이후 | `[loop]`, `[control]`, `[telemetry]` |

- `[console]`은 Phase 1~5에만 있다. `[loop]`가 표준 입력에서 블록할 수 없으므로 별도
  스레드가 읽어 큐에 넣는다
- `[telemetry]`가 늦게 오는 이유는 올릴 곳이 그때 생기기 때문이다. 텔레메트리 서비스와
  업로드 스레드가 같은 Phase 의 산출물이다 ([`roadmap.md`](roadmap.md))
- Phase 6에서 어댑터가 들어올 때는 Wintun 읽기 이벤트가 `[loop]`의 대기 집합에 직접
  합류하므로 스레드가 늘지 않는다

## 2. 대기

```text
WaitForMultipleObjects(n, handles, FALSE, timeout_ms)
```

| 순위 | 핸들 | 생성 | 유효 구간 |
|------|------|------|-----------|
| 0 | 종료 이벤트 | `CreateEvent` (수동 리셋) | 항상 |
| 1 | UDP 소켓 이벤트 | `WSACreateEvent` + `WSAEventSelect(sock, ev, FD_READ)` | 항상 |
| 2 | Wintun 읽기 이벤트 | `WintunGetReadWaitEvent(session)` | Phase 6 이후 |
| 3 | 콘솔 명령 이벤트 | `CreateEvent` (자동 리셋). `[console]`이 신호 | Phase 1~5 |
| 4 | 제어 응답 이벤트 | `CreateEvent` (자동 리셋). `[control]`이 응답 큐에 넣은 뒤 신호 | Phase 3 이후 |

**위 번호는 논리적 순위이지 배열 인덱스가 아니다.** `WaitForMultipleObjects`는 유효한
핸들이 빈틈없이 채워진 배열을 요구한다. 빈자리에 `NULL`을 넣으면 `WAIT_FAILED`가 난다.
구성이 바뀌는 시점마다 살아 있는 핸들만 모아 조밀한 배열을 만들고, 논리적 출처에서 실제
인덱스로 가는 대응표를 따로 둔다.

| 구간 | 배열 길이 | 들고 나는 핸들 |
|------|:---:|-----|
| Phase 1~2 | 3 | |
| Phase 3~5 | 4 | 제어 응답 이벤트가 들어온다 |
| Phase 6 이후 | 4 | 콘솔 이벤트가 빠지고 Wintun 이벤트가 들어온다 |

`timeout_ms`는 아래처럼 계산한다. **뺄셈을 먼저 하면 안 된다.**

> **왜.** `GetTickCount64()`는 부호 없는 값이라 마감이 이미 지났을 때 뺄셈이 언더플로해
> 거대한 값이 되고, `DWORD`로 좁히면 `0xFFFFFFFF`, 즉 `INFINITE`에 착지할 수 있다.
> 그러면 루프가 영원히 깨지 않는다.

```text
next_timeout:
    if 대기 중인 타이머 없음:  return INFINITE
    t = now()                              # 한 번만 읽는다
    d = next_deadline()
    if d <= t:                return 0
    return (DWORD) min(d - t, INFINITE - 1)
```

`now()`를 두 번 부르면 안 된다.

> **왜.** 비교와 뺄셈 사이에 시계가 `d`를 지나가면 언더플로해서 타임아웃이 약 49.7일이
> 되고, 루프가 사실상 멈춘다.

`WSAPoll`을 쓰지 않는 이유는 Wintun 읽기 대기가 소켓이 아니라 Win32 이벤트 핸들이기
때문이다. 소켓과 이벤트 핸들을 한 번의 대기에 섞으려면 `WaitForMultipleObjects`여야 한다.
`WSAEventSelect`는 소켓을 자동으로 논블로킹 모드로 바꾸므로 `ioctlsocket(FIONBIO)`를 따로
부르지 않는다.

## 3. 루프 한 바퀴

```text
busy = false
loop:
    r = WaitForMultipleObjects(n, handles, FALSE, busy ? 0 : next_timeout())

    if r == WAIT_FAILED:                      # 복구 불가
        로그 후 shutdown(); break             # 정상 경로와 같은 정리를 거친다
    if r == WAIT_OBJECT_0 + idx(SHUTDOWN):
        shutdown(); break

    WSAEnumNetworkEvents(sock, udp_ev, &ne)   # 소켓 이벤트를 리셋한다. 필수
    u = drain_udp(MAX_DRAIN)                  # r로 분기하지 않는다
    w = drain_wintun(MAX_DRAIN)
    if w == RESTART:
        어댑터 세션 재생성 -> 실패하면 shutdown(); break
        성공하면 살아 있는 핸들로 배열과 인덱스 대응표 재구성
    drain_console()
    drain_control()                           # 8장. Phase 3 이후
    run_expired_timers(now())
    busy = (u == BUDGET) or (w == BUDGET)
```

`WAIT_FAILED`도 `shutdown()`을 거친다. 여기서 바로 빠져나가면 `CLOSE` 송신과 어댑터 정리를 건너뛰어 상대는 50초 동안 죽은 세션을 붙들고 어댑터와 라우트가 남는다. **비정상 종료야말로 정리가 필요한 경우다.**

**`WSAEnumNetworkEvents`를 반드시 부른다.** 이 호출이 이벤트 리셋과 네트워크 이벤트 조회를
한 번에 처리한다.

> **왜.** `WSAEventSelect`가 만드는 이벤트는 수동 리셋이고, `recvfrom`은 `FD_READ` 통지를
> 재무장할 뿐 이미 신호된 이벤트 객체를 리셋하지 않는다. 이 호출을 빠뜨리면 첫 데이터그램
> 이후 이벤트가 계속 신호 상태로 남아 `WaitForMultipleObjects`가 매번 즉시 반환하고, 루프가
> CPU를 태우며 스핀한다.

**`r`로 분기하지 않는다.** 매 바퀴 양쪽을 모두 비우면 인덱스 순서와 무관해지고, 비어 있을
때의 비용은 `WSAEWOULDBLOCK` 하나와 `ERROR_NO_MORE_ITEMS` 하나뿐이다.

> **왜.** `bWaitAll = FALSE`인 `WaitForMultipleObjects`는 신호된 핸들 중 가장 낮은 인덱스
> 하나만 반환한다. 반환값으로 분기하면 UDP 이벤트가 계속 신호되는 동안 그보다 뒤에 놓인
> Wintun 이벤트가 굶는다. 게임 트래픽이 많을 때가 정확히 그 상황이다.

**두 drain은 예산을 가진다.** `MAX_DRAIN`은 한 바퀴당 소스별 64개다. 1472바이트 기준
94KB이고 파싱과 송신 비용이 1ms 미만이라, 가장 짧은 타이머(200ms `HELLO` 재전송) 대비
무시할 수 있다. 예산에 걸려 멈추면 `busy`가 참이 되어 다음 대기가 타임아웃 0으로 즉시
반환한다. 남은 데이터는 다음 바퀴에 처리되고 **그 사이에 타이머가 한 번 돈다.**

> **왜.** 예산 없이 비어질 때까지 돌면, 도착 속도가 처리 속도보다 빠를 때 `drain_udp`가
> 영원히 반환하지 않고 타이머가 한 번도 돌지 않는다. keepalive와 `HELLO` 재전송이 멈추고,
> 바로 위에서 세운 "수신 먼저, 타이머 나중" 순서가 "타이머는 절대 안 돈다"로 변한다.

```text
drain_udp(budget) -> {EMPTY, BUDGET}:
    budget회 반복:
        n = recvfrom(sock, buf, MAX_DATAGRAM + 1, &src)   # 버퍼는 1473바이트
        if n < 0:
            e = WSAGetLastError()
            if e == WSAEWOULDBLOCK:  return EMPTY      # 소스가 비었다
            if e == WSAEMSGSIZE:                       # 1473바이트로도 모자랐다
                drop_oversize_datagram++; continue     # 데이터그램은 이미 소비됐다
            카운터 증가 후 return EMPTY                 # 소켓은 계속 사용한다
        if n > MAX_DATAGRAM:                           # 정확히 1473바이트가 왔다
            drop_oversize_datagram++; continue
        classify(buf, n, src)                          # protocol.md 7장
    return BUDGET                                      # 예산 소진. 아직 남았다
```

**과대 데이터그램에서 비우기를 멈추지 않는다.** `MAX_DATAGRAM`(1472)을 넘는 데이터그램도
반환되는 시점에는 이미 소켓 큐에서 사라진 상태다. 거기서 `return EMPTY` 하면 그 바퀴의
비우기가 한 개에서 끝나므로, 과대 데이터그램을 섞어 보내는 것만으로 배칭이 무력화된다.
버리고 계속 비운다. 다른 오류는 원인을 모르므로 그 바퀴를 끝낸다.

**수신 버퍼는 `MAX_DATAGRAM + 1`(1473)바이트다.** 1바이트 크게 잡으면 `n > MAX_DATAGRAM`
이라는 길이 비교가 판정이 되고, 시험에서 1473바이트를 보내 이 경로를 결정적으로 재현할 수
있다. 버퍼를 `MAX_DATAGRAM` 크기로 잡으면 과대 패킷을 `WSAEMSGSIZE`라는 오류 코드로만 알 수
있고, 그 판정이 Winsock의 절단 동작에 의존한다.

**그래도 `WSAEMSGSIZE` 분기를 지우지 않는다.** 1473바이트를 넘는 데이터그램은 여전히 그
오류로 올라온다. 두 자리는 같은 사건이므로 카운터도 같은 것을 쓴다.

`FD_READ`는 레벨 성격이다. `recvfrom` 후에도 데이터가 남아 있으면 이벤트가 다시 신호되므로,
한 바퀴에 한 개만 읽어도 데이터그램을 잃지는 않는다. **비우는 이유는 정확성이 아니라
비용이다.** 데이터그램마다 대기와 `WSAEnumNetworkEvents`를 왕복하면 깨어남 횟수가 수신 패킷
수만큼 늘고 타이머 처리도 그만큼 밀린다. 정확성 요건은 위의 `WSAEnumNetworkEvents`
호출이고, 비우기는 그 위에 얹는 배칭 정책이다.

```text
drain_wintun(budget) -> {EMPTY, BUDGET, RESTART}:
    if session == NULL:  return EMPTY                  # Phase 1~5. 어댑터가 없다
    budget회 반복:
        p = WintunReceivePacket(session, &size)
        if p == NULL:
            e = GetLastError()
            ERROR_NO_MORE_ITEMS -> return EMPTY         # 링이 비었다. 정상
            ERROR_HANDLE_EOF    -> 종료 이벤트 신호 후 return EMPTY
            ERROR_INVALID_DATA  -> return RESTART       # 링 손상. 아래 참조
            그 외                -> 카운터 증가 후 return EMPTY
        guard = 스코프 이탈 시 WintunReleaseReceivePacket(session, p)
        route_and_send(p, size)
    return BUDGET
```

`WintunReleaseReceivePacket`은 **스코프 가드로 건다.** 호출 순서상 `route_and_send` 뒤에
두면 그 안에서 조기 반환하거나 예외가 나갈 때 링 패킷이 샌다. 한 번 빠뜨릴 때마다 링 버퍼가
영구히 그만큼 줄고 결국 수신이 멈춘다.

`RESTART`는 `[loop]`가 처리한다. 링이 손상되면 세션을 새로 만들어야 하는데, **새 세션은 새
읽기 이벤트 핸들을 준다.** 따라서 세션 재생성과 대기 배열 재구성이 한 묶음이다.
`drain_wintun` 안에서 재시작하면 자기가 방금 무효화한 핸들을 호출자가 계속 기다리게 된다.

재생성이 실패하면 어댑터 없이 계속 도는 대신 `shutdown()`으로 간다. 배열은 조밀하게 다시
만들어지므로 Wintun 핸들이 그냥 빠질 뿐 대기 자체는 정상 동작한다. 그래서 더 위험하다.
**터널이 죽은 채 살아 있는 척한다.** 세션은 `CONNECTED`로 남고 keepalive도 계속 나가지만
게임 패킷은 한 개도 흐르지 않는다.

**주입 실패는 폐기한다.** `DATA`가 [`protocol.md`](protocol.md) 8.4 `DATA` 내부 검증을
통과하면 `WintunAllocateSendPacket`으로 송신 링의 자리를 잡고 `WintunSendPacket`으로 넣는다.
송신 링에 자리가 없어 할당이 실패하는 것은 고장이 아니라 부하가 높을 때 정상적으로 일어나는
일이다. 그 패킷을 버리고 `drop_inject_error`를 올린다.

**재시도하지 않는다.**

> **왜.** 이 스레드가 타이머와 두 수신 경로를 같이 책임지므로, 자리가 날 때까지 기다리면
> 그동안 keepalive와 `HELLO` 재전송이 멈춘다. 링이 찰 만큼 소비가 밀린 상태에서는 그 자리에서
> 다시 시도해도 같은 곳에서 또 막힌다.

버리는 대가는 내부 패킷 한 개다. **그 대가가 회복되는지는 내부 프로토콜에 달렸다.** 내부가
TCP면 재전송이 메우므로 지연이고([`architecture.md`](architecture.md) 4장 데이터 평면 경로의
Minecraft 경로가 그렇다), UDP 같은 비신뢰 프로토콜이면 그 패킷은 그대로 잃는다. 터널은 내부를
구분하지 않으므로(NFR-2) 이것을 "항상 지연일 뿐"이라고 적지 않는다.

**지금 확정하는 것은 카운터 하나와 동작 계약 넷이다.** 카운터는 `drop_inject_error` 하나다.
동작은 **주입이 실패하면 그 패킷을 버리고, 카운터를 올리고, 재시도하지 않고, 루프를 멈추지
않는다.** 이 넷은 어떤 API 모양에서도 성립한다.

**어댑터가 없는 빌드(Phase 4~5)에서 8.4 `DATA` 내부 검증을 통과한 `DATA`가 갈 곳도 여기서
정한다.** 그 구간에는 주입할 어댑터가 없으므로 그 절이 가리키는 "Wintun 주입 직전" 이
가리키는 다음 단계가 비어 있다.

| 빌드 | 8.4 통과 `DATA` |
|------|------------------|
| 어댑터 있음 (Phase 6 이후) | 위의 주입 경로 |
| 어댑터 없음, 시험 빌드 | **페이로드 훅**에 넘긴다. 훅은 꺼낸 페이로드 바이트열과 길이를 그대로 받는 함수 하나이고, [`roadmap.md`](roadmap.md) Phase 4 의 M-5 byte-for-byte 비교와 에코 응답기가 그 자리에서 붙는다 |
| 어댑터 없음, 제품 빌드 | 버리고 `drop_no_sink`를 올린다 |

**훅을 시험 전용 경로로 따로 짜지 않는다.** 8.1~8.4 검증을 통과한 뒤의 같은 지점에 걸어야 그
시험이 실제 수신 경로를 검증한다. `protocol.md` 7장 수신 분류의 출발지 위생 시험이 수신
진입점을 하나로 못박은 것과 같은 이유이고, 여기는 그 대칭인 출구다. `drop_no_sink`는 제품
빌드에서 0이 아니면 설계가 어긋난 것이므로 그 자체가 진단이다.

**"링이 찬 것"을 별도 카운터로 나누는 것은 확인한 뒤에 한다.** 실패가 어느 호출에서 어떤
형태로(반환값인지 `GetLastError`인지, 애초에 보고되는지) 나오는지는 쓰는 Wintun 헤더와 그
문서가 정한다. 이 레포에는 그 헤더가 없고 확인하지 않았다. 확인한 뒤에 이 절에 세부 카운터를
추가한다. 언제 확인하는지는 `roadmap.md`가 갖는다.

> **왜.** 확인하지 않은 API 모양을 여기 적으면 구현이 그것을 그대로 믿는다.

`drain_console`은 `[console]`이 큐에 넣은 명령 줄을 비운다. 이벤트가 자동 리셋이라 별도 리셋
호출이 필요 없다. Phase 6 이후에는 이 핸들도 스레드도 사라진다.

**`quit` 명령은 종료 이벤트를 신호한다.** `shutdown()`을 직접 부르지 않는다. 그러면
`[telemetry]`와 `[control]`이 같은 신호로 함께 깨어나고, 다음 바퀴의 대기가 종료 핸들에서
반환해 7장 종료의 순서를 그대로 탄다. 7장 (1)이 "아직 안 됐으면"이라고 적은 것이 이
경로다.

**콘솔이 만든 송신 잔량은 `busy`에 포함한다.** `send <n>`(Phase 4~5)과 `raw`(`architecture.md`
3.5 기동 입력)는 한 바퀴에 몰아넣지 않고 `MAX_DRAIN`과 같은 방식으로 나눠 보내므로, 잔량이 남은
바퀴는 `busy = true`여야 다음 대기가 타임아웃 0으로 즉시 돌아온다. 그렇지 않으면 남은 송신이
타이머 간격만큼씩 늘어진다.

`drain_control`은 `[control]`이 응답 큐에 넣은 결과를 비우고 세션 상태에 반영한다(8장
`[control]` 스레드). 두 큐는 작고 요청이 사람 속도이므로 예산을 두지 않는다.

Wintun 문서는 부하가 높을 때 `ERROR_NO_MORE_ITEMS`에서 잠시 스핀한 뒤 이벤트를 기다리라고
권한다. **스핀하지 않는다.** 이 루프는 타이머도 책임지므로 스핀이 keepalive와 `HELLO`
재전송을 그만큼 지연시킨다. 스핀은 처리량 최적화이고 우리 목표는 지연(NFR-1)이다. Phase 7
실측에서 수신이 병목으로 나오면 그때 재검토한다.

**어댑터 읽기는 `adapter_rx`로 센다.** `WintunReceivePacket`이 패킷 하나를 돌려줄 때마다
오른다. Phase 6 검증이 "어댑터 read 카운터" 로 읽는 값이 이것이다(`roadmap.md`). 주입 쪽은
성공을 세지 않는다. 실패만 `drop_inject_error`로 센다.

**이 절의 카운터는 `protocol.md`의 카운터와 계층이 다르다.** `drop_oversize_datagram`,
`drop_inject_error`, `drop_no_sink`, `adapter_rx`는 소켓과 어댑터 API가 낸 결과를 세는 것이라
이 문서가 정의한다. `protocol.md` 7장 수신 분류와 8장 수신 검증 파이프라인의 `drop_*`는 와이어
분류와 검증 파이프라인의 카운터다. 목록을 만들 때 두 출처를 섞지 않는다.

## 4. 타이머

- 단조 시계는 `GetTickCount64()`를 쓴다. 밀리초 단위 64비트라 실질적으로 랩어라운드가
  없다(약 5.8억 년). RTT 측정만 `QueryPerformanceCounter`를 쓰고, **두 시계의 값을 서로
  비교하지 않는다.**
- 타이머 집합이 작다. [`protocol.md`](protocol.md) 11장 타이머의 표가 한 자릿수이고 최소
  범위에서 세션은 하나다. 매 바퀴 선형 주사로 가장 이른 마감을 구한다. 타이머 휠은 필요 없다.
  - 같은 장의 "만료 값" 표(폐기 목록, nonce, probe, `pending_pings`)는 세션 타이머가 아니라
    **항목마다 붙는 수명**이라 그 항목을 훑을 때 함께 본다
- `protocol.md` 11장 타이머는 마감 비교에 엄격 부등호를 쓰고, 우선순위를 꺼낸 시각 기준으로
  정의한다. 같은 바퀴에 꺼낸 수신 이벤트가 그 바퀴의 타이머보다 먼저 처리된다. **수신을 먼저
  비우고 타이머를 나중에 도는 이 루프 순서가 그 규칙의 구현이다.**
  - 도착 시각 기준이 아닌 이유는 drain 예산 때문이고, 그 근거는 `protocol.md` 11장에 있다

## 5. 상태 소유

다음은 전부 `[loop]`가 단독 소유한다. 뮤텍스도 원자 변수도 쓰지 않는다. 필요가 없어서다.

- 세션 상태 머신, `session_epoch`, 송신 `sequence`, 재생 방지 비트맵, `peer_endpoint`,
  마지막 수신 시각, 후보 목록, `pending_pings`, 모든 폐기 카운터
- **로컬 기록 파일의 핸들과 쓰기** ([`architecture.md`](architecture.md) 9장 텔레메트리와 기록)
- `room_id`·`peer_id`·`peer_token`·상대 피어 정보 같은 제어 평면에서 받은 값. `[control]`은
  그 값을 응답 큐로 넘길 뿐 자기 상태로 들고 있지 않다. 예외는 8장 `[control]` 스레드가
  적은 해석된 서버 주소 하나다

**송신 `sequence` 증가는 반드시 `[loop]`에서만 일어난다.** `DATA`와 `KEEPALIVE`가 같은
카운터를 쓰므로 두 스레드에서 증가시키면 같은 번호를 단 패킷 두 개가 나간다. 받는 쪽 중복
억제([`protocol.md`](protocol.md) 4.5 중복 억제와 손실 집계)는 뒤엣것을 정확히 버린다. 자기가
만든 위조 중복이다.

어떤 구조체에도 "스레드 안전"이라는 주석을 붙이지 않는다. 단일 소유가 유일한 규칙이고, 예외를 하나 허용하는 순간 규칙이 사라진다.

## 6. 텔레메트리 격리

`[telemetry]`가 별도 스레드인 이유는 병렬성이 아니라 **격리**다.

- `[loop]`는 고정 크기 SPSC 링 버퍼에 레코드를 넣는다. 생산자 하나, 소비자 하나뿐이라 원자
  head/tail만으로 **락 없이** 구현된다
- 가득 차면 새 레코드를 버리고 `telemetry_queue_dropped` 를 올린다. 대기 없음, 실패 보고 없음
- `[telemetry]`가 큐를 비워 텔레메트리 서비스에 올린다. 업로드가 블록되든 실패하든 `[loop]`와
  무관하다
- 텔레메트리는 **텔레메트리 서비스로 가는 자체 TCP 소켓**을 쓴다. 제어 평면 소켓과 공유하지
  않는다. [`protocol.md`](protocol.md) 6장 소켓 소유권의 단일 소켓 제약은 UDP 데이터 평면에만
  적용된다
- **데이터 평면에 락이 하나도 없다.**

**링은 256 항목이다.** 근거는 자동 주기 지표의 배경 생산 속도다. `PING` 5초, keepalive
15초처럼 주기가 정해진 것만 보면 평균 1건/초 미만이고, 그 속도에서 256칸은 분 단위 분량이라
업로드 하나가 소켓 타임아웃(7장 종료)에 걸려 소비가 몇 초 밀리는 구간을 덮는다.

**버스트는 이 크기가 보장하지 않는다.** 시험이 유발하는 연속 연결 시도, 수동 RTT 표본, 폐기
카운터가 몰리는 구간은 같은 초에 여러 건을 만들 수 있고 그러면 더 빨리 찬다. 그때는 새
레코드가 버려진다. 그것이 의도한 동작이다.

> **왜.** 지표는 유실을 허용하는 물건이고, 버스트를 덮으려고 크기를 올리면 장애 구간에서
> 오래된 지표를 더 오래 붙들 뿐이다.

**콘솔 명령 큐는 16 줄이고 같은 정책을 쓴다.** 가득 차면 새 줄을 버리고
`console_queue_dropped` 를 올린다. 생산자가 `[console]`, 소비자가 `[loop]` 하나씩이라 여기도
락이 필요 없다.

- **이 카운터만 5장 상태 소유의 단독 소유 규칙에서 예외다.** 버리는 쪽이 생산자인
  `[console]` 이라 그 스레드가 올린다. 원자 변수 하나이고 `[loop]` 는 읽기만
  한다([`architecture.md`](architecture.md) 9장의 `counter` 이벤트). 다른 폐기 카운터는 전부
  `[loop]` 가 올린다
- **두 큐의 카운터를 같은 이름으로 쓰지 않는다.** 이름이 없으면 Phase 1 검증이 무엇을 보는지
  정할 수 없다

> **왜 16줄인가.** 사람이 치는 명령이 16줄이나 밀리는 상황은 `[loop]`가 이미 막혔다는 뜻이고,
> 그때 큐를 키워도 처리되지 않는다.

가장 오래된 것을 버리는 쪽이 지표 품질로는 낫지만, 그러려면 생산자가 소비자의 tail을
움직여야 해서 락이 필요하다. **지표 하나 더 살리자고 `[loop]`에 락을 들이지 않는다.**
뮤텍스로도 임계 구역이 짧아 실제로는 거의 안 막히겠지만, "거의"는 보장이 아니다. 소비자가
락을 쥔 채 스케줄에서 밀리면 `[loop]`가 그만큼 멈춘다.

Phase 5의 "서버 중단 10분" 시험(NFR-3)은 이 격리 없이는 통과할 수 없다. 4스레드 안에서는
응답하지 않는 **텔레메트리 서비스**로의 TCP 업로드가 타이머 스레드를 수십 초 막고, 그 사이
keepalive가 나가지 않아 NAT 매핑이 만료된다. 원격 서비스 장애가 터널을 끊는다.

**서비스를 둘로 나눠도 이 격리는 여전히 필요하다.** 분리는 텔레메트리 장애가 제어 평면을 막지
않게 할 뿐이고, 클라이언트 안에서 업로드가 `[loop]`를 막는 문제는 스레드 격리만이 막는다.

## 7. 종료

- `[telemetry]`는 `WaitForSingleObject(shutdown_ev, 1000)`으로 1초마다 깨어 큐를 비운다.
  push마다 이벤트를 신호하지 않는다. 종료 이벤트는 수동 리셋이라 신호되는 즉시 이 대기도 함께
  깨운다.
- `[telemetry]`는 업로드 소켓에 `SO_SNDTIMEO` / `SO_RCVTIMEO` 1.5초를 건다. 업로드와 업로드
  사이마다 종료 이벤트를 확인한다.

**1.5초가 업로드 한 번의 총 시간을 2초 아래로 만들지는 못한다.** 두 타임아웃은 연산별이라
송신과 수신이 각각 걸리면 합이 3초까지 간다. 그래서 join 상한을 지키는 것은 이 값이 아니라
아래의 `_exit`다. 1.5초를 쓰는 이유는 **흔한 경우를 빨리 끝내는 것**이고, 더 키우면 그
효과마저 사라진다.

`SetConsoleCtrlHandler`가 종료 이벤트를 신호한다. **핸들러는 `[loop]` 소유 상태를 절대
건드리지 않는다.** 다른 스레드 컨텍스트에서 실행되기 때문이다.

**제어 신호 종류에 따라 반환 시점이 다르다.**

| 신호 | 핸들러 |
|------|--------|
| `CTRL_C_EVENT`, `CTRL_BREAK_EVENT` | 이벤트를 신호하고 즉시 `TRUE`를 반환하면 된다 |
| `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT`, `CTRL_SHUTDOWN_EVENT` | 종료 이벤트를 신호한 뒤 정리 완료 이벤트를 OS 유예 시간 안쪽(3초)까지 기다렸다가 반환한다 |

뒤의 세 신호는 **핸들러가 반환하는 순간 Windows가 프로세스를 종료한다.** 신호만 하고
돌아오면 `CLOSE` 송신도 어댑터 정리도 실행되지 않는다. 콘솔 창을 닫는 것은 이 프로그램의
정상적인 종료 방법이므로 예외 처리가 아니라 주 경로다.

`[loop]`의 `shutdown()`은 아래 순서로 돈다. `[control]`은 Phase 3 이후에만 있으므로 그 전에는
(8)이 `[telemetry]`만이다.

| # | 하는 일 |
|---|---------|
| 1 | 종료 이벤트 신호 (아직 안 됐으면) |
| 2 | [`protocol.md`](protocol.md) 5.6 `CLOSE` 가 정한 대상 세션마다 `CLOSE` 1회 송신. 대상과 reason 값은 그 절이 정한다. 여기에 조건을 다시 적지 않는다 |
| 3 | **아직 끝나지 않은 세션이 `CONNECTED`에 도달했었다면 로컬 기록 파일에 종료 줄을 쓴다** ([`architecture.md`](architecture.md) 9장. 이미 종료 상태라 그 줄을 쓴 세션은 다시 쓰지 않는다) |
| 4 | **카운터 전량을 `counter` 이벤트로 낸다** (`architecture.md` 9장) |
| 5 | 어댑터 세션 종료 |
| 6 | 어댑터/주소/라우트 정리 |
| 7 | **정리 완료 이벤트 신호** |
| 8 | `[telemetry]`와 `[control]` join |

- **종료 상태에 도달하면 프로세스도 끝난다.** 세션이 `FAILED`나 `CLOSED`가
  되면(`protocol.md` 9.6 실패 전이, 5.6 `CLOSE`) `[loop]`는 그 세션의 기록 줄과 카운터를 남긴
  뒤 스스로 `shutdown()`으로 간다. 최소 범위의 세션은 하나이므로 그 세션이 끝나면 프로세스가
  할 일이 없다. 사용자의 `quit`을 기다리지 않는다. **자동 재시도를 정하면 이 줄을 다시
  본다**(`protocol.md` 10.4 엔드포인트 학습의 미정 항목). 재시도가 생기면 `FAILED`가 곧 종료가
  아니게 된다.
- **큐에 종료 표식을 넣지 않는다.** 큐는 가득 차면 새 항목을 버리므로 하필 그때 표식이
  버려지면 `[telemetry]`가 종료를 영영 못 본다. 종료는 큐 밖의 이벤트로만 전달한다.
- **정리가 join보다 먼저다.** 이 순서 덕분에 콘솔 핸들러는 텔레메트리를 기다리지 않고 반환할
  수 있고, OS가 그 시점에 프로세스를 죽여도 잃는 것은 지표 몇 건뿐이다.
- join 상한은 두 스레드 합쳐 2초다. 넘기면 남은 레코드와 진행 중인 제어 요청을 포기하고 join을
  건너뛴 채 `_exit`로 즉시 끝낸다. 정리가 (7)에서 이미 끝났으므로 안전하다. **상한을 실제로
  강제하는 것은 소켓 타임아웃이 아니라 이 `_exit`다.** 소켓 타임아웃은 흔한 경우를 깔끔하게
  끝내줄 뿐이고, 어떤 경우에도 종료가 텔레메트리 서비스 가용성에 인질 잡히지 않게 하는 것은
  `_exit`다.
- **`[console]`은 join하지 않는다.** 이 스레드는 표준 입력 읽기에서 블록한다. **이 설계는 그
  읽기를 밖에서 취소하는 수단을 쓰지 않는다.** 그래서 join하면 사용자가 한 줄을 더 입력할
  때까지 종료가 멈춘다. 종료 이벤트를 신호한 뒤 그대로 두고 프로세스 종료에 맡긴다.
  `[console]`이 소유한 것은 명령 큐뿐이고 정리할 외부 자원이 없으므로 잃는 것이 없다.
- 어댑터, 가상 IP 주소, 라우트의 정리와 비정상 종료 후 잔존물 처리는
  [`windows-prereq.md`](windows-prereq.md) 3절에 있다.

## 8. `[control]` 스레드

제어 평면 TCP 호출과 DNS 해석은 `[loop]`에서 하지 않는다. `getaddrinfo`도 동기 호출이라 같은
자리다.

> **왜.** 제어 서버가 죽어 있으면 TCP `connect`가 SYN 재시도로 수십 초를 소모한다. Phase 4
> 검증이 일부러 만드는 상황이다. 그 시간이 `[loop]`에서 흐르면 `HELLO` 재전송(200ms)과
> keepalive(15s)와 종료 이벤트 응답이 전부 멈춘다. 6장 텔레메트리 격리가 4스레드 안을
> 폐기한 사유가 다른 문으로 돌아오는 것이고 [`spec.md`](spec.md) NFR-3 위반이다.

**논블로킹 소켓을 `[loop]`의 대기 집합에 넣는 안을 쓰지 않는다.** TCP 연결, HTTP 파싱, DNS를
전부 상태 머신으로 다시 써야 하고, `getaddrinfo`는 논블로킹 형태가 없다. 스레드 하나가 싸다.

| 항목 | 값 |
|------|-----|
| 큐 | `[loop]` -> `[control]` 요청 큐, `[control]` -> `[loop]` 응답 큐. 각각 SPSC 링 **8 항목**. 6장 텔레메트리 격리의 링과 같은 구현이고 락이 없다 |
| 가득 찼을 때 | 요청 큐가 차면 `[loop]`는 그 요청을 버리고 `control_queue_dropped`를 올린 뒤 **그 시도를 `CONTROL_PLANE_EXCHANGE_FAILED`로 끝낸다.** 요청은 한 번에 하나만 미결이므로(아래) 정상 경로에서는 차지 않는다. 차면 `[control]`이 멈춘 것이다 |
| 미결 요청 | **한 번에 하나.** `[loop]`는 응답을 받기 전에 다음 요청을 넣지 않는다. `get_peers` 폴링은 "응답 수신 후 500ms" 이다. 폴링 타이머가 만료했는데 앞 요청이 미결이면 그 바퀴는 건너뛴다 |
| 깨우기 | `[control]`은 `WaitForMultipleObjects`로 종료 이벤트와 요청 이벤트(자동 리셋, `[loop]`가 신호)를 기다린다. `[loop]`는 응답 이벤트(2장 대기의 순위 4)로 깨어난다 |
| 소켓 | 요청마다 새 TCP 소켓. 논블로킹 `connect` + `select`로 연결 시간 제한, `SO_SNDTIMEO`/`SO_RCVTIMEO`로 송수신 시간 제한. 값은 [`control_plane.md`](control_plane.md) 8.2 시간 제한 |
| DNS | 기동 시 한 번. 결과 IPv4 주소 하나를 `[control]`이 들고 이후 모든 요청에 쓴다. 이것이 `[control]`이 갖는 유일한 상태다 |
| 종료 | 종료 이벤트를 보면 진행 중인 요청의 응답을 기다리지 않고 소켓을 닫고 반환한다. 소켓 시간 제한 때문에 최대 한 요청 상한(`control_plane.md` 8.2 시간 제한)만큼 늦을 수 있고, 그것을 7장 종료의 join 상한 2초와 `_exit`가 가둔다 |

**`[control]`은 세션 상태를 읽지도 쓰지도 않는다.** 요청 큐에서 꺼낸 것을 보내고 받은 것을
응답 큐에 넣는다. 응답을 세션 상태에 반영하는 것은 `drain_control`이고 그것은 `[loop]`다.
응답 해석(JSON 파싱, 오류 분류)은 `[control]`이 해도 된다. 그 결과는 값이고 공유 상태가
아니다.

**`[telemetry]`와 합치지 않는다.** 텔레메트리 업로드는 유실을 허용하고 실패를 보고하지 않는다.
제어 요청은 응답이 필요하고 실패가 곧 `CONTROL_PLANE_EXCHANGE_FAILED`다. 한 스레드에서 두
성질을 섞으면 텔레메트리 서비스 장애가 제어 요청을 지연시켜 `get_peers` 마감(60s)을 잡아먹는다.
두 서비스를 분리한 이유(`architecture.md` 3.4 텔레메트리 서비스)를 클라이언트 안에서 다시
무너뜨리는 셈이다.

# 0015. 멤버를 사람이 정한 표시 이름으로 가리킨다

- 상태: 채택
- 날짜: 2026-10-07
- 관련: [ADR 0006](0006-무중계-스타-토폴로지.md), [ADR 0011](0011-로비는-방-소속으로-정한다.md), [`../spec.md`](../spec.md) FR-15·FR-16·T-7, [`../control_plane.md`](../control_plane.md) 2.7·4.1·4.2·4.3·4.5·4.6·6.3·6.4·6.5·7.6, [`../protocol.md`](../protocol.md) 3장·5.7, [`../architecture.md`](../architecture.md) 3.5·8장, [`../concurrency.md`](../concurrency.md) 7장, [`../roadmap.md`](../roadmap.md) Phase 4

## 맥락

`concurrency.md` 7장 로비는 호스트 쪽 쌍 하나가 실패하면 `FAIL` 줄을 내고 방에 남는다고 정했다.
그 줄이 어느 플레이어의 것인지를 담는지는 정하지 않았고, `roadmap.md` Phase 4 가 착수 전 결정으로
남겼다. 호스트는 쌍을 최대 넷 가지므로 줄만으로는 누구와의 연결이 실패했는지 알 수 없다.

멤버를 가리킬 수 있는 값은 둘뿐이었다.

- `peer_id` 는 서버가 참가마다 새로 뽑는 32비트 난수다. 사람에게 뜻이 없다
- `virtual_ip` 는 머무는 동안 고정이지만 다시 들어오면 바뀔 수 있고, 떠난 사람의 주소를 새
  참가자가 받는다(`control_plane.md` 4.3)

둘 다 사람이 "누구인지" 알아보는 값이 아니다. 같은 문제가 GUI 멤버 목록(FR-15)과 T-7 판정에도
있다.

## 결정

저장소 소유자가 아래를 정했다.

**1. 방에 들어가는 모든 피어가 표시 이름을 정한다.** 호스트도 정한다. `create_room` 과
`join_room` 요청의 필수 필드다. 클라이언트는 기동 인자로 받고 로비에서 바꿀 수 있다.

**2. 형식은 ASCII 영문자, 숫자, 밑줄이고 1자 이상 16자 이하다.** 대소문자는 등록한 그대로
보이고, 같은지 비교할 때는 무시한다. 한글은 받지 않는다.

**3. 이름은 방 안에서 유일하다.** 서버가 `NAME#` 항목의 조건부 쓰기로 보장하고, 겹치면 새 오류
코드 `name_taken` 으로 거부한다.

**4. 이름은 서버에서 호스트로, 호스트에서 플레이어로 간다.** 호스트와 플레이어는 상대의 이름을
`host_report` 와 `get_peers` 응답으로 받는다. 플레이어끼리는 서로의 이름을 `ROSTER` 로 받는다.
`ROSTER` 의 멤버 배치가 고정 9바이트에서 가변 길이로 바뀐다.

**5. 이름은 표시 전용이다.** 수신 검증, 라우팅, 로컬 기록의 짝짓기는 이름을 보지 않는다. 기계가
쓰는 식별자는 계속 `peer_id` 다.

**6. `FAIL` 줄에 상대 칸을 늘 둔다.** `FAIL <코드> <상대> <문장>` 이다. 세션에서 난 실패면 그
세션 상대의 이름이고, 그 밖에는 `-` 다. Phase 4 의 착수 전 결정 하나를 이것으로 닫는다.

## 대안

**대안 1. 이름 없이 `peer_id` 나 `virtual_ip` 를 `FAIL` 줄에 싣는다.**
버렸다. 줄 문법만 바꾸면 되어 싸다. 대가는 사람이 그 값을 보고 누구인지 모른다는 것이고, 그것이
이 결정의 출발점이다.

**대안 2. `FAIL` 줄 문법을 그대로 두고 쌍 실패일 때만 칸을 더한다.**
버렸다. 셋째 낱말이 이름인지 문장의 시작인지를 읽는 쪽이 추측해야 한다.

**대안 3. 이름을 문장 안에 넣는다.**
버렸다. 문장은 `architecture.md` 8장 표가 코드마다 하나씩 소유하고 GUI 도 같은 문장을 쓴다.
문장이 틀이 되고 기계가 읽기 어려워진다.

**대안 4. 한글 이름을 받는다.**
버렸다. 사람에게는 더 낫다. 대가는 바이트 길이와 글자 수의 구분, 유니코드 정규화, 보이지 않는
문자와 방향 제어 문자의 거부 규칙, 콘솔과 로그 출력 경로 검사가 서버와 클라이언트와 명부 수신에
각각 붙는 것이다. 영문자·숫자·밑줄은 공백이 없어 `FAIL` 줄과 로그의 `<이름>=<값>` 규칙을 깨지
않는다.

**대안 5. 이름이 겹쳐도 받는다.**
버렸다. 항목이 하나 줄고 회수 경로가 단순해진다. 대가는 같은 이름 둘을 사람이 구분하지 못하는
것이고, 그러면 이름을 둔 목적이 사라진다.

**대안 6. 유일성을 호스트가 판정한다.**
버렸다. 스타 토폴로지에서 호스트가 명부의 출처이긴 하다. 그러나 참가는 서버에서 끝나므로
호스트가 거부하려면 이미 들어온 피어를 내보내는 새 경로가 필요하다.

**대안 7. 이름을 `HELLO` 로 나른다.**
버렸다. 핸드셰이크 패킷의 길이와 검증이 바뀐다. 이름은 연결 수립에 필요 없다.

**대안 8. 기본 이름을 두고 필수로 하지 않는다.**
버렸다. 모두가 같은 기본값을 쓰면 결정 3 에 걸려 두 번째 참가부터 실패한다.

## 결과

**얻는 것.**

- 호스트의 `FAIL` 줄과 멤버 목록이 사람이 알아보는 이름을 보인다
- `FAIL` 줄 문법이 플레이어와 호스트에서 같다

**치르는 것.**

- 끝난 Phase 3 코드를 다시 고친다. 제어 서버의 요청 검사, 저장, 응답과 클라이언트의 기동 인자,
  로비, 응답 검사, `FAIL` 줄이다
- 방 하나의 저장 항목 상한이 15개에서 20개로 늘어 용량 최악값이 커진다(`control_plane.md` 7.6)
- `ROSTER` 가 가변 길이가 되어 수신 검사와 폐기 카운터가 하나씩 는다
- 이름은 인증하지 않는다. v1 의 `ROSTER` 는 경로 위의 누구든 만들 수 있으므로 화면의 이름도
  위조될 수 있다. 결정 5 가 그 위조가 검증과 라우팅에 닿지 않게 한다

# Phase 1 UDP 소켓 래퍼

**대상 커밋:** 이 커밋
**Phase:** 1 (핵심 UDP 네트워킹)

`protocol.md` 6장 소켓 소유권이 정한 계약을 코드로 옮겼다. `roadmap.md` Phase 1 의 "UDP
소켓 래퍼 구현" 이다.

## 무엇을 넣었나

| 대상 | 내용 |
|------|------|
| `protocol_constants.hpp` | `protocol.md` 3장 상수 블록을 옮겼다 |
| `network::UdpSocket` | 열기, `send_to`, `recv_from`, `enumerate_events`, 읽기 이벤트 |
| `open_udp_socket` | 6장 계약대로 연다. 실패하면 어느 호출에서 났는지와 오류 코드를 돌려준다 |

6장이 정한 것을 하나씩 옮겼다. `INADDR_ANY` 와 포트 0 으로 bind, `getsockname` 으로 실제
포트 읽기, `SO_RCVBUF` 요청 262144 와 `getsockopt` 적용값 읽기, `SO_EXCLUSIVEADDRUSE`,
`connect()` 미사용, `SIO_UDP_CONNRESET` 끄기, `WSAEventSelect` 로 `FD_READ` 묶기.

**`recv_from` 은 과대 데이터그램을 두 경로로 구분한다.** 버퍼가 `MAX_DATAGRAM + 1`(1473)
이라 정확히 1473바이트는 길이 비교로, 1474바이트 이상은 `WSAEMSGSIZE` 로 걸린다
(`architecture.md` 3.2.3). 둘 다 `Oversize` 로 돌려주되 `error` 값이 달라 어느 경로였는지
구분된다.

**`sendto` 실패를 삼키지 않는다.** 카운터를 올리는 것은 호출자의 일이다(6장). 래퍼는 실패와
오류 코드를 돌려주고 재전송하지 않는다.

## 검증

Catch2 케이스가 40건에서 55건으로 늘었다. 소켓 시험은 실제 소켓을 열고 루프백으로만
보낸다. 케이스마다 프로세스가 분리되므로 서로를 오염시키지 않는다.

실물로만 확인되는 것 넷을 케이스로 넣었다.

| 무엇 | 어떻게 |
|------|--------|
| `SIO_UDP_CONNRESET` | 닫힌 포트로 4발 보낸 뒤 수신이 `WSAECONNRESET` 이 아니라 비어 있는지 본다 |
| 1473 경계 | 정확히 1473바이트를 보내고 오류 코드 없이 길이로 걸리는지 본다 |
| 1474 경계 | 1474바이트를 보내고 `WSAEMSGSIZE` 로 걸리는지 본다 |
| 이벤트 리셋 | 다 읽고 `enumerate_events` 한 뒤 기다리면 바로 돌아오지 않는지 본다 |

## 시험 하네스의 결함이 먼저 드러났다

변이 하나가 **`FAIL` 이 아니라 무한 대기로 나타났다.** `WSAEventSelect` 를 빼면 소켓이
블로킹으로 남고, "빈 소켓에서 받기" 케이스의 `recvfrom` 이 돌아오지 않는다. `ctest` 에 시간
상한이 없어 하네스째로 매달렸다.

**변이가 아니라 하네스의 결함이다.** 고친 것은 둘이다.

- `catch_discover_tests` 에 `TIMEOUT 30` 을 걸었다. 가장 느린 케이스의 백 배가 넘는다
- 변이 드라이버에 300초 상한을 두고 **매달린 변이를 죽은 것으로 센다**

> 상한이 없으면 매달리는 케이스 하나가 하네스를 영원히 붙잡는다. 변이 시험이 아니었으면
> 이 구멍을 Phase 4 의 긴 시험에서 만났을 것이다.

## 변이 시험

17건 중 16건이 죽었다. 리뷰 반영으로 가드 둘이 늘어 세 건을 더 돌렸다.

| 죽은 변이 |
|------|
| `SIO_UDP_CONNRESET` 을 켠 채로 둠, `SO_RCVBUF` 미설정, 길이 비교 제거, `WSAEMSGSIZE` 분기 제거, `WSAEWOULDBLOCK` 분기 제거, 포트 고정 bind, 루프백 전용 bind, `WSAEventSelect` 제거, `enumerate_events` 무력화, `getsockname` 결과 무시, 이동 후 핸들 방치, 포트 바이트 순서 미변환, 주소 바이트 순서 미변환 |

### 살아남은 하나는 실측으로 동등 변이임을 확인했다

`getsockopt` 로 적용값을 읽는 대신 **요청값을 그대로 적는** 변이가 살아남았다. 처음에는
케이스의 구멍으로 보고, 소켓에 직접 다시 물어본 값과 대조하는 케이스를 넣었다. **그래도
살아남았다.**

그래서 Windows 가 `SO_RCVBUF` 를 어떻게 다루는지 직접 쟀다. 임시 시험으로 값 여덟 개를
설정하고 바로 읽었다.

| 요청 | 적용 | 다른가 |
|-----:|-----:|:---:|
| 0 | 0 | 아니오 |
| 1 | 1 | 아니오 |
| 512 | 512 | 아니오 |
| 2048 | 2048 | 아니오 |
| 65536 | 65536 | 아니오 |
| 262144 | 262144 | 아니오 |
| 1073741824 | 1073741824 | 아니오 |
| 2147483647 | 2147483647 | 아니오 |

**이 기기의 Windows 는 요청값을 그대로 돌려준다.** 따라서 "소켓에서 읽은 값" 과 "요청값을
그대로 적은 값" 은 어떤 입력으로도 갈라지지 않는다. 케이스를 더 넣어 죽일 수 있는 변이가
아니다.

**그래도 대조 케이스와 `native_handle()` 은 남긴다.** 값이 갈리는 환경에서는 그 케이스가
잡고, 남겨 두는 것이 계약을 코드에 적는 방법이기도 하다. 탐침 시험은 수치를 여기 옮기고
지웠다. 아무것도 단정하지 않는 시험을 레포에 두지 않는다.

**`protocol.md` 6장은 고치지 않았다.** 그 문장은 "OS 가 요청값을 그대로 주지 않을 수 있다"
라는 조건부 서술이고, 한 기기가 그대로 돌려준 것이 그 문장을 뒤집지 않는다.

## 크로스 모델 리뷰

Codex 에 렌즈 둘(Winsock 정확성, 시험의 강도)을 붙였다. 지적 4건 중 **3건 반영, 1건 기각**이다.

| 등급 | 지적 | 처리 |
|------|------|------|
| warn | `send_to` 가 `payload.size()` 를 `int` 로 좁힌다. 크기가 감싸 돌 수 있다 | **반영.** `INT_MAX` 를 넘으면 `WSAEMSGSIZE` 로 돌려보낸다. `MAX_DATAGRAM` 으로 자르지는 않는다. 시험이 일부러 그보다 큰 것을 보내 수신 쪽 과대 경로를 확인하기 때문이다 |
| warn | `recv_from` 이 `buffer.size()` 를 `int` 로 좁힌다 | **반영.** 읽는 길이를 `kRecvBufferSize` 로 자른다. 좁히기 문제만이 아니다. 호출자가 더 큰 버퍼를 주면 1474바이트 이상이 그냥 담겨 `WSAEMSGSIZE` 분기가 영영 돌지 않는다 |
| warn | "경로 없는 곳으로 보내기" 케이스가 실패했을 때만 단언하므로 아무것도 확인하지 않는다 | **반영.** 브로드캐스트 주소로 바꿨다. `SO_BROADCAST` 를 켜지 않은 소켓에서 실패가 결정적이라 `WSAEACCES` 를 단언할 수 있다 |
| warn | "닿지 않는 포트" 케이스가 방금 닫은 포트를 다른 프로세스가 잡을 수 있다고 가정하지 않는다 | **기각.** 틀린 실패를 내지 않는다. 누가 잡았으면 ICMP 가 돌아오지 않아 수신은 여전히 비어 있다. 잃는 것은 그 실행에서 아무것도 확인하지 못한다는 것뿐이고, `SIO_UDP_CONNRESET` 변이가 실제로 죽는 것으로 효력을 확인했다. 그 한계를 시험 주석에 적었다 |

**두 번째 지적이 좁히기보다 큰 것을 가리켰다.** 버퍼 길이를 자르지 않으면 3.2.3 이 설계한
두 경로 중 하나가 호출자의 버퍼 크기에 따라 사라진다. 그것을 막는 케이스를 같이 넣었고,
자르기를 지운 변이가 그 케이스에서 죽는다.

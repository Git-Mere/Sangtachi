### Paths the adapter MTU 1400 does not cover

Kept here until `experiments.md` exists.

- This run measured a maximum-size packet on one path between two homes in one direction (B→A). The A→B maximum size
  was not measured
- The outer packet is at most 1448 bytes (inner 1400 + tunnel 20 + UDP 8 + IPv4 20). If the path MTU is smaller, the
  packet goes as IP fragments because DF is not set. Whether fragments pass middleboxes or NATs was not measured
- The networks were only two homes' Wi-Fi and home routers. Mobile tethering, running over a VPN and corporate networks
  were not measured

No problem showed between keepalive and the mapping lifetime of the two homes.

### What 6-5 showed

The 6-5 row of `plan.md` holds what must be decided. Only observations are written here.

- The console `send` hit `WSAEWOULDBLOCK` (10035) from `sendto` at 576 bytes (110–133 datagrams) and 1452 bytes (45) and
  stopped with `send_failed`. This happened in both runs on both sides. At 20 bytes every run that sent them sent all 1,000. In the second
  run A's `send 1000 20` was typed before connecting and rejected with `not_connected`, and A's first `send` after
  connecting was rejected with `bad_send_args`
- The send counters exceed the capture: one 40-byte datagram in the second 6-5 run, three 40-byte datagrams in test 1.
  Receive matched exactly in both. A's test 1 capture has no packet sent to the peer's private candidate. This fits the
  hypothesis that the peer's private candidate is in the same range as A's own subnet, so ARP fails and the packet never
  reaches the wire, but ARP was not captured so it is not confirmed
- In the second 6-5 run A's per-pair `drop_too_old` was 168, and that pair's `session.loss` was 178 lost of 1180. The
  number received on the wire matches the counter. The cause was not examined
- 6-5 was started twice and `a-udp-before-1000.txt` was taken before the first run. Which run the receive errors belong to
  cannot be separated
- In the second run the repository owner typed `send 1000 20` before the session connected. It was rejected with
  `console.rejected reason=not_connected` and nothing was sent

## Key decisions

- The MTU keeps the conservative fixed value 1400. No reason to change it appeared
- Every attempt after the lobby runs STUN again. The repository owner decided. The client already does this (both logs
  of test 1 have `stun.result` in both attempts). One measurement in the 3-minute range cannot set a threshold for
  skipping it (ADR 0031)

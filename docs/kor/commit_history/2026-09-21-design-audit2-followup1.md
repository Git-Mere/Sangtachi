**대상:** 저장소 루트 `CLAUDE.md`, 그리고 `docs/kor/` 아래 `spec.md`, `roadmap.md`,
`architecture.md`, `protocol.md`, `plan.md`, `audit-history/design-audit2.md`(신규),

**한국어만 고쳤다.** `docs/eng` 미러는 푸시 지시 때 만든다. 그 사이 게이트가 `mirror`와
`parity`로 막히는 것이 정상이다.

## 왜 이 커밋이 있는가

Phase 1 구현 착수 전에 핵심 문서 5개를 전면 감사했다(`audit-history/design-audit2.md`,
blocker 6 / warn 24 / info 24). 그중 **제어 평면과 무관한 것만** 처리한 것이 이 커밋이다.
제어 평면 묶음(B-2, B-3, B-4, B-5, W-6, W-11, W-12, info 4건)은 별도 스키마 문서가 필요해
`plan.md`의 2차로 남겼다. 저장소 소유자가 B-2와 B-4를 2차로 옮기라고 지시했다.

## 감사 방법

렌즈 5개의 독립 리뷰를 병렬로 돌렸다. 시나리오 추적, 일관성 대조, 구현자 시점, 검증 기준,
적대적 입력이다. 각 렌즈의 "없다" 류 지적은 통합 시점에 HEAD 원문과 직접 대조했다.

**렌즈 하나가 잡지 못한 것을 다른 렌즈가 잡았다.** 세 렌즈가 독립적으로 같은 곳을 지목한
자리가 둘이었고(9.4 전이표 결측, 제어 평면 스레드 소유), 그 둘이 가장 큰 구멍이었다.

### architecture.md

### roadmap.md / spec.md

Phase 4 검증의 기대 카운터를 `drop_retired_epoch`로 정정했다. Phase 2의 공인 IP 일치 기준을
참고로 낮추고 판정을 파싱 성공으로 바꿨다. M-2 판정 자리를 Phase 4에 만들었다. RTT 기준선을
`DATA` 에코로 확정했다. NFR-2를 Phase 7로 옮겨 파일 전송 시험을 판정으로 삼았다. Phase 헤더의
요구사항 나열을 추적표 참조로 바꿨다. `send <n>` 합성 패킷을 절대 오프셋 표로 못박았다.

**새 계약마다 검증 항목을 함께 넣었다.** 출발지 위생, 종료 상태 폐기, 재협상 상한, 잠정 경로
상한, `CLOSE` 조건, bind, `SO_RCVBUF`, 과대 데이터그램, 폐기 목록 상한, epoch 난수원, 콘솔
큐, 링 크기, Wintun 주입이다. 변이로 확인하라는 문장도 같이 적었다.

## 결정

| 무엇 | 정한 값 | 근거 |
|------|---------|------|
| 수신 버퍼 | `MAX_DATAGRAM + 1`(1473) | 과대 패킷 판정이 Winsock의 절단 동작이 아니라 **길이 비교**로 나온다. 시험에서 결정적으로 재현된다 |
| 잠정 경로 포화 시 | 새 경로를 거부하고 **먼저 온 것을 지킨다** | 밀어내면 위조 출발지를 빠르게 보내는 쪽이 진짜 경로를 밀어낼 수 있다 |
| `drop_probe_full` | 경로 등록만 건너뛰고 **패킷은 정상 처리** | 버리면 유휴 타이머가 갱신되지 않아 살아 있는 세션이 단절로 판정된다 |
| `CLOSE` 대상 | 상태가 아니라 **`peer_endpoint` 학습 여부** | 상대가 `CONNECTED`일 때 우리가 `HANDSHAKING`일 수 있다. `CONNECTED`에만 보내면 상대가 50초를 기다린다 |
| Wintun 주입 카운터 | `drop_inject_error` **하나만** 확정 | 실패가 어느 호출에서 어떤 형태로 나오는지 확인할 수단이 없었다. 확인하지 않은 API 모양을 적으면 구현이 그것을 믿는다 |
| 재협상 쿨다운 기준 | **수용한** 재협상 시각 | 폐기한 것이 시각을 갱신하면 공격자가 쿨다운을 영구 연장해 정상 재시도까지 막는다 |

### 이 구간에서 고친 큰 것 셋

**무검증 목적지로 나가는 송신에 공통 예산을 뒀다.** 처음에는 `HELLO_ACK` 에만 속도 상한을
걸었는데, 적대적 렌즈가 **후보 밖 출발지의 `HELLO` 하나가 `HELLO_ACK` 과 경로 검증 `HELLO`
를 동시에 유발**하므로 경로별 상한의 합이 실제 송신량을 과소평가한다고 지적했다. `PONG`
까지 포함해 세션당 토큰 버킷 하나로 묶었다. 그러면서 세 곳에 흩어져 있던 수치를 9.4 하나로
모았다.

**로컬 기록 파일이 한 시도에 몇 줄인지 정했다.** `PING` 은 `CONNECTED` 뒤에 시작하므로 수립
시점에는 RTT 표본이 없다. 그래서 수립 줄의 RTT 는 대개 비어 있고, `CONNECTED` 에 도달한
시도만 종료 줄을 한 줄 더 갖는다. **줄 수로 도달 여부를 읽을 수 있다.**

**시험 빌드 에코 응답기의 무한 루프를 막았다.** 양쪽이 옵션을 켜면 에코가 다시 에코된다.
합성 패킷 오프셋 40 을 방향 표시로 쓰고 응답에는 응답하지 않게 했다.

| 입력 토큰 | 187k | **85k** |
| 토큰당 지적 | 0.20/1k | **0.28/1k** |

**묶음이 토큰당 1.39배 효율이지만 blocker 는 개별이 2.7배 더 찾았다.** 그리고 둘은 서로 다른
것을 찾았다. 묶음만 찾은 자리가 21건이다. 그래서 **한쪽으로 대체하지 않고 합집합을 쓴다.**

**렌즈를 셋 넣은 5라운드에서 한 렌즈가 통째로 빠졌다.** 지적이 0건인 것이 아니라 그 렌즈를
다루지 않았다. 2개를 넣은 네 라운드는 매번 둘 다 다뤘다. 지적마다 렌즈 이름을 붙이게 한
덕분에 빠진 것을 알 수 있었다.

## `CLAUDE.md` 규칙 추가 — 저장소 소유자의 사전 승인

**저장소 소유자가 이 세션에서 사전 승인했다.** "측정하고 한꺼번에 넣어라. 제안하지 말고 바로
넣고, 1차 작업 보고할 때 알려 달라"는 지시였다. 승인 없이 넣은 것이 아니다. 다음 세션이
이 기록을 근거로 확인할 수 있게 여기 남긴다.

넣은 것은 여섯이다. 앞의 넷은 "리뷰를 돌릴 때", 뒤의 둘은 "문서 작업 시" 절이다.

1. 리뷰 입력에서 기록 폴더를 뺀다 (측정: 호출당 20% 절감)
2. 개별 호출과 묶음 호출을 둘 다 돌리고 합집합을 쓴다 (측정: 위 표)
3. 묶음 호출에 렌즈를 셋 이상 넣지 않고, 지적마다 렌즈 이름을 붙이게 한다 (측정: 렌즈 누락)
4. 리뷰 실행 여부를 산출물 파일로만 판정하고, 사람이 없을 때 "돌리는 중"을 보고로 쓰지 않는다
5. 수리 라운드에서 **내가 새로 쓴 서술까지** 전수 확인한다 (blocker 6건 중 3건의 기전)
6. 빈자리를 메우려고 확인할 수 없는 사실을 단정하지 않는다 (Wintun API 건)

4번은 이 세션에서 같은 실수를 두 번 했기 때문에 넣었다. 리뷰를 띄웠다고 보고하고 실제로는
띄우지 않았다. 두 번 다 사용자가 물어서 잡혔다. 가드를 만들어 시험했더니 **시작 시점 검사는
사용량 한도 실패를 잡지 못했다.** 띄운 직후에는 `running` 이 참이고 오류는 몇 초 뒤에 난다.
그래서 판정을 산출물 파일로 옮겼다.

## 배운 것 하나 더

**기록 문서도 리뷰 대상이고, 내가 센 수치는 틀린다.** 12~15라운드의 지적 10건 중 6건이

라운드마다 넣을 필요는 없다. 그리고 **집계는 산출물을 세어 적되 무엇을 세는지도 확인한다.** 표를 눈으로 더해 세 번 틀렸고,
스크립트로 센 뒤에도 입력 범위가 틀려 한 번 더 틀렸다. 리뷰어가 매번 잡았다.

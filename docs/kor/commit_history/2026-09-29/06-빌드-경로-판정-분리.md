# 빌드 경로 판정을 한 자리로 모으고 잠금 실패를 다시 쟀다

## 왜 했나

빌드 산출물의 기본 위치가 `%LOCALAPPDATA%\Sangtachi\build` 였다. 저장소 소유자가 그 위치를
`C:\me\build` 로 옮기라고 정했다. 옮기면서 두 가지가 같이 걸렸다.

- 기본값이 네 스크립트(`build.ps1`, `test.ps1`, `cli-check.ps1`, `e2e-check.ps1`)에 같은
  식으로 네 번 적혀 있었다
- 기계마다 다른 절대 경로를 레포에 박을 수 없다

그리고 애초에 산출물을 레포 밖으로 뺀 근거(레포 안 4/18 실패, 레포 밖 0/18)가 약해서
(`p = 0.052`, 잠그는 프로세스 미확인) 지금도 같은지 다시 쟀다.

## 저장소 소유자가 정한 것

**이 기계의 빌드 루트는 `C:\me\build` 다.** 동기화 폴더(`C:\me\sync`) 밖이다.
처음에는 레포의 상위 폴더(`CSP400\build`)로 옮겼으나 그 자리도 동기화 폴더 안이라는 것을
확인하고 한 단계 더 올렸다.

## 무엇을 바꿨나

| 묶음 | 내용 |
|------|------|
| 신설 | `scripts/buildpath.ps1`. `Resolve-BuildDir` 와 `Get-BuildRootFromFile` 둘이 경로를 정한다 |
| 우선순위 | `-BuildDir` 로 준 값 -> `scripts/build-root.local` 의 첫 유효 줄 + `\<Config>` -> `%LOCALAPPDATA%\Sangtachi\build\<Config>` |
| 루트 형식 | 드라이브 문자로 시작하는 경로나 UNC 만 받는다. 아니면 그 자리에서 멈춘다 |
| 스크립트 넷 | 각자 적던 기본값을 지우고 `buildpath.ps1` 을 점 소스로 부른다 |
| 무시 | `.gitignore` 에 `scripts/build-root.local` |
| 문서 | `README.md` 빌드 절과 실행 절. `build.ps1` 머리 주석 |

**환경 변수로 하지 않았다.** 셸마다 값이 달라 같은 레포가 셸에 따라 다른 곳에 빌드된다.
파일은 새 터미널에서도 같은 값을 준다.

**루트 파일을 읽는 함수의 기본값은 "모르면 값 없음" 이다.** 파일이 없거나 유효한 줄이 없으면
빈 문자열을 돌려주고 `%LOCALAPPDATA%` 로 떨어진다. 읽을 수 없는 내용을 경로로 해석하면 엉뚱한
디렉터리에 빌드하거나 `-Fresh` 가 그것을 지우려 든다.

## 실측으로 다시 쟀다

같은 빌드를 두 위치에서 쌍으로 돌리고 쌍마다 순서를 뒤집었다. 늘 같은 순서로 돌리면 캐시
워밍업 같은 시간 의존 효과가 위치 효과를 흉내 낸다.

| 위치 | 경로 |
|------|------|
| 레포 안 | `Sangtachi\build\measure` |
| 레포 밖 | `C:\me\build\measure\b` |

### 첫 시행은 무효였다

드라이버가 건드리려던 소스 경로를 `client/src/network/wsa.cpp` 로 적었다. 실제 위치는
`client/src/platform/win32/wsa.cpp` 다. mtime 을 못 올렸으므로 ninja 는 할 일이 없었고
36회가 전부 **아무것도 만들지 않은 실행**이었다. 한 번에 2.8초였던 것이 그 표시다.

**그 결과를 그대로 보고할 뻔했다.** "36회 실패 0건" 은 링크를 한 번도 하지 않았으니 아무것도
재지 않은 값이다. 드라이버에 검사 둘을 넣어 고쳤다.

- 시작할 때 대상 파일이 있는지 본다. 없으면 그 자리에서 멈춘다
- 시행마다 출력에 `Linking CXX executable` 이 있는지 본다. 없으면 `relink=0` 으로 남기고
  판정에서 뺀다

### 두 라운드의 결과

| 라운드 | 조건 | 레포 안 | 레포 밖 | 평균 |
|--------|------|:--:|:--:|:--:|
| 1 | 소스 하나만 건드려 증분 링크 | 0 / 18 | 0 / 18 | 3.7초 |
| 2 | 소스 51개 전량을 건드려 오브젝트 34개 재생성 | **1 / 18** | 0 / 18 | 7.7초 |

2라운드의 실패는 이것이다.

```text
wsa.cpp : fatal error C1083: Cannot open compiler generated file:
  '...\build\measure\client\CMakeFiles\sangtachi_core.dir\src\platform\win32\wsa.cpp.obj':
  Permission denied
```

같은 실행에서 `hash.cpp.obj` 도 같은 오류였다. **컴파일러가 방금 만들려는 `.obj` 를 열지
못했다.** 원래 기록의 `LNK1168`, `LNK1201`, `C1041` 과 같은 계열(빌드 산출물 파일 접근 거부)
이고 단계만 링크가 아니라 컴파일이다.

**탐지 정규식이 그 오류를 못 잡았다.** `C1083` 이 목록에 없어 `lock=0` 으로 기록됐고, 종료
코드 검사가 잡아서 드러났다. 코드 목록만 보고 판정했으면 놓쳤다.

### 무엇을 말할 수 있나

| 측정 | 레포 안 | 레포 밖 |
|------|:--:|:--:|
| 앞선 기록 (전체 빌드) | 4 / 18 | 0 / 18 |
| 이번 1라운드 | 0 / 18 | 0 / 18 |
| 이번 2라운드 | 1 / 18 | 0 / 18 |
| 합 | 5 / 54 | 0 / 54 |

**2라운드만으로는 통계가 서지 않는다.** 단측 Fisher exact `p = 0.5` 다. 세 측정을 합치면
`p = 0.028` 이지만 **세 라운드의 방법이 서로 달라 이 합산은 참고다.**

확인된 것은 셋이다.

- 실패는 레포 안에서만 났다
- 5건 전부 같은 기전이다. 빌드 산출물 파일에 접근하지 못한다
- 레포 밖은 54회 중 0건이다

**잠그는 프로세스는 이번에도 특정하지 못했다.** 측정 중 `GoogleDriveFS` 와 `MsMpEng` 이
돌고 있었다는 것만 기록한다. 그리고 **2라운드의 실패는 36회 중 첫 실행이었다.** 갓 만든
디렉터리를 훑는 효과와 위치 효과가 이 한 건에서는 갈리지 않는다.

실측 원본(CSV 와 실패 로그, 드라이버)은 레포 밖에 둔다.

## Phase 2 공개 STUN 서버 관측

`roadmap.md` Phase 2 검증이 요구하는 관측을 돌렸다. `scripts/e2e-check.ps1` 은 망이 없어도
돌아야 해서 공개 서버를 부르지 않으므로 이것만 따로 한 번 띄웠다.

**판정은 통과다.** 서로 다른 두 서버의 Binding Response 를 파싱해 `XOR-MAPPED-ADDRESS` 를
얻었다. 두 번 돌려 같은 결과가 재현됐다.

| 무엇 | 값 |
|------|-----|
| `stun.result` 줄 수 | 2 |
| 답한 서버 | `stun.cloudflare.com:3478`, `stun.l.google.com:19302` |
| 두 줄의 `mapped` | **같다.** 목적지가 달라도 매핑이 갈리지 않았다 |
| `stun.duplicate` | 1건. 기본 목록의 앞 두 이름이 같은 주소로 풀렸다 |
| `session.failed` | 없다 |

**이 절이 그 검증이 요구하는 레포 쪽 기록이다.** 관측이 몇 건이고 서버별로 갈렸는지만
적는다.

**관측값 자체는 레포에 적지 않는다.** 공인 IP 가 들어가고, `tools/nat-probe/` 의 실측 원본을
`.gitignore` 로 로컬 보관하는 것과 같은 이유다.

**결과를 읽는 자리는 표준 오류다.** `stun.result` 줄이고 표준 출력은 0바이트다. 이 Phase 에는
`ROOM` 도 `FAIL` 도 나갈 자리가 없기 때문이다.

**확인하지 못한 관측이 하나 남았다.** 두 실행 모두 마지막에 세 번째 서버의 응답으로 보이는
`rx.raw` 한 줄이 더 있었는데, 대응하는 `stun.result` 도 `drop_*` 카운터도 없었다. 단계를
마친 뒤 도착한 응답을 어떻게 세는지 `protocol.md` 7장 수신 분류와 코드를 대조해야 안다.
**결함이라고 단정하지 않는다.** 그 자리는 `plan.md` 가 Phase 3 으로 걸었다.

### 확정 라운드의 2건이 진짜였다

`build-root.local` 에 상대 경로를 적으면 `Resolve-BuildDir` 가 부르는 쪽의 현재 디렉터리를
기준으로 경로를 만든다. 그 자리에 한 번 빌드하면 `CMakeCache.txt` 가 생겨 **`-Fresh` 의 삭제
안전장치도 통과한다.** 오타 하나가 엉뚱한 디렉터리를 지우는 경로가 된다.

**그런데 리뷰어가 준 수정안도 불충분했다.** `[System.IO.Path]::IsPathRooted` 를 쓰라고 했는데
그대로 넣으니 케이스 하나가 떨어졌다.

```text
FAIL  drive-less root is rejected: expected 'THROW', got '\noroot\Debug'
```

`IsPathRooted` 는 이름과 달리 `\noroot` 에도 참이다. 현재 드라이브에 붙는 드라이브 상대
경로이기 때문이다. `CLAUDE.md` 재발 방지 규칙 7번이 그대로 걸린 자리다. 그래서 배제가 아니라
**허용 목록**으로 바꿨다. 드라이브 문자로 시작하는 경로와 UNC 둘만 받는다.

**정규식으로 판정한 이유가 하나 더 있다.** `IsPathFullyQualified` 는 Windows PowerShell 5.1
에 없다. `README.md` 가 `powershell` 로 부르는 경로를 함께 지켜야 한다.

**고친 뒤 같은 렌즈를 다시 돌렸더니 그 허용 목록이 아직 느슨했다.** UNC 판정이 `\\server` 만
있어도 통과해서 `Join-Path` 가 `\\server\Debug` 를 만든다. 공유 이름 자리에 빌드 구성 이름이
들어간 경로다. 서버와 공유를 모두 요구하도록 좁혔다. **판정을 좁히는 수정은 한 번에 끝나지
않는다는 것**이 이 두 라운드의 교훈이다.

### 기각 4건

**셋은 리뷰 입력 범위가 만든 것이다.** 문서 렌즈에 `scripts/` 를 넣지 않았더니
"`buildpath.ps1` 이 diff 에 없다", "스크립트 넷을 고쳤다는데 없다", "검증 주장이 없는 코드를
가리킨다" 로 돌아왔다. **셋 다 스테이징에 있다.** `git diff --cached --stat` 으로 확인했다.
`CLAUDE.md` 가 말하는 "없다 류의 지적은 HEAD 를 직접 확인한 뒤에 받거나 기각한다" 에 해당한다.

**남은 하나는 판정이 갈린 자리다.** `roadmap.md` Phase 2 검증이 관측 기록을 어디에 두라고
했는지를 두고, 리뷰어는 `roadmap.md` 자신을 고치라고 봤다. 그 문서가 적은 것은 "기록은 레포
밖에 둔다. 레포에는 관측이 몇 건이고 서버별로 갈렸는지 아닌지만 적는다" 이고 **어느 파일인지는
정하지 않았다.** 살아 있는 문서는 그 시점의 관측을 담는 자리가 아니고 `commit_history/` 가 그
일을 하므로 이 기록이 그 자리다. 위 Phase 2 절에 그 판단을 적었다.

**문서 렌즈의 반영 1건은 그 기각에서 나왔다.** 이 절이 요구된 레포 쪽 기록이라는 문장이 없으면
다음 사람이 같은 지적을 다시 한다.

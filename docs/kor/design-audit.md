## 1. 점검 방법

diff가 아니라 **완성된 문서 전문**을 대상으로, 서로 다른 렌즈의 독립 리뷰 3회를 병렬로 돌렸다.

| 렌즈 | 질문 |
|------|------|
| 메커니즘 | 이 문서대로 정확히 구현하면 런타임에 어디서 깨지는가. 구현자가 스스로 발명해야 하는 구멍은 어디인가 |
| 플랫폼 | Windows/Wintun/방화벽/권한/AWS의 현실 중 문서가 무시하거나 틀리게 안 것은 무엇인가 |
| 성립성 | 한 학기 1인 프로젝트로서 일정과 성공 기준이 논리적으로 성립하는가 |

결과: **blocker 20건, warn 25건.**

## 2. 근본 원인

개별 버그가 아니라 두 가지 구조적 원인에서 파생됐다.

**원인 1. 시나리오를 끝에서 끝까지 추적한 적이 없다.**
문서는 "어떤 컴포넌트가 있는가"와 "어떻게 검증하는가"는 적었지만 "패킷 한 개가 어디서 어디로 가며 각 지점에서 무엇이 참이어야 하는가"를 추적하지 않았다. 그래서 리뷰가 실제로 추적할 때마다 새 구멍이 나왔다.

**원인 2. 지적을 고치면서 새 결함을 넣었다.**
이전 리뷰 라운드에서 지적을 국소적으로 반영하다 보니, 고친 자리가 새로운 모순이나 달성 불가능한 기준을 만들었다.

| 이전에 추가한 것 | 이번에 드러난 문제 |
|---|---|
| NFR-9 "STUN과 터널이 같은 소켓" | 그 소켓의 수신 소유권과 역다중화를 정의하지 않아 두 읽기가 서로의 패킷을 훔친다 |
| "지원 조건 = 두 STUN 서버 결과 일치" | 매핑 거동만 보고 필터링 거동을 보지 않았다. 조건을 만족해도 홀펀칭은 실패할 수 있다 |
| Phase 7 "카운터가 캡처와 정확히 일치, 오차 불허" | 캡처 위치, offload, 캡처 손실 때문에 정상 구현도 통과 못 한다 |
| Phase 8 "F3 지연 ±30ms" | 샘플링 방식이 달라 정상 터널도 순간적으로 실패한다 |
| Phase 4 "외부 관측점 probe로 매핑 수명 측정" | 그 외부 관측점 컴포넌트를 설계 어디에도 만들지 않았다 |
| A-2 "통제된 실패 시나리오 필수" | 방화벽 차단은 NAT 통과 실패가 아니라 매핑 거동 분석의 근거가 못 된다 |

교훈: **과하게 조인 검증 기준은 느슨한 기준만큼이나 나쁘다.** 정상 구현이 떨어지는 기준은 기준이 아니다.

### E. 프로젝트 성립성

| # | 문제 | 상태 |
|---|------|------|
| 18 | C-5 우선순위가 최소 산출물을 지키지 못한다. P1을 버리면 M-5가 사라지고 P3을 버리면 M-6과 과목 요구 분석이 함께 사라진다. Phase 1~9 안에서 실제로 버릴 수 있는 것은 P2(Wintun + 가상 IP + Minecraft, Phase 6~8)뿐이다. P4는 애초에 스트레치라 계산에 들어가지 않는다 | 대기, 후속 4번 |

| 20 | 가용한 두 가정망이 대칭형 거동이면 최소 성공이 불가능하고 대안이 없다. 릴레이는 Phase 9 이후 스트레치라 구제가 안 된다 | **해소 (2026-09-20).** 실측 22건, 망 7곳 전부 `endpoint-independent`, 대칭형 0건. 대비책 미도입, M-1/M-4 유지. **잔여 위험은 남는다** — 조건이 바뀌면 다시 성립하며 대비책이 없다. Phase 4 착수, Phase 8 준비, 시연 직전 세 지점에 재측정 게이트를 뒀다. [ADR 0001](decisions/0001-직접-연결-대비책-미도입.md) |

**20번이 가장 위험했다.** 나머지는 고치면 되지만 이것은 학기 중반에 드러나면 되돌릴 시간이 없었다. 프로젝트 전체가 통제 불가능한 외부 조건에 인질 잡혀 있었다.

**2026-09-20 실측으로 해소됐다.** 다만 인질 구조 자체가 사라진 것은 아니다. 측정은 특정 시점의 관측이고 공유기 교체나 ISP 구성 변경으로 무효가 될 수 있다. 대비책의 대비책은 여전히 없으므로 Phase 8 준비 절차에 시연 직전 재측정을 넣는다.

## 6. 재발 방지

이번 점검에서 얻은 규칙이다.

1. **문서를 완성했다고 선언하기 전에 시나리오 하나를 끝에서 끝까지 추적한다.** 패킷 한 개, 실패 한 건, 재시작 한 번. 컴포넌트 목록과 검증 항목만으로는 구멍이 안 보인다.
2. **diff 리뷰는 국소 결함만 잡는다.** 마일스톤마다 전문 대상 감사를 따로 돌린다.
3. **검증 기준은 정상 구현이 통과하는지부터 확인한다.** 통과 못 하는 기준을 넣으면 나중에 기준을 낮추게 되고, 그때는 진짜 결함도 같이 통과한다.
4. **지적을 반영할 때 그 수정이 만드는 새 계약을 함께 정의한다.** "같은 소켓을 쓴다"는 제약을 넣었으면 그 소켓의 소유권과 역다중화도 같이 정해야 했다.
5. **같은 주장을 두 곳 이상에 복사하지 않는다.** 주장은 한 곳에 쓰고 나머지는 링크한다. 복사하면 강도를 낮출 때마다 전부 따라가야 하는데 반드시 한두 곳을 흘린다. 이미 흩어져 있다면 고치기 전에 `grep` 으로 전수 확인하고 한 번에 맞춘다. **예외는 셋이다.** (1) `docs/kor` 와 `docs/eng` 의 미러 쌍(한국어가 원본). (2) **요약 색인.** 규칙 이름 한 줄까지만 적고 본문을 옮기지 않으며 원문 위치를 밝힌다. (3) **역사 기록** — `commit_history/` 와 실측 기록. 이들은 특정 시점의 사실을 적는 문서이므로 그때의 근거와 수치를 그대로 담는다. **원문이 바뀌어도 고치지 않는다.** 링크만 남기면 나중에 읽을 때 그 시점의 판단이 아니라 현재 문서를 보게 되어 기록의 목적이 사라진다.
6. **문서에 실행 가능한 절차를 넣으려면 코드와 같은 수준으로 검토한다.** 입력 검증, 중단 시 정리, 권한 범위, 결과 해석 범위까지 본다. 그럴 자신이 없으면 절차를 도구에 넣고 문서는 가리키기만 한다. **아직 실행하지 않은 시험의 스크립트는 문서에 두지 않는다.**
7. **판정을 내는 함수는 검증을 먼저 쓴다.** 기본값은 "모르면 판정 불가"다. 확실할 때만 단정한다. 표준 라이브러리 술어를 이름만 보고 믿지 않는다 (`is_private` 는 루프백과 문서용 대역을 포함하고, `is_global` 은 멀티캐스트에 참이다). 허용 목록이 배제 목록보다 안전하다.

**5~7번은 2026-09-20 blocker 20 작업에서 얻었다.** 크로스 모델 리뷰 19라운드에 93건이 나왔고
그중 56건이 두 곳에 몰렸다.

| 위치 | 건수 | 원인 |
|------|:----:|------|
| `natprobe.py` 의 `classify_nat` | 31 | 판정 함수를 편의 기능처럼 20줄로 썼다. 잘못된 입력에서 단정을 냈다 (규칙 7) |
| ADR 0002 의 PowerShell 절차 | 25 | 아직 실행하지 않은 시험의 스크립트를 문서에 넣었다. 13라운드 이후 10건 중 9건이 여기서 나왔다 (규칙 6) |

나머지는 대부분 같은 주장을 8곳(4개 문서 × kor/eng)에 복사해 두고 한 번에 한두 곳만 고친
결과다 (규칙 5). **4번도 다시 어겼다.** 원인 서술을 "유력" 으로 낮추면서, 그 원인에 의존하던
결론은 단정형으로 남겨뒀다.

### 이번에 확인한 것

초판이 blocker 30건을 받은 것 자체는 나쁜 소식이 아니다. **구현 전에 나왔기 때문이다.** 같은 결함이 Phase 4 구현 중에 드러났다면 원인 규명에만 며칠이 들었을 것이고, 특히 중복 억제 부재와 지명 교착은 "가끔 연결이 안 된다" 형태로 나타나 재현조차 어려웠을 것이다.

다만 2장의 근본 원인이 여전히 유효하다는 뜻이기도 하다. 초판을 쓸 때도 시나리오를 끝까지 추적하지 않았다. 상태 머신 표는 만들었지만 "같은 NAT 뒤의 두 피어", "재시작 직후 도착한 이전 epoch 패킷" 같은 구체적 상황을 대입해 보지 않았다. 6장의 재발 방지 규칙 1번을 문서마다 실제로 적용해야 한다.

### 3차, 4차 검증

2차 수정본을 다시 두 번 검증했다. 수렴하고 있다.

| 라운드 | blocker | 성격 |
|--------|---------|------|
| 초판 | 30 | 설계 자체의 공백 |
| 3차 | 5 | 대부분 2차에서 새로 넣은 엔드포인트 학습의 부작용 |
| 4차 | 5 | 의사코드 분기 정밀도와 직전 수정끼리의 상호작용 |

3차 blocker:

| 결함 | 수정 |
|------|------|
| 재협상 시 양쪽이 각자 로컬 epoch를 새로 뽑아 **무한 epoch 핑퐁**. 두 피어가 영원히 연결되지 않는다 | 9.5에서 로컬 epoch/nonce 유지. 로컬 epoch는 `IDLE`에서 새 시도를 시작할 때만 바뀐다 |
| 비트맵 `shift == 64`에서 비트맵을 지워 직전 `highest`가 중복인데도 다시 수용됨 | `shift > 64`일 때만 지우고 `shift == 64`는 비트 63을 세움 |
| 재정렬 윈도우에서 수용된 오래된 패킷이 엔드포인트를 이전 경로로 되돌림 | 10.4 (b): `highest`를 전진시킨 패킷만 학습에 사용 |
| 출발지를 위조하면 게임 트래픽 전체를 임의의 피해자에게 돌릴 수 있어 2장의 "제3자 피해 차단" 약속과 모순 | 10.4 (c): 후보 집합 밖 주소는 nonce 경로 검증 통과 후에만 전환 |
| 32비트 시퀀스 누적 뺄셈이 한 바퀴 후 무너짐 | 순환 없는 64비트 `position`과 `baseline` 도입 |

4차 blocker:

| 결함 | 수정 |
|------|------|
| `seq == highest`가 "오래됨" 분기로 내려가 `back == 0`, `uint64_t{1} << (0-1)` 미정의 동작 | 명시적 중복 판정을 먼저 배치 |
| `if / if / else`로 써서 `shift > 64`가 비트맵을 지운 뒤 `else`로도 들어가 64 초과 시프트 수행 | `if / else if / else` 상호 배타 분기 |
| 재정렬 패킷의 위치를 계산하지 않고 상태값 `position`을 써서 `accepted > expected` 언더플로 | 패킷별 `pkt_pos` 정의 (전진이면 `position`, 재정렬이면 `position - back`) |
| 재협상이 후보 밖 출발지를 바로 학습해 10.4 경로 검증을 우회 | `HELLO_ACK`은 데이터그램 출발지로 직접 보내되 `peer_endpoint`는 바꾸지 않음. 단건 응답과 대량 전환을 구분 |
| 경로 검증 nonce가 "시도당 하나" 규칙과 충돌 | probe nonce를 별도 표로 분리 (5.1, 8.2) |

### 현재 상태

4차 수정까지 반영했다. 5차 검증은 돌리지 않았으므로 **남은 결함이 없다고 주장하지 않는다.** 다음에 이 문서를 건드릴 때 한 번 더 돌린다.

수렴 추세(30 -> 5 -> 5)와 결함 성격의 변화(설계 공백 -> 부작용 -> 의사코드 정밀도)로 보아 구조적 문제는 해소된 것으로 판단한다. 다만 4차 5건이 **전부 직전 수정이 만든 부작용**이라는 점은, 수정이 만드는 새 계약을 함께 정의하라는 6장 규칙 4번을 아직 충분히 지키지 못하고 있다는 뜻이다. 넷은 3차 수정에서 나왔고, `seq == highest` 분기는 2차에서 중복 억제 알고리즘을 새로 넣으면서 생겼다. 초판에는 그 알고리즘 자체가 없었다.

| drain 루프에 상한이 없어 도착 속도가 처리 속도보다 빠르면 타이머가 한 번도 돌지 않는다. keepalive가 멈춘다 | 소스별 한 바퀴 64개 예산. 예산에 걸리면 `busy`로 표시하고 타임아웃 0으로 즉시 재진입 |
| Phase 1~5에 어댑터가 없는데 `drain_wintun`을 무조건 호출. 콘솔 이벤트는 대기 집합에 넣어놓고 아무도 처리하지 않아 루프가 스핀 | 세션 NULL 가드 추가, `drain_console` 신설, 콘솔 이벤트를 자동 리셋으로 지정 |
| 뮤텍스 큐를 두고 "`[loop]`는 블록하지 않는다"고 주장. 소비자가 락을 쥔 채 밀리면 거짓말이 된다. roadmap 검증 기준이 통과 불가 | 락 없는 SPSC 링으로 교체. 가득 차면 새 레코드를 버린다 |

세 번째는 6장 규칙 3번의 사례다. **정상 구현이 통과할 수 없는 기준을 내가 또 썼다.**

3차와 4차는 전부 내 수정의 부작용이었다. `now()`를 두 번 불러 언더플로가 나면 타임아웃이 49.7일이 되는 것, `ERROR_INVALID_DATA` 분기에 반환이 없어 `NULL` 포인터가 흘러가는 것, 종료 표식을 유실 허용 큐에 넣어 하필 가득 찬 순간 버려지는 것, 3초 소켓 타임아웃이 2초 join 상한보다 길어 상한이 무의미해지는 것.

5차에서 나온 blocker는 성격이 달랐다. 4차에서 protocol.md 11장의 타이머 순서 규칙을 "꺼낸 시각" 기준으로 바꿨는데, `architecture.md` 3.2.4에 남은 "도착 시각" 서술을 함께 고치지 않았다. **두 문서가 서로 다른 규칙을 말하고 있었다.** 6장 규칙 4번을 또 못 지킨 것이다.

6차에서 `LGTM - no blockers`가 나왔다. protocol.md 때와 달리 수렴을 확인하고 끝냈다.

### 여기서 배운 것

protocol.md는 4차에서 멈췄고 남은 결함이 없다고 주장하지 않았다. 이번에는 깨끗한 라운드가 나올 때까지 돌렸고, **실제로 5차에서 문서 간 모순이 하나 더 나왔다.** 4차에서 멈췄다면 그게 남았을 것이다.

1~4차에서 렌즈를 바꾼 것이 유효했다. 같은 프롬프트를 여섯 번 돌렸다면 1차에서 잡힌 것들만 반복해서 확인했을 것이다.

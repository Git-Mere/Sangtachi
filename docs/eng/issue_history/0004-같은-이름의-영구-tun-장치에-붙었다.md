# 0004. Attached to a persistent TUN device with the same name

- Status: Resolved
- Found: 2026-10-31
- Related: [`../linux-prereq.md`](../linux-prereq.md) section 3, `client/src/platform/linux/tun.cpp`, [`../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md`](../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md)

## Symptom

No symptom was actually hit. The pre-commit cross review (Codex `gpt-6.1-sol`) pointed it out. If a persistent TUN device with the same name (`Sangtachi`) already exists,
`TUNSETIFF` does not create a new device but attaches to that one. Then the client changes the address and MTU of someone else's device, and the device remains
after it ends. This contradicts "opens it non-persistent. When the process ends, the kernel deletes the device" in `linux-prereq.md` section 3.

## Investigation

On `mere-galaxy`, a persistent device was created with `sudo ip tuntap add Sangtachi mode tun`, and the build before the fix was started as host.

- It attached to that device and got as far as `adapter.open` and `adapter.address virtual_ip=10.100.0.1`
- The device remained after the process ended. Its state was `UP`, and its MTU had been changed to 1400

## Cause

**Confirmed.** The reproduction above. Without `IFF_TUN_EXCL` on `TUNSETIFF`, it attaches to a device with the same name.

## Handling

`IFF_TUN_EXCL` is passed to `TUNSETIFF`. If a device with the same name exists, it does not attach and startup fails. `linux-prereq.md` section 3 records that case and
how to handle it.

The first build failed with `-Werror=overflow`. `IFF_TUN_EXCL` is `0x8000`, so it hits the sign bit of `ifr_flags`, which is a `short`.
It is stored with `static_cast<short>`. The kernel reads the same bit.

## Result

- In the same reproduction, the fixed build failed to start with `adapter.error reason=open op=TUNSETIFF code=16` (`EBUSY`). The device stayed at MTU 1500 and not
  `UP`
- With no persistent device, the lifetime test passed with the fixed build ([0003](0003-linux-tun-수명-시험이-열자마자-패킷을-받았다.md)). The two-direction field test was run with the build before the fix and
  was not run again with the fixed build

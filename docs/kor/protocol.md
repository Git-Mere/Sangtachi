# Tunnel Protocol v1

**프로젝트:** Direct-First P2P Virtual Network for Multiplayer Games
**상태:** 구현 전 확정본. 이 문서와 코드가 다르면 코드가 틀린 것이다.
**설계 배경:** [`architecture.md`](architecture.md) / **요구사항:** [`spec.md`](spec.md)

> English version: [`../eng/protocol.md`](../eng/protocol.md)

목적은 **구현자가 아무것도 발명하지 않아도 되게** 하는 것이다. 값이 정해지지 않은 곳이 있으면 그것은 이 문서의 결함이다.

---

## 1. 범위와 전제

| 항목 | v1 확정값 |
|------|-----------|
| 외부 전송 | IPv4 UDP만 |
| 내부 페이로드 | IPv4 패킷만. 내부 IPv6는 폐기하고 카운터 증가 |
| 바이트 오더 | 모든 다중 바이트 정수는 **빅엔디안** |
| 피어 수 | 한 방에 2 피어 |
| 암호화 | 없음 (2장) |

IPv6 지원은 v2 이후다. v1은 `AF_INET`으로만 소켓을 열고 STUN 서버도 IPv4로만 해석한다.

## 2. 보안 모델

**v1은 기밀성, 무결성, 피어 인증, 재전송 공격 방어를 제공하지 않는다.** 이것은 누락이 아니라 명시적 선택이다.

경로상 또는 경로 밖 공격자가 `peer_id`와 `session_epoch`를 알거나 추측하면 다음이 가능하다.

- 게임 트래픽 도청 및 변조
- 임의 패킷 주입
- 위조 `CLOSE`로 세션 강제 종료
- 엔드포인트 로밍(10.5)을 악용한 트래픽 탈취

**위조 `HELLO`로 세션 재협상을 유도하는 것은 전제가 더 약하다. `peer_id`만 있으면 된다.**
재협상의 계기는 "고정된 epoch와 다른 `HELLO`"이므로(9.3) 공격자는 epoch를 알 필요가 없고
아무 값이나 넣으면 된다. `HELLO`가 통과해야 하는 나머지는 `virtual_ip` 일치(5.1)뿐인데 그
값은 `10.100.0.1`과 `10.100.0.2`로 예측 가능하다.

**한 발로 양쪽 세션이 끝난다. 확정이다.** 경로는 넷이다.

- 9.5 재협상 1단계가 진짜 상대의 살아 있는 epoch를 폐기 목록에 넣는다. 그 뒤 상대가 보내는
  모든 패킷이 8.1 검사 8번에서 `drop_retired_epoch`로 버려진다
- 상대가 `CONNECTED`라면 10.3 펀치에 따라 `HELLO` 재전송을 이미 멈췄다. 상대가 아직 펀치
  중이라도 그 재전송 `HELLO`는 폐기된 epoch를 달고 있어 같은 검사에서 버려진다
- 검사 8번이 8.2 epoch 및 출발지 검사와 9.3 epoch 규칙보다 앞이다. 그래서 그 `HELLO`는
  재협상의 계기가 되지 못한다
- 상대가 새 epoch를 뽑는 것은 9.6 실패 전이에 따라 `IDLE`부터 새 시도를 시작할 때뿐이다.
  그것은 상대가 유휴 타임아웃 50초를 채운 뒤이고, 우리 펀치 마감 10초보다 늦다

결과는 **우리 쪽 `PEER_HANDSHAKE_FAILED` 10초, 상대 쪽 `TUNNEL_DROPPED` 50초**다.
9.5 재협상의 상한(횟수와 간격)은 반복 비용을 유한하게 만들 뿐 이 한 발을 막지 못한다.

**최종 보고서는 이 전제를 `peer_id` 하나로 적어야 한다.**

> **왜.** 둘 다 필요하다고 적으면 공격 난이도를 실제보다 높게 말하는 것이 된다.

8.4 `DATA` 내부 검증은 **공격 방어 수단이 아니다.** 오배달, 버그, 잘못된 라우팅으로 인한 우발적 주입을 막는 위생 장치다.

이 선택의 근거는 `spec.md`의 비목표다. 자체 암호 알고리즘 개발과 인증된 피어 세션은 스트레치 목표이며 v1 범위 밖이다. 최종 보고서는 이 한계를 명시해야 한다.

**이 장은 터널 경로의 위협만 다룬다.** 제어 평면 경로(평문 TCP, 호출자 무인증, `room_id`가 유일한 비밀)의 신뢰 가정과 그 결과는 [`control_plane.md`](control_plane.md) 1.2 신뢰 가정이 갖는다. 최종 보고서는 두 한계를 나란히 적어야 한다.

다만 **타인에게 피해를 주는 경로는 막거나 상한을 건다. 둘을 구분해 적는다.**

| 경로 | v1의 처리 |
|------|-----------|
| 증폭 — 후보나 수신 출발지가 브로드캐스트·멀티캐스트인 경우 | **막는다.** 10.1 후보 수집과 위생, 7장의 출발지 위생이 필수인 이유다 |
| 유니캐스트 반사 — 후보 목록에 임의의 제3자 주소가 들어오는 경우 | **막지 못한다. 상한만 있다.** 후보 8개(`MAX_CANDIDATES`) × 펀치 10초 ÷ 200ms = 최대 400발이고, `CONNECTED`에 도달하면 재전송이 멈춘다 |
| 유니캐스트 반사 — 위조 출발지에 대한 회신(`HELLO_ACK`, `PONG`, 검증 `HELLO`) | **막지 못한다. 상한만 있다.** 9.4 전이표의 무검증 목적지 공통 예산이 세션당 초당 5패킷, 순간 10패킷으로 제한한다 |

**후보를 넣을 수 있는 쪽은 제어 평면만이 아니다.** 방에 참가한 상대 피어가
`register_candidate`로 임의의 유니캐스트 주소를 등록할 수 있고, 서버는 형식만 본다. 악의적
서버가 같은 일을 할 수 있다는 것은 `control_plane.md` 1.2 신뢰 가정이 적었다.
**두 문서가 같은 경로를 말한다.** 여기는 상한을, 그 문서는 신뢰 가정을 적는다.

## 3. 상수

```cpp
constexpr uint32_t TUNNEL_MAGIC   = 0x53414E47;  // "SANG"
constexpr uint8_t  TUNNEL_VERSION = 0x01;
constexpr size_t   HEADER_SIZE    = 20;
constexpr size_t   MAX_INNER      = 1452;
constexpr size_t   MAX_DATAGRAM   = HEADER_SIZE + MAX_INNER;   // 1472
constexpr uint32_t STUN_COOKIE    = 0x2112A442;                // RFC 5389
constexpr size_t   MAX_CANDIDATES = 8;                         // 피어당 상한
constexpr size_t   REPLAY_WINDOW  = 64;                        // 4.5. seen_bits 폭과 같이 움직인다
constexpr size_t   MAX_PENDING_PINGS   = 16;
constexpr size_t   MAX_PROBE_PATHS     = 4;                    // 10.4 (c) 동시 잠정 경로 상한
constexpr size_t   MAX_RETIRED_EPOCHS  = 16;                   // 4.3 폐기 목록 상한
constexpr size_t   MAX_RENEGOTIATIONS  = 8;                    // 9.5 시도당 재협상 상한
constexpr uint32_t MIN_RENEG_INTERVAL_MS = 1000;               // 9.5 재협상 최소 간격
constexpr size_t   UNVERIFIED_TX_BUCKET  = 10;                 // 9.4 무검증 목적지 송신 예산 용량
constexpr size_t   UNVERIFIED_TX_REFILL  = 5;                  // 9.4 초당 보충
```

**상대의 입력으로 자라는 표는 넷이고 전부 상한이 있다.** 후보 목록(`MAX_CANDIDATES`),
`pending_pings`(`MAX_PENDING_PINGS`), 잠정 경로(`MAX_PROBE_PATHS`), 폐기 목록
(`MAX_RETIRED_EPOCHS`). **상대의 입력으로 자라면서 상한 없는 표를 새로 만들지 않는다.**
상대를 인증하지 않으므로 그런 표를 키우는 입력은 전부 위조 가능하다.

**우리 자신의 시도만으로 자라는 표는 상한을 두지 않는다.** 5.1 `HELLO`의 시도 nonce 폐기 목록이
그것이다. 항목은 우리가 새 시도를 시작할 때만 하나 생기고 2분 뒤 사라지므로 공격자가 키울
수 없다. 상한이 없는 것이 아니라 **상한을 걸 대상이 아니다.** 중복 억제 상태(4.5)도 표가
아니다. 상대 epoch 하나에 대한 상태 하나이고, 재협상이 그것을 초기화한다(9.5 3번, 8.3).

`TUNNEL_MAGIC`의 첫 바이트 `0x53`은 상위 2비트가 `01`이고, STUN 메시지는 상위 2비트가 반드시 `00`이다. 이 성질이 7장 분류의 근거이므로 magic 값을 바꿀 때 유지해야 한다.

## 4. 헤더

### 4.1 와이어 레이아웃

```text
 오프셋  크기  필드              타입        설명
   0      4   magic             uint32 BE   0x53414E47 고정
   4      1   version           uint8       0x01 고정
   5      1   type              uint8       PacketType (5장)
   6      2   payload_length    uint16 BE   헤더 뒤 바이트 수
   8      4   peer_id           uint32 BE   송신 피어 식별자
  12      4   session_epoch     uint32 BE   송신 피어의 이번 세션 시도 식별자
  16      4   sequence          uint32 BE   방향별 단조 증가 카운터
  = 20 바이트
```

4바이트 필드가 모두 4의 배수 오프셋에 오므로 MSVC 기본 정렬에서도 패딩이 없다. 그래도 구조체를 `memcpy` 하지 않는다. 바이트 오더 변환이 필요하고 정렬이 우연히 맞는 것에 의존하면 조용히 깨진다. **필드 단위로 직렬화**하고 길이는 `HEADER_SIZE` 상수를 쓴다.

### 4.2 peer_id

제어 평면이 방 참가 시 할당한다. **한 방 안에서 유일하다.** 두 피어의 `peer_id`가 같으면 송신자 판별과 자기/상대 구분이 불가능하므로, 제어 평면은 그런 할당을 하지 않고 클라이언트는 `get_peers` 응답에서 자신과 같은 값을 발견하면 `CONTROL_PLANE_EXCHANGE_FAILED`로 중단한다.

### 4.3 session_epoch

**세션 시도 단위**로 뽑는다. 프로세스 단위가 아니다. `IDLE`에서 새 시도를 시작할 때마다 새로 뽑으며 그 시도가 끝날 때까지 바뀌지 않는다. 0은 쓰지 않는다.

이 필드가 없으면 재시작이나 재시도 후 이전 시도의 지연 패킷이 새 세션에 수용된다. 수신 측은 첫 유효 패킷에서 상대 epoch를 고정(pin)하고, 이후 다른 epoch의 패킷은 9장 규칙에 따라 처리한다.

**OS CSPRNG에서 뽑는다**(`BCryptGenRandom`, nonce와 같은 출처. 5.1). 0이 나오면 다시 뽑는다.
약한 난수원을 쓰면 재시도마다 같은 값이 나올 확률이 커져 아래 폐기 목록이 이전 시도의 패킷을
거르지 못한다. 예측 가능한 값은 2장의 위협 전제를 그만큼 낮춘다.

32비트 난수이므로 충돌 가능성이 있다. **폐기 목록**에 최대 2분간 보관하고, 폐기 목록에 있는 epoch를 담은 패킷은 전부 버린다(8.1 검사 8번).

**보관하는 것은 상대의 epoch다.** 검사 8번이 보는 것은 수신 패킷의 `session_epoch`이고 그것은 **송신자, 즉 상대의 값**이다. 우리 자신의 지난 epoch를 넣어도 어느 수신 패킷과도 일치하지 않으므로 아무것도 거르지 못한다. 등록 대상은 둘이다.

| 언제 | 무엇을 등록하는가 |
|------|-------------------|
| 우리가 `IDLE`에서 새 시도를 시작할 때 | **이전 시도에서 고정했던 상대 epoch.** 고정 전에 끝난 시도는 등록할 값이 없다 |
| 9.5 재협상 | 상대의 직전 epoch (9.5 1번) |

**우리 재시도 방향의 방어선은 폐기 목록만이 아니다.** 이전 시도에서 상대 epoch를 고정하기
전에 끝났다면 등록할 값이 없다. 그 구간의 지연 패킷은 8.2 epoch 및 출발지 검사가 막는다.

- 비-`HELLO` 는 epoch 미고정이라 `drop_no_epoch` 이다
- 이전 시도의 nonce 를 echo 한 `HELLO_ACK` 은 `drop_bad_nonce` 다. 5.1 `HELLO` 가 이전
  nonce 를 재사용하지 않는 이유가 이것이다

폐기 목록은 **고정까지 갔던 시도**를 덮는다.

**폐기 목록은 `MAX_RETIRED_EPOCHS`(16)개까지다.** 가득 찬 상태에서 새 항목이 생기면 가장
오래된 것을 밀어낸다. 항목은 우리 자신의 이전 시도(재시도할 때마다 1개)와 상대의 이전
epoch(9.5 재협상마다 1개)에서만 생긴다. 재협상의 횟수와 간격은 9.5 재협상이 제한한다.

> **왜.** 상한이 없으면 8.1 검사 8번이 모든 수신 패킷마다 조회하는 표가 무한히 자란다.

**상한이 2분 보관보다 먼저다. 그래서 2분은 보장이 아니라 best-effort다.** 2분 안에 항목이
16개를 넘으면 가장 오래된 것이 시간이 되기 전에 밀려난다. 빠른 로컬 재시도와 재협상이
겹치면 실제로 일어난다.

밀려난 epoch를 단 패킷이 뒤늦게 도착하면 8.1 검사 8번을 통과한다. 그때는 **epoch 고정
비교가 두 번째 방어선으로 남는다.**

- 고정값과 다르므로 `HELLO`가 아닌 타입은 `drop_stale_epoch`로 버려진다 (9.3 epoch 규칙)
- `HELLO`만 예외로 9.5 재협상을 유발할 수 있다. 그 피해는 9.5 재협상의 횟수·간격 상한이
  가둔다

**두 방어선을 합쳐서 유한하다**는 것이 이 설계가 주장하는 전부다. "2분 동안 반드시 거른다"는
주장은 하지 않는다.

### 4.4 sequence

- **방향별, 세션 시도별로 하나의 카운터.** 타입을 구분하지 않는다.
- **그 시도의 첫 송신 패킷이 `sequence = 0`이다.** 송신 직전에 현재 값을 할당하고 그 뒤 1을 더한다. 재전송에도 새 번호를 준다.
- 32비트에서 순환한다.

```cpp
// a 가 b 보다 엄격히 새로운가. a == b 는 거짓이다.
bool is_newer(uint32_t a, uint32_t b) {
    return a != b && (uint32_t)(a - b) < 0x80000000u;
}
```

`a == b`에서 참을 반환하면 중복이 새 패킷으로 분류되어 재생 방어가 무력화된다.

### 4.5 중복 억제와 손실 집계

수신 측은 상대 epoch별로 아래 상태를 유지한다.

```cpp
uint32_t highest;      // 지금까지 받은 최대 sequence (32비트 순환)
uint64_t position;     // highest 의 순환 없는 64비트 확장 위치
uint64_t seen_bits;    // back=1..REPLAY_WINDOW 에 해당하는 수신 비트맵. back=b 는 비트 (b-1)
bool     initialized;
```

수신 패킷 처리 순서는 다음과 같다. **이 판정은 어떤 부수 효과보다 먼저 온다.** 유휴 타이머 갱신, 상태 전이, Wintun 주입, `PONG` 매칭은 전부 이 단계를 통과한 뒤에만 일어난다.

**예외는 9.5 재협상 하나다.** 8.2 epoch 및 출발지 검사가 다른 epoch의 `HELLO`를 9.5 로 보내면 재협상이 이 판정보다 먼저 돌고, 그 3번이 중복 억제 상태를 초기화한다. 이 단계는 그 뒤에 새 epoch의 상태로 판정한다. 이유는 8.3 중복 억제에 있다.

```text
initialized 가 거짓이면:
    highest = seq; position = 0; seen_bits = 0; initialized = true
    -> 수용 (전진). 이 패킷의 pkt_pos = 0

seq == highest 이면:
    -> 폐기, drop_duplicate

is_newer(seq, highest) 이면:                       // 전진
    shift = (uint32_t)(seq - highest)              // 1 .. 2^31-1
    if      shift >  64:  seen_bits = 0
    else if shift == 64:  seen_bits = uint64_t{1} << 63
    else:                 seen_bits = (seen_bits << shift) | (uint64_t{1} << (shift-1))
    highest   = seq
    position += shift
    -> 수용 (전진). 이 패킷의 pkt_pos = position

그 외 (오래됨):
    back = (uint32_t)(highest - seq)               // 1 .. 2^31
    back > REPLAY_WINDOW                 -> 폐기, drop_too_old
    seen_bits & (uint64_t{1}<<(back-1))  -> 폐기, drop_duplicate
    seen_bits |= uint64_t{1} << (back-1)
    -> 수용 (전진 없음). 이 패킷의 pkt_pos = position - back
```

경계 네 가지를 틀리기 쉽다.

- **`seq == highest`를 먼저 걸러야 한다.** `is_newer`는 `a == b`에서 거짓이므로 이 경우가 아래 분기로 내려가고, `back == 0`이 되어 `uint64_t{1} << (0-1)`이라는 미정의 동작이 된다. 명시적 중복 판정으로 먼저 처리한다.
- **세 분기는 상호 배타여야 한다.** `if / if / else`로 쓰면 `shift > 64`가 비트맵을 지운 뒤 `else`로도 들어가 64를 넘는 시프트를 수행한다. `if / else if / else`로 쓴다.
- **`shift == 64`에서 비트맵을 지우면 안 된다.** 지우면 직전 `highest`가 `back == 64` 위치에 미기록 상태로 남아 그 패킷이 중복인데도 다시 수용된다. `shift == 64`는 비트 63을 세우는 경우다. `seen_bits << 64`는 C++에서 미정의 동작이므로 별도 분기로 처리한다.
- **모든 비트 연산은 `uint64_t`로 한다.** `1 << 63`은 `int` 시프트라 미정의 동작이다.

위 분기의 리터럴 `64`와 `63`은 `REPLAY_WINDOW`와 `REPLAY_WINDOW - 1`이다. `seen_bits`가
`uint64_t`이므로 **창 크기와 비트맵 폭은 같이 움직인다.** 창을 바꾸려면 두 개를 함께 바꿔야
하며, 상수만 고치고 비트맵을 그대로 두면 시프트가 미정의 동작이 된다.

**손실 집계는 `CONNECTED` 진입 시점에 초기화한다.** 펀치 구간에는 여러 후보로 보낸 `HELLO`가 각각 번호를 소모하지만 실제로 도달하는 경로는 하나뿐이므로, 그 구간의 간격을 손실로 세면 실측이 오염된다.

`CONNECTED`로 전이시킨 패킷을 처리한 **직후**에 기준선을 잡는다.

```text
baseline = position          // 전이 패킷 처리 후의 값
accepted = 0                 // baseline 보다 뒤에서 수용한 고유 패킷 수

이후 수용될 때마다: 그 패킷의 pkt_pos 가 baseline 보다 크면 accepted += 1

expected = position - baseline
손실     = expected - accepted
손실률   = expected > 0 이면 손실 / expected, 아니면 0
```

32비트 `sequence`가 아니라 순환 없는 64비트 `position`으로 계산하므로 시퀀스가 한 바퀴 돌아도 값이 무너지지 않는다.

`pkt_pos`는 전진 패킷이면 갱신된 `position`, 재정렬 패킷이면 `position - back`이다.
`baseline` 이하의 재정렬 패킷을 정확히 배제한다.

> **왜.** 상태값 `position`을 그대로 쓰면 `baseline` 이전에 보내진 재정렬 패킷까지
> `accepted`에 세어 `accepted > expected`가 되고, `손실`이 음수로 언더플로한다.

`drop_too_old`로 버린 패킷은 이미 손실로 확정된 것이므로 되돌리지 않는다. 손실률은 10초 주기로 스냅샷을 찍어 텔레메트리 서비스에 올린다.

## 5. 패킷 타입

| 값 | 이름 | 페이로드 길이 | 용도 |
|----|------|---------------|------|
| `0x01` | `HELLO` | 20 | 홀펀칭 및 핸드셰이크 개시 |
| `0x02` | `HELLO_ACK` | 20 | 상대 `HELLO`를 실제로 받았음을 증명 |
| `0x03` | `KEEPALIVE` | 0 | NAT 매핑 유지 |
| `0x04` | `DATA` | 20 ~ 1452 | 내부 IPv4 패킷 운반 |
| `0x05` | `PING` | 8 | RTT 측정 요청 |
| `0x06` | `PONG` | 8 | RTT 측정 응답 |
| `0x07` | `CLOSE` | 1 | 정상 종료 통지 |

목록에 없는 값은 폐기하고 `drop_unknown_type`을 올린다.

### 5.1 HELLO (20바이트)

```text
 오프셋  크기  필드         설명
   0     16   nonce        이번 시도의 128비트 난수
  16      4   virtual_ip   송신자에게 할당된 가상 IP (uint32 BE)
```

`nonce`는 **OS CSPRNG**에서 뽑는다(`BCryptGenRandom`). 세션 시도당 하나이며 재전송에서는 같은 값을 쓴다. 재전송마다 바꾸면 도착한 `HELLO_ACK`이 어느 nonce에 대한 응답인지 맞출 수 없다. 이전 시도의 nonce는 폐기 목록에 2분간 보관하고 재사용하지 않는다.

`virtual_ip`의 소비자: 수신 측은 제어 평면이 알려준 상대의 가상 IP와 비교한다. 다르면 폐기하고 `drop_vip_mismatch`를 올린다.

**probe nonce.** 10.4 (c)의 경로 검증용 `HELLO`는 시도 nonce가 아니라 별도의 **probe nonce**를 쓴다. 잠정 경로마다 하나씩 뽑아 5초간 별도 표에 보관한다. "시도당 하나"라는 위 규칙은 시도 nonce에만 적용된다. 두 종류를 같은 표에 섞으면 경로 검증 응답과 핸드셰이크 응답을 구분할 수 없다.

### 5.2 HELLO_ACK (20바이트)

```text
 오프셋  크기  필드         설명
   0     16   echo_nonce   응답 대상 HELLO 의 nonce 를 그대로 복사
  16      4   virtual_ip   송신자에게 할당된 가상 IP (uint32 BE)
```

`virtual_ip` 처리는 5.1 `HELLO`와 같다.

### 5.3 KEEPALIVE (0바이트)

페이로드 없음.

### 5.4 DATA (20 ~ 1452바이트)

페이로드는 **완전한 내부 IPv4 패킷**이다. 이더넷 헤더도 추가 래핑도 없다.

### 5.5 PING / PONG (각 8바이트)

```text
 오프셋  크기  필드      설명
   0      8   ping_id   uint64 BE
```

`ping_id`는 세션 시도마다 0에서 시작해 1씩 증가한다. **타임스탬프를 와이어에 싣지 않는다.** 송신 시각은 로컬 표에만 둔다.

```cpp
uint64_t id = next_ping_id++;
pending_pings[id] = steady_clock::now();
```

- `pending_pings`는 최대 `MAX_PENDING_PINGS`(16)개다. 삽입 전에 5초가 지난 항목을 제거하고, 그래도 가득 차면 새 `PING`을 보내지 않는다.
- `PONG` 수신 시 `ping_id`로 조회한다. 없으면 폐기하고 `drop_unmatched_pong`을 올린다. 있으면 RTT를 계산하고 **항목을 제거한다.** 각 `ping_id`는 한 번만 유효하다.
- 5초를 넘긴 항목은 표본을 버리고 제거한다.

`PONG`은 받은 `ping_id`를 그대로 되돌려준다.

### 5.6 CLOSE (1바이트)

```text
 오프셋  크기  필드      설명
   0      1   reason    0x00 정상 종료, 0x01 사용자 취소, 0x02 설정 오류, 0x03 수립 실패
```

`0x00`~`0x03` 외의 값은 폐기하고 `drop_bad_reason`을 올린다. 정상 종료 시 best-effort로 1회 보낸다. 재전송하지 않고 응답도 기다리지 않는다.

**수신 측은 라우팅 항목을 즉시 제거하고 세션은 `CLOSED`로 남긴다.** 세션 객체까지 지우면
그 뒤 도착한 패킷이 9.4.1 `IDLE`과 종료 상태의 수신이 정한 `drop_terminal_state`가 아니라 `drop_unknown_peer`로
떨어져, 종료 뒤의 수신을 세는 자리가 사라진다. 소켓은 프로세스 종료까지 열려 있으므로
(6장) 그 패킷은 실제로 계속 온다.

**우리가 `CLOSE`를 보낸 세션도 `CLOSED`로 전이한다. 송신 성공 여부와 무관하다.** 보내지
않는 세션(위 표의 학습 전, `FAILED`)은 종료 절차가 그대로 끝내며 `FAILED`는 `FAILED`로
남는다. 이 전이가 없으면 정상 종료 경로에서 세션이 어느 상태로 끝나는지가 정해지지 않아
[`architecture.md`](architecture.md) 9장의 종료 줄 코드와 카운터 덤프 시점이 구현마다
달라진다.

**어디로 보내는가. `peer_endpoint`를 학습한 세션에만 1회 보낸다.** 판단 기준은 상태가 아니라
학습 여부다.

| 세션 | 보내는가 |
|------|----------|
| `peer_endpoint` 학습 완료 (`CONNECTED`, 그리고 학습 후의 `HANDSHAKING`·`PUNCHING`) | **보낸다.** 검증된 주소 하나로 가는 패킷 1개다 |
| 학습 전 (`IDLE`, 학습 전 `PUNCHING`) | 보내지 않는다 |
| `FAILED`, `CLOSED` | 보내지 않는다 |

**`CONNECTED`에만 보내면 안 되는 이유.** 두 플래그는 양쪽에서 같은 시점에 서지 않는다(9.2).
상대의 `HELLO_ACK`이 유실되면 우리는 `HANDSHAKING`인데 상대는 `CONNECTED`인 상태가 된다.
상대가 `CONNECTED`라는 것은 우리가 이미 `HELLO_ACK`을 보냈다는 뜻이므로(그것이 상대의
`got_ack`이다) 그때 우리는 상대의 `HELLO`를 받은 상태이고 `peer_endpoint`도 학습돼 있다.
이 경우에 `CLOSE`를 보내지 않으면 **상대는 유휴 타임아웃 50초를 기다린다.** `CLOSE`가 아끼려는
바로 그 시간이다.

**학습 전에 보내지 않는 이유는 반사다.** 학습 전이면 송신 대상이 후보 전체가 되므로(10.4)
확인되지 않은 주소 여러 개로 종료 통지를 뿌리게 된다. 10.4 (c)가 상한을 건 것과 같은 종류의
경로다. 학습 전 세션은 상대도 아직 `CONNECTED`가 아니므로 아껴 줄 유휴 타임아웃도 없다.

**어느 값을 보내는가.** 수신 처리는 넷이 같으므로 이 구분은 상대의 진단 기록에만 쓰인다.

| reason | 보내는 경우 |
|--------|-------------|
| `0x00` | `CONNECTED` 세션을 정상 종료 경로로 닫는다 (사용자 종료 요청, 종료 신호) |
| `0x01` | **아직 `CONNECTED`에 도달하지 않은** 세션을 사용자가 종료시켰다. 수립 중 취소다 |
| `0x02` | 로컬 구성 때문에 이 세션을 이어갈 수 없다. 받은 가상 IP가 로컬 대역과 충돌하거나 어댑터 구성이 실패한 경우다 |
| `0x03` | **이 세션이 실패로 끝났다.** 9.6 실패 전이가 보낸다. 사람이 취소한 것이 아니다 |

**같은 종료 명령이 상태에 따라 다른 값을 낸다.** 사용자가 종료를 지시했을 때 세션이
`CONNECTED`면 `0x00`, `PUNCHING`이나 `HANDSHAKING`이면 `0x01`이다. 이 구분이 없으면 두 값이
같은 상황을 가리켜 상대의 진단 기록에서 "정상 종료"와 "수립 중 취소"를 나눌 수 없다.

**`0x03`을 따로 둔 이유도 같다.** 9.6 실패 전이도 수립 중에 나가는 `CLOSE`라 값이 없으면
`0x01`을 쓰게 되는데, 그러면 상대의 기록에서 "사람이 껐다"와 "핸드셰이크가 실패했다"가
같은 값이 된다. 앞은 Phase 9 집계에서 빼야 하는 사건이고 뒤는 세어야 하는 사건이다.
[`spec.md`](spec.md) A-2가 통제된 실패와 실제 실패를 따로 세라고 한 것과 같은 자리다.

`0x02`를 보낼 상황이 없는 Phase에서는 쓰지 않는다. 값을 없애지는 않는다. 와이어 열거값을
나중에 늘리면 기존 구현이 `drop_bad_reason`으로 버린다.

`CLOSE`가 없으면 정상 종료와 크래시를 구분할 수 없어 상대가 50초 유휴 타임아웃까지 죽은 세션을 붙든다. 크래시 대비로 유휴 타임아웃은 유지한다.

## 6. 소켓 소유권

**하나의 로컬 UDP 소켓을 하나의 수신 루프가 배타적으로 소유한다.** 그 루프의 스레드 구성, 대기 방식, 상태 소유 범위는 [`architecture.md`](architecture.md) 3.2 동시성 모델에 있다.

- STUN 클라이언트는 `recvfrom`을 직접 호출하지 않는다. 요청을 등록하고 응답을 수신 루프에서 전달받는다. 두 곳에서 읽으면 서로의 패킷을 소비한다.
- 소켓은 프로세스 시작 시 한 번 bind 하고 종료까지 유지한다. 재바인드하면 NAT 매핑이 바뀐다.
- **bind 대상은 `INADDR_ANY`, 포트 0이다.** 포트 0이면 OS가 고른다. 그 대가로 재실행마다
  로컬 포트가 바뀌고, 그 결과는 10.4 엔드포인트 학습의 재시작 한계에 적었다
  - 특정 인터페이스 주소에 bind 하면 다른 인터페이스로 들어온 패킷을 받지 못한다. 그러면
    10.1 후보 수집과 위생의 로컬 후보가 무의미해진다
  - 포트를 고정하면 이미 쓰이고 있을 때 기동이 실패하고, 같은 기기에서 두 프로세스를 띄우는
    시험도 못 한다
- bind 직후 실제 포트를 `getsockname`으로 읽어 10.1 후보 수집과 위생의 로컬 후보에 쓴다. 포트 0을 그대로 등록하지 않는다.
- **`SO_SNDBUF`는 기본값을 쓴다.** 송신은 이 루프가 속도를 직접 정하고(200ms 재전송, 15s keepalive, 게임 트래픽), 버퍼가 부족하면 `sendto`가 오류로 알려 준다. 늘려야 할 근거가 생기면 그때 이 줄을 고친다.
- **`SO_RCVBUF`를 명시적으로 설정한다.** 요청값은 `262144`(256KiB)다. 단위 접미사가 아니라
  바이트 수로 적는다
  - 기준은 `MAX_DRAIN` × `MAX_DATAGRAM`보다 크게 잡는 것이다. `MAX_DRAIN`은
    `architecture.md` 3.2.3 루프 한 바퀴가 소유하고, 그 문서의 현재 값으로 계산하면
    94208바이트다. 예산이 바뀌면 이 값도 다시 본다
  - 설정 뒤 `getsockopt`로 실제 적용값을 읽어 기록한다
  - 기본값을 쓰지 않는 이유는 OS와 버전에 따라 다르고 수신 루프 한 바퀴 예산보다 작을 수
    있기 때문이다. 한 바퀴 분량도 담지 못하면 예산 설계가 의미를 잃는다
  - 적용값을 기록하는 이유는 OS가 요청값을 그대로 주지 않을 수 있기 때문이다. 기록이 없으면
    손실의 원인을 나중에 찾을 수 없다
- `SO_REUSEADDR`를 쓰지 않는다. Windows에서 다른 소켓이 같은 엔드포인트를 bind 해 배달이 비결정적이 된다. `SO_EXCLUSIVEADDRUSE`를 쓴다.
- `connect()`를 호출하지 않는다. 연결된 UDP 소켓은 다른 출발지 데이터그램을 걸러내므로 STUN 서버와 여러 후보를 동시에 다룰 수 없다.
- **`SIO_UDP_CONNRESET`를 끈다.** 끄지 않으면 응답 없는 후보가 보낸 ICMP port unreachable이 `WSAECONNRESET`으로 올라와 수신 루프를 종료시킨다. 홀펀칭은 응답 없는 후보로 계속 쏘는 것이 정상이므로 이걸 빠뜨리면 Phase 4에서 반드시 터진다.

```cpp
BOOL off = FALSE;
DWORD bytes = 0;
WSAIoctl(sock, SIO_UDP_CONNRESET, &off, sizeof(off), nullptr, 0, &bytes, nullptr, nullptr);
```

**`sendto` 실패는 타입과 무관하게 `tx_err_send`를 올리고 그 패킷을 버린다. 재전송하지
않는다.** 다음 주기의 재전송이나 keepalive가 그 자리를 대신하고, 단절 판정은 송신 실패가
아니라 유휴 타임아웃이 한다(9.6 실패 전이).

**`HELLO_ACK`의 실패만 `tx_err_ack`를 함께 올린다.** 그 실패는 9.2 `CONNECTED` 조건의
`sent_ack`이 서지 않는 원인이라 따로 센다. 카운터 하나가 더 필요해서가 아니다.

로그는 `architecture.md` 9장의 `socket.error`가 맡는다. 카운터는 그 문서 9장의 지표 표
"keepalive 로컬 송신 오류" 가 읽는 값이기도 하다.

## 7. 수신 분류

수신 루프는 데이터그램마다 **첫 바이트의 상위 2비트로만** 분류한다. magic과 version은 분류
기준이 아니라 검증 항목이다.

> **왜.** 분류 단계에서 magic을 보면 magic이 틀린 패킷이 터널 파이프라인에 도달하지 못한다.
> 그러면 `drop_magic` 카운터가 영원히 0이 되고, 터널을 겨냥한 악성 트래픽이
> `drop_unclassified`에 섞여 보이지 않게 된다.

```text
출발지 위생 (아래 표). 통과 못 하면
      -> 폐기, drop_bad_source
(buf[0] & 0xC0) == 0x00  이고  len >= 20  이고  buf[4..8) == STUN_COOKIE
      -> STUN 메시지. 트랜잭션 ID로 대기 중인 요청과 매칭 (13장)
(buf[0] & 0xC0) == 0x40
      -> 터널 후보. 8장 검증 파이프라인으로
그 외
      -> 폐기, drop_unclassified
```

**출발지 위생이 분류보다 먼저인 이유.** 수신 데이터그램의 출발지는 우리가 되돌려 보내는
목적지가 된다. 9.4 전이표와 9.5 재협상의 `HELLO_ACK`은 "그 데이터그램의 출발지로" 나가고, 10.4 (c)의 검증
`HELLO`도 마찬가지다. 출발지는 위조할 수 있으므로, 10.1 후보 수집과 위생이 후보 목록에 대해 막은 반사·증폭
경로가 회신에서 열린다. 분류 전에 걸러야 STUN 경로와 터널 경로가 같은 보호를 받는다.

| 출발지 | 판정 | 근거 |
|--------|------|------|
| 멀티캐스트 `224.0.0.0/4` | 폐기 | 회신 1개가 그룹 구독자 수만큼 증폭된다 |
| 제한 브로드캐스트 `255.255.255.255` | 폐기 | 같은 이유 |
| 미지정 `0.0.0.0` | 폐기 | 회신할 곳이 없다 |
| 포트 0 | 폐기 | 회신할 곳이 없다 |
| 루프백 `127.0.0.0/8` | **통과** | 회신이 자신에게만 가므로 증폭이 없다. 같은 기기에서 두 프로세스를 띄우는 시험이 이 경로를 쓴다 |
| 그 외 | 통과 | |

**10.1 후보 수집과 위생과 같은 표가 아니다.** 그 절은 루프백을 거부하고 여기는 통과시킨다. 후보는
우리가 먼저 보낼 목적지 목록이라 루프백이 들어오면 무의미하거나 속임수지만, 수신 출발지의
루프백은 같은 기기의 다른 프로세스라는 정상 경우가 있다. **두 표를 하나로 합치지 않는다.**

**서브넷 브로드캐스트(directed broadcast)는 둘로 갈린다.**

| 무엇 | 판정 | 왜 |
|------|------|-----|
| **우리 자신의** 활성 IPv4 서브넷의 브로드캐스트 주소 | 폐기 | 10.1 후보 수집과 위생이 로컬 후보를 만들 때 각 인터페이스의 주소와 넷마스크를 이미 읽는다. 그 값으로 계산할 수 있다. 증폭이 실제로 일어나는 곳도 여기다 |
| 원격 서브넷의 브로드캐스트 주소 | 통과 (막지 못한다) | 그 서브넷의 넷마스크를 모른다. 유니캐스트와 구분할 수단이 없다 |

원격 서브넷의 경우는 **남는 위험으로 적는다.** 라우터가 directed broadcast를 전달하지 않는
것은 RFC 2644가 기본 동작으로 요구한 것이므로, 실제 증폭까지 이어지려면 그 요구를 지키지
않는 경로여야 한다. 그것을 방어로 세지 않는다. 우리가 확인할 수 없는 남의 설정이다.

`buf[a..b)`는 반열린 구간이다. `buf[4..8)`은 오프셋 4,5,6,7의 4바이트다.

`MAX_DATAGRAM`(1472)을 넘는 데이터그램은 이 단계에 오지 않는다. 수신 루프가 먼저 버린다
([`architecture.md`](architecture.md) 3.2.3).

## 8. 수신 검증 파이프라인

터널 후보는 아래 순서로 검사한다. 각 단계마다 전용 폐기 카운터를 둔다. 하나라도 실패하면 즉시 폐기한다.

### 8.1 공통 검사

| # | 검사 | 실패 카운터 |
|---|------|-------------|
| 1 | `len >= HEADER_SIZE` | `drop_short` |
| 2 | `magic == TUNNEL_MAGIC` | `drop_magic` |
| 3 | `version == TUNNEL_VERSION` | `drop_version` |
| 4 | `type`이 5장 목록에 있음 | `drop_unknown_type` |
| 5 | `payload_length == len - HEADER_SIZE` | `drop_length` |
| 6 | 타입별 길이 규정 충족: `HELLO`/`HELLO_ACK` 정확히 20, `KEEPALIVE` 0, `PING`/`PONG` 8, `CLOSE` 1, `DATA` 20~1452 | `drop_type_length` |
| 7 | `peer_id`가 이 방의 상대 피어 ID와 일치 | `drop_unknown_peer` |
| 8 | `session_epoch`가 폐기 목록에 없음 | `drop_retired_epoch` |

### 8.2 epoch 및 출발지 검사

`HELLO`와 `HELLO_ACK`은 epoch 고정 전에도 통과해야 한다. 나머지 타입은 epoch가 고정된
뒤에만 유효하다. 두 타입이 통과하는 이유는 서로 다르다.

- **`HELLO_ACK`은 `echo_nonce`로 스스로를 증명한다.** 우리가 보낸 128비트 난수를 되돌려
  주므로, 그 패킷이 우리 `HELLO`를 실제로 받은 쪽에서 왔다는 증거가 된다
- **`HELLO`는 아무것도 증명하지 않는다.** nonce는 송신자가 새로 뽑은 값이다. `HELLO`가
  통과하는 이유는 그것이 epoch를 고정하는 계기이기 때문이고, 2장이 위조 `HELLO`의 전제를
  `peer_id` 하나로 적은 것이 이 성질이다

**`HELLO`와 `HELLO_ACK`은 epoch 판정 전에 `virtual_ip`를 본다(5.1 `HELLO`).** 아래 표의
모든 행에 앞서는 검사이고, 불일치면 폐기하고 `drop_vip_mismatch`를 올린다.

> **왜.** epoch 고정 뒤에 두면 위조 `HELLO` 하나가 epoch를 먼저 고정해 버린다.

| 타입 | 규칙 |
|------|------|
| `HELLO` | `virtual_ip`가 상대의 가상 IP와 일치할 것(5.1). epoch 고정 여부와 무관하게 수용. 출발지가 후보 집합에 있을 것을 요구하지 않는다(7장 출발지 위생은 이미 통과했다). 9.3 epoch 규칙 적용 |
| `HELLO_ACK` (시도 nonce echo, epoch 미고정 또는 고정값과 일치) | `echo_nonce`가 **우리가 이번 시도에서 보낸 nonce**와 일치. 핸드셰이크 증거로 쓰고(`got_ack`), epoch가 미고정이면 이 패킷으로 고정한다 |
| `HELLO_ACK` (시도 nonce echo, epoch가 고정값과 다름) | 폐기, `drop_stale_epoch` |
| `HELLO_ACK` (probe nonce echo) | `echo_nonce`가 활성 probe nonce 중 하나와 일치하고 출발지가 그 probe를 보낸 주소와 같을 것. **해당 잠정 경로만 검증한다.** `got_ack`를 세우지 않고 epoch도 고정하지 않는다 |
| `HELLO_ACK` (그 외) | 폐기, `drop_bad_nonce` |
| 그 외 전부 | epoch 미고정이면 폐기, `drop_no_epoch`. 고정된 값과 다르면 폐기, `drop_stale_epoch` |

이 규칙이 없으면 "선행 `HELLO_ACK`은 정상"이라는 9.4 전이표의 서술과 epoch 검사가 서로 모순되어, 상대가 먼저 펀치를 시작한 정상 상황에서 양쪽이 타임아웃한다.

**epoch가 이미 고정된 뒤에 오는 유효 nonce `HELLO_ACK`은 버린다.** 실제로 생기는 경우다.
펀치 중 상대의 첫 `HELLO`로 epoch를 고정한 직후 상대가 크래시하고 재시작하면, 새 인스턴스가
우리의 재전송 `HELLO`에 새 epoch로 우리 nonce를 echo 한다.

> **왜.** 이것을 수용하면 이미 끝난 시도의 epoch 아래에서 `got_ack`이 서고, 그 뒤 `DATA`는
> 전부 `drop_stale_epoch`에 걸리는 세션이 `CONNECTED`가 된다. 버리는 쪽은 잃는 것이 없다.
> 상대가 살아 있다면 그쪽의 새 `HELLO`가 곧 도착해 9.5 재협상이 같은 일을 정상 경로로
> 처리한다.

### 8.3 중복 억제

4.5 중복 억제와 손실 집계의 판정을 적용한다. `drop_duplicate` 또는 `drop_too_old`로 버려진 패킷은 **유휴 타이머를 갱신하지 않고 어떤 상태도 바꾸지 않는다.**

**중복 억제 상태는 그 패킷이 실은 epoch로 조회한다.** 고정된 epoch가 아니다. 4.5 중복 억제와 손실 집계가 "상대
epoch별로 상태를 유지한다"고 한 것이 이 뜻이다. 상대가 재시작해 새 epoch로 `sequence = 0`
부터 다시 보내면, 그 epoch의 상태는 아직 없으므로 `initialized`가 거짓이고 첫 패킷이
수용된다. **고정된 epoch의 상태로 판정하면 그 패킷이 `drop_too_old`로 버려져 9.5 재협상이
계기를 잃는다.**

**epoch 처리가 중복 억제보다 먼저다.** 8.2 epoch 및 출발지 검사가 다른 epoch의 `HELLO`를 9.5로 보내면 재협상이
3번에서 중복 억제 상태를 초기화한다. 8.3 중복 억제는 그 뒤에 새 epoch의 상태로 판정한다. 순서를
뒤집으면 재시작한 상대의 첫 `HELLO`가 이전 시도의 창에 걸린다.

### 8.4 DATA 내부 검증

`DATA`는 Wintun 주입 직전에 아래를 전부 통과해야 한다.

| # | 검사 | 실패 카운터 |
|---|------|-------------|
| 9 | 상태가 `CONNECTED` | `drop_data_early` |
| 10 | 내부 IP 버전 니블 == 4 | `drop_inner_not_ipv4` |
| 11 | 내부 IHL이 5~15이고 `IHL*4 <= payload_length` | `drop_inner_ihl` |
| 12 | 내부 IPv4 헤더 체크섬 유효 | `drop_inner_checksum` |
| 13 | 내부 `total_length == payload_length` | `drop_inner_length` |
| 14 | 내부 출발지 IP == 상대 피어의 가상 IP | `drop_inner_src` |
| 15 | 내부 목적지 IP == 자신의 가상 IP | `drop_inner_dst` |

14번과 15번은 오배달과 라우팅 버그로 인한 우발적 주입을 막는 위생 장치다. 2장에서 밝힌 대로 **공격 방어 수단이 아니다.**

### 8.5 송신 측 검증

내부 패킷은 **출처와 무관하게** 아래를 통과해야 `DATA`로 캡슐화한다. 출처는 Phase 6 이후에는
Wintun 읽기이고, 그 전에는 시험이 만드는 합성 패킷이다. 검사는 같다.

> **왜.** 출처마다 다른 검사를 두면 합성 패킷으로 돌린 시험이 실제 경로를 검증하지 못한다.

| # | 검사 | 실패 카운터 |
|---|------|-------------|
| 1 | 상태가 `CONNECTED` | `tx_drop_not_connected` |
| 2 | 길이 >= 20 | `tx_drop_short` |
| 3 | IP 버전 니블 == 4 | `tx_drop_not_ipv4` |
| 4 | 길이 <= `MAX_INNER` | `tx_drop_oversize` |
| 5 | 출발지 IP == 자신의 가상 IP | `tx_drop_bad_src` |
| 6 | 목적지 IP == 상대 피어의 가상 IP | `tx_drop_no_route` |

**2번이 5번과 6번보다 먼저다.** 출발지와 목적지는 오프셋 12~20에 있으므로 20바이트 하한을
확인하기 전에 읽으면 버퍼 밖을 읽는다. 수신 측은 8.1 검사 6번이 같은 하한을 보장하지만 송신
측에는 대응물이 없었다. Wintun이 20바이트 미만을 내주는 일은 드물지만, 판정 함수는 드문
경우를 가정으로 두지 않는다.

## 9. 세션

### 9.1 상태

| 상태 | 의미 |
|------|------|
| `IDLE` | 아직 상대 후보를 받지 못함 |
| `PUNCHING` | 상대 후보를 받았고 왕복 증거가 없음 |
| `HANDSHAKING` | 한쪽 증거만 확보 |
| `CONNECTED` | 양쪽 증거 확보 |
| `FAILED` | 실패 코드와 함께 종료 |
| `CLOSED` | 정상 종료 |

**`PUNCHING` 진입은 후보 수신 시점이고 `HELLO` 재전송 시작은 그보다 늦다.** 10.2 랑데부의
펀치 지연이 만료돼야 재전송이 시작되기 때문이다. 그 사이의 대기 구간도 `PUNCHING`이며
9.4 전이표의 `PUNCHING` 열이 그대로 적용된다. 랑데부 오차(10.2, 상한 약 1초) 때문에 상대의
`HELLO`가 정확히 이 구간에 도착하는 것이 정상 경로다.

> **왜.** 구간에 별도 상태를 두면 전이표가 한 열 늘고 그 열의 규칙이 `PUNCHING`과 같아진다.
> 그래서 상태를 늘리는 대신 진입 시점을 앞당겼다.

펀치 마감(11장)은 `PUNCHING` 진입이 아니라 **실제 로컬 펀치 시작**부터 센다. 대기 구간이
마감을 갉아먹지 않게 하기 위해서다.

### 9.2 CONNECTED 조건

```text
got_ack   = 우리 nonce 를 echo 한 HELLO_ACK 을 받았다      (우리 -> 상대 경로 확인)
sent_ack  = 상대의 유효한 HELLO 에 HELLO_ACK 을 보냈다      (상대 -> 우리 경로 확인)

CONNECTED  <=>  got_ack && sent_ack
```

`sent_ack`는 `sendto`가 성공을 반환한 뒤에만 세운다. 실패하면 `tx_err_ack`를 올리고 세우지 않는다.

둘 중 하나만 선 것이 `HANDSHAKING`이다. **어느 쪽이 먼저 서는지는 정해져 있지 않다.** 순서를 가정하면 한쪽만 뚫린 경로를 연결로 오판하거나 정상 순서에서 양쪽이 타임아웃한다.

`CONNECTED` 진입 시 손실 집계 상태를 초기화한다(4.5).

### 9.3 epoch 규칙

| 상황 | 동작 |
|------|------|
| epoch 미고정 상태에서 유효한 `HELLO` 또는 nonce 일치 `HELLO_ACK` 수신 | 그 패킷의 epoch를 고정 |
| 고정된 epoch와 같은 패킷 | 정상 처리 |
| 고정된 epoch와 다른 `HELLO` 수신 | **상대가 재시도했다.** 9.5 재협상 절차 |
| 고정된 epoch와 다른 그 외 패킷 | 폐기, `drop_stale_epoch` |
| 폐기 목록에 있는 epoch | 폐기, `drop_retired_epoch` |

### 9.4 전이표

아래 표는 **활성 상태 셋**을 다룬다. `IDLE`과 종료 상태는 표 다음 절이 맡는다.

| 수신 \ 상태 | `PUNCHING` | `HANDSHAKING` | `CONNECTED` |
|---|---|---|---|
| `HELLO` (epoch 일치 또는 미고정) | `HELLO_ACK`을 **그 데이터그램의 출발지로** 응답, `sent_ack=true`, 출발지 학습(10.4 조건) | 같음 (중복이면 `HELLO_ACK`만 재응답) | 같음. **상대 ACK가 유실된 상황이므로 무시하면 상대가 타임아웃한다** |
| `HELLO` (다른 epoch) | 9.5 재협상 | 9.5 재협상 | 9.5 재협상 |
| `HELLO_ACK` (시도 nonce echo, 8.2 통과) | `got_ack=true`, 출발지 학습(10.4 조건), epoch 미고정이면 고정 | 같음 | 중복. `dup_ack`를 올리고 플래그는 그대로 둔다. **유휴 타이머 갱신과 출발지 학습은 한다**(검증을 전부 통과한 패킷이다) |
| `HELLO_ACK` (probe nonce echo) | 10.4 (c)의 경로 검증. 해당 잠정 경로만 검증하고 `got_ack`와 epoch는 건드리지 않는다 | 같음 | 같음 |
| `HELLO_ACK` (그 외) | 폐기, `drop_bad_nonce` 또는 `drop_stale_epoch` (8.2) | 같음 | 같음 |
| `KEEPALIVE` | 출발지 학습(10.4 조건). 유휴 타이머는 없다 | 같음 | 유휴 타이머 갱신, 출발지 학습(10.4 조건) |
| `PING` | `PONG` 응답 | 같음 | 같음 |
| `PONG` | 5.5 매칭 | 같음 | 같음 |
| `DATA` | 폐기, `drop_data_early` | 폐기, `drop_data_early` | 8.4 검증 후 주입 |
| `CLOSE` | `CLOSED` 전이 | `CLOSED` 전이 | `CLOSED` 전이 |

**`PUNCHING`에서 `HELLO_ACK`이 먼저 오는 것은 정상이다.** 상대가 먼저 펀치를 시작했고 우리 `HELLO`는 도착했지만 상대 `HELLO`가 아직 안 온 경우다.

**`PING`/`PONG` 두 행에 붙는 단서.** `PING` 송신은 `CONNECTED`부터다(11장). 그 전에는
`pending_pings`가 비어 있어 `PONG`이 와도 5.5 조회에 실패하고 `drop_unmatched_pong`으로
끝난다. 즉 **`CONNECTED` 이전에는 RTT 표본이 생기지 않는다.** `PING`에 `PONG`으로 답하는
것은 그 전 상태에서도 하지만, 무검증 목적지로 가는 `PONG`은 아래의 공통 예산을 쓴다.

**회신은 `peer_endpoint`가 아니라 받은 데이터그램의 출발지로 간다.** 9.5 재협상이 재협상 응답에
대해 정한 것과 같은 이유다. 응답 1개이고 증폭이 없으므로 안전하고, 상대의 경로가 바뀐
경우에도 닿는다. 반면 `peer_endpoint` 전환은 10.4 엔드포인트 학습의 조건을 거쳐야 한다. 단건 회신과
대량 전환은 다른 판단이다.

**무검증 목적지로 나가는 송신에 공통 예산을 둔다.** 위조 `HELLO` 하나에 회신 하나이므로
증폭은 없지만, 공격자가 같은 epoch의 패킷을 계속 보내면 그 수만큼 위조된 주소로 송신이
나간다. `CONNECTED`에서는 끝나는 시점도 없다.

**무검증 목적지**는 `peer_endpoint`도 아니고 승인된 후보 집합에도 없는 주소다. 그런 주소로
나가는 송신은 세 종류이고 **전부 하나의 예산을 쓴다.**

| 송신 | 계기 |
|------|------|
| `HELLO_ACK` | 후보 밖 출발지의 `HELLO` (9.4, 9.5 6번) |
| `PONG` | 후보 밖 출발지의 `PING` |
| 검증 `HELLO` | 10.4 (c)의 새 잠정 경로 |

**예산은 토큰 버킷이다.** 용량 `UNVERIFIED_TX_BUCKET`(10), 초당 `UNVERIFIED_TX_REFILL`(5)개 보충, 세션당 하나다. 위 셋 중 하나를 보낼 때마다
토큰 하나를 쓰고, 토큰이 없으면 **보내지 않고** `drop_unverified_tx`를 올린다. 후보 집합
안이나 `peer_endpoint`로 가는 송신은 토큰을 쓰지 않는다.

**세 경로의 예산을 따로 두면 합계 상한이 틀린다.** 후보 밖 출발지에서 온 `HELLO` 하나가
`HELLO_ACK`과 잠정 경로 검증 `HELLO`를 동시에 유발할 수 있으므로, 경로별로 "응답 1개"를
세면 실제로 나가는 양을 과소평가한다. 하나로 묶으면 세션이 무검증 주소로 보내는 총량이
**초당 5패킷, 순간 10패킷**으로 한 번에 정해진다.

"초당 5회"를 고정 창으로 세면 안 된다. **정상 재전송이 정확히 초당 5회**(200ms 간격)라
경계에서 5번째가 막힌다. 용량 10의 버킷은 그 5회를 계속 통과시키고 짧은 몰림도 흡수한다.
리바인딩으로 상대의 출발지가 후보 집합 밖으로 바뀐 경우가 정확히 이 경로를 쓰므로, 정상
경로를 막지 않는 것이 중요하다.

**9.5 재협상의 `HELLO_ACK`도 같은 예산을 쓴다.** 토큰이 없으면 보내지 않고, 보내지 않았으므로
**`sent_ack`을 세우지 않는다**(9.2 `CONNECTED` 조건은 `sendto` 성공 뒤에만 세운다). 9.5 7번이 그때의 상태를
플래그에서 파생시키므로 따로 정할 것이 없다. 예산을 우회하는 예외를 두면 그 경로가 곧
우회로가 된다.

**예산을 출발지별이 아니라 세션당으로 두는 이유.** 출발지는 위조할 수 있으므로 출발지별
버킷은 공격자가 주소를 바꿔 우회한다. 대가는 공격자가 예산을 비워 두면 그 구간에 진짜
상대의 새 경로가 응답을 못 받는 것이다. 10.4 (c)의 잠정 경로 고갈과 같은 종류의 수용된
한계이며, 그 경우에도 후보 집합 안과 `peer_endpoint`로 가는 경로는 제한을 받지 않는다.

**유휴 타이머는 `CONNECTED` 진입에 시작한다(11장).** 그 전 상태에는 갱신할 타이머가 없다.
표의 `PUNCHING`/`HANDSHAKING` 칸이 "유휴 타이머 갱신"을 적지 않는 이유다. 그 구간의 마감은
유휴 타임아웃이 아니라 펀치 마감이 맡는다.

**`CONNECTED`에서 유휴 타이머를 갱신하는 것은 해당 타입의 모든 검증을 통과한 패킷뿐이다.**
11장 타이머의 표기도 같은 뜻이다.

- 모든 타입에 8.1 공통 검사부터 8.3 중복 억제까지가 적용된다
- `DATA` 는 8.4 `DATA` 내부 검증까지 포함한다
- `PONG` 은 5.5 `PING` / `PONG` 의 `ping_id` 매칭까지 포함한다
- `CLOSE` 는 reason 값 검증까지 포함한다

`CONNECTED` 이전에는 갱신할 타이머가 없으므로 이 문장의 적용 대상이 아니다. 그 구간의 유효
패킷은 상태 전이와 출발지 학습에만 쓰인다.

### 9.4.1 `IDLE`과 종료 상태의 수신

| 상태 | 도착한 패킷의 처리 |
|------|--------------------|
| `IDLE` | 상대 `peer_id`를 아직 모르므로 8.1 검사 7번에서 전부 `drop_unknown_peer`로 떨어진다. 별도 규칙이 필요 없다 |
| `FAILED` | 타입과 무관하게 전부 폐기, `drop_terminal_state` |
| `CLOSED` | 타입과 무관하게 전부 폐기, `drop_terminal_state` |

**종료 상태에서 `HELLO`도 받지 않는다.** 재시도는 9.6 실패 전이가 정한 대로 `IDLE`부터 새 epoch와 새
nonce로 시작하는 것이지, 끝난 세션이 되살아나는 것이 아니다. 종료 상태의 세션이 `HELLO`에
응답하면 이미 정리한 라우팅과 카운터를 되살려야 하고, 그 경로는 어느 문서도 정의하지
않았다. **폐기가 정의된 동작이다.**

소켓은 프로세스 종료까지 유지되므로(6장) 종료 상태에 도달한 뒤에도 패킷은 계속 도착한다.
`drop_terminal_state`가 계속 오르는 것은 정상이며, 상대가 아직 우리 `CLOSE`를 받지 못했거나
유휴 타임아웃을 기다리는 중이라는 뜻이다.

### 9.5 재협상

고정된 epoch와 다른 `HELLO`를 받으면 상대가 새 시도를 시작한 것이다.

**먼저 상한을 본다.** 재협상은 위조 `HELLO` 하나로 유발할 수 있고(2장), 한 번마다 폐기 목록이
한 칸 차고 펀치 마감이 되돌아간다. 상한이 없으면 마감이 계속 미뤄져 세션이 `CONNECTED`에
도달하지도, 실패로 끝나지도 못한다.

| 조건 | 동작 |
|------|------|
| **마지막으로 수용한** 재협상으로부터 `MIN_RENEG_INTERVAL_MS`(1000ms) 이내 | 폐기, `drop_reneg_rate` |
| 이번 시도의 재협상 횟수가 이미 `MAX_RENEGOTIATIONS`(8) | 폐기, `drop_reneg_limit` |

**횟수는 시도가 끝날 때까지 회복되지 않는다. 그 결과를 적는다.** 위조 `HELLO`로 8번을 소진하면
그 뒤에는 **진짜 상대의 재시작도 `drop_reneg_limit`으로 버려진다.** 그 세션은 펀치 마감에
걸려 9.6으로 끝나고, 복구는 `IDLE`부터의 새 시도뿐이다. v1이 수용하는 가용성 한계다.
회복시키려면 "검증된 출발지에서 온 재협상만 센다" 같은 규칙이 필요한데, 출발지 검증이
곧 이 프로토콜이 아직 갖지 못한 것이다.

**정상 경로가 이 상한에 걸리지 않는다.** 재협상이 한 번 일어나면 4번이 새 epoch를 고정하므로
같은 시도의 `HELLO` 재전송은 더 이상 "다른 epoch"가 아니고 일반 `HELLO`로 처리된다. 간격
제한에 걸리는 것은 1초 안에 또 다른 epoch가 오는 경우뿐이고, 그것도 상대의 200ms 재전송이
1초 뒤 통과시킨다. 즉 같은 소켓에서의 정상 재시도는 최대 1초 늦어질 뿐 실패하지 않는다.

**프로세스 재시작은 다르다.** 그쪽은 이 상한과 무관하게 10.4 엔드포인트 학습의 한계를
따르며, v1이 복구를 보장하지 않는다.

**기준 시각은 수용한 재협상의 시각이다.** 상한에 걸려 폐기한 `HELLO`는 그 시각을 갱신하지
않는다. 갱신하면 공격자가 계속 보내는 것만으로 쿨다운을 영구히 연장해 정상 재시도까지
막을 수 있다.

두 상한을 통과하면 재협상 횟수를 1 늘리고 원자적으로 아래를 수행한다.

1. **상대의** 이전 epoch를 폐기 목록에 2분간 등록
2. `got_ack`, `sent_ack`를 거짓으로 초기화
3. 중복 억제 상태, `pending_pings`, 손실 집계를 초기화
4. 상대 epoch를 새 값으로 고정
5. **우리 쪽 `session_epoch`와 nonce는 그대로 유지한다**
6. 수신한 `HELLO`에 대한 `HELLO_ACK`을 그 데이터그램의 출발지로 직접 보낸다.
   `peer_endpoint`는 바꾸지 않는다. **송신이 성공하면 `sent_ack = true`다.** 9.2
   `CONNECTED` 조건의 규칙을 그대로 따른다
7. 펀치 마감을 이 시점부터 10초로 다시 잡는다. **상태는 9.2 `CONNECTED` 조건의 플래그
   개수가 정한다.** 6번이 성공했으면 `sent_ack`만 선 `HANDSHAKING`, 실패했으면 둘 다 거짓인
   `PUNCHING`이다
8. 제어 평면을 다시 거치지 않고 기존 후보 목록을 재사용한다
9. `HELLO` 재전송 대상은 **기존 후보 전체**다. 재협상을 유발한 `HELLO`의 출발지가 후보 집합 밖이면 10.4 (c)의 잠정 경로로 등록할 뿐 재전송 대상에 넣지 않는다
10. **타이머를 펀치 구간의 것으로 되돌린다.** `HELLO` 재전송(200ms)을 다시 시작하고,
    `KEEPALIVE`·`PING`·유휴 타임아웃을 멈춘다. 셋은 다음 `CONNECTED` 진입에 11장 타이머
    대로 다시 시작한다

위 열 가지 규칙의 근거는 아래와 같다. 규칙 번호 순이다.

2~3번 초기화를 빠뜨리면 이전 epoch에서 얻은 `got_ack`나 `sent_ack`가 남아 새 세션을 검증 없이 `CONNECTED`로 만든다.

5번이 핵심이다. 상대의 재시도에 반응해 우리도 epoch를 바꾸면, 상대가 그것을 다시 재시도로 인식해 또 바꾸고, **두 피어가 epoch를 무한히 주고받으며 영원히 연결되지 않는다.** 로컬 epoch는 우리가 `IDLE`에서 새 시도를 시작할 때만 바뀐다.

6번에서 `peer_endpoint`를 바꾸지 않는 것이 중요하다. 재협상을 유발한 `HELLO`의 출발지가 후보 목록에 없을 수 있고, 거기서 바로 전환하면 위조된 재시도 `HELLO` 하나로 트래픽 전체를 임의의 주소로 돌릴 수 있다. 10.4 엔드포인트 학습의 경로 검증을 우회하는 셈이다.

**단건 응답과 대량 전환을 구분한다.**

- `HELLO_ACK`을 받은 데이터그램의 출발지로 되돌려 보내는 것은 안전하다. 위조된 주소로
  가더라도 응답 1개이고 증폭이 없으며, 정상적인 NAT 리바인딩이라면 상대가 그 응답을 받는다
- `peer_endpoint` 전환은 이후의 모든 `DATA`를 그쪽으로 보낸다는 뜻이므로 10.4 (c) 경로
  검증을 거쳐야 한다. 출발지가 후보 집합 안이면 10.4 엔드포인트 학습에 따라 전진 패킷에서
  자동 전환되고, 밖이면 경로 검증 뒤에만 전환된다

**7번이 상태를 직접 지정하지 않는 이유.** 9.2 `CONNECTED` 조건은 상태를 플래그에서
파생되는 값으로 정했다.
6번이 유효한 `HELLO`에 `HELLO_ACK`을 보내는 것이므로 그 송신이 성공하면 `sent_ack`이 서고,
그러면 상태는 정의상 `HANDSHAKING`이다. 여기서 `PUNCHING`을 못박으면 **같은 패킷 하나가
두 상태를 가리키게 된다.** 재협상이 하는 일은 증거를 지우고 마감을 다시 잡는 것이고, 상태는
그 결과로 따라온다.

**9번이 필요한 이유.** 10.4 엔드포인트 학습의 "학습 전이면 모든 후보로"가 여기서 성립하지
않는다. 재협상은 `peer_endpoint`를 유지한 채(6번) 증거를 지운다. 그래서 "펀치 중 = 학습 전"이라는
등식이 깨진 상태가 생기고, 재전송을 학습된 `peer_endpoint` 하나로만 보내면 상대의 경로가
바뀐 재시도에서 죽은 주소로만 쏘게 된다. 후보 전체로 보내면 그 경우가 덮인다.

**재협상을 유발한 출발지를 재전송 대상에 넣지 않는 이유는 반사다.** 그 출발지는 위조일 수
있다. 재전송 대상에 넣으면 위조된 주소 — 임의의 제3자 — 로 200ms마다 `HELLO`가 나가 펀치
구간 동안 수십 발이 된다. 10.4 (c)의 잠정 경로는 검증 `HELLO`를 **1회만** 보내고 상한도
있으므로(`MAX_PROBE_PATHS`) 같은 목적을 반사 없이 달성한다.

**10번이 없으면 `CONNECTED`에서 온 재협상이 반드시 실패한다.** 11장은 `HELLO` 재전송의 취소
계기를 `CONNECTED` 도달로 정했으므로, 재전송을 다시 시작하지 않으면 재협상 뒤에 우리
`HELLO`가 한 발도 나가지 않는다. 그러면 상대는 `sent_ack`을, 우리는 `got_ack`을 얻지 못하고
양쪽이 펀치 마감에 걸린다. 9번이 재전송 **대상**만 정하는 것은 그 재전송이 다시 도는 것을
전제하기 때문이고, 그 전제를 여기서 못박는다.

**멈추는 셋도 같은 이유다.** `PING`은 `CONNECTED`부터라고 9.4 전이표가 정했는데 멈추지 않으면
`HANDSHAKING`에서 표본이 생겨 [`architecture.md`](architecture.md) 9장의 "`CONNECTED`
이전에는 RTT 표본이 만들어지지 않는다"가 깨진다. 유휴 타임아웃은 더 나쁘다. 9.4 전이표가
`HANDSHAKING`에서 그 타이머를 갱신하지 않으므로, 멈추지 않으면 재협상 직전에 남은 유휴
시간이 10초 미만일 때 펀치 마감 전에 `TUNNEL_DROPPED`가 나고 **수립 중인 세션이 단절로
기록된다.**

### 9.6 실패 전이

| 조건 | 기록 코드 |
|------|-----------|
| STUN 서버 목록을 다 쓰고도 서로 다른 두 서버의 응답을 얻지 못함 ([`architecture.md`](architecture.md) 3.5) | `STUN_DISCOVERY_FAILED` |
| `get_peers` 폴링 마감 초과, 제어 평면 오류, 또는 `peer_id` 충돌 | `CONTROL_PLANE_EXCHANGE_FAILED` |
| 펀치 마감까지 `got_ack`, `sent_ack` 둘 다 미성립 | `HOLE_PUNCH_TIMEOUT` |
| 펀치 마감까지 하나만 성립 | `PEER_HANDSHAKE_FAILED` |
| `CONNECTED` 이후 유휴 타임아웃 | `TUNNEL_DROPPED` |

**`FAILED`로 가면서 세 가지를 한다.**

1. `HELLO` 재전송과 남은 세션 타이머를 전부 멈춘다
2. `peer_endpoint`를 학습한 세션이면 `CLOSE` `0x03`을 그 주소로 1회 보낸다. 그 뒤 상태는
   `FAILED`이고 `CLOSED`가 아니다
3. 기록을 남긴다 (`architecture.md` 9장)

`FAILED`는 종료 상태다. 재시도는 `IDLE`부터 새 시도로 시작하며 새 epoch와 새 nonce를 뽑는다.
**프로세스가 그 뒤에 무엇을 하는지는 `architecture.md` 3.2.7 종료가 정한다.**

위 세 가지 규칙의 근거는 아래와 같다.

**1번은 살아 있는 시도 안의 규칙과 어긋나지 않는다.** 10.3 펀치의 "재전송을 멈추는 계기는
`CONNECTED` 도달뿐이다"는 살아 있는 시도 안의 규칙이고, 시도가 끝나면 재전송도 끝난다.
멈추지 않으면 끝난 세션이 후보 전체로 200ms마다 계속 쏜다.

**2번의 reason은 `0x03`이다.** 5.6 `CLOSE`의 표가 그 값을 실패 전용으로 둔다.
`0x01`(사용자 취소)을 쓰면 상대의 기록에서 사람이 끈 것과 구분되지 않는다.

**2번을 하는 이유는 5.6 `CLOSE`와 같다.** `HELLO_ACK`만 유실된 경우 상대는 이미 `CONNECTED`이고
우리는 학습을 마친 채 `PEER_HANDSHAKE_FAILED`로 끝난다. 알리지 않으면 상대가 유휴 타임아웃
50초를 기다린다. 5.6 표의 `FAILED` 행은 **그 상태에 이미 들어간 뒤의 종료 절차**를 말하는
것이고, 여기는 들어가는 전이다. 학습 전이면 보내지 않는 것도 5.6 `CLOSE`와 같다.

## 10. 후보와 엔드포인트

### 10.1 후보 수집과 위생

각 피어가 제어 평면에 등록하는 후보:

- **로컬 후보**: `활성 IPv4 인터페이스 주소 : bind 한 UDP 포트`다. 주소만이 아니라
  엔드포인트다
  - 포트는 6장이 `getsockname`으로 읽은 실제 값 하나를 모든 로컬 후보에 같이 쓴다. 소켓이
    하나이므로 포트도 하나다
  - 인터페이스에서 루프백, APIPA(`169.254.0.0/16`), 자신의 Wintun 어댑터, 다른 터널/VPN
    어댑터를 제외한다
  - 각 인터페이스의 prefix 길이(넷마스크)도 읽어 로컬에 보관한다. prefix는 후보로 보내지
    않는다
  - prefix를 보관하는 이유는 7장의 출발지 위생이 자기 서브넷의 directed broadcast를
    계산하는 데 그 값을 쓰기 때문이다. 버리면 그 판정을 할 수 없다. 상대에게 보내면 우리
    내부망 구조를 알려 줄 뿐이고 상대가 쓸 일이 없다
- **서버 반사 후보**: STUN으로 얻은 공인 엔드포인트. 질의한 STUN 서버별로 기록한다.

**수신한 후보 목록에 아래 위생 규칙을 적용한다. 선택이 아니다.**

| 규칙 | 근거 |
|------|------|
| 최대 `MAX_CANDIDATES`(8)개. 초과분은 버린다 | 무제한 목록은 무제한 송신을 뜻한다 |
| 브로드캐스트, 멀티캐스트(`224.0.0.0/4`), 미지정(`0.0.0.0`), 루프백(`127.0.0.0/8`) 주소 거부 | 반사 및 증폭 방지 |
| 포트 0 거부 | |
| 중복 제거 | |

2장에서 밝힌 대로, 이 규칙이 없으면 클라이언트가 공격자 지정 제3자에게 200ms마다 패킷을 보내는 반사 도구가 된다.

**이 표는 후보 목록에만 적용된다.** 수신 데이터그램의 출발지에는 7장의 출발지 위생이 따로
적용되며, 두 표는 루프백 처리가 다르다. 이유는 7장에 적었다.

### 10.2 랑데부

펀치 시작이 어긋나면 한쪽 패킷이 상대 NAT에 전부 버려진다.

1. 두 피어가 각각 `register_candidate`를 완료한다.
2. `get_peers`는 양쪽 등록 전에는 `not_ready`를 반환한다.
3. **두 번째 등록이 완료되는 순간 서버가 `punch_delay_ms = 1000`을 방 단위로 한 번 확정해 저장한다.** 이후 모든 `get_peers` 응답은 저장된 값을 그대로 돌려준다. 응답마다 새로 계산하면 두 피어가 서로 다른 시각을 받는다.
4. 응답에는 `punch_delay_ms`와 함께 `elapsed_since_ready_ms`(서버가 준비 완료 이후 흐른 시간)를 담는다. **절대 시각을 쓰지 않는다.** 클라이언트 시계가 동기화되어 있다는 보장이 없다.
5. 클라이언트는 `get_peers`를 500ms 간격으로 폴링한다. 최대 60초.
6. 준비 완료 응답을 받으면 `max(0, punch_delay_ms - elapsed_since_ready_ms)` 밀리초 뒤에 펀치를 시작한다. 음수면 즉시 시작한다.

상대가 50초 늦게 클라이언트를 켜도 동작한다. 먼저 켠 쪽은 계속 폴링하고 있고, 준비가 되는 순간 양쪽이 같은 기준점에서 지연을 계산한다.

**남는 오차의 상한.** 두 피어의 실제 펀치 시작 시각 차이는 `폴링 간격(500ms) + 두 응답의
전송 지연 차이`로 제한된다.

- 서버가 준비 완료를 판정한 시점부터 각자가 응답을 받기까지 걸린 시간이
  `elapsed_since_ready_ms`에 반영되지 않기 때문이다
- 일반적인 조건에서 이 값은 1초 미만이고, 펀치 구간 10초와 200ms 재전송이 충분히 흡수한다
- 이 상한을 넘는 환경(예: 응답 지연이 수 초)에서는 펀치 구간을 늘려야 한다. 그 경우 이
  문서를 갱신한다

### 10.3 펀치

- 펀치 시작부터 **상대의 모든 후보에** `HELLO`를 200ms 간격으로 보낸다
  - 살아 있는 시도 안에서 재전송을 멈추는 계기는 `CONNECTED` 도달뿐이다 (11장 타이머).
    상태가 `HANDSHAKING`으로 바뀌어도 멈추지 않는다. 한쪽 증거만 선 상태에서 멈추면 남은
    증거를 얻을 수단이 없어진다
  - 시도가 끝나면 재전송도 끝난다. 9.6 실패 전이가 이 타이머를 멈추고, 9.5 재협상은 반대로
    다시 시작한다(10번)
- 펀치 마감은 **실제 로컬 시작 시각으로부터 10초**다. 예정 시각이 이미 지나서 즉시 시작한 경우에도 마감은 그 시점부터 10초다.
- 마감까지 `CONNECTED`에 도달하지 못하면 9.6 실패 전이에 따라 실패 기록.

### 10.4 엔드포인트 학습

v1은 고정 지명(nomination) 대신 **학습(learning)** 을 쓴다.

```text
peer_endpoint = 아래 조건을 모두 만족하는 가장 최근 패킷의 출발지 엔드포인트

  (a) 해당 타입의 모든 검증을 통과했다
      (8.1~8.3 공통 + DATA 는 8.4, PONG 은 5.5 매칭, CLOSE 는 reason 검증까지)
  (b) 4.5 중복 억제와 손실 집계에서 highest 를 **전진**시켰다 (재정렬 수용 패킷은 제외)
  (c) 출발지가 승인된 후보 집합에 있거나, 경로 검증(아래)을 통과했다
```

**이 절이 정하는 것은 우리가 먼저 보내는 `DATA`, `KEEPALIVE`, `PING`의 목적지다.** 그 셋은
학습된 `peer_endpoint`로 보내고, 아직 학습하지 못했으면 후보 전체로 보낸다.

**응답은 이 절이 정하지 않는다.** 응답은 받은 데이터그램의 출발지로 가며 9.4 전이표가
소유한다. 나머지 송신은 각자 다른 절이 정하며 이 규칙의 예외다.

| 송신 | 목적지 | 정하는 곳 |
|------|--------|-----------|
| `DATA`, `KEEPALIVE`, `PING` | `peer_endpoint`. 학습 전이면 후보 전체 | 이 절 |
| `PONG` (응답) | 이 절이 정하지 않는다 | 9.4 |
| `HELLO` 재전송 (펀치) | **후보 전체.** `CONNECTED` 도달까지 계속한다. 학습 여부와 무관하다 | 10.3 |
| `HELLO` 재전송 (재협상 뒤) | 후보 전체 | 9.5 9번 |
| `HELLO_ACK` (응답) | 받은 데이터그램의 출발지 | 9.4, 9.5 6번 |
| 검증 `HELLO` (probe) | 그 잠정 경로의 주소 | 10.4 (c) |
| `CLOSE` | 학습한 `peer_endpoint`. 학습 전이면 보내지 않는다 | 5.6 |

**`HELLO` 재전송을 `peer_endpoint`로 좁히지 않는 이유.** 학습은 한 경로가 살아 있다는 증거일
뿐이고, 펀치의 목적은 **아직 열리지 않은 경로를 여는 것**이다. 학습 뒤에 재전송을 한 주소로
좁히면 그 경로가 죽었을 때 대안이 사라진다.

학습 여부의 판단 기준은 상태가 아니다. `PUNCHING`이라는 이유만으로 후보 전체가 되는 것이
아니다. 9.5 재협상은 `peer_endpoint`를 **유지한 채 왕복 증거만 지우므로**, 학습된 값이 있는
상태에서 `CONNECTED` 이전으로 돌아간 세션이 존재한다. 그 경우의 `HELLO` 재전송 대상은
9.5 9번이 따로 정한다. 그때의 상태 이름은 9.5 7번이 플래그에서 파생시키므로 여기서 특정
상태를 전제하지 않는다.

**(b)가 없으면** 4.5 중복 억제와 손실 집계의 64칸 수용 창 안에서 수용된 오래된 패킷이 엔드포인트를 이전 경로로 되돌린다. 전진한 패킷만 학습에 쓰면 되돌림이 생기지 않는다.

**(c)의 경로 검증.** 후보 집합에 없는 주소에서 패킷이 오면 즉시 전환하지 않는다. NAT 리바인딩으로 포트가 바뀐 정상적인 경우와, 출발지를 위조한 공격의 구분이 불가능하기 때문이다.

```text
1. 잠정 경로 표가 MAX_PROBE_PATHS(4) 로 차 있으면 경로 등록만 건너뛰고 drop_probe_full.
   원 패킷은 9.4 전이표대로 계속 처리한다. 폐기가 아니다.
   가장 오래된 항목을 밀어내지 않는다.
2. 9.4 전이표의 무검증 목적지 공통 예산에서 토큰 하나를 확보한다. 없으면 여기서 멈추고
   drop_unverified_tx 를 올린다. 잠정 경로를 만들지 않는다.
3. 새 주소를 잠정 경로로 기록한다. peer_endpoint 는 그대로 둔다.
4. 그 주소로 probe nonce 를 담은 HELLO 를 1회 보낸다 (5.1). 재전송하지 않는다.
   앞에서 확보한 토큰을 여기서 쓴다.
5. 같은 주소에서 그 probe nonce 를 echo 한 HELLO_ACK 이 오면 그때 peer_endpoint 를 전환한다.
   이 ACK 은 핸드셰이크 상태(got_ack, epoch)를 바꾸지 않는다.
6. 5초 안에 오지 않으면 잠정 경로를 버리고 path_probe_failed 를 올린다.
7. 표의 자리는 **결과와 무관하게 5초를 채우고 비워진다.** 전환에 성공해도 그 자리를
   즉시 반납하지 않는다. 성공이 자리를 즉시 비우면, 주소를 실제로 받을 수 있는 공격자가
   probe 마다 응답해 자리를 계속 회전시켜 위 상한을 무력화한다.
```

**표가 가득 찼거나 토큰이 없어 멈추는 경우에도 원 패킷은 버리지 않는다.** 그 패킷은 8.1
공통 검사부터 8.3 중복 억제까지를 이미 통과하고 `sequence`도 전진시킨 정상 패킷이며,
9.4 전이표가 그 상태와 타입에 대해 정한 대로 계속 처리된다.

- 유휴 타이머 갱신과 `DATA` 주입은 그 표가 허용하는 상태에서만 일어난다. 이 절차가 멈춰도
  그 처리를 바꾸지 않는다는 뜻이지, 상태와 무관하게 전부 수행한다는 뜻이 아니다
- 멈추면서 건너뛰는 것은 새 경로를 검증 대상으로 올리는 일뿐이다. 그 결과로
  `peer_endpoint` 전환이 늦어진다
- `drop_probe_full`이라는 이름이 세는 것도 "버린 패킷"이 아니라 "등록하지 못한 경로"다

> **왜.** 원 패킷을 버리면 유휴 타이머가 갱신되지 않아 살아 있는 세션이 단절로 판정될 수
> 있다.

**표가 가득 찼을 때 밀어내지 않는 이유.** 가장 오래된 것을 밀어내면 위조 출발지를 빠르게 보내는 쪽이
진짜 새 경로를 표에서 밀어낼 수 있다. 채우는 쪽이 공격자이므로 **먼저 온 것을 지키는 편이
안전하다.** 대가는 진짜 경로의 검증이 늦어지는 것이다.

**그 대가를 정확히 적는다. "5초 뒤에는 풀린다"가 아니다.** 공격자가 자리가 비는 대로 다시
채우면 그 세션은 새 엔드포인트를 영영 검증하지 못한다. 즉 지속적인 출발지 위조는 그 세션의
경로 전환 능력을 무기한 막을 수 있고, 실제로 경로가 바뀐 상황이었다면 유휴 타임아웃 50초 뒤
`TUNNEL_DROPPED`로 끝난다. v1이 수용하는 한계다.

> **왜.** 공평성을 주려면 출발지별 쿨다운이 필요한데, 출발지를 위조할 수 있는 상대에게
> 출발지 기준 공평성은 성립하지 않는다.

**반사의 상한은 이 절이 따로 정하지 않는다.** 검증 `HELLO`는 무검증 목적지로 나가는 송신
셋 중 하나이고, 그 총량은 9.4 전이표의 공통 예산이 정한다. **세션당 초당 5패킷, 순간 10패킷이다.**
여기에 숫자를 다시 적지 않는다. 경로별로 따로 세면 세 경로의 합이 보이지 않는다.

이 절이 추가로 거는 제약은 **동시 잠정 경로 4개와 경로당 검증 `HELLO` 1회**다. 그 둘은
표의 크기와 재전송 여부를 정하는 것이고 송신 속도를 정하는 것이 아니다. 2장이 약속한
"타인 피해 경로 차단"은 여기서 완전한 차단이 아니라 공통 예산으로 지켜진다.

**이 절차의 전제와 실측 한계.** 이 절차 전체는 후보 집합 밖 주소에서 패킷이 실제로
도착한다는 것을 전제한다. 실측에서 그 전제가 성립하지 않는 경우를 확인했다.

- 측정한 망은 3쌍이다. Windows↔Windows, Windows↔macOS, Windows↔Linux
- 세 쌍 모두에서 **출발지 IP는 같고 출발지 포트만 다른** UDP 가 양방향 전부 차단됐다
  (6건, 각 20발 중 0발 도착)

**가장 유력한 설명은 NAT의 포트 제한 필터링이다.** 호스트 방화벽 필터링이 없다고 보이는
macOS와 Linux에서도 같은 결과였기 때문이다. 다만 단정하지는 않는다. 확인하지 못한 것이
셋이다.

- macOS 쪽은 기본값에 근거한 추론이고 직접 조회하지 않았다
- Linux 쪽은 `ufw` 가 꺼진 것만 확인했다. root 권한이 없어 `nft`/`iptables` 규칙 전체는
  보지 못했다
- 양쪽 패킷 캡처도 하지 않았다

**따라서 v1은 (c)로 NAT 리바인딩을 복구한다고 보장하지 않는다.** 정확히는, 시험한
거동(출발지 포트만 바뀐 경우)과 일치하는 엔드포인트 변화에 대해 보장하지 않는다. 실제
리바인딩을 인위적으로 일으켜 시험하지는 않았으므로 "모든 리바인딩에서 실패한다"고 주장하지
않는다.

보장되지 않는 경우에는 아래가 일어난다.

- 이 절차가 시작되지 않고, 같은 이유로 9.5 재협상도 계기를 얻지 못한다
- 양쪽이 유휴 타임아웃(50s)에 도달해 `TUNNEL_DROPPED`로 세션이 끝난다
- 9.6 실패 전이가 정한 대로 재시도를 한다면 `IDLE`부터 새 epoch와 새 nonce로 시작하며 제어
  평면을 다시 거친다

**재시도를 누가 언제 개시하는지는 이 문서가 정하지 않았다.** 자동 재시도 여부는 미정이다.

**프로세스 재시작도 같은 실패에 걸린다.** 6장에 따라 소켓은 포트 0으로 bind 하므로 재시작한
쪽은 새 로컬 포트를 얻고, 따라서 새 NAT 매핑을 얻는다. 살아남은 쪽에는 **같은 IP, 다른
포트**로 도착하는데 그것이 위에서 실측한 차단 케이스다. 살아남은 쪽은 9.5 8번대로 제어
평면을 다시 거치지 않으므로 상대의 새 엔드포인트를 알 길도 없다. 정리하면 이렇다.

| 무엇이 바뀌었나 | 9.5 재협상이 복구하는가 |
|-----------------|-------------------------|
| 같은 소켓에서 새 시도 (epoch만 바뀜) | **그렇다.** 출발지가 그대로라 `HELLO`가 도착한다 |
| 소켓이 바뀜 (프로세스 재시작, 리바인딩) | **아니다.** 새 출발지의 `HELLO`가 위 실측대로 차단되면 재협상의 계기 자체가 생기지 않는다 |

따라서 **`session_epoch`와 9.5 재협상은 같은 소켓에서의 재시도를 위한 장치이고, 재시작 복구를
보장하지 않는다.** 재시작한 쪽이 혼자 다시 시도해도 상대의 세션이 살아 있는 동안에는
닿지 않는다.

**두 쪽이 서로 다른 코드를 남긴다.** 위 리바인딩 설명의 "양쪽이 유휴 타임아웃에 도달한다"는
두 쪽이 같은 세션에 남아 있는 경우이고, 재시작은 그렇지 않다.

| 쪽 | 무엇에 걸리는가 | 기록되는 코드 |
|----|-----------------|----------------|
| 살아남은 쪽 | 수립 후 유휴 타임아웃 50초 | `TUNNEL_DROPPED` |
| 재시작한 쪽 | 새 시도의 펀치 마감 10초 | 9.6 실패 전이의 플래그 개수 기준. 둘 다 미성립이면 `HOLE_PUNCH_TIMEOUT`, 하나만 성립이면 `PEER_HANDSHAKE_FAILED` |

복구하려면 양쪽이 `IDLE`부터 새 시도를 시작해야 하는데, 살아남은 쪽은 위 50초를 기다린
뒤에야 그 지점에 온다. 그 다음이 위에 적은
미정 항목(자동 재시도)이다. 4.3 `session_epoch`가 "재시작이나 재시도 후 이전 시도의 지연 패킷"을 막는다고
적은 것은 **지연 패킷을 거르는 것**이지 재시작한 세션을 잇는 것이 아니다.

살아남은 쪽이 제어 평면을 다시 폴링해 상대의 새 후보를 받는 방법이 있다. v1은 채택하지
않는다. 그 전제인 "재참가 시 `peer_id`와 가상 IP가 유지된다"는 14장 계약 7로 정해졌으므로,
채택하지 않는 이유는 전제가 없어서가 아니라 **누가 언제 재폴링을 개시하는지**가 위의 자동
재시도와 같이 미정이기 때문이다.

(c)를 없애지는 않는다. 두 가지 이유다.

- **위조 출발지 방어**라는 보안 역할이 그대로 남는다. 후보 집합 밖 주소에서 패킷이
  도착하기만 하면 그 검증이 필요하다
- **주소 제한(restricted cone) 필터링을 쓰는 NAT에서는 도착할 수 있다.** 이번 관측은 전부
  포트 제한 NAT 과 일치할 뿐이고, 그렇다고 확정된 것은 아니다

근거와 버린 대안은 [`decisions/0002-리바인딩-복구-미보장.md`](decisions/0002-리바인딩-복구-미보장.md)에 있다.

출발지를 위조한 공격자는 2번의 `HELLO`를 받지 못하므로 3번을 통과할 수 없다. 이것이 2장에서 약속한 "제3자 피해 경로 차단"을 학습 방식에서도 유지하는 방법이다. 이 절차가 없으면 세션 식별자를 아는 쪽이 출발지를 위조해 게임 트래픽 전체를 임의의 피해자에게 돌릴 수 있다.

지명 방식을 쓰지 않는 이유는 세 가지다.

- **같은 NAT 뒤**: 두 피어가 LAN 경로와 헤어핀 공인 경로를 각각 지명하면 서로 다른 엔드포인트에 고정되어 상대 패킷이 전부 걸러지는 교착이 생긴다.
- **비대칭 지명**: 한쪽은 LAN 후보로 받고 다른 쪽은 공인 후보로 보내면 같은 교착이 생긴다.
- **NAT 리바인딩**: 매핑이 바뀌어도 epoch는 그대로이므로, 고정 방식에서는 재협상 계기가
  없어 유휴 타임아웃까지 기다려야 한다
  - 이 이유는 실측으로 약해졌다. 학습 방식도 시험한 거동(출발지 포트만 바뀌고 관측된
    필터링에 걸리는 경우)과 일치하는 리바인딩에 대해서는 복구를 보장하지 못한다
    (위 (c)의 실측 한계 참조)
  - 즉 두 방식을 가르는 근거가 되지 못한다. 리바인딩 자체를 일으켜 시험한 것이 아니므로 이
    이유가 모든 리바인딩에서 무효라고 주장하지도 않는다

나머지 두 이유는 유효하므로 학습 방식 자체는 유지한다.

학습 방식은 **가장 최근에 실제로 도착한 경로**를 쓰므로 앞의 두 경우(같은 NAT 뒤, 비대칭
지명)는 자동으로 수렴한다. 중복 억제(4.5)가 오래된 패킷을 먼저 걸러내므로 이전 경로의 지연
패킷이 엔드포인트를 되돌리지 못한다.

**리바인딩은 다르다.** 후보 집합 밖 주소에서 패킷이 실제로 도착해야 10.4 (c) 경로 검증이
시작되고, 도착하지 않으면 수렴하지 않는다.

엔드포인트가 바뀌면 `endpoint_learned` 카운터를 올린다. 이 값이 계속 증가하면 경로가 진동하는 것이므로 진단에 쓴다.

### 10.5 보안 결과

10.4 (c)의 경로 검증 덕분에, 세션 식별자를 아는 공격자가 **출발지만 위조해서 `DATA` 흐름
전체를 제3자에게 돌리는 것**은 v1에서도 막힌다. 검증용 `HELLO`가 위조된 주소로 가므로
공격자가 응답할 수 없고, 응답이 없으면 `peer_endpoint`가 전환되지 않는다.

**막는 것과 제한하는 것을 구분하고, 소유자도 나눈다.** `DATA` 흐름의 대량 전환은 10.4 (c)의
경로 검증이 막는다. 그 검증용 `HELLO` 자체는 위조된 주소로 나가므로 남고, **그 송신량은
9.4 전이표의 무검증 목적지 공통 예산이 제한한다.** 10.4 (c)가 정하는 것은 동시 잠정 경로 수와
경로당 송신 횟수이고, 속도 상한이 아니다. 수치는 9.4 전이표에만 적는다.

막지 못하는 것은 여전히 남는다. 공격자가 실제로 패킷을 받을 수 있는 주소를 쓰면(자기 주소) 경로 검증을 통과해 트래픽을 자신에게 끌어올 수 있다. 내용을 읽고 변조하는 것도 막지 못한다. 2장의 전제상 v1은 이를 막지 않으며, 암호화와 피어 인증을 도입할 때 경로 검증에 MAC을 붙여야 한다.

## 11. 타이머

**세션 타이머.** "세션 종료" 는 `CONNECTED`를 떠나는 것 전부다. 9.5 재협상(10번), 9.6 실패
전이, `CLOSE` 송수신이 모두 여기에 든다.

| 타이머 | 값 | 시작 | 초기화 계기 | 취소 |
|--------|-----|------|-------------|------|
| STUN 재시도 | 500ms, 1s, 2s (3회) | STUN 요청 송신 | 없음 | 응답 수신 |
| STUN 마감 | 5s. **서버별이다** | 그 서버로 보낸 첫 요청 | 없음 | 그 서버의 응답 수신 |
| `get_peers` 폴링 | 500ms 간격 | **`register_candidate` 성공 응답** | 매 응답 | 준비 완료 응답 |
| `get_peers` 마감 | 60s | **`register_candidate` 성공 응답** | 없음 | 준비 완료 응답 |
| 펀치 지연 | 10.2 랑데부의 계산값 | 준비 완료 응답 | 없음 | 만료 시 펀치 시작 |
| `HELLO` 재전송 | 200ms 간격 | 펀치 시작, **9.5 재협상(10번)** | 매 송신 | `CONNECTED` 도달, 9.6 실패 전이 |
| 펀치 마감 | 10s | **실제 로컬 펀치 시작** | 9.5 재협상 | `CONNECTED` 도달 |
| `KEEPALIVE` | 15s 간격 | `CONNECTED` 진입 **즉시 1회 송신 후** | 매 송신 | 세션 종료 |
| 유휴 타임아웃 | 50s | `CONNECTED` 진입 | 타입별 전체 검증 통과 패킷 수신 (9.4) | 세션 종료 |
| `PING` | 5s 간격. **진입 즉시 보내지 않는다. 첫 송신은 진입 5s 뒤다** | `CONNECTED` 진입 | 매 송신 | 세션 종료 |
| `pending_pings` 정리 | 삽입 전 매회 | - | - | - |

**STUN 마감이 서버별인 결과.** 한 서버가 마감에 걸리면 목록의 다음 서버로 바꿔 다시 질의하고
(그 서버의 재시도 일정과 마감이 새로 시작한다), 실패는 목록을 다 쓴 뒤에 판정한다. 선택과
교체 규칙은 [`architecture.md`](architecture.md) 3.5 기동 입력이 갖고, 실패 조건은 9.6 실패 전이가 그 절을
가리킨다. **STUN 단계 전체의 상한은 `5s × ceil(목록 길이 / 2)`다.** 두 서버에 동시에 질의
하기 때문이다. 기본 목록 4개면 10초다.

**아래 만료 값은 타이머 표에 없지만 시간으로 만료된다.** 세션마다 하나씩 도는 타이머가
아니라 표의 항목마다 붙는 수명이라 위 표에 넣지 않았다. 구현은 이것도 함께 챙긴다.
**이 표는 색인이다. 값의 출처는 "어디" 열의 절이다.**

| 무엇 | 값 | 어디 |
|------|-----|------|
| 폐기 목록 항목 | 2분 (상한이 먼저다. best-effort) | 4.3 |
| 시도 nonce 폐기 목록 항목 | 2분 | 5.1 |
| probe nonce와 잠정 경로 자리 | 5초 (결과와 무관하게 채운다) | 5.1, 10.4 (c) |
| `pending_pings` 항목 | 5초 | 5.5 |
| 재협상 최소 간격 | `MIN_RENEG_INTERVAL_MS`(1000ms) | 9.5 |

마감 비교는 **엄격 부등호**를 쓴다. 우선순위는 큐에서 꺼낸 시각 기준이다. 같은 바퀴에 꺼낸
수신 이벤트가 그 바퀴의 타이머 만료보다 먼저 처리된다.

도착 시각이 아니라 꺼낸 시각인 이유는 수신 루프가 한 바퀴에 처리하는 데이터그램 수에
상한을 두기 때문이다(`architecture.md` 3.2.3 루프 한 바퀴). 상한 없이 비우면 타이머가 아예
돌지 않는다.

그 대신 마감 직전에 도착한 데이터그램이 다음 바퀴로 밀려 타이머에 질 수 있다. 루프가 부하를
따라가는 동안 이 지연은 1ms 미만이고, 가장 짧은 마감(200ms)보다 두 자릿수 작다. 루프가
지속적으로 못 따라가면 소켓 버퍼가 넘쳐 패킷이 버려진다. 그것은 타이머 순서 문제가 아니라
과부하다.

유휴 타임아웃이 45s가 아니라 **50s**인 이유: `CONNECTED` 진입 즉시 keepalive를 1회 보내므로 45s 안에 0s, 15s, 30s, 45s의 4회 송신 기회가 있다. 45s로 잡으면 마지막 송신과 타임아웃이 같은 시각에 경합한다. 50s는 3회 손실을 견디고 네 번째에 회복할 여유를 준다.

15s와 50s는 초기값이다. 매핑 수명 실측으로 조정하면 이 문서를 갱신한다.

## 12. 크기 제한과 조각화

```text
1500 (외부 경로 MTU 가정)
 - 20 (외부 IPv4 헤더)
 -  8 (외부 UDP 헤더)
 - 20 (터널 헤더)
= 1452 바이트 = MAX_INNER
```

가상 어댑터 MTU 기본값은 **1400**이다. `MAX_INNER`보다 52바이트 여유를 둬서 외부 경로 MTU가 1448까지 떨어져도 버틴다.

**외부 UDP 패킷에 DF 비트를 세우지 않는다.** Windows에서 `IP_DONTFRAGMENT`는 UDP 기본값이
off이므로 켜지 않으면 된다.

> **왜.** DF를 세우면 경로 MTU가 작을 때 중간 라우터가 조용히 버려서 작은 패킷만 통과하고
> 큰 패킷이 사라진다. 내부 TCP가 재전송 블랙홀에 빠진다. 로그인은 되는데 월드 로딩에서
> 멈추는 전형적 증상이 이것이다.

완전한 PMTU 탐색은 v1 범위 밖이다. 실측으로 기본값을 확정하고 한계를 [`experiments.md`](experiments.md)에 기록한다. **보수적 고정값을 그대로 쓰기로 결정하는 경우에도 그 값이 못 덮는 경로를 같은 곳에 적는다.** 값을 정하지 않는 것과 정하고 한계를 적는 것은 다르다.

## 13. STUN 사용 범위

RFC 5389 중 아래만 구현한다.

- **메시지**: Binding Request(`0x0001`), Binding Success Response(`0x0101`), Binding Error Response(`0x0111`)
- **송신 속성**: 없음. Binding Request는 헤더만 보낸다
- **해석 속성**: `XOR-MAPPED-ADDRESS`(`0x0020`)만. 나머지 속성은 건너뛴다. `ERROR-CODE`는 값만 로그에 남긴다
- **트랜잭션 ID**: OS CSPRNG로 96비트
- **응답 검증**: magic cookie 일치, 트랜잭션 ID 일치, 메시지 길이가 헤더의 길이 필드와 일치, 속성 순회 중 경계 초과 시 중단
- **주소군**: `XOR-MAPPED-ADDRESS`의 family가 IPv4(`0x01`)가 아니면 폐기
- **재시도**: 11장 표

FINGERPRINT, MESSAGE-INTEGRITY, 인증, TURN, ICE 절차는 구현하지 않는다.

## 14. 제어 평면 스키마

제어 평면의 요청/응답 인코딩, 오류 스키마, 상태 전이는 이 문서 범위 밖이고 [`control_plane.md`](control_plane.md)가 확정한다. 이 문서가 제어 평면에 요구하는 계약은 다음뿐이고, **각 계약을 어디서 충족하는지는 그 문서 1.3 (`protocol.md` 14장 계약과의 대응)이 색인한다.**

1. `peer_id`는 방 안에서 유일하다 (4.2)
2. `get_peers`는 양쪽 등록 전에 `not_ready`를 반환한다 (10.2)
3. `punch_delay_ms`는 두 번째 등록 완료 시 방 단위로 한 번 확정되고 이후 변하지 않는다 (10.2)
4. `get_peers` 응답은 `elapsed_since_ready_ms`를 포함하고, 그 값은 **단조 시계**로 계산한다
   (10.2 랑데부)
   - 벽시계로 계산하면 NTP 가 시각을 건너뛰는 순간 두 피어가 받는 값이 어긋나 10.2 랑데부의 오차
     상한이 깨진다
   - 서버가 단조 기준을 잃는 경우(인스턴스 재부팅)의 대체 계산은 `control_plane.md` 7.4
     시계가 정한다. 그 경우에는 10.2 랑데부의 오차 상한이 보장되지 않는다
5. 후보는 10.1 후보 수집과 위생의 규칙을 통과한 것만 저장하고 전달한다
6. 각 피어의 가상 IP를 상대에게 알려준다 (5.1 `HELLO`의 `virtual_ip` 검증에 필요)
7. **재참가한 피어에게 같은 `peer_id`와 같은 가상 IP를 돌려준다.** 새 값을 주면 상대 쪽 8.1 검사 7번(`drop_unknown_peer`)과 5.1 `HELLO`의 `virtual_ip` 검증에서 전부 버려지고 재협상의 계기도 되지 못한다. 재참가가 성립하는 조건은 그 문서가 정한다
8. `peer_id`는 **CSPRNG 32비트**로 뽑는다. 유일성만 요구하면 순차 할당도 계약을 지키는데, 그러면 2장의 "알거나 추측하면"에서 추측이 자명해진다

이 8개 계약이 깨지면 터널 프로토콜이 성립하지 않는다.

## 15. 구현 체크리스트

Phase 4 에서 아래가 전부 코드에 있어야 한다. Phase 4 가 이 체크리스트를 구현하는 단계다.

- [ ] 3장 상수 전부
- [ ] 필드 단위 헤더 직렬화/역직렬화 + 라운드트립 테스트
- [ ] `SO_EXCLUSIVEADDRUSE`, `SO_REUSEADDR` 미사용, `SIO_UDP_CONNRESET` off, `connect()` 미호출
- [ ] `INADDR_ANY` + 포트 0 bind, `getsockname`으로 실제 포트 확인, `SO_RCVBUF` 설정과 적용값 확인 (6장)

- [ ] 7장 출발지 위생(분류 전, `drop_bad_source`)과 분류 (상위 2비트 기준, magic은 검증 단계에서)
- [ ] 8.1 공통 검사 8단계와 전용 카운터
- [ ] 8.2 epoch/출발지 규칙 (특히 nonce 유효 `HELLO_ACK`의 epoch 고정)
- [ ] 8.2 epoch 및 출발지 검사의 `virtual_ip` 검사(`drop_vip_mismatch`). **epoch 판정보다 먼저** (5.1, 5.2)
- [ ] 4.5 중복 억제 알고리즘 (`highest` + `position` + 64비트 비트맵), 부수 효과보다 먼저
- [ ] `seq == highest` 선행 판정, `if/else if/else` 상호 배타 분기, `shift == 64` 처리, 모든 비트 연산 `uint64_t`
- [ ] `is_newer`의 `a != b` 조건
- [ ] 세션 시도 단위 `session_epoch`, CSPRNG와 0 회피, 2분 폐기 목록과 `MAX_RETIRED_EPOCHS` 상한. **폐기 목록에 넣는 것은 상대의 epoch다** (4.3)

- [ ] 10.1 후보 위생 규칙 전부, 로컬 인터페이스 주소와 prefix 보관 (7장 판정의 입력)
- [ ] 10.2 상대 시각 기반 랑데부
- [ ] 10.4 엔드포인트 학습 (전진 패킷만, 후보 밖 주소는 경로 검증 후), `MAX_PROBE_PATHS` 상한과 검증 `HELLO` 1회
- [ ] 9.2 `CONNECTED` 조건의 이중 플래그, `sendto` 성공 후에만 `sent_ack`
- [ ] 9.4 전이표 전체와 9.4.1 종료 상태 폐기(`drop_terminal_state`)
- [ ] 9.4 무검증 목적지 공통 예산. 세션당 토큰 버킷(`UNVERIFIED_TX_BUCKET`, `UNVERIFIED_TX_REFILL`), `HELLO_ACK`·`PONG`·검증 `HELLO` 셋에 적용, `drop_unverified_tx`. **경로별로 따로 세지 않는다**
- [ ] 9.5 재협상 10단계. **특히 로컬 epoch/nonce 유지와 10번 타이머 되돌리기**

  - 10번은 `HELLO` 재전송 재시작과 `KEEPALIVE`·`PING`·유휴 타임아웃 정지다
- [ ] 9.5 재협상 상한 둘 (`MIN_RENEG_INTERVAL_MS`, `MAX_RENEGOTIATIONS`)
- [ ] 11장 타이머 값과 생명주기
- [ ] `CLOSE` 송수신, reason 값 검증, 송신·수신 양쪽의 `CLOSED` 전이와 라우팅 항목만 제거 (5.6)

- [ ] 13장 STUN 범위

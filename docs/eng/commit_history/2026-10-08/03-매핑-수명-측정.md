# Mapping Lifetime Measurement Tool and First Measurement (ADR 0019)

## Why

This is the redesign of the keepalive mapping lifetime measurement procedure, first in "next" of `plan.md`.
A probe that EC2 sends first is unsolicited inbound and is blocked, so the original plan misjudges the
lifetime as 0. The repository owner chose the "separate tool" option and asked for the measurement too.

## Important decisions

- **Warm up.** Checked the Linux conntrack source (`nf_conntrack_proto_udp.c`). A flow that has seen a reply
  and stays active past 2 seconds gets 120 seconds, otherwise 30 seconds. Without warm-up the measurement is
  shorter than a live tunnel
- **One socket and one LATE per delay value.** Avoids overestimating on NATs where inbound packets refresh the
  timer (RFC 4787 REQ-6)
- **Port 47000.** RFC 4787 REQ-5a allows shorter timers on well-known ports
- **No public IP in logs or results.** Result JSON stays only in the ignored `results/`
- The repository owner opened the security group rule briefly in the console to the measuring machine's `/32`.
  This machine has no AWS CLI

## Measurement

Conditions. This development machine, one home Wi-Fi (gateway `10.0.0.1`). The `python.exe` used has a Windows
firewall inbound allow rule, so the host firewall was not measured. Tailscale was on and the path to EC2 was
Wi-Fi. The responder was the control plane instance in us-west-2, UDP 47000.

| Run | Delays (s) | Arrived | Verdict |
|------|------|------|------|
| r1, r2, r3 | 5, 20, 30, 45, 60, 90, 120, 150, 180, 240, 300 | 5-45 | `[45, 60)` all three times |
| fine1, fine2 | 5, 46, 48, 50, 52, 54, 56, 58 | All | `58` or more both times |

- Every trial got 6/6 warm-up ACKs and the final ACK. No trial was excluded
- The responder log shows `late_sent` 50 (1 check + 33 + 16). The responder sent the LATEs that did not arrive
  too. The loss is on the path
- Arrived LATEs were within -0.091 s to +0.141 s of the requested delay, by the idle time the client measured
- **The combined result is `[58, 60)` seconds.** It is an estimate of when late replies stop on this path. It
  does not separate mapping expiry from filter closing, so whether RFC 4787 REQ-5 (mapping 2 minutes or more) is
  met is not decided
- EC2 has no host firewall (`iptables -S` is all `ACCEPT`, no `nft` rules). The responder log shows 0 refusals
- The security group outbound rule is the default "All traffic `0.0.0.0/0`" (checked by the repository owner in the
  console). LATEs after connection tracking ends still leave. The cutoff is not on the EC2 side

**Rule.** The repository owner chose `interval × 3 < smallest measured lifetime` (`protocol.md` chapter 11, ADR
0019 Decision 7). 15 seconds gives 45 seconds and keeps it. 15 and 50 seconds stay. Measuring the other home is
waiting in `plan.md`.

**The measurement used the tool before the review fixes.** Two fixes could change results: signaling refusal in
the ACK and the per-trial window. The responder log shows 0 refusals and every arrived LATE was inside the window
(T + 5 s), so the result stands.

## Cross-model review

Codex. Two lenses (code and security, measurement method and documentation) run separately on the staged diff.

| Lens | Finding | Handling |
|------|------|------|
| Code | blocker. Requests refused by caps get the same ACK, so refusal reads as NAT expiry. The loopback test took that as correct | Accepted. The ACK's second byte is a status (none, scheduled, refused). Refused trials are invalid. The test now simulates expiry by dropping LATEs on the sending side, and refusal is checked separately |
| Code | blocker. A short trial's LATE counts even if it arrives after that trial's window | Accepted. Per-trial `T + grace` window; outside it is `late_outside_window` |
| Code | warn. A long delay list exceeds the Windows `select` limit (512) and sockets are not closed | Accepted. 64-trial cap, closed in `finally` |
| Code | warn. ACK plus LATE is 52 bytes, longer than REQ (32). Spoofed-source reflection is not prevented | Accepted. REQ is 64 bytes. README states spoofing is not prevented and relies on the security group `/32` |
| Code | warn. No rate limit on ACKs and logs | Accepted. Per-second REQ cap; dropped datagrams are only counted and reported in one line at the end |
| Code | warn. The clock is read before sending the ACK, so a slow send shortens the idle | Accepted. Read after the ACK. Test added |
| Code | warn. `inf` and delays under 0.5 ms | Accepted. Finite values of 1 ms or more within the wire limit |
| Method | blocker. After AWS connection tracking ends, the LATE depends on the outbound rule. The cutoff might not be the NAT's | Accepted. Checked the AWS documentation (UDP 30 s, stream 180 s by default, stream minimum 60 s). README now requires checking the outbound rule and the host firewall. The outbound rule check for this measurement is below |
| Method | warn. Compared with RFC 4787 REQ-5 and said "before the mapping ends" while not separating filter and mapping | Accepted. Written as a cutoff estimate; no REQ-5 verdict |
| Method | warn. The ±0.1 s claim contradicts +0.141 s on the r2 45-second trial | Accepted. Actual range |
| Method | warn. Zero ACKs do not mean only the security group | Accepted. Undeterminable, causes checked in order |

The second review (repair check) raised one blocker. The end of the whole measurement was fixed at `final request + max
delay + grace`, so a trial whose final ACK came late was cut before its promised window. Accepted. Each final ACK now
extends the end to that trial's window end. A test with a slow path for one trial was added. The first measurement is not
affected, since its RTT is far shorter than the 5-second grace.

The third review (checking that fix) returned `LGTM - no blockers`.

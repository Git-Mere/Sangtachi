# 0001. Linux 기기의 Wi-Fi 절전으로 터널 ping 이 느렸다

- 상태: 우회
- 발견: 2026-10-31
- 관련: [ADR 0035](../decisions/0035-linux-콘솔-클라이언트.md), [`../linux-prereq.md`](../linux-prereq.md),
  [`../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md`](../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md)

## 증상

Linux 콘솔 클라이언트의 첫 두 기기 확인이다. Linux 기기 `mere-galaxy` 가 어댑터를 붙인 호스트(`10.100.0.1`), Windows 기기가
플레이어(`10.100.0.2`)였다. 두 기기는 같은 공유기의 무선 LAN 에 있었다.

| 방향 | 결과 |
|------|------|
| Windows → `10.100.0.1` | 4/4, 168~208ms, 평균 189ms |
| `mere-galaxy` → `10.100.0.2` | 6/6, 5~23ms |

같은 터널인데 한쪽 방향만 열 배쯤 느렸다.

## 조사

| 의심한 것 | 본 것 | 판단 |
|-----------|-------|------|
| 클라이언트가 TUN 에서 늦게 읽는다 | `strace` 로 보면 `[loop]` 의 `poll` 대기 집합에 TUN fd 가 있고, `POLLIN` 직후 `read` 가 나온다 | 아니다 |
| TUN 경로 자체가 느리다 | `mere-galaxy` 가 먼저 보내는 방향도 같은 TUN 읽기와 주입을 거치는데 5~23ms 다 | 아니다 |
| 무선 구간이 느리다 | 클라이언트 없이 Windows 가 `mere-galaxy` 의 LAN 주소로 보낸 `ping` 도 3~208ms, 평균 96ms 였다 | 맞다. 우리 프로그램 밖이다 |
| 무선 절전 | `iw dev wlo1 get power_save` 가 `on` 이었다. `mere-galaxy` 가 공유기로 50ms 마다 `ping` 을 쏘아 무선을 깨워 두면, 같은 LAN `ping` 이 3~19ms, 평균 9ms 로 내려갔다 | 원인으로 본다 |

## 원인

**확인한 것.** 느린 것은 터널이 아니라 `mere-galaxy` 의 무선 구간이다. 클라이언트 없이도 같은 지연이 나왔다. 무선을 깨워 두면
지연이 사라졌다.

**추정한 것.** 절전 중인 무선 장치는 공유기가 들어오는 프레임을 잡아 두었다가 장치가 깨어날 때 넘긴다. 그래서 밖에서 먼저 오는
패킷만 늦다. `mere-galaxy` 가 먼저 보내는 방향은 보내는 순간 장치가 깨어 있어 응답을 바로 받는다. 한쪽 방향만 느린 것과 맞는다.
공유기 쪽 설정은 보지 않았다.

## 처리

실측 동안 `mere-galaxy` 의 무선 절전을 껐다. 코드는 바꾸지 않았다.

```bash
sudo iw dev wlo1 set power_save off
```

이 설정은 재부팅하면 되돌아간다. 영구 설정(NetworkManager 의 `wifi.powersave`)은 넣지 않았다.

## 결과

절전을 끈 뒤 같은 구성의 `ping` 이다.

| 방향 | 결과 |
|------|------|
| Windows → `10.100.0.1` | 4/4, 10~78ms, 평균 31ms |
| `mere-galaxy` → `10.100.0.2` | 4/4, 25~113ms, 평균 76ms |

Windows 에서 보낸 방향은 평균 189ms 에서 31ms 로 내려갔다. 반대 방향은 처음(5~23ms)보다 오히려 높았다. 그 원인은 보지 않았다.
두 측정은 다른 세션이고 표본이 넷이나 여섯이라 분포를 말할 수는 없다.

값은 그때의 `ping` 출력에서 옮겼다. 출력 원본은 저장소에 남기지 않았다.

- 실측 전에 `iw dev wlo1 get power_save` 로 절전이 꺼져 있는지 본다. 유선을 쓰면 이 이슈가 없다
- 절전을 되돌리는 일은 `plan.md` 가 갖는다

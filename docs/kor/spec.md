## 목적

멀티플레이 게임 서버를 호스팅하려면 보통 공유기 포트 포워딩 설정, 공인/사설 IP 이해, 방화벽 규칙 수정이 필요하다. 일반 사용자에게는 이것 자체가 진입 장벽이다.

이 프로젝트는 사용자 공간에서 동작하는 경량 가상 네트워크를 만들어, **수동 포트 포워딩 없이** 참가자들이 가상 IP 주소만으로 서로의 게임 서버에 접속하게 한다. STUN으로 공인 엔드포인트를 발견하고, UDP 홀펀칭으로 NAT를 통과하며, 게임 트래픽은 피어 간 직접 경로로 전달한다. AWS는 조율과 텔레메트리에만 쓰고 게임 트래픽 경로에는 두지 않는다.

한 문장 정의:

> STUN 기반 NAT 통과와 UDP 홀펀칭으로 수동 포트 포워딩 없이 가상 IP를 통해 멀티플레이 서버에 접속하게 하고, AWS는 조율과 텔레메트리에만 사용하는 Windows용 direct-first P2P 가상 네트워킹 시스템.

## 범위

### 포함

- **C++20 Windows 클라이언트**: Winsock2 기반 UDP 소켓, 엔드포인트 표현, 로깅
- **자체 STUN 클라이언트**: Binding Request 생성, 트랜잭션 ID, 응답 파싱, `XOR-MAPPED-ADDRESS` 디코드, 타임아웃 처리
- **Python 제어 평면 (AWS EC2)**: 방 생성/참가, 피어 등록, 가상 IP 할당, 후보 엔드포인트 교환
- **Python 텔레메트리 서비스 (AWS EC2)**: 연결 결과와 성능 지표 수신과 저장. **제어 평면과 분리된 별개 서비스다.** 경계 계약은 [`architecture.md`](architecture.md) 3.4가 갖는다
- **UDP 홀펀칭**: 양방향 동시 송신, 재시도, keepalive, 실패 사유 분류
- **자체 터널 프로토콜**: 20바이트 와이어 헤더, `HELLO`/`HELLO_ACK`/`KEEPALIVE`/`DATA`/`PING`/`PONG`/`CLOSE`, 직렬화 및 손상 패킷 검증
- **Windows 가상 네트워크 어댑터 연동**: Wintun을 통한 어댑터 생성과 패킷 read/inject, Windows IP Helper API를 통한 가상 IP 주소 및 라우트 설정
- **가상 IP 라우팅**: 목적지 가상 IP에서 피어 세션 결정, 캡슐화 및 역캡슐화
- **텔레메트리와 진단**: 연결 성공률, 수립 시간, RTT, 패킷 손실, 지터, 세션 지속 시간, 단계별 실패 코드
- **실험 및 분석**: 복수 네트워크 환경에서의 반복 측정, 성공/실패 NAT 사례 비교, 결과 시각화
- **Minecraft Java Edition 검증**: 가상 IP를 통한 실제 멀티플레이 세션

### 제외

- 상용 VPN 제품의 완전한 대체
- 대규모 공개 배포
- 자체 암호 알고리즘 개발
- 모바일 지원
- macOS 지원
- 고급 GUI
- 완전한 ICE 구현
- 모든 NAT 구성에서의 연결 보장
- 자체 STUN **서버** 구현 (클라이언트만 구현하고 공개 서버를 이용)

### 스트레치 목표

직접 연결 작업이 조기에 끝날 경우에만 착수한다. 핵심 P2P 목표를 희생하면서 진행하지 않는다.

- 직접 연결 실패 피어를 위한 릴레이 폴백
- 암호화 및 인증된 피어 세션
- Windows 설치 프로그램
- 간단한 GUI
- 자동 재연결
- 한 가상 네트워크에 3자 이상
- UDP 기반 게임 검증
- Linux 상호 운용성

## 요구사항

### 기능 요구사항

| ID | 요구사항 |
|----|----------|
| FR-1 | 클라이언트는 Winsock2로 UDP 소켓을 열고 지정된 원격 엔드포인트와 양방향 송수신할 수 있다. |
| FR-2 | 클라이언트는 자체 구현한 STUN 클라이언트로 공개 STUN 서버에 Binding Request를 보내고 `XOR-MAPPED-ADDRESS`를 디코드해 자신의 공인 IP와 UDP 포트를 알아낸다. |
| FR-3 | STUN 응답이 없거나 형식이 잘못된 경우, 클라이언트는 무한 대기하지 않고 타임아웃 후 `STUN_DISCOVERY_FAILED`로 기록한다. |
| FR-4 | 제어 평면은 방 생성과 참가를 지원하고, 참가 피어에게 `10.100.0.0/24` 대역의 고유한 가상 IP를 할당한다. |
| FR-5 | 제어 평면은 각 피어의 후보 엔드포인트(로컬, 공인)를 등록받아 같은 방의 다른 피어에게 전달한다. 로컬 후보는 두 피어가 같은 LAN에 있을 때 쓰인다. |
| FR-6 | 클라이언트들은 교환받은 엔드포인트로 UDP 홀펀칭을 시도하고, 수동 포트 포워딩 없이 직접 UDP 경로를 수립한다. 연결 수립은 **양방향 증거**로 확인한다. 자신이 보낸 nonce를 echo한 `HELLO_ACK`을 받았고(자신 -> 상대 경로), 상대의 유효한 `HELLO`에 `HELLO_ACK`을 보냈을 때(상대 -> 자신 경로) 둘 다 성립해야 한다. 한쪽 증거만으로도, 자신의 송신 성공만으로도 판정하지 않는다. 판정식은 [`protocol.md`](protocol.md) 9.2가 정한다. |
| FR-7 | 수립된 세션은 keepalive로 NAT 매핑을 유지하고, `PING`/`PONG`으로 RTT를 측정한다. 단절은 송신 실패가 아니라 유휴 타임아웃(상대 패킷 무수신)으로 판정한다. |
| FR-8 | 터널 프로토콜은 [`protocol.md`](protocol.md)가 확정한 20바이트 와이어 헤더(magic, version, type, payload_length, peer_id, session_epoch, sequence)를 사용하며, 필드 단위로 직렬화하고 수신 검증 파이프라인을 통과하지 못한 패킷을 폐기한다. |
| FR-9 | 클라이언트는 Wintun으로 가상 어댑터를 생성하고, Windows IP Helper API로 할당받은 가상 IP와 `10.100.0.0/24` 경로를 설정한다. |
| FR-10 | 클라이언트는 가상 어댑터에서 읽은 IP 패킷을 목적지 가상 IP 기준으로 라우팅해 `DATA` 패킷으로 캡슐화하고 직접 UDP 경로로 전송한다. |
| FR-11 | 수신 측은 `DATA` 패킷을 역캡슐화해 원본 IP 패킷을 가상 어댑터에 주입한다. 주입 전에 내부 IPv4 유효성, 내부 출발지 IP가 송신 피어의 가상 IP와 일치하는지, 내부 목적지 IP가 자신의 가상 IP인지를 검증한다. |
| FR-12 | 플레이어가 Minecraft 서버 주소란에 `10.100.0.1:25565`를 입력하면 원격 호스트의 서버에 접속된다. |
| FR-13 | 모든 연결 시도는 성공/실패와, 실패 시 단계별 코드(`STUN_DISCOVERY_FAILED`, `CONTROL_PLANE_EXCHANGE_FAILED`, `HOLE_PUNCH_TIMEOUT`, `PEER_HANDSHAKE_FAILED`, `TUNNEL_DROPPED`)를 기록한다. |
| FR-14 | 클라이언트는 연결 수립 시간, RTT, 패킷 손실, 지터, 전송량, 세션 지속 시간을 수집해 **텔레메트리 서비스**에 보고한다. 제어 평면에 보고하지 않는다. |

### 비기능 요구사항

| ID | 요구사항 |
|----|----------|
| NFR-1 | 게임 트래픽은 정상 경로에서 AWS를 경유하지 않는다. AWS는 조율과 텔레메트리 전용이다. |
| NFR-2 | 터널 계층에 Minecraft 전용 로직이 없다. Minecraft를 다른 IP 기반 애플리케이션으로 바꿔도 터널 코드는 변경되지 않는다. |
| NFR-3 | 제어 평면 장애가 이미 수립된 P2P 터널을 끊지 않는다. 텔레메트리 전송 실패는 무시한다. **실패한 레코드를 다시 보내지 않는다.** 다음 주기에는 그 주기의 새 지표를 보낸다. 판정 근거는 업로드가 아니라 로컬 기록 파일이다([`architecture.md`](architecture.md) 9장). |
| NFR-4 | STUN, NAT 통과, 홀펀칭, 터널 프로토콜, 라우팅, 세션 관리는 직접 구현한다. Wintun은 가상 인터페이스 접근만 제공한다. |
| NFR-5 | 비기본 서드파티 의존성은 통합 **전에** 교수 승인을 받고, 각 라이브러리가 제공하는 범위를 문서화한다. Wintun과 `boto3`는 승인됨. |
| NFR-6 | 터널 헤더 오버헤드를 고려해 가상 어댑터 MTU를 설정하고, 일반 게임 트래픽에서 IP 조각화가 발생하지 않는다. |
| NFR-7 | 실패를 숨기지 않는다. 통과하지 못한 NAT 환경은 지원 범위 밖으로 명시하고 기록한다. |
| NFR-8 | 소스 관리와 주간 개발 기록을 유지한다. AI 도구가 코드나 문서에 기여한 경우 검증하고 과목 정책에 따라 출처를 밝힌다. |
| NFR-9 | STUN, 홀펀칭, 터널 트래픽은 모두 동일한 로컬 UDP 소켓을 사용한다. 소켓이 다르면 NAT 매핑도 달라져 발견한 엔드포인트가 무효가 된다. |
| NFR-10 | 텔레메트리 서비스는 제어 평면과 배포 단위가 다르고, 두 서비스 사이에 **호출 의존이 없다.** 텔레메트리 서비스 프로세스가 멈춰도 제어 평면의 연산과 데이터 평면은 그 때문에 막히지 않는다. **자원 격리는 이 요구에 포함되지 않는다.** 두 서비스가 한 인스턴스에 있는 동안 공유 자원 고갈은 위험으로 남고, 격리 수단을 정하기 전까지 그렇다. 경계 계약은 [`architecture.md`](architecture.md) 3.4가 갖는다. |

### 제약

| ID | 제약 |
|----|------|
| C-1 | 클라이언트 대상은 Windows 10 / 11 x64. 개발과 시연 모두 Windows 환경에서 수행한다. |
| C-2 | 클라이언트 언어는 C++20, 빌드는 CMake. 고수준 네트워킹 프레임워크 대신 네이티브 Windows API를 쓴다. |
| C-3 | 제어 서버와 텔레메트리 서비스의 언어는 Python. 배포 대상은 **AWS EC2 단일 인스턴스 위의 프로세스 둘**(포트 분리)과 **Amazon DynamoDB**. 표준 라이브러리 외에 AWS SDK(`boto3`)를 쓴다. `boto3` 는 NFR-5에 따라 승인받았다. |
| C-4 | 한 학기 안에 완료 가능해야 한다. **Phase 를 특정 주차에 못박지 않는다.** 진행 속도가 정하므로 주차 배분을 문서에 고정하면 곧 사실과 어긋난다. |
| C-5 | 범위 초과 시 하위 우선순위부터 제거한다. P0: UDP + STUN + 엔드포인트 교환 + 홀펀칭 + 터널 헤더 + `DATA` 최소 왕복 + 로컬 기록 (Phase 1-4) / P1: 프로토콜 견고성. 손실·재정렬 집계, 퍼즈 방어, 장시간 안정성 (Phase 5) / P2: Wintun + 가상 IP + Minecraft (Phase 6-8) / P3: 텔레메트리 + 진단 + 분석 (Phase 9) / P4: 암호화 + 릴레이 + GUI + 추가 플랫폼 (스트레치). [`roadmap.md`](roadmap.md)의 우선순위 블록과 **등급 내용이 같아야 한다.** 글자 그대로 같을 필요는 없다. 한쪽은 문장이고 한쪽은 코드 블록이다. **무엇을 버릴 수 있고 버리면 무엇이 사라지는지는 아래 "우선순위 제거의 대가"에 적는다** |

#### 우선순위 제거의 대가

C-5의 등급을 버릴 때 **어떤 성공 기준이 함께 사라지는지** 적는다. 이것을 적지 않으면
"하위부터 제거"가 최소 산출물을 깨는 지시가 된다.

| 버리는 등급 | 사라지는 것 | 버릴 수 있는가 |
|-------------|-------------|----------------|
| P4 (스트레치) | 없다. 애초에 계산 밖이다 | 예 |
| P3 (Phase 9) | A-1 ~ A-4, T-6, FR-14, NFR-7 의 검증(환경별 실패 기록과 집계), NFR-10 의 검증 | 예. 단 **과목이 요구하는 분석 성공이 사라진다.** 최소 성공은 남는다 |
| P2 (Phase 6-8) | T-1 ~ T-5, FR-9 ~ FR-12, NFR-2 의 검증(Phase 7 파일 전송 시험), NFR-5 의 Wintun 범위 문서화, NFR-6(MTU 확정) | 예. 최소 성공은 남는다 |
| P1 (Phase 5) | FR-8 의 손실·재정렬 집계, FR-13 실패 코드 집합의 완성(`TUNNEL_DROPPED`), NFR-3 의 검증. **M/T/A 성공 기준은 사라지지 않는다** | 예. 요구사항 검증이 줄어든다는 것을 알고 버린다 |
| P0 (Phase 1-4) | M-1 ~ M-6 전부 | **아니다.** 최소 성공이 사라진다 |

**최소 성공 M-1 ~ M-6은 P0만으로 성립한다.** 그것이 P0의 정의다. `DATA` 최소 왕복(M-5)과
로컬 기록(M-6)을 P0에 둔 이유가 그것이다.

## 성공 기준

#### 지원 네트워크 조건 (사전 정의)

M-4의 "지원 NAT 환경"은 사후에 정하지 않는다. 아래를 성공 판정 **전에** 고정한다.

| 항목 | 정의 |
|------|------|
| 지원 조건 | 각 피어가 서로 다른 두 STUN 서버에 질의했을 때 자신의 공인 IP:Port가 동일하게 관측되는 경우. 즉 목적지에 따라 매핑이 바뀌지 않는 경우 (엔드포인트 독립 매핑) |
| 필수 시험 토폴로지 | (1) 동일 LAN, (2) 서로 다른 가정망 2곳. 이 두 가지에서 M-4가 성립해야 최소 성공으로 인정한다 |
| Best-effort 토폴로지 | 모바일 핫스팟, 캠퍼스망. 실패해도 최소 성공 판정에 영향을 주지 않으나 실패 기록은 남긴다 |
| 미지원 조건 | 목적지마다 공인 포트가 바뀌는 매핑(대칭형 거동). 분류 기준은 통신사 구성이 아니라 관측된 거동이다. CGNAT는 정의상 미지원이 아니라 어려울 수 있는 토폴로지로 분류한다. 일부 CGNAT는 엔드포인트 독립 매핑을 써서 홀펀칭이 된다. 직접 연결 실패는 정상 동작으로 간주하고 기록만 한다 |

### 최소 성공 (Minimum)

전부 충족해야 한다.

| # | 기준 | 검증 방법 |
|---|------|-----------|
| M-1 | 서로 다른 네트워크의 Windows 머신 2대에서 클라이언트가 동작한다. | 판정은 둘이다. **정상 기동**은 각 머신의 로그에 **bind 한 실제 로컬 엔드포인트**가 나오고 그 뒤 프로세스가 종료하지 않는 것으로 한다. 그 값은 [`protocol.md`](protocol.md) 6장의 계약이다(`INADDR_ANY` 와 포트 0 으로 bind 하고 `getsockname` 으로 실제 포트를 읽는다). **서로 다른 네트워크**는 M-2 의 로그에 나온 공인 IP 가 두 머신에서 서로 다른 것으로 한다. 같은 공인 IP 면 이 기준에서는 서로 다른 네트워크로 인정하지 않는다. 공유 CGNAT 뒤의 서로 다른 망이 같은 공인 IP 로 보일 수 있으므로 "같은 NAT 뒤"라고 단정하지는 않는다. 기동 판정에 STUN 결과를 쓰지 않는 이유는 M-1 이 M-2 의 부분집합이 되기 때문이다. 그러면 "떴지만 STUN 이 안 된다" 가 어느 기준에서도 보이지 않는다 |
| M-2 | 두 머신 모두 자체 STUN 클라이언트로 사용 가능한 공인 엔드포인트를 발견한다. | 각 머신 로그에 로컬 엔드포인트와 공인 엔드포인트가 출력된다. 공인 엔드포인트 확인은 **같은 UDP 소켓으로 서로 다른 두 STUN 서버에 질의해** 같은 IP:Port가 관측되는 것으로 한다(위 지원 조건과 같은 판정이다). HTTPS 기반 IP 확인 서비스는 TCP 경로라 UDP 송신 경로와 다를 수 있어 **참고로만 기록한다.** 발견한 IP:Port가 실제로 수신 가능함은 M-4/M-5에서 확인된다 |
| M-3 | 두 피어가 AWS 제어 평면을 통해 연결 정보를 교환한다. | 두 머신 모두 `get_peers` 준비 완료 응답에서 상대의 가상 IP 와 **상대 머신의 M-2 로그에 찍힌 공인 엔드포인트**를 받는다. 응답 형식은 [`control_plane.md`](control_plane.md) 4.5 가 정하고, 클라이언트 로그의 `control.peers` 이벤트([`architecture.md`](architecture.md) 9장)의 `virtual_ip` 와 `candidates` 에서 읽는다. `candidates` 에 상대의 `stun.result` `mapped` 값이 들어 있어야 한다. **판정은 두 머신의 로그에서 각각 한다.** 한쪽만 받은 것은 교환이 아니다 |
| M-4 | 지원 NAT 환경에서 수동 포트 포워딩 없이 직접 UDP 연결을 수립한다. | 공유기 포트 포워딩 규칙이 없는 상태에서 세션이 `CONNECTED`에 도달. 패킷 캡처로 AWS 경유가 아님을 확인 |
| M-5 | 직접 터널로 내부 IP 패킷을 전송한다. | `DATA` 왕복이 양방향으로 성공하고 수신 바이트가 송신 바이트와 일치. 페이로드는 [`protocol.md`](protocol.md) 5.4가 정의한 **완전한 내부 IPv4 패킷**이다. Phase 4에서는 Wintun 없이 합성한 패킷으로 판정하고, 실제 애플리케이션 트래픽 운반은 T-3에서 확인한다 |
| M-6 | 연결 상태와 기본 성능 데이터가 기록된다. | 클라이언트가 연결 결과(성공 또는 FR-13의 실패 코드)와 RTT를 **로컬 기록 파일**에 남긴다. 계약은 [`architecture.md`](architecture.md) 9장이 갖는다. 판정에 걸리는 것은 둘이다. **수립에 실패한 시도는 한 줄, `CONNECTED`에 도달한 시도는 수립 줄과 종료 줄 두 줄**이며, **RTT 는 표본이 없으면 빈 값인 것이 정상이다**(`PING`은 `CONNECTED` 뒤에 시작하므로 수립 줄에는 대개 표본이 없다). 빈 RTT 를 실패로 판정하지 않는다. 그 파일의 경로와 줄 형식은 아직 정하지 않았고 **정하기 전에는 이 기준을 판정할 수 없다.** 제어 평면 업로드와 환경별 집계는 FR-14이고 Phase 9다 |

| T-1 | 두 Windows 머신에 가상 어댑터가 올라간다. | `ipconfig`에 가상 어댑터와 할당된 가상 IP가 보임 |

### 분석 성공 (CSP 요구)

| # | 기준 | 검증 방법 |
|---|------|-----------|
| A-1 | 복수의 네트워크 환경에서 반복 실험이 수행된다. | 동일 LAN, 가정망 대 가정망, 가정망 대 모바일 핫스팟, 캠퍼스망 대 가정망 각각의 측정 결과 |
| A-2 | 성공한 NAT 통과와 실패한 NAT 통과 사례가 비교된다. | 실패 건마다 단계별 코드와 NAT 환경 정보가 남고, 관측된 매핑 거동별로 집계됨. NAT 유형은 단정하지 않는다. **통제된 실패 시나리오 두 가지를 모두** 돌린다. 방화벽으로 UDP를 차단하면 `STUN_DISCOVERY_FAILED`가, 응답 없는 엔드포인트를 주입하면 `HOLE_PUNCH_TIMEOUT`이 기록되어야 한다. **그것이 무엇의 증거인지 구분해 적는다.** 통제된 실패는 실패 처리 경로가 동작한다는 증거이고, 실제 환경의 실패율이나 실패 분포에 대한 증거가 아니다. 실패율은 A-1의 반복 측정에서만 나온다. **실제 실패가 0건이면 0건이라고 적는다.** 통제된 실패로 대신하지 않는다 |
| A-3 | 실험 결과가 시각화되고 한계가 문서화된다. | [`experiments.md`](experiments.md)에 그래프와 한계 서술 포함 |
| A-4 | 반복 가능한 실험 절차가 존재한다. | **작성자가 아닌 1인**이 문서만 보고 **1회 재현을 시행해 끝내는 것**이 통과 조건이다. 재현자는 문서 밖의 설명을 묻지 않고 진행하고, 막힌 지점을 기록한다. **시행 없이 "재현 가능" 을 선언하지 않는다.** 작성자는 자기 문서에서 빠진 전제를 읽는 것만으로는 찾기 어렵다 |

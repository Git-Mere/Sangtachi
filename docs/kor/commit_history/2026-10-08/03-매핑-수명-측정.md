# 매핑 수명 측정 도구와 첫 측정 (ADR 0019)

## 왜 했나

`plan.md` 다음에 할 일의 첫째였던 keepalive 매핑 수명 측정 절차의 재설계다. EC2 가 먼저 보내는 probe 는
요청하지 않은 인바운드라 막히므로 처음 계획으로는 수명을 0 으로 오판한다. 저장소 소유자가 선택지 가운데
"별도 도구" 를 고르고 측정까지 하라고 했다.

## 중요한 결정

- **데운다.** Linux conntrack 소스(`nf_conntrack_proto_udp.c`)를 확인했다. 응답을 본 흐름이 2초 넘게
  이어지면 120초, 아니면 30초를 쓴다. 데우지 않으면 살아 있는 터널보다 짧게 잰다
- **지연값마다 소켓 하나, LATE 하나.** 들어온 패킷이 타이머를 갱신하는 NAT(RFC 4787 REQ-6)에서 길게 재지
  않게 한다
- **포트는 47000.** RFC 4787 REQ-5a 가 잘 알려진 포트에 더 짧은 타이머를 허용한다
- **로그와 결과에 공인 IP 를 남기지 않는다.** 결과 JSON 은 ignore 된 `results/` 에만 둔다
- 보안 그룹 규칙은 저장소 소유자가 콘솔에서 측정 기기의 `/32` 로 잠시 열었다. 이 기기에는 AWS CLI 가 없다

## 측정

조건. 이 개발 기기, 집 Wi-Fi(게이트웨이 `10.0.0.1`) 한 곳. 실행한 `python.exe` 에 Windows 방화벽 인바운드
허용 규칙이 있어 호스트 방화벽은 재지 않았다. Tailscale 은 켜져 있었고 EC2 로 가는 경로는 Wi-Fi 였다.
응답기는 us-west-2 의 제어 평면 인스턴스, UDP 47000.

| 회차 | 지연(초) | 도착 | 판정 |
|------|------|------|------|
| r1, r2, r3 | 5, 20, 30, 45, 60, 90, 120, 150, 180, 240, 300 | 5~45 | 세 번 모두 `[45, 60)` |
| fine1, fine2 | 5, 46, 48, 50, 52, 54, 56, 58 | 전부 | 두 번 모두 `58` 이상 |

- 모든 시행에서 데우기 ACK 6/6 과 마지막 ACK 를 받았다. 제외한 시행은 없다
- 응답기 로그의 `late_sent` 는 50 이다(확인 1 + 33 + 16). 오지 않은 LATE 도 응답기는 보냈다. 끊긴 곳은 경로다
- 도착한 LATE 는 클라이언트가 잰 유휴로 요청한 지연의 -0.091초에서 +0.141초 안이었다
- **합친 결과는 `[58, 60)` 초다.** 이 경로에서 늦은 답이 끊기는 시점의 추정이다. 매핑이 끝난 것인지 필터가
  닫힌 것인지는 가르지 않으므로 RFC 4787 REQ-5(매핑 2분 이상)를 지키는지는 정하지 않는다
- EC2 의 호스트 방화벽은 없다(`iptables -S` 가 전부 `ACCEPT`, `nft` 규칙 없음). 응답기 로그의 거절은 0 이다
- 보안 그룹의 아웃바운드 규칙은 기본값 "모든 트래픽 `0.0.0.0/0`" 이다(저장소 소유자가 콘솔에서 확인). 연결 추적이
  끝난 뒤의 LATE 도 나간다. 끊김은 EC2 쪽이 아니다

**규칙.** 저장소 소유자가 `간격 × 3 < 잰 수명의 최솟값` 을 골랐다(`protocol.md` 11장, ADR 0019 결정 7). 15초는
45초라 지킨다. 15초와 50초를 그대로 둔다. 상대 가정의 측정은 `plan.md` 대기다.

**측정은 리뷰 수정 전의 도구로 했다.** 수정 가운데 결과를 바꿀 수 있는 것은 둘이다. 거절을 ACK 로 알리는 것과
시행마다의 창이다. 응답기 로그의 거절이 0 이고, 도착한 LATE 가 모두 창(T + 5초) 안이었으므로 결과는 그대로다.

## 크로스 모델 리뷰

Codex. staged diff 에 렌즈 둘(코드와 보안, 측정 방법과 문서)을 따로 돌렸다.

| 렌즈 | 지적 | 처리 |
|------|------|------|
| 코드 | blocker. 상한으로 거절한 요청도 같은 ACK 를 받아 거절이 NAT 만료로 읽힌다. 루프백 시험이 그것을 정답으로 삼았다 | 반영. ACK 둘째 바이트가 상태(없음, 예약, 거절)다. 거절된 시행은 무효다. 시험은 보내는 쪽이 LATE 를 버리는 것으로 만료를 흉내 내고, 거절은 따로 본다 |
| 코드 | blocker. 짧은 시행의 LATE 가 그 시행의 창 뒤에 와도 센다 | 반영. 시행마다 `T + grace` 창, 밖이면 `late_outside_window` |
| 코드 | warn. 지연 목록이 길면 Windows `select` 한도(512)를 넘고 소켓이 닫히지 않는다 | 반영. 시행 64개 상한, `finally` 에서 닫는다 |
| 코드 | warn. ACK 와 LATE 를 합치면 52바이트로 REQ(32)보다 길다. 위조 출발지 반사를 막지 못한다 | 반영. REQ 를 64바이트로. 위조는 막지 못한다고 README 에 적고 보안 그룹 `/32` 를 전제로 했다 |
| 코드 | warn. ACK 와 로그에 속도 제한이 없다 | 반영. 초당 REQ 상한, 버린 것은 세기만 하고 끝날 때 한 줄 |
| 코드 | warn. 시계를 ACK 송신 전에 읽어 송신이 늦으면 유휴가 짧아진다 | 반영. ACK 뒤에 읽는다. 시험 추가 |
| 코드 | warn. `inf` 와 0.5ms 미만 지연 | 반영. 1ms 이상 유한한 값, 와이어 상한 안 |
| 방법 | blocker. AWS 연결 추적이 끝난 뒤의 LATE 는 아웃바운드 규칙에 달렸다. 끊김이 NAT 의 것이 아닐 수 있다 | 반영. AWS 문서를 확인했다(UDP 30초, 스트림 180초 기본, 스트림 최소 60초). README 에 아웃바운드 규칙과 호스트 방화벽 확인을 넣었다. 이 측정의 아웃바운드 규칙 확인 결과는 아래 |
| 방법 | warn. 필터와 매핑을 가르지 않으면서 RFC 4787 REQ-5 와 비교하고 "매핑이 끝나기 전" 이라고 적었다 | 반영. 끊김 시점의 추정으로 적고 REQ-5 판정은 하지 않는다 |
| 방법 | warn. ±0.1초 주장과 r2 45초 시행의 +0.141초가 어긋난다 | 반영. 실제 범위로 |
| 방법 | warn. ACK 0 이 보안 그룹만 뜻하지 않는다 | 반영. 판정 불가로 두고 원인을 차례로 본다 |

2차 리뷰(수정 확인)에서 blocker 하나가 나왔다. 측정 전체의 끝이 `마지막 요청 + 최대 지연 + grace` 로 고정이라, 마지막 ACK 가
늦게 온 시행은 약속한 창보다 일찍 잘린다. 반영했다. 마지막 ACK 를 받을 때마다 끝을 그 시행의 창 끝까지 늘린다. 경로가 늦은
시행의 시험을 더했다. 첫 측정은 RTT 가 grace 5초보다 훨씬 짧아 영향이 없다.

3차 리뷰(그 수정 확인)는 `LGTM - no blockers` 였다.

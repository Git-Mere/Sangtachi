# Redeploying the call settings and measuring the rollback

## Why

The previous commit (`b20224e`) decided the server's DynamoDB call settings, but what was deployed was
`2cc0eef` before it. Also, the rollback path of the deployment tool was a procedure that had never been run
(`CLAUDE.md` rule 6).

## What was done

| What | Result |
|------|--------|
| Redeploy `b20224e` | `deploy.py` gave `VERDICT: pass`. `server.started` in this run's journal, smoke test `room_not_found` |
| `verify.py` after the redeploy | The five operations passed. Four concurrent joins and imitation of the 8.3 retry five times, all 20 joined (9 retries) |
| Rollback, first try | Failed. Below |
| Rollback, second try | Passed. Exit code 1, "rolled back to the previous state and the server is up", `current` is `b20224e`, no `.new`, `.prev` or temporary folder, smoke test passed |

The rollback was run with a bundle that fails startup on purpose. In the `HEAD` bundle only `__main__.py` was
changed to end with exit code 1, and the remote script was run directly with a fake commit name (40 `f`s).
After it finished, that release folder was deleted.

## First rollback failure and server outage

The remote script rolled back as designed. It put the previous config and the previous release back in
place. But the `systemctl restart` that starts it again was refused with "Start request repeated too
quickly".

- The failed release kept restarting for 30 seconds with `Restart=always` (2-second interval) and hit the
  systemd start rate limit
- In that state, restart is refused too
- As a result, **the production server was down for about 2 minutes.** It was brought back by hand with
  `systemctl reset-failed` and restart

The fix is `systemctl reset-failed` before restart. It was added to both the rollback and the normal
deployment. The second try passed.

**Whether it was right to run this test directly on the production instance is open to question.** There is
no other instance, and the rollback is a path meant for use in production, so this was the only place to run
it. However, the repository owner was not told before the run that the server could go down.

## What was not run

- The path when the first deployment fails. It stops the service and deletes the config, the unit and
  `current`. Running it would require removing the service entirely
- The path where the rollback itself fails, leaves `.prev`, and refuses the next deployment

## Seen on the instance

`/etc/sangtachi/control-plane.env` (owner `ubuntu`, mode 0600, 2026-10-06 18:31) exists. The deployment tool did
not make it and the service does not read it. Its content was not opened.

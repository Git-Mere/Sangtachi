# 0003. `linux_tun` 수명 시험이 열자마자 패킷을 받아 실패했다

- 상태: 해결
- 발견: 2026-10-31
- 관련: `tests/platform/linux_tun_test.cpp`, [0004](0004-같은-이름의-영구-tun-장치에-붙었다.md), [`../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md`](../commit_history/2026-10-31/02-linux-콘솔-클라이언트.md)

## 증상

`sudo` 로 돌리는 `linux_tun` 수명 시험(`[adapter]`)이 6번 중 5번 실패했다. 실패 자리는 하나였다.

```text
linux_tun_test.cpp:102: FAILED:
  CHECK( tun.receive().status == sangtachi::adapter::ReceiveStatus::kEmpty )
with expansion:
  0 == 1
```

장치를 연 직후 `receive()` 가 빈 상태(`kEmpty`)가 아니라 패킷(`kPacket`)을 돌려줬다. 같은 시험은 그 전에 작업자의 실행과 이 세션의
첫 실행에서 통과했다.

## 조사

| 의심한 것 | 본 것 | 판단 |
|-----------|-------|------|
| 바로 전에 넣은 `IFF_TUN_EXCL`([0004](0004-같은-이름의-영구-tun-장치에-붙었다.md)) | 그것을 뺀 빌드로 6번 돌렸다. 6번 모두 같은 자리에서 실패했다 | 아니다 |
| 시험의 단정이 경합에 걸린다 | 장치를 올린 뒤 커널이 내보낸 패킷이 이미 TUN 에 들어와 있으면 "열자마자 빈 상태" 는 성립하지 않는다 | 맞다 |

## 원인

**확인한 것.** 장치를 연 직후 TUN 에 읽을 패킷이 이미 있었다. 시험이 그때 빈 상태를 단정했다.

**추정한 것.** 그 패킷은 장치가 올라갈 때 커널이 내보내는 IPv6 링크 로컬 패킷(라우터 요청 등)이다. 같은 기기의 호스트 로그에
`tx_drop_not_ipv4 value=7` 이 있어 IPv4 가 아닌 패킷이 TUN 에서 나오는 것은 맞다. 이 시험에서 받은 패킷의 내용은 보지 않았다. 전에는
통과하고 이번에는 실패한 이유도 모른다. 타이밍으로 본다.

## 처리

시험이 받은 패킷을 비운 뒤 빈 상태를 보게 고쳤다. 비우는 횟수는 64번까지다. 클라이언트 코드는 바꾸지 않았다. 클라이언트는 IPv4 가
아닌 패킷을 이미 버린다(`tx_drop_not_ipv4`).

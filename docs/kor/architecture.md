# Architecture

**프로젝트:** Direct-First P2P Virtual Network for Multiplayer Games
**대상 플랫폼:** Windows 10 / 11 x64 (클라이언트), Linux/AWS EC2 (제어 서버)

> English version: [`../eng/architecture.md`](../eng/architecture.md)

---

## 1. 설계 원칙

| # | 원칙 | 의미 |
|---|------|------|
| 1 | Direct-First | 게임 트래픽은 가능한 한 피어 간 직접 경로로 흐른다. AWS는 조율 전용이며 데이터 경로가 아니다. |
| 2 | 평면 분리 | 제어 평면(Python/AWS)과 데이터 평면(C++/클라이언트)은 서로 독립적으로 동작하고 테스트된다. |
| 3 | 게임 비종속 | 터널 계층에 Minecraft 전용 로직을 넣지 않는다. Minecraft는 검증 대상일 뿐이다. |
| 4 | 관측 가능 | 모든 연결 시도는 성공/실패와 **실패 단계**를 기록한다. |
| 5 | 의존성 최소화 | Wintun은 가상 인터페이스 접근만 담당한다. STUN, NAT 통과, 터널, 라우팅은 직접 구현한다. |
| 6 | 위험 우선 | 가장 불확실한 것(NAT 통과)을 가장 먼저 검증한다. 가상 어댑터는 그 뒤다. |

## 2. 시스템 구성

```text
             AWS (EC2 1 인스턴스, 프로세스 2개, 포트 분리)
   +---------------------------+     +--------------------------+
   | Python Coordination Server|     | Python Telemetry Service |
   |  rooms / peers            |     |  telemetry ingest        |
   |  candidate exchange       |     |  connection results      |
   +-------------+-------------+     +------------+-------------+
                 |                                |
                 +------- Amazon DynamoDB --------+
                 |                                |
      조율 트래픽 (TCP/JSON)             지표 업로드 (TCP/JSON)
                 |                                |
                 +----------------+---------------+
                                  |
            +---------------------+---------------------+-- ...
    +-------v---------+   +-------v---------+   +-------v---------+
    | Windows Host    |   | Windows Player 1|   | Windows Player 2|
    |  Wintun Adapter |   |  Wintun Adapter |   |  Wintun Adapter |
    |  Router         |   |  Router         |   |  Router         |
    |  Tunnel         |   |  Tunnel         |   |  Tunnel         |
    |  Hole Punch     |   |  Hole Punch     |   |  Hole Punch     |
    |  STUN Client    |   |  STUN Client    |   |  STUN Client    |
    |  Telemetry      |   |  Telemetry      |   |  Telemetry      |
    +-+-+-+-----------+   +--------+--------+   +--------+--------+
      | | |                        |                     |
      | | +==== Direct P2P UDP ====+                     |
      | +================ Direct P2P UDP ================+
      |
    Minecraft Server      Minecraft Client      Minecraft Client
      10.100.0.1:25565      10.100.0.2            10.100.0.3
```

**플레이어는 둘만 그렸다.** 인원 상한과 터널을 맺는 범위는 [`spec.md`](spec.md) FR-4 가 갖는다.

제어 평면이 죽어도 **이미 수립된 P2P 터널은 계속 동작**해야 한다. 제어 평면은 세션
수립에만 필요하다.

**텔레메트리 수집은 제어 평면이 맡지 않는다.** 별개 서비스이고 배포 단위가 다르다. 두
서비스는 같은 EC2 인스턴스에 서로 다른 프로세스로 뜨지만 의존은 한 방향도 없다. 경계
계약은 3.4 텔레메트리 서비스가 갖는다.

## 3. 컴포넌트

### 3.1 클라이언트 (C++20)

| 모듈 | 책임 | 외부 의존 |
|------|------|-----------|
| `network/udp_socket` | Winsock2 초기화/해제, UDP 소켓 생성, 논블로킹 송수신, 이벤트 핸들 노출 ([`concurrency.md`](concurrency.md)) | Winsock2 |
| `network/endpoint` | `IP:Port` 값 타입, 파싱, 비교, 직렬화 | 없음 |
| `peer/peer` | 피어 식별자, 가상 IP, 후보 엔드포인트 목록 | 없음 |
| `peer/hole_punch` | 양방향 동시 송신, 재시도, 성공 판정, 실패 사유 분류 | 없음 |
| `peer/session` | 핸드셰이크, keepalive, 연결 상태 머신, RTT 측정 | 없음 |
| `tunnel/packet` | 터널 헤더 직렬화/역직렬화, 손상 패킷 검증 | 없음 |
| `tunnel/tunnel` | 패킷 타입별 디스패치, 캡슐화/역캡슐화, 시퀀스 관리 | 없음 |
| `tunnel/router` | 가상 IP -> 피어 세션 매핑, 목적지 결정 | 없음 |
| `adapter/wintun_adapter` | 가상 어댑터 생성/개방과 패킷 read/inject (Wintun), 가상 IP 주소 및 라우트 설정 (IP Helper) | **Wintun (승인 완료)**, IP Helper |
| `telemetry/telemetry` | 지표 수집, 로컬 버퍼링, 텔레메트리 서비스 전송 | 없음 |
| `ui/main_window` | 최소 GUI의 창과 위젯. 다섯 동작은 [`spec.md`](spec.md) FR-15 가 갖는다 | Qt |
| `loop` | 이벤트 루프 한 바퀴, 대기 집합, 소스별 비우기 예산, 콘솔 명령 처리. 구조는 `concurrency.md` 2·3장 | 없음 |
| `timer` | 주기 타이머 집합과 다음 대기 타임아웃 계산 (`concurrency.md` 4장) | 없음 |
| `console` | `[console]` 스레드의 줄 큐와 그 수명 (`concurrency.md` 6장 텔레메트리 격리가 그 큐 정책을 함께 갖는다). 콘솔 빌드에만 있다 | 없음 |
| `log` | 9장 로그 출력의 줄 형식과 필드 인코딩 | 없음 |
| `counters` | 9장 `counter` 이벤트의 표. 이름의 출처는 [`protocol.md`](protocol.md)와 `concurrency.md` 다 | 없음 |
| `args` | 기동 인자 파싱 (3.5) | 없음 |
| `hash` | `rx.raw` 가 싣는 SHA-256 | Windows CNG |
| `network/stun` | STUN 메시지 구성과 파싱. `XOR-MAPPED-ADDRESS` 디코드를 포함하고 순수 함수만 둔다. RFC 5389 를 직접 구현한다 ([`protocol.md`](protocol.md) 13장 STUN 사용 범위) | 없음 |
| `network/stun_client` | STUN 재시도와 마감, 서버 선택과 교체. 시계·소켓·난수원·이름 해석을 주입받는다 | 없음 |
| `platform/wait` | 단조 시계, 이벤트 핸들, 여러 핸들 한 번에 기다리기 (`concurrency.md` 2·4장) | Win32 |
| `platform/random` | CSPRNG 바이트. 트랜잭션 ID 와 뒤의 epoch·nonce 가 쓴다 | Win32 |

| `control/control_client` | 제어 평면 HTTP/JSON 호출과 DNS 해석. `[control]` 스레드가 소유한다 (`concurrency.md` 8장 `[control]` 스레드). 연산과 인코딩은 [`control_plane.md`](control_plane.md) | Winsock2 |

클라이언트는 단일 프로세스다. 스레드 구성과 상태 소유는 `concurrency.md` 가 갖는다.

위 표의 이름은 **공개 헤더의 자리**이고 그 이름이 책임을 가리킨다. 그 책임을 어느 OS 의
API 로 채웠는지는 **원본이 있는 디렉터리**가 말하고 둘은 다를 수 있다. `network/udp_socket`
의 헤더는 `network/` 에 있고 그 구현은 `platform/win32/` 에 있다. **OS 헤더를 포함하는 원본은 `client/src/platform/` 아래에만 둔다.** 이식할 때 다시
쓰는 자리가 그 디렉터리이고, 규칙과 그 결정의 근거는
[ADR 0010](decisions/0010-플랫폼-이식-이음새.md)이 갖는다. `tools/platformgate/` 가 그 규칙을
판정하고, **현재 그 자리에 무엇이 있는지는 10장 레포 구조의 트리가 갖는다.**

**`ui/main_window` 가 어느 스레드에서 도는지는 정하지 않았다.** Qt 는 자기 이벤트 루프를
갖고 `concurrency.md` 1장 스레드는 `[loop]` 를 프로세스 주 스레드로 정했다. 둘의 관계는
[ADR 0007](decisions/0007-gui-핵심-범위-qt.md)이 미결로 두었고, 정하는 시점은
[`roadmap.md`](roadmap.md) Phase 8 이 갖는다.

**모든 UDP 송수신은 하나의 로컬 소켓을 공유하고, 그 소켓은 하나의 수신 루프가 배타적으로
소유한다.** 이 제약은 Phase 2 시점부터 지켜야 한다.

> **왜.** 서로 다른 소켓을 쓰면 NAT가 각각 다른 공인 포트를 매핑하므로 STUN으로 발견한
> 엔드포인트가 터널에 적용되지 않는다.

소켓을 공유한다는 것은 STUN 응답과 터널 패킷이 같은 큐로 들어온다는 뜻이다. STUN
클라이언트가 직접 `recvfrom`을 부르면 두 읽기가 서로의 패킷을 훔친다. STUN 클라이언트는
요청만 등록하고 응답은 수신 루프에서 전달받는다. 분류 규칙과 필수 소켓
옵션(`SO_EXCLUSIVEADDRUSE`, `SIO_UDP_CONNRESET` off, `connect()` 미호출)은
[`protocol.md`](protocol.md) 6장 소켓 소유권과 7장 수신 분류에 있다.

### 3.2 동시성 모델

**터널 상태를 건드리는 모든 코드는 한 스레드에서만 돈다.** 스레드는 `[loop]`, `[telemetry]`,
`[console]`, `[control]` 넷이고 `[loop]`가 프로세스 주 스레드다. 나머지 셋은 그 일이 있는
구간에만 있다.

스레드 구성, 대기 집합, 루프 한 바퀴의 순서, 타이머, 상태 소유, 종료 순서, `[control]`
스레드는 [`concurrency.md`](concurrency.md)가 갖는다.

### 3.3 제어 평면 (Python)

**제어 평면의 단일 출처는 [`control_plane.md`](control_plane.md)다.** 연산, 인코딩, 오류,
식별자, 방과 피어의 상태 전이, DynamoDB 테이블 설계, 저장 계약, 서버 모듈 구조, 클라이언트 쪽
호출 계약이 전부 그 문서에 있다. 이 절은 아키텍처 수준의 사실만 적는다.

- Python 표준 라이브러리(`asyncio`, `json`)와 AWS SDK(`boto3`)를 쓴다. 웹 프레임워크는 쓰지
  않는다. **`boto3` 는 표준 라이브러리가 아니다.** [`spec.md`](spec.md) NFR-5 에 따라
  승인받았다
- 상태는 Amazon DynamoDB 에 두고 서버는 방·피어 상태를 메모리에 들지 않는다. 저장 계약 다섯은
  `control_plane.md` 6.1 저장 계약이 갖는다
  - **왜 이렇게 정했고 무엇을 버렸는지는** [ADR 0004](decisions/0004-상태-저장소-dynamodb.md)가
    갖는다
- 그래서 "재시작 복원" 절차가 없다. `spec.md` NFR-3 이 요구하는 재시작 후 방 상태 유지는 복원
  절차가 아니라 저장 계약으로 성립한다
- 게임 트래픽도, 지표도, UDP 도 다루지 않는다. 하지 않는 것의 목록은 `control_plane.md` 1.1
  하는 것과 하지 않는 것

### 3.4 텔레메트리 서비스 (Python)

**제어 평면과 분리된 별개 서비스다.** 제어 평면의 모듈이 아니다.

| 모듈 | 책임 |
|------|------|
| `server.py` | HTTP/JSON 수집 엔드포인트 |
| `ingest.py` | 연결 결과와 성능 지표 수신, 검증, DynamoDB 저장 |

분리의 계약은 넷이다.

| 계약 | 내용 |
|------|------|
| 분리 1 | 제어 평면은 텔레메트리 서비스를 호출하지 않는다 |
| 분리 2 | 텔레메트리 서비스는 제어 평면을 호출하지 않는다. 받은 식별자의 유효성을 제어 평면에 묻지 않는다 |
| 분리 3 | 두 서비스의 접점은 식별자 이름 공간뿐이다. `room_id` 와 `peer_id` 는 제어 평면이 발급하고 텔레메트리는 그것을 불투명한 값으로 기록한다. 대조는 분석 시점에 한다 |
| 분리 4 | 텔레메트리 서비스 프로세스가 멈춰도 제어 평면의 연산은 **호출 경로에서** 막히지 않는다. 계약의 범위는 서비스 간 호출까지다. 같은 인스턴스의 공유 자원 고갈은 이 계약이 덮지 않는다 |

**접점이 식별자뿐이라서 텔레메트리가 받은 값은 신뢰할 수 없다.** 제어 평면이 발급한 적 없는
`room_id` 도 그대로 저장된다. 이것을 수집 시점에 막으려면 텔레메트리가 제어 평면에 물어봐야
하고 그러면 분리 2가 깨진다. 그래서 막지 않는다. 대신 분석 시점에 제어 평면 쪽 기록과 대조해
걸러낸다. 이 한계와 대조 방법은 [`roadmap.md`](roadmap.md) Phase 9 가 갖는다.

**같은 EC2 인스턴스에 두는 것은 배포 편의지 결합이 아니다.** 다만 한 대에 있는 동안은 CPU와
디스크를 공유한다.

**분리 4는 그 위험을 덮지 않는다.** 텔레메트리가 디스크나 CPU를 고갈시키면 제어 평면도 같이
멈추고, 그것은 이 계약을 지켜도 일어난다. 설계상의 의존이 없다는 것과 자원이 격리됐다는 것은
다른 말이다.

**자원 격리는 아직 없다.** 무엇으로 나눌지는 `roadmap.md` Phase 9 의 착수 전 항목이 갖는다.

### 3.5 기동 입력

클라이언트가 기동 시 받는 값과 전달 방식이다. **Phase 1~5 는 CLI 인자만 쓴다.** 설정 파일은 두지 않는다. 값이 적고, 시험마다 바뀌는 값을 파일에 두면 어느 파일로 돌렸는지가 기록에 남지 않는다. 파일이 필요해지는 시점은 [`roadmap.md`](roadmap.md) 가 정한다.

| 입력 | 인자 | 필수 | 값 |
|------|------|:---:|-----|
| 역할 | 첫 위치 인자 `host` 또는 `player` | 아니오. 없으면 로비에서 시작한다 | 기동 직후 로비 명령을 한 번 친 것과 같다. `host` 는 `host`, `player` 는 `join <--room 값>` 이다. Phase 1~2 는 받아서 보관만 한다 |
| 제어 서버 주소 | `--server <이름 또는 IPv4>[:<포트>]` | Phase 3 이후 예. Phase 1~2 는 받아서 보관만 하고 없어도 기동한다 | DNS 이름 또는 IPv4 리터럴. 포트를 생략하면 [`control_plane.md`](control_plane.md) 2.6 상수의 `CONTROL_PORT`. 문서에 실제 주소를 박지 않는다 |
| 방 코드 | `--room <6자>` | `player` 는 항상. Phase 3 이후. **`host` 에 주면 기동 실패다.** 역할 없이 주는 것도 Phase 3 이후 기동 실패다 | `control_plane.md` 2.1 `room_id` 의 형식. 소문자를 쳐도 된다. 서버가 대문자로 정규화한다 |
| 표시 이름 | `--name <이름>` | Phase 4 이후 예. 그 전에는 받아서 보관만 하고 없어도 기동한다 | [`control_plane.md`](control_plane.md) 2.7 `name` 의 형식. 이 프로세스의 모든 방 만들기와 참가가 이 이름을 쓴다. 로비에서 아래 `name` 명령으로 바꾼다 |
| STUN 서버 | `--stun <이름 또는 IPv4>:<포트>` 반복 | 아니오 | 주면 아래 기본 목록을 **통째로 대체**한다. 목록이 한 개일 때의 거동은 표 아래에 있다 |

**`--stun` 목록이 한 개면 기동 시 `WARN` 한 줄을 남긴다.** 그 목록으로는 서로 다른 두 서버의
응답을 얻을 수 없어 아래 "서버 선택" 대로 `STUN_DISCOVERY_FAILED` 로 끝난다.

> **왜.** 경고를 기동 시점에 내는 이유는 5초를 기다린 뒤 실패를 보는 것보다 입력이 틀렸다는
> 것을 먼저 알리는 편이 낫기 때문이다.

**STUN 기본 목록.** 출처는 [`tools/nat-probe/natprobe.py`](../../tools/nat-probe/natprobe.py) 의 `DEFAULT_STUN_SERVERS` 다. 실측 22건이 그 목록으로 돌았다. **그 값을 옮겨 적은 자리가 둘 더 있다.** 이 절의 아래 블록과 클라이언트의 기본 목록 상수다. 한 곳을 바꾸면 셋을 같이 바꾼다.

```text
stun.l.google.com:19302
stun1.l.google.com:19302
stun.cloudflare.com:3478
stun.nextcloud.com:3478
```

**서버 선택.** 목록의 앞 두 서버에 같은 소켓으로 **동시에** 질의한다. 트랜잭션 ID 가 응답을
가른다([`protocol.md`](protocol.md) 13장 STUN 사용 범위). STUN 마감은 서버별이다(`protocol.md`
11장 타이머).

**한 자리가 비면 목록의 다음 서버가 그 자리를 받는다.** 자리가 비는 계기는 셋이다.

| 계기 | 그 서버를 어떻게 보나 |
|------|----------------------|
| 마감에 걸렸다 | 답이 없다 |
| 성공 응답을 받았다 | 관측 하나를 얻었다 |
| 오류 응답(Binding Error Response)을 받았다 | 답을 받았고 그 답이 거절이다. 재시도하지 않는다 |

새로 들어온 서버는 재시도 일정과 마감을 새로 시작한다. 단계 전체의 상한은
[`protocol.md`](protocol.md) 11장 타이머가 계산하고 **그 계산의 "목록 길이" 는 아래 중복
제거를 마친 뒤의 길이다.**

> **왜 응답을 받은 자리도 다시 채우나.** 마감에서만 채우면 앞 서버가 일찍 답한 뒤 남은
> 항목들이 한 자리를 차례로 쓰게 되어 단계가 상한을 넘는다.

**해석 결과가 같은 엔드포인트인 항목은 하나로 친다.** 이름이 다르다고 서버가 다른 것이
아니다. 한 제공자가 여러 이름을 같은 주소로 두는 일이 흔하다. 해석을 마친 뒤 같은 `IP:포트`가
남으면 앞의 것 하나만 목록에 두고 나머지는 빼면서 `WARN` 한 줄을 남긴다. 그 뒤에 아래의
"두 개 미만" 판정을 적용한다.

> **왜.** 두 서버에 묻는 이유는 목적지가 달라져도 매핑이 그대로인지 보는 것이다
> ([`spec.md`](spec.md) 지원 네트워크 조건). 같은 주소에 두 번 물으면 목적지가 하나이므로 그
> 판정이 성립하지 않는데, 목록 항목 수만 보면 두 개로 보인다.

**목록을 다 써도 서로 다른 두 서버의 응답을 얻지 못하면 `STUN_DISCOVERY_FAILED` 다.** 응답이
하나뿐이어도 실패다.

> **왜.** M-2 와 "지원 네트워크 조건" 판정에 둘이 필요하고, 하나로 진행하면 목적지 의존 매핑을
> 구분하지 못한 채 펀치에 들어가 그 실패가 NAT 실패로 기록된다.

**STUN 서버 이름은 기동 시 한 번 해석한다.** 기본 목록이 전부 DNS 이름이므로 해석이 필요하고,
그 호출(`getaddrinfo`)은 동기라 `[loop]` 안에 두지 않는다.

- **`[loop]` 시작 전에 목록 전체를 해석한다.** Phase 1~2 에는 `[control]` 스레드가 없으므로
  ([`concurrency.md`](concurrency.md) 1장 스레드) 그 자리를 빌릴 수도 없다
- 결과가 여럿이면 첫 IPv4 주소 하나를 쓴다. `control_plane.md` 3.2 주소와 같은 규칙이다.
  `AAAA` 는 쓰지 않는다
- **해석에 실패한 항목은 목록에서 빼고 `WARN` 한 줄을 남긴다.** 남은 목록이 두 개 미만이면 위
  규칙대로 `STUN_DISCOVERY_FAILED` 다
- **숫자로만 이루어진 이름은 해석하지 않는다.** 점으로 나눈 라벨이 전부 10진수이거나 `0x`
  16진 표기이면 IPv4 리터럴을 잘못 적은 것으로 보고 값 없음으로 끝낸다. `1.2.3` 처럼 자리가
  모자란 것을 이름으로 물으면 검색 접미사를 붙이는 망에서 엉뚱한 주소가 돌아온다.
  **`1drv.ms` 처럼 숫자로 시작하는 정상 이름은 막지 않는다.** 라벨 하나라도 숫자가 아니면
  이름이다

제어 서버 주소와 달리 여기서는 해석 실패가 기동 실패가 아니다. 목록이 여럿이라 하나가 죽어도
진행할 수 있다.

**`peer_token` 은 프로세스 밖으로 나가지 않는다.** `create_room` 과 `join_room` 응답으로
받아 그 참가 동안 제어 평면 호출에 쓰고 버린다(`control_plane.md` 2.3 `peer_token`). 표준
출력에도 로그에도 싣지 않고 파일에 보관하지 않는다.

> **왜.** 재참가가 없으므로(`control_plane.md` 4.3 `join_room`) 그 값을 사람이 나를 이유가
> 없다. 쓰는 데가 없는 비밀을 화면과 셸 기록에 남기지 않는다.

**방 코드도 표준 출력이다.** 호스트는 `create_room` 응답의 `room_id` 를 함께 할 플레이어들에게
전해야 한다. 표준 오류의 로그(9장)에는 싣지 않는다.

> **왜.** 로그 파일이 곧 방 코드 목록이 되면 로그 열람이 방 탈취다. 표준 출력은 사람이 보는
> 화면이고 리다이렉트하지 않는 것이 기본이다.

**실패도 표준 출력이다.** [`spec.md`](spec.md) FR-13 의 실패 코드와 사람이 읽는 문장을 한
줄에 같이 낸다. 코드는 8장 실패 진단이 소유하고 문장도 그 표에 있다.

```text
ROOM <room_id>
FAIL <실패 코드> <상대> <사람이 읽는 문장>
```

첫 낱말은 고정이다. 시험이 이것으로 줄을 가른다. **`FAIL` 줄의 넷째 필드부터 줄 끝까지가
문장 하나이고 공백을 포함한다.** 로그의 `<이름>=<값>` 형식(9장)과 다른 줄이다.

**`<상대>` 는 실패가 어느 멤버와의 것인지를 사람이 정한 이름으로 담는다.** 칸은 늘 있다.

| 실패 코드 | `<상대>` |
|-----------|----------|
| `HOLE_PUNCH_TIMEOUT`, `PEER_HANDSHAKE_FAILED`, `TUNNEL_DROPPED` | 그 세션 상대의 표시 이름. 제어 평면 응답의 `peers` 원소에서 받은 값이다(`control_plane.md` 4.5) |
| `STUN_DISCOVERY_FAILED`, `CONTROL_PLANE_EXCHANGE_FAILED` | `-` |

뒤의 두 코드는 세션이 생기기 전이거나 방 전체의 실패다. `-` 는 이름의 문자 집합(`control_plane.md`
2.7)에 없으므로 이름과 섞이지 않는다.

> **왜 칸을 늘 두나.** 호스트는 쌍을 여럿 가지므로 상대가 없으면 줄만으로 누구와의 실패인지 알 수
> 없다. 쌍 실패일 때만 칸을 두면 셋째 낱말이 이름인지 문장의 시작인지를 읽는 쪽이 추측해야 한다.
> 근거와 버린 대안은 [ADR 0015](decisions/0015-멤버를-표시-이름으로-가리킨다.md) 다.

**`<상대>` 는 사람이 읽는 값이다.** 시험이 실패한 쌍을 기계로 가를 때는 이름이 아니라 `peer_id`
를 쓴다. 이름은 인증하지 않는다.

**표준 출력이 리다이렉트되면 UTF-8 바이트로 쓴다.** 줄 끝은 LF 하나다. 표준 출력이 콘솔이면 콘솔의
유니코드 쓰기로 낸다. 콘솔 코드 페이지는 바꾸지 않는다.

> **왜.** 문장이 한국어라 바이트 인코딩이 정해지지 않으면 스크립트가 줄을 맞출 수 없다. 코드
> 페이지를 바꾸면 프로세스가 끝난 뒤에도 그 콘솔에 남는다.

> **왜 코드와 문장을 같이 내나.** 코드만 내면 사용자가 다음에 무엇을 할지 모르고, 문장만
> 내면 사용자가 보고한 내용을 8장의 분류와 맞출 수 없다.

**`FAIL` 줄을 낸 뒤 프로세스는 끝나지 않는다.** 그 뒤에 로비로 가는지는 `concurrency.md` 7장
로비가 정한다. 종료 코드는 시도의 결과를 담지 않으므로 스크립트는 `FAIL` 줄로 판정한다.

**로비 명령.** 로비는 프로세스가 방에 속하지 않은 상태다(`concurrency.md` 7장 로비). 로비에서
콘솔 명령으로 방을 만들거나 방에 참가한다. 순서는 `control_plane.md` 8.4
기동부터 펀치까지의 4번부터다.

| 명령 | 하는 일 | 받는 때 |
|------|---------|---------|
| `host` | `create_room` 으로 방을 만든다 | 로비에 있고 미결 제어 요청이 없을 때 |
| `join <방 코드>` | `join_room` 으로 그 방에 참가한다. 방 코드의 형식 검사는 `--room` 과 같다 | 로비에 있고 미결 제어 요청이 없을 때 |
| `leave` | 로비로 간다. 하는 일은 `concurrency.md` 7장 로비가 정한다 | 로비가 아닐 때 |
| `name <이름>` | 다음 `host` 와 `join` 이 쓸 표시 이름을 바꾼다. 요청을 보내지 않는다. 형식 검사는 `--name` 과 같다 | 로비에 있을 때 |

받지 않는 때에 온 명령과 방 코드가 없거나 형식이 틀린 `join`, 이름이 없거나 형식이 틀린 `name` 은
요청을 보내지 않고 `WARN` 한 줄을 남긴다. 틀린 `name` 은 이름을 바꾸지 않는다. 명령 뒤에 낱말이 남는 것도 형식이 틀린 것이다. 명령은 대소문자를 가린다. 프로세스는 그 상태 그대로 남는다. `--room` 의 형식 위반과 달리 기동 실패가 아니다. 미결 요청이 있는 동안
`host` 와 `join` 을 받지 않는 이유는 `concurrency.md` 8장 `[control]` 스레드에 있다.

**CLI 역할은 기동 직후의 로비 명령이다.** 위 표의 역할 행대로 바꿔 한 번 실행한다. 시도가 끝난
뒤 다음 방으로 가는 경로는 역할과 무관하게 로비 명령이다.

> **왜.** CLI 와 콘솔이 다른 경로로 방에 들어가면 같은 실패가 들어온 경로에 따라 다르게
> 끝난다. 규칙을 한 벌로 둔다.

**Phase 1~2 의 시험용 인자 둘.** 위 표는 제품 경로의 입력이다. Phase 1 은 제어 평면도 STUN 도
없이 "알려진 두 엔드포인트" 로 송수신을 확인하므로(`roadmap.md` Phase 1) 상대 주소를 받을
자리가 필요하다.

| 입력 | 인자 | 값 |
|------|------|-----|
| 상대 엔드포인트 | `--peer <IPv4>:<포트>` | Phase 1~2 시험 전용. 없으면 송신하지 않고 수신만 한다. 이 인자로 보내는 것은 터널 헤더가 없는 시험 바이트열이고 Phase 4 이후의 `DATA` 와 다르다 |
| 원시 송신 | 콘솔 명령 `raw <바이트 수>` | `--peer` 로 받은 주소에 그 길이의 데이터그램을 1개 보낸다. 내용은 `0x00` 부터 1씩 증가하는 바이트열이라 수신 측이 계산으로 대조할 수 있다. 길이는 1 이상 `MAX_DATAGRAM`(1472) 이하. 범위 밖이면 보내지 않고 `WARN` |
| 카운터 출력 | 콘솔 명령 `counters` | 카운터 전량을 즉시 낸다. 9장이 정한 세 시점 중 하나다 |
| 종료 | 콘솔 명령 `quit` | 종료 이벤트를 신호한다. `concurrency.md` 3장 루프 한 바퀴가 그 경로를 정한다 |

**수신 측은 `rx.raw` 로그 한 줄을 낸다.** 필드는 `from`(출발지 `IPv4:port`), `len`,
`sha256`(수신 바이트열의 16진 해시 앞 16자)이다. **이 줄은 받은 데이터그램 전부에 나간다.**
[`protocol.md`](protocol.md) 7장 수신 분류가 버리는 것도 포함하고, Phase 2 부터는 STUN 응답도
여기 찍힌다. 버려진 것이 진단에 남아야 하고 로그는 회신이 아니므로 분류보다 앞에 둔다. 바이트열 자체를 로그에 싣지 않는다. **송신
측도 같은 줄을 낸다.** 두 줄의 `len` 과 `sha256` 이 같으면 Phase 1 의 "바이트 단위로 일치" 가
성립한다.

**송신 측의 `from` 은 자신의 로컬 엔드포인트다.** 그 데이터그램의 출발지가 자신이기
때문이다. bind 가 `INADDR_ANY` 이므로 주소 부분은 `0.0.0.0` 이다(`protocol.md` 6장). 판정이
보는 것은 `len` 과 `sha256` 둘이고 `from` 은 어느 쪽 줄인지를 사람이 가르는 데 쓴다.

> **왜.** 눈으로 바이트를 비교하는 절차를 두지 않는 이유는 그것이 사람마다 다른 판정이 되기
> 때문이다.

**둘 다 Phase 6 에서 사라진다.** `[console]` 스레드는 콘솔 빌드에 남는다. 위 로비 명령을 받아야 하기 때문이다(`concurrency.md` 1장 스레드).

**기동 입력이 아닌 것.** 로컬 기록 파일 경로는 9장의 계약이 정해지면 그때 같이 정한다. 텔레메트리 서비스 주소는 Phase 9 다. 둘 다 여기 표에 없다는 것이 현재 상태다.

**인자 오류의 거동.** 알 수 없는 인자, 필수 인자 누락, 형식 위반은 전부 **`ERROR` 한 줄을
남기고 종료 코드 2로 기동 실패**다. 추측해서 고쳐 받지 않는다.

- 같은 인자를 두 번 주면 `--stun` 은 목록에 쌓이고 나머지는 마지막 값이 이긴다
- **준 인자는 그 구간에서 쓰지 않아도 검사한다.** 위 표의 "보관만 한다" 는 값을 쓰지 않는다는
  뜻이지 검사하지 않는다는 뜻이 아니다

> **왜.** 검사를 미루면 Phase 1 에서 통과한 입력이 Phase 3 에서야 거부되고, 그 사이 시험이
> 어느 형식으로 돌았는지 기록에서 읽을 수 없게 된다.

**누락 판정은 위 표의 "필수" 열이 정한다.** 그 열이 요구하는 구간에서 없는 것이 누락이다.
역할은 어느 구간에서나 없어도 기동한다. 다만 값이 `host` 도 `player` 도 아니면 형식 위반이다.

**형식의 출처는 값마다 다르다.** 규칙을 여기에 옮겨 적지 않는다.

| 값 | 출처 |
|----|------|
| `--room` | `control_plane.md` 2.1 `room_id` 의 정규화와 검사 |
| `--name` | `control_plane.md` 2.7 `name` 의 검사 |
| `--server` 의 포트 | 생략하면 `control_plane.md` 2.6 상수의 `CONTROL_PORT` |
| 모든 포트 | 1~65535 |
| `--peer` 의 주소 | IPv4 리터럴만 받는다. 이름을 받지 않는다 |
| `--stun` 의 주소 | 이름 또는 IPv4 리터럴. 포트는 생략할 수 없다 |

**반례 목록은 시험이 갖는다.** IPv4 리터럴, 포트 범위, `--room` 의 케이스 표는
`tests/` 에 있다. 문서에 두면 같은 표를 두 곳에서 맞춰야 하고, 반례는 구현이 자라면서 는다.

## 4. 데이터 평면 경로

게임 패킷이 상대 머신에 도달하기까지의 전체 경로다.

```text
Minecraft (TCP, 10.100.0.2 -> 10.100.0.1:25565)
   |
   v  Windows 라우팅 테이블이 10.100.0.0/24 를 가상 어댑터로 보냄
Wintun Adapter (송신측)
   |
   v  wintun_adapter 가 원본 IP 패킷을 읽음
Router: 목적지 가상 IP -> 피어 세션 결정
   |
   v  tunnel 이 DATA 헤더를 붙임
[TunnelHeader][원본 IP 패킷]
   |
   v  udp_socket 이 직접 P2P 경로로 송신
Internet (UDP, 공인 엔드포인트 -> 공인 엔드포인트)
   |
   v  상대 udp_socket 수신
tunnel: 헤더 검증 및 제거
   |
   v  wintun_adapter 가 원본 IP 패킷을 주입
Wintun Adapter (수신측)
   |
   v
Minecraft Server
```

Minecraft Java Edition은 게임플레이에 TCP를 쓰지만, 터널 자체는 UDP를 쓴다. 원본 TCP 패킷이 페이로드로 실려 가기 때문에 문제되지 않는다. TCP 재전송과 혼잡 제어는 게임의 TCP 스택이 그대로 담당한다.

### MTU 처리

터널 헤더가 붙으므로 페이로드 가용 크기가 줄어든다.

```text
1500 (경로 MTU 가정)
 - 20 (외부 IPv4 헤더)
 -  8 (외부 UDP 헤더)
 - 20 (TunnelHeader)
= 1452 바이트 (내부 IP 패킷 최대치)
```

가상 어댑터 MTU 기본값은 [`protocol.md`](protocol.md) 12장이 소유한다. 위 1452바이트보다 여유를 둔 값이며, 여유폭의 근거와 DF 비트 취급도 그 장에 있다. **여기에 숫자를 복사하지 않는다.** 그 값은 실측으로 확정하는 대상이라(`roadmap.md` Phase 7) 복사해 두면 확정 시점에 이 문서가 낡는다.

다만 위 계산은 **외부 경로 MTU가 1500이라는 가정**에 의존한다. PPPoE 회선이나 다른 터널을 경유하는 경로는 이보다 작고, 그 경우 외부 UDP 패킷이 조각화된다. 가정이 깨지는 경로의 실측과 한계 기록도 같은 장이 정한다.

## 5. 터널 프로토콜

### 5.1 헤더

```text
 오프셋  크기  필드              설명
   0      4   magic             0x53414E47 ("SANG")
   4      1   version           0x01
   5      1   type              PacketType
   6      2   payload_length    헤더 뒤 바이트 수
   8      4   peer_id           송신 피어 식별자
  12      4   session_epoch     송신 피어의 이번 세션 시도 식별자
  16      4   sequence          방향별 단조 증가 카운터
  = 20 바이트, 네트워크 바이트 오더
```

`session_epoch`는 **세션 시도 단위**이고 프로세스 단위가 아니다. 이 필드가 없으면 재시작이나
재시도 후 이전 시도의 지연 패킷이 새 세션에 수용된다.

수신 측은 첫 유효 패킷에서 상대 epoch를 고정하고, 이후 다른 epoch의 `HELLO`는 상대가 새 시도를
시작했다는 뜻이므로 폐기가 아니라 재협상으로 처리하고, 나머지 타입은 폐기한다. 추첨 방법, 폐기
목록, 재협상 절차는 [`protocol.md`](protocol.md) 4.3 `session_epoch` 와 9.3 epoch 규칙, 9.5
재협상이 갖는다.

4바이트 필드가 모두 4의 배수 오프셋에 오도록 배치해 MSVC 기본 정렬에서도 패딩이 생기지 않는다. 그래도 구조체를 그대로 `memcpy` 하지 않는다. 바이트 오더 변환이 필요하고, 정렬이 우연히 맞는 것에 의존하면 조용히 깨진다. **필드 단위로 직렬화**하고 길이는 상수로 고정한다.

> **상세는 `protocol.md` 에 있다.** 상수 값, 페이로드 레이아웃, 수신 검증 파이프라인, 후보
> 지명, 전이표 전체, 확정 타이머 값은 그 문서가 유일한 출처다. 이 절은 요약이며 충돌하면
> `protocol.md`가 우선한다.

### 5.2 패킷 타입

| 타입 | 방향 | 페이로드 | 용도 |
|------|------|----------|------|
| `HELLO` `0x01` | 양방향 | nonce(16) + 가상 IP(4) | 홀펀칭 시도 및 핸드셰이크 개시 |
| `HELLO_ACK` `0x02` | 양방향 | echo nonce(16) + 가상 IP(4) | 상대가 내 패킷을 실제로 받았음을 증명 |
| `KEEPALIVE` `0x03` | 양방향 | 없음 | NAT 매핑 유지 (주기 15초) |
| `DATA` `0x04` | 양방향 | 내부 IPv4 패킷 | 게임 트래픽 전달 |
| `PING` `0x05` | 양방향 | ping_id(8) | RTT 측정. 타임스탬프는 와이어에 싣지 않는다 |
| `PONG` `0x06` | 양방향 | ping_id 에코(8) | RTT 측정 응답 |
| `CLOSE` `0x07` | 양방향 | reason(1) | 정상 종료 통지. 없으면 상대가 50초 유휴 타임아웃까지 죽은 세션을 붙든다 |
| `ROSTER` `0x08` | **호스트 -> 플레이어** | generation(4) + count(1) + 멤버(이름 길이에 따라 11~26 × count) | 방 명부와 멤버의 이름과 연결 상태. GUI 의 멤버 목록이 이것으로 그려진다 ([`spec.md`](spec.md) FR-15) |

### 5.3 세션 상태 머신

```text
IDLE
  | 제어 평면에서 피어 후보 수신
  v
PUNCHING  --- 펀치 마감 --->  FAILED(HOLE_PUNCH_TIMEOUT)
  | got_ack 또는 sent_ack 중 하나가 섬 (어느 쪽인지는 정해져 있지 않다)
  v
HANDSHAKING --- 펀치 마감 --->  FAILED(PEER_HANDSHAKE_FAILED)
  | 남은 하나가 섬
  v
CONNECTED
  | 유휴 타임아웃 (상대 패킷 무수신)
  v
FAILED(TUNNEL_DROPPED)
```

UDP `sendto`의 성공은 전달을 보장하지 않는다. 따라서 두 전이 모두 **수신한 패킷**으로만
판정한다.

- `HANDSHAKING -> CONNECTED`: **두 개의 독립적인 플래그가 모두 서야 한다.** `got_ack`(우리가
  보낸 nonce를 echo한 `HELLO_ACK` 수신, 우리 -> 상대 경로 확인)와 `sent_ack`(상대의 유효한
  `HELLO`에 `HELLO_ACK` 송신, 상대 -> 우리 경로 확인)이다.
  - 어느 쪽이 먼저 서는지는 정해져 있지 않다. 순서를 가정하면 한쪽만 뚫린 경로를 연결로
    오판하거나 정상 순서에서 양쪽이 타임아웃한다
- `CONNECTED -> FAILED`: keepalive 송신 실패가 아니라, 50초 동안 상대로부터 유효 패킷을 하나도
  받지 못한 것으로 판정한다. keepalive는 15초 간격이고 `CONNECTED` 진입 즉시 1회 보내므로 3회
  손실을 견딘다.
- 펀치 마감에 걸린 두 전이는 같은 마감을 쓰고 **그 시점에 선 플래그 개수로만** 코드가 갈린다.
  판정 근거는 8장 실패 진단에 있다.

**그림에 없는 되돌아가는 전이가 하나 있다.** 상대가 새 시도를 시작하면(다른 `session_epoch`의
`HELLO`) 세션은 `CONNECTED`에서도 왕복 증거를 지우고 `CONNECTED` 이전으로 돌아간다. 절차와
그때의 상태 판정은 [`protocol.md`](protocol.md) 9.5 재협상이 갖는다. 이 문서만 읽고 전이가
단방향이라고 구현하면 그 경로가 빠진다.

위 그림은 정상 경로의 뼈대다. **활성 상태 셋**(`PUNCHING`, `HANDSHAKING`, `CONNECTED`)과 모든
수신 패킷의 전이는 `protocol.md` 9.4절 전이표에 있고, `IDLE`과 종료 상태(`FAILED`, `CLOSED`)의
수신 처리는 9.4.1절이 따로 맡는다. 특히 `PUNCHING`에서 `HELLO_ACK`이 먼저 도착하는 것과
`CONNECTED`에서 `HELLO`에 다시 응답하는 것은 정상 동작이며, 이를 빠뜨리면 양쪽이 타임아웃한다.

## 6. 제어 평면 인터페이스

### 6.1 연산

연산은 다섯이다. `create_room`, `join_room`, `register_candidate`, `get_peers`,
`host_report`. 입력, 출력, 오류, 인코딩은 [`control_plane.md`](control_plane.md) 4장 연산이
갖는다. **`host_report` 는 호스트만 부른다.** 방 임대를 갱신하고, 끝난 세션의 자리를
회수하고, 쌍을 준비 완료로 확인하는 셋을 한 요청이 한다.

**`register_peer` 도 `leave_room` 도 없다.** 근거는 `control_plane.md` 4장 머리에 있다.

**`report_connection` 과 `report_telemetry` 는 여기에 없다.** 둘 다 텔레메트리 서비스의
연산이고 6.3 텔레메트리 서비스 인터페이스가 갖는다. 연결 결과는 9장 지표 표의 첫 줄(`연결
성공/실패 + 실패 단계`)이므로 지표와 같은 곳으로 간다.

### 6.2 연결 수립 시퀀스

```text
Host                 AWS (조율 / 텔레메트리)            Player
 |                         |                          |
 |--- create_room -------->|                          |
 |<-- room_id, 10.100.0.1--|                          |
 |                         |<------- join_room -------|
 |                         |-- room_id, 10.100.0.2 -->|
 |                         |                          |
 |-- STUN Binding Req ->(공개 STUN 서버)<- STUN Binding Req --|
 |<- XOR-MAPPED-ADDRESS -                - XOR-MAPPED-ADDRESS ->|
 |                         |                          |
 |-- register_candidate -->|<-- register_candidate ---|
 |                         |                          |
 |--- host_report -------->|<-------- get_peers ------|
 |<-- peers (후보 없음) ----|--- ready: false -------->|
 |                         |                          |
 |--- host_report(confirm)>|                          |
 |<-- 쌍 준비 완료 ---------|                          |
 |                         |<-------- get_peers ------|
 |                         |-- 상대 엔드포인트 ------->|
 |                         |                          |
 |=========== UDP HELLO 동시 송신 (홀펀칭) =============|
 |=========== Direct P2P Tunnel 수립 =================|
 |                         |                          |
 |--- host_report (주기) -->|                          |
 |--- report_connection -->|<--- report_connection ---|
```

**마지막 줄의 `report_connection` 만 목적지가 다르다.** 조율 서버가 아니라 텔레메트리 서비스로 간다. 그림에서 AWS를 한 칸으로 그린 것은 두 서비스가 같은 인스턴스에 있기 때문이고, 같은 서비스라는 뜻이 아니다.

### 6.3 텔레메트리 서비스 인터페이스

| 연산 | 입력 | 출력 |
|------|------|------|
| `report_connection` | room_id, peer_id, 결과, 실패 단계, 수립 시간 | 확인 |
| `report_telemetry` | room_id, peer_id, RTT/손실/지터/전송량 | 확인 |

**두 연산은 실패해도 클라이언트가 재시도하지 않는다.** 다만 둘은 주기가 다르다.

- `report_telemetry` 는 주기 업로드라 실패하면 다음 주기로 넘어간다
- **`report_connection` 은 연결 시도 한 건마다 한 번뿐이라 넘어갈 다음 주기가 없다.** 그 시도의
  업로드는 그것으로 끝이고, 같은 내용이 로컬 기록 파일에 이미 남아 있다(9장)

근거는 [`spec.md`](spec.md) NFR-3과 9장 로컬 기록 계약이다. 판정에 쓰이는 것은 로컬 기록이지 이
업로드가 아니다.

**실패를 삼키지는 않는다.** 업로드가 실패하면 `[telemetry]` 가 카운터 `telemetry_upload_failed`
를 올리고 로그에 한 줄 남긴다. 큐가 가득 차 버리는 것(`telemetry_queue_dropped`,
[`concurrency.md`](concurrency.md) 6장 텔레메트리 격리)과 다른 카운터다.

> **왜.** 앞의 것은 원격이 받지 못한 것이고 뒤의 것은 보내기 전에 버린 것이라, 둘을 한
> 이름으로 세면 텔레메트리 서비스 장애와 클라이언트 과부하를 구분할 수 없다.

**이 실패는 로컬 기록 파일에 쓰지 않는다.** 9장 로컬 기록은 연결 시도 한 건마다 한 줄이라는
계약이고, 업로드 실패는 연결 시도가 아니다.

## 7. 가상 네트워크 설계

- 대역: `10.100.0.0/24`
- `10.100.0.1`: 방 생성자(호스트). 게임 서버가 여기서 돈다.
- `10.100.0.2` 부터 `10.100.0.5` 까지: 참가자 넷. 제어 평면이 순차 할당한다.
- 가상 IP는 방 단위로 유효하다. 방이 사라지면 전부 회수하고, 방이 살아 있는 동안에도 호스트가
  세션이 끝난 피어를 알리면 그 자리를 회수해 다음 참가자가 쓴다. 회수 규칙과 방이 언제
  사라지는지는 [`control_plane.md`](control_plane.md) 2.5 절(가상 IP 풀)과 5.1 절(방)이
  갖는다.
- **떠난 피어의 자리를 그 피어에게 남겨 두지 않는다.** 다시 들어올 때의 주소 배정은 `control_plane.md` 4.3 `join_room` 이 정한다.

플레이어는 Minecraft 서버 주소란에 `10.100.0.1:25565`를 입력한다. 공인 IP나 포트를 알 필요가 없다.

Windows 라우팅은 가상 어댑터에 `10.100.0.0/24` 경로를 붙여 처리한다. 클라이언트가 어댑터 생성 시 Windows IP Helper API로 이 경로를 직접 설정하고, 종료 시 제거한다. Wintun은 주소나 라우트를 설정해 주지 않는다.

**플레이어끼리는 가상 IP 로도 통신하지 않는다** ([`spec.md`](spec.md) FR-4). 위 경로 설정이
`10.100.0.0/24` 전체를 가상 어댑터로 보내므로 플레이어가 다른 플레이어의 주소로 보낸 패킷도
어댑터까지는 들어온다. 그 패킷을 버리는 것은 운영체제가 아니라 클라이언트의 라우팅 표이고,
판정은 [`protocol.md`](protocol.md) 8.5 송신 측 검증이 갖는다.

## 8. 실패 진단

연결 실패는 반드시 단계로 분류해 기록한다. "연결 안 됨"은 기록으로 받아들이지 않는다.

| 코드 | 단계 | 판정 근거 |
|------|------|-----------|
| `STUN_DISCOVERY_FAILED` | 공인 엔드포인트 발견 | STUN 응답 없음 또는 파싱 실패 |
| `CONTROL_PLANE_EXCHANGE_FAILED` | 후보 교환 | `get_peers` 폴링 마감 초과, 제어 평면 오류, `peer_id` 충돌. 조건 목록은 [`protocol.md`](protocol.md) 9.6 실패 전이가 갖는다 |
| `HOLE_PUNCH_TIMEOUT` | 홀펀칭 | 펀치 마감까지 `got_ack`와 `sent_ack`가 **둘 다 미성립** |
| `PEER_HANDSHAKE_FAILED` | 핸드셰이크 | 펀치 마감까지 둘 중 **하나만 성립** |
| `TUNNEL_DROPPED` | 유지 | 수립 후 유휴 타임아웃 동안 상대 패킷 무수신 |

**사람에게 보이는 문장은 이 표가 소유한다.** 코드와 문장을 같이 내는 규칙은 3.5 기동 입력의
표준 출력 절에 있고, GUI 도 같은 문장을 쓴다([`spec.md`](spec.md) FR-15).

| 코드 | 사람이 읽는 문장 |
|------|------------------|
| `STUN_DISCOVERY_FAILED` | 인터넷에서 내 주소를 확인하지 못했습니다. 네트워크 연결을 확인하고 다시 시도하세요. |
| `CONTROL_PLANE_EXCHANGE_FAILED` | 방 정보를 주고받지 못했습니다. 방 코드가 맞는지, 방이 아직 열려 있는지 확인하고 다시 시도하세요. 방에 같은 이름이 있으면 다른 이름을 쓰세요. |
| `HOLE_PUNCH_TIMEOUT` | 상대와 직접 연결을 만들지 못했습니다. 둘 중 한 명이 다른 네트워크에서 다시 시도해 보세요. |
| `PEER_HANDSHAKE_FAILED` | 연결이 한쪽 방향만 열렸습니다. 방화벽 설정을 확인하고 다시 시도하세요. |
| `TUNNEL_DROPPED` | 상대와의 연결이 끊어졌습니다. 상대가 접속을 종료했거나 네트워크가 불안정합니다. |

**문장은 다음에 할 일을 말한다.** 원인을 단정하지 않는다. 위 판정 근거는 우리가 관측한 것이고
그 관측이 곧 원인은 아니기 때문이다.

**로그에는 코드만 남는다.** 9장 로그 계약이 문장을 싣지 않는다. 문장은 사람이 보는 경로에만
나간다.

**뒤의 두 코드는 패킷 종류가 아니라 플래그 성립 개수로 가른다.** 두 플래그의 뜻과 어느 쪽이
먼저 서는지 정해져 있지 않다는 점은 5.3 세션 상태 머신에 있고, 판정 규칙의 출처는
`protocol.md` 9.6 실패 전이다.

> **왜.** "상대 `HELLO`를 받았는가"로 가르면 `HELLO_ACK`이 먼저 도착하는 정상 경로에서
> `got_ack`만 선 채 마감을 맞은 세션이 `HOLE_PUNCH_TIMEOUT`으로 기록된다. 그 세션은 우리 패킷이
> 상대에게 닿았음을 이미 증명했으므로 홀펀칭은 실패하지 않았다. 코드가 틀리면 Phase 9의 실패
> 단계 분포가 그만큼 틀린다.

각 실패에는 확보 가능한 NAT 환경 정보(로컬 대역, 공인 엔드포인트, STUN 서버별 매핑 차이)를 함께 남긴다. `STUN_DISCOVERY_FAILED`는 발견 자체가 실패한 경우라 공인 엔드포인트가 없다. 모든 필드를 요구하지 말고 존재하는 것만 기록한다.

**NAT 유형을 단정하지 않는다.** RFC 5389 Binding 결과와 포트 변화만으로는 NAT 유형이나 필터링
거동을 판별할 수 없다. Phase 9의 분석은 "NAT 유형"이 아니라 **관측된 매핑 거동**(목적지에 따라
공인 포트가 바뀌는가)과 연결 성공 여부로 분류한다. 유형 판별이 필요해지면 RFC 5780 지원
서버나 통제된 다중 목적지 시험이 추가로 필요하며, 이는 초기 범위 밖이다.

## 9. 텔레메트리와 기록

| 지표 | 수집 지점 | 용도 |
|------|-----------|------|
| 연결 성공/실패 + 실패 단계 | 세션 수립 종료 시 | 신뢰성 분석 |
| 연결 수립 시간 | 기점부터 `CONNECTED` 까지. 기점은 아래 로컬 기록 파일의 수립 시간이 정한다 | 사용자 체감 분석 |
| RTT | `PING`/`PONG` 주기 측정 | 지연 분석 |
| 패킷 손실률 | `sequence` 간격 누락 집계 | 품질 분석 |
| 지터 | 연속 RTT 편차 | 품질 분석 |
| keepalive 로컬 송신 오류 | `[loop]` 송신 경로. 카운터는 `tx_err_send` ([`protocol.md`](protocol.md) 6장) | 안정성 분석. 로컬 `sendto` 오류만 세며 전달 실패의 근거가 아니다. 그래서 단절 판정은 유휴 타임아웃으로 한다 |
| 유휴 타임아웃 발생 횟수 | 수신 경로 | 안정성 분석 |
| 직접 연결 유지 시간 | `CONNECTED` 지속 구간 | 안정성 분석 |
| 터널 처리량 | 송수신 바이트 카운터 | 성능 분석 |
| 세션 지속 시간 | 게임 세션 전체 | Minecraft 안정성 |

클라이언트는 로컬 링 버퍼에 먼저 쌓고 전용 스레드가 주기적으로 **텔레메트리 서비스**에 보낸다.
업로드는 데이터 평면과 완전히 분리되어 있어 텔레메트리 서비스 장애가 터널에 영향을 주지
않는다. 격리 구조는 [`concurrency.md`](concurrency.md) 6장 텔레메트리 격리에 있다.

### 로컬 기록 파일

**업로드와 별개로 로컬 기록 파일이 있다.** [`spec.md`](spec.md) M-6 이 요구하는 것은 이것이고, 제어 평면 저장이 아니다. 계약은 넷이다.

| 항목 | 계약 |
|------|------|
| 내용 | 연결 시도 한 건마다 결과(성공, `spec.md` FR-13 의 실패 코드, 또는 중단이나 상대의 실패 통지. 아래 결과 값)와 RTT, 그리고 성공한 수립의 수립 시간. **RTT 는 측정하지 못한 시도에서는 비운다** |
| 시점 | 두 번이다. **수립이 끝나는 시점**에 한 줄(성공, 실패, 중단 모두), 그리고 세션이 끝나는 시점에 한 줄을 더한다 |
| 방식 | 추가 전용(append-only). 이전 줄을 고치지 않는다 |
| 독립성 | 텔레메트리 큐와 업로드 경로에 의존하지 않는다. 제어 평면과 텔레메트리 서비스가 **둘 다** 없어도 기록이 남는다 |

**RTT 가 없는 시도가 있다.** `PING` 송신은 `CONNECTED` 진입에 시작하므로(11장) 그 전에는
보낸 `PING` 이 없고, 따라서 `pending_pings` 에 항목이 없다. 그 구간에 `PONG` 이 도착하면
[`protocol.md`](protocol.md) 5.5 `PING` / `PONG` 에 따라 조회에 실패해 `drop_unmatched_pong`
으로 버려진다.

**즉 `CONNECTED` 이전에는 RTT 표본이 만들어지지 않는다.** `protocol.md` 9.4 전이표가 그
구간에서 `PING` 에 응답하고 `PONG` 을 매칭 절차에 넣는 것과 모순되지 않는다. 그래서 그 전에
끝난 시도(`STUN_DISCOVERY_FAILED`, `CONTROL_PLANE_EXCHANGE_FAILED`, `HOLE_PUNCH_TIMEOUT`,
`PEER_HANDSHAKE_FAILED`)에는 값이 없다.

**없는 것을 0 으로 적지 않는다.** 빈 값으로 적는다. 표기는 아래 줄 형식이 정한다.

> **왜.** 0ms 는 측정된 값처럼 보이고 Phase 9 의 집계를 오염시킨다.

`TUNNEL_DROPPED` 줄에는 단절 직전까지의 마지막 RTT 표본을 적고, **표본이 하나도 없으면 그
줄도 비운다.** `CONNECTED` 직후 첫 `PONG` 전에 끊기면 그런 경우다. 규칙은 하나다. 없으면
비운다. 예외를 두지 않는다.

**줄이 둘인 이유.** `TUNNEL_DROPPED`는 수립이 끝난 **뒤에** 나오는 코드다(8장). 시점을 수립 종료 하나로 두면 그 줄을 쓸 자리가 없고, 이미 쓴 줄을 고쳐 적으면 위의 추가 전용 계약이 깨진다.

**RTT 도 같은 이유로 두 줄이 필요하다.** `PING` 송신은 `CONNECTED` 진입에 시작하므로(11장)
**수립이 끝나는 순간에는 RTT 표본이 아직 없다.** 첫 줄의 RTT 는 그래서 대개 비어 있다. 두
번째 줄이 세션이 끝날 때 쓰이므로 거기에 값이 들어간다.

> **왜.** 수립 줄을 첫 표본까지 미루지 않는 이유는 그 사이에 프로세스가 죽으면 기록이 아예
> 남지 않기 때문이다.

- **수립 줄**: 모든 시도에 쓴다. 결과는 아래 줄 형식의 결과 값이다. RTT 는 그 시점에 표본이
  있으면 적고 없으면 비운다
- **종료 줄**: **`CONNECTED` 에 도달한 시도에만 쓴다.** 종료 코드와 마지막 RTT 표본, 없으면
  빈 값. 종료 코드는 아래 줄 형식의 결과 값 가운데 종료 줄의 것이다
  - `TUNNEL_DROPPED` 가 흔한 경우다. 재협상으로 `CONNECTED` 이전으로 돌아간 뒤 펀치 마감에
    걸리면 `HOLE_PUNCH_TIMEOUT` 이나 `PEER_HANDSHAKE_FAILED` 가 종료 줄에 온다
    (`protocol.md` 9.5 재협상, 9.6 실패 전이). 코드 집합을 둘로 못박으면 그 경우에 쓸 값이
    없다

**수립에 실패하거나 중단된 시도는 한 줄이다.** `STUN_DISCOVERY_FAILED`, `CONTROL_PLANE_EXCHANGE_FAILED`,
`HOLE_PUNCH_TIMEOUT`, `PEER_HANDSHAKE_FAILED`, 그리고 아래 `ABORTED` 와 `PEER_FAILED` 는 `CONNECTED` 에 닿지 못한 것이므로
끝낼 세션이 없다. 수립 줄이 곧 그 시도의 마지막 줄이다. **줄 수로 도달 여부를 읽을 수 있다.** 한 줄이면
수립 전에 끝났고, 두 줄이면 연결됐다가 끝났다.

**한 프로세스가 여러 시도를 기록한다.** 방을 나가면 로비로 돌아가 다시 참가할 수 있으므로
([`concurrency.md`](concurrency.md) 7장 로비) 줄마다 시도 번호가 있다. 한 시도의 두 줄은 그
번호로 묶는다. 파일은 추가 전용이고 시도마다 새로 열지 않는다.

#### 경로

**실행 파일이 있는 폴더 아래 `records\` 다. 프로세스마다 새 파일 하나를 만든다.**

```text
<실행 파일 폴더>\records\<UTC 기동 시각>-<PID>.log
예: C:\Sangtachi\records\20261007T123456Z-4812.log
```

- 실행 파일 폴더는 OS 가 돌려주는 실행 중인 실행 파일의 경로(`GetModuleFileNameW`)에서 마지막 구성
  요소를 뺀 것이다. 링크를 풀거나 경로를 정규화하지 않고 받은 그대로 쓴다. 현재 작업 폴더를 쓰지
  않는다
- 경로는 와이드 문자 API 로 다룬다. 한글이 든 경로도 그대로 쓴다. 경로를 끝까지 얻지 못하면(버퍼가
  모자라 잘린 경우 포함) 아래 열기 실패와 같다
- `records` 폴더가 없으면 만든다
- 기동 시각은 `YYYYMMDDTHHMMSSZ` 꼴의 UTC 다. PID 는 10진수다
- 같은 이름의 파일이 이미 있으면 새로 만들지 않고 기동 실패다. 다른 프로세스의 기록을 덮거나
  잇지 않는다
- 파일을 지우거나 돌려쓰지 않는다. 쌓인 파일은 사람이 지운다
- 경로를 바꾸는 기동 인자는 없다

**기동 시 인자 검사 뒤, `[loop]` 를 시작하기 전에 연다.** 열고 나면 로그에 `record.open` 한 줄을
남긴다(아래 로그 출력의 고정 키 표). 그 줄은 파일 이름만 싣는다. 경로 전체는 공백을 포함할 수
있어 로그 값 규칙에서 깨지기 때문이다. 시험은 실행 파일 폴더와 PID 로 파일을 찾는다.

> **왜 프로세스마다 새 파일인가.** 한 기기에서 여러 프로세스를 띄우는 시험이 있다. 파일 하나를
> 나눠 쓰면 동시 추가가 섞이지 않는다는 보장이 필요한데 그것을 확인하지 않았다.

> **왜 실행 파일 옆인가.** 저장소 소유자가 정했다([ADR 0016](decisions/0016-로컬-기록-파일의-경로와-줄-형식.md)). 사람이 찾기 쉽다. 대가는 실행 파일 폴더에 쓸
> 수 있어야 한다는 것이다. 그 전제는 [`windows-prereq.md`](windows-prereq.md) 4절 배포물
> 패키징이 갖는다.

#### 줄 형식

**한 줄은 `<이름>=<값>` 쌍을 공백 하나로 이은 것이다.** 필드와 순서는 아래 표로 고정하고 두 종류의
줄이 같은 필드를 쓴다. 파일은 UTF-8 이고 실제로는 ASCII 만 나온다. 줄 끝은 LF 하나다.

| 순서 | 필드 | 값 |
|:--:|------|-----|
| 1 | `v` | 형식 버전. 지금은 `1` |
| 2 | `kind` | `establish`(수립 줄) 또는 `end`(종료 줄) |
| 3 | `ts` | 줄을 쓴 시각. UTC 벽시계 밀리초. `2026-10-07T12:34:56.789Z` 꼴 |
| 4 | `attempt` | 시도 번호. 아래 "시도 번호" |
| 5 | `role` | `host` 또는 `player` |
| 6 | `peer` | 상대 `peer_id` 의 10진수. 아래 "상대" |
| 7 | `result` | 아래 "결과 값" |
| 8 | `rtt_us` | 마지막 RTT 표본. 마이크로초 정수 |
| 9 | `setup_ms` | 수립 시간. 밀리초 정수. 아래 "수립 시간" |

**값이 없으면 `-` 다.** 빈 문자열이나 `0` 을 쓰지 않는다. 0 은 측정된 값이다.

```text
v=1 kind=establish ts=2026-10-07T12:34:56.789Z attempt=1 role=player peer=3021551877 result=OK rtt_us=- setup_ms=2410
v=1 kind=end ts=2026-10-07T13:02:10.004Z attempt=1 role=player peer=3021551877 result=CLOSED rtt_us=23410 setup_ms=-
v=1 kind=establish ts=2026-10-07T13:05:01.120Z attempt=2 role=player peer=- result=STUN_DISCOVERY_FAILED rtt_us=- setup_ms=-
```

> **왜 RTT 를 마이크로초로 적나.** 같은 LAN 의 RTT 는 1ms 보다 작다. 밀리초 정수로 내리면 0 이 되어
> 측정한 값과 "없는 값" 을 0 으로 적지 않는 규칙이 섞인다.

> **왜 이름을 적지 않나.** 이 파일은 M-6 판정의 입력이다. 판정은 기계 식별자인 `peer_id` 로 한다.
> 표시 이름은 표시 전용이다([`spec.md`](spec.md) FR-16).

**결과 값.**

| 줄 | `result` |
|----|----------|
| 수립 줄 | `OK`, `spec.md` FR-13 의 실패 코드, `ABORTED`, 또는 `PEER_FAILED` |
| 종료 줄 | `CLOSED`, FR-13 의 실패 코드, 또는 `PEER_FAILED` |

`ABORTED` 와 `PEER_FAILED` 는 FR-13 의 실패 코드가 아니다. 이쪽이 실패를 관측한 것이 아니라 그만두거나
상대에게서 끝났다는 통지를 받은 것이다.

**상대의 `CLOSE` 로 끝난 시도는 그 `reason` 으로 가른다**([`protocol.md`](protocol.md) 5.6 CLOSE).

| `reason` | 수립 줄 (`CONNECTED` 전) | 종료 줄 (`CONNECTED` 뒤) |
|----------|--------------------------|--------------------------|
| `0x00` 정상 종료, `0x01` 사용자 취소 | `ABORTED` | `CLOSED` |
| `0x02` 설정 오류, `0x03` 수립 실패 | `PEER_FAILED` | `PEER_FAILED` |

**이쪽이 그만둔 시도도 같은 두 값을 쓴다.** `leave`, 또는 종료 이벤트(`quit`, 창 닫기, Ctrl+C.
`concurrency.md` 7장 종료)로 끝내면 `CONNECTED` 전은 `ABORTED`, 뒤는 `CLOSED` 다.

`CONNECTED` 에 한 번이라도 닿은 시도는 그 뒤 재협상 중이었더라도 종료 줄로 끝난다.

> **왜 `ABORTED` 를 두나.** 줄을 쓰지 않으면 "모든 시도에 수립 줄" 규칙에 예외가 생긴다. 실패
> 코드로 적으면 사람이 그만둔 것이 NAT 실패로 집계된다.

> **왜 `PEER_FAILED` 를 따로 두나.** `protocol.md` 5.6 은 사람이 끈 것(`0x01`)과 실패(`0x03`)를
> Phase 9 가 따로 세도록 `reason` 을 나눴다. 둘을 `ABORTED` 하나로 적으면 그 구분이 이 파일에서
> 사라진다. 실패의 원인 코드는 상대의 기록 파일에 있다.

**시도 번호.** 수립 줄을 쓸 때 1 부터 하나씩 붙인다. 종료 줄은 그 세션의 수립 줄 번호를 쓴다.
파일이 프로세스마다 따로이므로 파일 안에서 유일하다.

**상대.** 그 시도의 상대 `peer_id` 를 이미 받았으면 그 값이고, 받기 전에 끝났으면 `-` 다.
플레이어는 `get_peers` 의 응답 하나라도 받았으면 호스트의 `peer_id` 를 안다. 그 응답은 준비 전에도
`peer_id` 를 싣는다([`control_plane.md`](control_plane.md) 4.5 get_peers).

**수립 시간.** 수립 줄의 `result` 가 `OK` 일 때만 값이 있다. 기점에서 그 세션이 `CONNECTED` 에
들어간 순간까지를 단조 시계로 잰다. 종료 줄은 늘 `-` 다.

| 쪽 | 기점 |
|----|------|
| 플레이어 | 그 시도의 STUN 단계 시작 (`control_plane.md` 8.4 기동부터 펀치까지의 5번) |
| 호스트 | 그 플레이어가 `host_report` 응답의 `peers` 에 처음 보인 때 |

> **왜 호스트의 기점이 다른가.** 호스트의 STUN 은 방을 만들 때 한 번 돌고, 플레이어는 그 뒤 언제든
> 들어온다. 호스트 쪽을 STUN 에서 재면 사람이 참가를 기다린 시간이 수립 시간에 섞인다. 그래서 두
> 쪽의 값은 서로 비교하지 않는다.

#### 무엇이 시도 하나인가

**시도는 세션 하나, 또는 세션이 생기기 전에 끝난 참가나 방 만들기 하나다.** 줄 수 판정이 이 표를
따른다.

| 경우 | 줄 |
|------|----|
| 플레이어가 연결되고 나중에 끝남 | 수립 `OK`, 종료 줄은 위 결과 값 표의 종료 줄 값 |
| 플레이어의 STUN, 참가, 폴링 실패 (`name_taken`, `room_full` 포함) | 수립 한 줄. 실패 코드 |
| 플레이어의 펀치나 핸드셰이크 실패 | 수립 한 줄. 실패 코드 |
| 호스트가 방을 세우기 전의 실패 (`create_room`, STUN, `register_candidate`) | 수립 한 줄. `peer=-`. 방을 세운 시점은 `register_candidate` 가 성공한 때다(`concurrency.md` 7장 로비) |
| 호스트의 쌍 하나 | 쌍마다 따로 센다. 플레이어 넷이면 시도도 넷이다. 쌍의 시도는 그 쌍이 준비 완료되어 펀치를 시작할 때 생긴다 |
| 호스트가 본 플레이어가 준비 전에 `peers` 에서 사라짐 (회수) | 호스트 쪽 줄 없음. 쌍의 시도가 생기기 전이다. 그 플레이어 쪽 기록에 그 시도가 남는다 |
| 호스트가 방을 만들었고 아무도 오지 않음 | 줄 없음. 연결 시도가 없었다 |
| 서버에서 호스트의 방이 끝났고 세션은 이어짐 | 줄 없음. 세션의 수립도 종료도 아니다. 세션이 나중에 끝날 때 종료 줄을 쓴다 |
| 한 번도 `CONNECTED` 에 닿지 못한 시도를 이쪽이 그만두거나 상대의 `CLOSE` 로 끝남 | 수립 한 줄. 위 결과 값 표대로 `ABORTED` 나 `PEER_FAILED`. 호스트는 그때 수립 중이던 쌍마다 한 줄이고, 방을 세우기 전이면 `peer=-` 로 한 줄이다 |
| `CONNECTED` 에 닿은 뒤 재협상 중에 그만두거나 상대의 `CLOSE` 로 끝남 | 종료 줄. 위 결과 값 표대로 `CLOSED` 나 `PEER_FAILED` |
| 연결 뒤 재협상하다 펀치 마감에 걸림 | 같은 시도다. 종료 줄에 그 실패 코드 |
| 프로세스가 강제로 죽음 | 쓴 줄까지만 남는다 |

#### 쓰기와 실패

- **줄마다 바로 OS 에 쓴다.** 런타임 라이브러리의 버퍼에 쌓아 두지 않는다. 그래야 프로세스가 죽어도
  쓴 줄이 남는다. 디스크 캐시를 비우는 호출은 하지 않는다. 전원이 나가는 경우까지는 막지 않는다
- 쓰는 것은 `[loop]` 다(`concurrency.md` 5장 상태 소유). 시도 하나에 두 줄이라 루프를 막는 시간이
  작다
- **기동 때 폴더나 파일을 만들지 못하면 기동 실패다.** `ERROR` 한 줄을 남기고 0 이 아닌 종료 코드로
  끝난다. 기록 없이 돈 실행은 M-6 으로 판정할 수 없다
- **한 줄은 쓰기 호출 하나다.** 줄 끝 LF 까지 한 번에 넘긴다
- **실행 중 쓰기가 실패하면 터널은 그대로 둔다.** `WARN` 한 줄과 카운터 `record_write_failed` 를
  올린다. 일부만 쓰인 경우도 실패다. **그 뒤로는 그 파일에 아무것도 쓰지 않는다.** 줄이 반만 남은
  자리에 다음 줄을 이으면 두 줄이 한 줄로 붙기 때문이다. 같은 프로세스에서 다시 열지 않는다
- 읽는 쪽은 LF 로 끝나지 않은 마지막 줄을 버린다

**판정할 수 있는 실행은 정해져 있다.** 줄 수로 M-6 을 판정하는 것은 프로세스가 `quit` 이나 창 닫기로
끝까지 종료 절차(`concurrency.md` 7장 종료)를 돌았고 `record_write_failed` 가 0 인 실행뿐이다. 그
밖의 실행은 판정 불가이고 통과도 실패도 아니다. 강제로 죽은 프로세스와 쓰기가 실패한 실행은 쓴
줄이 시도의 전부가 아니다.

### 로그 출력

Phase 2~3의 검증 항목이 "`STUN_DISCOVERY_FAILED` 기록", "로그로 확인"을 판정 수단으로
쓴다([`roadmap.md`](roadmap.md)). 무엇을 어디에 어떤 모양으로 내는지가 없으면 그 검증을
통과했는지 판정할 수 없다. **그 항목들이 말하는 "기록"은 이 로그다.** 로컬 기록 파일은 Phase
4의 산출물이라 Phase 2~3에는 아직 없다. 최소 계약은 넷이다.

| 항목 | 계약 |
|------|------|
| 출력처 | 표준 오류(stderr). 버퍼링에 갇히지 않아 크래시 직전 줄이 남고, 표준 출력과 따로 리다이렉트할 수 있다 |
| 수준 | `INFO`, `WARN`, `ERROR` 셋. 더 나누지 않는다 |
| 단위 | 한 줄에 이벤트 하나. **값에 공백과 제어문자를 싣지 않는다.** 둘 다 밑줄 하나로 바꾼다. 이스케이프 표기도 따옴표도 쓰지 않는다 |
| 실패 표기 | 8장의 실패 코드 문자열을 **그대로** 쓴다. 번역하거나 다른 말로 바꾸지 않는다. 이 규칙은 로그에만 적용한다. 사람에게 보이는 문장은 8장의 문장 표가 갖고 3.5 기동 입력의 `FAIL` 줄이 나른다 |

수준을 셋으로 묶는 이유는 판정에 쓰이는 축이 "정상 진행 / 계속 가능한 이상 / 그 시도의 실패" 셋뿐이기 때문이다. 더 나누면 구현마다 경계가 달라지고, 검증 항목은 여전히 문자열 하나를 찾을 뿐이다.

> **왜 밑줄인가.** 공백으로 바꾸면 `이름=값`의 경계가 사라진다. 사용자가 준 문자열을 그대로
> 싣는 필드가 있어 그 일이 실제로 일어난다. 따옴표로 감싸면 경계는 서지만 따옴표가 든 값을
> 위해 이스케이프가 필요해지고, 그러면 읽는 쪽이 그것을 해석해야 한다.

**치환은 값에만 적용하고 되돌릴 수 없다.** 원문이 필요한 판정을 로그로 하지 않는다. 로그는
사람이 읽는 진단이고, 판정의 입력은 로컬 기록 파일이다.

**판정은 바이트 단위다.** 바꾸는 것은 ASCII 공백(`0x20`)과 제어 바이트(`0x00`~`0x1F`,
`0x7F`) 뿐이다. `0x80` 이상은 그대로 싣는다. 그 바이트는 줄을 끊지 않고 `이름=값` 의 경계도
흐리지 않는다.

> **한계.** 유니코드 수준의 줄 구분자(U+2028 같은 것)는 바뀌지 않는다. 로그를 유니코드
> 줄바꿈으로 나누는 도구를 판정에 쓰지 않는다. 판정은 `0x0A` 로 나눈다.

**검증이 찾는 이벤트에는 고정 키를 준다.** 위 계약만으로는 "로그로 확인"하는 검증 항목이 무엇을 찾아야 하는지 정해지지 않는다. 줄은 `<수준> <이벤트키> <이름>=<값> ...` 모양이고, 검증이 쓰는 이벤트키와 필드는 아래로 고정한다. 값의 형식은 정하지 않는다. 검증은 키와 필드 이름으로 찾는다.

| 이벤트키 | 필수 필드 | 어느 검증이 쓰는가 |
|----------|-----------|--------------------|
| `socket.bind` | `local` (bind 한 실제 엔드포인트), `rcvbuf_requested`, `rcvbuf_applied` | Phase 1 bind 계약, `SO_RCVBUF` 적용값, [`spec.md`](spec.md) M-1 기동 판정 |
| `stun.result` | `server`, `mapped` (관측된 공인 엔드포인트) | Phase 2, M-2 |
| `session.state` | `from`, `to` ([`protocol.md`](protocol.md) 9.1 상태의 이름 문자열 그대로) | Phase 4 전이 확인 |
| `session.failed` | `code` (8장 문자열) | Phase 2~5 실패 코드 확인 |
| `counter` | `name`, `value` | 폐기 카운터를 보는 모든 항목 |
| `socket.error` | `op` (호출 이름), `code` (Winsock 오류 코드) | Phase 1 소켓 오류에도 프로세스가 죽지 않는지 |
| `control.result` | `op`, `ok`, `error` (실패 코드 문자열, 성공이면 `-`) | Phase 3 연산 검증, `CONTROL_PLANE_EXCHANGE_FAILED` 원인 확인. **`room_id` 와 `peer_token` 을 싣지 않는다** (3.5) |
| `control.peers` | `peer_id`, `virtual_ip`, `candidates` (상대 후보 `ip:port` 를 쉼표로 이어 붙인 것) | `spec.md` M-3, Phase 3 `get_peers` 검증 |
| `timer.tick` | `name`, `elapsed_ms` (직전 만료로부터 실제로 흐른 밀리초) | Phase 1 drain 예산, Phase 3 제어 평면 사망 중 `[loop]` 생존 |
| `rx.raw` | `from`, `len`, `sha256` | Phase 1 원시 송수신 대조 (3.5) |
| `record.open` | `file` (로컬 기록 파일의 이름. 폴더를 빼고) | Phase 4 기록 확인, `spec.md` M-6 |

여기 없는 이벤트는 자유롭게 늘려도 된다. **이 열한 개의 키와 필드 이름만 바꾸지 않는다.** 바꾸면 검증 항목이 같이 낡는다.

**`timer.tick` 은 만료하는 모든 타이머가 낸다.** `name` 이 어느 타이머인지를 가른다. Phase 2
부터는 STUN 재시도와 마감이 `[loop]` 의 같은 집합에 들어가므로 제품 빌드에서도 이 줄이 나간다
([`protocol.md`](protocol.md) 11장 타이머). **시험 빌드는 여기에 주기 200ms 짜리 타이머
하나(`name=probe200`)를 더 넣는다.** 그 타이머는 제품 빌드에 없다. **`elapsed_ms` 는 로그 줄에 시각이 없어도 간격을 판정할 수 있게 하려는 것이다.**
검증이 보는 값이 그것 하나이므로 줄 자체의 시각 형식을 정할 필요가 없다. 켜는 방법은 에코
응답기와 같은 CMake 옵션이고(`roadmap.md` Phase 4), 켜진 빌드는 기동 시
`WARN` 한 줄을 남긴다.

**검증이 값을 비교하는 필드는 형식도 고정한다.** 형식을 정하지 않으면 `256KB` 와 `262144` 와 `0x40000` 중 무엇을 비교할지 검증자가 정하게 된다.

| 필드 | 형식 |
|------|------|
| `rcvbuf_requested`, `rcvbuf_applied` | 10진 바이트 수. 단위 접미사를 붙이지 않는다 |
| `local`, `mapped` | `IPv4:port` 10진 표기 |
| `virtual_ip` | 점 십진 IPv4 |
| `candidates` | `IPv4:port` 를 쉼표로 이어 붙인 것. 공백 없음 |
| `code` | 8장의 실패 코드 문자열, 또는 `socket.error` 에서는 10진 오류 코드 |
| `error` (`control.result`) | [`control_plane.md`](control_plane.md) 4.1 공통 봉투의 오류 코드 문자열, 전송 오류면 `transport`, 4.1 표에 없는 코드면 `unknown_code`, 응답의 상대 목록에 자신의 `peer_id` 가 있으면 `self_in_peers`, 성공이면 `-`. 서버가 보낸 코드가 표에 없을 때 그 문자열을 그대로 싣지 않는다 |
| `value` (`counter`) | 10진 정수 |

나머지 필드의 값 형식은 정하지 않는다. 사람이 읽는 진단이다.

**`counter` 이벤트를 언제 내는지도 정한다.** 시점이 없으면 카운터를 보는 검증 항목이 무엇을
기다려야 하는지 알 수 없다. 세 시점이다.

- 세션이 종료 상태(`FAILED`, `CLOSED`)에 도달할 때 그 세션의 카운터 전량
- 프로세스 종료 절차([`concurrency.md`](concurrency.md) 7장 종료)에서 전량
- `[console]` 명령으로 요청받았을 때 즉시 전량

**증가할 때마다 내지 않는다.** 폐기 카운터는 공격 트래픽에서 초당 수천 번 오를 수 있고,
그때마다 로그를 쓰면 로그가 데이터 평면의 부하가 된다. 값이 0인 카운터도 함께 낸다. 없는
것과 0인 것을 구분해야 검증이 "오르지 않았다"를 판정할 수 있다.

**로그는 위의 로컬 기록 파일과 다른 물건이다.** 로그는 사람이 읽는 진단이라 줄이 늘거나
문구가 바뀌어도 되고, 기록 파일은 `spec.md` M-6 판정의 입력이라 위의 계약을 지킨다.

**M-6 판정을 로그에서 읽지 않고, 진단을 기록 파일에 늘리지 않는다.** 둘을 섞으면 진단 문구를
고칠 때마다 M-6 판정이 같이 흔들린다.

**Phase 1~3 검증이 위의 고정 이벤트 키를 읽는 것은 다른 이야기다.** 그 Phase 에는 기록 파일이
아직 없고, 그래서 키와 필드 이름을 고정해 둔 것이다.

## 11. 외부 의존성

| 의존성 | 제공 범위 | 승인 상태 |
|--------|-----------|-----------|
| Wintun | Windows 가상 네트워크 인터페이스 접근만. 어댑터 생성, 패킷 read/inject | **승인됨** |
| Windows IP Helper / NetIO API | 가상 어댑터의 IP 주소와 라우트 설정. **Wintun은 이 기능을 제공하지 않는다** | OS 기본 제공 |
| Winsock2 | Windows 기본 소켓 API | OS 기본 제공 |
| Windows CNG (`BCryptHash`) | 9장 `rx.raw` 가 싣는 SHA-256 | OS 기본 제공 |
| 공개 STUN 서버 | Binding Response 응답. 서버는 구현하지 않고 이용만 한다 | 외부 공개 서비스 |
| Python 표준 라이브러리 | `asyncio`, `json` | 표준 라이브러리 |
| AWS SDK for Python (`boto3`) | 제어 서버와 텔레메트리 서비스의 DynamoDB 접근 | **승인됨** |
| Catch2 v3 | 시험 케이스 등록, 실행, 실패 보고. 시험 실행 파일에만 링크한다 | **승인됨.** 승인 주체는 [`spec.md`](spec.md) NFR-5 |
| pytest | 제어 서버의 시험 실행과 실패 보고. 배포하는 서버 프로세스는 import 하지 않는다 | **승인됨.** 시험 전용 ([ADR 0014](decisions/0014-제어-서버-시험-pytest와-docker.md)) |
| DynamoDB local | 제어 서버 로컬 시험의 저장소. Docker 컨테이너로 띄운다 | **승인됨.** 시험 전용 (ADR 0014) |
| Qt | 최소 GUI의 창, 위젯, 이벤트 루프. 범위는 `spec.md` FR-15 | **승인됨.** 제품 의존성이라 승인 주체는 교수다 |
| Amazon DynamoDB | 방·피어 상태와 지표의 영속 저장 | 외부 관리형 서비스 |

Wintun이 제공하지 **않는** 것을 명확히 한다. 피어 발견, STUN, NAT 통과, 홀펀칭, 터널 프로토콜, 라우팅 결정, 세션 관리, 모니터링, 진단은 모두 이 프로젝트가 직접 구현한다. Wintun은 커널 모드 가상 NIC 드라이버에 대한 접근 수단일 뿐이다.

## 12. 초기 범위 밖

다음은 의도적으로 초기 아키텍처에 넣지 않는다. 필요해지면 [`decisions/`](decisions/)에 결정 기록을 남기고 도입한다.

- **암호화 및 피어 인증**: 터널 페이로드는 평문이다. 스트레치 목표.
- **릴레이 폴백 (TURN 유사)**: 직접 연결 실패 시 대안 경로 없음. 스트레치 목표.
- **완전한 ICE**: 초기에는 최소 연결 수립 절차만. Phase 9에서 ICE 개념과 비교 분석만 수행.
- **6명 이상과 플레이어 간 메시**: 한 방은 최대 5명이고 터널은 호스트와 각 플레이어 사이에만
  맺는다 ([`spec.md`](spec.md) FR-4). 6자 이상은 스트레치 목표다.
- **macOS / 모바일**: 지원하지 않는다. Linux는 시간이 남으면 상호 운용성만 검토.
  범위는 넓히지 않되 **이식할 때 다시 쓰는 자리는 이음새 다섯으로 고정했다**
  ([ADR 0010](decisions/0010-플랫폼-이식-이음새.md)).

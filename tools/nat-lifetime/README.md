# nat-lifetime

NAT 의 UDP 매핑 수명을 재는 도구. 표준 라이브러리만 쓴다. Python 3.8+.

`protocol.md` 11장 타이머의 `KEEPALIVE` 15초와 유휴 타임아웃 50초를 실측으로 조정하기 위한 것이다.
측정 시점은 `docs/kor/roadmap.md` Phase 4 착수 전 항목이 갖는다. 왜 이 방식인지는
[ADR 0019](../../docs/kor/decisions/0019-매핑-수명은-별도-도구로-잰다.md) 가 갖는다.

## 무엇을 재는가

**재는 것은 "그 경로의 필터+매핑 수명" 이다.** 클라이언트가 응답기에 마지막으로 패킷을 보내고 답을 받은
뒤, 아무것도 보내지 않은 채 몇 초가 지나도 **같은 응답기 IP:포트에서 온** 패킷이 들어오는가를 본다.
매핑이 살아 있어도 필터가 닫혔으면 도착하지 않으므로 둘을 가르지 않는다. keepalive 가 지켜야 하는 것도
그 둘을 합친 것이다.

| 재지 않는 것 | 왜 |
|------|-----|
| 요청하지 않은 인바운드 | 응답기는 클라이언트가 보낸 목적지 그 자체에서 답한다. 그 외의 출발지는 실측상 막힌다(`windows-prereq.md` 2절) |
| 호스트 방화벽의 수명 | 실행하는 `python.exe` 에 인바운드 허용 규칙이 있으면 호스트 방화벽은 재지 않는다. 기록에 그 여부를 적는다 |
| 상대 피어 쪽 NAT | 이 도구는 한쪽 NAT 만 잰다. 두 가정이면 양쪽에서 따로 돌린다 |

## 절차

지연값 하나마다 소켓 하나를 열고, 모든 소켓을 같은 시각에 돌린다.

1. **데우기.** 1초 간격으로 요청 6개를 보내고 응답기가 각각 ACK 를 바로 돌려준다
2. **마지막 요청.** 6초에 지연 T 를 담은 요청을 보낸다. 응답기는 ACK 를 바로 보내고, 그 ACK 를 보낸
   시각부터 T 뒤에 LATE 하나를 보낸다
3. **유휴.** 클라이언트는 그 소켓으로 **아무것도 보내지 않는다.** 마지막 ACK 를 받은 시각부터 `T + 5초`
   동안 LATE 를 기다린다
4. 지연값마다 LATE 가 왔는지로 판정한다(아래)

기본 지연값은 `5,20,30,45,60,90,120,150,180,240,300` 초다. 한 번 도는 데 약 311초다.

> **왜 데우나.** 응답을 본 UDP 흐름에 더 긴 타임아웃을 주는 NAT 이 있다. Linux conntrack 은 응답을 본 뒤
> 2초 넘게 이어진 흐름에 `nf_conntrack_udp_timeout_stream`(기본 120초)을, 그 밖에는
> `nf_conntrack_udp_timeout`(기본 30초)을 쓴다. 데우지 않고 재면 살아 있는 터널보다 짧은 수명이 나온다.
>
> **왜 지연값마다 소켓을 따로 쓰나.** 한 소켓에서 LATE 를 여러 번 받으면 들어온 패킷이 타이머를 갱신하는
> NAT(RFC 4787 REQ-6 이 허용한다)에서 수명을 길게 잰다. 소켓마다 LATE 는 하나뿐이다.
>
> **왜 1024 보다 큰 포트인가.** RFC 4787 REQ-5a 는 잘 알려진 포트(0-1023)에 더 짧은 타이머를 허용한다.

## 실행

```
python natlife.py serve --port 47000 [--duration 3600] [--max-delay 600]
python natlife.py run --server IP:47000 [--delays 5,20,...] [--label NAME] [--out DIR]
```

| 옵션 | 기본값 | 뜻 |
|------|--------|-----|
| `serve --duration` | `3600` | 이 초가 지나면 응답기가 스스로 끝난다. 띄워 둔 채 잊지 않게 한다 |
| `serve --max-delay` | `600` | 이보다 긴 지연은 ACK 만 하고 LATE 를 예약하지 않는다 |
| `serve --max-pending-per-ip`, `--max-pending` | `64`, `1024` | 예약해 둔 LATE 의 상한 |
| `serve --max-req-per-s` | `200` | 초당 받는 REQ 의 상한. 넘는 것은 답하지 않고 센다 |
| `run --delays` | 위 목록 | 쉼표로 이은 초. 1ms 이상의 유한한 값, 많아야 64개. 겹치면 거부한다 |
| `run --warmup-count`, `--warmup-interval` | `6`, `1.0` | 데우기 |
| `run --grace` | `5.0` | T 뒤에 더 기다리는 초 |
| `run --out` | `results/` | 결과 JSON. `.gitignore` 가 막는다 |

**EC2 에서 띄우는 순서.** 제어 서버의 기능이 아니다(`control_plane.md` 1.1).

1. 보안 그룹에 인바운드 `UDP 47000` 을 **측정하는 기기의 공인 IP `/32` 로만** 연다. 사람이 콘솔에서 한다
2. `natlife.py` 를 인스턴스에 복사하고 `serve` 를 `--duration` 과 함께 띄운다
3. 짧은 확인: `run --delays 2 --warmup-count 2 --warmup-interval 0.5 --grace 2`. ACK 가 0 이면 판정 불가다.
   보안 그룹, 응답기가 떠 있는지, 주소, 호스트 방화벽, 경로 손실 가운데 무엇인지 차례로 본다
4. 보안 그룹의 **아웃바운드** 규칙이 UDP 를 모든 목적지로 허용하는지 확인하고 기록한다(기본 규칙 "모든
   트래픽 `0.0.0.0/0`"). 인스턴스의 호스트 방화벽(`iptables -S`, `nft list ruleset`)도 기록한다
5. 측정이 끝나면 응답기를 끝내고 인바운드 규칙을 지운다

> **왜 아웃바운드를 보나.** 보안 그룹은 인바운드 규칙이 특정 출처인 흐름을 추적하고, 추적은 유휴 시간이 지나면
> 끝난다. AWS 문서의 기본값은 단방향이거나 요청-응답이 한 번인 UDP 30초, 그보다 많은 UDP 스트림 180초이고
> 스트림은 60초까지 줄일 수 있다. 추적이 끝난 뒤의 LATE 는 새 아웃바운드 흐름이라 아웃바운드 규칙이 막으면
> 나가지 못하고, 그 끊김이 NAT 의 것으로 보인다.

## 와이어 형식

모두 빅엔디언이다.

| 메시지 | 길이 | 구성 |
|------|:---:|-----|
| REQ | 64 | `"NLT1"`, type 1, 0, seq u16, nonce 16B, delay_ms u32, 0 서른여섯 바이트 |
| ACK | 24 | `"NLT1"`, type 2, 상태, seq u16, nonce 16B |
| LATE | 28 | `"NLT1"`, type 3, 0, seq u16, nonce 16B, idle_ms u32 |

ACK 의 상태는 0 이 "지연 없음", 1 이 "LATE 예약함", 2 가 "거절(상한)" 이다. 길이, magic, type, 상태, 예약
바이트가 정확히 맞지 않으면 버린다. 클라이언트는 응답기 주소와 그 소켓의 nonce 가 맞는 것만 센다. LATE 는
그 시행의 창(마지막 ACK 를 받은 시각부터 `T + grace`) 안에 와야 센다. 창 밖에 온 것은
`late_outside_window` 로 적고 도착으로 치지 않는다.

**응답기의 반사와 증폭을 줄인다.**

- 응답은 받은 데이터그램의 출발지로만 간다. 목적지를 지정하는 필드가 없다
- REQ 하나가 낳는 응답 전체(ACK 하나와 LATE 많아야 하나, 합쳐 52바이트)가 REQ(64바이트)보다 짧다
- LATE 예약은 지연과 개수에, REQ 는 초당 개수에 상한이 있다
- 버린 데이터그램은 한 건씩 로그에 남기지 않고 세어 끝날 때 한 줄로 낸다. 로그에 클라이언트 주소를 남기지
  않는다
- **출발지 위조는 막지 못한다.** 위조된 출발지로도 답이 간다. 그래서 보안 그룹이 측정 기기의 `/32` 만
  받게 하는 것이 이 도구의 전제다. 그러면 위조로 겨눌 수 있는 곳이 그 기기 하나다

## 판정

가장 짧은 지연의 시행이 **대조군**이다. 시행은 마지막 ACK 를 받았고, 그 ACK 가 "LATE 예약함" 이고, 데우기
ACK 를 하나 이상 받았을 때만 **유효**하다. 응답기가 거절한 시행은 NAT 과 무관하므로 무효다.

| 조건 (위에서부터 처음 맞는 것) | 판정 |
|------|------|
| 시행이 없다 | 판정 불가 `no_trials` |
| 대조군이 유효하지 않다 | 판정 불가 `control_invalid`. 경로가 열리지 않았거나 응답기 문제다 |
| 대조군의 LATE 가 오지 않았다 | 판정 불가 `control_missing` |
| 유효한 시행 가운데, 오지 않은 지연의 최솟값이 온 지연의 최댓값 이하다 | 판정 불가 `non_monotonic`. 손실이나 NAT 의 비결정성이다 |
| 유효한 시행이 모두 왔다 | `at_least`. 수명은 온 최댓값 이상이다 |
| 그 밖 | `bounded`. 수명은 `[온 최댓값, 오지 않은 최솟값)` 이다 |

유효하지 않은 시행은 빼고 보며 `excluded` 에 적는다. 이 표를 행으로 펼친 것이
[`test_natlife.py`](test_natlife.py) 의 `JUDGE_CASES` 다.

**한 번의 결과로 판정하지 않는다.** 같은 망에서 여러 번 돌려 구간이 겹치는지 본다.

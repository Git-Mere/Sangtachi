# Phase 9 전체 상한까지의 부하 확인

## 왜 했나

`roadmap.md` Phase 9 검증의 "두 서비스를 함께 띄운 인스턴스에 부하를 걸어 제어 평면 연산이 정상 응답하고 텔레메트리 서비스가 systemd 제한 안에 머묾" 이다. 방법은 앞 커밋에서 정한 루프백 출발지다. 소유자가 실행을 승인했다.

## 무엇을 했나

같은 5분 동안 셋을 함께 돌렸다.

| 무엇 | 어디서 | 명령 |
|------|--------|------|
| 텔레메트리 부하 | 인스턴스 안. `verify.py` 와 `deploy.py` 를 임시 폴더에 올려 시스템 `python3`(3.14) 로 | `verify.py --target tm --host 127.0.0.1 --tm-load 300 --tm-rate 5 --tm-sources 12` |
| 제어 평면 부하 | 이 PC | `verify.py --host <Elastic IP> --soak 300` |
| 감시 | 인스턴스 안 | 10초마다 두 서비스의 `MemoryCurrent`, `CPUUsageNSec`, `NRestarts`, load average, 가용 메모리 |

끝난 뒤 임시 폴더를 지웠다. 부하 레코드 1499건(`build_kind` 가 `test`)은 텔레메트리 테이블에 남는다.

## 결과

| 무엇 | 결과 |
|------|------|
| 텔레메트리 부하 | 300초에 1499건, 모두 `ok`. `rate_limited` 와 `unavailable` 없음. 전체 상한(초당 5)에서 거절 없이 받았다 |
| 텔레메트리 journal | 부하 구간의 `http.request` 1500줄. 200 이 아닌 것은 연기 시험의 `bad_request` 하나. 카운터 `internal_error` 1, `http_read_timeout` 4 는 부하 전 21:40:58 UTC 의 값과 부하 뒤의 값이 같다 |
| 텔레메트리 자원 | 메모리 44~45MB, 최고 45MB(상한 256M). CPU 는 300초에 약 6.6초로 약 2.2%(상한 20%). 재시작 0 |
| 제어 평면 | `--soak` 의 `VERDICT: pass`. `get_peers` 2064회, 중앙값 71ms, p95 162ms, 최대 332ms. 재시도 0. 부하 구간 journal 의 200 이 아닌 응답 0. 재시작 0, 메모리 최고 65MB |
| 인스턴스 | load average 최대 0.13, 가용 메모리 454MB 이상 |
| 텔레메트리 테이블 | `ConsumedWriteCapacityUnits` 분당 약 300(초당 5 WCU). `WriteThrottleEvents` 는 데이터점이 없다. 두 지표는 한 반복문에서 지표 이름만 바꿔 같은 `TableName` 차원으로 읽었다. 소비 용량은 나왔으므로 질의는 맞고 스로틀은 0 으로 읽는다 |

**한계.** 부하 프로그램이 같은 인스턴스에서 돌았고 망과 보안 그룹을 지나지 않았다. 상한을 넘기는 부하(`unavailable`)는 이번에 돌리지 않았다. 상한 판정은 텔레메트리 서비스의 단위 시험이 본다.

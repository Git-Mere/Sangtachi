## 왜 만들었는가

사용자가 물었다. "왜 한 번에 끝나지 않고 작업 → 리뷰 → 블로커 → 수정 → 리뷰를 반복하는가."
커밋 기록을 세어 답을 냈다.

`2026-09-21-windows-prereq` 는 **31라운드에 73건**이다. 지적을 주제별로 묶으면 이렇다.

| 주제 | 건수 | 등장한 라운드 수 |
|------|:----:|:----:|
| 서브넷·주소 판정식 하나 | 24 | 20 |
| 주장 강도·근거 부족 | 16 | 9 |
| 방화벽 정책 판정식 하나 | 8 | 7 |
| 문서 전파 누락 | 6 | 6 |
| 기타 | 19 | 13 |

**판정식 두 개가 73건 중 32건을 냈다.** 결함이 32개 있었던 것이 아니라, 입력 케이스 표가 없어서
리뷰어가 반례를 한 라운드에 하나씩 던진 것이다. 그러면 라운드 수는 결함 수가 아니라 반례 수를
따라간다. `CLAUDE.md` 의 "기계 검증 완료에 근거가 없다" 는 라운드 4, 6, 30 에 세 번 나왔다.

원인은 넷이다.

1. 판정 로직에 케이스 표가 없어 리뷰를 테스트 케이스 생성기로 썼다 (규칙 7)
2. 착수 전 수용 기준이 없어 "완료" 의 정의를 리뷰어가 쥐었다
3. 같은 주장이 네 문서 × kor/eng 여덟 곳에 복사되어 있었다 (규칙 5)
4. 수정 후 자기검사 없이 다음 라운드로 보내 리뷰어가 회귀 검사를 대신했다

이 커밋은 그중 1번과 3번을 기계가 먼저 거르게 만든다.

## 게이트가 판정하는 것

| 검사 | 판정 | 내용 |
|------|------|------|
| `mirror` | 차단 | `docs/kor` 와 `docs/eng` 의 문서 짝 |
| `parity` | 차단 | 헤딩 레벨 순서, 표 행 수, 코드 블록 수, 링크 수 |
| `link` | 차단 | 상대 링크의 실재 여부. 예외는 `experiments.md` 두 경로뿐 |
| `claim` | 보고 | 강한 주장 문구의 위치. 막지 않는다 |

`claim` 을 판정으로 만들지 않았다. 문구 하나가 곧 결함은 아니고, 판정으로 만들면 정상 문서가
떨어진다 (규칙 3). 목적은 주장 강도를 낮출 때 전수 확인을 손으로 하지 않게 하는 것이다.

마지막 줄은 항상 `VERDICT: pass` 또는 `VERDICT: fail` 이고 종료 코드가 따라간다. 루트가 잘못돼
판정할 수 없으면 통과로 적지 않고 종료 코드 2로 끝난다. `windows-prereq` 라운드 5 지적("명령이
판정을 내지 않고 목록만 찍는다")을 처음부터 반영했다.

**지원하지 않기로 정한 것**은 스크립트 첫머리에 적고 같은 이름의 시험으로 고정했다. Setext 헤딩,
참조 스타일 링크의 사용처, 선행 파이프 없는 표, 닫히지 않은 펜스다. 모른 채로 두는 것과 정하고
두는 것을 구분하기 위해서다.

## 검증을 먼저 썼다

규칙 7대로 `test_docgate.py` 를 구현보다 먼저 썼다. 케이스 105건이고 양방향이다. 정상 문서가
통과하는지(규칙 3)와 결함을 잡는지를 쌍으로 확인한다.

```bash
cd tools/docgate && python -m unittest test_docgate   # Ran 105 tests ... OK
```

케이스 표가 실제로 결함을 잡았다. **첫 판은 문서 짝을 13개만 검사하고 통과했다.** 그때 실제 짝은
25개였다. 파일 이름의 앞 숫자를 열쇠로 쓴 탓에 `commit_history/2026-...` 13건이 `2026` 한 열쇠로
뭉쳐 12건이 조용히 사라졌다. 이름 짝을 먼저 맞추고 번호 짝은 `decisions/` 안에서만 쓰도록
고쳤다. "모든 파일이 짝이거나 결함이거나 둘 중 하나" 를 케이스로 넣어 같은 구멍을 닫았다.

**두 번째는 반대 방향이었다.** 이 커밋 기록이 링크 문법을 예로 들자 게이트가 그 예를 진짜
링크로 읽고 **정상 문서를 떨어뜨렸다.** 규칙 3이 말하는 자리다. 인라인 코드 스팬을 링크
검사에서 빼고 케이스 5건으로 고정했다. 게이트를 자기 문서에 돌려 보지 않았으면 리뷰어가
잡았을 것이다.

## 0. 이 문서의 위치

**제어 평면의 단일 출처다.** 연산, 요청/응답 인코딩, 오류, 식별자, 방과 피어의 상태 전이, DynamoDB 테이블 설계, 서버 구현 구조, 클라이언트 쪽 호출 계약을 여기서 정한다. [`architecture.md`](architecture.md) 3.3 과 6장은 이 문서를 가리키는 요약이고, [`protocol.md`](protocol.md) 14장은 **터널 프로토콜이 제어 평면에 요구하는 것**을 적은 목록이다. 요구는 그 문서가, 충족 방법은 이 문서가 갖는다.

| 충돌하는 것 | 우선 |
|-------------|------|
| 제어 평면의 와이어 인코딩, 오류 코드, 상태 전이, 테이블 설계 | 이 문서 |
| 터널 와이어 포맷, 세션 상태, 프로토콜 타이머(`get_peers` 폴링 간격과 마감 포함) | [`protocol.md`](protocol.md) |
| 클라이언트 스레드와 루프 구조 | [`architecture.md`](architecture.md) 3.2 |
| 요구사항과 성공 기준 | [`spec.md`](spec.md) |

구현 중 이 문서에 없는 값을 만나면 코드에서 정하지 않고 이 문서를 먼저 고친다.

## 1. 범위와 신뢰 가정

### 1.1 하는 것과 하지 않는 것

| 하는 것 | 하지 않는 것 |
|---------|--------------|
| 방 생성과 참가 | 게임 트래픽 중계. 데이터 경로에 있지 않다 (NFR-1) |
| 가상 IP 배정 | 지표 수집. 텔레메트리 서비스가 맡는다 ([`architecture.md`](architecture.md) 3.4, [ADR 0003](decisions/0003-텔레메트리-서비스-분리.md)) |
| 후보 엔드포인트 저장과 전달 | **UDP 소켓을 열지 않는다.** NAT 매핑 수명 측정에 쓰는 EC2 쪽 UDP probe 송신기는 제어 서버의 기능이 아니라 별개 도구다. 그 도구의 소속과 절차는 [`roadmap.md`](roadmap.md) Phase 4 착수 전 항목이 갖는다 |
| 랑데부 기준점(`punch_delay_ms`, `elapsed_since_ready_ms`) 제공 | NAT 유형 판정, 홀펀칭 결과 판정. 클라이언트가 한다 |
| 재참가한 피어에게 같은 식별자 돌려주기 | 세션 재시도 개시. 누가 언제 재시도하는지는 미정이고 [`protocol.md`](protocol.md) 10.4 가 그렇게 적었다 |

### 1.2 신뢰 가정

**v1 의 제어 평면 경로는 평문이고 호출자 인증이 없다.** [`protocol.md`](protocol.md) 2장이 터널 경로에 대해 한 것과 같은 종류의 명시적 선택이다. 최종 보고서는 이 한계를 터널 쪽 한계와 나란히 적어야 한다.

| 가정 | 내용 | 결과 |
|------|------|------|
| 서버를 신뢰한다 | 클라이언트는 서버가 돌려준 상대 후보와 가상 IP 를 검증 없이 쓴다. 후보 위생([`protocol.md`](protocol.md) 10.1)은 클라이언트가 따로 적용하지만 그것은 형식 검사이고 진위 검사가 아니다 | 악의적 서버는 임의의 후보를 넣어 클라이언트를 제3자에게 200ms 마다 패킷을 보내는 반사 도구로 쓸 수 있다. 10.1 이 막는 것은 브로드캐스트·멀티캐스트 같은 **증폭** 경로다. **서버만 할 수 있는 일이 아니다.** 방에 참가한 상대 피어가 `register_candidate` 로 같은 주소를 등록하면 결과가 같다. 서버는 형식만 보고 전달한다. 그 반사의 상한은 [`protocol.md`](protocol.md) 2장이 적는다 |
| `room_id` 가 유일한 비밀이다 | 방에 참가하는 데 필요한 것은 `room_id` 하나다. 호스트가 그것을 참가자에게 다른 채널로 전달한다 | `room_id` 를 아는 임의의 호출자가 두 번째 피어로 참가해 후보를 받고 게임 상대가 된다. **방 탈취**다. 그러면 진짜 참가자는 `room_full` 을 받는다 |
| 경로상 관측자가 있다 | TCP 평문이라 경로상 관측자가 `room_id`, `peer_token`, 양쪽의 로컬·공인 엔드포인트를 읽는다 | 위와 같은 방 탈취, 그리고 **내부망 주소 노출.** 로컬 후보는 사설 IP 와 포트다 |
| `peer_token` 은 재참가 증명일 뿐이다 | 참가 시 발급하는 비밀로, 같은 피어임을 증명해 같은 `peer_id` 와 가상 IP 를 돌려받는다 | 평문 경로에서 새는 것은 `room_id` 와 같다. **경로상 관측자에 대한 방어가 아니다.** 막는 것은 `room_id` 만 아는 제3자가 이미 참가한 피어를 **사칭**해 그 피어의 후보를 바꾸는 것이다 |
| 호출자 IP 를 그 TCP 연결에서 응답할 수 있는 주소로 본다 | 핸드셰이크를 마친 연결의 출발지다. 그 뒤에 NAT 나 프록시가 있어 여러 사용자가 한 주소로 보일 수 있고, 반대로 한 호출자가 여러 주소를 쓸 수 있다 | 6.4 의 출발지별 속도 제한이 이 가정 위에 선다. 주소가 많은 호출자에게는 효과가 그만큼 줄고, 주소를 공유하는 정상 사용자는 남의 예산 소진에 걸린다(6.4 케이스 표 12번) |
| `client_nonce` 도 비밀이다 | 멱등성 키(2.4)이지만, 그 값을 아는 누구든 같은 요청을 다시 보내 **같은 응답**을 받는다. 응답에는 `peer_token` 이 들어 있다(4.2, 4.3) | 경로상 관측자는 토큰을 이미 읽으므로 새 능력은 아니다. 다만 클라이언트가 nonce 를 로그나 화면에 남기면 토큰을 남긴 것과 같다. **`room_id` 와 같은 등급으로 다룬다** |

**v1 이 수용하는 한계다.** 인증과 TLS 는 [`spec.md`](spec.md) 스트레치 목표다. 도입할 때 위 표의 "결과" 열이 무엇을 잃는지가 판정 기준이 된다. `room_id` 의 크기가 작은 것(2.1)도 같은 표의 연장이다.

**가용성 쪽 한계도 여기에 적는다.** 위 표가 기밀성과 사칭을 다뤘다면 아래 둘은 **무인증
호출자가 서비스를 느리게 만드는** 경로다. v1 은 둘 다 수용한다.

| 경로 | 무엇이 일어나는가 | 왜 수용하는가 |
|------|-------------------|---------------|
| 동시 연결 자리 고갈 | 헤더를 보내지 않는 연결 32개(`MAX_INFLIGHT`)를 5초마다 다시 여는 호출자가 그 구간의 정상 요청을 `unavailable` 로 만든다 (3.4, 7.2) | 출발지별 동시 연결 상한이 필요한데 그 판정이 위 표의 "호출자 IP" 가정 위에 서므로 같은 한계를 물려받는다 |
| `create_room` 남용 | `create_room` 은 입력이 `client_nonce` 하나이고 성공 응답이라 6.4 가 세지 않는다. nonce 를 바꿔 반복하면 호출마다 항목 4개짜리 트랜잭션 쓰기가 생기고 만료 뒤 하루까지 남는다(6.5). provisioned 쓰기 용량을 소진하면 정상 요청이 스로틀에 걸려 `internal` 이 된다 | 성공을 세면 정상 폴링이 걸린다는 6.4 의 이유는 `get_peers` 에 대한 것이고 `create_room` 에는 폴링이 없다. 출발지별 방 생성 상한은 넣을 수 있으나 v1 은 넣지 않는다. **관측은 한다.** `room.created` 로그(7.5)의 출발지별 빈도가 그 근거다 |

**이 둘은 방을 탈취하거나 값을 바꾸지 못한다.** 느리게 하거나 멈출 뿐이다. 그래서 위 신뢰
가정 표와 나누어 적는다.

## 2. 식별자와 상수

### 2.1 room_id

**6글자, 32자 알파벳, CSPRNG.** 알파벳은 다음이다.

```text
ABCDEFGHJKLMNPQRSTUVWXYZ23456789      (32자. I, O, 0, 1 을 뺐다)
```

- 엔트로피는 32^6 = 2^30 이다. **약 10억 가지이고 온라인 추측이 가능한 크기다.** 사람이 콘솔에 치는 값이라 길이를 6으로 정했고, 그 대가로 6.4 의 속도 제한을 둔다. 속도 제한이 없으면 열린 방을 찾아내는 데 드는 요청 수를 제한하는 것이 서버 처리량뿐이다. 제한을 두어도 **막는 것이 아니라 느리게 하는 것**이다. 1.2 의 한계 표에 속한다
- `I`, `O`, `0`, `1` 을 뺀 이유는 사람이 읽고 옮겨 적을 때 헷갈리기 때문이다. 알파벳에 없는 글자를 받으면 오류다. **닮은 글자로 바꿔 해석하지 않는다.** `0` 을 `O` 로 고쳐 주면 두 입력이 같은 방을 가리켜 알파벳을 줄인 의미가 없어진다
- 입력은 **대소문자를 무시한다.** 서버는 받은 값을 대문자로 바꾼 뒤 알파벳 검사를 한다. 소문자 `a` 는 `A` 다. 이것은 닮은 글자 치환이 아니라 같은 글자의 표기 차이다
- 서버는 생성 시 `ROOM` 항목의 조건부 쓰기(6.3)로 충돌을 잡고, 충돌하면 다시 뽑는다. 시도 상한은 `MAX_ROOM_ID_ATTEMPTS`(4)다. 넘기면 `internal` 오류다. 열린 방이 수십 개인 규모에서 30비트 공간의 충돌은 사실상 없고, 상한은 저장소 오류가 무한 재시도로 번지는 것을 막기 위한 것이다

**케이스 표.** 정규화와 검사는 이 표를 통과해야 한다. Phase 3 시험이 이 표를 그대로 돌린다.

| 입력 | 정규화 결과 | 판정 |
|------|-------------|------|
| `ABCDEF` | `ABCDEF` | 통과 |
| `abcdef` | `ABCDEF` | 통과 |
| `aBcDeF` | `ABCDEF` | 통과 |
| `ABCDE` | - | 거부 `bad_request` (5글자) |
| `ABCDEFG` | - | 거부 `bad_request` (7글자) |
| `ABCDE0` | - | 거부 `bad_request` (`0` 은 알파벳 밖) |
| `ABCDEO` | - | 거부 `bad_request` (`O` 는 알파벳 밖) |
| `ABCDE1` / `ABCDEI` | - | 거부 `bad_request` |
| ` ABCDEF` (앞 공백) | - | 거부 `bad_request`. 공백을 지워 주지 않는다 |
| `ＡＢＣＤＥＦ` (전각) | - | 거부 `bad_request`. ASCII 만 받는다 |
| `""` (빈 문자열) / 필드 없음 / 문자열 아님 | - | 거부 `bad_request` |

### 2.2 peer_id

**CSPRNG 32비트, 0 제외, 방 안 유일.** 와이어 헤더가 `peer_id` 를 4바이트로 정했고([`protocol.md`](protocol.md) 4.2) 서버가 이 값을 발급한다. `secrets.randbits(32)` 로 뽑고 0 이면 다시 뽑는다. 방 안 유일성은 `PEER#<peer_id>` 항목의 조건부 쓰기(6.3)가 보장한다. 충돌하면 다시 뽑고 시도 상한은 `MAX_PEER_ID_ATTEMPTS`(4)다.

순차 할당을 쓰지 않는 이유는 [`protocol.md`](protocol.md) 2장의 위협 전제가 "`peer_id` 를 알거나 추측하면" 이기 때문이다. 순차 할당이면 추측이 자명해져 그 문서의 위조 `HELLO` 공격이 경로 밖에서 성립한다. 32비트 난수는 그 추측을 어렵게 하는 **보조 수단**이다. 위조 `HELLO` 는 UDP 로 클라이언트에 직접 오므로 서버의 속도 제한(6.4)이 그 추측을 늦추지 못하고, 추측 비용의 상한을 이 문서가 계산하지는 않는다. **경로상 관측자에게는 아무것도 숨기지 못한다.** 평문이다.

### 2.3 peer_token

**128비트 CSPRNG, 소문자 16진수 32자.** `secrets.token_hex(16)`. 참가(또는 방 생성) 응답에 실리고, 그 뒤 그 피어의 모든 요청에 들어간다. **서버는 원문을 저장한다**(6.3). 해시만 저장하면 응답을 잃은 클라이언트가 같은 `client_nonce` 로 다시 왔을 때(2.4, 4.2, 4.3) 같은 토큰을 돌려줄 수 없다. 저장소가 읽히면 토큰이 새는 대가가 있는데, 경로가 평문이고 `room_id` 가 유일한 비밀인 v1 에서 그 대가는 이미 치르고 있는 것과 같은 종류다(1.2). 인증을 도입할 때 이 줄을 다시 본다.

토큰이 필요한 이유는 둘이다. (1) 재참가 시 같은 `peer_id` 와 가상 IP 를 돌려주려면 "같은 피어" 를 판정할 근거가 필요하다. (2) `register_candidate` 가 `room_id` 와 `peer_id` 만으로 되면 `room_id` 를 아는 제3자가 상대 피어의 후보를 덮어써 그 피어의 `HELLO` 를 임의의 주소로 보내게 할 수 있다.

### 2.4 client_nonce

**클라이언트가 만드는 128비트 CSPRNG, 소문자 16진수 32자.** `create_room` 과 `join_room` 요청에 실린다. 멱등성 키다. 응답을 받지 못하고 재시도한 요청이 두 번째 피어 자리를 다시 차지하는 것을 막는다(4.2, 4.3). 클라이언트는 **한 기동에서 한 값**을 쓰고 재시도마다 바꾸지 않는다. 바꾸면 멱등성이 사라진다.

### 2.5 가상 IP 풀

| 항목 | 값 |
|------|-----|
| 대역 | `10.100.0.0/24` ([`spec.md`](spec.md) FR-4) |
| 호스트(방 생성자) | `10.100.0.1`. 방 생성 시 확정 |
| 참가자 풀 | `10.100.0.2` 부터 `10.100.0.(MAX_PEERS)` 까지. `MAX_PEERS` 가 2 이므로 **v1 의 풀은 `10.100.0.2` 하나**다 |
| 배정 순서 | 풀을 낮은 주소부터 순회하며 `VIP#<ip>` 항목을 조건부 쓰기로 선점한다(6.3). 실패하면 다음 주소. 풀이 끝나면 `room_full` |
| 시도 상한 | 풀 크기. 풀을 한 바퀴 돌면 끝난다. 무한히 돌지 않는다 |
| 회수 | 방이 만료되면 항목이 TTL 로 삭제된다(6.5). **방 살아 있는 동안에는 회수하지 않는다.** 피어가 나가도 자리는 그 피어 것이다. 재참가(4.3)가 같은 주소를 돌려줘야 하기 때문이다 |

`MAX_PEERS` 를 올리면 풀이 그만큼 늘고 다른 것은 바뀌지 않는다. 3자 이상은 [`spec.md`](spec.md) 스트레치 목표다.

### 2.6 상수

```python
CONTROL_PORT              = 8000        # TCP. windows-prereq.md 6절이 이 값을 참조한다
MAX_PEERS                 = 2           # protocol.md 1장. 한 방에 2 피어
ROOM_TTL_S                = 3600        # 생성부터 만료까지. 연장 없음 (5.1)
STORAGE_GRACE_S           = 86400       # 만료 뒤 DynamoDB TTL 삭제까지 여유 (6.5)
PUNCH_DELAY_MS            = 1000        # protocol.md 10.2. 준비 완료 시 방에 1회 기록
MAX_CANDIDATES            = 8           # protocol.md 3장과 같은 값. 피어당
MAX_BODY_BYTES            = 4096        # 요청 본문 상한 (3.3)
MAX_HEADER_BYTES          = 2048        # 요청 줄과 헤더 전체 상한 (3.3)
SERVER_READ_TIMEOUT_S     = 5           # 요청 한 건을 다 받기까지 (3.4)
CLIENT_CONNECT_TIMEOUT_S  = 3           # 클라이언트 connect (8.2)
CLIENT_IO_TIMEOUT_S       = 3           # 클라이언트 송신/수신 각각 (8.2)
MAX_ROOM_ID_ATTEMPTS      = 4           # room_id 충돌 재추첨 상한 (2.1)
MAX_PEER_ID_ATTEMPTS      = 4           # peer_id 충돌 재추첨 상한 (2.2)
RATE_LIMIT_BUCKET         = 10          # 출발지별 실패 예산 (6.4)
RATE_LIMIT_REFILL_PER_MIN = 10          # 분당 보충 (6.4)
MAX_RATE_ENTRIES          = 4096        # 속도 제한 표 상한 (6.4)
MAX_INFLIGHT              = 32          # 동시 처리 요청 상한 (7.2)
```

`MAX_CANDIDATES` 와 `PUNCH_DELAY_MS` 는 [`protocol.md`](protocol.md) 가 소유하는 값의 복사다. **그 문서가 바뀌면 여기를 따라 고친다.** 두 값만 예외로 복사하는 이유는 서버 코드가 그 값을 가져야 하고, 서버 코드는 C++ 헤더를 읽지 않기 때문이다.

## 3. 전송과 인코딩

### 3.1 왜 HTTP 부분집합인가

전송은 **TCP 위의 HTTP/1.1 부분집합**이고 본문은 JSON 이다. 세 가지를 저울질했다.

| 안 | 장점 | 단점 |
|----|------|------|
| **HTTP/1.1 부분집합 (채택)** | `curl` 로 시험할 수 있다. 서버 쪽 `ss`, 보안 그룹, `Test-NetConnection` 같은 기존 절차([`windows-prereq.md`](windows-prereq.md) 6절)가 그대로 맞는다 | 양쪽을 손으로 짜야 한다. 부분집합을 좁게 못박아 그 비용을 줄인다 |
| 줄 단위 JSON over TCP | 구현이 가장 단순하다 | 표준 도구로 시험할 수 없다. 시험 도구를 하나 더 만들게 된다 |
| 웹 프레임워크 | 파싱을 안 짠다 | [`spec.md`](spec.md) NFR-5 승인이 필요하고, 클라이언트 쪽 비용은 그대로다 |

부분집합은 아래 3.3 이 전부다. **거기 없는 HTTP 기능은 지원하지 않고, 받으면 거부한다.** 지원하는 척하다 조용히 틀리는 것보다 낫다.

### 3.2 주소

| 항목 | 값 |
|------|-----|
| 프로토콜 | TCP, IPv4 |
| 서버 bind | `0.0.0.0:8000`. 판정 방법은 [`windows-prereq.md`](windows-prereq.md) 6절 |
| 클라이언트가 받는 주소 | **DNS 이름 또는 IPv4 리터럴.** 기동 입력([`architecture.md`](architecture.md) 3.5)으로 받는다. DNS 이름은 Elastic IP 를 가리키는 A 레코드다. Elastic IP 가 필요한 이유는 [`windows-prereq.md`](windows-prereq.md) 10절 |
| 경로 접두사 | `/v1/`. 인코딩이 호환되지 않게 바뀌면 `/v2/` 를 연다. 같은 서버가 두 접두사를 동시에 낼 수 있다 |

DNS 해석은 클라이언트의 `[control]` 스레드가 한다([`architecture.md`](architecture.md) 3.2.8). 해석 결과가 여럿이면 첫 IPv4 주소를 쓰고 나머지는 쓰지 않는다. `AAAA` 는 쓰지 않는다. 터널이 IPv4 전용인 것([`protocol.md`](protocol.md) 1장)과 같은 범위다.

### 3.3 HTTP 부분집합

**요청.**

```text
POST /v1/<op> HTTP/1.1\r\n
Host: <서버 주소>\r\n
Content-Type: application/json\r\n
Content-Length: <본문 바이트 수>\r\n
Connection: close\r\n
\r\n
<JSON 본문>
```

**응답.**

```text
HTTP/1.1 <status> <reason>\r\n
Content-Type: application/json\r\n
Content-Length: <본문 바이트 수>\r\n
Connection: close\r\n
\r\n
<JSON 본문>
```

| 항목 | 규칙 |
|------|------|
| 메서드 | `POST` 만. 조회(`get_peers`)도 `POST` 다. 인증 정보(`peer_token`)가 URL 이나 로그에 남지 않게 본문에 싣기 때문이다 |
| 경로 | `/v1/` + 4장의 연산 이름. 쿼리 문자열 없음 |
| 본문 길이 | `Content-Length` 필수. `Transfer-Encoding` 이 있으면 값이 무엇이든 거부 |
| 연결 | 요청 하나에 연결 하나. 응답 뒤 서버가 닫는다. keep-alive 와 파이프라이닝 없음 |
| 헤더 | 이름은 대소문자 무시. 위 표에 없는 헤더는 무시한다(두 번 와도 무시한다). **표에 있는 헤더가 두 번 오면 거부.** **`Content-Length` 가 두 번 오는 것을 특히 거부한다.** 값이 다른 `Content-Length` 가 여럿인 메시지를 거부하라는 것은 RFC 9112 6.3 의 규정이고, 앞뒤 중계자가 다른 값을 고르는 것이 요청 밀반입의 한 형태다. 값이 같아도 거부한다. 구분할 이유가 없다 |
| 본문 | UTF-8 JSON **객체** 하나. 배열이나 스칼라는 거부. 알 수 없는 키는 무시한다(전방 호환) |
| 크기 | 요청 줄과 헤더 합계 `MAX_HEADER_BYTES`(2048), 본문 `MAX_BODY_BYTES`(4096) |
| 인코딩 | 문자열은 UTF-8. 정수는 JSON number 이고 소수점 없음. `uint32` 필드는 0 이상 4294967295 이하 |
| 압축, 청크, 100-continue, 업그레이드, 인증 헤더 | 없음 |
| 바이트 정확 일치 | 요청 줄은 `POST <경로> HTTP/1.1` 이고 구분자는 공백 하나다. 공백 둘, 탭, 절대 형식(`POST http://host/v1/op`), 끝에 붙은 `/`, 퍼센트 인코딩(`%5F`)은 전부 거부한다. 경로는 대소문자를 구분한다 |
| `Content-Length` 값 | `^[0-9]+$` 만 받는다. `+17`, `1_7`, 앞뒤 공백, 전각 숫자는 거부한다. 언어의 정수 변환 함수에 맡기지 않는다. Python `int()` 는 앞의 셋을 받는다 |
| 헤더 접기 (obs-fold) | 헤더 줄이 공백이나 탭으로 시작하면 거부한다. 이어 붙이지 않는다 |
| `Host`, `Content-Type` | **검사하지 않는다.** 클라이언트는 항상 보내지만(위 형식) 서버는 값을 보지 않는다. 가상 호스트도 콘텐츠 협상도 없다 |
| `Content-Length` 보다 긴 본문 | 앞의 `Content-Length` 바이트만 읽고 응답한 뒤 연결을 닫는다. 남은 바이트는 읽지 않는다. 연결 하나에 요청 하나이므로 그 바이트는 두 번째 요청이 될 수 없다 |

**서버 파싱 케이스 표.** 판정 함수는 이 표를 통과해야 한다. 행마다 하나씩 변이를 넣어 그 행이 `FAIL` 하는지 본다.

| 입력 | 응답 |
|------|------|
| 정상 `POST /v1/get_peers`, 올바른 `Content-Length`, JSON 객체 | 연산 결과 |
| `GET /v1/get_peers` | `405` `method_not_allowed` |
| `POST /v1/unknown_op` | `404` `unknown_op` |
| `POST /get_peers` (접두사 없음) | `404` `unknown_op` |
| `POST /v1/get_peers?x=1` | `404` `unknown_op`. 쿼리 문자열을 지원하지 않는다 |
| `Content-Length` 없음 | `411` `length_required` |
| `Content-Length: abc` / 음수 / 두 번 | `400` `bad_request` |
| `Content-Length: 4097` | `413` `too_large`. 본문을 읽지 않고 응답한 뒤 닫는다 |
| `Transfer-Encoding: chunked` | `400` `bad_request` |
| 요청 줄 + 헤더가 2048 바이트 초과 | `431` `too_large` |
| 본문이 `Content-Length` 보다 짧고 5초 안에 더 오지 않음 | 응답 없이 연결을 닫는다. 카운터 `http_read_timeout` |
| 본문이 JSON 이 아님 / 배열 / 스칼라 | `400` `bad_request` |
| 본문이 UTF-8 이 아님 | `400` `bad_request` |
| `HTTP/1.0` | `400` `bad_request`. 1.1 만 받는다 |
| 정상 요청에 알 수 없는 헤더 `X-Foo: bar` | 연산 결과. 무시한다 |
| 알 수 없는 헤더 `X-Foo` 가 두 번 | 연산 결과. 표 밖 헤더는 중복도 무시한다 |
| `content-length: 17` (소문자) | 연산 결과. 이름은 대소문자 무시 |
| `Content-Length: 4096` | 연산 결과. 상한 안쪽이다. `>=` 로 잘못 쓴 구현이 이 행에서 걸린다 |
| 요청 줄 + 헤더가 정확히 2048 바이트 | 연산 결과. 상한 안쪽이다 |
| `Content-Length: +17` / `1_7` / ` 17` | `400` `bad_request`. 값은 `^[0-9]+$` 만 |
| 헤더 줄이 공백으로 시작 (obs-fold) | `400` `bad_request` |
| `POST  /v1/get_peers HTTP/1.1` (공백 둘) / `POST /v1/get_peers/ HTTP/1.1` / `POST http://h/v1/get_peers HTTP/1.1` | `400` `bad_request`. 요청 줄은 바이트로 일치해야 한다 |
| `Host` 없음 | 연산 결과. 검사하지 않는다 |
| `Content-Type: text/plain` | 연산 결과. 검사하지 않는다 |
| 본문이 `Content-Length` 보다 김 | 연산 결과. 앞의 `Content-Length` 바이트만 읽고 닫는다 |
| `GET /v1/unknown_op` | `405` `method_not_allowed`. 아래 검사 순서대로 메서드가 경로보다 먼저다 |
| `Transfer-Encoding: chunked` 이고 `Content-Length` 없음 | `400` `bad_request`. `Transfer-Encoding` 이 `Content-Length` 부재보다 먼저다 |

**검사 순서.** 복합 결함의 응답을 정하려면 순서가 필요하다. 위에서부터 본다.

1. 요청 줄의 바이트 형식과 `HTTP/1.1` -> `400`
2. 메서드 -> `405`
3. 경로 (`/v1/` 접두사와 연산 이름, 쿼리 문자열 없음) -> `404`
4. 헤더 전체 크기 -> `431`
5. 헤더 문법 (접기, 표에 있는 헤더의 중복) -> `400`
6. `Transfer-Encoding` 존재 -> `400`
7. `Content-Length` 존재 -> `411`, 값 형식 -> `400`, 상한 초과 -> `413`
8. 본문 읽기와 시간 제한 (3.4) -> 응답 없이 닫음
9. 본문이 UTF-8 JSON 객체인가 -> `400`

`400` 대 오류에도 본문은 4.1 의 오류 봉투다. **파싱 실패 응답은 요청 내용을 되돌려 보내지 않는다.** 그러면 서버가 임의 바이트를 반사하는 자리가 된다.

### 3.4 서버 쪽 시간 제한

연결 수락부터 요청 한 건을 다 읽기까지 `SERVER_READ_TIMEOUT_S`(5초)다. 넘기면 응답 없이 닫고 `http_read_timeout` 을 올린다. 응답 송신에도 같은 5초를 건다.

**막는 것과 막지 못하는 것을 구분해 적는다.** 이 값이 막는 것은 **한 연결의 점유 시간**이다.
**동시 연결 자리의 고갈은 막지 못한다.** `MAX_INFLIGHT`(32)는 수락 직후, 파싱 전에 오르므로
(7.2) 헤더를 보내지 않는 연결 32개를 5초마다 다시 여는 호출자는 그 구간의 정상 요청을 전부
`unavailable` 로 만든다. 그 호출자는 6.4 의 예산도 쓰지 않는다. `http_read_timeout` 은 세는
셋에 없기 때문이다. 정상 클라이언트는 8.3 대로 재시도 뒤 `CONTROL_PLANE_EXCHANGE_FAILED` 로
끝난다. **v1 이 수용하는 한계다.** 1.2 의 한계 표에 속한다. 막으려면 출발지별 동시 연결
상한이 필요하고, 그것은 6.4 의 출발지 가정(1.2)을 그대로 물려받는다.

### 3.5 클라이언트가 하는 검사

클라이언트는 응답에서 다음만 본다. 그 외는 무시한다.

1. 상태 줄이 `HTTP/1.1 <3자리 숫자>` 로 시작하는가. 아니면 `CONTROL_PLANE_EXCHANGE_FAILED` 로 이어지는 전송 오류다(8.3)
2. `Content-Length` 헤더 하나. 없거나 `MAX_BODY_BYTES` 를 넘으면 전송 오류
3. 본문을 그 길이만큼 읽고 JSON 객체로 해석한다. 실패하면 전송 오류
4. `ok` 필드(4.1)로 성공과 오류를 가른다. **HTTP 상태 코드로 가르지 않는다.** 상태 코드는 `curl` 을 든 사람을 위한 것이고 프로그램이 보는 것은 본문이다. 둘이 어긋나는 구현은 시험에서 걸러야 하지만, 클라이언트가 둘 다 보면 어긋났을 때 어느 쪽을 믿을지가 구현마다 달라진다

## 4. 연산

연산은 넷이다. `create_room`, `join_room`, `register_candidate`, `get_peers`.

**`register_peer` 는 없다.** 이전 설계는 재연결용으로 그 연산을 두었다. 재참가를 `join_room` 의 한 형식(4.3)으로 넣었으므로 별도 연산이 할 일이 없다. 연산이 하나 줄고, 클라이언트가 "언제 `join_room` 이고 언제 `register_peer` 인가" 를 판단하지 않는다.

### 4.1 공통 봉투

**성공.**

```json
{"ok": true, ...연산별 필드}
```

**오류.**

```json
{"ok": false, "error": "<오류 코드>", "message": "<사람용 한 줄>"}
```

`error` 는 아래 표의 문자열 중 하나이고 프로그램이 본다. `message` 는 사람이 읽는 것이고 내용을 못박지 않는다. **`message` 에 요청 본문이나 토큰을 넣지 않는다.**

| 오류 코드 | HTTP | 뜻 | 클라이언트 동작 |
|-----------|------|-----|-----------------|
| `bad_request` | 400 | 필수 필드 누락, 형식 위반, 2.1 알파벳 위반 | 재시도하지 않는다. `CONTROL_PLANE_EXCHANGE_FAILED` |
| `method_not_allowed` | 405 | `POST` 아님 | 같음 |
| `unknown_op` | 404 | 경로가 4장의 연산이 아님 | 같음 |
| `length_required` | 411 | `Content-Length` 없음 | 같음 |
| `too_large` | 413 / 431 | 본문 또는 헤더 상한 초과 | 같음 |
| `room_not_found` | 404 | 그 `room_id` 의 방이 없다 | 같음. **만료된 방도 이 코드가 아니다.** 아래 `room_expired` |
| `room_expired` | 410 | 방이 있으나 만료 시각이 지났다(5.1) | 같음 |
| `room_full` | 409 | 참가자 풀의 주소가 전부 선점됐다(2.5) | 같음 |
| `unauthorized` | 403 | `peer_token` 이 그 `peer_id` 의 것이 아니다 | 같음 |
| `rate_limited` | 429 | 6.4 의 출발지별 예산 소진 | 같음. 클라이언트가 스스로 기다렸다 다시 하지 않는다. 사람이 다시 시작한다 |
| `internal` | 500 | 저장소 오류, 재추첨 상한 도달 | **일시 오류다.** 8.3 의 재시도 규칙을 따른다 |
| `unavailable` | 503 | `MAX_INFLIGHT` 초과(7.2) | 같음. 일시 오류 |

**`bad_request`, `rate_limited`, `internal`, `unavailable` 은 모든 연산에서 나올 수 있다.** 파싱과 속도 제한과 저장소 오류는 연산 앞뒤의 공통 단계(7.2, 7.3)에서 나기 때문이다. 아래 연산별 "오류" 줄은 **그 연산에서만 나는 것**을 적고 이 넷을 다시 적지 않는다.

**`room_not_found` 와 `room_expired` 를 나누는 이유.** 사람이 방 코드를 잘못 친 것과, 맞게 쳤는데 호스트가 한 시간 전에 만든 것은 다른 조치가 필요하다. 합치면 어느 쪽인지 알 수 없다. 대신 **존재하지 않는 방을 추측하는 호출자에게 만료된 방의 존재를 알려 준다.** 만료된 방은 참가할 수 없으므로 알려 줘도 잃는 것이 없다.

### 4.2 create_room

호스트가 부른다. 방을 만들고 호스트를 첫 피어로 등록하고 `10.100.0.1` 을 준다.

**요청.**

| 필드 | 형 | 필수 | 뜻 |
|------|-----|:---:|-----|
| `client_nonce` | 16진수 32자 문자열 | 예 | 멱등성 키(2.4) |

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `room_id` | 문자열 6자 | 2.1 |
| `peer_id` | uint32 | 2.2 |
| `peer_token` | 16진수 32자 | 2.3 |
| `virtual_ip` | 점 십진 문자열 | `10.100.0.1` |
| `expires_in_s` | 정수 | 응답 시점부터 만료까지 남은 초. 절대 시각을 주지 않는다. 클라이언트 시계를 믿지 않는다 |

**멱등성.** 같은 `client_nonce` 로 다시 오면 **이미 만든 방의 같은 응답**을 돌려준다. `expires_in_s` 만 줄어든다. 그 방이 만료됐으면 `room_expired` 다. 새 방을 만들지 않는다. 판정 근거는 `NONCE#` 항목(6.3)이다.

**오류.** 연산 고유의 것은 없다. 공통 넷(4.1)만 난다.

### 4.3 join_room

**새 참가는 참가자가 부르고, 재참가는 어느 피어든 부른다.** 재시작한 호스트도 재참가다([`architecture.md`](architecture.md) 3.5). 두 형식이 있고 **필드 조합으로 가른다.**

| 형식 | 필드 | 뜻 |
|------|------|-----|
| 새 참가 | `room_id`, `client_nonce` | 풀에서 가상 IP 를 선점하고 새 `peer_id`, `peer_token` 을 발급 |
| 재참가 | `room_id`, `peer_id`, `peer_token` | 같은 피어임을 증명하고 **같은 `peer_id` 와 가상 IP** 를 돌려받는다 ([`protocol.md`](protocol.md) 14장 계약 7) |

두 형식의 필드를 섞어 보내면(`client_nonce` 와 `peer_token` 둘 다) `bad_request` 다. 어느 쪽인지 서버가 추측하지 않는다.

**요청 (새 참가).**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예. 2.1 정규화를 거친다 |
| `client_nonce` | 16진수 32자 | 예 |

**요청 (재참가).**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예 |
| `peer_id` | uint32 | 예 |
| `peer_token` | 16진수 32자 | 예 |

**응답 (두 형식 공통).**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `room_id` | 문자열 6자 | 정규화된 값. 클라이언트는 이후 이 값을 쓴다 |
| `peer_id` | uint32 | |
| `peer_token` | 16진수 32자 | 재참가에서는 **받은 값 그대로** 다시 준다. 새 토큰을 발급하지 않는다 |
| `virtual_ip` | 점 십진 문자열 | |
| `expires_in_s` | 정수 | |

**재참가가 되돌려 놓는 것.** 후보 목록은 지운다. 재시작한 프로세스는 포트 0 으로 다시 bind 하므로([`protocol.md`](protocol.md) 6장) 이전 후보는 전부 낡았다. 낡은 후보를 남기면 상대가 `get_peers` 로 죽은 주소를 받는다. 방의 `ready_at` 은 **지우지 않는다.** 한 번 확정된 `punch_delay_ms` 기준점은 방 단위로 불변이다(14장 계약 3). 재참가한 피어가 새 후보를 등록해도 `get_peers` 는 준비 완료를 유지하고 `elapsed_since_ready_ms` 는 계속 커진다. 클라이언트 계산식 `max(0, punch_delay_ms - elapsed)` 가 0 이 되어 즉시 펀치한다. 그것이 [`protocol.md`](protocol.md) 10.2 가 정한 동작이다.

**재참가가 살아남은 상대를 살리지는 못한다.** 재시작한 쪽의 새 `HELLO` 가 상대 NAT 에 도착하지 않는 실측 한계는 [`protocol.md`](protocol.md) 10.4 에 있다. 이 연산이 보장하는 것은 **식별자와 가상 IP 의 유지**까지다. 살아남은 쪽이 `get_peers` 를 다시 폴링해 새 후보를 받는 절차는 v1 에 없다. 그 절차를 나중에 넣을 때 이 계약이 전제가 된다.

**멱등성 (새 참가).** 같은 `room_id` 와 `client_nonce` 로 다시 오면 처음 발급한 것을 그대로 준다. `NONCE#` 항목이 근거다. 다른 `client_nonce` 로 오면 새 참가이고, 풀의 주소가 전부 선점됐으면 `room_full` 이다. **응답을 잃은 클라이언트가 nonce 를 바꿔 재시도하면 자기 자신이 방을 채운다.** 그래서 2.4 가 한 기동에 한 값이라고 정했다.

**오류.** `room_not_found`, `room_expired`, `room_full`, `unauthorized`(재참가에서 토큰 불일치, 또는 그 `peer_id` 가 방에 없음). 공통 넷(4.1)은 따로 적지 않는다.

**`peer_id` 가 방에 없을 때 `room_not_found` 가 아니라 `unauthorized` 인 이유.** 방은 있다. 없는 것은 그 피어다. 존재하지 않는 `peer_id` 와 토큰이 틀린 `peer_id` 를 같은 코드로 답해야 `room_id` 만 아는 호출자가 방 안의 `peer_id` 를 열거하지 못한다. 32비트 공간이라 열거는 어차피 비현실적이지만, 응답으로 구분해 줄 이유가 없다.

### 4.4 register_candidate

피어가 STUN 을 마친 뒤 부른다. 후보 목록을 **통째로 교체**한다. 추가가 아니다. 두 번 부르면 두 번째 목록이 남는다. 교체 의미를 택한 이유는 멱등하기 때문이다. 응답을 잃고 다시 보내도 결과가 같다.

**요청.**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예 |
| `peer_id` | uint32 | 예 |
| `peer_token` | 16진수 32자 | 예 |
| `candidates` | 배열 | 예. 길이 1 이상 `MAX_CANDIDATES`(8) 이하 |

후보 원소:

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `ip` | 점 십진 IPv4 문자열 | |
| `port` | 정수 1~65535 | |
| `kind` | `"local"` 또는 `"reflexive"` | [`protocol.md`](protocol.md) 10.1 의 두 종류. 서버는 저장하고 전달만 한다. 판정에 쓰지 않는다 |

**위생.** [`protocol.md`](protocol.md) 10.1 의 규칙을 서버가 적용한다(14장 계약 5). 클라이언트도 받은 목록에 같은 규칙을 다시 적용한다. 서버를 신뢰하는 것과 무관하게 형식 검사는 양쪽이 한다. 아래 케이스 표는 10.1 의 규칙을 **서버 입력에 대해** 펼친 것이고 규칙 자체는 그 절이 소유한다.

| 후보 | 결과 | 근거 |
|------|------|------|
| `192.168.0.10:51000 local` | 저장. `accepted`+1 | 정상 로컬 후보 |
| `203.0.113.7:51000 reflexive` | 저장. `accepted`+1 | 정상 반사 후보 |
| `255.255.255.255:51000` | 그 후보만 폐기. `rejected`+1 | 10.1 브로드캐스트 |
| `224.0.0.1:51000` / `239.255.255.250:1900` | 그 후보만 폐기. `rejected`+1 | 10.1 멀티캐스트 `224.0.0.0/4` |
| `0.0.0.0:51000` | 그 후보만 폐기. `rejected`+1 | 10.1 미지정 |
| `127.0.0.1:51000` | 그 후보만 폐기. `rejected`+1 | 10.1 루프백. **수신 출발지 위생(7장)과 달리 후보 목록은 루프백을 거부한다** |
| `10.0.0.5:1` / `10.0.0.5:65535` | 저장. `accepted`+1 | 포트 범위의 양 끝은 정상이다. 상한을 `>=` 로 잘못 쓴 구현이 이 행에서 걸린다 |
| `10.0.0.5:0` | 그 후보만 폐기. `rejected`+1 | 10.1 포트 0. 위생 규칙이 정한 값이라 형식 위반이 아니다 |
| `10.0.0.5:65536` / `-1` / `"51000"`(문자열) | **요청 전체 `bad_request`** | `port` 가 1~65535 의 JSON 정수가 아니다. 형 위반이다 |
| `"10.0.0"` / `"10.0.0.5.1"` / `"::1"` / `"10.000.0.5"` | **요청 전체 `bad_request`** | `ip` 가 IPv4 점 십진 4옥텟이 아니다. 형 위반이다. **`inet_aton` 류의 관대한 파서를 쓰지 않는다.** 이 레포의 Windows Python 3.11 에서 `socket.inet_aton` 은 `10.0.5` 를 `10.0.0.5` 로, `010.0.0.5` 를 `8.0.0.5`(8진수) 로 받았다 |
| `kind` 가 `"local"`/`"reflexive"` 가 아님, 또는 `ip`·`port`·`kind` 중 하나가 없음 | **요청 전체 `bad_request`** | 형 위반이다 |
| 같은 `ip:port` 두 번 | 하나만 저장. `accepted`+1, **`rejected` 는 그대로** | 10.1 중복 제거. `kind` 가 달라도 같은 엔드포인트다. 중복은 위생 거부가 아니므로 세지 않는다. 따라서 `accepted + rejected` 가 보낸 개수보다 작을 수 있다 |
| 9개 (전부 정상) | **요청 전체 `bad_request`** | 클라이언트가 8개를 넘겨 보내는 것은 형식 위반이다. 10.1 의 "초과분은 버린다" 는 **수신한** 목록에 대한 클라이언트 규칙이고, 서버는 보내는 쪽에 상한을 강제한다 |
| 8개 (전부 정상) | 저장. `accepted`=8 | 상한 안쪽이다 |
| 빈 배열 | **요청 전체 `bad_request`** | 후보가 없으면 등록할 것이 없다 |
| 위생에 걸린 것만 있는 목록 (예: 루프백 1개) | **요청 전체 `bad_request`** | 저장할 후보가 0개다. 아래 거부 정책 |

**거부 정책. 결과는 둘뿐이고 위 표의 "결과" 열이 행마다 어느 쪽인지 적는다.**

| 무엇 | 결과 |
|------|------|
| **위생 거부** — 주소나 포트 값이 10.1 의 규칙에 걸린다(브로드캐스트, 멀티캐스트, 미지정, 루프백, 포트 0) | 그 후보만 버리고 나머지를 저장한다. `rejected` 를 올리고 응답은 `ok` 다 |
| **형 위반** — `ip`·`port`·`kind` 가 형이나 범위를 벗어나거나 없다, 목록이 9개거나 비었다 | **요청 전체가 `bad_request`** 다. 개별 후보 문제가 아니라 요청 문제다 |

**가르는 기준은 "값이 규칙에 걸리는가" 와 "형이 아닌가" 다.** `10.0.0.5:0` 은 형으로는 정수
`0` 이고 규칙이 그 값을 거부하는 것이라 위생 거부다. `10.0.0.5:65536` 은 범위 밖이라 형
위반이다. 이 구분이 없으면 같은 입력에 `{"ok": true, "rejected": 1}` 과 `400 bad_request`
둘 다 규정에 맞게 읽혀 시험을 쓸 수 없다.

**전부 위생 거부되어 저장할 후보가 0개면 `bad_request`** 다. 0개를 저장해 놓고 `ok` 를 주면
상대가 준비 완료 뒤 빈 목록을 받아 `HOLE_PUNCH_TIMEOUT` 으로 끝나고, 그 실패가 NAT 실패로
위장한다.

**클라이언트 쪽 결과가 다르다.** 위생 거부는 `rejected` 가 0 이 아니므로 `WARN` 한 줄을
남기고 진행하고, `bad_request` 는 확정 오류라 재시도 없이 `CONTROL_PLANE_EXCHANGE_FAILED`
다(8.3).

**응답.**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `accepted` | 정수 | 저장한 후보 수 |
| `rejected` | 정수 | 위생에서 버린 후보 수. 클라이언트는 0 이 아니면 `WARN` 한 줄을 남긴다 |
| `ready` | 불 | 이 등록으로 방이 준비 완료가 됐거나 이미 준비 완료였으면 참 |

**준비 완료 판정. 자기 `PEER#` 를 쓴 뒤 방을 다시 읽어서 한다.** 순서를 못박는다.

1. `PEER#` update 로 자기 후보를 저장한다
2. **`Query(pk, ConsistentRead=true)` 를 다시 읽는다**
3. 그 결과에서 방의 모든 피어(`MAX_PEERS` 명)가 후보를 1개 이상 갖고 있고 `ROOM.ready_at_wall_ms` 가 없으면, 조건부 쓰기로 `ready_at_*` 과 `punch_delay_ms = PUNCH_DELAY_MS` 를 한 번 기록한다(6.3)

**2번이 없으면 준비 완료가 한 번도 기록되지 않는 순서가 있다.** 쓰기 전에 읽은 결과에 자기
등록만 얹어서 판정하면, 두 피어가 각자 쓰기 전에 읽었을 때 **둘 다 상대의 후보를 못 본다.**
조건부 쓰기 `attribute_not_exists(ready_at_wall_ms)` 는 두 번 쓰는 것을 막지 그 자리에서
0번 쓰는 것을 막지 못한다. 그러면 4.5 의 정의상 `get_peers` 는 영원히 `ready: false` 이고
양쪽이 폴링 마감까지 기다리다 `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다. **NAT 실패로
위장한 제어 평면 실패다.**

**쓰기 뒤에 읽으면 적어도 한쪽은 둘 다 본다.** 각자의 재읽기가 자기 쓰기 뒤에 오므로,
나중에 읽는 쪽은 상대의 쓰기도 이미 보인다. 둘 다 보는 경우에는 조건부 쓰기가 한 번만
성공하고 실패한 쪽은 이미 기록됐다는 뜻이므로 오류가 아니다. 이것이 14장 계약 3 의 충족이다.

**케이스 표.** `A`, `B` 는 두 피어의 `register_candidate` 다. `R` 은 1번 쓰기, `Q` 는 2번
재읽기다.

| 순서 | A 의 재읽기가 보는 것 | B 의 재읽기가 보는 것 | `ready_at` 기록 |
|------|----------------------|----------------------|-----------------|
| A 전체 → B 전체 (순차) | A 만 | A, B | B 가 1회 |
| `A:R` → `B:R` → `A:Q` → `B:Q` | A, B | A, B | 먼저 조건부 쓰기에 성공한 쪽 1회 |
| `A:R` → `B:R` → `B:Q` → `A:Q` | A, B | A, B | 같음 |
| `A:R` → `A:Q` → `B:R` → `B:Q` | A 만 | A, B | B 가 1회 |
| `B:R` → `B:Q` → `A:R` → `A:Q` | A, B | B 만 | A 가 1회 |
| 재읽기를 하지 않는 구현(`R` 전에 읽은 결과로 판정) | — | — | **0회. 이 표가 잡는 결함이다** |

마지막 행이 변이 시험이다. 2번을 지운 구현이 그 행에서 `FAIL` 해야 한다.

**오류.** `room_not_found`, `room_expired`, `unauthorized`. 공통 넷(4.1)은 따로 적지 않는다.

### 4.5 get_peers

클라이언트가 [`protocol.md`](protocol.md) 11장의 간격(500ms)과 마감(60s)으로 폴링한다. **간격과 마감은 그 문서가 소유한다.** 여기에 숫자를 다시 적지 않는다.

**요청.**

| 필드 | 형 | 필수 |
|------|-----|:---:|
| `room_id` | 문자열 | 예 |
| `peer_id` | uint32 | 예 |
| `peer_token` | 16진수 32자 | 예 |

**응답 (준비 전).**

```json
{"ok": true, "ready": false}
```

**응답 (준비 완료).**

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `ready` | `true` | |
| `punch_delay_ms` | 정수 | 방에 기록된 값. 응답마다 같다 |
| `elapsed_since_ready_ms` | 정수 0 이상 | 준비 완료 기록 시점부터 이 응답을 만드는 시점까지. 계산 방법은 7.4 |
| `peers` | 배열 | **자신을 제외한** 피어. v1 은 길이 1 |

`peers` 원소:

| 필드 | 형 | 뜻 |
|------|-----|-----|
| `peer_id` | uint32 | |
| `virtual_ip` | 점 십진 문자열 | [`protocol.md`](protocol.md) 5.1 `virtual_ip` 검증에 쓴다 (14장 계약 6) |
| `candidates` | 배열 | 4.4 와 같은 원소 형. 저장된 순서대로 |

**준비 완료의 정의는 `ROOM.ready_at_wall_ms` 의 존재다.** 피어 수나 후보 수를 응답 시점에 다시 세지 않는다. 다시 세면 재참가(4.3)가 후보를 지운 순간 준비 완료가 거짓으로 돌아가 상대가 이미 시작한 펀치와 어긋난다.

**준비 완료인데 상대 후보가 0개인 응답이 있을 수 있다.** 재참가(4.3)가 후보를 지운 뒤 다시 등록하기 전의 구간이다. 클라이언트는 그 응답을 준비 완료로 취급하지 않고 **폴링을 계속한다.** 마감에 닿으면 [`protocol.md`](protocol.md) 9.6 의 폴링 마감 초과로 `CONTROL_PLANE_EXCHANGE_FAILED` 다. 빈 목록으로 펀치에 들어가면 보낼 곳이 없는 채 10초를 기다려 `HOLE_PUNCH_TIMEOUT` 이 되고, 그것은 NAT 실패로 위장한 제어 평면 실패다. [`architecture.md`](architecture.md) 8장이 "상대 후보 없음" 을 `CONTROL_PLANE_EXCHANGE_FAILED` 로 분류한 것과 같은 판단이다.

**자신을 제외하는 판정은 `peer_id` 다.** 같은 `peer_id` 가 둘일 수 없으므로(2.2) 응답에 자신과 같은 `peer_id` 가 있으면 서버 결함이다. 클라이언트는 그 경우 `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝낸다([`protocol.md`](protocol.md) 4.2).

**오류.** `room_not_found`, `room_expired`, `unauthorized`. 공통 넷(4.1)은 따로 적지 않는다.

**`not_ready` 는 오류가 아니다.** `ok: true` 에 `ready: false` 다. 폴링이 정상 진행 중인 것이라 오류 봉투에 넣으면 클라이언트가 "오류지만 계속" 이라는 예외 경로를 갖게 된다.

## 5. 상태 전이

### 5.1 방

방의 상태는 **저장된 필드에서 파생**한다. 상태 필드를 따로 두지 않는다. 두면 필드와 상태가 어긋나는 경우가 생긴다.

| 상태 | 정의 |
|------|------|
| `waiting` | `ROOM` 항목이 있고, `now < expires_at`, `ready_at_wall_ms` 없음 |
| `ready` | `ROOM` 항목이 있고, `now < expires_at`, `ready_at_wall_ms` 있음 |
| `expired` | `ROOM` 항목이 있고, `now >= expires_at`. TTL 삭제 전까지 이 상태로 보인다 |
| (없음) | `ROOM` 항목이 없다. 처음부터 없었거나 TTL 이 지웠다 |

```text
(없음) --create_room--> waiting --모든 피어가 후보를 갖게 한 register_candidate--> ready
                          |                                                  |
                          +---------------- ROOM_TTL_S 경과 -----------------+--> expired --TTL 삭제--> (없음)
```

**만료는 연장하지 않는다.** `ROOM_TTL_S`(3600초)는 생성 시점부터 고정이다. 활동으로 연장하면 "방이 언제 사라지는가" 를 아무도 답할 수 없다. 연결 수립 뒤에는 제어 평면이 필요 없으므로(NFR-3) 이 값은 **방 코드가 유효한 기간**이고 세션 길이와 무관하다.

**한 시간이 덮는 것과 덮지 않는 것을 나눠 적는다.** 3600초는 사람이 방 코드를 전달하고
참가자가 클라이언트를 켜기까지의 여유다. **양쪽이 등록을 마치기까지의 여유는 이 값이 아니라
[`protocol.md`](protocol.md) 11장의 `get_peers` 마감이다.** 먼저 켠 쪽은 자기
`register_candidate` 성공 시점부터 그 마감 안에 상대의 등록을 봐야 하고, 넘기면 방이 아직
살아 있어도 `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다(9.6). 자동 재시도는 미정이므로
([`protocol.md`](protocol.md) 10.4) 그 뒤는 사람이 다시 띄운다. 방이 살아 있으므로 재참가로
같은 `peer_id` 와 가상 IP 를 돌려받는다(4.3). **두 값의 역할이 다르다는 것을 시연 대본에
반영한다.** 먼저 켠 쪽이 1분 안에 실패하는 것은 제어 평면 장애가 아니다. 30분 게임 뒤 재참가가 필요해지면 만료된 방이라 `room_expired` 를 받고 새 방을 만든다. v1 이 수용하는 한계이고, 자동 재시도를 정할 때([`protocol.md`](protocol.md) 10.4 미정 항목) 이 값을 다시 본다.

**연산별 허용 상태.**

| 연산 | `waiting` | `ready` | `expired` | (없음) |
|------|-----------|---------|-----------|--------|
| `create_room` | 같은 nonce 면 기존 방(4.2) | 같음 | 같은 nonce 면 `room_expired`(4.2) | 생성 |
| `join_room` 새 참가 | 선점 시도 | 선점 시도. 주소가 전부 선점됐을 것이므로 `room_full` | `room_expired` | `room_not_found` |
| `join_room` 재참가 | 토큰 검사 후 반환 | 같음 | `room_expired` | `room_not_found` |
| `register_candidate` | 저장. 준비 판정 | 저장. 준비 판정은 이미 참 | `room_expired` | `room_not_found` |
| `get_peers` | `ready: false` | 준비 완료 응답 | `room_expired` | `room_not_found` |

**만료 판정 케이스 표.** `now` 는 서버 벽시계 밀리초, `expires_at_ms` 는 저장값이다.

| `now` 와 `expires_at_ms` | 판정 |
|--------------------------|------|
| `now < expires_at_ms` | 살아 있음 |
| `now == expires_at_ms` | **만료.** 경계는 만료 쪽이다. `expires_in_s` 가 0 인 방은 참가할 수 없다 |
| `now > expires_at_ms` | 만료 |
| `expires_at_ms` 필드 없음 | **`internal`.** 판정 불가를 통과로 바꾸지 않는다. 생성 경로가 항상 넣는 필드이므로 없으면 저장소가 손상된 것이다 |

`expires_in_s` 는 `max(0, ceil((expires_at_ms - now) / 1000))` 이다. **살아 있는 방에서는 1 이상이다.** 1ms 라도 남았으면 올림이 1 을 만든다. **0 은 만료를 뜻한다.** 위 경계 행과 같은 말이다. 클라이언트는 이 값을 표시에만 쓰고 판정에 쓰지 않는다.

### 5.2 준비 완료

`ready_at_wall_ms` 는 **한 번 기록되면 방이 사라질 때까지 바뀌지 않는다.** 재참가가 후보를 지워도, 어느 피어가 후보를 다시 등록해도 그대로다. 근거는 4.3 과 4.5 에 있다.

### 5.3 피어

| 상태 | 정의 |
|------|------|
| `joined` | `PEER#` 항목이 있고 `candidates` 가 비어 있다 |
| `registered` | `candidates` 가 1개 이상 |

```text
(없음) --create_room / join_room 새 참가--> joined --register_candidate--> registered
                                              ^                              |
                                              +---- join_room 재참가 (후보를 지운다) ----+
```

피어는 방과 함께 사라진다. 피어만 지우는 연산은 없다. `leave_room` 을 두지 않는 이유는 방 수명이 짧고(5.1) 자리 회수가 재참가 계약(2.5)과 충돌하기 때문이다.

## 6. 저장

### 6.1 저장 계약

상태는 Amazon DynamoDB 에 둔다. **왜 DynamoDB 이고 무엇을 버렸는지는** [ADR 0004](decisions/0004-상태-저장소-dynamodb.md)가 갖는다. 계약은 다섯이다.

| 계약 | 내용 |
|------|------|
| 저장 1 | 읽은 값으로 판정하는 읽기는 **테이블에 `ConsistentRead=true`** 를 건다. 저장 5 때문에 **연산이 방·피어 항목을 읽는 모든 자리가 여기에 해당한다.** `get_peers` 만이 아니다. 기본 읽기는 최종 일관성이라([ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 1 의 AWS 문서 인용) 방금 등록된 후보가 빠질 수 있고, 그러면 펀칭이 `HOLE_PUNCH_TIMEOUT` 으로 끝나 **NAT 실패로 위장한다** |
| 저장 2 | 강한 일관성 읽기는 테이블과 LSI 에서만 된다. **GSI 를 만들지 않는다.** 이 설계에는 GSI 가 필요한 조회가 없다 |
| 저장 3 | 가상 IP 배정은 아이템 하나를 키로 두고 **조건부 쓰기(`attribute_not_exists`)로 선점**한다. 원자적 카운터를 쓰지 않는다. 그것은 멱등하지 않아 재시도가 주소를 건너뛴다. 선점에 실패하면 다음 후보 주소로 넘어가고, 풀을 한 바퀴 돌면 `room_full` 로 끝낸다(2.5). 무한히 돌지 않는다 |
| 저장 4 | 방 만료 **판정은 애플리케이션이 한다**(5.1). TTL 은 저장 공간 회수 수단이며, 만료 시각이 지난 항목도 삭제 전까지 조회에 보인다 |
| 저장 5 | 제어 서버는 방·피어 상태를 **메모리에 들고 있지 않는다.** 요청마다 DynamoDB 에서 읽는다 |

**저장 5 때문에 "재시작 복원" 절차가 없다.** 기동 시 방 목록을 읽어 들이는 단계가 없고, 재시작 직후의 첫 요청이 평소와 똑같이 읽는다. [`spec.md`](spec.md) NFR-3 이 요구하는 재시작 후 방 상태 유지는 **복원 절차가 아니라 이 계약으로 성립한다.** 캐시를 두면 그 캐시가 최종 일관성 읽기와 같은 문제를 다시 만들므로, 캐시가 필요해지면 저장 1 과 함께 다시 정한다.

**저장 5 의 예외는 속도 제한 표(6.4)와 처리 중 요청 수(7.2)다.** 둘은 방·피어 상태가 아니라 서버 프로세스의 자기 보호 상태다. 재시작하면 사라지고, 사라져도 잃는 것은 재시작 직후 잠깐의 보호뿐이다. 이 둘 외에 메모리에 두는 상태를 만들지 않는다.

### 6.2 테이블

**테이블 하나다.** 이름은 배포 설정(7.6)이 정하고 코드에 박지 않는다.

| 항목 | 값 |
|------|-----|
| 파티션 키 | `pk` (문자열). 값은 `room_id` |
| 정렬 키 | `sk` (문자열). 항목 종류와 식별자 |
| TTL 속성 | `ttl` (숫자, epoch 초). 6.5 |
| 용량 모드 | [ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 4. provisioned. 값은 배포 설정 |
| 인덱스 | 없음 (저장 2) |

방에 속한 항목(`ROOM`, `PEER#`, `VIP#`)은 같은 파티션 키를 가지므로 방 하나의 전체 상태를 `Query(pk = room_id, ConsistentRead=true)` 하나로 읽는다. 항목 수는 `1 + MAX_PEERS × 2` 이하다(`ROOM` 하나, 피어마다 `PEER#` 와 `VIP#`). v1 에서 최대 5개다. **`NONCE#` 항목은 파티션 키가 다르다.** `create_room` 의 멱등성 조회는 `room_id` 를 아직 모르는 시점에 nonce 만으로 찾아야 하기 때문이다.

### 6.3 항목

| `sk` | 속성 | 뜻 |
|------|------|-----|
| `ROOM` | `created_at_ms`, `expires_at_ms`, `host_peer_id`, `ttl` | 방. 아래 준비 완료 속성은 처음엔 없다 |
| `ROOM` (준비 완료 뒤) | 위에 더해 `ready_at_wall_ms`, `ready_at_mono_ns`, `ready_boot_id`, `punch_delay_ms` | 7.4 가 세 시계 값을 쓴다 |
| `PEER#<peer_id>` | `peer_id`, `peer_token`, `virtual_ip`, `candidates`(리스트), `client_nonce`, `joined_at_ms`, `ttl` | 피어. `peer_id` 는 `sk` 에서 10진수로 적는다. `peer_token` 은 원문이다(2.3) |
| `VIP#<virtual_ip>` | `peer_id`, `ttl` | 가상 IP 선점 표식. `<virtual_ip>` 는 점 십진 |
| (pk = `NONCE#<client_nonce>`, sk = `NONCE`) | `room_id`, `peer_id`, `ttl` | 멱등성 키 → 방과 피어 대응. **pk 가 방이 아니라 nonce 다** |

토큰 비교는 상수 시간 비교(`hmac.compare_digest`)로 한다. 조건식에 넣는 비교(`peer_token = :t`)는 DynamoDB 가 하므로 상수 시간을 주장하지 않는다. 그래서 토큰이 필요한 연산은 **먼저 `PEER#` 를 읽어 애플리케이션에서 상수 시간 비교를 하고**, 조건식의 `peer_token = :t` 는 읽기와 쓰기 사이에 값이 바뀌지 않았음을 확인하는 용도다.

**쓰기는 전부 조건부이고, 여러 항목을 함께 쓰는 자리는 `TransactWriteItems` 다.** 하나라도 조건이 실패하면 전부 취소된다.

| 연산 | 쓰기 | 조건 |
|------|------|------|
| `create_room` | 트랜잭션: `ROOM` put, `PEER#host` put, `VIP#10.100.0.1` put, `NONCE#` put | **네 put 전부 `attribute_not_exists(pk)`** 다. `ROOM` 실패는 `room_id` 충돌 → 재추첨(2.1). `NONCE#` 실패는 동시에 같은 nonce 가 들어온 것이므로 다시 읽어 그 결과를 돌려준다. `PEER#`·`VIP#` 는 `ROOM` 이 없으면 있을 수 없으므로 실패가 나면 저장소가 앞선 방의 항목을 일부만 지운 상태다. 그때는 `internal` 이고 재추첨하지 않는다 |
| `join_room` 새 참가 | 풀의 주소마다 트랜잭션: `ROOM` **ConditionCheck**, `VIP#<ip>` put, `PEER#<peer_id>` put, `NONCE#` put | `ROOM` 에 `attribute_exists(pk) AND expires_at_ms > :now`. 사전 읽기와 쓰기 사이에 방이 만료되거나 삭제되는 경합을 막는다. `VIP#` 와 `PEER#` 와 `NONCE#` 각각 `attribute_not_exists(pk)`. 실패 처리는 아래 취소 사유 표 |
| `join_room` 재참가 | `PEER#` update: `candidates = []` | `attribute_exists(pk) AND peer_token = :t`. 실패는 `unauthorized` |
| `register_candidate` | `PEER#` update: `candidates = :list` | `attribute_exists(pk) AND peer_token = :t` |
| 준비 완료 기록 | `ROOM` update: `ready_at_wall_ms`, `ready_at_mono_ns`, `ready_boot_id`, `punch_delay_ms` | `attribute_not_exists(ready_at_wall_ms)`. 실패는 오류가 아니다(4.4) |

**트랜잭션이 취소되면 취소 사유를 항목별로 읽고 아래 우선순위로 판정한다.** `TransactionCanceledException` 의 `CancellationReasons` 는 트랜잭션에 넣은 항목과 **같은 위치**에 하나씩 나온다. 그래서 위치로 항목을 식별하고, 판정 순서는 위치가 아니라 아래 표다. 여러 항목이 동시에 실패할 수 있으므로 어느 것을 먼저 보는지가 응답을 정한다.

| 순서 | 실패한 조건 | 동작 |
|:----:|-------------|------|
| 1 | `NONCE#` | **다른 사유가 무엇이든** 같은 nonce 의 요청이 먼저 성립한 것이다. `NONCE#` 를 다시 읽어 그 `room_id`·`peer_id` 로 방을 `Query` 하고 같은 응답을 돌려준다. 그 방이 만료됐으면 `room_expired` 다(4.2). `room_full` 이나 재추첨으로 가지 않는다. **다시 읽은 `room_id` 가 요청의 방과 다르면 `bad_request`** 다. nonce 를 다른 방에 재사용한 것이고, 사전 읽기 경로가 같은 입력에 내는 답과 같아야 한다 |
| 2 | `ROOM` ConditionCheck (`join_room`) | 방을 다시 읽는다. 없으면 `room_not_found`, 있으면 `room_expired`. 다음 주소로 넘어가지 않는다 |
| 3 | `VIP#` | 다음 주소. 풀이 끝나면 `room_full` |
| 4 | `PEER#` | `peer_id` 재추첨. 상한은 `MAX_PEER_ID_ATTEMPTS` |
| 5 | `ROOM` put (`create_room`) | `room_id` 재추첨. 상한은 `MAX_ROOM_ID_ATTEMPTS` |
| - | 조건 실패가 아닌 사유 (`TransactionConflict`, 스로틀) | `internal`. 클라이언트가 8.3 대로 재시도한다 |

1번이 앞인 이유는 재시도 시나리오다. 응답을 잃은 참가자가 같은 nonce 로 다시 왔을 때 첫 요청이 이미 `VIP#` 를 선점했으면 `VIP#` 와 `NONCE#` 가 **같은 트랜잭션에서 함께** 실패한다. `VIP#` 를 먼저 보면 다음 주소로 넘어가 `room_full` 을 돌려주고, 그 클라이언트는 자기가 이미 들어간 방에 못 들어갔다고 믿는다.

**단일 항목 update(재참가, `register_candidate`, 준비 완료 기록)는 방 생존을 조건에 넣지 않는다.** 7.3 의 순서대로 만료를 먼저 판정한 뒤 쓰므로, 걸리는 것은 읽기와 쓰기 사이 수십 ms 안에 방이 만료되는 경합뿐이다. **그 경합은 허용한다.** 그 결과를 정확히 적는다. **현재 요청은 `ok` 를 받을 수 있다.** `register_candidate` 라면 `accepted` 와 `ready` 까지 정상 값으로 돌아온다. 갱신된 항목은 만료된 방 안에 있고, 그 방을 읽는 **이후의** 모든 연산이 7.3 의 6번에서 `room_expired` 로 끝나므로, 갱신된 값이 실리는 응답은 그 요청 하나뿐이다. 클라이언트는 다음 요청(대개 `get_peers` 폴링)에서 `room_expired` 를 받고 `CONTROL_PLANE_EXCHANGE_FAILED` 로 끝난다. 응답 직전에 만료를 다시 검사하지 않는다. 검사해도 그 검사와 응답 사이에 같은 경합이 있다. 새 참가만 조건에 넣는 이유는 그 경합이 `VIP#`·`NONCE#` 항목을 **만료된 방에 새로 만들고** 그 항목의 `ttl` 을 방 값에서 파생시켜야 하는데 방이 이미 없을 수 있기 때문이다.

**조건이 실패해도 쓰기 용량을 쓴다** ([ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 2). 그래서 새 참가는 풀을 돌기 **전에** 방을 읽어 만료와 존재를 먼저 확인하고, 풀 크기가 곧 시도 상한이다.

**읽기.**

| 연산 | 읽기 |
|------|------|
| `create_room` | `NONCE#` GetItem (멱등성). 있으면 그 `room_id` 로 `Query` 해 같은 응답을 조립 |
| `join_room` 새 참가 | `NONCE#` GetItem → 있으면 저장된 `room_id` 가 요청과 같아야 한다(다르면 `bad_request`. nonce 를 다른 방에 재사용한 것이다) → 없으면 `ROOM` GetItem (만료·존재) → 트랜잭션 |
| `join_room` 재참가 | `ROOM` GetItem → `PEER#` GetItem (토큰 검사) → update |
| `register_candidate` | `Query(pk)` 로 `ROOM` 과 `PEER#` 전부 (만료·토큰 검사) → `PEER#` update → **`Query(pk)` 를 다시 읽어** 준비 판정 (4.4). 읽기가 두 번인 이유는 그 절에 있다 |
| `get_peers` | `Query(pk)` 한 번. `ROOM` 과 `PEER#` 전부가 나온다. 토큰 검사도 그 결과로 한다 |

전부 `ConsistentRead=true` 다(저장 1). **재참가에서 `PEER#` 를 GetItem 으로 읽는 것은 `peer_id` 를 요청이 주기 때문이다.** 토큰만으로 피어를 찾는 형식을 두지 않은 이유가 그것이다. 토큰으로 찾으려면 피어 전부를 읽어 대조해야 한다.

### 6.4 속도 제한

**출발지 IP 별로 실패 응답에 예산을 둔다.** 세는 것은 `room_not_found`, `room_expired`, `unauthorized` 셋이다. 성공과 `bad_request` 는 세지 않는다. `bad_request` 는 추측과 무관한 형식 오류이고, 성공을 세면 정상 폴링이 걸린다.

| 항목 | 값 |
|------|-----|
| 예산 | 출발지 IP 당 토큰 `RATE_LIMIT_BUCKET`(10). 위 세 오류가 한 번 나갈 때마다 하나 쓴다 |
| 보충 | 분당 `RATE_LIMIT_REFILL_PER_MIN`(10). **연속형이다.** 마지막 보충 시각으로부터 6초가 지날 때마다 1개씩 차고 상한은 `RATE_LIMIT_BUCKET`(10)이다. **기준 시각은 보충이 일어난 시각만 갱신한다.** 토큰 소모도, `rate_limited` 응답도 그 시각을 바꾸지 않는다. 소모가 기준을 미루면 계속 쓰는 출발지의 보충이 영원히 늦어지고, `rate_limited` 가 미루면 공격자가 두드리는 것만으로 쿨다운을 연장한다. 60초에 10개를 한꺼번에 채우지 않는다. 일괄 보충은 예산이 빈 구간을 최대 1분으로 늘려 정상 클라이언트의 한 번뿐인 실패 응답이 오래 막힌다 |
| 소진 시 | **요청을 처리하지 않고** `rate_limited`. 저장소를 읽지 않는다. 그래야 제한이 저장소 비용도 막는다 |
| 표 | 메모리. 출발지 IP → (토큰, 마지막 보충 시각). 상한 `MAX_RATE_ENTRIES`(4096) |
| 항목 생성 | **토큰을 쓸 때만 만든다.** 조회만 하고 만들지 않는다. 항목이 없는 출발지는 토큰이 가득한 것과 같다 |
| 항목 제거 | **보충으로 토큰이 상한에 닿으면 지운다.** 가득 찬 항목은 없는 것과 판정이 같으므로 들고 있을 이유가 없다. 제거 규칙이 없으면 표가 단조 증가해 4096 개를 채운 뒤 새 출발지가 재시작까지 제한을 받지 않는다 |
| 표가 찼을 때 | **새 출발지를 제한하지 않고 통과시킨다.** 그리고 `rate_table_full` 카운터를 올린다. 가장 오래된 항목을 밀어내면 많은 IP 를 가진 공격자가 표를 채워 진짜 추측자의 항목을 밀어낸다. 통과시키면 공격자는 표를 채우는 것으로 얻는 것이 없다. 대가는 표가 찬 동안 새 출발지에 제한이 없는 것이고, 이 값이 오르면 상한을 다시 본다 |
| 예산 검사 시점 | 요청을 파싱한 **뒤**, 저장소를 읽기 **전** |

**보충 시각의 기준은 마지막 보충이고, `rate_limited` 응답은 그것을 갱신하지 않는다.** 갱신하면 공격자가 계속 두드리는 것만으로 쿨다운을 영구히 연장해 같은 출발지의 정상 사용자를 영원히 막을 수 있다. [`protocol.md`](protocol.md) 9.5 가 재협상 쿨다운에 같은 규칙을 둔 이유와 같다.

**막는 것이 아니라 느리게 하는 것이다. 얼마나 느려지는지를 적는다.**

| 무엇 | 값 |
|------|-----|
| 한 IP 로 30비트 공간(2^30) 전체 | 분당 10회면 약 **204년**. `2^30 / 10 / 60 / 24 / 365` |
| 살아 있는 방 하나를 맞히기까지 | 그 시점에 열린 방이 `N` 개면 기대 시도 수가 `2^30 / N` 이다. 2.1 이 상정한 "열린 방 수십 개" 규모(`N` = 50)면 한 IP 로 약 **4년** |
| IP 가 여럿이면 | 그만큼 나뉜다. IP 100 개면 위 값의 1/100 이다 |

만료된 방도 `room_expired` 로 존재를 알려 주므로(4.1) 표적은 살아 있는 방만이 아니다.
**이 수치는 보호의 크기가 아니라 한계의 크기다.** 1.2 의 마지막 줄이 그 한계다.

**케이스 표.**

| 순서 | 입력 (같은 출발지) | 응답 | 남은 토큰 |
|:----:|--------------------|------|:---------:|
| 1~10 | 없는 방 `join_room` 10회 | `room_not_found` 10회 | 0 |
| 11 | 없는 방 `join_room` | **`rate_limited`.** 저장소 읽기 없음 | 0 |
| 12 | 있는 방에 정상 `get_peers` | **`rate_limited`.** 예산은 출발지 단위라 정상 요청도 막힌다 | 0 |
| 13 | 11번 응답으로부터 6초 뒤, 없는 방 `join_room` | 토큰 1 보충 후 소모. `room_not_found` | 0 |
| 14 | 13번의 **보충 시각**으로부터 70초 뒤 (그 사이 아무 요청 없음) | 토큰이 상한 10 에 닿아 **항목이 지워진다.** 그 뒤 첫 요청은 항목이 없는 출발지로 처리된다 | - |
| - | 다른 출발지에서 없는 방 `join_room` | `room_not_found`. 표가 출발지별이다 | 그 출발지 9 |
| - | 정상 `get_peers` 100회 (성공) | 전부 처리 | 10. 성공은 세지 않는다 |
| - | `bad_request` 100회 | 전부 `bad_request` | 10. 세지 않는다 |

**14번이 60초가 아니라 70초인 이유.** 상한 10 에 닿는 데 드는 시간이 정확히 60초라, 60초를
기대값으로 적으면 시계 해상도와 측정 시점에 따라 9개에서 멈춘 구현과 10개를 채운 구현이
갈린다. 경계를 판정에 쓰지 않는다. 경계 자체를 보려면 "60초 직전에는 지워지지 않는다" 를
별도 행으로 둔다.

12번 줄이 뜻하는 것을 적는다. **같은 NAT 뒤의 두 사용자가 공인 IP 를 공유하면 한 사람의 추측이 다른 사람의 정상 요청을 막는다.** 캠퍼스망이 그렇다. 정상 클라이언트는 한 기동에 실패 응답을 한두 번 받고 끝나므로 예산 10 은 그 경우를 덮지만, 옆 사람이 예산을 태우면 막힌다. v1 이 수용하는 한계다. 대안(토큰 있는 요청은 세지 않기)은 `unauthorized` 추측을 열어 두므로 쓰지 않는다.

### 6.5 TTL

| 항목 | `ttl` 값 |
|------|----------|
| 방의 모든 항목 (`ROOM`, `PEER#`, `VIP#`, `NONCE#`) | `floor(expires_at_ms / 1000) + STORAGE_GRACE_S` |

같은 방의 항목은 같은 `ttl` 을 갖는다. 방이 만료된 뒤 하루가 지나면 DynamoDB 가 지운다. **하루의 여유를 두는 이유는 만료 판정이 저장 4 대로 애플리케이션 몫이기 때문이다.** 만료 직후 항목이 지워지면 `room_expired` 와 `room_not_found` 의 구분(4.1)이 삭제 시점에 따라 흔들린다. 하루 뒤에는 어느 쪽으로 답하든 상관없는 시점이다. AWS 문서가 삭제 지연을 "within a few days" 로만 적고 상한을 정하지 않는다는 것은 [ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 3 과 "확인하지 못한 것" 1번에 있다.

## 7. 서버 구현

### 7.1 모듈

| 모듈 | 책임 | 외부 의존 |
|------|------|-----------|
| `server.py` | 수락 루프, 3.3 HTTP 파싱과 응답 직렬화, 연산 디스패치, 시간 제한, `MAX_INFLIGHT`, 속도 제한 표(6.4) | `asyncio` |
| `ops.py` | 4장의 연산 넷. 요청 검증, 상태 판정(5장), 응답 조립 | 없음 |
| `ids.py` | `room_id`, `peer_id`, `peer_token` 생성과 정규화. 2.1 알파벳과 케이스 표가 여기 시험으로 붙는다 | `secrets` |
| `candidates.py` | 4.4 위생. 후보 형식 검사와 10.1 규칙 | `ipaddress` 는 쓰지 않는다. 아래 |
| `clock.py` | 7.4 의 세 시계 값 | `time`, `/proc/sys/kernel/random/boot_id` |
| `store.py` | `boto3` 호출 전부. 6.3 의 조건식이 **이 파일에만** 있다 | `boto3` |

**`ipaddress` 모듈로 후보를 판정하지 않는다.** 이 레포의 Python 3.11 에서 확인한 값으로 `ip_address('127.0.0.1').is_private` 와 `ip_address('192.0.2.1').is_private` 가 참이고 `ip_address('224.0.0.1').is_global` 도 참이다. 버전에 따라 다를 수 있으므로 어느 버전에서도 그 술어에 판정을 맡기지 않는다. 4.4 케이스 표의 판정은 옥텟 4개를 직접 파싱해 앞 옥텟과 범위로 가른다. 파싱은 `^\d{1,3}(\.\d{1,3}){3}$` 에 각 옥텟 0~255, **선행 0 거부**다. `ipaddress.IPv4Address` 를 형식 파싱에만 쓰는 것은 된다. 판정에 그 술어를 쓰지 않는다는 뜻이다.

`asyncio` 와 `json` 은 표준 라이브러리다. `boto3` 는 [`spec.md`](spec.md) NFR-5 승인을 받았다. 웹 프레임워크는 쓰지 않는다(3.1).

### 7.2 요청 처리 한 바퀴

```text
on_connection(reader, writer):
    src = peer IP
    if inflight >= MAX_INFLIGHT:
        counters.unavailable += 1
        respond(503, unavailable); close; return          # 저장소를 건드리지 않는다
    inflight += 1
    try:
        req = await wait_for(read_request(reader), SERVER_READ_TIMEOUT_S)
                                                          # 3.3 케이스 표. 실패는 여기서 4xx 로 끝난다
        if rate.exhausted(src):                           # 6.4. 파싱 뒤, 저장소 전
            counters.rate_limited += 1
            respond(429, rate_limited); return
        result = await to_thread(ops.dispatch, req)       # boto3 는 블로킹이다. 스레드로 보낸다
        if result.error in {room_not_found, room_expired, unauthorized}:
            rate.spend(src)                               # 6.4 가 세는 셋
        respond(result)
    except TimeoutError:
        counters.http_read_timeout += 1; close            # 응답 없음 (3.4)
    except Exception:
        counters.internal_error += 1
        respond(500, internal)                            # 예외 내용을 본문에 싣지 않는다
    finally:
        inflight -= 1; close
```

**`boto3` 호출은 블로킹으로 취급한다.** 이벤트 루프 스레드에서 직접 부르면 DynamoDB 응답 지연 동안 다른 연결의 수락과 파싱이 멈춘다. `asyncio.to_thread` 로 보낸다. 동시 처리 상한 `MAX_INFLIGHT`(32)는 그 스레드 풀이 무한히 자라는 것과, 저장소가 느려질 때 대기 요청이 쌓여 메모리를 먹는 것을 막는다. 넘치면 `unavailable` 이고 클라이언트는 8.3 대로 재시도한다.

**한 프로세스, 이벤트 루프 하나, 스레드 풀 하나다.** 멀티프로세스를 두지 않는다. 두면 속도 제한 표(6.4)가 프로세스마다 따로 생겨 예산이 프로세스 수만큼 늘어난다.

### 7.3 연산 처리 순서

`ops.dispatch` 안의 공통 순서다. 연산마다 이 순서를 지킨다. 순서를 바꾸면 케이스 표의 응답이 달라진다.

```text
1. 필드 존재와 형 검사 (4장 표)             -> 실패: bad_request
2. room_id 정규화 (2.1)                     -> 실패: bad_request
3. 연산별 필드 조합 검사 (4.3 두 형식)       -> 실패: bad_request
4. 저장소 읽기 (6.3 읽기 표, ConsistentRead)
5. 방 존재                                  -> 없음: room_not_found
6. 방 만료 (5.1 케이스 표)                  -> 만료: room_expired
7. 토큰 검사 (필요한 연산만)                 -> 실패: unauthorized
8. 연산 본체 (조건부 쓰기, 준비 판정)
9. 응답 조립
```

**형식 검사가 저장소 읽기보다 먼저다.** 그래야 `bad_request` 가 저장소 비용을 쓰지 않고, 속도 제한(6.4)이 형식 오류를 세지 않아도 추측 공격이 저장소에 닿지 않는다. **만료가 토큰보다 먼저다.** 만료된 방에 토큰이 틀린 요청은 `room_expired` 다. 만료된 방은 어차피 쓸 수 없으므로 토큰 유무를 알려 줘도 잃는 것이 없고, 순서를 못박아야 케이스 표가 결정적이다.

### 7.4 시계

`elapsed_since_ready_ms` 는 **단조 시계로 계산한다** ([`protocol.md`](protocol.md) 14장 계약 4). 벽시계로 계산하면 NTP 가 시각을 건너뛰는 순간 두 피어가 받는 값이 어긋나 10.2 의 오차 상한이 깨진다. 그런데 저장 5 때문에 서버는 메모리에 준비 완료 시각을 들고 있지 않고, 단조 시계 값은 부팅마다 기준이 다르다. 그래서 세 값을 함께 저장한다.

| 저장값 | 출처 | 용도 |
|--------|------|------|
| `ready_at_mono_ns` | `time.monotonic_ns()`. **전제는 배포 환경(Linux)에서 이것이 시스템 전체 시계(`CLOCK_MONOTONIC`)여서 프로세스 재시작에 기준이 바뀌지 않는다는 것이다.** 아래 참조 | 같은 부팅 안의 경과 계산 |
| `ready_boot_id` | `/proc/sys/kernel/random/boot_id` 내용. **전제는 이 값이 부팅마다 바뀐다는 것이다** | 위 값이 같은 기준인지 판정 |
| `ready_at_wall_ms` | `time.time()` 밀리초 | 부팅이 바뀌었을 때의 대체, 그리고 5.1 의 준비 완료 존재 판정 |

```text
elapsed_since_ready_ms(room):
    if room.ready_boot_id == current_boot_id:
        d = (monotonic_ns() - room.ready_at_mono_ns) // 1_000_000
        source = "mono"
    else:
        d = wall_ms() - room.ready_at_wall_ms                # 인스턴스가 재부팅됐다
        source = "wall"
        counters.elapsed_wall_fallback += 1
    return max(0, d)
```

**케이스 표.**

| 상황 | 계산 | 결과 |
|------|------|------|
| 같은 부팅, 프로세스 재시작 없음 | 단조 | 정확 |
| 같은 부팅, 프로세스 재시작 | 단조. `CLOCK_MONOTONIC` 은 프로세스와 무관하다 | 정확 |
| 인스턴스 재부팅 뒤 | 벽시계 대체 | NTP 스텝만큼 틀릴 수 있다. **이 경우 [`protocol.md`](protocol.md) 10.2 의 오차 상한은 보장되지 않는다.** 14장 계약 4 가 그 예외를 이 문서에 위임한다. 준비 완료와 폴링 응답 사이 몇 초 안에 재부팅과 시각 조정이 겹쳐야 하므로 드물다. 카운터로 관측한다 |
| 벽시계 대체에서 음수 | `max(0, ...)` | 0. 클라이언트는 `punch_delay_ms` 를 다 기다린다 |
| `boot_id` 파일이 없다 (Linux 가 아니다) | 프로세스 시작 시 뽑은 난수를 `boot_id` 로 쓴다 | 프로세스 재시작마다 벽시계 대체로 떨어진다. 로컬 시험에서 그렇다. **배포 대상은 Linux 다** |

**두 전제는 이 레포에서 확인하지 않았다.** 이 기기는 Windows 이고 `time.get_clock_info('monotonic')` 이 `GetTickCount64()` 를 돌려준다. 배포 인스턴스에서 같은 호출로 구현이 `clock_gettime(CLOCK_MONOTONIC)` 인지 확인하고, 재부팅 전후의 `boot_id` 가 다른지 확인하는 것이 [`roadmap.md`](roadmap.md) Phase 3 의 착수 전 항목이다. 확인 전에는 이 절이 **설계이지 검증된 동작이 아니다.** 어느 쪽이든 어긋나면 벽시계 대체로 떨어지므로 틀린 값이 아니라 정확도를 잃는다.

### 7.5 로그와 카운터

표준 오류에 한 줄 한 이벤트. 클라이언트 로그 계약([`architecture.md`](architecture.md) 9장)과 같은 모양 `<수준> <이벤트키> <이름>=<값> ...` 을 쓴다. Phase 3 검증이 찾는 키는 다음이다.

| 이벤트키 | 필수 필드 | 어느 검증이 쓰는가 |
|----------|-----------|--------------------|
| `http.request` | `op`, `status`, `error`(성공이면 `-`), `src`, `ms` | 모든 연산 검증. **`peer_token`, 본문, `room_id` 를 싣지 않는다.** 방 코드가 로그에 남으면 로그 열람이 곧 방 탈취다 |
| `room.created` | `peer_id`, `virtual_ip` | 가상 IP 배정 검증. `room_id` 는 싣지 않는다 |
| `room.ready` | `peer_id` (준비 완료를 확정시킨 등록의 피어), `punch_delay_ms` | 준비 완료 1회 기록 검증. 방마다 **정확히 한 번** 나와야 한다. 방이 둘 이상인 로그에서 줄을 가르려면 `peer_id` 가 있어야 한다 |
| `vip.claimed` | `virtual_ip`, `peer_id` | 동시 참가 중복 배정 검증 |
| `counter` | `name`, `value` | 아래 카운터 |

카운터는 `http_read_timeout`, `internal_error`, `rate_limited`, `rate_table_full`, `elapsed_wall_fallback`, `unavailable` 이다. 종료 시와 60초마다 전량을 낸다. 값이 0 인 것도 낸다.

**`room_id` 를 로그에 싣지 않는 것을 다시 적는다.** `http.request` 의 `op` 와 `status` 만으로 Phase 3 검증은 충분하다. 어느 방인지가 필요한 진단은 `peer_id` 로 한다. `peer_id` 는 방 안에서만 뜻이 있어 그것만으로는 참가할 수 없다.

### 7.6 설정과 배포

설정은 환경 변수다. 파일을 두지 않는다. 값이 넷뿐이다.

| 변수 | 뜻 | 기본값 |
|------|-----|--------|
| `SANGTACHI_CP_PORT` | bind 포트 | `8000` |
| `SANGTACHI_CP_TABLE` | DynamoDB 테이블 이름 | 없음. **필수** |
| `AWS_REGION` | 리전 | 없음. 필수. `boto3` 표준 변수 |
| `SANGTACHI_CP_ENDPOINT` | DynamoDB 엔드포인트 URL 덮어쓰기. 로컬 시험용 | 없음. 없으면 리전 기본 |

**자격 증명 변수는 없다.** EC2 에서는 IAM 역할이고([ADR 0004](decisions/0004-상태-저장소-dynamodb.md) 결정 5), 로컬 시험은 DynamoDB local 이라 자격 증명이 필요 없다. 액세스 키를 받는 변수를 두면 누군가 그것을 쓴다.

배포는 **systemd 서비스 하나**다. `Restart=always`. 재시작 복원 절차가 없으므로(6.1) 재시작이 싸다. 보안 그룹은 인바운드 TCP 8000 을 연다. 텔레메트리 서비스의 포트는 이 문서 범위 밖이고 [`roadmap.md`](roadmap.md) Phase 9 착수 전 항목이다. **유닛 파일과 배포 명령은 여기 두지 않는다.** 아직 실행하지 않은 절차를 문서에 두지 않는다는 규칙 때문이고, Phase 3 에서 실제로 배포한 뒤 그 절차를 도구로 넣고 문서는 가리킨다.

**로컬 시험의 한계.** DynamoDB local 은 읽기가 대개 최신 값처럼 보여 `ConsistentRead` 누락이 드러나지 않고, `TransactionConflictException` 도 나지 않는다. 둘 다 [ADR 0004](decisions/0004-상태-저장소-dynamodb.md) "치르는 것" 절이 AWS 문서를 인용해 적었다. 저장 1 은 코드를 읽어 판정하고, 트랜잭션 충돌 경로는 실제 테이블에서 확인한다.

## 8. 클라이언트 쪽 계약

### 8.1 소유 스레드

제어 평면 TCP 호출과 DNS 해석은 **`[control]` 스레드**가 한다. 스레드 구성, `[loop]` 와의 큐, 종료 순서는 [`architecture.md`](architecture.md) 3.2.8 이 소유한다. 여기서는 그 스레드가 이 문서의 어느 규칙을 지키는지만 적는다.

`[loop]` 에 넣지 않는 이유는 한 줄이다. 제어 서버가 응답하지 않으면 연결 시간 제한을 걸지 않은 TCP `connect` 가 OS 기본 재시도 동안 길게 블록되고, 그동안 `HELLO` 재전송과 keepalive 가 멈춘다. 그것은 [`spec.md`](spec.md) NFR-3 위반이다.

### 8.2 시간 제한

| 단계 | 값 | 넘기면 |
|------|-----|--------|
| DNS 해석 (`getaddrinfo`) | OS 기본. **별도 제한을 걸지 않는다.** 동기 호출에 시간 제한을 거는 수단을 이 설계는 쓰지 않는다 | `[control]` 이 그만큼 블록된다. `[loop]` 는 영향 없다 |
| `connect` | `CLIENT_CONNECT_TIMEOUT_S`(3). 논블로킹 `connect` + `select` | 전송 오류 |
| 송신, 수신 각각 | `CLIENT_IO_TIMEOUT_S`(3). `SO_SNDTIMEO` / `SO_RCVTIMEO`. [`architecture.md`](architecture.md) 3.2.7 의 텔레메트리 소켓과 같은 옵션이고 같은 한계(연산별이라 합이 더 길 수 있다)가 있다 | 전송 오류 |
| 요청 한 건 상한 | 위 셋의 합. **DNS 를 빼고 최대 9초** | - |

**DNS 해석은 기동 시 한 번만 한다.** 결과 IPv4 주소를 `[control]` 이 들고 그 뒤의 모든 요청에 쓴다. 폴링마다 해석하면 DNS 장애가 폴링을 멈춘다. 주소가 기동 중에 바뀌지 않는다는 전제는 Elastic IP 에서 오고, 그 근거와 대가는 [`windows-prereq.md`](windows-prereq.md) 10절이 갖는다.

**해석에 실패하면 기동 실패다. 재시도하지 않는다.** 이것은 [`spec.md`](spec.md) FR-13 의
실패 코드가 아니다. 연결 시도를 시작하지도 못한 것이라 `ERROR` 한 줄과 0 이 아닌 종료
코드로 끝나고, 세션이 없으므로 로컬 기록 파일에도 줄이 생기지 않는다
([`architecture.md`](architecture.md) 9장). **이름이 풀린 뒤 서버가 응답하지 않는 것은
다르다.** 그것은 요청 실패이고 8.3 대로 `CONTROL_PLANE_EXCHANGE_FAILED` 다. 경계는 "요청을
보낼 주소를 얻었는가" 다.

**연결은 요청마다 새로 연다** (3.3). 재사용하지 않는다.

### 8.3 오류 분류와 재시도

`[control]` 이 `[loop]` 에 돌려주는 결과는 셋 중 하나다.

| 결과 | 무엇 | 예 |
|------|------|-----|
| 성공 | `ok: true` 응답 | 연산 결과 |
| 확정 오류 | `ok: false` 이고 `error` 가 일시 오류가 아님 | `room_not_found`, `room_full`, `unauthorized`, `bad_request`, `rate_limited` |
| 일시 오류 | 전송 오류(3.5), `internal`, `unavailable` | connect 타임아웃, 500, 503 |

**재시도를 판단하는 것은 `[loop]` 다.** `[control]` 은 한 번의 요청을 보내고 결과를 응답 큐에
넣을 뿐이다([`architecture.md`](architecture.md) 3.2.8). 재시도 횟수와 1초 간격 타이머는
`[loop]` 가 세션 상태 옆에 들고, 재시도할 때 요청 큐에 같은 요청을 다시 넣는다. 그래야
`[control]` 이 "유일한 상태는 해석된 서버 주소" 라는 그 절의 규칙을 지킨다.

**재시도는 일시 오류에만, 그리고 연산마다 규칙이 다르다.**

| 연산 | 일시 오류 시 |
|------|--------------|
| `create_room`, `join_room` 새 참가 | **같은 `client_nonce` 로** 1초 간격, **첫 시도를 포함해 총 3회**. 넘기면 `CONTROL_PLANE_EXCHANGE_FAILED` |
| `join_room` 재참가 | 같은 `room_id`, `peer_id`, `peer_token` 으로 1초 간격, 첫 시도를 포함해 총 3회. 서버 쪽 동작이 멱등해서(후보 비우기) nonce 가 필요 없다 |
| `register_candidate` | 1초 간격, 첫 시도를 포함해 총 3회. 교체 의미(4.4)라 재시도가 안전하다 |
| `get_peers` | **재시도 규칙이 따로 없다.** 다음 폴링이 곧 재시도다. 폴링 간격과 마감은 [`protocol.md`](protocol.md) 11장 |

확정 오류는 재시도하지 않고 즉시 `CONTROL_PLANE_EXCHANGE_FAILED` 다. **`rate_limited` 도 확정 오류다.** 클라이언트가 스스로 기다렸다 다시 하면, 같은 NAT 뒤의 정상 클라이언트 여럿이 동시에 물러나고 동시에 몰려와 다시 걸린다. 사람이 다시 시작한다.

`CONTROL_PLANE_EXCHANGE_FAILED` 로 끝나는 조건의 목록은 [`protocol.md`](protocol.md) 9.6 이 소유한다. 이 절은 그 조건 중 "제어 평면 오류" 가 무엇인지를 펼친 것이다.

### 8.4 기동부터 펀치까지

클라이언트가 이 문서의 연산을 부르는 순서다. 타이머 값은 전부 [`protocol.md`](protocol.md) 11장 것이고 여기서는 순서만 정한다.

```text
1. 기동 입력을 읽는다 (architecture.md 3.5). 역할이 host 면 create_room, player 면 join_room
2. [control] 이 DNS 를 한 번 해석한다. 실패면 기동 실패
3. UDP 소켓 bind, getsockname (protocol.md 6장)
4. create_room 또는 join_room. 응답의 room_id 를 콘솔에 낸다 (host 는 이것을 상대에게 전한다)
5. STUN (protocol.md 13장). 두 서버에 질의한다
6. register_candidate. 로컬 후보 + 반사 후보. 8개를 넘으면 클라이언트가 먼저 자른다
7. get_peers 폴링. ready: true 이고 상대 후보가 1개 이상일 때까지 (4.5).
   **폴링 간격과 마감은 6번의 성공 응답을 받은 시점부터 센다** (protocol.md 11장)
8. 받은 후보에 10.1 위생을 다시 적용한다. 자신의 peer_id 가 보이면 CONTROL_PLANE_EXCHANGE_FAILED
9. max(0, punch_delay_ms - elapsed_since_ready_ms) 뒤 펀치 (protocol.md 10.2)
```

**4번이 5번보다 앞이다.** STUN 은 5초 마감이 있고 방 코드는 사람이 전달해야 한다. 방을 먼저 만들어 코드를 내주고 그 사이에 STUN 을 돌리면 사람이 기다리는 시간이 겹친다. 순서를 바꿔도 프로토콜은 성립하지만 사람이 더 기다린다.

**재참가는 4번의 `join_room` 형식만 다르다.** 재참가에 필요한 `peer_id` 와 `peer_token` 을 어디에 보관하는지는 기동 입력 절([`architecture.md`](architecture.md) 3.5)이 정한다.

## 9. 검증

Phase 3 의 검증 항목은 [`roadmap.md`](roadmap.md) 가 갖는다. 이 문서는 **그 항목이 돌리는 케이스 표**를 갖는다. 케이스 표는 2.1, 3.3, 4.4(후보 위생과 준비 완료 경합 둘), 5.1, 6.4, 7.4 에 있고, Phase 3 착수 시 `control-server/tests/` 로 옮겨 시험이 그 표를 직접 읽게 한다. 옮긴 뒤 이 문서는 표 대신 그 파일을 가리킨다. 문서에 표 한 벌, 시험에 한 벌을 두지 않는다.

**케이스 표마다 변이 시험을 붙인다.** 규칙 한 줄을 지운 구현이 그 표의 어느 행에서 `FAIL` 하는지 확인한다. 한 행도 떨어뜨리지 못하는 변이가 있으면 그 규칙은 아직 아무것도 지키지 않는다.

**코드를 읽어서만 판정할 수 있는 것.**

| 무엇 | 왜 동작 시험으로 안 되는가 |
|------|----------------------------|
| 저장 1 `ConsistentRead=true` | 최종 일관성 읽기도 대개 최신 값을 준다. 로컬은 더 그렇다 |
| 토큰 비교가 상수 시간이고 애플리케이션에서 먼저 한다 (6.3) | 시간 차이는 시험으로 재현하기 어렵다 |
| 판정에 `ipaddress` 술어를 쓰지 않음 (7.1) | 케이스 표 행이 우연히 통과할 수 있다 |
| `room_id` 와 `peer_token` 이 로그에 없음 (7.5) | 로그를 전부 훑어도 "어느 경로에서도 안 나온다" 는 증명이 아니다 |
| 준비 완료 판정이 `PEER#` update **뒤에** 다시 읽는가 (4.4) | 두 요청의 읽기·쓰기 순서를 밖에서 강제할 수 없다. 그냥 동시에 보내면 대개 순차로 끝나 결함이 드러나지 않는다. 4.4 케이스 표의 마지막 행을 돌리려면 store 계층에 **쓰기 직후 지연을 넣는 주입점**이 있어야 하고, 그 주입점이 있는지도 코드로 본다 |

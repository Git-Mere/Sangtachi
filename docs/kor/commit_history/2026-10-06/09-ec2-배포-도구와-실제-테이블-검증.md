# EC2 배포 도구와 실제 테이블 검증, DynamoDB 호출 설정

## 왜 했나

`plan.md` 다음에 할 일 1번이다. 제어 서버를 EC2 에 올리고 `roadmap.md` Phase 3 검증의 "배포" 묶음을
돌렸다. `control_plane.md` 7.6 이 "배포 절차를 실제로 한 번 돌린 뒤 도구로 넣고 문서는 가리킨다" 고
정했으므로 절차는 처음부터 도구로 썼고, 그 도구를 실제로 돌렸다.

## 한 것

| 무엇 | 내용 |
|------|------|
| `tools/cp-deploy/deploy.py` | 커밋된 코드만 올린다. 시스템 사용자, 릴리스 폴더, venv, 설정 파일, systemd 유닛. 이번 실행의 journal 에서 `server.started` 를 보고 연산 하나로 확인한다. 실패하면 앞 상태로 되돌린다 |
| `tools/cp-deploy/verify.py` | 배포한 서버에 연산 다섯을 돌린다. 동시 참가, 8.3 클라이언트 재시도 흉내, 용량 확인용 부하 |
| `__main__.py`, `constants.py` | 서버의 DynamoDB 호출 설정. connect 1초, read 1초, SDK 재시도 없음 |
| `control_plane.md` 2.6, 7.6, 10장 | 상수 셋, 배포 도구 가리킴, 호출 설정과 근거, 실제 테이블의 트랜잭션 충돌 실측. 10장의 미결 한 줄을 지웠다 |
| `roadmap.md` Phase 3 | 배포 작업 항목이 도구와 7.6 을 가리킨다 |

배포한 커밋은 `2cc0eef` 다. 이 커밋의 호출 설정은 아직 배포하지 않았다. 다음 커밋 기록이 그 재배포를 적는다.

## 배포 검증 결과

| 검증 항목 | 결과 | 어떻게 |
|-----------|------|--------|
| 연산 다섯이 실제 테이블에서 돈다 | 통과 | `verify.py`. `join_room` 과 `host_report` 확인이 권한 오류 없이 돌았다. IAM 의 `ConditionCheckItem` 이 있다는 뜻이다 |
| 트랜잭션 충돌 | 난다. 설계대로 흡수된다 | 넷 동시 참가를 다섯 번 돌려 20건 중 7건이 `internal`. 인스턴스에서 같은 모양의 트랜잭션을 돌려 취소 사유가 `TransactionConflict`(`ROOM` ConditionCheck) 임을 읽었다. 8.3 재시도를 흉내 내면 열 번 40건 모두 참가 |
| `elapsed_since_ready_ms` 가 재시작에도 이어진다 | 통과 | 준비 완료 뒤 서비스를 재시작했다. 값이 111ms 에서 3024ms 로, 그 사이 흐른 시간만큼 늘었다. 종료 때의 `elapsed_wall_fallback` 이 0 |
| 벽시계를 1분 당겨도 값이 뛰지 않는다 | 통과 | chrony 를 멈추고 `date -s '+60 seconds'`. 그 사이 값이 1620ms 늘었고 실제 흐른 시간은 1654ms. 시계를 되돌리고 chrony 를 다시 띄워 동기화를 확인했다 |
| CloudWatch 용량 | 대기 | 서버 역할에 CloudWatch 읽기 권한이 없다. 최소 권한이라 주지 않는다. `verify.py --soak 180` 으로 UTC 2026-10-07 02:45 ~ 02:49 에 부하를 걸었고 저장소 소유자가 콘솔에서 본다 |

서버 쪽 시간(`http.request` 의 `ms`)은 연산별 중앙값 8~118ms, 가장 긴 것이 331ms(`host_report`)였다. 이
값이 호출 설정의 근거다.

## 처음 돌렸을 때의 실패

| 실패 | 원인 | 처리 |
|------|------|------|
| 원격 bash 가 `$'\r': command not found` | 원격 스크립트를 텍스트 모드로 넘겨 Windows 가 줄 끝을 CRLF 로 바꿨다 | 바이트로 넘긴다 |
| 서비스가 `CHDIR Permission denied` 로 계속 재시작 | `mktemp -d` 가 0700 으로 만든 릴리스 폴더 | 권한을 맞춘다 |
| 디렉터의 테이블 생성 스크립트 | 앞 커밋(`2cc0eef`)의 로컬 확인 때 이야기다. 이번에는 없다 | - |

## 호출 설정이 깬 시험

설정을 넣은 뒤 server 변이 둘이 살아남았다. 종료 시험이 "답하지 않는 저장소" 로 dispatch 를 막아 두고
멈춤 신호를 보내는데, read 시간 제한 1초가 그 막힘을 1초 만에 풀어 버려 `os._exit` 없이도 프로세스가
끝났다. 시험의 전제가 깨진 것이다. 저장소가 응답 본문을 0.3초에 한 바이트씩 흘리게 바꿔 읽기마다의
시간 제한이 걸리지 않게 했다. 그 뒤 90/90 이다. 변이 실행이 이것을 잡았고 리뷰는 잡지 못했다.

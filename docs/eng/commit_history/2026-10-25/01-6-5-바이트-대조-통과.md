# 6-5 byte comparison passes, Phase 7 closed

## Why

Of the two-device items in the `roadmap.md` Phase 7 verification, only the byte counter versus capture comparison
(test 6-5) was left. The 2026-10-22 run could not be judged, and [ADR 0032](../../decisions/0032-byte-count-check-uses-a-file-transfer.md)
changed the comparison to a 64 MiB transfer and the network to one where the two PCs' private subnets do not overlap.
It was re-measured under that condition on 2026-10-25.

## Result

A was on a phone hotspot (`10.205.170.0/24`), B on the friend's home Wi-Fi (`10.0.0.0/24`). **Pass.**

| Check | Result |
|-------|--------|
| 64 MiB transfer | `VERDICT: pass`, 97.1 s, SHA-256 match |
| dumpcap drops | 0 |
| `netstat` receive errors | 0 -> 0 |
| `tx_bytes`, `tx_datagrams` | 1,615,582 / 26,343. Equal to the capture |
| `rx_bytes`, `rx_datagrams` | 70,147,217 / 49,608. Equal to the capture |

The capture contains two `HELLO`s sent to B's private candidate. Every sequence number of the tunnel packets A sent is in
the capture. The two ranges differ, so those `HELLO`s went out through the gateway. This matches the hypothesis in ADR 0032.

An earlier run the same day had A on the home Wi-Fi, outside the network condition. Its raw data and report were
discarded. In that run the send counter was 120 bytes above the capture, and by header sequence number the three missing
datagrams were `HELLO`s to B's private candidate.

ADR 0032 "Consequences" says the decision is reopened if the difference remains on a hotspot. It did not remain, so the
decision is not reopened.
